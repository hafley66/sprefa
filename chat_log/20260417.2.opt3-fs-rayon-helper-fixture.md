## Key Insights
- **init_cursors serial expr loop is the biggest layer miss so far.** `_7_init_cursors.rs:115` drains each expr to completion before starting the next. That's why g4 is exactly 4× g1 in debug. RxJS mergeMap analogy: four independent observables should run concurrent; we're running them sequential. Parse cache + fs rayon don't even touch this because they operate inside one expr.
- The opt-level=3 block at workspace root (`/sprefa/Cargo.toml`) never applied to v2/ because v2/Cargo.toml declares `[workspace]` of its own. Verify profile changes via `cargo build --message-format=json | jq 'select(.reason=="compiler-artifact") | .profile.opt_level'` — the JSON output is the only ground truth.
- `set -o pipefail` + `grep -q` + `echo | grep` pattern trips SIGPIPE when grep short-circuits. Use here-string `<<<` instead of pipe.
- Single-repo fs rayon = no win because `Arc<Mutex<Repository>>` serializes all concurrent `.files()` on the same repo. Real fs parallelism needs multi-repo batches (or a redesigned reader that doesn't hold one mutex per repo — but that's premature).
- v1 insight (from prior explore): content-hash skip set + single tree walk per rev are the transferable wins. v1 deliberately has NO parse cache (extractors reparse every pass). That design bends when many ops×many rules hit same file in one pipeline run — which is sprf+module refactor surface.
- Cursor.slots (typed SlotKey<T>) is natural home for cross-op parsed-tree handoff inside a batch; ParseCacheReader handles cross-batch/cross-expr reuse.

## Open Questions
- Payload typing for ParsedTree: commit to `Arc<AstGrep<StrDoc<SupportLang>>>` as the RsAst/TsAst payload? Or Arc<dyn Any> stays and each op downcasts? Tied to whether AstGrep<...> is Send+Sync.
- Invalidation when buffer overlay writes: epoch counter on BufferOverlay vs per-key version bump? Epoch is simpler but invalidates everything.
- Weak<ParsedTree> vs Arc: Weak lets cache not pin memory but costs upgrade() on hit. For multi-rule one-pipeline workload, strong Arc with size cap is probably simpler.
