## Analysis

### Symbol/Scope Node Model

Stack graphs separate name resolution into two independent stacks:

1. **Symbol Stack:** Tracks which symbols we're resolving (e.g., `foo` in `A.foo`). Pushed by `PushSymbol` and `PushScopedSymbol` nodes; popped by `PopSymbol` and `PopScopedSymbol` nodes. See `/stack-graphs/src/graph.rs:559-599` (node type checks).

2. **Scope Stack:** Tracks which scopes we're searching in. Manipulated by `DropScopes` (clears top N) and `JumpTo` (jumps back to previous). Automatically populated by references to exported scopes in `PushScopedSymbol` nodes. See `/stack-graphs/src/partial.rs:150-190` (SymbolStackVariable offset model) and `/stack-graphs/src/graph.rs:750-835` (DropScopesNode/JumpToNode).

### Push/Pop Semantics

- **PushSymbol/PushScopedSymbol:** Mark a reference site. PushSymbol pushes a bare symbol; PushScopedSymbol pushes a symbol with an associated scope list (for member access). See `/stack-graphs/src/lib.rs:18-56` (conceptual docs) and `/stack-graphs/src/graph.rs:1000-1100` (node definitions).

- **PopSymbol/PopScopedSymbol:** Mark definition sites. Must match the top symbol on the stack. PopScopedSymbol additionally requires an attached scope list on the popped symbol. When `is_definition=true`, these nodes are proper definitions that can be the target of queries. See `/stack-graphs/src/graph.rs:839-950`.

- **Valid Paths:** Both stacks must be empty at path start and end. A path from reference to definition succeeds iff all push/pop/scope operations are balanced. See `/stack-graphs/src/paths.rs:1-63` (error types like `EmptySymbolStack`, `IncorrectPoppedSymbol`).

### Tree-Sitter Integration (tree-sitter-graph)

Rules are written in `.tsg` files (tree-sitter graph DSL):

1. **Node Creation:** `node my_node; attr (my_node) type = "push_symbol", symbol = (source-text @id)`. See `/tree-sitter-stack-graphs/src/lib.rs:45-95` (DSL vocabulary).

2. **Edge Creation:** `edge @src -> @dst`. Edges connect nodes; TSG evaluator ensures acyclic per-file construction.

3. **Attributes:** Type, symbol, scope, is_definition, is_reference, source_node (AST span for IDE navigation), syntax_type, definiens_node. See `/tree-sitter-stack-graphs/src/lib.rs:63-160`.

4. **Rule Files:** `/languages/tree-sitter-stack-graphs-python/src/stack-graphs.tsg`, etc. Matched against parsed syntax tree; DSL execution produces StackGraph. See `/tree-sitter-stack-graphs/examples/nested-scope/stack-graphs.tsg:1-100` (Python example with lexical scoping).

### Cross-File Resolution

**Partial Paths & Stitching:**

- Each file produces a `PartialPath` collection containing all name-binding paths that touch the file boundary (root node or jump-to node). Stored in SQLite via `bincode` serialization. See `/stack-graphs/src/storage.rs:39-67` (schema: graphs, file_paths, root_paths tables).

- At query time, `PathStitcher` loads partial paths from the database and concatenates them using the `concatenate` method. Symbol stack variables are renamed to avoid collisions. See `/stack-graphs/src/stitching.rs:74-100` (Appendable trait, variable offset).

- **ForwardCandidates trait** (`/stack-graphs/src/stitching.rs:186-200`): Allows lazy loading of partial paths. Database `load_forward_candidates` is called before processing each phase, enabling on-demand loading from disk.

- **Root & Jump Nodes:** Cross-file paths go through `root_node()` (singleton, shared across files) and `jump_to_node()` (allows resuming resolution at another scope). See `/stack-graphs/src/graph.rs:439-454`, `/stack-graphs/src/graph.rs:803-834`.

### Incremental Model

- **Per-File Analysis:** Each file's partial paths are computed independently; no inter-file dependencies during extraction. See `/stack-graphs/src/partial.rs:1-35` (conceptual overview).

- **Partial Path Storage:** Pre-stitched at index-time; keyed by file + local_id (for file_paths) or symbol_stack (for root_paths). Indexed by `symbol_stack` for root paths to enable fast lookup. See `/stack-graphs/src/storage.rs:44-60` (index definitions).

- **Query-Time Stitching:** Partial paths loaded on-demand; concatenation is fast (variable unification only). Multi-phase stitching for large repos. See `/stack-graphs/src/stitching.rs:1-36` (conceptual docs on lazy loading).

- **Limitation:** Changes to a single file require re-indexing that file only; downstream files' partial paths remain valid (only their reference points may change). Inverse: upstream changes require re-indexing downstream files that import them.

### Call Resolution

**Important:** Stack graphs do NOT directly output call graphs. They perform **name resolution only**. To build a call graph:

1. Extract all references marked `is_reference=true` (e.g., function calls).
2. For each reference, query the database to find all possible definitions.
3. Build edges (caller → callee) from the results.

See `/tree-sitter-stack-graphs/src/cli/query.rs:49-150` (Definition query shows how references are resolved to definitions, not calls to callees).

### Storage Format

- **In-Memory (Runtime):** Arena-based allocation in `StackGraph` struct (`/stack-graphs/src/graph.rs:1478-1493`). Symbols, files, nodes, and edges live in arenas; no deletion (batch drop only).

- **Serialized (Disk):** SQLite + bincode. PartialPath instances are bincode-encoded. Per-file partial paths indexed by (file, local_id); root paths indexed by symbol_stack. See `/stack-graphs/src/storage.rs:149-200` (SQLiteWriter API).

### Unique Features

1. **Scope Stack Variables:** Enable symbolic binding of scopes across file boundaries without materializing the full graph. Key to incrementality. See `/stack-graphs/src/partial.rs:150-184`.

2. **Exported Scope Nodes:** Allow resolving field/member access (`A.foo`) by nesting scope queries. PushScopedSymbol pushes a scope list when a symbol resolves to a type. See `/stack-graphs/src/lib.rs:109-122`.

3. **Multi-Phase Stitching:** Database processes paths in phases; each phase can trigger loading of new candidates. Supports repositories with many inter-dependencies. See `/stack-graphs/src/stitching.rs:14-34`.

4. **No Rebuild on Downstream Changes:** Because partial paths are pre-computed per-file, changing a downstream dependency does not force re-indexing of upstream files (only queries change scope).
