## Problem/Context
The reference engine (v6/prolog/conformance/engine.pl) rebuilt two whole-store
views per OCCURRENCE, not per write. golden-flex many: 4,355 occurrences over a
~1,074-row store, of which only 851 occurrences write anything.

## Solution/Approach
Measure, change, measure, and PRICE a fix before building it. Four changes
landed in e3a103ce, two more were built, measured at zero, and backed out.

Landed:
  1. store_view/4 memo. Visible and PreState are a pure function of the store,
     so they are carried through the occurrence recursion and rebuilt only when
     `==/2` says the store TERM changed (O(1) on identical pointers).
     5.63s -> 3.76s. The single biggest win of the session.
  2. store_rows/2 from findall+member to a two-clause first-argument-indexed
     recursion. Its bag was 4,704,007 of the run's 5,187,990 findall bag adds.
     7.02s -> 5.78s.
  3. trigger_items/2 hoisted out of the occurrence loop (a property of the rule,
     not the occurrence). Priced by adding it back: 0.18s / 0.22s.
  4. oracle_dump.pl final_state_line/2: one findall over FinalAll per rel name,
     55 rels x ~3,800 rows. keysort + group_pairs_by_key. ~0.1s.

Backed out, in the commit body so nobody re-tries them:
  - Open-tail accumulator to make the occurrence loop last-call, on the theory
    that 4,355 live frames each holding two whole-store lists was the cost.
    5.81s vs 5.78s. The frames were not the cost.
  - A trigger-ref prefilter testing the occurrence's Name/Arity against the
    rule's items BEFORE copying. Worked exactly as designed (56,615 copy_term/2
    calls -> 1,234) and bought nothing (3.74s vs 3.76s). copy_term shares ground
    subterms, so copying a rule is nearly free.

## Key Insights
- **The SWI sampling profiler lies about built-ins, by ~70x.** It charged is/2
  0.54s (13% of the run) for 26,303 calls; the same 26,303 integer operations
  run standalone in 0.0077s. member_/3's 1.65s (39%) is the same illusion:
  stubbing out 35% of its steps (both whole-store scans) moved the wall clock
  3.76s -> 3.69s. Sampling attribution survives as a POINTER to shapes worth
  looking at, never as a cost. Wall-clock stubbing is the instrument.
- **Price a fix before building it.** apply_edge_writes/6 scans the whole store
  per keyed write (456,348 member steps) and next_seq/3 does the same per log
  write (80,361). Both look exactly like the polynomial the session was hunting.
  Stubbing both: 0.07s. A keyed assoc index threaded through six predicates was
  designed and then not written, on that number.
- **The memo pattern that keeps paying: a view guarded by ==/2 on the term it
  derives from.** Pure function of the store + identity guard = no drift risk,
  no duplicated state, no invalidation protocol. That is what took the occurrence
  loop from 4,355 rebuilds to 851, and it is the shape to reach for before
  reaching for an index.
- **The counter harness (wrap_predicate/4) answers "what shape", the clock
  answers "what cost".** rel_ref/2 at 1,013,060 calls / 108,988 solutions was a
  genuine filter-driven-as-search and fixing it was worth 0.1s. Chasing call
  counts alone would have burned the session on a 2% win.
- Caller attribution: prolog_frame_attribute frame-climbing inside the wrapper
  is too slow to finish a run (timed out at 2m). Use
  profile_procedure_data/2 + get_dict(callers, D, Cs) instead. NOTE: dict
  functional notation (`D.callers`) does NOT expand inside a `-g` goal; it reads
  as a literal term and silently fails the goal. get_dict/3 or nothing.
- Oracle time now: 0.12s load, 0.26s parse+schedule, 3.27s ticks, 0.11s render.
  The ticks are 159,414 derivations across 116 fixpoint iterations (2.7 per
  call), which is the fixture's real join size. Semi-naive would buy little at
  2.7 iterations, and a reference engine is the wrong place for it anyway.
