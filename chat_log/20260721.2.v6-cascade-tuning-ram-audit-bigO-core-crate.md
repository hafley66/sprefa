## RAM AUDIT (user catch: "aren't we taking RAM from sqlite while saying rust is fine")
- memcap `#[global_allocator]` (CappedAlloc wraps System) sees ONLY Rust GlobalAlloc.
  SQLite = bundled C, mallocs via C allocator — INVISIBLE to memcap. DL_MEMCAP_MB
  bounds Rust heap only.
- Added libsqlite3-sys dev-dep -> read sqlite3_memory_highwater; DL_SQLITE_HEAP_MB
  -> PRAGMA hard_heap_limit. Measured: retract SQLite C-heap = **54.5MB @5M**, grows
  38->44->54 over 1M->5M nodes = WAVEFRONT-bounded, not corpus. Retract completes
  correctly under 80/128MB hard_heap_limit; :memory: fails at 128MB. Wall holds on
  SQLite's OWN allocator.
- Fixed 2 hidden-RAM bugs: (1) survivor dump sorted a computed expr forcing ~250MB
  C-heap sort -> use `key` (rowid) = no-sort; (2) survivors was out.len() over 4.5M
  materialized rows -> scalar count(*) (correct under any cap).
- CAVEAT: hard_heap_limit corrupts SILENTLY past cap (sqlx swallows NOMEM, partial
  rows). Measurement tool, not guardrail. dd/dbsp are pure Rust so memcap fully
  covers them — comparison is honest.

## Big-O of retract (user asked, with receipts)
- Axis 1 (grow width, n & delta together): 2x delta -> 2x time (LINEAR); us/killed
  2.62->2.88 over 8x n = weak log(n).
- Axis 2 (grow depth/layers, delta FIXED 100k): 5x corpus (400k->2M) -> retract
  FLAT 270->273ms. Untouched corpus costs nothing.
- **VERDICT: retract = O(delta * log n_hot) ~= O(delta)**. Setup is O(n).
