# sprefa extractor architecture + type system design

**Date:** 2026-04-11
**Prior work:**
- `20260411.1.call-tree-survey-plan.md` — the 12-tool survey plan
- `20260411.4.call-tree-survey-raw-NN-*.md` — 12 raw per-tool reports
- `20260411.5.call-tree-survey-matrix.md` — comparison matrix + four-axis findings
**This file:** design sketch that falls out of the survey, covering extractor architecture, fact schema, type system with Lodash-style path enumeration, and per-language tooling choices.

---

## Goals (from the conversation)

1. Cross-language static code intelligence with a generic relational schema and a datalog-to-SQL query surface (sprefa differentiator).
2. AST as the base for 90% of extraction, regex for narrow post-filtering, statistical techniques for fuzzy ranking only.
3. Capture: classes, functions, args, return counts, consts, imports, exports, visibility flags, string constants, file/folder tree, and types (with Lodash-style path enumeration).
4. Pluggable extractor trait so adding a new language is a trait impl, not a schema change.
5. Integrate existing tools (from the 12-tool survey) as external adapters where useful, so sprefa can consume their output as fact rows tagged by `source`.
6. Explicit per-language configuration knobs (PYTHONPATH vomit, tsconfig paths, GOFLAGS, cfg flags, include dirs, defines).

---

## The capture targets — green field vs claimed

| Capture | State across the 12 peers |
|---|---|
| entity kinds (function, class, method, const) | all 12 capture some subset, none normalize |
| function signatures with args + return | ~4 capture as structured rows (graph-sitter, rust-analyzer, codebase-memory-mcp, ACER), rest as signature blobs |
| return counts | none capture structurally (Go multi-return, Python tuple unpack) |
| visibility flags normalized | graph-sitter partially, nobody fully |
| imports / exports | all capture imports, most capture exports for JS family, nobody normalizes across languages |
| string constants | only codebase-memory-mcp (for URL classification), rest drop on floor |
| file/folder tree as queryable facts | codebase-memory-mcp (CONTAINS_*) and codedb (FileOutline), rest walk and forget |
| named types | rust-analyzer (full HIR, Rust only), graph-sitter (Python/TS partial) |
| field-level type tracking | rust-analyzer (HIR), nobody else |
| Lodash-style path enumeration over types | **nobody** |

**Four capture dimensions are green field:** type paths, normalized visibility, string constants, file tree as queryable facts.

## Fact schema (v0 sketch)

Every fact row carries `source TEXT` identifying which extractor produced it. Multiple extractors can produce the same logical fact for the same location; queries filter or union across sources.

### Core entities + files

```sql
CREATE TABLE files (
  id INTEGER PRIMARY KEY,
  rel_path TEXT NOT NULL UNIQUE,
  content_hash TEXT NOT NULL,           -- sha256 or xxhash
  language TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  last_extracted_at INTEGER,            -- unix epoch
  is_vendored INTEGER NOT NULL DEFAULT 0,
  is_generated INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE file_tree (
  path TEXT PRIMARY KEY,                -- rel_path
  parent_path TEXT,
  kind TEXT NOT NULL,                   -- file | dir
  language TEXT,                        -- NULL for dirs
  depth INTEGER NOT NULL                -- segments from repo root
);

CREATE TABLE entities (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id),
  kind TEXT NOT NULL,                   -- function | method | class | interface | struct
                                        -- enum | union | trait | impl | const | var
                                        -- type_alias | module | namespace
  name TEXT NOT NULL,
  qualified_name TEXT NOT NULL,
  parent_entity INTEGER REFERENCES entities(id),
  visibility TEXT,                      -- public | private | protected | internal | package
                                        -- (normalized 5-value domain)
  start_byte INTEGER NOT NULL,
  end_byte INTEGER NOT NULL,
  start_line INTEGER NOT NULL,
  is_exported INTEGER NOT NULL DEFAULT 0,
  is_default_export INTEGER NOT NULL DEFAULT 0,
  is_static INTEGER NOT NULL DEFAULT 0,
  is_abstract INTEGER NOT NULL DEFAULT 0,
  source TEXT NOT NULL
);
```

**Visibility normalization:** Rust `pub(crate)`, Java `protected`, TS `private`, Python `_name`, Go lowercase-leading-letter all collapse into one of five values. Each extractor owns its local-to-global mapping. Queries get a uniform column without knowing the source language.

### Imports, exports, string literals

```sql
CREATE TABLE imports (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id),
  local_name TEXT,                      -- alias in this file
  module_path TEXT NOT NULL,            -- raw module specifier
  resolved_file_id INTEGER REFERENCES files(id),  -- resolved target, NULL when external
  is_wildcard INTEGER NOT NULL DEFAULT 0,
  is_type_only INTEGER NOT NULL DEFAULT 0,
  is_dynamic INTEGER NOT NULL DEFAULT 0,
  source TEXT NOT NULL
);

CREATE TABLE exports (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id),
  exported_name TEXT NOT NULL,
  local_entity_id INTEGER REFERENCES entities(id),
  is_default INTEGER NOT NULL DEFAULT 0,
  is_reexport INTEGER NOT NULL DEFAULT 0,
  reexport_source TEXT,
  source TEXT NOT NULL
);

CREATE TABLE string_literals (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id),
  enclosing_entity INTEGER REFERENCES entities(id),
  ordinal INTEGER NOT NULL,             -- DFS pre-order within enclosing entity
  start_byte INTEGER NOT NULL,
  end_byte INTEGER NOT NULL,
  value TEXT NOT NULL,                  -- literal content, quotes stripped
  kind TEXT NOT NULL,                   -- string | template | raw | bytes | char | regex
  is_template_with_interpolation INTEGER NOT NULL DEFAULT 0,
  source TEXT NOT NULL
);
```

String literals as first-class rows enable:
- URL/path detection inside string values via regex post-filter
- Configuration key extraction (env vars, feature flags) via pattern match
- Embedded SQL / JSX / shell fragment detection for nested analysis
- Documentation-reference linking

Only codebase-memory-mcp captures this among the 12, and only as internal state for its HTTP classification pass. Elevating to a first-class table unlocks general queryability.

### Call sites (the thing the whole survey was about)

```sql
CREATE TABLE call_sites (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id),
  enclosing_entity INTEGER NOT NULL REFERENCES entities(id),
  ordinal INTEGER NOT NULL,             -- DFS pre-order inside enclosing entity
  branch_path TEXT NOT NULL DEFAULT '', -- "if[0].then", "for[1].body", empty string = top-level
  start_byte INTEGER NOT NULL,
  end_byte INTEGER NOT NULL,
  start_line INTEGER NOT NULL,
  callee_text TEXT NOT NULL,            -- raw name as it appears in source
  callee_entity INTEGER REFERENCES entities(id),   -- set when scope resolution succeeds
  callee_kind TEXT,                     -- function | method | constructor | macro | dynamic
  receiver_type_id INTEGER REFERENCES types(id),   -- for method calls
  is_awaited INTEGER NOT NULL DEFAULT 0,
  arg_count INTEGER NOT NULL,
  source TEXT NOT NULL
);

CREATE INDEX idx_call_sites_enclosing ON call_sites(enclosing_entity, ordinal);
CREATE INDEX idx_call_sites_callee_entity ON call_sites(callee_entity);
CREATE INDEX idx_call_sites_callee_text ON call_sites(callee_text);
```

`ordinal` + `branch_path` are the two columns no peer tool exposes at the storage layer. They make source-order and branch-context queryable via SQL, which is sprefa's load-bearing differentiator over the 12-tool field.

### Function signatures + params

```sql
CREATE TABLE function_signatures (
  id INTEGER PRIMARY KEY,
  entity_id INTEGER NOT NULL UNIQUE REFERENCES entities(id),
  type_id INTEGER REFERENCES types(id),  -- function_sig type, enables path queries over sigs
  return_type_id INTEGER REFERENCES types(id),
  return_type_text TEXT,
  return_count INTEGER NOT NULL DEFAULT 1,    -- Go multi-return, Python tuple, Rust (T, U)
  is_async INTEGER NOT NULL DEFAULT 0,
  is_generator INTEGER NOT NULL DEFAULT 0,
  is_const INTEGER NOT NULL DEFAULT 0,        -- Rust const fn, C++ constexpr
  source TEXT NOT NULL
);

CREATE TABLE function_params (
  id INTEGER PRIMARY KEY,
  signature_id INTEGER NOT NULL REFERENCES function_signatures(id),
  ordinal INTEGER NOT NULL,
  name TEXT,                            -- nullable, C/Go allow unnamed
  param_type_id INTEGER REFERENCES types(id),
  param_type_text TEXT NOT NULL,
  is_variadic INTEGER NOT NULL DEFAULT 0,
  is_optional INTEGER NOT NULL DEFAULT 0,
  has_default INTEGER NOT NULL DEFAULT 0,
  default_text TEXT,
  source TEXT NOT NULL,
  UNIQUE(signature_id, ordinal)
);
```

`return_count` handles Go's `func f() (string, error)` and Python's `def f() -> tuple[int, str]` and Rust's `fn f() -> (T, U)` under one column. Extractors set it from the language's tuple/multi-return idiom.

## Type system — the Lodash-path layer

Three tables: `types`, `type_fields`, `type_paths`. The last is the payoff that no peer tool provides.

```sql
CREATE TABLE types (
  id INTEGER PRIMARY KEY,
  file_id INTEGER REFERENCES files(id),   -- NULL for primitives and externals
  name TEXT NOT NULL,
  qualified_name TEXT,
  kind TEXT NOT NULL,
    -- class | interface | struct | enum | enum_variant
    -- type_alias | primitive | generic_param
    -- function_sig | tuple | union | intersection
    -- array_of | map_of | optional_of | literal
  is_anonymous INTEGER NOT NULL DEFAULT 0,
  parent_type_id INTEGER REFERENCES types(id),  -- extends, impl trait
  generic_args TEXT,                        -- JSON array of type_ids for instantiations
  language TEXT NOT NULL,
  source TEXT NOT NULL,
  UNIQUE(qualified_name, language, source)
);

CREATE TABLE type_fields (
  id INTEGER PRIMARY KEY,
  owner_type_id INTEGER NOT NULL REFERENCES types(id),
  name TEXT NOT NULL,                   -- "0", "1" for tuple positions
  ordinal INTEGER NOT NULL,
  field_type_id INTEGER REFERENCES types(id),
  field_type_text TEXT NOT NULL,        -- always populated
  is_optional INTEGER NOT NULL DEFAULT 0,
  is_readonly INTEGER NOT NULL DEFAULT 0,
  is_static INTEGER NOT NULL DEFAULT 0,
  visibility TEXT,
  source TEXT NOT NULL
);

CREATE TABLE type_paths (
  id INTEGER PRIMARY KEY,
  root_type_id INTEGER NOT NULL REFERENCES types(id),
  path TEXT NOT NULL,                   -- "profile.address.city" dot-joined
  depth INTEGER NOT NULL,
  leaf_type_id INTEGER REFERENCES types(id),
  leaf_type_text TEXT NOT NULL,
  has_array_segment INTEGER NOT NULL DEFAULT 0,
  has_optional_segment INTEGER NOT NULL DEFAULT 0,
  has_anonymous_segment INTEGER NOT NULL DEFAULT 0,
  traverses_cycle INTEGER NOT NULL DEFAULT 0,
  source TEXT NOT NULL
);

CREATE INDEX idx_type_paths_root_depth ON type_paths(root_type_id, depth);
CREATE INDEX idx_type_paths_leaf ON type_paths(leaf_type_id);
CREATE INDEX idx_type_paths_path ON type_paths(path);
```

### Path enumeration algorithm

Runs once per root type at extraction end, after `types` and `type_fields` are populated.

```rust
fn enumerate_paths(
    types: &TypeTable,
    root: TypeId,
    max_depth: usize,
    skip_anonymous: bool,
) -> Vec<TypePathRow> {
    let mut out = Vec::new();
    let mut stack: Vec<(TypeId, Vec<Segment>, BitSet)> =
        vec![(root, vec![], BitSet::new())];

    while let Some((current, segments, visited)) = stack.pop() {
        for field in types.fields_of(current) {
            let mut new_segments = segments.clone();
            new_segments.push(Segment {
                name: field.name.clone(),
                is_optional: field.is_optional,
                is_array: types.is_array_like(field.field_type_id),
                is_anonymous: field
                    .field_type_id
                    .map_or(false, |id| types.is_anonymous(id)),
            });

            out.push(TypePathRow {
                root_type_id: root,
                path: new_segments.iter().map(|s| s.name.as_str()).join("."),
                depth: new_segments.len() as i32,
                leaf_type_id: field.field_type_id,
                leaf_type_text: field.field_type_text.clone(),
                has_array_segment: new_segments.iter().any(|s| s.is_array),
                has_optional_segment: new_segments.iter().any(|s| s.is_optional),
                has_anonymous_segment: new_segments.iter().any(|s| s.is_anonymous),
                traverses_cycle: false,
            });

            if new_segments.len() >= max_depth { continue; }
            let Some(next_id) = field.field_type_id else { continue };

            if visited.contains(next_id) {
                let mut cycle_row = out.last().unwrap().clone();
                cycle_row.traverses_cycle = true;
                out.push(cycle_row);
                continue;
            }
            if skip_anonymous && types.is_anonymous(next_id) { continue; }
            if types.is_primitive(next_id) { continue; }

            let mut new_visited = visited.clone();
            new_visited.insert(next_id);
            stack.push((next_id, new_segments, new_visited));
        }
    }
    out
}
```

Properties:
- **Cycle-safe** via BitSet visited set
- **Bounded** by `max_depth` (5-10 typical)
- **Skips primitives** during recursion (no fields worth exploring)
- **Emits every prefix** so `user.profile`, `user.profile.address`, `user.profile.address.city` are three separate rows, queryable at any depth
- **Flag columns** (`has_array_segment`, `has_optional_segment`, `has_anonymous_segment`, `traverses_cycle`) let queries carve out subsets without re-enumerating

### Anonymous type handling (TypeScript's inline-type chaos)

Three-stage approach:

1. **Named types** emit rows with `is_anonymous=0` unconditionally.
2. **Inline types** encountered during extraction (TS `{a: string, b: number}` in a param position) have two representation options:
   - **Synthesize a row** with `is_anonymous=1`, a dummy name like `User_foo_param0_anon`, and field rows derived from the inline shape. Pros: path enumeration can traverse through them. Cons: type table pollution.
   - **Text-only** via `param_type_id=NULL` and `param_type_text="{a: string, b: number}"`. Pros: clean type table. Cons: path enumeration stops at the anonymous boundary.
3. **Query-time knob** via `skip_anonymous`: path enumeration traverses or skips anonymous types based on config. Queries then filter on `has_anonymous_segment`.

Default policy: synthesize anonymous types as rows for completeness, and let queries filter them out via `has_anonymous_segment=0` when the user wants "flat proper people types." The clean-type view stays one WHERE clause away from the full view.

### Function signatures participate in path enumeration

Represent function sigs as `types` rows with `kind='function_sig'`. Populate `type_fields` for each parameter (name = param name, ordinal = position) plus a synthetic `_return` field (name = `_return`, ordinal = -1 or a sentinel).

With this representation:
- `handler.onEvent` (a field whose type is a function_sig)
- `handler.onEvent.event` (param named `event`)
- `handler.onEvent.event.payload` (into the param type)
- `handler.onEvent._return.status.code` (through the return type)

All queryable through the same `type_paths` table. Function signatures become first-class citizens in the type graph, same as struct fields.

## Extractor architecture

### Trait

```rust
#[derive(Debug, Clone)]
pub enum ExtractionCost {
    PerFile,                             // runs in the walker loop, one call per file
    PerRepo,                             // runs once with all files visible
    External { bin: PathBuf },           // subprocess, output cached by repo-state hash
}

pub struct ExtractCtx<'a> {
    pub repo_root: &'a Path,
    pub cache_dir: &'a Path,
    pub lang_config: &'a LangConfig,
    pub max_type_path_depth: usize,
    pub skip_anonymous_type_paths: bool,
}

pub struct LangConfig {
    pub python_paths: Vec<PathBuf>,
    pub python_src_layout: bool,
    pub tsconfig_path: Option<PathBuf>,
    pub ts_base_url: Option<PathBuf>,
    pub ts_paths: HashMap<String, Vec<String>>,
    pub go_mod_cache: Option<PathBuf>,
    pub go_build_tags: Vec<String>,
    pub rust_cfg_flags: Vec<String>,
    pub cpp_include_dirs: Vec<PathBuf>,
    pub cpp_defines: Vec<String>,
    // new languages add fields here
}

pub struct Facts {
    pub files: Vec<FileFact>,
    pub entities: Vec<EntityFact>,
    pub function_signatures: Vec<FunctionSignatureFact>,
    pub function_params: Vec<FunctionParamFact>,
    pub call_sites: Vec<CallSiteFact>,
    pub imports: Vec<ImportFact>,
    pub exports: Vec<ExportFact>,
    pub string_literals: Vec<StringLiteralFact>,
    pub types: Vec<TypeFact>,
    pub type_fields: Vec<TypeFieldFact>,
    pub type_paths: Vec<TypePathFact>,
    pub file_tree: Vec<FileTreeFact>,
    pub extras: HashMap<String, Vec<serde_json::Value>>,
}

pub trait Extractor: Send + Sync {
    fn name(&self) -> &'static str;
    fn languages(&self) -> &[Language];
    fn cost(&self) -> ExtractionCost;

    fn extract_file(&self, ctx: &ExtractCtx, file: &SourceFile) -> Result<Facts> {
        Err(anyhow!("{}: not a PerFile extractor", self.name()))
    }

    fn extract_repo(&self, ctx: &ExtractCtx, files: &[SourceFile]) -> Result<Facts> {
        let mut all = Facts::default();
        for f in files {
            if self.languages().contains(&f.language) {
                all.merge(self.extract_file(ctx, f)?);
            }
        }
        Ok(all)
    }
}
```

### Composition model

- **Multiple extractors can run on the same file.** Each writes into the same tables, distinguished by the `source` column.
- **Queries filter or union across sources.** "call sites where any extractor found them" vs "call sites where oxc and cymbal agree" vs "call sites only cymbal found" (likely false positives).
- **Cost tier determines scheduling.**
  - `PerFile` runs inside the file walker loop, in parallel across files.
  - `PerRepo` runs once with all files visible (needed for cross-file resolution in stack-graphs, ra_ap_ide, etc.).
  - `External` runs out-of-band, output cached by a hash of (repo state, extractor config). Re-runs only when the cache key changes.
- **Base walker always runs first**, populating `files`, `file_tree`, lexical `string_literals`, lexical `imports` / `exports`. Extractors layer on top.

## Extractor roster (10-12 impls)

### Heavyweight per-language (band 2+, in-process Rust)

1. **OxcExtractor** — JS / TS / TSX / JSX via `oxc_parser`, `oxc_semantic`, `oxc_resolver`. Built-in name resolution, module resolution (tsconfig paths, baseUrl, Node module resolution). Highest leverage per impl because it covers the whole JS family with real semantics.

2. **RuffPyExtractor** — Python via `ruff_python_parser` or `rustpython_parser`. AST only; scope resolution is a custom walker driven by PYTHONPATH config. Handles type annotations directly from the CST. Falls back to text-only type fields when annotations are absent.

3. **SynRustExtractor** — Rust via `syn`. Structure, generics, traits, lifetimes, all from the CST. Type paths over `Struct` and `Trait` defs. Does not resolve trait impls or generic method dispatch; that lives in the opt-in ra_ap_ide extractor.

4. **GoExtractor** — Go via `tree-sitter-go` + custom scope walker. Handles struct fields, interface method sets, receiver types. Subprocess `go list` for module resolution when needed.

5. **TreeSitterUniversalExtractor** — one impl that dispatches across 20+ languages via per-language `.scm` query files. Covers Ruby, Java, Kotlin, PHP, Swift, Lua, Bash, Elixir, Scala, C#, Dart, etc. Each language gets a ~100-line `.scm` file for entity / call / import / type queries. Total code surface ~2k Rust lines plus 20+ small query files.

### Opt-in band-3 (heavyweight subprocess or external)

6. **RaApIdeExtractor** — Rust semantic, wraps `ra_ap_ide` crate. Users enable for full Rust type resolution, method dispatch through traits, macro expansion. Slow, correct, worth it for Rust-heavy work.

7. **ClangdExtractor** — C / C++ / Objective-C via clangd LSP subprocess. Preprocessor expansion, template instantiation, inclusion graph. The only way to get real semantic C++ without reinventing a C++ frontend.

8. **GoplsExtractor** — Go semantic via gopls LSP subprocess. Cross-module type resolution, interface satisfaction tracking.

### External adapters (wrap surveyed tools)

9. **CymbalAdapter** (~300 LOC) — runs `cymbal index`, reads its SQLite, maps symbols+refs to entities+call_sites, uses cymbal's EnclosingSymbol query for `enclosing_entity`.

10. **SemAdapter** (~200 LOC) — runs `sem entities --json`, parses output, maps EntityRefs to sprefa entities. 22 languages from one subprocess.

11. **CbmAdapter** (~400 LOC) — runs `codebase-memory-mcp cli index_repository`, reads the project SQLite at `~/.cache/codebase-memory-mcp/{project}.db`, maps nodes/edges into sprefa tables. 66 languages when the project needs the long tail.

### Base pass (always runs)

12. **BaseFileWalker** — file discovery (`.gitignore` aware), content hashing, language detection, file tree emission, universal string literal extraction, lexical import/export extraction. Runs before any specific extractor. Uses tree-sitter generically for 30+ languages via a shared set of queries.

Total extractor code surface: ~15-20k Rust lines, most of it in the heavyweight per-language impls. Adding a new tree-sitter language is one `.scm` file plus a Language enum variant. Adding a new heavyweight is ~1-2k lines. Adding a new external adapter is ~200-400 lines.

## AST vs regex vs statistical techniques

### AST — the default, ~90% of facts

Tree-sitter or native parser is the load-bearing extraction mechanism. Everything structured: entities, call sites, type declarations, function signatures, imports, exports, visibility modifiers, string literals as nodes, class inheritance, trait impls. Both band 1 (lexical name capture) and band 2 (scope-resolved) facts come from AST walks.

Choice per language: native parser (oxc, syn, ruff) where a good Rust-native one exists, tree-sitter otherwise. Tree-sitter is the universal fallback because of grammar coverage breadth.

### Regex — narrow supplementary role, three use cases

1. **Pre-AST detection**: file type from extension + shebang, encoding sniff, minified-file detection (average line length heuristic), vendored-file detection (path patterns like `vendor/`, `node_modules/`, `third_party/`). Runs before any parser is loaded.

2. **Post-AST filter over string literals**: URL detection inside a string literal, API path patterns, framework marker strings (`__tests__`, `.spec.`, `@pytest.mark`), environment variable names, embedded SQL fragments. The string itself comes from AST extraction; regex operates on its content.

3. **Unstructured text files**: config formats thin enough that a grammar is overkill. Dockerfile variants, .env files, some Makefile syntax. Used as a fallback for files where tree-sitter grammar coverage is weak.

Regex lives at the extractor layer as helper functions. When used standalone it shows up in fact rows as `source='regex'`. When used as a filter over AST-sourced data, it piggybacks on the originating source.

### Statistical — three specific bands

1. **Fuzzy rename detection**: sem's model, structural hash + token-overlap similarity. Detects cosmetic changes vs real rewrites between revisions. Deterministic, no training, runs over entity tables.

2. **Classification confidence scoring**: when cross-file resolution has multiple candidates, rank them. codebase-memory-mcp's static heuristics (import_map 0.95, same_module 0.90, suffix_match 0.70) set the precedent. The slot exists for Bayesian ranking based on call-site context.

3. **Partial type inference for dynamic languages**: Python / Ruby / JS type inference where no annotations exist. Out of scope for sprefa v1. The escape hatch: subprocess mypy / pyright / Flow as an External extractor and consume their output.

Statistical techniques sit **above** the deterministic AST layer. They never produce base facts; they produce scores and confidence values that annotate existing facts. Interface: `confidence FLOAT` column on `call_sites` and `type_fields`.

## What the 12 surveyed tools do about each capture dimension

Compact answers per dimension, one row per tool. "Partial" means some coverage, "nope" means none.

### Type tracking beyond entity kind

| Tool | Named types | Field level | Paths |
|---|---|---|---|
| sem | kind column only | nope | nope |
| cymbal | kind in symbols | nope | nope |
| grepai | kind + Go receiver | nope | nope |
| codebase-memory-mcp | Type label nodes, USES_TYPE edges, Go/C/C++ type inference | nope | nope |
| CodeRLM | kind + signature blob | nope | nope |
| codedb | kind field | nope | nope |
| SocratiCode | file-level only | nope | nope |
| tree-sitter-codeviews | symbol table with types | nope | nope |
| graph-sitter | Python + TS function params, return, inheritance | partial | nope |
| ACER | param count + FullType for disambiguation | nope | nope |
| rust-analyzer | **full HIR** (Rust only) | yes | nope |
| stack-graphs | name binding paths, not type paths | nope | nope |

Nobody enumerates Lodash-style paths. rust-analyzer is the only tool with a proper type system, and it's Rust-only and heavyweight. graph-sitter is second-best on structural typing for Python + TS.

### Visibility flags normalized across languages

Nobody. graph-sitter tracks visibility partially for Python + TS. codebase-memory-mcp has implicit conventions (Python underscore prefix) without a real flag. Every other tool ignores the dimension.

### String constants as queryable facts

Only codebase-memory-mcp extracts them (`CBMStringRef` arrays), and only as internal state for its HTTP classification pass. It's not exposed in its SQLite schema as a general-purpose table. Every other tool drops string literals on the floor. Elevating this to a first-class table is free once the AST walk is happening.

### File / folder tree as facts

codebase-memory-mcp (CONTAINS_FOLDER, CONTAINS_FILE edges) and codedb (FileOutline hierarchy) are the only two. Everyone else walks files and forgets the tree.

### Imports / exports

All tools capture imports. Most capture exports for JS-family. Nobody normalizes across languages into a uniform schema; each tool has per-language regex or AST dispatch with its own row shape.

### Function signatures with args + return as structured rows

- graph-sitter: structured for Python + TS via its NodeClasses system
- rust-analyzer: full HIR-level signature representation
- codebase-memory-mcp: CBMCall captures up to 8 args per call site, but for function definitions stores signature as text
- ACER: param count + FullType tuple (Java only)
- sem: entity name + signature text blob
- cymbal: signature text blob
- grepai: parameter strings
- The rest: kind + name + optional signature blob

Four tools capture some structured form; eight store signatures as text blobs. Normalizing into `function_signatures` + `function_params` tables across all source languages is green field.

### Return counts (multi-return, tuple unpack)

Nobody has a `return_count` column. Go's multi-return and Python's tuple-unpacking returns are flattened into the signature string everywhere. Structural query like "functions that return 3+ values" is unanswerable across the 12 tools.

## Specific technique lessons distilled from the survey

Ranked by sprefa relevance.

### Tier A — directly applicable to call_sites extraction

1. **cymbal's EnclosingSymbol range query** (`store.go:1168-1181`). Store flat refs as `(file_id, line, name)` triples. At query time, given a line, find enclosing symbol via `ORDER BY (end_line - start_line) ASC LIMIT 1`. Narrowest-span symbol wins. Replaces scope-stack tracking at extraction time.

2. **codebase-memory-mcp's import-map + registry resolution** (`pass_calls.c:94-167`). Per-file `local_name → target_qn` map from IMPORTS edges. Three-strategy fallback: `import_map → same_module → suffix_match`, each step emits confidence 0.0-1.0. Cross-file resolution via indexing, zero type inference.

3. **rust-analyzer's dual call-hierarchy mechanism** (`call_hierarchy.rs:44-158`). Incoming: `func.usages(sema).all()` + ancestor walk to enclosing function. Outgoing: body descendants for `CallableExpr`, resolved via `sema.type_of_expr().as_callable()` or `sema.resolve_method_call()`. Two algorithms, same API.

4. **tree-sitter-codeviews's per-statement CFG emitter** (`CFG_java.py:884-1300`). Per statement type, emit typed edges: `if` → `pos_next`/`neg_next`, `while`/`for` → `pos_next` + `loop_control` back-edge + `neg_next` exit, `break`/`continue` → jumps, try/catch/finally → propagation rules. This is the reference for how to materialize `branch_path` as a storage column.

### Tier B — narrower but real

5. **grepai's parent-chain ancestor walk** (`extractor_ts.go:868-912`). AST equivalent of cymbal's line-range query. Walk tree-sitter parents until hitting function_declaration.

6. **ACER's Preprocessor/Generator split** (`src/acer.py:33-220`). Two-pass: enumerate defs first into `method_dict` + `unique_dict`, then enumerate uses and resolve via lookup. Handles overload ambiguity via dual-dict design.

7. **graph-sitter's Cython sort by start_byte** (`compiled/sort.pyx:25`). If source order is load-bearing, sort at the leaves and concatenate upward.

8. **rust-analyzer's `descend_into_macros_exact`** (`call_hierarchy.rs:113`). Walks macro expansions to find call sites inside macro invocations, with `sema.original_range()` mapping back to source location.

### Tier C — theoretical frames worth reading

9. **stack-graphs push/pop symbol stacks** (`graph.rs:559-599`, `partial.rs:150-190`). Symbol stack + scope stack, refs push / defs pop. Cross-file via partial paths with scope variables `%1, %2` unified at stitch time. The GitHub paper is the reference; Rust implementation is ~3000 lines.

10. **codebase-memory-mcp's FQN computation**. `project.path.module.name` where path uses dots. Dead simple, makes the global registry a hash table.

### Tier D — skip for call graphs specifically

11. **sem's `infer_ref_type` heuristic** (`graph.rs:914`). Context-based classifier for Calls vs TypeRef vs Imports. Narrow trick.

12. **codedb's trigram index with DocPosting**. Irrelevant to call graphs, relevant if sprefa ever wants grep-scale substring search.

13. **SocratiCode's RRF** (`qdrant.ts:305-355`). Merge technique for ranked lists, parameter-free. Generic, relevant when sprefa has multi-signal ranking.

## codebase-memory-mcp service_patterns — the allowlist port

codebase-memory-mcp classifies CALLS edges as HTTP_CALLS / ASYNC_CALLS / CONFIGURES / ROUTE_REG via a hand-maintained substring allowlist in `internal/cbm/service_patterns.c`. The match is literally `strstr(resolved_qn, library_id)` against three static tables (~70 HTTP libraries, ~50 async, ~20 config).

**Mechanism:** the match runs on the **resolved** qualified name, so `r.get()` with `import requests as r` → `project.venv.requests.api.get` → `strstr("requests")` hits. Import aliases are transparent because resolution happened first.

**Route-reg precedence:** checked before HTTP-client matching so `gin.GET` doesn't match as an HTTP client.

**HTTP method extraction:** separate suffix match on callee name: `.get` → GET, `.Post` → POST, `.MapGet` → GET.

**Port to sprefa:** the C code is gross (closed-world, hardcoded, recompile to add a library). The idea is sound and directly translates to a tag-classification rule file in sprefa's own query language:

```
tag(call, "http") :-
  call_site(call),
  callee_entity(call, e),
  entity_qn(e, qn),
  qn ~ "(requests|httpx|aiohttp|axios|reqwest|hyper|okhttp|HttpClient)\\..*".

tag(call, "async.kafka") :-
  call_site(call),
  callee_entity(call, e),
  entity_qn(e, qn),
  qn ~ "(kafka|kafkajs|sarama|rdkafka|confluent)\\..*".

tag(call, "external_io") :- tag(call, "http").
tag(call, "external_io") :- tag(call, "async").
```

Three properties the C allowlist can't express:
- **Open-world**: users add rules for in-house libraries in a project-local `.sprf` file without forking sprefa
- **Composable**: tags can depend on other tags (hierarchy)
- **Queryable with the same language as everything else**: zero second surface for classification

The ~140 library entries from codebase-memory-mcp's `service_patterns.c` port directly into a default rule file under MIT attribution. Classification becomes one query over `call_sites`, fires only where `callee_entity` resolved, and stays in the same language as every other sprefa query.

## Green-field territory (what sprefa gets to define)

1. **Normalized visibility column** across all languages (5-value domain)
2. **String literals as first-class rows** with position, enclosing entity, kind
3. **File tree as queryable facts** rather than a walk artifact
4. **Type paths via Lodash-style enumeration** with depth + flag columns
5. **Function signatures as structured rows** (signatures + params tables) across all languages, with return_count
6. **`ordinal` + `branch_path` columns on call_sites** — source-order and branch-context queryable via SQL
7. **Source tagging column** letting multiple extractors contribute facts to the same tables
8. **Datalog-to-SQL query surface** for user queries (composable, relation-based)
9. **Tag classification as queries**, with library allowlists as rule files rather than hardcoded C arrays
10. **PerFile / PerRepo / External cost tiers** for extractor scheduling with external-adapter caching

No peer tool combines more than two of these. Most peer tools combine zero.

## Feedback loops captured this session

- User has strong allergy to negative parallelism ("not X, Y" patterns). Existing memory `feedback_no_negative_parallelism.md` already covers. Strength escalation: user stops reading at the word "not" in descriptive prose. Apply as a hard constraint in all future output.

- User prefers terse, content-dense output. Long explanations are fine when every sentence carries information; fluff is stripped aggressively.
- codebase-memory-mcp is impressive as a standalone tool but architecturally wrong for sprefa as a dependency: its 18-edge-type taxonomy and missing ordinal column on edges make it a consumer, not a source.
