## Problem/Context
The auto-refactor vision (concept doc `plans/2026-06-25-graph-reachability-clustering-auto-refactor.md`): engine builds graph relations (call_edge, type_edge, df_edge, CST node/child) + has `closure(edge)` reachability + count/min/max aggregates. Question: is the "discovery" step (find cohesive fn clusters = refactor candidates) free, or does it need new engine code?

Theory test result (the key finding): per-fn signals ARE free (fan-in/out, single-caller move-candidates, seeded blast-radius). But all-pairs SCC is NOT — `scc(a,b) <- reaches(a,b), reaches(b,a)` reads the closure relation UNPINNED, which the engine forbids ("would materialize the full O(N²) closure"). The naive datalog asks via the expensive intermediate. Tarjan finds SCCs in O(V+E) WITHOUT the closure; and `closure` ALREADY runs Tarjan internally (to condense for its own reachability) — it just throws the partition away. So `scc(edge)` exposes already-computed data. Zero second Tarjan.

## Solution/Approach
`scc(edge)` mirrors `closure(edge)`, reuses `closure_cache[edge].cond` (the `scc::Cond` struct has `members: Vec<Vec<u32>>` = comp→member ids + `comp: Vec<u32>` = node→comp). Six touch points:
1. ast.rs: `BodyItem::Scc { rel }` + `Rule::scc_edge()` detector.
2. parse.rs: `fn scc()` (4 lines) + dispatch `if s == "scc"`.
3. engine.rs: scc rules excluded from `all_derived` (can't lower to SQL) → collected into `scc_rules`; `cond_edges_for` helper feeds closure+scc edges to `refresh_cond_cache` while keeping closure-VIEW rebuild (`any_closure_empty`/`rebuild_closures`) closure-only; `eval_scc_rule` materializes (rep, member) from cond.members + names (rep = min member name); `rels_used` gates the edge build.
4. typecheck.rs + frontend.rs: `| Scc {..} => {}` exhaustiveness arms.

One crash fixed during impl: fact-only `scc(edge)` (no companion closure) had no SQL view → missing `scc_node_<edge>` table. Root cause: the closure-VIEW path creates those tables; scc reads the in-memory cond instead. Fix = `cond_edges_for` splits the edge sets (refresh_cond_cache sees both; view-rebuild sees closure-only).

## Key Insights
- `closure` runs Tarjan internally for its own condensation; `scc` exposes that partition. Zero second Tarjan — they share `closure_cache[edge].cond`.
- The engine forbids unpinned closure reads (O(N²) materialization). closure = relation (pairs, directed); scc = partition (groups). A partition isn't a projection of a relation — needs reverse direction + equivalence-class folding = Tarjan.
- Rep = min member name (stable, readable cluster id). Singletons get rep==member.
- scc heads materialize in the query phase (after refresh_cond_cache); a derived rule reading one sees last-tick's value (1-tick latency, converges) — same pattern as closure seed heads / data-driven scan.
- Refactor targets found on the engine: 1 cross-file cycle (GitBatch.read ↔ rpc::read_line), ~10 single-call-site inline candidates (tick_audit, cast_int, opt_var...), 2 god-methods (tick_paths fan_out=72, tick=57).
