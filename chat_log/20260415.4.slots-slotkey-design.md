## 1. API surface

### 1.1 `Slots` and `SlotKey<T>`

```rust
// v2/src/_0_types.rs  (new submodule section, still in _0_types)

use std::any::{Any, TypeId};
use std::collections::HashMap;
use std::marker::PhantomData;
use std::sync::Arc;

/// Typed handle to a slot. Zero-sized; the `T` lives in the phantom.
///
/// Use `fn() -> T` variance so `SlotKey<T>` is invariant in `T` at the
/// nominal level but keeps `Send + Sync` regardless of `T`'s auto-traits
/// (we only ever hold the key, never a `T`). This is the standard trick
/// for type-tag phantoms. `PhantomData<T>` would leak T's auto-traits
/// and break Send/Sync on keys that wrap e.g. an Rc-bearing T — we do
/// not want that.
pub struct SlotKey<T: 'static + Send + Sync> {
    _marker: PhantomData<fn() -> T>,
}

impl<T: 'static + Send + Sync> SlotKey<T> {
    /// Const ctor so ops can declare `pub const JSON_TREE: SlotKey<JsonTree> = SlotKey::new();`
    pub const fn new() -> Self {
        Self { _marker: PhantomData }
    }
}

// Manual impls: PhantomData<fn() -> T> already gives us Copy/Clone/Send/Sync,
// but spell them out for clarity and to pin the contract.
impl<T: 'static + Send + Sync> Copy for SlotKey<T> {}
impl<T: 'static + Send + Sync> Clone for SlotKey<T> {
    fn clone(&self) -> Self { *self }
}

/// Typed, type-erased slot store keyed by `TypeId::of::<T>()`.
///
/// Payload is `Arc<dyn Any + Send + Sync>`. Downcast is exact-type; no
/// trait-object witnessing. Cheap to clone: `HashMap::clone` + per-entry
/// `Arc::clone`, no deep copies.
#[derive(Debug, Default, Clone)]
pub struct Slots {
    map: HashMap<TypeId, Arc<dyn Any + Send + Sync>>,
}

impl Slots {
    pub fn is_empty(&self) -> bool { self.map.is_empty() }
    pub fn len(&self) -> usize { self.map.len() }

    /// Insert / replace. Returns the prior value if one existed.
    /// Last-write-wins. See section 1.5 for rationale.
    pub fn set<T: 'static + Send + Sync>(&mut self, _k: SlotKey<T>, v: T) -> Option<Arc<T>> {
        let prior = self.map.insert(TypeId::of::<T>(), Arc::new(v));
        prior.and_then(|a| Arc::downcast::<T>(a).ok())
    }

    /// Insert pre-shared Arc. Common when the value is already `Arc`-wrapped
    /// upstream (e.g. a parse tree shared across a batch).
    pub fn set_arc<T: 'static + Send + Sync>(&mut self, _k: SlotKey<T>, v: Arc<T>) -> Option<Arc<T>> {
        let prior = self.map.insert(TypeId::of::<T>(), v);
        prior.and_then(|a| Arc::downcast::<T>(a).ok())
    }

    /// Get. Returns `Option<Arc<T>>` — the cheap clone of the stored Arc.
    /// See section 1.6 for why Arc over &T.
    pub fn get<T: 'static + Send + Sync>(&self, _k: SlotKey<T>) -> Option<Arc<T>> {
        self.map.get(&TypeId::of::<T>())
            .and_then(|a| Arc::downcast::<T>(a.clone()).ok())
    }

    pub fn contains<T: 'static + Send + Sync>(&self, _k: SlotKey<T>) -> bool {
        self.map.contains_key(&TypeId::of::<T>())
    }

    pub fn remove<T: 'static + Send + Sync>(&mut self, _k: SlotKey<T>) -> Option<Arc<T>> {
        self.map.remove(&TypeId::of::<T>())
            .and_then(|a| Arc::downcast::<T>(a).ok())
    }
}
```

### 1.2 Variance / phantom choice

Use `PhantomData<fn() -> T>`:
- Invariant in `T`, which is correct: a `SlotKey<Foo>` and `SlotKey<Bar>` are distinct handle types.
- Does **not** leak `T`'s auto-traits onto the key. The key is a zero-sized tag; it contains no `T`. Users can declare `SlotKey<T>` where `T: 'static + Send + Sync` without the key itself needing to witness those bounds through phantom.
- `PhantomData<T>` would inherit non-Send from e.g. `Rc<…>` inside T and silently poison the key.
- `PhantomData<*const T>` would forgo Send/Sync needlessly.

### 1.3 Payload representation

`Arc<dyn Any + Send + Sync>` at the map, downcast-on-read.

Rejected alternatives:
- **Per-type map-of-maps**: requires a registry, explodes op-owned-everything.
- **`Box<dyn Any>`** at the map: forces clone-on-insert of T, eliminates the zero-copy story for shared parse trees.
- **Downcast via `dyn Trait`** (e.g. a `SlotPayload` trait): forces ops to write impls, burns the "just stash any `T: 'static + Send + Sync`" ergonomics.

Downcast path:
```
Arc<dyn Any + Send + Sync>  -- Arc::downcast::<T>() -->  Arc<T>
```
`Arc::downcast` requires `T: Any + Send + Sync`; `'static` is transitively required by `Any`. The `Option` return is fine — shape of the API already accepts absence.

### 1.4 Clone cost

`Cursor` already clones on every hop (framework-driven path tagging, witness recording). Adding `slots: Slots` changes per-hop clone cost from O(captures + fks + evidence) to O(captures + fks + evidence + slot_count). Slot count in realistic pipelines is 0–3. The `HashMap<TypeId, Arc>` clone is a few pointer bumps plus a small malloc for the bucket array. Net impact is negligible and dwarfed by `captures` and `evidence` which already exist.

The **win** is that parse trees flow by Arc, not by deep copy. Today a json re-parse rebuilds `AnyDataNode` from bytes at every json invocation; nested `json > json` would triple-parse. With slots, parse trees become Arc-shared along a pipeline branch until a later op narrows / replaces them.

### 1.5 Insert / replace semantics: **last-write-wins**

Reject "registry" (forces central state) and "reject on conflict" (brittle; nested json is a legitimate overwrite pattern — inner walk narrows, it's the new view). Last-write-wins matches the op-owned-everything stance: ops declare keys, ops write them, downstream reads the most recent write. Ops that need "prior value" semantics can `get` before `set` and handle it themselves.

One non-rule: when two distinct ops share a `SlotKey<T>` by **design** (json + yaml both populate `CANONICAL_TREE: SlotKey<AnyDataNode>`), the later one clobbers the earlier. This is identical to how two captures with the same name overwrite, and is fine.

### 1.6 Get semantics: `Option<Arc<T>>`

Return the Arc, not a `&T`:
- `Arc<T>` frees the caller from carrying the `Slots`'s borrow into an async flat_map. `Op::pipe` closures are `'static`; borrows off `Cursor::slots` don't survive the `move`.
- `Arc::clone` on a hot-path is a single atomic inc and is free compared to the surrounding stream/batch clones.
- Ops that want a `&T` can just deref: `let tree: Arc<JsonTree> = c.slots.get(JSON_TREE)?; let t: &JsonTree = &*tree;`.

### 1.7 Lifetime requirements

`T: 'static + Send + Sync`. Concretely:
- **tree-sitter `Tree`**: owns its input bytes via `Source`; `Send` (check ts version; true as of recent). `'static` when owned. Fine.
- **ast-grep `AstGrep<L>`**: owns source. Fine.
- **oxc arenas**: the arena plus the AST root, bundled into a wrapper struct that holds both. Fine.
- **`AnyDataNode`**: owns `Arc<Bytes>` + parsed tree. Fine.

Any lending / self-referential tree must be boxed into an owner type before going into Slots. This is the standard Rust move.

### 1.8 Newtype discipline (collision risk)

Two ops, written independently, both doing `pub const TREE: SlotKey<AnyDataNode> = SlotKey::new();` collide silently — both map to `TypeId::of::<AnyDataNode>()`. Last write wins, which may be wrong intent.

**Rule (documented in this memo, not enforced by types):**

> Every op that publishes a slot declares a **newtype wrapper** around the payload value. `SlotKey<Wrapper>` keys are therefore distinct between ops.

Example:
```rust
// json op
pub struct JsonTree(pub Arc<AnyDataNode>);
pub const JSON_TREE: SlotKey<JsonTree> = SlotKey::new();

// yaml op (different instance of same backend)
pub struct YamlTree(pub Arc<AnyDataNode>);
pub const YAML_TREE: SlotKey<YamlTree> = SlotKey::new();
```

Cross-op slot sharing by convention is fine — an ecosystem can agree on a shared wrapper type living in a common crate. What we forbid is accidental clash via re-used primitive/backend types.

## 2. Shared-slot semantics

### 2.1 Can N ops publish to the same SlotKey<T>? Yes.

Legitimate pattern: `json` and a hypothetical `yaml` op both produce `AnyDataNode` trees. If they agree on a wrapper type (say `StructuredTree(Arc<AnyDataNode>)` in a shared crate) and both publish under the same `SlotKey<StructuredTree>`, then downstream ops that operate on `StructuredTree` see a uniform upstream regardless of which parser produced it.

Constraint: only one publisher fires per branch of the pipeline for a given cursor (the DAG is linear along any single cursor's lifetime inside a branch). Cross-branch (Fork) publishing runs against distinct cursor clones, so no race.

### 2.2 Can N ops read? Yes.

Free. No gotchas. A tree stamped by `json` is read by `line`, `regex`, `hover`, and a downstream `json` interchangeably.

### 2.3 Ownership convention

> One op declares the canonical `SlotKey<T>` constant. Others import and reuse.

Concrete shape for later landing:
```rust
// crate: sprefa-v2-ops-tree (hypothetical shared concept crate)
pub struct StructuredTree(pub Arc<AnyDataNode>);
pub const STRUCTURED_TREE: SlotKey<StructuredTree> = SlotKey::new();

// in json op
use sprefa_v2_ops_tree::{StructuredTree, STRUCTURED_TREE};

// in yaml op  
use sprefa_v2_ops_tree::{StructuredTree, STRUCTURED_TREE};
```

No registry. No central enum. The `TypeId` of `StructuredTree` is the collision key; the newtype is the discipline that prevents accidental clash.

### 2.4 Interaction with op-owned-everything

Slots are owned by **concept**, not by op. `json` and `yaml` are two *implementations* of the "structured tree" concept. Multiple ops can be implementations of the same concept and all publish to the same slot. This is the clean separation: ops own their **code**, the **concept** owns the slot key.

## 3. `byte_range` narrowing protocol

### 3.1 `byte_range` does not exist on `Cursor` today

It exists only on `ParseSite` (compile-time byte range of the op invocation in `.sprf` source) and on slot source structs. A **new** runtime field is required.

### 3.2 Proposed field

```rust
pub struct Cursor {
    // ...existing fields...
    pub content:    Option<Arc<bytes::Bytes>>,
    /// Runtime byte window into `content`. When `Some`, byte-oriented
    /// downstream ops (line, regex) restrict their scan to this range.
    /// When `None`, the cursor addresses the whole file (file-wide ops).
    /// Indices are into `content`, not into `fs` on disk (same thing,
    /// just clarifies the invariant).
    pub byte_range: Option<Range<usize>>,
    pub slots:      Slots,
}
```

### 3.3 Protocol rules

1. **Read-time (fs/read) ops**: leave `byte_range = None`. Cursor addresses the whole file.
2. **Tree-walking ops** (json, ast-grep, md): on selecting a subtree / node, set `byte_range = Some(node_span)`. `node_span` is the span of the selected node **inside `content`**. Always set — never `take`.
3. **Non-tree scope-narrowing ops** (hypothetical `line_at(n)`, `slice(a..b)`): narrow further by intersecting with the current `byte_range`.
4. **Byte-oriented consumer ops** (line, regex): read `content[byte_range]` where `byte_range` defaults to `0..content.len()` when `None`.
5. **Reset rule**: `byte_range` is cleared (set to `None`) **only** when `fs` or `content` changes (new file). Within a single file's branch, narrowing is monotonic — once narrowed, later ops either narrow further or stay at the current window. No "un-narrow" step.
6. **Non-file ops** (repo, rev, fs glob): `byte_range` stays `None`. It is invalid before a file is chosen.

### 3.4 Interaction with `content`

`byte_range` is an index into `content`. Keep them paired:
- A cursor with `Some(content)` and `None` byte_range means whole file.
- A cursor with `Some(content)` and `Some(r)` byte_range means bytes `content[r]`.
- A cursor with `None` content and `Some` byte_range is a bug.

A small helper method pays rent:
```rust
impl Cursor {
    pub fn active_bytes(&self) -> &[u8] {
        match (&self.content, &self.byte_range) {
            (Some(bs), Some(r)) => &bs[r.clone()],
            (Some(bs), None)    => &bs[..],
            (None, _)           => &[],
        }
    }
}
```

### 3.5 Fork / Switch

Each Fork arm receives its own cursor clone with the pre-fork `byte_range`. Arms narrow independently. Join is not a thing in the current model (Fork emits parallel streams; no recombine), so the cross-arm narrowing question is moot.

## 4. Composition case studies

Notation per hop: `(fs, content, byte_range, slots)`. `-` = unchanged.

### 4.1 `fs(**/*.json) > read > json({ a: $A }) > line(re: /TODO/)`

| Hop | `fs`              | `content`   | `byte_range` | `slots`                      |
|-----|-------------------|-------------|--------------|------------------------------|
| after fs  | `foo.json`  | `None`      | `None`       | `{}`                         |
| after read| `foo.json`  | `Some(all)` | `None`       | `{}`                         |
| after json| `foo.json`  | `Some(all)` | `Some(r_a)`  | `{JSON_TREE: Arc<JsonTree>}` |
| after line| `foo.json`  | `Some(all)` | `Some(r_a)`  | `{JSON_TREE: ...}`           |

- `json` reads `content`, parses `AnyDataNode`, walks pattern, picks match for `$A`, narrows `byte_range` to the span of that value, stamps `JSON_TREE`.
- `line` reads `c.active_bytes()` and regex-scans only that window. It ignores `JSON_TREE` entirely.

### 4.2 `fs > read > json({a: $A}) > json({b: $B})` (nested)

| Hop | `fs`    | `content`   | `byte_range` | `slots`                 |
|-----|---------|-------------|--------------|-------------------------|
| after read | `foo.json` | `Some(all)` | `None`    | `{}`                   |
| after json#1 | `foo.json` | `Some(all)` | `Some(r_a)` | `{JSON_TREE: t1}`   |
| after json#2 | `foo.json` | `Some(all)` | `Some(r_ab)`| `{JSON_TREE: t2}`   |

Two paths for the inner json:

**Path A (slot reuse, preferred for JSON):** read `JSON_TREE` slot. Since json's tree is a position-independent `AnyDataNode` with absolute byte offsets attached per-node, the inner walker restricts traversal to nodes whose span ⊆ current `byte_range`. No re-parse. Inner op may still replace `JSON_TREE` with a sub-rooted view — cheap because nodes are Arc-like shared.

**Path B (re-parse):** ignore the slot; call `parse_by_ext(&ext, Arc::new(content[byte_range].to_vec()))`. Correct but costly.

**Decision**: prefer Path A when the slot is present and the stored tree type is compatible. Every op frees to pick; neither is mandated. The canonical `json` implementation should prefer slot reuse and fall back to re-parse if absent.

### 4.3 `fs > read > md(code_block{lang:ts}) > ast-grep(pat)` — hardest case

Two distinct tree backends, two distinct slot types.

```rust
// md op
pub struct MdTree(pub Arc<CommonMarkTree>);
pub const MD_TREE: SlotKey<MdTree> = SlotKey::new();

// ast-grep op
pub struct AstGrepTree(pub Arc<AstGrep<TypeScript>>);
pub const AST_GREP_TREE: SlotKey<AstGrepTree> = SlotKey::new();

// optional hint slot published by md and read by ast-grep:
pub struct Lang(pub Arc<str>);
pub const LANG: SlotKey<Lang> = SlotKey::new();
```

Choreography:

| Hop | `fs`      | `content`   | `byte_range`        | `slots`                                         |
|-----|-----------|-------------|---------------------|-------------------------------------------------|
| after read | `doc.md` | `Some(all)` | `None`           | `{}`                                            |
| after md   | `doc.md` | `Some(all)` | `Some(fence_body)` | `{MD_TREE: ..., LANG: Arc(Lang("ts"))}`         |
| after ast-grep | `doc.md` | `Some(all)` | `Some(fence_body_narrowed_to_match)` | `{MD_TREE: ..., LANG: ..., AST_GREP_TREE: ...}` |

- `md` parses the markdown, selects a fenced code block with `lang:ts`, narrows `byte_range` to the **body** of the fence (inside the ```ts ... ``` delimiters), stamps `MD_TREE`, stamps `LANG`.
- `ast-grep` reads `c.active_bytes()` (the ts source inside the fence), optionally checks `LANG` slot to confirm expected language, calls its tree-sitter parser with TypeScript grammar on those bytes, stamps `AST_GREP_TREE`, narrows `byte_range` further to the matched node span.
- Downstream ops see both `MD_TREE` and `AST_GREP_TREE` in slots. Neither conflicts; distinct types ⇒ distinct `TypeId` keys.

Handoff contract:
- Md **publishes**: `MD_TREE`, narrows `byte_range`, optionally `LANG`.
- Ast-grep **reads**: `byte_range` (required) + `content` (required) + `LANG` (optional hint).
- Ast-grep **publishes**: `AST_GREP_TREE`, narrows `byte_range`.
- Md **ignores**: whatever ast-grep publishes (it runs upstream).
- Ast-grep **ignores**: `MD_TREE` (wrong backend).

No shared slot between the two. No coupling in v2 core. `LANG` is a loose hint, not a contract; ast-grep could infer language from file extension if md didn't stamp it.

### 4.4 `fs > read > oxc(pat)` — third-party op crate

A hypothetical `sprefa-op-oxc` external crate, zero edits to `v2/src/_0_types.rs`:

```rust
// crate: sprefa-op-oxc, file: sprefa-op-oxc/src/lib.rs
use sprefa_v2::{Cursor, Op, OpCtx, SlotKey};
use oxc::allocator::Allocator;
use oxc::parser::Parser;
use oxc::ast::ast::Program;
use std::sync::Arc;

/// Wrapper that bundles arena + root for 'static ownership.
pub struct OxcTree {
    _arena: Box<Allocator>,
    // SAFETY: program borrows from _arena which is pinned by the Box; we
    // never move the arena after construction. Wrapper is !Send unless
    // oxc's arena is Send — check upstream. For this memo, assume wrapper
    // is engineered to be Send + Sync, which typically means boxing the
    // arena and erasing the lifetime with a self-ref crate like ouroboros
    // or by transmuting the lifetime behind a sealed API.
    program: Program<'static>,
}

pub struct OxcSlot(pub Arc<OxcTree>);
pub const OXC_TREE: SlotKey<OxcSlot> = SlotKey::new();

pub struct OxcOp { /* pattern, etc. */ }

impl Op for OxcOp {
    fn name(&self) -> &'static str { "oxc" }
    // ... parse_site, witness, hover_* ...

    fn pipe(&self, input: BoxStream<'static, Arc<[Cursor]>>, _ctx: OpCtx)
        -> BoxStream<'static, Arc<[Cursor]>>
    {
        input.map(|batch| {
            let out: Vec<Cursor> = batch.iter().map(|c| {
                let mut c = c.clone();
                let bytes = c.active_bytes();
                // parse, walk, narrow, stamp
                let tree = parse_oxc(bytes);
                c.slots.set_arc(OXC_TREE, Arc::new(OxcSlot(Arc::new(tree))));
                // c.byte_range = Some(match_span_in_content);
                c
            }).collect();
            Arc::<[Cursor]>::from(out.into_boxed_slice())
        }).boxed()
    }
}
```

Zero changes to `v2/src/_0_types.rs`. Zero changes to `Slots`. The third-party crate adds a new slot type into the ambient typed pool and a new `Op` impl. Done.

> **Footnote (parked).** OXC's AST borrows from its arena — making the wrapper `'static + Send + Sync` requires either `ouroboros` / `self_cell` self-ref erasure or a sealed-API lifetime `transmute`. Not unique to OXC; any lending tree (tree-sitter with source borrow, rustc libs, etc.) hits the same wall. The commit-1 API already accommodates it — the op author pays the self-ref tax, v2 core stays unchanged. Flag surfaced here so it is not rediscovered mid-integration.
>
> **Related parked item — yaml/toml under the existing `json` op.** `json` today dispatches on extension inside one op. yaml/toml walker byte-span surfacing requires per-backend impls behind a small trait (`TreePos` or similar) covering JSON/YAML/TOML. serde is little help; we hand-roll. Same shape as the OXC lending issue but one level shallower. Future problem, out of commit-1 scope.

## 7. Open questions

### 7.1 `cursor.get_slot::<T>()` shortcut?

Tempting:
```rust
impl Cursor {
    pub fn get_slot<T: 'static + Send + Sync>(&self, k: SlotKey<T>) -> Option<Arc<T>>
    { self.slots.get(k) }
    pub fn set_slot<T: 'static + Send + Sync>(&mut self, k: SlotKey<T>, v: T)
    { self.slots.set(k, v); }
}
```
Pro: one fewer `.slots.` in every op body. Pro: opens a spot to later inject instrumentation (e.g., "log all slot reads when collect_witnesses is on") without touching every call site.
Con: two ways to do the same thing. `TypeId` magic gets shallower in callers.

**Recommendation**: add the `get_slot` / `set_slot` shortcuts on `Cursor`. Instrumentation hook is the dispositive reason; op code reads as clean `c.get_slot(JSON_TREE)`. Keep `c.slots.get(…)` available for cases where the op is mutating `slots` alongside other Slots-specific operations (rare).

### 7.2 Interior mutability for parse caches?

A later "cache" slot (e.g., memoized jq-paths per tree) wants shared mutation. Options:
- `Arc<RwLock<Cache>>` stored under the slot. Set once, readers lock-read, writers lock-write.
- Per-slot caches live outside `Slots` (on `OpCtx` or a dedicated cache object on `RunCtx`).

**Recommendation**: do not mix interior-mutability slots into the clean payload model now. When the need lands, the idiom is `SlotKey<Arc<RwLock<Cache>>>` — the `Slots` API already supports it, no new machinery. Leave as a follow-up design question.

### 7.3 Codegen registry escape hatch

Per `memory/project_op_owned_cursor_slots.md`: future `marker()/render()` codegen could assemble a static slots struct from per-op slot declarations, monomorphizing away the `TypeId` dispatch. This is out of scope for commit 1. The dyn-Any path must land first so ops can be written before the codegen exists; the codegen is an optional perf step later. API stays identical from the op author's view either way.
