## Analysis

### Scaling to 40M LOC

SocratiCode achieves 40M-LOC scale primarily through external infrastructure rather than algorithmic innovations:

1. **Qdrant vector database** (src/services/qdrant.ts): Offloads all indexing, search, and persistence to a dedicated vector store. Qdrant handles HNSW indexing, sparse BM25 (server-side), and concurrent read/write. SocratiCode acts as a thin client that batches upserts and queries (src/services/qdrant.ts:172-212, 305-355).

2. **Batched resumable indexing** (src/services/indexer.ts:40-77): Files processed in batches of 50 (FILE_SCAN_BATCH), with chunks batched in 100-point units (src/services/qdrant.ts:205). After each batch, progress is checkpointed to Qdrant. If indexing crashes, the next run loads file hashes from Qdrant and skips already-indexed files (src/services/indexer.ts:137-158).

3. **Incremental indexing via content hashing** (src/services/indexer.ts:137-158): File hashes are persisted in Qdrant metadata. On subsequent runs, only files with changed hashes are re-chunked and re-embedded, skipping gigabytes of unchanged code.

4. **Parallel processing** (src/services/indexer.ts:40): 50 files scanned in parallel I/O, while embedding batching happens separately. Embedding provider batches 32 texts per call (src/services/embeddings.ts:8).

5. **Provider-agnostic embedding** (src/services/embedding-provider.ts, embedding-config.ts): Supports Ollama (local), OpenAI, Google Gemini. Large codebases can offload embedding generation to cloud providers or native Ollama (Metal/CUDA), avoiding bottlenecks.

### Call Extraction Mechanism

Import-based only; not function-level calls. ast-grep NAPI bindings parse each file and extract import statements via language-specific AST rules:

- **JavaScript/TypeScript** (src/services/graph-imports.ts:169-172): `import_statement`, `call_expression` (require/import), `export_statement`
- **Python** (src/services/graph-imports.ts:140-160): `import_statement`, `import_from_statement`
- **Java/Kotlin** (src/services/graph-imports.ts:175-195): `import_declaration`, `import_header`
- **Go** (src/services/graph-imports.ts:198-200): `import_spec`
- **Regex fallback** (src/services/graph-imports.ts:81-103): Dart, Lua, CSS @import, HTML `<style>` blocks

Extraction happens during graph build (src/services/code-graph.ts:104, 153), with imports stored as raw module specifiers. Resolution to file paths is deferred (graph-resolution.ts, graph-aliases.ts).

### Tree-Sitter / Parser Choice

**ast-grep** (NAPI bindings, NOT Tree-sitter): ast-grep is a higher-level wrapper that uses Tree-sitter grammars internally but exposes a simpler AST query interface. SocratiCode uses dynamic language registration to load pre-compiled grammars:

- src/services/code-graph.ts:250-286 registers dynamic languages via `registerDynamicLanguage(langModules)` from npm packages like `@ast-grep/lang-python`, `@ast-grep/lang-java`, etc.
- The NAPI binding (src/package.json:79: `@ast-grep/napi:^0.40.5`) provides the parse() and Lang enum.

No direct Tree-sitter integration observed.

### Storage Format and Schema

**Qdrant point schema** (src/services/qdrant.ts:183-202):

```
{
  id: string,
  vector: {
    dense: number[],
    bm25: { text: string, model: "qdrant/bm25" }
  },
  payload: {
    filePath: string,
    relativePath: string,
    content: string,
    startLine: number,
    endLine: number,
    language: string,
    type: "code" | "comment" | "mixed",
    contentHash: string
  }
}
```

**Collections**:
- `codebase_{projectId}`: File chunks with dense + BM25 vectors
- `codegraph_{projectId}`: Code graph metadata (nodes/edges) stored as single JSON point
- `context_{projectId}`: Context artifacts (database schemas, API specs)
- `socraticode_metadata`: Project-level metadata (indexing status, file hashes, build timestamps)

Payload indexes created on filePath, relativePath, language, contentHash for efficient filtering (src/services/qdrant.ts:88-103).

### Source-Order Preservation

**Not preserved**. Import statements are extracted as unordered lists (src/types.ts:17-18: `imports: string[]`). Edges in the graph store only source, target, and type—no ordinal position (src/types.ts:23-27).

### Query Surface

**Hybrid search API** (RRF fusion in Qdrant):

- `codebase_search(query, limit, fileFilter, languageFilter, minScore)`: Dense + BM25 prefetch with RRF fusion (src/tools/query-tools.ts:60-123, src/services/qdrant.ts:305-355)
- `codebase_status(projectPath)`: Indexing progress, lock state, watcher status
- `codebase_graph_query(filePath)`: Dependencies and dependents for a file
- `codebase_graph_stats(projectPath)`: Connectivity stats, circular deps, language breakdown
- `codebase_graph_circular(projectPath)`: Mermaid diagram of circular dependencies

No SQL query language; queries are parameterized tools.

### Interop Model

**MCP (Model Context Protocol)** server (src/index.ts). Exposes tools via Claude Code plugin, VS Code MCP, Cursor, Claude Desktop, Windsurf, Cline. Also supports generic MCP hosts via npx command (README:82-89).

### Incremental & Watched

- **File watcher** (src/services/watcher.ts): Uses @parcel/watcher (debounced 2s) to detect file changes. Invalidates graph cache and triggers incremental index update.
- **Checkpoint resumption**: Qdrant stores indexing status ("in-progress" or "completed") in metadata. On restart, incomplete indexes resume from the last batch boundary.
- **Multi-agent coordination**: File-based locking (proper-lockfile) prevents concurrent indexing/watching of the same project. Cross-process lock queries allow one agent to detect if another is actively indexing.

### Chunking Strategy

1. **AST-aware** (when grammar available): Splits at function/class boundaries using ast-grep (src/README.md:174)
2. **Line-based fallback**: 100 lines per chunk with 10-line overlap (src/constants.ts:68-69)
3. **Minified detection**: If average line length > 500 chars, switches to character-based chunking (src/constants.ts:88-89)
4. **Hard cap**: 2000 character limit per chunk payload (src/constants.ts:101-102)

### Unique Design Patterns

1. **RRF (Reciprocal Rank Fusion)** in Qdrant: Both dense and BM25 queries prefetch 3x candidates, then Qdrant fuses results server-side (src/services/qdrant.ts:328-342). No client-side merging complexity.

2. **Batched embedding generation** with inter-batch rate-limit pauses: Respects Google Gemini free-tier 5 RPM by inserting 15s delays between batches (src/services/embeddings.ts:17-21).

3. **Hash-based incremental detection**: SHA-256 of file content stored in Qdrant metadata allows instant detection of unchanged files without re-reading (src/services/indexer.ts:137-158).

4. **Path migration**: On first load, detects if hashes were stored with absolute paths and transparently migrates to relative paths (src/services/indexer.ts:164-189).

5. **Sparse vectors on-disk**: Qdrant `on_disk_payload: true` (src/services/qdrant.ts:84, 454) avoids keeping all point data in RAM, enabling 40M-LOC scale with bounded memory.
