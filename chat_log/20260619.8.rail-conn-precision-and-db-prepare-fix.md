## Problem/Context
The rail at `.dl/rails.dl:75` warns on `.conn()` sites whose enclosing fn is
loop-reachable. My `refresh_doc_rels` bridge (added in session 7) used
`self.db.conn().prepare(...)` to load `type_entity` rows; the rail fired because
`refresh_doc_rels` is in `tick`'s call tree. But the actual usage is a single
SELECT + collect before iteration -- categorically a read, not a per-row write.

The rail's own comment (`.dl/rails.dl:72-74`) acknowledged this would happen:
"Severity stays warn because the Db seam does not yet expose prepare/query_row/
execute_batch, so most sites have no alternative today; the warnings are the
worklist for that extension." Session 6 (`c569e14`) shipped those alternatives,
so the migration path exists.

After the fix, the user stepped back and asked whether sprefa should use "regex
or confirmed hit" -- a precision-tier question. The honest framing: the user

### S2: precision-tier grounding (no code; conceptual)
Three precision tiers exist in sprefa v5 today, all queryable:

| Tier | Confirms | Op |
|---|---|---|
| Regex | text on a line | `match(p, rev, /pat/, line)` |
| AST | real syntax position | `sg(p, rev, :rust, "pat", ...)`, `ast_yaml(...)`, `ast(...)` |
| Graph | typed semantic edge | `call_site`, `call_name`, `type_link`, `df_node`, `nest`, `type_entity` |

Key clarification: the rail is ALREADY regex-seed + graph-confirm, not
regex-only. `conn_site` is regex-seeded; `conn_fn` joins with `call_site` to
confirm each candidate is a real call. A `.conn()` inside a string literal or
comment would match the regex but fail the `call_site` join, so `conn_fn`
doesn't fire. The "is this a real .conn()" question is already graph-confirmed.

The fix in S1 was a DIFFERENT axis: not regex-vs-graph, but `.conn()` API vs
`Db::prepare` API. The regex seed only matches `.conn()` literally; switching
APIs makes the site invisible. That's a workaround (use the alternative the
rail pushes you toward), not a precision improvement.

Two real precision gaps in the rail (neither is regex-vs-graph):
1. read vs write at the `.conn()` site: `.conn().prepare(...).query_map()` is
   a read; `.conn().execute(...)` inside iteration is a write. The rail treats
   both as bad.
2. loop-entry vs loop-reachable: per-tick one-shots called from `tick`'s call
   tree are transitively loop-reachable but not actually per-iteration.

## Key Insights
- The rail at `.dl/rails.dl` is regex-seed + graph-confirm, not regex-only.
  Reading the rule (`conn_site` regex-seeded, `conn_fn` joins `call_site`) is
  the disambiguator when "regex vs confirmed" comes up. The pattern is in the
  comment at line 24-26.
- Three precision tiers (regex/AST/graph) all coexist; most real rules are
  multi-tier. The question "regex or confirmed" is usually the wrong frame --
  the right question is "which tier is the SEED and which is the CONFIRM".
- The `.conn()` rule's badness lives in the GRAPH (per-row writes inside
  loops), not in the syntax. Regex is the seed; `call_site` + `nest` +
  `call_edge` closure are the confirm. Adding `call_kind` would push the
  confirm further into "what KIND of call" without changing the seed.
- `Db::prepare` (and `query_row`, `execute_batch`) shipped in `c569e14`. They
  are counted (the rail sees them via the same `Db` seam monitoring). New code
  should prefer them; old `.conn()` sites are the migration worklist.
- The amend-wrong-commit pattern: `git commit --amend` always amends HEAD. If
  HEAD is a chat_log commit but you want to amend the code commit one back,
  reset --soft, unstage chat_log, amend, re-commit chat_log.
