## Solution/Approach
### The salt_rev defect (the concrete win)
`src/engine/extract/mod.rs:978`: `fn salt_rev(id, rev) -> String { format!("{rev}\u{1}{id}") }`
Call sites: `src/engine/extract/dataflow.rs:144,170,215,216,232,233,243`.
Five decls carry it: `df_node_rev`, `df_node_repo_rev`, `df_arg_rev`, `df_field_rev`, `df_lit_rev`.

Receipts (hand-run, NOW SUSPECT per correction 3, need a committed harness):
- `_strings`: 314,892 of 939,845 rows (33.5%, 15MB) contain the U+0001 separator
- `rel_df_node` 283,127 rows, `rel_df_node_rev` 297,620 rows, **join on id = 0 rows**
- prior audit attributed 36.4% of all `_strings` bytes to `salt_rev`, 26.6% to `mint_sym`

Fix: real composite `(id, rev)` PRIMARY KEY, `id` reusing the same interned id as `rel_df_node.id`, `rev` interned once.

### The digest/lazy analysis (corrected mid-session)
My first framing of "laziness breaks incrementality" was WRONG. Real machinery:
- PHASE 1 attribution (`tick.rs:531-800`): per-namespace content digests (`src:`/`async:`/`hook:`/`port:`/`daemon:`/`effect:`) build `changed_source_rels`
- PHASE 2 scoping (`strata.rs:337-366`): `affected_derived` is PURE SYNTACTIC reachability over rule bodies. Reads no rows, no digests, no storage.
- PHASE 3 evaluation (`derive.rs:444-498`): TEMP mirror + COUNT/EXCEPT, skips the WRITE only. `skipped_rels` never feeds back into phase 2.
Conclusion: laziness costs ZERO incrementality. It costs recompute x reader-count R, plus loss of any index.

### The resident-graph idea (user's, unresolved)
df family is ~163.6MB across 4 projections of one fact set; same graph as CSR with dense u32 is ~2.2MB (~70x). Precedent exists: `multi_source_halt_bfs` replaced a SQL fixpoint, 1850ms->451ms, 220 statements->22.
User: "as long as retraction works it should be fine". I argued retraction belongs to the TABLES, and the resident graph is a throwaway cache rebuilt per (family, rev) from `ORDER BY src, dst`.
USER THEN CHALLENGED the numbers I built that on (petgraph `add_edge` 120us/edge, LadybugDB 5ms/edge) as insane. They are: 120us for an amortized-O(1) Vec push is ~100,000x too slow, and 5ms/edge is a transaction commit. Both were NEVER PROFILED. Likely measuring node-lookup-per-edge and per-row-commit N+1 in the lab harness. The "rebuild beats incremental past 43 edges" conclusion is UNSUPPORTED.

## Key Insights
- `affected_derived` is pure syntax. Downstream re-derivation is rule-graph reachability from changed SOURCES, never derived-content digests. The mirror compare skips writes only.
- The df family's four projections exist to serve joins a resident walk would not do. If the graph goes resident they stop earning their keep, a bigger prize than the 55.3MB WITHOUT ROWID item.
- `pk_never_null` is a Rust-only vouch, so `.dl`-declared rels (`named_call_site`, `port_reach`) cannot take WITHOUT ROWID. Drops the reclaim from 55.3MB to ~29MB.
- `df_lit` has ZERO rows containing `{`. Rust `format!` never reaches the dataflow layer; the 40 template + 22 concat rows are TS. So a taint/dataflow rail cannot see `salt_rev`; it must be structural (`sg`/`ast`).
