## Problem/Context

deliberate design. User wants: the module system to be ONE module among several (type-graph,
call-graph, entity-graph, scip-import) sharing a CORE of custom built-in predicates/rules;

handling state over time. Also: SCIP can be incremental — if rust-analyzer is already running,
just import its index too.

## Solution/Approach — FOUR DECISIONS SETTLED (in plans/v5-architecture.md)
1. **Datalog + effects, NOT Prolog.** sh/docker-cache/k8s aren't stronger logic — they're 3
   orthogonal axes: effect edge (pure core=WHAT, interpreter=DO; v4 had effect_runtime), content-
   addressed memo (have digest-skip), reconcile loop (have the tick). Datalog's only real gap vs
   Prolog = function symbols (term construction); rarely needed for span/file/symbol analysis;
   add ONE built-in predicate if a tree/list recursion appears. No Prolog.
2. **Glean/Salsa/Souffle-over-SQLite, NOT Differential Dataflow.** DD semantics good but its
   arrangements (indexed multiversioned (data,time,diff)) live IN RAM + history = the RAM trap on
   a single board. PROOF: Materialize is DD-over-SQL and had to bolt on a disk `persist` layer
   (VLDB 2023) for exactly this. v5's actual position named: Glean disk-backed fact model (Glean
   is RocksDB-backed NOT DD-in-RAM, so the framing reinforces) + Salsa red-green early-cutoff
   (digest-skip IS red-green) + Souffle bottom-up fixpoint (SQL INSERT-until-zero) − DD's in-RAM
   arrangements. The trace is SQLite (OS-paged); RAM is a per-tick working set, not the state.
   Already decided in memory: digest-skip at RELATION grain not row-granular MEMO_DEPS (the RAM trap).
3. **SCIP as an importer tier (not just oracle).** Import rust-analyzer's incremental index.scip
   as a compiler-backed indexer: scip_def/scip_ref/scip_edge keyed by the same ref coordinate;
   diet module_edge UNIONs with scip_edge where present. Two tiers (diet 90% + compiler 10%) in
   one relational model.
4. **Peak-RSS invariant:** peak RSS ≈ max(parse working set, condensation adjacency, SQLite cache)
   — none is the corpus. Cold-build is the concern (warm 61MB on 36k-file kernel is fine). Levers:
   cap rayon pool + chunk collect-then-insert; RAM/speed knob = Rust condensation (fast spike) vs
   SQL recursive-CTE view (paged bounded); PRAGMA cache_size = budget. Content-addressing compresses
   history (file unchanged across 200 revs = 1 content row + 200 cheap path rows).

## Key Insights
- DD is the WRONG fit: its in-RAM arrangements are the RAM problem; Materialize spilled to disk to survive.
  Take Salsa red-green semantics + keep the trace in SQLite (paged), not RAM. This is what v5 already half-built.
- "Glean++" reinforces bounded-RAM: Glean is disk-backed (RocksDB), not DD-in-RAM. Disk-backed facts = SQLite-as-trace.
- sh/docker/k8s = an EFFECT axis, not Prolog. Pure core says WHAT, an interpreter DOES (v4 effect_runtime shape).
- Capture matchers become typed language terms via the v4 Dsl/Compiled trait; Span captures feed the ref-spine directly.
- N+1 discipline (this session's build): Db is the single SQL owner; insert_rows = chunked multi-row VALUES = one op;
  per-tick counter screams >64x same statement; conn() = metered escape hatch (36 left). Sync plural-API + collect-then-
  flush, NOT async DataLoader (the redux-out-of-hand trap). oxc resolve() ignores Auto-tsconfig (use resolve_file);
  toml str::parse::<Value> fails in 1.1 (use toml::from_str).
- Banned identifiers/prose: provenance(→source), substrate(→base), load-bearing(→critical), regime(→mode).
