## Key Insights

1. **rule? predicate is fundamentally a port of tag?, not net-new design.** Grammar already supports ?-suffix; OpInvocation::predicate flag exists; lower-time routing branch is mechanical. The real work was deciding rule_row indexing semantics: capture-named vs positional. Chose param-name-based lookup (zip args by position with rule's params, look up by param_name in capture-named rows). Rev-iter last-wins matches the SQLite drain's HashMap-overwrite behavior.

2. **Auto-fire arity-1+ pollution is benign.** Auto-fire of 2-arity rule with empty params produces one row with empty captures. Probe with literal args won't match it; Query drains all 4 (including empty); Join filters it out. Smoke tests for presence of expected rows, not exact count.

3. **lower_rule_def was doing two things at different abstraction levels.** Metadata (name, params, byte_range) is a cheap walk. Body Pipeline lowering is heavy + runtime-specific. Splitting them lets DocSession take metadata only without taking on the runtime lowering surface.

4. **sprefa_parse-as-dev-dep was a leftover** from when pipeline didn't touch the host CST. rule_def::collect needs host_parse_with_injections to count brace-body pipes (the host grammar parses `{...}` as opaque text; the inside must be re-parsed). Promoting to [dependencies] is correct.

5. **User flagged the architectural smell** that lower-time logic was sitting in server/. Both sprefa-run (binary) and DocSession (library) are consumers of the lower; shared walking belongs in pipeline. The refactor was cheap because rule_def::collect was already the local helper in session.rs — just lifted.

6. **predicate_suffix_present walks ?-token children** because tree-sitter exposes the literal '?' as an anonymous-token child between name and paren. The OpInvocation type has a predicate flag for this, but the hover path operates on raw tree-sitter Nodes (not the typed wrapper), so we walk children directly.

## Open Questions

1. **rule_def shared walker home.** Currently pipeline::rule_def. Should it move to a future "lower" subcrate alongside other parse-to-Pipeline pieces, or stay in pipeline? V0 punt: keep in pipeline; revisit if a third consumer appears.

2. **Rule call hover does not currently use the lowered_pipes path.** It uses the static_doc fallback (registry.doc -> rule_doc). render_enriched_hover for rule sites still bails because the lowered slot has op=None. Fixing this would let rule calls show config banner + pipe position + diagnostics. Out of scope for v0; file as enhancement card if user wants it.

3. **rule_doc body content is minimal.** Doesn't show: live invocation count, recent rule_row samples, exit-row count, link to body source. The card description (1uf) listed all of these as goals; current shape is "v0 minimal" — the hooks (file path, line, params) are enough to make a working hover. Live counts require RtCtx access at hover time which DocSession doesn't currently have.

4. **_2_rule.sh failure shape:** auto-fire of multi-pipe rule body should iterate per arm with header "rule N pipe K — M rows" but currently prints "rule N (auto)". Likely needs sprefa-run print logic to know about Pipeline::Fork shape and label arms. Pre-existing; not in scope.
