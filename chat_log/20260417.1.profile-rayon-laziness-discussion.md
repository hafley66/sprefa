### Rayon retrofit on ast op
`v2/src/ops/_9_ast_grep.rs` — replaced the serial `for c in batch` loop with:
1. **Phase 1 (async)** — `futures::future::join_all` over `prep_cursor(c, reader)`.
   Each future resolves PATH B (content already on cursor) or PATH C
   (`reader.bytes().next().await`). Output: `Vec<Prep>` with hydrated bytes.
2. **Phase 2 (rayon)** — `tokio::sync::oneshot::channel` + `rayon::spawn` +
   `preps.into_par_iter().map(process_one).collect()`. Oneshot bridges back
   into async. `rx.await` yields to tokio until rayon completes.
3. Diags re-emit on the async side via `DiagSink` (which is
   `Arc<dyn Fn + Send + Sync>`, so it could be called from rayon too, but
   keeping diag emission on the async side makes ordering obvious).

State that crosses into rayon: `lang: SupportLang` (Copy), `Arc<Pattern>`,
`Arc<Vec<(String, Regex)>>`, `Arc<Vec<Arc<str>>>`, `Arc<ParseSite>`. All
Send+Sync. Prep stores `Arc<bytes::Bytes>` (not `Vec<u8>` — the cursor type is
`Option<Arc<bytes::Bytes>>` and Reader::bytes returns `Bytes`).

`rayon = "1"` added to `v2/Cargo.toml`.

`process_one` is a free function (not a closure) — makes rayon's Send bounds
land on obvious named types when they're violated.

## Discussed but landed nowhere: laziness semantics

User observation: at 4 revs × ~110 files, the system does 4× the work of a
single-rev scan. Cost is visible. Prompted a design discussion on whether
laziness should be a language primitive.

Options walked, all eventually rejected:

1. **`$V!` on captures** (Haskell-bang flavor) — "make this capture eager."
   Rejected because: mixes binding with amplification; scanning for cost
   requires reading every capture.

2. **`op!` after op name** — "this op enumerates." Lazy default on `rev`/`repo`
   (HEAD / workspace-detected), eager on `fs` / `ast` always. Felt clean but
   user rejected because: "i dont like feeling of mixing eager/lazy based on op."

3. **Uniform per-op `op!`, lazy everywhere** — every op lazy by default, `!`
   opts in. fs would default to "first matching file" which is weird but
   consistent. Walked briefly, got complicated when user brought up Prolog.

4. **Positional `!` as Prolog cut** — `> fs > ! > ast` commits upstream, runs
   downstream normally. Prolog-authentic. Rejected because: opposite polarity
   from Haskell bangs (which mean "strict/eager"), and user wanted "fs exhausts
   always," not "user controls what cuts."

5. **Metacalls — `once(op)`, `take(N, op)`** — per-op wrappers, SQL-LIMIT-ish.
   Reserved as option but not picked.

6. **Drop axis-op captures entirely** — user noted that in ast-grep tradition,
   binding must be in the pattern. Axis ops (repo/rev/fs) take filters only;
   captures come only from pattern ops (ast/json/marker/md/line). `&.repo`,
   `&.rev`, `&.fs` cursor_ref + scan-pointer sigils reach axis values from
   inside patterns. This was the cleanest surface of the session. Would have
   required removing `RevMode::Bind` / `RepoMode::Bind` and migrating
   `g1_fns.sprf` from `rev($V)` → `rev!`. Not pursued — user decided not to
   change semantics.

**User's final position:** keep current semantics — everything enumerates, ast-grep/prolog style, matching-all is the point. Optimize Rust hard instead.
No syntactic laziness added.

Prior art surveyed during the discussion (for future reference):
- Prolog `!` = positional cut. `once/1` = first solution. `findall/3` = eager.
- Mercury `cc_multi` = committed-choice determinism.
- miniKanren `run 1` vs `run*` = driver-level cardinality.
- Haskell `!` = strictness / force evaluation (opposite polarity from Prolog).
- SQL `LIMIT N` / `LIMIT ALL`.
- XPath `[1]` / `//`.

> each, that is fucking nothing lol, we optimize the living fuck out of
> git2/fs/ast/cpu bound shit with rayon streaming etc."

Priorities, in order:

1. **Verify the dep opt-level bump is real.** `cargo clean && cargo build` and
   retime. If debug drops sub-3s from the bump alone, profile lever confirmed.
   If no change, the profile block is a no-op and we should investigate why.

2. **fs op rayon-ization.** Currently single-task git2 blob enumeration across
   revs serial. Release run shows fs phase = 391 ms out of 533 ms total. Port
   fs op to rayon over (repo, rev) + glob walk. The ast op's
   async-prefetch → rayon-map pattern transfers directly.

3. **Tree-sitter tree cache.** If the same (repo, rev, file) is parsed by
   multiple ops or multiple rules, cache the parsed tree. Currently every ast
   op call re-parses. Needs a keyed cache on (repo_hash, rev_hash, path,
   file_hash). Probably lives on `ServerState` or behind Reader.

4. **fs enumeration via git2 batch.** git2's tree walking is serial per tree.
   Walk the whole tree once, filter the glob in-memory, hand to rayon. No
   per-file libgit2 calls.

5. **Extract the rayon bridge helper.** The ast op has
   async-prefetch + rayon::spawn + oneshot + collect inline. Factor into
   `v2/src/_util_parallel.rs` or similar once a second op (fs) uses it. Shape
   already validated; extraction is mechanical.

6. **Runtime tuning.** `sprefa-server` main currently defaults tokio settings.
   Worth explicitly capping tokio blocking pool = num_cpus, rayon pool already
   defaults to physical cores. Verify rayon + tokio aren't fighting over CPU.

7. **Diag noise.** 422 diags per smoke run, mostly `AstDiag::NoMatch` at
   `Severity::Error`. ~393 false errors per run = Box allocations + formatting
   cost. Demote to Hint or drop when "no match" is the common case. Perf side
   effect + UX win.
