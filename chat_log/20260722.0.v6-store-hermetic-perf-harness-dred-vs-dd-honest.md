## Key measured findings (PERF-REPORT.md)
- All correct engines produce BYTE-IDENTICAL output (hashes verified cross-process);
  inputs verified identical too.
- Counting: fast + correct on DAGs (~0.44s @ 960k, 29 stmts), WRONG on cycles
  (keeps phantom rows — flagged NO).
- DRed loop: correct on cycles, ~5x slower than counting (~2.05s @ 960k, 75 stmts).
  Cost = two passes (over-delete cone + rederive), NOT sqlite abuse.
- DRed CTE: ~20% SLOWER than loop despite 6 stmts (recursive CTE loses to the
  index-driven temp-table frontier loop). Known lab result, now reproduced.
- dd: fastest (~0.17s @ 960k) but RESIDENT — rust_live ~215 B/node (618MB @ 2.9M).
  Store rust_live 0.09MB FLAT (state on disk). That's the whole tradeoff.
- Breakpoint HONEST CAVEAT: at 5.76M all engines abort on the SHARED in-RAM graph
  BUILDER (benchgraph holds whole graph pre-insert), NOT the retract. Store's real
  engine memory is the matrix rust_live column, not the ramp.

## Key Insights
- Hermetic = one process per engine, else arrangements/allocator/cache bleed.
- Correctness via blake3 hash equality across processes, never in-process compare.
- Never count corpus residence: drop staging + graph before timing the op.
- CTE-is-faster is FALSE for this workload (measured). Loop with TEMP tables +
  PK-driven frontier joins wins.
- DRed's cost is algorithmic (2 passes), not sqlite misuse. On DAGs counting
  dominates; DRed only justified on cycles.
- The shared in-RAM graph builder is a harness artifact that masks dd's true wall
  at extreme scale — needs streaming gen (G6) to show store-survives-dd-dies.
