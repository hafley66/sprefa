## Source Findings

### 1. Transaction Is Mandatory Baseline

SQLite official speed notes say wrapping many inserts in a transaction avoids repeated close/reopen/cache invalidation work between statements.

Source: [SQLite Database Speed Comparison](https://www.sqlite.org/speed.html)

Current code already uses:

```rust
let tx = conn.transaction()
```

for `insert_batch`, so the major transaction footgun is already closed.

### 2. Sync And Journal Mode Are Durability/Speed Knobs

SQLite docs state `synchronous=NORMAL` in WAL mode keeps atomic/consistent/isolated behavior but may lose durability across power loss. `synchronous=OFF` is faster but hands safety to the OS and can risk corruption or lost durability depending on mode and crash shape.

Source: [SQLite PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)

Current likely posture:

```text
runtime DB should default to safe-ish WAL/NORMAL for normal use
perf stress can optionally expose unsafe load mode
```

Do not silently change production durability semantics to chase benchmark numbers.

### 3. Host Parameter Limit Is Runtime Specific

SQLite official limits document says max host parameter number defaults to `32766` on modern SQLite, and can be changed at compile time or lowered at runtime via `sqlite3_limit`.

Source: [SQLite Limits](https://www.sqlite.org/limits.html)

Observed mismatch:

```text
sqlite3 CLI compile_options: MAX_VARIABLE_NUMBER=500000
rusqlite bundled runtime error: variable number must be between ?1 and ?32766
```

Conclusion:

```text
Do not trust system sqlite3 CLI for rusqlite bundled limits.
The process connection decides the limit.
```

Current safe code budget:

```text
SQLITE_PARAM_BUDGET = 32000
```

Better future telemetry:

```text
report sqlite variable limit from the exact rusqlite connection
```

### 4. Prepared Statement Reuse Is The Normal SQLite Bulk Insert API

Rusqlite docs expose `Transaction::prepare` and statement execution. The common pattern is:

```rust
let tx = conn.transaction()?;
let mut stmt = tx.prepare("INSERT INTO t(a,b,c) VALUES (?1,?2,?3)")?;
for row in rows {
    stmt.execute(params![row.a, row.b, row.c])?;
}
tx.commit()?;
```

Source: [rusqlite Transaction docs](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html)

SQLite prepared statements have fixed SQL text. A 1-row `VALUES` statement and a 1000-row `VALUES` statement are different SQL strings, so there is no stable reusable prepared statement for arbitrary batch width unless the width is fixed.

Implication:

```text
single-row prepared loop:
  many sqlite3_step calls
  one parse/prepare

dynamic multi-row VALUES:
  fewer sqlite3_step calls
  repeated parse/prepare of huge SQL text
  many bind slots
```

Measured in this workload:

```text
single-row prepared was faster than giant dynamic VALUES
```

### 5. Multi-Row VALUES Is Legal But Limit-Bound

SQLite `INSERT` supports one or more rows via `VALUES`.

Source: [SQLite INSERT](https://www.sqlite.org/lang_insert.html)

But every placeholder consumes host parameter budget. For our fact row:

```text
params_per_row = 4
max safe params ~= 32766
max rows per statement ~= 8191
```

That yields a lower bound of roughly:

```text
706778 / 8191 ~= 87 statements for hit_pairs
```

Total observed with all tables:

```text
sqlite_insert_exec_calls=127
```

So the call count is close to the host-parameter floor. More pitter-pattering on `VALUES` width cannot make it one call without changing the load strategy.

### 6. INSERT INTO ... SELECT Is A First-Class SQLite Form

SQLite supports:

```sql
INSERT INTO dest(col1, col2, ...)
SELECT ...
FROM source
```

Source: [SQLite INSERT](https://www.sqlite.org/lang_insert.html)

Official docs phrase it as inserting one row for each row returned by the SELECT.

This is the path that matches our workload better than dynamic `VALUES`:

```text
stage rows once
then INSERT INTO facts SELECT id_hex, col_id...
```

### 7. Indexes During Load Are Expensive

SQLite indexes are independent schema objects and can be dropped/recreated.

Source: [SQLite CREATE INDEX](https://www.sqlite.org/lang_createindex.html)

Current experiment:

```text
drop secondary fact indexes before huge insert
recreate after insert
keep _id UNIQUE live
```

Measured:

```text
index_drop_ms ~= 0.4-0.6
index_create_ms ~= 450-704
```

This is worth keeping as telemetry-controlled behavior, but it did not solve the remaining insert path by itself.

## What This Means For sprefa

### Current Dynamic VALUES Path

Current shape:

```text
Rust cursor rows
  -> compute id_hex
  -> intern strings
  -> build huge SQL VALUES text
  -> bind N values
  -> execute
```

Pros:

- Reduces SQLite statement executions.
- Telemetry can now prove actual SQLite exec count.

Cons:

- Builds large SQL strings repeatedly.
- Parses those strings repeatedly.
- Still constructs Rust cursor payloads.
- Still converts string values into ids in Rust-side batches.
- Does not beat prepared one-row loop in current measurement.

### Prepared One-Row Loop

Shape:

```text
prepare once
for row:
  bind 4 params
  step
```

Pros:

- Small stable SQL.
- Low parse cost.
- Measured faster than giant `VALUES` in this workload.

Cons:

- Statement execution count is high.
- Telemetry must label this clearly as inner SQLite row-loop behavior.

### Staging Table + INSERT SELECT

Target shape:

```text
CREATE TEMP TABLE stage_hit_pairs(
  id_hex TEXT NOT NULL,
  fs_id INTEGER NOT NULL,
  lo_id INTEGER NOT NULL,
  other_lo_id INTEGER NOT NULL
);

load stage

INSERT OR IGNORE INTO hit_pairs_facts(_id, FS_id, LO_id, OTHER_LO_id)
SELECT id_hex, fs_id, lo_id, other_lo_id
FROM stage_hit_pairs;
```

This changes the expensive part from:

```text
Rust builds giant INSERT VALUES commands
```

to:

```text
SQLite copies from one table cursor to another table cursor
```

Expected advantages:

- One stable `INSERT INTO ... SELECT` statement per destination table.
- No giant SQL `VALUES` text.
- No host parameter pressure for final fact table insert.
- Can sort/order stage before insert if helpful.
- Better fit for future SQL fusion where terminal SQL output is already inside SQLite.

Remaining cost:

- Need load stage rows somehow.
- Need generate `id_hex`.
- Need map output strings to `sprf_strings.id`.

## Best Next Architecture

### Dedicated Terminal Fact Sink For SQLite

Add a SQLite-specific fast path for terminal SQL fact writes:

```rust
run_sql_terminal_fact_on_sqlite_store(
    source_store: &SqliteFactStore<Cursor>,
    sql: &str,
    referenced_tables: &[String],
    input_batch: &[&Cursor],
    output_table: &str,
)
```

Avoid:

```text
Vec<Arc<Cursor>> for all terminal rows
FactWrite::render_batch
dynamic multi-row VALUES for final fact table
```

Prefer:

```text
SQL query -> stage table -> intern/map ids -> INSERT INTO facts SELECT
```

### Stage Schema

For `hit_pairs`:

```sql
CREATE TEMP TABLE stage_hit_pairs_raw(
  id_hex TEXT NOT NULL,
  FS TEXT NOT NULL,
  LO TEXT NOT NULL,
  OTHER_LO TEXT NOT NULL
);
```

Then intern values:

```sql
INSERT OR IGNORE INTO sprf_strings(value)
SELECT FS FROM stage_hit_pairs_raw
UNION
SELECT LO FROM stage_hit_pairs_raw
UNION
SELECT OTHER_LO FROM stage_hit_pairs_raw;
```

Then id-mapped stage:

```sql
CREATE TEMP TABLE stage_hit_pairs_ids AS
SELECT
  r.id_hex,
  s_fs.id AS FS_id,
  s_lo.id AS LO_id,
  s_other.id AS OTHER_LO_id
FROM stage_hit_pairs_raw r
JOIN sprf_strings s_fs ON s_fs.value = r.FS
JOIN sprf_strings s_lo ON s_lo.value = r.LO
JOIN sprf_strings s_other ON s_other.value = r.OTHER_LO;
```

Then final insert:

```sql
INSERT OR IGNORE INTO hit_pairs_facts(_id, FS_id, LO_id, OTHER_LO_id)
SELECT id_hex, FS_id, LO_id, OTHER_LO_id
FROM stage_hit_pairs_ids;
```

This reduces final table insert to one SQLite statement.

### `_id` Computation

Need deterministic row id:

```text
_id = blake3(table || canonical projected cols)
```

Options:

1. Rust computes `_id` while streaming terminal SQL rows into `stage_raw`.
2. Register a SQLite scalar UDF for row id computation.
3. Push canonical id computation into SQL using a non-blake hash only if identity semantics change, currently not acceptable.

Best next prototype:

```text
Rust computes id_hex while reading SQL output rows,
but writes to stage_raw only.
Final table insert is INSERT SELECT.
```

This still streams SQL output through Rust once, but it avoids rebuilding all final fact rows as cursors and avoids dynamic final `VALUES` inserts.
