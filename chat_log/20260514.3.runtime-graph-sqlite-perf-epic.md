## Thread Frame

The thread started around v4 LSP/retraction behavior for edits to HEAD files:

- Need deterministic invalidation for unstaged HEAD changes.
- Need durable runtime graph state in SQLite, not process-local RAM identity.
- Need source/subscription/wake mechanics that can resume after restart.
- Need RxJS/React-reconciler mental model translated into Rust/SQLite terms.
- Need support retraction where output rows remain visible while any owner still supports them.
- Need future impure/stateful operators such as `poll`, `switchMap`, `combineLatest`, `merge`, RSS, git diff, and external event sources.

Core design phrase:

```text
run to completion, persist graph/state in SQLite, wake/re-render affected owners later
```

## Runtime Graph Substrate

The implemented model stores generic graph rows with typed Rust wrappers:

- `runtime_node`
- `runtime_edge`
- `runtime_value`
- `runtime_edge_value`
- `runtime_event`

Typed nouns:

- `OwnerNode`
- `SourceNode`
- `OutputNode`
- `RowNode`
- `SubscribeEdge`
- `SupportEdge`
- `ActiveEdge`
- `RuntimeValue`

Identity rules:

- Logical ids are URI-shaped.
- URI/kind/label/mode strings intern through `_strings`.
- Durable graph identity avoids queue ids, process-local counters, and pointers.
- Runtime graph rows store ids/refs, not repeated payload strings.

Important semantics:

- `owner --subscribe(label)--> source`
- `owner --support--> row`
- `row --member_of--> table`
- `owner --active(active-inner)--> child_owner`
- `runtime_event` is append-only source wake history.
- Edge-local values hold subscribe readiness, not source-global values.

## React / RxJS Translation

React-ish mapping:

```text
render()        = re-run owner operation
DOM             = durable graph/fact rows in SQLite
effects         = source subscriptions / wake actions
reconciliation  = compare supports/subscriptions/active edges by durable keys
```

RxJS-ish mapping:

```text
subscribe       = durable subscribe edge
next value      = wake event plus edge-local latest value
combineLatest   = reads all subscribe edge readiness slots
merge           = emits from whichever edge receives an event
switchMap       = replaces active child edge and retracts old child supports/subs
```

Key distinction:

```text
React holds DOM in memory.
sprefa stores the rendered graph/facts in SQLite and can resume without RAM identity.
```

## Sprf Runtime Surface Direction

Several design discussions converged on:

- Keep operator bodies pure where possible.
- Runtime subscription should be an effect/action, not hidden local state.
- Prefer rule bodies over sending values into zero-arity rules as fake subjects.
- Avoid new DSL sigils when existing pipe/block/rule/type syntax can express the shape.
- Future operator declarations should allow action/event facts with minimal repetition.

Example direction that came up:

```sprf
action(`ghcache`, `pull_request_changed`);
```

And more structural experiments:

```sprf
ghcache > FAM? > pull_request_changed > EVENT? > type {
    repo > String;
    number > i64;
}
```

No final syntax landed in this perf pass.

## Queue / Replay Direction

The queue was reframed as:

- Useful proof mechanism for replay and resumption.
- Eventually should be less central for durable runtime graph wake/replay.
- External events should become source wake keys into the runtime.
- Sprf-specific action enum can be built from declared operator/action facts later.

Current note:

```text
replayable queue proves the model, but long-term runner should consume durable wake jobs/events from graph state.
```

## Major Perf Findings

### Codec

`cursor_codec_stress` showed codec was not the wall-clock bottleneck:

```text
binary_encode 73.8ms for 706778 rows
binary_decode 481.3ms
json_encode 526.7ms
json_decode 1461.0ms
```

Codec matters, but not enough to explain 100s, 18s, or 14s runs.

### Queue

Queue stress showed raw SQLite queue movement was seconds, not 100s:

```text
enqueue ~= 3.5s to 4.2s for 706778 payloads
raw drain ~= 2.2s
queue API drain ~= 3.2s
```

Queue was not the only problem.

### SQL In-Memory Materialization

Old path used temp in-memory SQLite tables and copied fact tables out of the real store.

Direct SQLite fact-store views cut the catastrophic path:

```text
before direct SQLite:
  SqlQueryComponent wall ~= 77.5s
  run wall ~= 98.7s

after direct SQLite:
  SqlQueryComponent wall ~= 7.5s
  run wall ~= 18.1s
```

Direct SQLite path:

- Creates temp `input`.
- Creates temp views over real `*_facts` tables.
- Joins through `sprf_strings`.
- Avoids copying entire fact tables into an in-memory SQLite DB.

## RSS Reduction Passes

Initial RSS after direct SQLite:

```text
rss_peak_MB ~= 1625
```

Main causes:

- SQL output materialized as `Vec<Node<Cursor>>`.
- Terminal fact sink called `FactWrite::render_batch`, cloning all output cursors.
- `FactWrite::render_batch` returned `Node::Emit` values that terminal SQL discarded.
- `SqliteFactStore::insert_batch` chunk loop cloned every `Arc` payload.
- `pending` stored full accepted cursors until commit.

Changes:

- Terminal SQL bypasses `FactWrite::render_batch`.
- Terminal SQL reads SQL rows into output cursors directly.
- `SqliteFactStore::insert_batch` consumes owned `Arc`s instead of cloning each row.
- Pending commit state stores `(table, row_id)` instead of full cursors.

RSS measurements:

```text
1625 MB -> 907 MB -> 874 MB -> 735 MB -> ~722-742 MB range
```

## Commit Fanout Fix

Commit was ~3.8s because every row dirty event did:

```text
EventBus::dispatch_dirty(row)
  lock listeners
  clone listener vec
  DirtyQueuePromoter dispatch_park(row key)
```

for ~776k pending row ids.

Changes:

- Added `EventBus::dispatch_dirty_batch`.
- Added listener batch hook.
- Added `QueueBackend::has_parked_domain`.
- Dirty queue promoter skips all row-key dispatches when no parked rows exist for that domain.

Commit went:

```text
commit ~= 3.8s -> ~= 45-95ms
```


### Param Limit Check

CLI showed:

```text
MAX_VARIABLE_NUMBER=500000
```

But bundled `rusqlite` runtime failed at:

```text
variable number must be between ?1 and ?32766
```

So the real safe budget is process/runtime-specific.

The code was set to:

```text
SQLITE_PARAM_BUDGET = 32_000
SQLITE_FACT_CHUNK_ROWS = 100_000
```

Latest measured:

```text

sqlite_insert_exec_rows=776117
sqlite_insert_ms=5669.1
wall_ms=15428.4
rss_peak_MB=730
```

This got calls down:

```text

```

But performance stayed worse than best prepared row loop:

```text
best prepared row loop sqlite_insert_ms ~= 4248
current giant VALUES sqlite_insert_ms ~= 5669
```

## Current Technical Diagnosis

The remaining big problem is not:

- queue outer API
- commit fanout
- codec
- fact-store outer insert call count
- mounted SQL output persistence
- index rebuild visibility

The remaining big problem is:

```text
terminal fact sink still constructs Rust rows and sends them back to SQLite through generated INSERT shapes
```

Two bad options were measured:

```text
prepared one-row execute:
  more exec calls, faster than giant SQL in this setup

giant VALUES execute:
  fewer exec calls, slower due dynamic SQL parse/bind size
```

## Next Target

Next credible fix:

```text
SQLite staging table + set-oriented INSERT INTO facts SELECT ...
```

Shape:

1. Terminal SQL produces output rows.
2. Instead of converting to full `Cursor` rows and huge dynamic `VALUES`, write to a temp/staging table.
3. Intern strings in bulk.
4. Insert facts from staging with `INSERT OR IGNORE INTO <table>_facts SELECT ...`.
5. Compute or carry `_id` in staging.
6. Rebuild indexes if large batch.

Needed decision:

```text
How to compute _id for staged rows without rehydrating full Cursor payloads?
```

Options:

- Rust computes `_id` while streaming SQL row results into staging.
- SQLite UDF computes `_id` from projected columns.
- Terminal SQL sink bypasses `Cursor` entirely and writes `(id_hex, col_id...)` rows.

Most direct next implementation:

```text
terminal fact sink emits rows as (id_hex, Vec<i64 string_ids>) and inserts those through a dedicated SqliteFactStore path
```

This avoids:

- Cursor object churn.
- Rehydrating full row maps.
- Huge dynamic SQL strings.
- Per-row prepared statement execute.
