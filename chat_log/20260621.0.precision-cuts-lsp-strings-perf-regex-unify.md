## Problem/Context
The session had five distinct work units, each closing a documented gap:

### 1. call_kind builtin (precision gap #1 from session 8)
The conn-loop-reachable rail fired on every `.conn()` in a loop-reachable
fn, regardless of whether the fn actually wrote. The fix: classify each
fn's calls as read/write by bare callee name, join on write only.

### 2. loop_entry_fn (precision gap #2, queued since session 3)
The rail's base case was `loop_hot_fn` (fn CONTAINS a call in a loop).
Transitive closure from that over-approximated: per-tick one-shots called
from tick's call tree were transitively loop-reachable but not per-
iteration. The fix: `loop_entry_fn` (fn is CALLED FROM a loop-nested site).

### 3. Phase C hover + Phase E def_target (north-star gaps)
LSP had textDocument/definition (module-edge only) and references. No
hover. No rule-driven go-to-def. Phase C: auto-synthesize hover markdown
from type_entity + call_def. Phase E: program-declared def_target rel
drives go-to-def, falling back to module_edge.

### 4. split/replace string functions (Known gap: "String manipulation is thin")
No way to split/replace a BOUND text value in a derived rule. Every cross-
format query needed it (last path segment, package from import, etc.).
Added Term::Call variant for split/replace, plus computed bindings and
unary minus as engine improvements that fell out.

### 5. Perf regex fix + regex unification
The stress.dl `/./` regex matched every CHARACTER (16.7M rows), not every
line. Fixed to `/$/` (204s -> 19.6s debug, 5.4s release). Then unified
the two regex forms: `=~` now takes `/pat/` literal, not `"string"`.

## Solution/Approach

### S1: call_kind(fn, kind)
Added `call_kind` to CALL_RELS (const at engine.rs:82). Classified in the
existing site loop of refresh_call_rels: for each call_site, if the bare
callee name is in the write set (execute/execute_batch/execute_returning)
or read set (prepare/query_row/query_map/etc.), emit (caller, kind).
Deliberately dropped collection-shaped names (insert/update/delete) that
collide with HashMap::insert. Rail joins `call_kind(fn, "write")`.

### S2: loop_entry_fn
Replaced the loop_hot_fn base with a tighter join chain in rails.dl:
nest(call_id) -> df_node(call_id, caller, p, l) -> call_site(caller,
callee_text, p, l) -> call_name(fn, callee_text). 43 fns dropped (top-
level entries like run_check/run_lsp), 0 .conn()-bearing fns affected.

### S3: Phase C hover + Phase E def_target
- Engine::hover(file, text) joins type_entity(name=text) + call_name ->
  call_def. Returns markdown. No new builtin.
- Engine::definition_targets upgraded to consult def_target rel first
  (queried by column name like diag), fall back to module_edge. Returns
  (file, line) pairs; Locations now point at real lines.
- lsp.rs: hover_provider capability + handle_hover. def_target join in
  handle_definition.
- 2 new lsp_protocol tests.

### S4: split/replace
- Term::Call { name, args } variant in ast.rs. Parser detects ident(args)
  in term position. Lower.rs: replace is SQLite-native, split is the new
  sprf_split UDF in db.rs (returns NULL for out-of-range, dropping the
  row via IS NOT NULL guard).
- Three engine improvements fell out:
  - Unary minus: `-1` desugars to `0 - 1` (natural negative idx)
  - Computed bindings: `x = split(...)` in a body binds x to the expr
    (previously an unbound var on a Cmp side was always an error)
  - IS NOT NULL guards: head terms containing Call get NULL-filtered

### S5: perf fix + regex unification
- stress.dl `/./` -> `/$/`: the regex `.` with captures_iter matches every
  character position. 16.7M bind expansions -> 581k. The deeper bug (no
  projection pushdown) noted but not fixed.
- `=~` constraint parser changed to require Tok::Regex instead of term.
  10 usage sites updated across examples + tests. `~~` (glob) keeps
  strings (/ is a path separator in globs).

## Key Insights
- The precision-tier framing (regex seed / AST confirm / graph edge) from
  session 8 was the right read. call_kind + loop_entry closed the two real
  precision gaps without touching the regex seed.
- call_kind's table must be deliberately narrow (rusqlite-shaped only).
  First pass had insert/update/delete/replace/commit -> 127 rows on v5/src,
  mostly HashMap::insert false positives. Tightened to execute* + prepare/
  query_row/query_map/query_and_then/query_named -> 44 clean rows.
- Per-fn aggregation `(fn, kind)` was chosen over per-site `(file, line,
  kind)` for call_kind. The rail's conn_fn join already pins the site; per-
  fn write-classification is the right cut. A fn with both read and write
  emits two rows.
- The v4 regex opinion is `${x?}` holes (bind) vs `${x}` (read), desugaring
  to named captures. Index-based capture is dead. v5's match op already
  uses `(?<name>...)` named groups; a bound-value regex op would mirror
  that when added.
- The biggest perf finding: `/./ ` in captures_iter matches every CHARACTER,
  not every line. 16.7M rows from 1483 files. The `/` -division heuristic
  in the lexer is NOT ambiguous after `=~` (the lexer already treats it as
  regex-opening), so the unification was a parser-only change.
- Term::Call follows the Arith positioning rules exactly: head columns and
  comparison sides, never a body-atom binding position. This made the
  integration minimal — same lower/typecheck/engine sites Arith already
  touched.
- Computed bindings (`x = split(...)`) in body_sql was a generalization
  that also benefits Arith (`x = line + 1`). The pattern: if a Cmp is
  `unbound_var = computation`, bind the var to the expr's SQL (same canon
  slot a Pos atom fills). No subquery needed; the expr is inlined at each
  use.
- The engine has NO projection pushdown. seen(path) <- scan, match(/$/, l)
  expands 581k binds for 1483 output rows. SQLite dedupes via INSERT OR
  IGNORE but the bind expansion + row construction is pure waste. This is
  the next perf lever.
- The north-star plan (2026-06-18) is now mostly landed: A1/A2/B/C/D/E all
  done. Only F (full SCIP) and G (CSS/XPath) remain, both on-demand.

## Open Questions
- Projection pushdown: is it worth the engine complexity? The stress test
  at 581k rows/1483 output isn't blocking (19.6s debug, 5.4s release). At
  500-repo polyglot scale it would matter.
- Regex capture over bound values: the v4 `${x?}` hole form is the design.
  When does a real program need it (vs split + replace covering the case)?
- The type/call/dataflow graph refreshers each syn-parse every .rs file
  independently (3x parse). Sharing the parse across the three extractors
  would cut ~2s off the stress cold tick (3.2s -> ~1.2s). Worth doing?
