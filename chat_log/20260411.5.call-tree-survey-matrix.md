# Call-tree survey: comparison matrix

**Date:** 2026-04-11
**Sources:** 12 raw reports at `20260411.4.call-tree-survey-raw-NN-*.md`
**Plan:** `20260411.1.call-tree-survey-plan.md`

## Method

One Haiku agent per repo, each producing a 24-field rigid schema block plus a free-form Analysis section with file:line citations. Reports range from 8 KB (graph-sitter) to 32 KB (codebase-memory-mcp), proportional to architectural surface area. Spot checks on `04-codebase-memory-mcp` and `01-sem` confirm citation density and accuracy.

### Axis-1 — who uses `locals.scm`?

Nobody. Every surveyed tool either rolls its own scope resolution (custom grammar files in C, per-language visitors in Python, HIR in rust-analyzer) or skips scope entirely (sem lexical, SocratiCode import-only). That is the single most surprising result of the survey: the tree-sitter standard file for scope queries is not what any of these tools reach for. Implication for sprefa: adopting `locals.scm` would be **path-breaking**, not path-following.

### Axis-2 — who preserves source order?

Four do: codebase-memory-mcp (byte range + enclosing FQN), tree-sitter-codeviews (per-statement CFG), graph-sitter (explicit Cython sort), rust-analyzer (IndexMap insertion + syntax order). Seven do not. sem explicitly does not (unordered `Vec<EntityRef>`, parallel rayon collection). sprefa would join a minority that treats ordering as first-class, which is the stated differentiator.

### Axis-3 — query surfaces in use

- **Cypher subset compiled to SQL**: codebase-memory-mcp (the only one).
- **Fixed commands**: sem, cymbal, grepai (trace-callers/callees depth N).
- **Imperative API**: graph-sitter (FunctionCall objects, no text DSL).
- **Graph library in-process**: tree-sitter-codeviews (NetworkX), stack-graphs (Rust crate).
- **LSP protocol message**: rust-analyzer (CallHierarchyIncomingCall, outgoing, no DSL).
- **HTTP REST + parameterized filters**: CodeRLM, SocratiCode.

The datalog-to-SQL space sprefa targets is **open**. codebase-memory-mcp is the closest neighbor; it is Cypher rather than datalog, and it lacks ordinal/branch-path columns, so the precise slot sprefa wants is unoccupied.

### Axis-4 — interop surface area

| Interop | Tools |
|---|---|
| SQLite file (cross-language FFI via schema-as-ABI) | sem, cymbal, codebase-memory-mcp |
| MCP stdio JSON-RPC | sem, cymbal, grepai, codebase-memory-mcp, SocratiCode |
| Pure Rust library embeddable | rust-analyzer, stack-graphs, (sem-core) |
| Go cgo + SQLite FFI | cymbal, grepai |
| HTTP REST | CodeRLM, SocratiCode (Qdrant-backed) |
| Pure Python library | tree-sitter-codeviews, graph-sitter, ACER |
| In-memory only (no persistent store) | tree-sitter-codeviews, graph-sitter, ACER, rust-analyzer |

**SQLite file + MCP stdio** is the dominant shape for cross-language reach. Three of three Go tools (grepai with .gob is the one exception to SQLite) use it; codebase-memory-mcp (pure C) uses it; sem (Rust) uses it. For sprefa the choice is already pre-validated by the peer set: ship a SQLite file plus an MCP stdio server, and every existing agent/editor can drop in.
