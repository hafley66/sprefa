**Date:** 2026-04-11

## Method

One Haiku agent per repo, each producing a 24-field rigid schema block plus a free-form Analysis section with file:line citations. Reports range from 8 KB (graph-sitter) to 32 KB (codebase-memory-mcp), proportional to architectural surface area. Spot checks on `04-codebase-memory-mcp` and `01-sem` confirm citation density and accuracy. All 12 raws stitched for this matrix.

## Headline findings

### Finding 1 — nobody uses `locals.scm`

Zero of twelve. Every surveyed tool either rolls its own scope resolution (custom grammar files in C, per-language visitors in Python, HIR in rust-analyzer, push/pop stacks in stack-graphs) or skips scope entirely (sem lexical blacklist, SocratiCode import-only, codedb regex lines, ACER user-pluggable). The tree-sitter standard file for scope queries is absent from every one of them. **Implication for sprefa:** adopting `locals.scm` is path-breaking, not path-following. If it works it's a free win; no peer has validated it for you.

Related: **graph-sitter explicitly rejects tree-sitter queries** — 56k LOC of imperative NodeClasses factories instead of .scm files. That's a deliberate design position, not an oversight.

### Finding 2 — source-order preservation splits 7-vs-5

**Preserve order (7):** cymbal, grepai, codebase-memory-mcp, CodeRLM, tree-sitter-codeviews, graph-sitter, rust-analyzer. Add codedb on a technicality (symbol ranges, but no call edges).

**Lose order (5):** sem, SocratiCode, ACER, stack-graphs (n/a), plus sem as the baseline. sem's loss is explicit in `extract_references_from_content` — parallel rayon collection into unordered `Vec<EntityRef>`. ACER's loss is structural — Dict[K, Set[V]] throws away ordering by definition.

**Mechanisms used by the preserving camp:**

- **byte range + enclosing FQN** (codebase-memory-mcp)
- **refs.line column + SQL `ORDER BY line`** (cymbal)
- **Reference.Line + CallGraph insertion order** (grepai)
- **per-statement CFG with pos_next/neg_next encoded in edge type** (tree-sitter-codeviews — by far the richest)
- **Cython sort.pyx by ts_node.start_byte** (graph-sitter — dedicated compiled module for it)
- **FxIndexMap + syntax tree pre-order descent** (rust-analyzer)

The cheapest mechanism is the (file, line) column pair. The richest is tree-sitter-codeviews's pos_next/neg_next/loop_control edge-type encoding, which gives a proto-CFG for free. **sprefa should take the (ordinal, branch_path) column pair** — ordinal for source order, branch_path for then/else/loop context — and be the second tool after tree-sitter-codeviews with branch-path columns, and the first to expose them via a query surface.

### Finding 3 — the datalog-to-SQL query space is empty

- **Cypher subset compiled to SQL**: codebase-memory-mcp (only one). Variable-length paths `*1..3`, MATCH / WHERE regex / RETURN aggregates.
- **Fixed commands**: sem, cymbal, grepai, codedb (MCP tools). No query composition.
- **Imperative Python/Rust API**: graph-sitter (FunctionCall objects), rust-analyzer (Analysis::incoming_calls), stack-graphs (Rust crate).
- **Graph-library-in-process**: tree-sitter-codeviews (NetworkX MultiDiGraph with edge_type strings — no DSL, just traversal).
- **LSP protocol message**: rust-analyzer (CallHierarchyIncomingCall / Outgoing). Protocol-defined, no composability.
- **HTTP REST + parameterized filters**: CodeRLM, SocratiCode (Qdrant-backed).
- **tree-sitter-graph DSL**: stack-graphs — but this is a build-time rule language, not a query-time DSL.
- **CLI with file:line args**: stack-graphs `query definition PATH:LINE:COL`.

**Nobody ships datalog.** Nobody ships a path-pattern DSL similar to ast-grep. The closest neighbor is codebase-memory-mcp's Cypher-subset, but it's Cypher (property-graph) rather than datalog (relation), and it **lacks ordinal / branch-path columns**. The precise slot sprefa wants — datalog-style path queries over ordered call-site rows in SQL — is unoccupied.

### Finding 4 — interop concentration

| Interop | Tools |
|---|---|
| SQLite file (cross-language via schema-as-ABI) | sem, cymbal, codebase-memory-mcp, stack-graphs |
| MCP stdio JSON-RPC | sem, cymbal, grepai, codebase-memory-mcp, codedb, SocratiCode |
| Pure Rust library embeddable | rust-analyzer, stack-graphs, (sem-core) |
| Cgo binding (requires C FFI) | cymbal, grepai |
| HTTP REST | CodeRLM, SocratiCode (Qdrant), codebase-memory-mcp (UI), codedb |
| Pure Python library | tree-sitter-codeviews, graph-sitter, ACER |
| In-memory only (no persistent store) | tree-sitter-codeviews, graph-sitter, ACER, rust-analyzer, CodeRLM |
| WASM-buildable today | codedb (explicit Cloudflare Workers target) |

**SQLite file + MCP stdio** is the dominant cross-language shape. 4 of 4 systems-language tools with persistence use SQLite. 6 of 12 ship MCP. For sprefa the choice is pre-validated: ship a SQLite file plus an MCP stdio server, every existing agent/editor drops in.

**WASM reality check:** of 12 tools, exactly one (codedb) has a working WASM target. Everyone else is "unknown" or "no." Shipping WASM extractors is not a validated path — it's a green field with one precedent in a Zig tool that doesn't even extract calls.

### Finding 5 — extractor mechanism splits three ways

1. **tree-sitter native bindings** (sem, cymbal, grepai, CodeRLM, graph-sitter, tree-sitter-codeviews, ACER) — the common case
2. **custom hand-rolled parsers** (codebase-memory-mcp in C, codedb in Zig) — the "control the extractor" path
3. **full semantic engine** (rust-analyzer via HIR/Salsa, stack-graphs via tree-sitter-graph DSL) — the "we gave up on string matching" path

**ast-grep appears exactly once** (SocratiCode's NAPI binding). **tree-sitter-graph appears exactly once** (stack-graphs). The ecosystem is dominated by direct tree-sitter node walks, not higher-level query languages.

### Finding 6 — branch-path preservation has one precedent

tree-sitter-codeviews is the only tool that encodes `pos_next` / `neg_next` / `loop_control` / `method_return` in edge types — a proto-CFG over tree-sitter, statement-granularity. It's Python-only, single-file-only, and stores results in NetworkX (no queryable store), but **the encoding idea is directly transferable**: store branch-path as a column alongside ordinal in sprefa's call_sites table, and the query surface gets "calls inside the then branch of conditional X" for free.

rust-analyzer preserves syntax descendant order but does not encode branch context. No one else even tries.

## Decision commentary

### Shell-bridge vs WASM extractor

Evidence from the survey:

- **WASM in the wild: 1/12.** codedb compiles to WASM for Cloudflare Workers. No one else. rust-analyzer's Salsa + HIR has no WASM feature flag. sem, graph-sitter, tree-sitter-codeviews all depend on tree-sitter native bindings (C) that don't portability-compile cleanly. ast-grep-napi (SocratiCode) is also native.
- **stdin/stdout friendliness: 7/12.** Every MCP-shipping tool is stdio-friendly by definition. The shell-bridge model is the *default* for the survey population.
- **Cgo/native binding pain: real.** cymbal and grepai both require `CGO_ENABLED=1`. This is the exact interop wall sprefa cares about — and the Go tools don't solve it; they live inside it.

**Recommendation for sprefa's extensibility seam:**

Go with the **shell/template bridge first**, not WASM. Reasoning:

1. The shape is pre-validated by 7 of 12 peers (every MCP shipping tool).
2. WASM requires a from-scratch extractor ecosystem — no peer has done it except for one Zig outlier.
3. A subprocess extractor can pipe *any* existing tool as an extractor: `ast-grep --rule foo.yml | sprefa ingest --ndjson`. That includes the existing Go ecosystem (cymbal, grepai) as possible inputs.
4. The ~2ms/file spawn cost disappears with a long-lived worker pool (standard LSP pattern, already shipping in sprefa-lsp).

Hold WASM as a **later fast-path** for the specific case of ast-grep rule bundling, once `ast-grep` stabilizes its WASM story. It's a genuine optimization, not a blocker.

### Where sprefa sits on the four axes, after the survey

| Axis | Position | Precedent |
|---|---|---|
| `locals_resolution` | **`locals.scm` first, fallback to custom scope stack** | nobody — green field |
| `call_order_preserved` | **yes, via ordinal + branch_path columns** | 6 peers preserve order; 1 (tree-sitter-codeviews) encodes branch context |
| `query_surface` | **datalog → SQL** | 1 peer (codebase-memory-mcp) ships Cypher→SQL; datalog slot is empty |
| `interop` | **SQLite file + MCP stdio + CLI** | 4 peers ship this exact combination |

Three of four axes have sprefa either in an open slot or joining a small validated minority. Only `locals.scm` is truly path-breaking. That's the one to de-risk early.

## Proposed sprefa `call_sites` schema

Row-per-call-site table, ordered within an enclosing entity.

```sql
CREATE TABLE call_sites (
  id              INTEGER PRIMARY KEY,
  file_id         INTEGER NOT NULL REFERENCES files(id),
  enclosing_id    INTEGER NOT NULL REFERENCES entities(id),  -- the function/method containing the call
  ordinal         INTEGER NOT NULL,  -- DFS pre-order index within enclosing_id, 0-based
  branch_path     TEXT NOT NULL,     -- "" top-level; "if[0].then" / "if[0].else" / "for[1].body" / "match[0].arm[2]"
  start_byte      INTEGER NOT NULL,
  end_byte        INTEGER NOT NULL,
  start_line      INTEGER NOT NULL,
  start_col       INTEGER NOT NULL,

  -- the call target, three-tier resolution
  callee_text     TEXT NOT NULL,     -- always set — raw name as it appears in source (e.g. "foo", "self.bar", "a.b.c")
  callee_entity   INTEGER REFERENCES entities(id),  -- set when scope resolution succeeds (band 2+)
  callee_kind     TEXT,              -- "function" | "method" | "constructor" | "macro" | "dynamic" | "unknown"
  receiver_type   TEXT,              -- method calls: the receiver expression's static type if inferable

  -- metadata
  is_awaited      INTEGER NOT NULL DEFAULT 0,  -- 1 if the call is awaited / .await'd
  arg_count       INTEGER NOT NULL,
  language        TEXT NOT NULL
);

CREATE INDEX idx_call_sites_enclosing ON call_sites(enclosing_id, ordinal);
CREATE INDEX idx_call_sites_callee_entity ON call_sites(callee_entity);
CREATE INDEX idx_call_sites_callee_text ON call_sites(callee_text);
CREATE INDEX idx_call_sites_file ON call_sites(file_id, start_line);
```

**Key design choices and which peer each is cribbed from:**

- `(file_id, enclosing_id, ordinal)` — follows cymbal's refs + EnclosingSymbol model, but ordinal is explicit rather than inferred from `(end_line - start_line)` span. Ordinal is computed at extraction time via DFS pre-order over `call_expression` nodes inside the enclosing entity's byte range.
- `branch_path` — cribbed from tree-sitter-codeviews's pos_next/neg_next edge encoding, but flattened into a string column so SQL `LIKE 'if[0].%'` works as a branch query. Zero peers do this at the storage layer; this is the sprefa differentiator.
- `callee_text` always + `callee_entity` sometimes — the "both" call edge model. sem stores only text, rust-analyzer stores only resolved IDs; sprefa stores both, in the style of cymbal (text-first, resolution post-hoc) but with the resolved-id column available when scope resolution succeeds.
- `is_awaited` — cribbed from graph-sitter's FunctionCall.is_awaited property.
- `receiver_type` — cribbed from grepai's Go receiver field tracking.

## Proposed sprefa path-query DSL (sketch)

Datalog-style, compiles to SQL joins over `call_sites` × `entities` × `files`. Surface syntax is illustrative — the storage schema is what matters.

```
# "what does login() call in source order"
?- call_site(c), enclosing(c) = $login, order_by(c, ordinal).

# "calls inside the then-branch of any if in login()"
?- call_site(c), enclosing(c) = $login, branch_path(c) ~ "if[*].then*".

# "direct callees of login() that are async"
?- call_site(c), enclosing(c) = $login, callee_entity(c) = f, entity(f, kind: "function"), is_awaited(c) = 1.

# "transitive callees, depth <= 3, preserving order"
?- call_reaches($login, f, depth: 1..3), order_by(f, discovery_ordinal).
```

**Key primitives:**

1. **Path patterns on branch_path** — glob-style over the dot-separated branch spec, like ast-grep's metavar fan-out but over the branch column. `if[*].then*` matches any `then` branch at any `if` depth. This is where the ast-grep-esque declarative feel lives.
2. **ordinal-preserving aggregation** — `order_by(c, ordinal)` compiles to `ORDER BY enclosing_id, ordinal`.
3. **Depth-bounded transitive closure** — `call_reaches(x, y, depth: 1..3)` compiles to a recursive CTE (WITH RECURSIVE) capped at 3 steps. Closest peer: codebase-memory-mcp's `*1..3` Cypher variable-length — but theirs loses order at depth >1; sprefa's compiles with a `discovery_ordinal` column so BFS/DFS order can be requested.
4. **Three-band callee matching** — match by `callee_text` (band 1 lexical), `callee_entity` (band 2 scope-resolved), or `callee_entity` + `receiver_type` (band 3 type-aware). Same query, different precision based on what extraction has populated.

## What this survey answered

The five questions from the plan's "What sprefa is trying to learn from this":

1. **Has anyone shipped call-order preservation?** Yes, 6 peers preserve it — none with branch-path context, one (tree-sitter-codeviews) with branch-typed edges. sprefa can steal the storage idea from tree-sitter-codeviews and be the first with both columns plus a query surface.
2. **Does anyone use `locals.scm`?** No. Zero. It's untested territory — a free win if it works, but no validation from the peer set.
3. **What is the query-surface landscape?** Cypher (1), fixed commands (4), imperative API (3), LSP call hierarchy (1), library graph (2), HTTP REST (2), build-time DSL (1). Datalog is completely open.
4. **What does interop look like?** SQLite+MCP is the dominant cross-language shape (4 of 4 systems-language tools with persistence). Shell/stdio is the dominant everything shape (7 of 12).
5. **Shell bridge or WASM — precedent?** WASM has one precedent (codedb, Zig). Shell/stdio has six. Ship shell-bridge first; hold WASM for a later ast-grep-specific fast path.

End of matrix.
