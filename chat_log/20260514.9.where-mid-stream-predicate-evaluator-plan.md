# 20260514.9 — `where` mid-stream predicate evaluator plan

Captured while context is hot. Not implemented. The session that
shipped phases 1–4 of "where strictly via SQL where-clause DSL" left
one architectural constraint visible: `where\`...\`` only fires inside
fully-fusable rule bodies (Pure + RuleQuery). Any body with a Stream
op (`fs`, `ast`, `re`, `glob`, ...) is rejected at lower time with
`lower/rule-stream-after-relation`. This plan is the fix.

## What's in main today (verify before starting)

- `WhereDef::lower` is `Ok(Pipe::new().step(VoidComponent))` — a pass-
  through with no runtime. The fuser intercepts `where` in
  `classify_op` (v4/src/compile/fuser.rs ~162) and emits the predicate
  into SQL.
- `where`'s body is a `DslShape::Plain` backtick body. Raw text in
  `op.dsl.as_ref().raw`. `${capture}` host holes.
- `cst/dsls/sql_where/` is the LSP-side DSL for the body (phase 2).
- The fuser pushes the predicate into JOIN ON via
  `rewrite_pure_predicate` (substitutes `${X}` → `alias.col`).
- `mixed_stream_then_rule_query_is_diagnostic` test currently pins
  the rejection. After this plan lands, that diag goes away for the
  Stream → ... → where case (still appropriate for Stream-after-Rule
  shape).

## What "works mid-stream" looks like

```sprf
rule(:hot_hits, FS?, LO?) {
  fs(glob`**/*.c`) > ast(:c)`printk(${LO?})` > where`${LO} > 1000`
};
```

Today this is rejected. After: the closure inside ast's parallel
match loop accepts `>` chained `where` and drops cursors where the
predicate evaluates to false. Output is identical to writing two
rules with a fused-SQL filter, but without the temp fact table.

## Architecture: predicate AST + interpreter

Two layers. Both small; neither touches the fuser.

### Layer A — predicate AST (parser-side)

```rust
// v4/src/compile/predicate.rs (new)
pub enum PredExpr {
    Hole(Arc<str>),           // ${LO}
    Lit(PredLit),             // 1000, "main", NULL
    Bin(PredOp, Box<PredExpr>, Box<PredExpr>),
    Unary(PredUnary, Box<PredExpr>),
    Call(Arc<str>, Vec<PredExpr>),   // length(${LO})
    Between(Box<PredExpr>, Box<PredExpr>, Box<PredExpr>),
    In(Box<PredExpr>, Vec<PredExpr>),
    IsNull(Box<PredExpr>),
}

pub enum PredOp  { Eq, Ne, Lt, Le, Gt, Ge, And, Or, Add, Sub, Mul, Div, Mod, Like, Glob }
pub enum PredUnary { Not, Neg }
pub enum PredLit { Int(i64), Float(f64), Str(Arc<str>), Null }

pub fn parse_predicate(raw: &str) -> Result<PredExpr, PredParseError>;
```

Reuse `SqlWhereDsl`'s lexer (`scan_predicate` in `cst/dsls/sql_where/`)
for tokens. Add a Pratt parser over the token stream — predicates
fit in ~150 LOC of operator-precedence climbing.

Why not lift from `sqlparser-rs::Parser::parse_expr`? It would also
work. Decision lives at code-review time:
- Hand-rolled: ~200 LOC, zero deps, matches SqlWhereDsl vocab exactly.
- `sqlparser-rs`: ~25k LOC dep, accepts a wider grammar than the
  predicate slot allows, returns a richer AST you'd have to map down.

Default to hand-rolled. Reach for `sqlparser-rs` only if predicate
expressions get type-checking or constant-folding requirements.

### Layer B — predicate interpreter (runtime-side)

```rust
// v4/src/predicate.rs (new) — or inline in v2_ops.rs near WhereDef
pub struct PredicateComponent {
    expr: PredExpr,
    // Captures referenced by ${X}, resolved at lower time to Term
    // names. Each eval reads cursor.get(name).
    holes: Vec<Arc<str>>,
}

impl Component for PredicateComponent {
    type Next = Cursor;
    fn render_batch(&self, _ctx: &RenderCtx, batch: &[&Cursor]) -> Vec<Node<Cursor>> {
        batch.iter()
            .filter(|c| eval_pred(&self.expr, c))
            .map(|c| Node::Emit(Arc::new((*c).clone())))
            .collect()
    }
}

fn eval_pred(e: &PredExpr, c: &Cursor) -> bool {
    match eval_value(e, c) {
        PredVal::Bool(b) => b,
        PredVal::Int(n)  => n != 0,
        PredVal::Null    => false,         // SQL three-valued logic
        _                => false,
    }
}

fn eval_value(e: &PredExpr, c: &Cursor) -> PredVal {
    match e {
        PredExpr::Hole(name) => match c.get(name) {
            Some(s) => coerce(s),
            None    => PredVal::Null,
        },
        PredExpr::Bin(op, a, b) => apply_op(*op, eval_value(a, c), eval_value(b, c)),
        // ...
    }
}
```

`coerce` parses Term values (which are `Arc<str>`) to int/float/string
on demand. Conservative: prefer int when the string is all-digits,
else string. Float only if `.` present. Match SQLite's type affinity
rules where it's cheap; deviate where it's not.

### Lower-time wiring

```rust
// v4/src/compile/lower/ops.rs::WhereDef::lower
fn lower(&self, ctx: &LowerCtx, _flow, _args, _block, dsl) -> Result<Pipe<Cursor>, LowerError> {
    let Some(body) = dsl else {
        return Ok(Pipe::new().step(Arc::new(VoidComponent)));
    };
    let expr = parse_predicate(body.raw.as_ref())
        .map_err(|e| LowerError::Unknown(format!("where: {e}")))?;
    let holes = collect_holes(&expr);
    Ok(Pipe::new().step(Arc::new(PredicateComponent { expr, holes })))
}
```

The fuser's `classify_op` continues to intercept `where` for fusable
bodies — it sees the same raw text and emits SQL. The lower step
runs only when the rule body is non-fusable (i.e. has a Stream op).
Lowering and fusing both pull from the same `op.dsl.raw`, so the
two paths can't disagree on what the predicate says.

## Edge cases to handle in implementation

- **Stream-after-Rule rejection stays.** `rule_a(X?) > fs(...)` is
  still a diag — that's about cursors flowing into a stream source,
  which is a different bug class. Only the `Stream > ... > where`
  shape becomes legal.
- **`${X}` referencing a capture not in scope.** Compile-time error
  in `WhereDef::lower`. Same diag code as today (`lang/use-before-bind`).
- **SQLite-specific functions in the predicate (`length`, `instr`,
  `substr`, etc.).** Interpreter implements the subset listed in
  `cst/dsls/sql_where/PREDICATE_FUNCTIONS`. Fail-closed on unknown
  function names with a clear diag.
- **`LIKE` and `GLOB` patterns.** Implement as a real string-pattern
  matcher (`like_match` is ~30 LOC). Do NOT depend on `regex` — the
  fuser path would diverge in semantics.
- **NULL semantics.** SQL three-valued logic: any operand NULL
  except `IS NULL`/`IS NOT NULL` yields NULL, which falsifies the
  predicate. Test pinned at: `where\`${MISSING} != 0\`` drops every
  cursor.
- **Type coercion.** When `${LO}` is "1234" and the literal is `1000`,
  compare as ints. When `${X}` is "main" and literal is `"main"`,
  compare as strings. Mirror SQLite affinity rules.

## What this enables on the demo path

- `cargo_name_lines` style fs-scan rules with predicates without
  splitting into two rules:
  ```sprf
  rule(:rust_panics, FS?, LO?) {
    fs(glob`**/*.rs`) > ast(:rust)`panic!($$$)` > where`${FS} LIKE "%/src/%"`
  };
  ```
- Cross-rev filter without per-rev seed-binding rules:
  ```sprf
  rule(:cargo_names, REV?, NAME?);
  rule(:head_only_names, NAME?);

  repo() > rev(:HEAD, :test/1) > fs > glob`**/Cargo.toml` > read
    > re`(?m)^name\s*=\s*"(?P<NAME>[^"]+)"`
    > cargo_names(REV, NAME);

  cargo_names?(REV?, NAME?) > where`${REV} = "HEAD"` > head_only_names(NAME);
  ```
  (Today this works via the fused path because both `cargo_names?` and
  the second `cargo_names?` are RuleQuery — adding a `repo() > rev() >
  fs() > ...` source-scan with an inline predicate is the new shape.)
- AI-authored rules that lean on inline predicates rather than rule
  splits stay readable.

## When NOT to pick this up

- If the cross-repo dep crawl demo doesn't actually need mid-stream
  predicates (the two-rule split is fine for the demo's surface).
- If predicate semantics drift between the fused path (SQLite) and
  the interpreted path (Rust) becomes a recurring source of bugs.
  Likely point of divergence: type coercion edge cases.
- If switching to `sqlparser-rs` as a shared parser-side AST changes
  the LOC budget enough to be unattractive.

## Open questions for the next session

1. **Hand-rolled Pratt vs sqlparser-rs.** Decision pending — see Layer A.
2. **Should `where` between two RuleQuery steps prefer fused or
   interpreted?** Today the fuser always wins. After this, both paths
   produce the same observable behavior, but the fuser is faster.
   Keep the fuser-first preference; the interpreter is the fallback
   for non-fusable bodies only.
3. **Aggregate predicates** (`HAVING\`COUNT(*) > 3\``). Out of scope.
   Belongs to a future `having\`...\`` op that lives only in fused
   bodies (aggregates require GROUP BY which is fuser-only).
4. **Streamed-Rust path for ORDER BY / LIMIT.** Same shape — would
   need an interpreter. Mark as "needed when" and defer.
