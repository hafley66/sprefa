# Runtime-graph next steps — reconciled

Reconciliation of `20260515.2.runtime-graph-audit-and-canonical-shape.md`
against the user's full reactive model. Read-only. No code edits.

## Anchor: end goal

A general programmable shell. Pipes compose, state persists, jobs
schedule, queries materialize, the prompt drives it. Every design choice
below is scored against that target, not against an isolated "tidy up
the audit" goal.

## TL;DR (7 bullets, one per phase + anchor)

1. **End-goal anchor.** Every primitive added or kept must serve
   composable pipes + persistent state + schedulable work + materialized
   views, callable from a shell-style prompt. Cursor-pause, Rx
   operators, redux-saga lifecycle, and DD-style joins are FOUR
   contributors to that surface, not alternatives.
2. **Phase 1.** The 2-node / 2-edge / 1-aux canonical shape covers Rx +
   React + saga PARTIALLY. Gaps: operator completion status, per-edge
   `scan` state, Suspense status, action-stream `take(action)`,
   per-pipe scheduling hint. Each gap = one small column or one new
   aux. Total schema growth: 2 columns + 1 enum table.
3. **Phase 2.** Scheduler is one trait with three drain strategies
   (`BreadthFirst`, `DepthFirst`, `Streaming`), hint inherited from
   parent owner. `run_to_quiescence` is the BF drain. DF and streaming
   variants reuse the dirty-bit query, change only the inner loop
   shape.
4. **Phase 3.** `effect_runtime::v2::FactRuntimeGraph<R: Row>` already
   exists at 700 LOC and is genuinely generic. v4's `RuntimeGraph`
   wraps it via `core: FactRuntimeGraph<Cursor>` but ALSO re-implements
   most surfaces above it. Right move: **collapse**. Promote
   Continuation + run-to-quiescence + dirty-bit columns into the
   generic crate; keep only sprf URI helpers + RuleMemo + CompactSource
   on the sprf side.
5. **Phase 4.** DD adoption: **use for one operator** initially
   (`materialized_join` / `seminaive_recursion`). The prior session
   `20260501.0` already accepted DD as backbone with tiered memory
   (Strategy 4) under a pinned perf test. Reconciliation here narrows
   v4's entry point: DD-backed op surfaces as opaque sink, output rows
   flow back through `notify_table_inserted`. No DD scope at the graph
   level yet.
6. **Phase 5.** First slice = **delete the three dead clusters** named
   in the audit (ActiveEdge family, EDGE_VALUE reader, VisibleDelta
   return). Pure deletion, zero behaviour change, ~210 LOC out, ~0
   risk. Unblocks every subsequent move because the kept surface is
   then small enough to lift.
7. **Phase 6.** The four shipped D-slices map cleanly:
   `notify_table_inserted` survives (renamed `wake_table` in the
   collapsed model), `RuleMemo` stays sprf-side, `run_to_quiescence`
   becomes one of three scheduler strategies, mode-dispatch invalidation
   stays as-is (it is downstream of the graph, not part of it).

### 1.3 Revised canonical schema

## Phase 2 — Scheduler (BF + DF + Stream)

### 2.1 Type signatures first

```rust
/// Drain strategy. Inherited from parent owner if unset; default = BF.
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub enum ScheduleHint {
    /// Drain all dirty owners in a wave, then re-check.
    /// Matches today's `run_to_quiescence`.
    BreadthFirst,
    /// After running owner O, prefer to run the next-downstream owner
    /// (subscriber of O's output) before any sibling of O.
    /// Latency win for narrow pipes.
    DepthFirst,
    /// Owner's body runs in streaming mode: each emitted row is
    /// immediately enqueued downstream without waiting for the body
    /// to finish. `replace_supports` is replaced by `add_support`
    /// per row.
    Streaming,
}

/// Bookkeeping for one owner that the scheduler hands the handler.
pub struct OwnerRun {
    pub owner: OwnerNode,
    pub generation: u64,
    pub hint: ScheduleHint,
}

/// What the scheduler did or why it stopped.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum DrainOutcome {
    Quiescent { handled: usize },
    BudgetExhausted { handled: usize, remaining: usize },
    IterationCap { iters: usize, handled: usize },
}

/// Single-strategy scheduler. Multi-strategy is the `Mixed` impl.
pub trait Scheduler {
    /// Enqueue `owner` for the next drain pass. Idempotent — the dirty
    /// bit on the owner's subscribe edges is the source of truth.
    fn enqueue(&self, owner: &OwnerNode, hint: ScheduleHint);

    /// Run to fixed point or until the budget is hit. `max_iters`
    /// caps recursion in cyclic rule graphs.
    fn drain_to_quiescence(
        &self,
        max_iters: usize,
        handler: &mut dyn FnMut(&OwnerRun),
    ) -> DrainOutcome;

    /// One step. Pulls the next runnable owner; returns None when
    /// quiescent. For tests and instrumented runs.
    fn step_one(&self, handler: &mut dyn FnMut(&OwnerRun)) -> Option<OwnerRun>;
}

pub struct BfScheduler { graph: Arc<RuntimeGraph> }
pub struct DfScheduler { graph: Arc<RuntimeGraph> }
pub struct StreamScheduler { graph: Arc<RuntimeGraph> }

/// Mixed-strategy scheduler. Reads `schedule_hint_id` per owner; falls
/// back to parent's hint via owner.parent_uri_id walk.
pub struct MixedScheduler { graph: Arc<RuntimeGraph> }
```

Hint selection rule:

```text
hint(owner) =
  owner.schedule_hint_id                    if set
  hint(owner.parent_uri_id)                 if parent exists
  ScheduleHint::BreadthFirst                otherwise
```

An operator overrides the hint by declaring `schedule_hint_id` on the
owner it spawns. `streaming_each(...)` sets `Streaming` on the inner
owner; everything else inherits `BreadthFirst`.

### 2.2 BF drain (today's `run_to_quiescence`, unchanged)

```text
loop:
    owners = SELECT DISTINCT from_uri_id FROM runtime_edge
              WHERE kind = 'subscribe' AND dirty = 1
    if empty: break
    for owner in owners:                   <-- wave, all in one iter
        handler(owner)
        UPDATE runtime_edge SET dirty = 0
         WHERE from_uri_id = owner

  (Identical to the current run_to_quiescence loop at
   runtime_graph.rs:494-522; rename only.)
```

ASCII trace, 3 owners (O1, O2, O3) on sibling subscribe edges, all
dirty before drain:

```
  iter 1                  iter 2
  ------                  ------
  dirty = {O1, O2, O3}    dirty = {}        (assuming no cascade)
    run O1                  break
    run O2
    run O3
  clear all bits
```

### 2.3 DF drain

```text
worklist = stack of (owner, hint)
push every initial dirty owner
loop:
    (owner, hint) = worklist.pop()
    handler(owner)
    cleared = UPDATE edges SET dirty=0 WHERE from_uri_id = owner

    newly_dirty = SELECT DISTINCT from_uri_id FROM runtime_edge
                   WHERE kind = 'subscribe' AND dirty = 1
                     AND to_uri_id IN (SELECT table_uri
                                         FROM owner_outputs(owner))
    push newly_dirty (LIFO) so they run before siblings

    if worklist empty: break
```

ASCII trace, O1 dirty initially; O1's render writes to T1 which wakes
O2; O2 writes to T2 which wakes O3:

```
  step 1                  step 2                  step 3
  ------                  ------                  ------
  worklist: [O1]          worklist: [O2]          worklist: [O3]
  run O1                  run O2                  run O3
  O1 -> T1, wake O2       O2 -> T2, wake O3       (no further wake)
  push O2                 push O3
```

DF visits the chain O1 -> O2 -> O3 to completion before returning to
any sibling. Latency: one cursor's worth of work per outer step.

### 2.4 Streaming drain

```text
Components ALREADY have a streaming tier — Component::dispatch
(component.rs:67-78). The streaming scheduler differs from BF/DF only
in WHAT it calls for support reconciliation:

  - BF/DF call replace_supports(owner, table, [all rows], gen)
    once per owner render. Diff at end-of-render.
  - Streaming calls add_support(owner, table, row, gen) per emitted
    row, then retract_support_tail(owner, table, gen) when the owner's
    pipe Done signal arrives.

Drain loop is otherwise the same as DF (handler returns after each
row, scheduler re-checks dirty bits per row).
```

The streaming variant requires the `add_support` / `retract_tail`
verbs (A6 in Phase 1.2). Without those it cannot exist.

ASCII trace, one owner O streaming 4 rows downstream to T1:

```
  row 1               row 2               row 3               complete
  -----               -----               -----               --------
  add_support(O,T1,r1) add_support(O,T1,r2) add_support(O,T1,r3) retract_tail(O,T1,gen)
  wake T1 sub          wake T1 sub          wake T1 sub
  (downstream sees     (downstream sees     ...
   r1 immediately)      r1 + r2)
```

### 2.6 What replaces today's `run_to_quiescence`

`run_to_quiescence` (`runtime_graph.rs:494-522`) becomes
`BfScheduler::drain_to_quiescence`. The function body moves into a
trait impl; the `RuntimeGraph` keeps its public-API method as a thin
wrapper that constructs `BfScheduler` on the fly for the default case.

```rust
impl RuntimeGraph {
    pub fn run_to_quiescence(
        &self,
        max_iters: usize,
        handler: impl FnMut(&RuntimeJob),
    ) -> Result<usize, QuiescenceError> {
        // Wrap as BfScheduler. Adapter for the legacy job-shape API.
        let sched = BfScheduler { graph: ... };
        let outcome = sched.drain_to_quiescence(max_iters, ...);
        match outcome { ... }
    }
}
```

Existing callers (`v4/src/sql.rs`, `v4/src/fact.rs`, and the four
chat_log notes for D-slice 4 / `aeee250`) keep working unchanged.

### 3.2 Verdict

**Partial.** The lower half (insert/read/edge/value/event mechanics)
is already in effect_runtime. The upper half (jobs, continuation,
quiescence, rule memo, sprf URIs) is v4-only. The collapse plan:

1. **Promote into effect_runtime** (generic on `R: Row`):
   - `RuntimeJob` row + `enqueue_jobs` / `pending_jobs` / `mark_job_done`
   - `RuntimeContinuation` row + `record_continuation` /
     `continuation_for_owner`
   - `Scheduler` trait + BF / DF / Stream / Mixed impls
   - Dirty-bit on `RuntimeEdge` (column add)
   - Status enums on Subscribe edge and Continuation
   - `add_support` / `retract_support_tail` (streaming verbs)

2. **Stay sprf-side** (in v4/src/runtime_graph.rs, much thinner):
   - `OwnerNode` / `SourceNode` / `OutputNode` Rust wrappers (these are
     sprf URI conventions; the generic layer takes `&str`)
   - `RuleMemo` (sprf rule-call dispatch, not a graph primitive)
   - `CompactSourceGraph` (sqlite-direct fast path for sources;
     sprf-specific opt-in)
   - URI helpers `owner_uri` / `row_uri` / `edge_uri` /
     `runtime_uri` / `table_source_uri` (sprf URI scheme)
   - `notify_table_inserted` -> rename or alias to `wake_table` in
     the generic crate; sprf version just calls the generic verb with
     `table_source_uri(table)`
   - `SprfSubscribe` / `SprfSupportRows` `RuntimePut` impls (these
     project sprf types onto the generic Subscribe / SupportRows
     already in effect_runtime; consider deleting and using the

## Phase 4 — DD honest reread

### 4.1 Memory cost (refresher)

DD's three memory consumers:

| Consumer | Bounded by | Mitigation |
|----------|------------|------------|
| Trace history | retained logical times | `Trace::set_logical_compaction(frontier)` collapses old times into the latest |
| Arrangements (sorted, indexed copies of collections) | one per `arrange_by_key` site | reuse arrangements via `share_arrangement_handle`; or use `JoinCore` which manages its own |
| Frontier capabilities | open input sessions | drop input handles to advance |

For sprf's case (mostly append, occasional retract on source delete):

- A DD configuration with `set_logical_compaction(frontier.minus(K))`
  where K = a small generation window keeps RAM proportional to active
  relations, not history.
- This matches what `20260501.0.dd-adoption-effects-control-flow-types-perf.md`
  bullet 11 already concluded (K_GENS=5, M=10 starting policy).

### 4.2 The appealing piece

`JoinCore::join_core` performs incremental hash-join with O(delta) work
per update. For sprf's "rule R joins table A and table B" use case
the alternative is re-scanning both tables every drain pass. At 500-
repo / 50 GB src scale the re-scan is the bottleneck the user signaled.

`Iterate::iterate` performs seminaive recursion: each iteration
processes only the delta from the previous step, not the full
transitive frontier. The alternative (today's naive drain) re-fires
the recursive rule once per outer wave.

### 4.3 Reuse vs duplication

Three options:

| Option | Surface area | Risk |
|--------|--------------|------|
| Use DD as the WHOLE substrate (replace `RuntimeGraph`) | huge | RAM at scale (already studied in `20260501.0`); large rewrite |
| Use DD for ONE OP (`materialized_join`, `recurse`) | small | DD-backed op surfaces as opaque sink; outputs flow back through `notify_table_inserted` like any other rule output |
| Don't use DD | none | re-scan cost on every join + naive recursion |

### 4.4 Recommendation: option 2 (single-op)

Wire DD as an opt-in operator under a feature flag. The operator
contract:

```rust
/// DD-backed materialized join. Takes two source tables and an
/// equijoin key. Outputs into `output_table`. Internally maintains
/// a timely::worker with one DD scope; pushes deltas as
/// `notify_table_inserted` calls arrive; reads results back via an
/// inspect_batch sink that writes to the fact-store.
pub struct DdMaterializedJoin {
    left_table: Arc<str>,
    right_table: Arc<str>,
    join_key: JoinKey,
    output_table: Arc<str>,
    worker: timely::worker::Worker<...>,
    sinks: Mutex<Vec<TraceHandle<...>>>,
}

impl Component for DdMaterializedJoin {
    fn dispatch(&self, ctx, rows, queue) {
        // 1. Read deltas from left_table / right_table via fact-store.
        // 2. Push into DD input handles.
        // 3. advance_to(ctx.expand_tick); step_while(...).
        // 4. Drain inspect_batch sink -> write to output_table via fact-store.
        // 5. notify_table_inserted(output_table) -> graph picks up downstream subscribers.
    }
}
```

The rest of the graph treats this operator as a black-box: it has
Subscribe edges to left + right source tables, and Support edges to
its output table. The DD-internal trace/arrangement is invisible to
the graph. Memory budget is bounded by the operator's own
`set_logical_compaction(frontier - K_GENS)` policy.

Compatibility:

- Compiles in feature `dd` (already present in `v4/Cargo.toml:29-30`,
  `differential-dataflow = "0.12"` + `timely = "0.12"`).
- Off by default; sprf works without DD.
- Failure mode: if DD scope panics, op surfaces an error diagnostic
  and the rule output table is empty for that gen. Downstream
  subscribers see retraction.

### 4.5 What this does NOT decide

The prior session (`20260501.0`) studied DD as state backbone. That
plan is still on the table for a future v5 redesign. The Phase 4
recommendation here is the **minimum-risk introduction** of DD into
the current v4 codebase: one operator, opaque sink, feature-gated.
Adopt it; gather perf data on real join workloads; decide later
whether to broaden.

### 6.1 `run_to_quiescence` specifically

The question raised in the task: does `run_to_quiescence` stay as the
BF scheduler, get replaced by the multi-strategy `Scheduler` trait,
or become one of multiple drain modes?

**Answer:** all three, layered.

1. The function body unchanged becomes `BfScheduler::drain_to_quiescence`.
   This is the literal answer to "stays as the BF scheduler".
2. The `Scheduler` trait subsumes the API: any caller wanting a
   strategy switch instantiates `BfScheduler` / `DfScheduler` /
   `StreamScheduler` / `MixedScheduler` directly.
3. The legacy `RuntimeGraph::run_to_quiescence` method survives as a
   one-call shim to BfScheduler, so the four current call sites
   (`v4/src/sql.rs:299` etc. transitively via `notify_table_inserted`)
   keep working without touching ops code.

This is the same shape v3 uses for `Component::dispatch` /
`render_batch` / `render` — three layers, default flows inward, callers
override at the layer that fits.

## Closing

The audit's canonical shape stands; the reconciliation here adds five
columns (status × 2, counter_blob, schedule_hint, debounce_until_gen),
two streaming verbs (add_support / retract_support_tail), one
scheduler trait with four impls, and one DD-backed operator behind a
feature flag. Everything else collapses into the generic
`effect_runtime::v2::FactRuntimeGraph<R: Row>` that already exists.

The end goal — a general programmable shell — is served by:
composable pipes (the Component trait, untouched), persistent state
(Continuation + dirty-bit drain), schedulable jobs (Scheduler trait),
materialized queries (DD-backed `materialized_join` + standard
`Support`-edge tables). All four scoring constraints from the user's
philosophy (Rx, React, saga, cursor-pause) hit the canonical shape
with at most one new column each.

First slice: delete ActiveEdge family. Smallest, zero-risk, sets
direction.
