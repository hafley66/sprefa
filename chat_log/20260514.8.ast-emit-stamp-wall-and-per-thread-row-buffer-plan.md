# 20260514.8 — ast emit_stamp wall and per-thread row-buffer plan

Session goal: drive down the materialized-query cost on the rules-as-tables
fuser path, then chase the next perf ceiling once the demo bench worked end
to end.

## What landed today (on `main`)

1. **`1b4ce46` fix(v4): route fused INSERTs by INSERT-target, not by substring.**
   The dispatch in `run_fused_sql` discriminated primary fact INSERT vs
   support_edges INSERT with `raw_sql.contains(&target_facts)`. That
   matches the table name embedded as a string literal in the
   support_edges SELECT, so support_edges was routed to the primary
   branch, `build_live_facts_insert` returned `None`, `had_error=true`,
   and the executor fell through to legacy expand — even after the
   primary INSERT had already committed. Fixed to discriminate on
   `starts_with("INSERT OR IGNORE INTO <table>")`.

   Bench delta on `linux-join.sprf` with `--fact-db` + Bench profile:

   ```
   files  hits   pairs   before          after          speedup
   50     100    100     1067ms / 64MB   17ms / 18MB     63x
   1000   4000   12000   64834ms / 4.4G  232ms / 86MB    279x
   5000   20000  60000   would-OOM       1185ms / 295MB  n/a
   ```

   Wall on medium/large is now bounded by ast parse + string intern,
   not the materialized self-join.

2. **`da11b3a` perf(store): DashSet for seen_*, StripedLru for hot caches.**
   Replaced seven `Mutex<HashSet<u64>>` with `DashSet`, and the seven
   `Mutex<LruCache>` with a 16-shard `StripedLru` wrapper. Both
   families are content-addressed (ids are blake3 of payload), so the
   locks were protecting correctness-optional in-memory caches. Result
   on synthetic 5000-file fixture at W=8: emit_stamp_summed dropped
   from 2316ms → 1951ms (-16%). ast wall stayed at 733ms because the
   ceiling lives somewhere else (see Finding below).

3. **`4392599` perf(ast): use locally known source_path instead of store.path_of lookup.**
   In `emit_stamp`'s hot path, `MATCH_FS` was populated via
   `store.path_of(coord.fs)` which on cache miss does `flush()` +
   linear scan over `_files_facts`. The path is already in scope as
   `source_path: Option<Arc<str>>` from the source-read branch — use
   it directly. Eliminates a cliff when the file working set exceeds
   the `files_lru` cap (4096).

## The wall, finally diagnosed

Linux kernel through sprf (v4/bench/linux-join.sprf, 63316 .c/.h files):

```
wall_ms      7901.8        (target <8000)
rss_peak_MB  449
files_seen   63316
source_MB    1340.3
prefilter_skips 58899  (93% files skipped pre-parse)
parses       4417     (the 7% that survived "printk" prefilter)
hits         15077
hit_pairs    559880   (self-join materialized in SQL)
```

Inside the synthetic 5000-file fixture, instrumentation revealed:

```
ast wall            = 711ms
  par_render wall   = 709ms
    subs build      = 18ms
    splice_into     = 1.8ms (serial enqueue, but 20k items in <2ms)
  closure_summed    = 3118ms (across 8 CPU)
                    = 4.1 effective workers of 8 → ~50% parallelism
```

Closure CPU time breakdown (all inside `ast_timed` regions):

```
read         723ms summed  (parallel, IO-bound)
parse        178ms
match         44ms
emit_stamp  2084ms summed  ← 67% of CPU
others        70ms
─────────────────────────
total       3099ms summed  ≈ closure_summed (only ~20ms untimed)
```

**The actual ceiling: `pending_core` lock serializes 5 fact-row inserts per ast match.**

Per match inside `emit_stamp`:

```
1. stamp_source_value
     intern_string(slice)        — usually HIT
     intern_where_bytes(coord)   — MISS → pending_core.lock() + insert
2. observe_string(...)            — MISS → pending_core.lock() + insert
3. set_at("LO")
     intern_string + intern_where_bytes (LO coord)   — MISS row
4. set_at("HI")
     intern_string + intern_where_bytes (HI coord)   — MISS row
5. set_at("MATCH")
     intern_string + intern_where_bytes (MATCH coord) — MISS row
```

5 inserts × 20000 matches = **100k contended mutex acquisitions** on a
single global `Mutex<HashMap<table, Vec<Row>>>`. With 8 workers, this
caps effective parallelism at ~3.3 workers.

## Why earlier attempts didn't move the wall

- DashSet swap: only made `seen_*` checks faster. The Mutex is hit
  AFTER the seen check on the MISS path, which is where the
  contention lives.
- StripedLru: only made LRU updates faster. Same issue — the actual
  `pending_core.lock()` was untouched.
- SegQueue per-table (lock-free): per-push atomic CAS bouncing across
  cache lines was MORE expensive than the contended Mutex for our
  access pattern (regression: +18% wall, +143% emit_stamp).

## The next fix (not yet done)

**Per-thread row buffers, drained at end-of-batch.** No lock on the
hot path.

Approach: replace `pending_core: Mutex<HashMap<&'static str, Vec<Arc<Cursor>>>>`
with a `ThreadLocal` (from the `thread_local` crate, not `std::thread_local!`)
of per-thread `HashMap<&'static str, Vec<Arc<Cursor>>>`. Each worker pushes
into its own buffer (no synchronization). Flush iterates ALL thread
buffers and merges per table.

Why this should work where SegQueue didn't:
- No atomic CAS per push — just a regular Vec::push on a thread-owned
  buffer
- Flush is rare (CORE_FLUSH_ROWS=16384 threshold, or end-of-batch)
- Order is preserved per thread; cross-thread order doesn't matter for
  INSERT OR IGNORE into a content-keyed table

Estimated wall impact: from 733ms → ~400ms on the 5000-file
synthetic, based on the 67% of closure CPU spent in emit_stamp
with mostly mutex contention.

## Open questions for the next session

1. **Drop seen_* entirely?** With content-hashed ids, INSERT OR IGNORE
   on the cold store is idempotent. The `seen_*` early-exit saves a
   round-trip on duplicates. On the synthetic fixture, intern_string
   is 99.95% hits (only ~15 unique strings out of 20k attempts) —
   dropping seen_strings would force all 20k to take the miss path
   and write to pending_core. NET WORSE. So seen_* is still useful as
   a write-amplification damper. Don't drop.

2. **Why are LO/HI/MATCH set_at calling intern_where_bytes 3 separate
   times per match with 3 different coords?** Each set_at builds a
   distinct WhereBytes around the match coord but with different
   `lo/hi` slots for the LO term, the HI term, and the MATCH term.
   So 3 distinct WhereBytesIds get interned, 3 distinct
   `_where_bytes` rows get written. Is this necessary? If the
   downstream fuser/query only ever reads one of them, the other two
   are pure overhead. (Pre-computation P1 dead-capture elim was on
   the wishlist but isn't wired yet.)

3. **Can we move the `_where_bytes` and `_string_observations` writes
   out of the parse-time hot path entirely?** They're meta-tables for
   "where did this term come from" provenance, not the actual fact
   rows the rule queries against. A deferred-write design would queue
   them, drain off-loop, and let the parse stage finish first.
