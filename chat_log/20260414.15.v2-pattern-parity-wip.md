## Problem/Context
During manual smoke on commit 7b94a26, user found:
1. `fs()` hover rendered the path as both heading and bullet — duplicate nesting. Fixed (flat list) and committed test snapshot update.
2. `fs(*/|)` completion returned nothing. Editor fell back to word-completion (`abc A`, `abc across`, etc.). Root cause: the completion filter did `v.contains("*/")` which no file path matches.

First pass: I added a metachar detector that skipped the filter for `*?[]{}` partials. User corrected: "i do want pattern autocomplete to work" and then "do not invent ur own sub pattern whatever for this omg please reuse ltieralyl anything we already ahve llm LOVES MAKING REPEAT CODE". Switched to call `_8_parse::glob_match` directly.

Then user asked: "and double glob? and glob shortcut, and regex syntax with re: like do all patterns work?" Investigation showed v2 has TWO matchers:
- `_8_parse::glob_match` — only `*`, `?`, `**/`. Used by `repo`, `rev` (and via fs reader call).
- `walk/_0_pattern::PatternMatcher` — full v1 parity: `re:` regex, `$NAME` segment capture, `|` alternation, globset (`**`, `?`, `[abc]`, `{a,b}`). Only walker ops used it.

User response: "wtf we literally got that to work in v1 did we not". Confirmed via `crates/rules/src/pattern.rs` + `crates/rules/src/{file_match,git_match}.rs` — v1 was uniform. v2 regressed top-level ops to the hand-rolled glob_match.

Decision locked: promote `PatternMatcher` to crate root, have all ops consume it, have completion filter consume it. Kill `_8_parse::glob_match` when done. This is task #8.

Also deliberated but open: **ParseMode::Strict vs Tolerant collapse**. Strict gives nothing semantic over `host_parse_tolerant` + checking `errs.is_empty()`. Proposed collapse: one entry point returning `(Vec<Pipe>, Vec<ParseError>)`, callers decide. Benefit: kills the `ProgramCtx.parse_mode` plumbing task entirely since RuleFactory::parse just runs tolerant uniformly and fragment ops emit `op/unknown` diagnostics on lowering. I offered two options (revert-then-collapse vs land-as-followup) but user pivoted to the smoke bugs and the ParseMode collapse remains a pending decision.

## Key Insights
- **v1 had pattern parity; v2 regressed it.** `crates/rules/src/pattern.rs` served `file_match`, `git_match`, `walk`. v2 split: walker got the full PatternMatcher, top-level ops got the hand-rolled `glob_match`. Promoting the matcher closes the regression in one shot.
- **One matcher, one filter, one path.** Completion filter must call the same matcher the op will consume at runtime. Otherwise "what the editor suggests" drifts from "what the op accepts." The `CompiledPattern` wrapper is the shared substrate.
- **ParseMode is load-bearing nothing.** Once partial-parse lands at top level and ops' internal parses (RuleFactory::parse) also use tolerant, there's no caller who needs the "atomic bail" semantics. The CLI can emit errs and exit whether it got 0 or 3 pipes. Collapse is additive-negative.
- **Worktree isolation silently no-ops today.** All four parallel agents wrote straight into the main working tree. Safe for conflict-free lanes; dangerous for overlapping lanes.
- **LLM has a standing instinct to duplicate pattern-matching logic** — the user called this out directly. Principle for this codebase: pattern matching is one crate-root module, everyone consumes it.

## Open Questions
- Should `CompiledPattern::compile` failure inside `complete_in_paren` fall back to substring, to empty filter (pass all), or to no-match (return nothing)? Current plan: substring fallback, because during mid-typing `re:foo[` (unclosed class), user still wants to see SOMETHING narrow.
- Does `fs(pattern)` want the CompiledPattern to filter cursors post-reader, or does the reader's own globbing suffice? Reader currently handles globs; if the matcher matches what the reader matches, the filter is redundant. But `re:` and segment-capture are NOT in the reader's vocabulary — so without an in-op filter, `fs(re:^src/)` would be silently over-broad. Needs a diag or an in-op filter; prefer in-op filter.
