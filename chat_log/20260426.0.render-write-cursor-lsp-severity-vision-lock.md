## Solution/Approach
Locked design:
- **render[fmt]**: universal output op family. md/ascii/lsp/rust/json/sql backends. Bracket-arg discriminator. Body is template str with bound captures.
- **write_cursor(target, mode)**: positional sink op. Mode atoms :replace (default), :append, :prepend, :wrap. Backed by single WriteRangeEffect{file,byte_range,new_bytes,mode}. Same effect powers write_file (range=whole file) and LSP code-action edits.
- **lsp[severity]**: lsp[error|warn|hint|info]. Bracket-arg as severity. Cursor.byte_range IS the diagnostic range; backend collects per-doc.
- **Backtick strings**: `foo ${X}` JS-template-literal. `${...}` re-enters host carveout, read-mode only. Token unclaimed.
- **Comment bidirectional**: comment(@sprf ${BODY?}) > eval reads; comment(@begin ${SCOPE?} @end) + write_cursor writes.
- **tag**: variadic write tag(:name, ${A?}, ${B?}) + nullary read tag(:name) > .... Replaces v2 scan-pointer. First Pending client.
- **rule**: SQLite table sink, batched via Store::flush_batch. NEVER inline NEVER in loop. Gated on crates/sprefa port-or-revive.
- **Sigil set after lock**: ${X?}, ${{shell}}, :atom, `template`, "str"/r"raw"/r#"raw"#, # comment. Dropped: &{...}, <<, >>, $$.

Bashism << redirect rejected. Reasoning: sprf pipe direction is > L-to-R, sinks at right end, op-form is universal trait not syntax, sigil consolidation favors fewer tokens. If sugar ever earns weight, land later as parser-level desugar to op call.

## Key Insights
1. Cursor.byte_range is universal — it's BOTH a read address AND a write address. That tuple already IS the LSP Diagnostic minus the message. No new plumbing for programmable LSP, just a collector.
2. Bashism << redirect is the wrong direction for sprf because pipe is unidirectional `>`. Bash uses both `>` and `<` because it has no pipe alternative; sprf has pipe.
3. Universals belong on the Op trait, not on syntax. Adding `<<` would be a parser-level structural separator for an effect that any sink op already covers.
4. Once parametric rules land, rules ARE the symbol table — `rule_name(args)` IS the entity reference. `&{...}` for entity addressing was redundant.
5. WriteRangeEffect with mode atom collapses what would have been three separate effects (write_file/write_into/lsp_code_action_edit) into one. Idempotent because byte_range is recomputed each pass.
6. Bracket-arg discriminator (`render[md]`, `lsp[error]`, `ast[rust]`) is the standing convention. One fewer slot to thread per op family.
7. Comment bidirectional (read @sprf bodies, write @begin/@end scopes) closes the surgical-codegen loop in-file with no build step.

## Open Questions
1. write_cursor mode atom set: just {:replace, :append, :prepend, :wrap} or also {:line_above, :line_below, :inside_braces}? Probably YAGNI past the four core.
2. Does rendered output's trailing newline get included or excluded by default? bash here-doc convention is include; LSP edit convention varies. Probably include with a `:trim` mode if needed.
3. Comment marker syntax: `@begin ${SCOPE?} @end` puts ${SCOPE?} mid-marker, but the binding semantics is "SCOPE binds to byte_range BETWEEN markers". Might want `comment(@begin :scope-name @end) > ${:scope-name}` or similar. Defer.
4. lsp[severity] code-action variant: how does the edit slot lower? Probably `lsp[code_action](title, edit = render[rust](...))` where edit is a Value::Pipeline that produces a write_cursor effect at apply time.
5. Backtick template inside ast[lang] body — does ${X} bind ast-grep metavar OR sprf capture? Probably forbid backticks inside pattern bodies; backticks are output-position only.
