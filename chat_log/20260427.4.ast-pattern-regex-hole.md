# Design: Inline regex/glob holes in ast patterns

## Goal
Extend `.sprf` DSL `ast` op to support embedding regex and glob patterns inline as constraints on metavar slots. Lets `use${HOOK_OP_NAME}${re(Query|LazyQuery|Mutation)}()` match hook names satisfying a suffix constraint.

## Current State
- **ast op** (v3/crates/pipeline/src/ops/ast_grep.rs): Patterns use `${VAR}` and `$$${VAR}` metavars; single-token form rewrites to synthetic `$SPRFSLOTN` + named regex for sub-token extraction via `lower_sugar` (line 378–509).
- **re op** (v3/crates/pipeline/src/ops/re/mod.rs): Regex literal; exposes `.regex` field (line 36) with `.as_str()` accessor.
- **glob op** (v3/crates/pipeline/src/ops/glob/mod.rs): Glob-to-regex via `compile_from_tree` (line 72–174), emits anchored regex (`^...$`) baked into `.regex` field.
- **ast-grep-core** 0.36: `Pattern::try_new` (line 275) compiles source string. Current lowering doesn't use constraints; investigate API shape for per-metavar regex constraints.
- **parse.md** §14.5 (line 1209+): Op trait surface includes `try_raw_regex()` capability method.

## Problem
Current `ast` op metavars match any AST node shape. For identifier-suffix patterns like `use${HOOK_OP_NAME}${SUFFIX}()`, we can't constrain SUFFIX to specific values. The workaround is post-pipeline filtering (inefficient). Need a first-class surface to embed regex constraints inline.

## Solution: Surface Syntax

**Form:** `${re(...)}` and `${glob(...)}` as anonymous (synthetic) metavars.

```
use${HOOK_OP_NAME}${re(Query|LazyQuery|Mutation)}()
```

**Rationale:**
- Anonymous: user doesn't name the synthetic slot (no `${NAME=re(...)}` form). The value is always the matched text; no binding.
- Embedding: wraps `re(...)` or `glob(...)` op bodies directly in the pattern (no separate DSL), avoiding grammar friction.
- Captures: if the regex has named groups `(?P<X>...)`, they become user-visible captures (same as `re(...)` op). Glob holes never have groups.

**Rejected alternatives:**
- `${$re(...)}` — confusing dual-$; breaks term_ref symmetry.
- Named form `${NAME=re(...)}` — adds syntactic weight; anonymous binds the whole match, which is the common case.

## Lowering Pipeline

### Parse layer
**Location:** ast op's body grammar is implicit (raw string, no injected grammar).
**Approach:** Extend `reject_bare_metavars` + `lower_sugar` to recognize `${re(...)}` and `${glob(...)}` forms alongside `${VAR}`.

When parsing the paren body in `lower_ast_paren` (line 216–308):
1. Tokenize the pattern looking for `${re(...)`, `${glob(...)}`.
2. For each hole, parse the inner op body (extract everything between parentheses).
3. Compile the op (call `ReOp::compile_from_tree` or `GlobOp::compile_from_tree`).
4. Extract the regex string from `.regex.as_str()`.
5. Generate a synthetic metavar name (e.g., `SPRFHOLE0`, `SPRFHOLE1`).
6. Splice into pattern source, collect regex constraints.

### Lowering outline
```
Input:  use${HOOK_OP_NAME}${re(Query|LazyQuery)}()
        
Step 1: Parse outer pattern for metavars + holes
  ${HOOK_OP_NAME} → MetaVar("HOOK_OP_NAME")
  ${re(Query|LazyQuery)} → Hole { op: "re", body: "Query|LazyQuery" }

Step 2: For each Hole, compile the embedded op
  re("Query|LazyQuery") → ReOp { regex: "(?P<…>Query|LazyQuery)" }
  Extract regex.as_str() → "(?P<…>Query|LazyQuery)"

Step 3: Generate synthetic name + constraint
  synthetic_id = "SPRFHOLE0"
  Extract regex pattern: "Query|LazyQuery"
  (Caveat: if regex has groups, extract the outer alternation or full source)

Step 4: Splice pattern + emit constraint
  Rewritten pattern: "use$HOOK_OP_NAME_$SPRFHOLE0()"
  Constraint: { "SPRFHOLE0": { regex: "Query|LazyQuery" } }

Step 5: Lower via ast-grep rule API
  Pattern::try_new() with constraints attached
  (See §ast-grep API shape below)
```

## RTKQ Example Fully Worked

**Input:**
```
ast[rust](use${HOOK_OP}${re(Query|LazyQuery|Mutation)}())
```

**Parsing:**
- Detect `${HOOK_OP}` → metavar
- Detect `${re(Query|LazyQuery|Mutation)}` → hole
- Extract body: `Query|LazyQuery|Mutation`

**Compilation:**
- `re("Query|LazyQuery|Mutation")` parses as literal regex (no $-terms, no special ops)
- ReOp compiles to regex: `Query|LazyQuery|Mutation` (no (?P<...>) unless named groups present)
- Extract: `"Query|LazyQuery|Mutation"`

**Lowering:**
- Rewritten source: `use$SPRFSLOT0$SPRFHOLE0()`
  - `$SPRFSLOT0` = existing synthetic for `${HOOK_OP}` (handles sub-token extraction; regex = `^(?P<HOOK_OP>\S+)$`)
  - `$SPRFHOLE0` = new synthetic hole
- Constraints: `{ "SPRFHOLE0": { regex: "Query|LazyQuery|Mutation" } }`

**ast-grep rule API:**
- Call `Pattern::try_new(&rewritten, lang)` (existing line 275)
- For each constraint, attach via... **TBD** — need to inspect ast-grep 0.36 API for constraint attachment. Likely:
  - Post-construction, mutate `Pattern` internal state (if mutable)
  - Or, use ast-grep's rule YAML struct if Pattern wraps it
  - Or, rebuild Pattern from rule YAML doc with constraints baked in

**Matching:**
- ast-grep matches `use<OP_NAME><SUFFIX>()` in source
- Applies `$SPRFSLOT0` regex to `<OP_NAME><SUFFIX>`, extracts `HOOK_OP`
- Applies `$SPRFHOLE0` regex to matched text at that position — must satisfy `Query|LazyQuery|Mutation`
- If constraint fails, skip this match

## Constraint Shape: ast-grep API investigation

**Question:** How does ast-grep 0.36 `Pattern` accept per-metavar constraints?

**Candidates:**
1. `Pattern::try_new(src, lang)` returns a `Pattern` that is opaque to constraint mutation.
   - **Fallback:** Emit a constraint-bearing YAML rule struct separately; wrap both in a custom pattern wrapper.

2. ast-grep rule YAML shape (from user docs):
   ```yaml
   rule:
     pattern: use$OP$SUFFIX()
     constraints:
       SUFFIX:
         regex: Query|LazyQuery|Mutation
   ```
   - ast-grep loads YAML rules; our `Pattern` might expose a method to load from rule doc.
   - **Action:** Check `ast_grep_core::Rule` struct and loaders.

3. `env.get_match(slot_name)` (line 170) is where we validate slots post-match.
   - Current: named regex applied to captured node text (line 172).
   - Extension: Apply hole constraints the same way (treat holes as implicit regex validators).

**Recommended approach:** Treat holes as implicit slot_regexes with synthetic names. They're applied post-match in `scan_with_grep` (line 169–184), same as user-named slots. Simplest path.

## Edge Cases

### Hole positioning
- **Start of pattern:** `${re(...)}foo()` — synthetic metavar at token boundary, no identifier neighbors. ✓
- **Between metavars:** `use${HOOK}${re(...)}()` — both are tokens; ast-grep sees two adjacent metavars. ✓
- **End of pattern:** `foo${re(...)}` — same. ✓
- **Nested in structure:** `foo[${re(...)}]` — bracket sub-expression. ✓

### Multiple holes in one pattern
Each gets a unique synthetic ID (`SPRFHOLE0`, `SPRFHOLE1`, ...). Spliced independently, constraints collected in one list.

### Hole inside string literal vs identifier
- `"use${re(...)}"` — hole inside a tree-sitter string node. ast-grep sees a string with a metavar inside (implementation-dependent; likely metavar is stripped during pattern compilation).
- **Issue:** If the host grammar parses `${...}` carveouts separately, holes inside strings might not reach the lowerer. **TODO:** Confirm via test.

### Glob → regex anchoring
- GlobOp emits anchored regex `^...$` (line 146, 159).
- When spliced into ast pattern, the anchors apply to the matched **node text**, not the whole pattern.
- **Decision:** For ast holes, **strip anchors** from glob regex. ast-grep's metavar match is already bounded by the AST node.
  - Change: `GlobOp.regex.as_str()` → strip `^` prefix and `$` suffix before use.
  - Rationale: `**/*.rs` should compile to `[^/]*\.rs` inside ast, not `^[^/]*\.rs$`.

### Regex capture groups in holes
- `re((Query)(Mutation))` — two capture groups. Does the user expect them to bind?
- **Decision:** Hole captures are **implicitly named** (users don't see them, only the whole match is constraint). If the regex has named groups `(?P<X>...)`, they become user-visible captures (reuse re op's logic). Unnamed groups are stripped.
- **Rationale:** Anonymous holes are for constraints, not structure binding. If users want capture structure, use a named metavar `${NAME=re(...)}` (future extension).

### Kind-filtered metavars
- The RTKQ example requires `$SPRFHOLE0` to match an **identifier**, not arbitrary bytes.
- **Current:** ast-grep metavars match any AST node of the base kind (determined by context in pattern).
- **Action:** Inspect how ast-grep infers kind constraints. For `use<X>()`, the hole is in identifier position, so ast-grep should naturally constrain it to identifier nodes.
- **Fallback:** If ast-grep doesn't infer, we may need to emit `pattern: use$OP$SUFFIX()` with kind hints (not standard; revisit).

## Error Handling

**Diagnostics:**

1. **Malformed hole syntax:** `${re(` without closing `)` 
   → `ast/malformed-hole` error + span

2. **Invalid op body:** `${re([bad regex)`
   → Delegate to op's compiler; surface as `ast/hole-compilation-failed: <error>`

3. **Synthetic ID collision:** Unlikely, but if a user names a capture `SPRFHOLE0`, collision.
   → Detect during lowering; rename user captures with a namespace prefix `SPRFCAP_` if needed, or error "reserved name".

4. **Unsupported op in hole:** `${json(...)}` in ast pattern
   → `ast/unsupported-hole-op: json` (only re, glob allowed)

## Future Extension Hooks

### Named holes
```
${SUFFIX=re(Query|LazyQuery|Mutation)}
```
- User-named hole; binds the matched text + regex groups.
- Lowering: synthetic metavar stays; user name becomes an alias for the synthetic in the binding table.

### Other to_regex-capable ops
- `str`: convert to literal regex (escape special chars). `${str(hello)}` → `hello`.
- **Future:** Custom ops with `fn to_regex(&self) -> String` trait method.

### Multi-op composition
```
${glob(**/src/*.rs)}  // in ast pattern; capture directory structure + file name
```
- Glob holes preserve named groups from brace expansion (e.g., `{ts,tsx}` doesn't create groups, but intermediate steps might).

### Constraint negation
```
${re(!(Query|Mutation))}  // match anything except these
```
- Requires negative lookahead in regex or post-match validation.
- Deferred to Phase 2.
