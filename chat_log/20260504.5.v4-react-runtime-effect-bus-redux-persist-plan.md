User's stated goal: "i want to pool cursors to prove total dynamic serialization with sqlite, idea is that we eval 1 group of cursors then yes drive down... pure POC v4 rampage." Constraints:
- Render returns CursorNode (description, not action) — sync forever

- "Subject regist etc. are not wake-able right?" — v3's SubjectRegistry is async-shaped (BoxFuture+oneshot), wrong primitive for v2's sync pull-loop
- Cache invalidation = events. Wake = events. Same bus.
- "We need pathing and ability to take advantage of cascade delete in a sql sense or literal sense from store"
- "How do we guarantee a redux like system where we init from localstorage, and sync to local storage, so we can restart at same state" — answer: Phase F's transactional-drive + persistent ResponseStore + atomic per-render commit.

User's vocabulary preference: bias toward React/Redux/react-query/redux-saga/RxJS terms. Components, render, Suspense, useMemo, useQuery, queryKey, invalidateQueries, dispatch, action, Subject, Observer, mutationFn.

The "ungodly fusion" is RxJS operators flipped from push to pull, driven from a durable queue. ~6 core concepts (Pipe / Component / Node / Queue / EventBus / Driver) carry the entire system. NOT a tree algorithm — "tree" is implicit in parent_id chain; never walked eagerly. Reconciliation = multiset diff per parent, not tree diff.

## Key Insights
- **Render is description, not execution.** Components return CursorNode trees that describe what should happen next. Driver is execution. EventBus is reactivity. Queue is memory. JSX insight applied to a non-UI domain.
- **Pull beats push for durable resumability.** RxJS push assumes live producer. Pull lets storage own values; resume = reopen file. RAM = O(in-flight pc count), basically constant.
- **Yielding ≠ thread-blocking.** Render returns Suspense as a VALUE. Row goes to parked bucket. Driver exits. No thread suspended. Resume = re-render at pc+1, parent never re-runs (memoization-by-data-position).
- **Render boundary IS the yield boundary.** No `yield` keyword needed. Sequence of components = sequence of yield points. State between = cursor terms.
- **Wake and cache invalidation are the same kind of event** — fire to subscribers. Parker rows = one subscriber kind. Cache entries = another. Unified mechanism.
- **NextKey is structurally derivable** from existing QueueRow data + Next::content_hash. parent_id chain || drive_tick || batch_idx || pipe_hash || pc || content_hash. No new identity scheme needed.
- **No tree algorithms.** Reconciliation = multiset diff per parent, not tree diff. Tree exists only in the stack frame of `flatten` then dies.
- **v3's SubjectRegistry is async-shaped (oneshot+BoxFuture); v2's pausability is sync (HashSet of ready keys).** v2 stands alone. v3 is an OPTIONAL bridge for typed async dispatch.
- **Genericity is cheap (~10–15% LoC bloat).** Generic-over-Carrier compiles clean, no HRTBs, no PhantomData on user code. Integer-carrier test proves runtime is genuinely domain-neutral.
- **Sqlite-as-queue ≠ sqlite-as-relational-store.** Both use sqlite, both should share a Connection, but they're different concerns. Queue belongs in v2 (generic). Relational store stays in sprefa (schemas are language-shaped).
- **Atomic transaction per render = redux-persist semantics.** BEGIN; consume row; insert children; insert facts; insert response; COMMIT. Either all or none. Process death between renders → restart picks up consistent state.
- **Idempotence via content-derived EffectKey + persistent ResponseStore.** Re-render finds cached response, doesn't re-dispatch. Exactly-once for typical effects without per-effect ceremony.
- **Three storage layers (queue, response cache, relational facts) all sqlite, all atomic per render, all hydrate on `open(file)`. No explicit hydration step.**
- **Channel ops (Next/NextQ/Close) STAY** — user wants them as language-level pause/wait primitives, not internal plumbing. Earlier "delete in Phase 5" decision is rescinded.

## Open Questions
- **Path-as-Vec<u32> vs implicit-via-parent_id-chain:** Adding flat `path: Vec<u32>` upfront enables sqlite prefix-LIKE indices, but adds size to every QueueRow. Defer until SqliteQueue lands and prefix queries become a real cost?
- **Persistent vs ephemeral Memoize cache:** Memoize is a performance hint, not state. Persisting it speeds up cold-start. Ephemeral keeps Phase C simple.
- **EventBus dispatch ordering:** When multiple subscribers match an event, in what order do they fire? FIFO by subscribe time, or unspecified? Matters for cache-then-wake vs wake-then-cache-drop ordering.
- **External effect idempotence:** HTTP POST / send-email / kick-CI effects need user-supplied idempotency keys for exactly-once. Spec a contract for this in Phase B/D.
- **Mount when:** Bring back if a real switchMap-keyed-cancel scenario surfaces. Currently no use case in sprefa.
- **In-flight effect cancellation on restart:** Process dies with effect dispatched but not completed. Response cache shows no entry. Re-dispatch on restart. For long-running effects (LSP requests), is re-dispatch correct, or do we want a "pending" marker that persists?
- **EventBus subscriber GC:** When parker row is pulled or cache entry is dropped, the subscription should be removed. RAII guard pattern (like v3's YieldGuard) or explicit unsubscribe?
- **Cargo.lock churn:** `rusqlite` gains in Phase F. The crate was already in v4's tree; adding to effect_runtime is a workspace-level change.
