# Session: typespec-prolog-soup-lsp-recon

## Goal
Research whether Sprefa's unused type system should become a small TypeSpec-like contract language for Rust/TypeScript, HTTP, WebSocket, browser-extension, Electron, channel, queue, filesystem, and object-path boundaries. Test typed delimiter patterns, Datalog/Prolog semantics, bootstrapped generation, and a self-hosted LSP without integrating the experiments into shipping Sprefa.

## Current State
Two isolated prototypes and one study sub-book exist. No prototype has been migrated into Sprefa's shipping engine.

1. `labs/bootstrap-typegen-lab` is a single Rust binary implementing JSON-shaped types, aliases, literal unions, typed patterns, consumers, structural path enumeration, relational facts, Rust model/server generation, JavaScript fetch generation, and an explicit partial-bootstrap boundary.
2. `labs/swi-typespec-lab` authors `schema.soup`, parses it through a SWI-Prolog DCG, checks nested values, parses and evaluates typed patterns, enumerates paths, generates Rust/JavaScript, and implements a stdio LSP in SWI-Prolog.
3. `book/swi-prolog` contains a SQL -> Datalog -> Prolog learning bridge, SWI toolbox chapters, Rust/Scryer comparison, self-LSP design/status, exercises, diagrams, research notes, and the session arc.
4. `docs/bootstrap-typegen-lab-vs-typespec.md` compares the Rust lab with current TypeSpec.

## Problem/Context
The user has experience using TypeSpec and a Rust Alloy helper to generate both sides of Rust/TypeScript systems. Desired semantics include generic typed delimiter patterns that apply beyond HTTP:

- `/users/{id: UserId}`
- `users/:id/events/{kind: EventKind}`
- `users.{id: UserId}.profile.name`

Patterns should bind, match, destructure, compose, enumerate slots, enumerate nested paths, and attach to arbitrary consumers. The user also wants a shell-like/Docker-like system where declared calls/effects are cached and derived reactively.

The session expanded from Rust type-system libraries into TypeSpec comparison, Alloy, Datalog, SWI-Prolog, DCGs, Soup, and an LSP. The current concern is that this risks reimplementing existing infrastructure without a concrete unsupported use case.

## Solution/Approach
Treat all current work as reconnaissance.

Existing infrastructure:
- TypeSpec supplies the semantic type graph, templates, decorators, protocol libraries, diagnostics, packages, and standard emitters.
- Alloy supplies structured target-language generation, references, imports, and declarations.
- SWI-Prolog supplies DCGs, unification, tabling, constraints, dynamic relations, JSON/server libraries, source tooling, and saved applications.
- Existing SWI packs `lsp_server` and `prolog_lsp` already implement substantial protocol/document machinery.
- Scryer Prolog is a Rust implementation, but exact parity with SWI advanced tabling/server/tooling features was not established.

Custom semantic nucleus:
- Normalize `{name: Type}` and `:name` slots.
- Typed bind/match/destructure/compose.
- Slot enumeration.
- Nested JSON structural path enumeration with `[*]` and `{key}`.
- Protocol-neutral consumers for HTTP, channels, queues, filesystem, object paths, and message pairs.

Likely bounded product route:
- TypeSpec library records normalized pattern/consumer metadata through decorators/state.
- Alloy emitters generate Rust, TypeScript, fetch, WebSocket, extension, and Electron surfaces.
- Keep Rust and Prolog labs as evidence and learning artifacts.
- Require a concrete TypeSpec/Alloy gap before integrating a custom compiler or LSP into Sprefa.

## Key Insights
- TypeSpec string templates are interpolation objects for types/values and emitters. The custom pattern algebra adds runtime matching, destructuring, composition, and protocol-neutral slot/path enumeration.
- Alloy materially reduces emitter implementation cost and is the main reason TypeSpec remains a strong base.
- DCGs make pleasant DSL syntax independent from Prolog's internal semantic terms.
- Prolog maps cleanly from SQL/Datalog concepts: shared variables are joins, rules resemble views, tabling resembles demand-driven recursive closure, and compound terms add tree-shaped relational values.
- Prolog code generation can accidentally multiply output through valid backtracking paths. Cuts or deterministic boundaries must be deliberate.
- Existing `prolog_lsp` uses URI/range document items as the basis for hover and cross-reference operations, matching the general Soup index shape.
- The handwritten Soup LSP transport is a protocol proof and duplicates existing LSP-pack machinery.
- An embedded `initialization(build, main)` in the saved image caused the executable to rebuild and overwrite itself on launch. Explicit build invocation fixed it.
- SWI language-level terms are managed, while the runtime and native packs remain C/native safety boundaries. Tabling, atoms, dynamic clauses, and full-document rebuilding remain resource concerns.
- The session's recurring idea is: represent behavior as data, derive consequences relationally, cache derived results, and generate every boundary from one semantic source.

## Open Questions
- Does a real typed-pattern/message-pair use case exceed TypeSpec decorators plus Alloy emitters?
- Should generic typed patterns become a TypeSpec library, a standalone Soup language, or a Sprefa DSL feature?
- Is the Docker-like cached shell/effect runtime the actual product center, with types and patterns serving it?
- What exact cache key includes command, declared inputs, environment, working directory, toolchain identity, and outputs?
- Does the shell model need Datalog, differential dataflow, content-addressed storage, or only a deterministic effect graph?
- Is SWI deployment with a shared library acceptable, or is static/single-file packaging absolute?
- Would Scryer provide enough Prolog semantics and tooling while fitting the Rust distribution requirement?
