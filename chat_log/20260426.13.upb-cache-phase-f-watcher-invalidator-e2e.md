## Solution/Approach

**Phase F primitives (commit f9e050e):**

1. `invalidate.rs`: `Change` enum (FileContent | FileBatch | RevHead), `ChangeSubject` (broadcast::Sender wrapper, Store on RtCtx), `apply_change(cache, change)` pure function, `spawn_invalidator(cache, subject)` long-running drain task.

2. `cache_key.rs` extension: new `paths: Mutex<HashMap<LeafCoord, HashSet<key>>>` reverse index populated on insert from batch's `(repo, rev, fs)` cursors. `evict_paths(coords)` and `evict_rev(repo, rev)` scrub L1 + L2 + reverse index. `LeafCoord = (Arc<str>, Arc<str>, PathBuf)`.

3. `disk_cache.rs` extension: `delete_many(keys)` wraps bulk DELETE in transaction.

4. `fs_watcher.rs`: `spawn_fs_watcher(repo, root, sender, debounce)` uses notify-debouncer-mini; canonicalizes root for macOS /private/var prefix; emits `Change::FileBatch` per quiesce window. macOS dir-granularity caveat documented as Phase F.2.

**E2E proof (commit 5361311):**

- `invalidate_e2e.rs` — three Pipeline::Op tests with CountingOp: (1) miss → hit → evict → miss recompute counter ticks 1→1→2; (2) unrelated path eviction is no-op; (3) rev-hop drops every entry under (repo, rev) but HEAD survives.
- `disk_cache_e2e.rs +1` — insert → evict_paths → assert L1.len==0 AND L2.len==0 → drop process → reopen sqlite → still 0 → next run recomputes (calls counter ticks). Proves DiskCache.delete_many is a real write.
- `watcher_loop_e2e.rs` — pre-populate 3 entries, spawn_fs_watcher + spawn_invalidator, write to file, wait 2s, assert cache shrinks AND unrelated entry survives. Cleanup ordering: drop watcher → drop subject → invalidator.abort().

## Key Insights

**No Watcher trait — concrete producer functions.** Original instinct was Java-brain: trait Watcher { fn subscribe → Stream<Event> }. Reframed as one tokio::sync::broadcast::Sender<Change> + concrete function-per-source (notify-glue today, .git poller tomorrow, pack watcher later). The seam is the Change value type, not a polymorphic trait. User pushed for this framing explicitly.

**Loop closure requires the integration test, not the unit test.** Unit tests of evict_paths called OpCache.insert directly with hand-crafted cursors. They proved the eviction *function* works in isolation. The integration test (Pipeline::Op + CountingOp + apply_change) proves the *runner* threads through eviction correctly. Two different things; only the latter catches "we forgot to populate path_idx in Pipeline::Op's insert path".

**L2 eviction must cross process boundary.** Without the drop+reopen sqlite assertion, delete_many could silently no-op and the in-process test would still pass via L1 alone. The disk_cache_e2e extension explicitly asserts l2.len() == 0 after evict + reopen.

**Cleanup ordering for tokio + notify.** Debouncer guard owns a Sender clone of the broadcast channel. drop(subject) alone won't close the channel — the watcher's clone keeps it alive, so invalidator.recv() never returns Closed and any .await on the JoinHandle hangs forever. Fix: drop watcher FIRST, then drop subject, then either await OR abort the invalidator. Tests use .abort() because awaiting risks indefinite hang on missed cleanup.

**Live binary gap is structural, not a wiring oversight.** backend.rs:373 instantiates OpCache inside the per-seed loop. Even after binding ChangeSubject next to it, the cache dies when the function returns. Wiring Phase F into LSP requires hoisting OpCache to Backend state — bigger refactor than just calling spawn_invalidator. Ditto sprefa-run (one-shot CLI, process exits before any FS event arrives).

- L2 path for LSP: workspace-relative .sprefa/cache.db? Or per-repo .sprefa/cache.db? sprefa-run uses cfg.run.out_db; LSP needs an equivalent that doesn't pollute every workspace it opens.
