## Problem/Context
`fs()` over swc = 14s/rule because `git2::Tree::walk` walks 83k objects every call, and 4 rules × N revs × repeated runs re-walk identically. Real fix: materialize once via `git worktree add`, index once via sqlx, query forever. Unbounded rev patterns (`rev(**)`) would blow up materialization, hence 6a guardrail.

## Solution/Approach
Reader-side cache pair, fully optional:
- WorktreeProvisioner maps (repo,rev) → on-disk WT via `git worktree add` (shelled via spawn_blocking; tokio::process not enabled in v2).
- SqlxPathIndex maps (repo,rev,path,blob_oid) in own SQLite pool (NOT coupled to crate::store::Store — isolation chosen to avoid deep refactor).
- GitBlobReader.files() 3-phase: (1) PathIndex hit = 1 GLOB query; (2) miss + WT materialize + `git ls-tree -r -z` + bulk upsert + re-query; (3) libgit2 fallback.

Design decisions made during session:
- sqlx over rusqlite (workspace already has sqlx at tokio runtime; rusqlite only in v1 crates).
- Separate pool for path_index (don't extend Store trait).
- No RepoId/RevId types — codebase uses Arc<str> for both; FilePath(Arc<Path>) is the path type.
- Option<Arc<...>> instead of PathIndexMode enum + NoopPathIndex — simpler; None at every call site today until 6e wires Some.
- `new_with_index` new ctor + delegation preserves all 8 existing `new` callers without edits.

## Key Insights
- Subagent dispatch worked well with: (1) explicit reading list with file:line, (2) ground-truth corrections inline (spec said rusqlite, reality is sqlx; spec said `RevOp::from_args`, reality is `RevFactory::parse`), (3) absolute stop conditions enumerated, (4) N+1 discipline as hard rule not suggestion.
- Agents default to N+1 — 6c upsert_rev shipped per-row INSERT inside tx; 6c files_at shipped pre-check has_rev before SELECT. Both audited + fixed inline. Lesson for future dispatches: include explicit "no per-row loops in transactions" and "one query per method" requirements.
- 6d shipped a subtle N+1 regression: the async block rebuilt `GitBlobReader::new(locator, config)` with empty caches for phase 3 fallback. With path_index=None (current production), every call lost self's tree cache. Sync fast-path short-circuit at top of `files()` fixes by returning `self.files_libgit2(...)` directly before entering async. Until 6e wires Some(index), behavior is now identical to pre-6d.
- tokio::process feature not enabled — spawn_blocking + std::process::Command is the pattern used throughout. Don't add the feature for 6e/6g.
- thiserror not in v2/Cargo.toml — manual Display+Error impls for PathIndexErr, ProvErr. Keep pattern.
