## Problem/Context
The mounted_query N+1 was caught by the unit budget test (MemFactStore path), but the bench was STILL slow after the fix. The real N+1 was in a DIFFERENT code path: `runtime_graph::resolve_source_root` shelled `git rev-parse --show-toplevel` per call, and `ast.dispatch`'s serial pre-par_render loop hit it once per file cursor. 63k cursors × ~10ms fork = the 10-min wall.

The existing budget test used `MemFactStore` and `Rule::run_with`. It missed:
1. SqliteFactStore satellite-table per-row inserts (the `SupportLedger.add` per-row writes inside `reconcile_owner_table`).
2. `RuntimeGraph::source_index(hint)` → `resolve_source_root(hint)` per-row fork+exec called from `ast.dispatch`.

The stress-test agent landed 7 isolation tests that cover both shapes plus 5 other per-row primitives.

## Solution/Approach
- `SupportLedger::add_batch(triples)` — one `SUPPORT_TABLE` scan, one `insert_batch`. Replaces the per-row `add` loop.
- `resolved_root_cache: Arc<DashMap<PathBuf, PathBuf>>` on `RuntimeGraph` keyed by INPUT hint (cached BEFORE resolving). 63k calls collapse to 1 fork. Then `resolve_source_root` itself replaced with a stat-walk for `.git` (or `.git` file for worktrees) — pure FS ops, off-git returns instantly.

## Key Insights
- Budget tests using `MemFactStore` miss SqliteFactStore-only N+1s. Stress tests need to cover EACH primitive in isolation (per-row fork+exec, per-row sqlite scan, per-row insert_batch with vec![1], per-row triple_mult scan) regardless of where they're called from.
- The user's mental model "I have a file listener for all files I know facts are on" matches the runtime's actual wake path EXCEPT for the missing OS-side trigger. `MEMO_DEPS` is the deduped file set. `notify_table_inserted` is the table-side wake. Missing: an FsWatcher that bumps `SourceClock` and emits `RuntimeJob` per owner reading the changed file.
- `warm_changed_paths` returns the union of (files whose SourceIdentity moved) + (`git status --porcelain` dirty set). It IS the "untracked/changed-only" scope, but only after the FIRST cold run populates `_memo_deps`. Backend holds ONE persistent `SprfClient` across keystrokes, so the cache survives.
- I claimed earlier that `FsComponent` emits "one big Node::Many of 63k cursors" — WRONG. It already chunks via `self.batch` and `flush()` (`v2_ops.rs:435-456`). The remaining concern is QUEUE peak (atomic dispatch holds all chunks before ast drains them), not FS-side memory. The corrected plan reflects this.
- `Diag` carries the rust-file span where the error is, but NOT the sprf-file span of the rule that emitted it. `OpAst.span` (`compile/ast.rs:60`) has it; runtime drops it. Fix is 3 files, ~50 LOC, threads through to LSP `Diagnostic.relatedInformation`.
- BANNED WORD: "provenance" (per CLAUDE.md, alongside substrate, load-bearing, regime). Use "source location" / "origin" instead.
- `daemon-owned FsWatcher` is the right architectural home (one per workspace, survives LSP frontend reconnects, can serve CLI clients via the same RPC surface).
