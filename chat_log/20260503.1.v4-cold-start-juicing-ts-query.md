# Session: v4-cold-start-juicing-ts-query

## Goal
Drive v4's cold-start (no parse-cache) bulk-scan wall down by replacing
N separate `find_all` walks per file with a single tree-sitter native
`Query` walk that captures all M patterns in one CST traversal.
Cache is **explicitly out of scope** — author preference is to make
the first run fast, not the second run fast.

## Current State
HEAD `db5e9fb` on `wip/kitchen-sink-react-hook-fix`. v4 has:

- buffered-channels pipeline (`drive_with`) and Fs-via-spawn_blocking
  fully decoupled at cap=64
- batch=4096 tuned for bulk scan
- byte-to-byte parity with v3 (16627 matches both sides on `printk($$$)`)
- rich telemetry (bytes_in, parse_ns, match_ns, rss gauge per op-batch)
- MultiAstNm with chunked output (out_chunk_files=256), share-the-parse
- skip-utf8 (`fs::read` + `from_utf8_unchecked`)

Empirical cost model on linux fixture (63482 .c/.h files, --workers 8,
--cap 64, --batch 4096, pattern `$X($$$)`):

  wall(M) ≈ 17 s + 3.5 s × M

  M      wall    parse_sum   match_sum   p/m    rss_max
  1      21.9s   132.0s      22.2s       6.0×   607 MB
  5      38.3s   137.9s      112.1s      1.2×   756 MB
  10     57.4s   145.6s      239.8s      0.6×   849 MB

Parse-wall is a fixed 17 s ceiling (parse_sum/8 workers ≈ 17). Match-wall
is dead linear in M. Crossover at M ≈ 5.

The 3.5 s × M slope is what the next session attacks.

## Problem/Context
At M ≥ 5, MultiAstNm is match-bound. Each pattern in the rule pack costs
~3.5 s of wall on the linux corpus, paid as **N separate `find_all`
calls on the same `AstGrep<StrDoc>`**. Each `find_all` walks the entire
CST. So for a rule pack with M patterns, we do M full tree walks per
file even though tree-sitter has a native multi-capture query engine
that walks once.

`tree_sitter::Query` compiles N S-expression patterns into a state
machine. `QueryCursor::matches(query, root_node, source)` walks the
tree once and yields `(pattern_index, captures)` tuples. That's the
"one walk, N captures" primitive. Predicates (`#match?`, `#eq?`)
run inside the cursor without surfacing every candidate to user code.

Predicted impact on the cost model:
- match cost per pattern collapses from ~3.5 s to ~0.5 s
- new model: `wall(M) ≈ 17 s + 0.5 s × M`
- M=10 cold scan: 57.4 s → ~22 s (≈ M=1 baseline!)
- M=20: would be ~27 s instead of ~87 s

This is the big lever.

## Solution/Approach
Build a `TsQueryAstNm` op alongside `MultiAstNm`. Same Op trait
shape, same input/output Cursor stream, same chunked output to
bound RSS, same per-batch atomic accumulators for telemetry.

API plan:
```rust
pub struct TsQueryAstNm {
    pub query_src: String,                 // composite ts-query S-expr
    pub label_per_pattern: Vec<String>,    // index → PAT label
    pub lang: SupportLang,
    pub out_chunk_files: usize,
}
```

Internals:
1. Construct once: `tree_sitter::Query::new(lang.get_ts_language(), &query_src)?`.
   Bind labels via `query.capture_names()`.
2. Per-file inside par_iter:
   - `fs::read` + `from_utf8_unchecked` (same as today)
   - prefilter: extract per-pattern literal anchors via Query walk OR
     pre-compute a fused fixed-string set and `String::contains` for
     any of them. Probably skip per-pattern prefilter on first cut and
     just always parse — the share-the-parse is the win, not the
     prefilter (and ts-query already prunes by node kind in its NFA).
   - Parse: `tree_sitter::Parser::parse(bytes.as_slice(), None)` —
     directly bytes, even cheaper than AstGrep wrapper.
   - Walk: `QueryCursor::matches(&query, tree.root_node(), src.as_bytes())`.
     For each match, look up `match.pattern_index` → label, push a
     Cursor with PAT=label, LO/HI from capture range.
3. Aggregate per chunk, send via bounded mpsc (same as MultiAstNm).

Plumbing:
- ast-grep-language exposes `SupportLang::get_ts_language()` returning
  a `tree_sitter::Language` (verify; if not, depend on `tree-sitter-c`,
  `tree-sitter-cpp`, etc. directly — already in v4 Cargo.toml features).
- Add `tree-sitter` crate dep to v4/Cargo.toml.
- Translate ast-grep `$X($$$)` patterns → ts-query S-expressions.
  v3 already has this lowering somewhere (check v3/crates/sprefa_parse).
  For the bench, hand-author the ts-queries:
    - `$X($$$)` → `(call_expression) @call`
    - `$F($A,$B)` → `(call_expression arguments: (argument_list . (_) @a . (_) @b))`
    - `printk($$$)` → `((call_expression function: (identifier) @f) (#eq? @f "printk"))`

For the bench we don't need a general lowering. Just hand-write the
ts-query equivalents of the patterns we already use in v4-bench. v4-bench
gets a `--ts-query "..."` flag that swaps MultiAstNm → TsQueryAstNm.

## Key Insights from this session
1. **Prefilter selectivity is the only ≥4× pattern-level dial.** Rare
   literal (`printk`) → 4.3 s scan. Common literal (`static`) → 18 s.
   Empty fixed_string → 23 s. Once parse is forced, AST node kind /
   metavar count / nesting are second-order (±15 %).
2. **Parse cost is 92 % of empty-prefilter wall.** Read + UTF-8 alloc
   + memchr is ~8 %. File open is sub-second on 63 k files. tree-sitter
   parse is the wall.
3. **Parse rate per worker on real C: ~7.7 MB/s.** Confirmed from
   three independent angles (single-file, bulk, parse_sum/wall ratio).
   On `#define`-only AMD register headers: ~51 MB/s. Real C is 5×
   harder per byte than `#define`.
4. **Linear in file size.** 1×/2×/4×/8× of a 24 MB file shows flat
   slope at 19.7 ms/MB ±1 % — no quadratic, no allocator cliff at
   200 MB. RSS bounded.
5. **Chunked sub-batches in MultiAstNm cut peak RSS 45–60 % at no wall
   cost.** Operator chooses output batch size; should be a general v4
   pattern for high-fanout ops.
6. **Cost model is two-term linear.** parse-wall is a corpus-and-machine
   constant; match-wall is linear in pattern count. Crossover at M ≈ 5
   for current config. Useful for capacity planning.
7. **Knob defaults are workload-shaped.** bulk scan: cap=64, batch=4096
   (huge wins from 256 → 4096 — 6.1 s → 3.8 s). Incremental/single-file:
   cap=8, batch=256 (preserve tail latency).
8. **v4 is now 8 % faster than v3 on the bulk-scan baseline.** Was +37 %
   before tuning. Fs::new keeps incremental defaults; v4-bench uses bulk.
