## Problem/Context
v0/v3 had sqlite over-bound; v4 needed the Store trait mastered with
empirical numbers across all four backends. Author asked "are rules
super duper special?" — answer: 80% an op already, 20% special by
historical accident (typed sink, name-addressable cache state, not
callable from inside pipelines). The lockfile-crawl use case
(dynamic repo+rev pairs, custom parsers, recursive dep graphs) drives
the next round of design — needs cheap op authoring (SimpleOp landed
this session) + RuleCall/RuleRegistry + drive_rule_to_fixpoint.

## Solution/Approach
- Bench wired sqlite-{mem,disk,fast} via FactWrite (declared schema)
  + commit at end of Insert mode. Trial-1 wipes db for cold determinism.
- PRAGMA bundle: page_size=8192, journal=MEMORY, sync=OFF,
  locking=EXCLUSIVE, temp=MEMORY, cache_size=-65536. 1.87× win over
  default WAL+NORMAL on 366k rows.
- Phase spans isolated where commit cost is spent: write (bind+VDBE)
  vs txn (page flush). On sqlite-disk, fsync overhead lives inside
  write, not just txn.
- Multi-row INSERT VALUES (?,?,?,?), (?,?,?,?), ... chunked at
  SPREFA_SQLITE_CHUNK env (default 500). Ceiling at ~2000; bigger
  chunks regress.
- Option<&str> bind avoids 1.5M per-cell String allocations on the
  366k-row workload (in noise vs Strings due to sqlite copy-in cost).
- Empty-body Rule passthrough via Rule::into_chain_with_seed: prepends
  Seed(seed) to body chain. Empty body collapses to [Seed > FactWrite].
- drive_rule_cached now early-returns Skipped on empty body, after
  calling rule.declare. Schema gets ensured; nothing drives.
- Sh::is_pure=true ⇒ wraps under OpCache. Skip-on-hit semantics
  identical to AstNm. ShBang refused (is_pure=false).
- SimpleOp: kind() + instance() + step(&Cursor) -> Vec<Cursor>. Blanket
  impl provides ident, run, telemetry. Existing ops keep manual Op
  impl (would conflict with blanket if they also impl SimpleOp).

## Key Insights
- Final SQL throughput on 366k rows, 4-col TEXT:
    mem        875ns        no-op
    dd         13.9µs       no-op
    sqlite-mem 141.7ms      2.59M rows/s    write 140 + txn 1.5
    sqlite-disk (WAL+NORMAL)  447.6ms  818k rows/s   write 313 + txn 135
    sqlite-fast (MEMORY+OFF)  238.9ms  1.53M rows/s  write 139 + txn 100
- sqlite-fast bind loop ≡ sqlite-mem bind loop (140 vs 139ms). The
  WAL fsync overhead lives in `write` not just `txn` on default.
- Per-tx fixed cost ~800µs even at sync=NORMAL on disk. Reactive (LSP)
  workloads with many small commits eat this fixed cost N times.
- Multi-row VALUES chunking sweet spot ~100 rows; beyond ~2000 regresses
  due to prepare-cache miss on irregular tail + larger param vectors.
- Author's mental model is React with relational substrate: Op = pure
  fn, Hooks (literal name), useEffect = Effect, useMemo = OpCache,
  Suspense = switchMap. Diverges: relational reconciliation (DD diffs),
  parallel by default (rayon), persistent cross-process cache.
- "Render-then-flatten": op chain expands a tree shape during run;
  FactWrite commits flat rows. SqliteStore + Layer-3 OpCache is SSG-
  with-revalidation: static-by-default, recompute when input set hash
  flips.
- Lockfile crawl is the load-bearing use case: parse lockfile A → emit
  (repo, rev) pairs → drive Repo source → parse those files → emit
  more pairs. Recursive read-of-own-sink. Drives need #11 fixpoint.
- "Op easy as fuck to use" + "least var ref" → SimpleOp + emit-as-bind-
  then-pass-through. Chain reads/writes via documented term names; never
  thread cursors explicitly.
- Rules are 80% an op already. Remaining 20%: typed sink, name-keyed
  cache state, not-callable-from-inside-pipelines. RuleCall + Registry
  (#10) closes the gap.

## Open Questions
- RuleCall::run signature: pipe input batches into rule body directly,
  or collect into Seed and re-drive? Direct piping preserves backpressure
  but RuleStateCache keying becomes per-call-site, not per-rule-name.
- drive_rule_to_fixpoint convergence detection: count rows? hash sink?
  Max-iteration cap default = 64? User-configurable per rule?
- Lockfile-reader format: do we use a tree-sitter grammar (consistent
  with AstNm) or a typed crate (toml_edit, serde_json) wrapped as
  SimpleOp? Tree-sitter wins for incremental + injection; typed crates
  are 1-day vs 1-week.
- Persistent OpCache sqlite table eviction: LRU + bounded row count, or
  TTL? Probably bounded count, discarded oldest first by `last_seen_at`.
- Connection pool: rusqlite supports it via r2d2 / deadpool; or hand-roll
  a Vec<Mutex<Connection>>? Single-writer + N-readers is the actual
  shape, not full pool.
