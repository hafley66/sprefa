## Problem/Context
User explored composing existing primitives (tag, str, print) into ergonomic shapes and hit two walls:
1. `tag(:a, str(A), str(B))` — tag rejects Value::Op args (tag/op-arg-unsupported).
2. `str(ABC) > ${X} > print(:a)` — `${X}` is illegal as a pipe step (carveout_expr only valid inside paren slots, not as standalone op_invocation).
Also: print emits cursor.active() bytes, NOT the StrValue slot str() writes — so str>print does not "render" the str template.

## Key Insights
- print op is fully wired: PrintOp::from_values accepts Atom or Str as prefix, emits cursor.active() via PrintEffect (print.rs:39, 99). NOT a string-template renderer.
- str op writes to a typed StrValue slot via cursor.put_slot, NOT to active bytes. Consumed by downstream source ops (fs(str(...)), repo(str(...))) that read the slot through their arg spec. str(ABC) > print does not print "ABC".
- tag's classification logic (tag.rs:118-139) splits args into bound/unbound. Atoms+Strs+Ints+Floats+Read-mode terms = bound. Unbound terms = read. Mixed = error tag/mixed-mode. Op args = error tag/op-arg-unsupported. First arg must be Atom (bag name).
- tag's ?-suffixed counterpart (TagPredicateOp) routes all-bound→Probe, mixed→Join (datalog filter+project), all-unbound→Query.
- ${X} carveout_expr is a value-position form. Pipe steps must be op_invocation. The grammar split is intentional — carveouts only mean things to outer ops via ArgSpec introspection.
- `;` distributes the parent step as a Fork — it is NOT a statement separator. Two top-level pipes go on separate lines.
