type (`CompiledPattern`) consumed uniformly by top-level ops, the Reader trait,
and the LSP completion filter. Close the v2 regression where `re:`, `$NAME`,
`{a,b}`, `[abc]`, and `a|b` only worked inside walker slots.

## Key Insights
- **v2 drifted from v1 by putting pattern matching in the Reader.** v1 had
  enumerators return everything and op-side `CompiledFileSelector.matches(path)`
  filter (`crates/rules/src/extractor.rs:96`). v2 moved glob_match into
  `Reader::files` and lost every matcher flavor beyond `*`/`?`/`**/`. The fix
  is not to add in-op filtering but to upgrade the Reader to take a
  `CompiledPattern` (option B in the design deliberation).
- **One matcher, one filter, one path.** Completion filter calling the same
  compiler the op uses at runtime means editor suggestions never drift from
  runtime behavior. This is what `CompiledPattern::compile(partial)` in
  `complete_in_paren` buys.
- **Mid-typing LSP source is hostile to full parse tests.** Special characters
  inside parens (`|`, `$`, `[`, `]`) confuse the top-level tokenizer even
  though they should be paren-internal. The boundary between "syntactically
  complete source being edited" and "mid-typing source" deserves its own tests
  but those belong to scanner/tokenizer, not pattern matching.
