# Session: sprefa-overfit-loop-invariant-perf

## Goal
Iteratively build a static-analysis rail in sprefa v5 that captures the
*prog_rels* perf bug class (loop-invariant recomputation: `prog_rels(prog)`
called once per rule inside a loop, O(F*R) -> O(R+F)). The meta-goal: make it
possible to "overfit" a rule to any newly-found perf bug so future instances of
the same shape get caught. Dogfood the rule on sprefa's own source.

## Problem/Context
The prog_rels regression (typecheck.rs:439 called prog_rels(prog) once per rule
in the loop; flamegraph found it; fixed by hoisting). Original v0 dataflow lift
was value-flow only: blind to loops/branches/closures (31% of nodes were
unhandled "expr" holes), so it could not see into the loop body where the bug
lived. The question: can the lift + a derived rule catch this bug class, and is
that what CodeQL/Semgrep/Glean are for?

## Solution/Approach
Tiered build, each tier validated on the host before the next:
- **T1** — close control-flow holes: route block-bearing syn Expr variants
  (ForLoop/While/Loop/If/Match/Block/Closure/Try/Assign) through flow_block.
  Hole rate 31% -> 12%; node count 5466 -> 22179. Kotlin already recursed; TS
  + Rust were the holes (one default arm each).
- **T2** — loop_over(file,start,end,var,collection,fn) relation + a flag rule
  joining loop spans against df_node/df_edge. Param-proxy invariance
  ("arg is a param, not the loop var"). 415 suspects on host. Bug site
  (check_and_normalize:438) flagged but buried in noise.
- **T3 S1+O1** — allocates(fn) cost signal (Vec/HashMap/String ctor,
  .collect/.clone/.to_string) + call_name(sym,name) to resolve call_site.callee
  text to a def sym + O1 line-shortcut (def.line < loop.start, generalizes
  param-only). 415 -> 123.
- **T3 strict** — antijoin: exclude calls with ANY loop-carried input. A
  fully-loop-invariant allocating call = pure recomputation = the prog_rels
  signature. 1 hit buggy / 0 fixed on fixture; 13 on host.
- **destructuring** — bind_pat recurses into tuple/tuplestruct/struct/slice/
  reference/paren; match-arm patterns edged from the scrutinee. Cuts FPs where
  match/tuple-bound loop vars looked loop-invariant.

## Key Insights
- Node id = `file:line:col:kind` (kind suffix disambiguates parent/first-child
  that share a start span).
- Closure-read of df_reaches in a rule body needs a LITERAL-PINNED endpoint
  (engine guard). The strict rule sidesteps this by using plain df_edge (2-hop
  param->var_read->call_res) + an antijoin, no closure needed.
- The precision lever is NOT reaching-defs (the closure is already reaching-defs)
  but the antijoin "no loop-carried input reaches the call." A param is
  loop-invariant by definition; a fully-loop-invariant allocating call is pure
  recomputation. That single antijoin took 415 -> "catches the bug, 0 on fix".
- syn 2.0 in use (not 1.0): no ExprWhileLet/ExprAssignOp; Block.span() not
  brace_token.span; ToTokens not via syn::export. proc_macro2 Span has .end().
- Kotlin tree-sitter: additive/multiplicative/infix_expression (NOT
  binary_expression), no named fields -> first/last named children for operands.
- The "overfit a rule to a bug, then generalize" loop IS the CodeQL/Semgrep
  variant-analysis workflow. sprefa is architecturally a CodeQL peer (Datalog
  engine over extracted code facts). See v5/docs/perf-variant-analysis.md.
