# Call-tree survey: plan + schema

**Date:** 2026-04-11
**Goal:** Cross-compare local-first call-graph / code-intelligence tools so sprefa can pick where to sit on the partial-call-tree axis. No AI at query time, no build-system coupling, tree-sitter-class extractors.
**Status:** Plan written, agents NOT yet dispatched. Resume by reading this file, then dispatching haikus per the "Dispatch" section.

## Why this survey exists

User observation: "it's all Go." Initial survey conflated "built on tree-sitter" with Rust. The actual class is Go-dominated (grepai, cymbal, SocratiCode), with C (codebase-memory-mcp), Zig (codedb), Rust (sem, CodeRLM server), and Python (COMEX, graph-sitter, ACER) as branches. sprefa is the Rust outlier — the interop question is load-bearing, not incidental.

User is leaning: **shell/template bridge OR WASM extractors** as the extensibility seam that crosses the Rust/Go gap cleanly.

## The four load-bearing axes

Every other dimension is context. These four drive the sprefa design decision:

1. **`locals_resolution`** — does the tool use tree-sitter `locals.scm` scope queries, a custom scope resolver, full semantic, or nothing? This is the cheap-to-scoped-resolution upgrade path.
2. **`call_order_preserved`** — can you ask "what does `login()` call in the order it appears in the source"? Most tools throw away order; sprefa's opportunity is to keep it.
3. **`query_surface`** — fixed commands (cymbal/grepai), Cypher (codebase-memory-mcp), SQL, datalog, path-DSL. sprefa's opening is declarative query surface.
4. **`interop`** — CLI, MCP, library, daemon-stdio, FFI, shared DB file. Determines how cheaply Rust sprefa can interop with Go peers.

Agents emit one markdown block with these exact headers and no extras. Concatenation of 12 blocks is the matrix.

```
- license: <SPDX id>
- store: <sqlite | gob | custom-binary | in-memory | protobuf | jsonl | other>
- store_file_path: <relative path where it persists, or "in-memory">
- schema_shape: <table-rows | property-graph | triple-store | ast-dump | other>

- call_edge_model: <text-field | resolved-id | both>
- call_order_preserved: <yes | no | unclear>
- branch_path_preserved: <yes | no | unclear>
- cross_file_resolution: <no | symbol-table | import-aware | semantic>
- query_surface: <fixed-commands | cypher | sql | datalog | path-dsl | custom-dsl>

- core_files: <up to 5 paths, each with ONE line purpose>

- wasm_embeddable: <yes | no | would-need-work>
- stdin_stdout_friendly: <yes | no>
```

### Why these fields, field by field

| Field | Why it matters for sprefa |
|---|---|
| `language` / `build` / `runtime` | Determines interop cost with Rust sprefa |
| `license` | Do we fork it, wrap it, or reimplement the idea |
| `store` / `store_file_path` | Shared-DB-as-FFI feasibility — can sprefa read their file or vice versa |
| `schema_shape` | Do they model calls as rows (SQL-joinable) or as graph nodes (Cypher/Gremlin) |
| `extractor` | Prior art for the `ast-grep + tree-sitter + syn` multi-extractor story |
| `languages_supported` | Calibrates sprefa's language-coverage expectation |
| `locals_resolution` | The cheap upgrade from band-1 lexical to band-2 scoped — do they use locals.scm? |
| `call_edge_model` | Text-field (sem) vs resolved-id (rust-analyzer) — sprefa wants both columns |
| `call_order_preserved` | **The sprefa differentiator** |
| `branch_path_preserved` | Proto-CFG lite — does anyone else extract `then`/`else`/`loop` context |
| `cross_file_resolution` | Where they stop on the resolution ladder |
| `query_surface` | **The other sprefa differentiator** |
| `interop` | How the agent can call them without cgo pain |
| `incremental` | Reindex cost model — matters for watcher integration |
| `loc_approx` | Complexity signal — is this a 2kloc hack or a 50kloc engine |
| `core_files` | For any later drill-down pass |
| `call_extraction_mechanism` | The most important free-text field — mandates file-path citation so claims are checkable |
| `partial_tree_support` | Direct answer to the sprefa use case |
| `unique_ideas` | Ideas to steal |
| `wasm_embeddable` | WASM-extractor plugin path feasibility |
| `stdin_stdout_friendly` | Shell-bridge extractor path feasibility |

## Agent prompt template

Every haiku gets this exact prompt with `<TOOL_NAME>`, `<LOCAL_PATH>`, and `<KNOWN_LANG>` substituted. No other context.

```
You are one of 12 parallel agents surveying local-first call-graph and
code-intelligence tools. Your target is ONE repo, already cloned locally.
Read it thoroughly and produce a structured report.

TOOL_NAME: <TOOL_NAME>
LOCAL_PATH: <LOCAL_PATH>
KNOWN_LANG: <KNOWN_LANG>

Task:
1. Fill in the "## <tool-name>" schema block below exactly — every field,
   in this order, no reordering. These are the comparison keys; the matrix
   grep depends on them staying consistent.
2. After the schema block, write an "## Analysis" section. Here you can
   explain in as much depth as the tool warrants. Walk through how the
   extractor works, quote relevant code with file:line citations, describe
   interesting design decisions, flag gotchas, note LOC and complexity,
   compare patterns you see to what you know about tree-sitter locals.scm /
   CFG extraction / name resolution. The length of the Analysis section is
   your call — a trivial wrapper warrants one paragraph, a novel
   architecture warrants several pages. Be thorough where it is earned,
   terse where it is not. No upper word limit.
3. At the end, write a "## Files read" section listing every file path you
   actually opened, so the human-driven second pass can re-check claims.

Rules:
- Every claim about call extraction, storage, or schema shape MUST cite a
  file path (and line number when feasible). Unsourced prose is worse than
  "unknown".
- If a schema field cannot be determined after reasonable searching, write
  "unknown" for that field — do not guess. Discuss the uncertainty in
  Analysis if it matters.
- Do NOT run the tool. Static reading only.
- Do NOT synthesize across tools. You see only your one target.
- Do NOT skim — if the repo is small (under 5kloc) cover it fairly
  completely. If it is large, anchor on the call/symbol extraction path
  and follow imports outward from there.

Specifically hunt for:
- Where the tool visits `call_expression`, `method_call`, `call_site`,
  `CallExpr`, `ExprCall`, or equivalent.
- Whether resolution is purely lexical (`name(` substring), syntactic
  (tree-sitter node kind), scoped (locals.scm or custom scope stack), or
  semantic (type-aware).
- Whether source order is preserved — look for `ordinal`, `index`,
  `position`, `source_span`, or ordered collections. If calls go into a
  set/map keyed on name only, source order is LOST.
- How cross-file resolution works, if at all. Symbol table? Import
  following? Or does it give up and emit text?
- The storage format and schema. If SQLite, dump the `CREATE TABLE`
  statements. If custom, describe the record layout in prose.
- Extensibility seams: can users plug in custom extractors? Via what
  interface — shell/CLI, library, WASM, scripting, config files?

If the tool does not extract calls at all, say so explicitly in the schema
AND explain why in Analysis — do not invent a description.
```

## What sprefa is trying to learn from this

In one sentence each, the questions this survey answers:

1. **Has anyone already shipped call-order preservation?** (If yes, steal the schema and move on. If no, sprefa ships it.)
2. **Does anyone use `locals.scm` for cheap scope resolution, or does everyone skip straight to band-1 lexical?** (Determines whether `locals.scm` is a free-win or an untested path.)
3. **What is the query-surface landscape — Cypher, fixed commands, or is datalog/path-DSL territory actually open?**
4. **What does each tool use for interop — CLI, MCP, library, FFI, shared DB file?** (Determines the Go-peer interop story.)
5. **Shell bridge or WASM extractor — do any peers do either?** (Validates the extensibility seam direction.)

## Shell bridge vs WASM extractor framing (for post-survey decision)

Both are the extensibility seam for crossing Rust/Go/anything. Survey should reveal whether anyone has precedent; post-survey decision is:

- **Shell/template bridge**: long-lived extractor subprocess, NDJSON over stdin/stdout, LSP-pattern. Universal, debuggable, one fork amortizes over many files. ~2ms/file spawn cost without amortization, near-zero with workers.
- **WASM extractors**: sprefa loads `.wasm` modules via `wasmtime`, passes file bytes in linear memory, reads capture rows back. In-process, sandboxed, sub-µs call overhead. Biggest win: **ast-grep compiles to WASM**, so ast-grep rule files are a zero-user-compilation plugin surface.
- **Hybrid**: ship WASM fast-path for ast-grep rules and Rust extractors; shell bridge as escape hatch for "pipe a Go tool as extractor" cases.

The survey's `wasm_embeddable` and `stdin_stdout_friendly` columns feed directly into this decision.
