## Solution / Approach

### Glob pair/triple lowering

Couldn't fix with a naive per-node substitution (`**` → any single
regex fragment) because zero-segment semantics require the surrounding
slashes to be absorbed. Collecting children into a Vec allowed O(1)
lookahead for the three patterns. Order of checks: triple first
(slash + double_star + slash), then tail-form (double_star + slash),
then head-form (slash + double_star). Never overlap at the same
index since each starts with a different kind.

### Rule as driver-level sugar, not an Op

Rule is control-flow (brace body → sub-program), not a pure pipeline
stage. Handling it above the Op layer in the driver:
1. Keeps `Op` trait from sprouting a "what's my brace body" API.
2. Lets the brace body re-enter the host parser unchanged.
3. Makes the print-header conventions a driver concern (future: LSP
   could render rule-scoped row tables the same way).

Grammar already supported `brace_slot` on any op_invocation, so no
grammar change needed. The brace body tokenizes as `_slot_body`
(opaque atoms) from the host's perspective; re-parsing the raw
substring via `host_parse_with_injections` gets proper pipe/stmt
structure back.

## Key Insights

1. **Pair/triple lookahead is the right tool for glob `**`.** A pure
   per-node substitution can't express zero-segment consumption of
   surrounding slashes. Collecting children to a Vec and walking
   with a skip index is linear, readable, and easy to extend for
   more globset features later (e.g. `[charclass]` would slot in
   as another kind branch).

2. **Rule is driver sugar, not a pipeline op.** The CLI handles
   `rule(name) { ... }` by re-parsing the brace body and running
   sub-pipes. Trying to make rule an Op with a `Pipeline` arg
   requires higher-order dispatch the current Op trait doesn't
   have; deferring until the trait grows arg_spec.

3. **`host_parse_with_injections` composes cleanly for sub-programs.**
   Passing the same resolver into the nested parse gives rule bodies
   the same pattern-op grammar injections (glob/re) as top-level
   pipes. No extra plumbing — the resolver is a closure, not a
   registry singleton.

4. **Smoke scripts are the right shape for rule.** `_2_rule.sh`
   mirrors v2's pattern: build if missing, run fixture, grep for
   headers + row shapes. Cheaper than a Rust integration test for
   a CLI-shaped feature and one source of truth.

5. **Grammar already carried rule.** `op_invocation` had `brace`
   as an optional field from day one. No grammar regen needed for
   rule to parse; the semantics landed in the driver alone.

## Open Questions

1. Registry crate location: pipeline vs new `lower` crate vs server.
   Prior chat_log tie-breaks to pipeline, but that means
   `sprefa_parse` enters pipeline's dep graph.

2. Rule body parse error coordinate space. Current brace body parse
   uses `<rule-body>` as synthetic file path and reports offsets
   inside the brace substring. When should the shift land — before
   LSP diagnostics flow through rule bodies, or earlier as a
   defensive fix?

3. Should `rule` eventually be a registry op? The driver handling
   is simpler today but forecloses treating `rule(name)` as a term
   inside other ops (e.g. `cache(rule(x), 1h)`). Likely yes once
   arg_spec lands.

4. Rule brace body: currently expects `pipe; pipe;` — does every
   body end with a trailing `;` or is the terminator optional?
   Grammar allows either; the smoke fixture uses a trailing `;`
   and parses fine. Worth a grammar-level test once more rule
   fixtures land.

5. `pipeline::lower` module (the speculative 6-concept v3 shape):
   keep, delete, or evolve it toward the real runtime? Currently
   unused — every landed op uses `_0_cursor::Cursor` +
   `_2_pipeline::Pipeline` directly.
