## Primitives: the RxJS trinity, named literally
Observable / Subject / BehaviorSubject + a BufferPolicy. Named this way on
purpose to keep the prize in view. NOT a 4th primitive: a long-running effect is
a pipe (`concatMap` into effects), not a type.

| type | temperature | shape | replay | read | dl home |
|---|---|---|---|---|---|
| Observable | cold, unicast | a pipe (creation ops / `new` / `.pipe`) | 0 | lazy: re-subscribe re-runs | a cold/lazy derived rel |
| Subject | hot, multicast | event | 0 | late subscribers miss the past | an event feed / `@in` / `@out` |
| BehaviorSubject | hot, multicast | state | 1 | sync-eager, non-blocking (current value) | `@next`, latest-by-gen |

`BufferPolicy = { replay: usize, on_full: block | overwrite | drop }`. This IS the
CSP / Go-channel tuning knob:
- replay 0, no state = Subject (event bus).
- replay 0, rendezvous = unbuffered `chan` (send blocks until a receiver).
- replay N = ReplaySubject(N) = buffered `chan` (send blocks when full).
- replay 1, overwrite = BehaviorSubject (non-blocking, latest wins).

BehaviorSubject read is non-blocking (state); Subject/channel send is the blocking
pole, tuned by the buffer. One knob bridges rx and CSP.

## Why it is NOT a "3 primitive" basis
Lowered the proposed triple to raw JS, RxJS, and Go. State is first-class in ONLY
rx (BehaviorSubject); in JS a closure `let`, in Go a mutexed field, so state is
DATA, not a primitive. In rx, BehaviorSubject extends Subject (one family). Go
settles on goroutine + chan + data = 2 primitives + data. The cross-runtime
invariant is resumable-work + boundary-channel + state-as-data, named via the rx
trinity.

### rxjs can EXHAUST SYNC (the reframe)
rxjs is not async-only: a synchronous Observable exhausts to completion in one stack
frame → covers BOTH sync generators (a datalog fixpoint run to exhaustion) and async
generators (effects, watchers). So a SYNC rxjs pipeline can BE the fixpoint: an element
stream `Observable<Row>` that `scan`-accumulates to quiescence, run synchronously, IS the
semi-naive fixpoint — no SQL when the data fits. SQL = the RAM backstop for data that
does not fit, not the only engine. This dissolves set-vs-element toward ELEMENT semantics
(native `filter`/`scan`/`reduce`) for bounded rels.

### `expand` IS the fixpoint (datalog semi-naive + prolog SLG) — YES, a real use for expand
`expand(project, concurrent)` is rxjs's recursive flatMap: each level's emissions feed
back through `project`, recursively, until `project` returns `EMPTY`. That is LITERALLY
semi-naive evaluation:
- seed = the initial delta (EDB facts / the base frontier / the query goal).
- `project(delta)` = one frontier hop: the JOIN (datalog) or UNIFY+resolve (prolog).
- dedup against a seen-set inside `project` (monotone) → a hop with no NEW facts returns
  `EMPTY` → expand STOPS = quiescence = the least fixpoint.
- fold expand's emissions with `scan`/`mergeScan` → the closure (the materialized set).

```ts
closure$ = seedDelta$.pipe(
  expand(delta => {
    const novel = frontierHop(delta).filter(f => !seen.has(key(f)));   // the join/resolution
    novel.forEach(f => seen.add(key(f)));
    return novel.length ? from(novel) : EMPTY;                          // empty → expand stops
  }),
  scan((acc, d) => union(acc, d), new Set()),                           // → the closure
);
```

- DATALOG recursive stratum: `expand` IS `lowerRecursiveStratum` (Epic 2). One hop = the
  delta-join; EMPTY delta = fixpoint. Makes Epic 2's "expand-in-rxjs vs delegate-to-
  cascade" concrete: `expand` for BOUNDED recursive rels (sync exhaust); the cascade/SQL
  for huge ones.
- PROLOG: `expand` IS the goal-tree unfold (resolution); UNIFICATION is the project step
  (`unify(clause.head, goal)` → bind vars → emit body subgoals). + a table
  (`shareReplay`/`switchMapCache` per canonical goal) = SLG: the table is not just memo,
  it is the TERMINATION condition for `expand` over a cyclic search space (without it a
  cycle loops forever; with it a repeated goal returns cached = quiescence).
- Caveat: `expand` is breadth-first-ish (concurrent levels) → matches SLG/tabled prolog +
  datalog's monotone least-fixpoint (both BFS-correct, terminating). It does NOT match
  pure SLD prolog (DFS, Prolog's default) — that wants a stack driver, not expand's level
  queue. We want SLG (terminating), so `expand` is right.

The other two:
- `mergeScan` = the ASYNC accumulator (fold deltas → the running closure). Pair WITH
  expand; it is not a self-driving fixpoint loop.
- `switchScan` is NOT stdlib rxjs (you mean `switchMap`, or a custom rxjs-ext op).
  `switchMap` = the demand/cancellation fold (switch-to-latest, cancel-stale = the
  `switchMapCache`/react-query family), NOT a fixpoint.

This STRENGTHENS the element-semantics lean: `expand`/`scan` (the fixpoint + accumulator)
only make sense over individual deltas/facts/goals, not whole sets → FORK below leans element.

### FORK — set vs element semantics (OPEN; the rxjs-soul decision)
Lowering core today = SET semantics (`Observable<Row[]>`, whole set per emission;
selection/agg inside `map`; element-ops `filter`/`reduce`/`scan` unused at the rel
level). ELEMENT semantics (`Observable<Row>`, a stream of deltas) makes
`filter`/`map`/`scan`/`reduce` native, and `@next`/latest-by-gen = a `scan`. Lean (owner
+ the sync-rxjs reframe): ELEMENT for bounded/demand rels; heavy rels never enter TS
(`RecursiveStratumDeferred` → cascade/SQL). DECIDE ON RESUME: flip the lowering to
element, or keep set + proceed.
