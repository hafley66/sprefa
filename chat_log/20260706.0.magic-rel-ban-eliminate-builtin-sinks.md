# Session: magic-rel-ban-eliminate-builtin-sinks

## Goal
Ban the "magic rel" pattern forever in the dl/sprefa v5 engine: relations the
engine special-cases by a LITERAL string name in its own Rust source
(`eng.rels.get("scip_want")`, `FROM rel_effect_cmd`) that nothing in rel_catalog
advertises. Chris escalated from "audit + plan" to "ban forever, dogfood +
skill/subagent" to "wait so we still have magic special rels" (documenting isn't
eliminating) to picking Option 1 (promote to builtin sinks) after rejecting the
`@`-qualifier design.

## Problem/Context
Four relations were bound to engine behavior by hardcoded name, invisible in the
catalog: scip_want (SCIP index demand), rev_cmp_want (git ancestry demand),
def_target (LSP go-to-def), effect_cmd (effect-template overlay). They are
UNRESERVED conventions a user HEADS from a rule (not reserved output rels — my
first-pass claim "reserved yet undocumented" was wrong; those reserved_msgs
belong to the OUTPUT rels scip_def/rev_behind).

## Solution/Approach
FIRST PASS (superseded): a `special_rel` registry (src/rels/special.rs) that
DOCUMENTED the magic — Chris pushed back that magic still existed.
FINAL (Option 1, ELIMINATE): promote the four to first-class builtin SINKS,
exactly like `diag`/`repo` (the precedent: repo is a catalogued group-`core`
builtin users head to trigger cloning). Mechanism:
- src/engine/mod.rs: `demand_rel_decls()` (RelDecls, group `demand`) +
  `DEMAND_RELS` reserved array + bail ("head it directly, like diag/repo") +
  chained into all_builtin_decls + declare_builtins. Mirrors
  diag_rel_decls/DIAG_RELS one-for-one.
- Migrated 10 `rel <name>` consumer decls (they now head the pre-declared
  builtin): 4 examples/.dl + 6 test programs.
- DELETED src/rels/special.rs, unwired SpecialKind from rel_kinds, reverted the
  4 read-site consts to plain literals (clean now that names are catalogued).
- Rail .dl/magic-rel-audit.dl now anti-joins rel_catalog ONLY (one known-set).
Rejected: `@out(cap)`/`@demand(cap)` qualifier (Chris dislikes at-symbol). The
answer to "how not do @" = "they were always just builtin sinks we forgot to
declare." Also considered but not taken: making them USER-EXTENSIBLE (a real
v4-custom-op-style registry / `builtin(...)` effect target) — Option 1 catalogues
but does not make them pluggable; that's a further step if wanted.

## Key Insights
- `repo` precedent: a catalogued builtin (group `core`) users HEAD to trigger
  cloning proves builtins can be catalogued AND head-writable. My earlier "can't
  catalogue them, cataloguing reserves them" was WRONG.
- The reserved-name guard bails only on a `rel X.` RE-declaration; heading a
  pre-declared builtin (no rel decl) is how diag/repo sinks are written.
- BUILTIN_RELS is the WRONG set (core scan coordinates, marked changed every
  reconcile in tick.rs) — mirror diag (DIAG_RELS + diag_rel_decls) instead.
- A demand sink is conceptually v5's name-bound extension seam (v4 custom-op
  role) but mechanically much thinner: builtin relation + post-tick RelKind
  reader, NO OperatorDef/Component lowering. Closest real primitive is the EFFECT
  (sh/@async) — "derivation triggers IO"; a demand sink = an effect whose
  executor is hardcoded Rust instead of a declared template.
- The hook runs the INSTALLED dl — must `cargo install --path . --force` after
  changing the catalog or the hook/CI break (old binary lacks `demand` group +
  rejects the un-declared heads).
- dl self-lint (banned-word rail) scans src/**/*.rs and caught "load-bearing" in
  my own comment — use source/base/critical/mode.
- def_target is 4-col (name, file, line, kind); engine reads name/file/line by
  column name so a named-arg subset works.
