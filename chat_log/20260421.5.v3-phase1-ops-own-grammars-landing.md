Grammar `literal: /[^*?/$]+/` parses `file.txt` fine in isolation; symptom surfaces through host_parse_with_injections at the injected reparse. Not debugged yet — flagged in commit message, sidestepped in test.

## Problem / Context

Three Phase 1 concerns the previous session had left to resolve before ripping could begin:

1. str body semantics. User locked: str is **const**, body bytes unparsed, no holes. This collapses str out of the pattern-op trait surface — it is a plain Op — and deletes the `pattern/str-forbids-hole` diag entirely.

2. tree-sitter CLI as build-dep vs committed parser.c. User locked: YOLO, manual via justfile, parser.c committed per op, build.rs becomes 40 LoC of cc + codegen, injections.scm hand-edited. Dogfood the automation later (§14.9 Phase 2).

3. Two red spec items: §13 carveout sentence contradicted §14.6; ParsedSource/InjectedTree structs were only in chat_log, not spec body. Both fixed before landing code.

## Solution / Approach

One-line Phase 1 summary: **shared/tokens.js + justfile regen + three ops (str plain, glob parsed, re parsed) + sprefa_parse learns to reparse paren bodies + proc-macro boilerplate eliminator + build.rs compiles committed parser.c via cc**. Framework zero-per-op LSP code intact; carveout recursion deferred to Phase 2.

Two non-obvious bits:

- `extern crate self as pipeline;` at top of pipeline/src/lib.rs — required so `#[sprf_pattern_op]`-expanded `::pipeline::Op` paths resolve when the macro is used inside the crate that declares the trait. Without it: E0433 on every pattern op's generated impl.
- `PatternOp::binds_captures` trait signature grew a `bytes: &[u8]` param late — originally tree-only, but extracting term_ref names from node byte-ranges requires source bytes. Caller (resolver at lower time) has the slot-body slice; wire it through.

## Key Insights

1. **str cannot be a pattern op even though it lives in the injection registry conceptually.** The moment the body is unparsed bytes, there is no injected tree, no binds_captures, no compile. Plain Op is the right shape. Spec §14.5 now explicitly calls this out.

2. **`extern crate self as pipeline;` is the price of proc-macro self-use.** Without it, a macro that emits `::pipeline::Op` paths fails inside the pipeline crate. With it, the rest of the pattern is invisible.

3. **`PatternOp::binds_captures` needs bytes.** The injected tree alone does not let you extract node text; node byte-ranges are substring-relative, and tree-sitter does not hold the source. Caller owns the slot-body slice; pass it through. Trait was revised mid-session; all existing impls updated.

4. **Substring reparse beats set_included_ranges for Phase 1.** `Parser::parse(&src[body_range], None)` is simpler than `set_included_ranges` and produces the same tree shape for contiguous slot bodies. Byte offsets become substring-relative, which is a feature not a bug — callers that want absolute offsets add `host_node.byte_range.start`.

5. **Manual regen via justfile is genuinely fine at N≈3 pattern ops.** parser.c files are ~1200 LoC each; committed, they add ~3600 LoC to the repo that never gets reviewed. Once the count exceeds ~10 pattern ops the cost-benefit flips and the Phase 2 dogfood rule earns its keep. Not yet.

6. **Integration tests at the boundary catch what unit tests miss.** Each op's unit tests pass by hand-feeding parser; the integration test wires host_parse_with_injections → op_languages::language_of → injected tree → op.compile. That chain caught the glob `.` regression unit tests would never have surfaced.

7. **Parse-phase diagnostics flow automatically through the shifted-offset helper.** Any pattern op that gets a grammar also gets ERROR/MISSING diags for free via `collect_errors_shifted`. No per-op diag code needed for syntactic badness; PatternDiagnostic covers only structural / lowering-phase issues.

## Open Questions

1. glob `.`-in-literal regression: diagnosis not done. See "Next session — triage" task 1.

2. Should shared/tokens.js export carveout_expr? Currently it exports only term_ref; each grammar writes its own carveout. Phase 2 could factor it out with a body-rule parameter (shared module becomes a function taking the body-parser). Defer until the second pattern op needs carveout.

3. Is `CompiledPattern { op_name: &'static str, inner: Arc<dyn Any + Send + Sync> }` the right shape long-term? Works for dispatch by op_name + downcast. Alternative: associated type `type Compiled` on PatternOp (breaks object safety). Hybrid: keep CompiledPattern as a runtime wrapper but add a generic helper `op.compile_typed::<T>()` for callers with a static op. Not urgent.

4. Injected-tree byte offsets are substring-relative. That means any consumer wanting absolute offsets (LSP hover, diagnostic rendering) must add `host_node.byte_range.start`. Is it worth storing the offset on InjectedTree directly? One field; trivially added. Defer until a consumer actually trips on it.

5. Proc-macro emits `expect(...)` for language_of returning None. That is a runtime panic on a codegen mismatch. Better: compile-time check that the named op has a registered grammar. Hard to do from the macro without reading OUT_DIR at proc-macro time. Phase 2 dogfood problem.
