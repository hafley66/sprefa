## Problem/Context

### Parse pool split
Rayon was already wired for ast-op PATH B (local slice parse) and fs-op fan-out via `_17_parallel::rayon_map`. But PATH C (whole-file parsed() through the cache) was still using `tokio::task::spawn_blocking`. Two pools fighting for CPU, tokio blocking pool was doing parse work instead of being reserved for real blocking IO.

### Persistent cache decision
Disk cache keyed by `(oid, kind)` is architecturally correct for restart survival and multi-process sharing. Net-slower on g4 (tokio::fs::read > git2 packfile mmap). Landed env-var-gated (off by default) with in-code explanation of where it inverts (mutex-saturated blob reads, LSP reparses across restarts, multi-process). User said keep it rather than revert — "work that is done and minimal."

### Interning
~361 `Arc::from(&str)` sites across the crate. Hot path (ParseCacheReader::parsed key construction + BufferOverlay BufferKey construction) allocates 3-4 fresh Arcs per bytes() / parsed() call. 5476 of those calls per g4 run means thousands of redundant allocations. `WorkspaceCtx` now owns a `StrInterner` (dashmap-backed Arc<str> dedup); reader stack looks up there.

## Key Insights

### N+1 trap avoided on blob_oid short-circuit
Critical design: the oid fast path is a single short-circuit inside ParseCacheReader::parsed, not a wrapper layer. Readers that can't answer (MemReader, dirty BufferOverlay) inherit the Reader::blob_oid default (None) and the caller falls through to bytes+hash in the same async block. No extra stream op per read for non-git readers. One virtual call returning None is the whole cost.

### spawn_blocking vs rayon::spawn distinction
`spawn_blocking` is the tokio blocking pool — reserved for long sync IO (file read, subprocess, blocking drivers). Parse is pure CPU; belongs on rayon. Work-stealing balances N parses across M cores better than spawn_blocking's naive pool — per-parse avg wall went 2000 us → 1000 us after the switch with no change in total wall (critical path is elsewhere, but CPU efficiency halved).

### Disk cache threshold
Architecturally correct, currently net-slower. Writing this down matters more than the code: 400 us tokio::fs::read > 300 us git2 packfile mmap (warm). Where it wins: (1) blob reads mutex-saturate (handle pool pending), (2) LSP reparse across process restart, (3) multi-process CLI + LSP sharing. None of those hold on g4. Kept gated off so baseline is preserved; opt-in for the workloads that invert.

### DashMap is read-optimized, not a Mutex
64 independent shards by key hash; per-operation lock is per-shard not global. Read path on a hit is lock-free-ish (shard RwLock read guard). The interner's 96% hit rate means most operations touch only a single shard's read guard, fast and concurrent.

### Intern efficacy is an observability-first claim
Unit tests prove the API contract (ptr_eq, len, hit/miss counters). The actual efficacy claim (5476 calls, 96% hits, 199 unique) has to come from a real run. [timing] intern line surfaces this on every release run, so any regression (a new call site that bypasses the interner and adds fresh Arc::from's) will change the hit ratio visibly.

### BufferOverlay signature split is a compat pattern worth remembering
Adding a required dependency to a constructor that has many callers breaks every caller including tests. Solution: keep `new(inner)` as a backward-compat wrapper that self-owns a fresh dep; add `with_intern(inner, intern)` as the path for code that wants to share. Workspace builds use the shared ctor, tests and LSP bin callers stay on new(). Clean migration without test fan-out.

### Near-miss: sed corrupted _1_workspace.rs
`sed -i '' 's/A/B/g'` on a file where pattern A was not found left the file empty. Recovered via `git checkout HEAD -- <file>` and re-applied changes with Edit. Lesson: prefer Edit tool for structured replacements; only reach for sed when the scope justifies the blast radius. Never ran a destructive sed without a commit point right before.

## Open Questions

### Disk cache eviction
by_oid and on-disk cache both unbounded today. g4 = 200 entries, 2.3 MB. 500-repo worst case = hundreds of MB in RAM, possibly gigabytes on disk. Want LRU bound or size cap. Probably: RAM by_oid bounded to ~1 GB total bytes; disk unbounded (users can nuke the dir). Defer until RAM analysis shows the cost.

### Wider interning rollout
361 Arc::from sites. Reader stack done (5 sites, 5476 calls). 300+ in ops. Migrate lazily when an op profiles hot. Or bulk migrate? If ops share workspace.intern through OpCtx, that's a cleaner threading than one-op-at-a-time. Worth a bulk pass before the medium-repo fixture so the measurement is clean.

### RAM/lifetime analysis shape
User asked for this next: "analyze lifetimes of things across space and time for ram characteristics." What they mean: produce a map of what allocates, what pins it, how long it lives, how many copies exist concurrently. Targets:
- Cursor captures — now refcount clones after intern
- ParsedTree.bytes — held for life of by_oid slot (entire run, or longer if workspace long-lived)
- Result rows in ResultStore — ephemeral per run or persistent across runs?
- Per-repo git2 Repository handles — one-per-repo in GitBlobReader.repos HashMap
- mpsc channels — bounded by runtime.buffer_size
Format probably: diagram-ish map across (alloc site, holder, drop trigger, refcount fanout).

### medium-repo fixture still owed
Every perf claim since session 3 has been on g4/sprefa-self (442 files × 4 revs, mostly near-identical). Disk cache win, handle pool K-sizing, cross-rev dedup scaling — all need a workload where blob reads are expensive and unique-blob fraction varies. Pick a real crate (tokio? ast-grep? syn? servo?) and scan across 5-10 tags. Without this, every future perf change will have the same "is this real" feeling.
