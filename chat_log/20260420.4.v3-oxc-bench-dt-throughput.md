# Session: v3-oxc-bench-dt-throughput

## Goal
Validate that in-process oxc parsing via the v3 effect_runtime matches shell-out oxc CLI throughput on a large TS corpus. Land the bench as a committed artifact.

## Current State
Committed at e9d7885 on branch wip/kitchen-sink-react-hook-fix. 11 files, +1059 LoC. Covers both the rxRust adapter spike (from earlier in the session) and the full oxc bench. Build green, no regressions in existing tests.

## Problem/Context
Followup from 20260420.0 (perf+plugin synthesis) and 20260420.2 (cancel+ArcSwap+cache). User wanted to quantify whether ctx.put dispatch overhead is visible on heavy parse work at scale. Existing synthetic benches (ast-grep, sqlite, git2) showed ~8.4µs/item per-file tax and parity in batch mode, but none used a non-trivial parser at 30k+ file corpus scale.

## Solution/Approach
Added two oxc crates to effect_proof (oxc_allocator / oxc_ast / oxc_parser / oxc_span @ 0.127). Wrote OxcParse effect + OxcParseBatch + parse_one helper. Arena is allocated inside the batcher and dropped before returning an owned summary (bytes, errors, panicked) — keeps Program<'arena> off the Send boundary, avoiding ouroboros/self_cell for this first pass.

Two bins:
- oxc_parse_one: minimal shell-mode target, takes paths, prints "bytes=N errors=N"
- oxc_v3_bench: five modes (shell-serial, shell-batch, rayon, ctx-put, ctx-batch), RSS + MB/s + p50 reporting

Corpus: DefinitelyTyped/types, 33,543 .ts/.tsx files, 256 MB source. Cloned to /Users/chrishafley/projects/ext/DefinitelyTyped.

## Key Insights
- DT .d.ts files average ~8 KB; parse dominated by file read + setup, not AST walk
- ctx-put tax is a constant per-call value (~few hundred ns to low µs), shows as 15% at DT file size, shrinks to <5% on larger files where parse is 100s of µs
- Shell-batch at 64 files/fork is within 20% of rayon ceiling; shell-serial collapses to 9 MB/s (fork-per-file is fatal)
- jemalloc keeps RSS low (123-147 MB in-process, 31 MB shell — parent holds no parse arenas in shell mode)
- oxc's Allocator is !Send; returning an owned projected summary is the zero-ceremony path for the framework

## Open Questions
- Is the rayon first-trial 468ms real or an artifact? Later trials 678-713ms. Possibly jemalloc thread-cache priming; warrants dedicated warmup beyond page cache.
- For the full-AST case (ctx.put returning Arc<(Allocator, Program)>), does self_cell integrate cleanly with moka Cache, or does the inability to return a borrow through Arc force a different cache value type?
- Should OxcImports be a separate PureEffect or a compose-layer on OxcParse? (User said parse AND import graph wanted.)
