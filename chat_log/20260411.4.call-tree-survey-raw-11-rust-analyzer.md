## Analysis

### incoming_calls flow (call_hierarchy.rs:44-97)

Entry point: `incoming_calls(db: &RootDatabase, config, FilePosition)` resolves the function at the cursor position, then finds all files/ranges where that function is referenced.

**Semantic index seam (line 68):**
```rust
.flat_map(|func| func.usages(sema).all());
```
This is where incoming_calls touches the semantic index. `func` is a `hir::Definition` (specifically `Definition::Function`), and `.usages()` returns a `UsageSearchResult`, which `.all()` unpacks into an iterator of `(FileId, Vec<FileReference>)` pairs. This delegates to ide_db's search module (imported line 11: `search::FileReference`), which likely uses the Salsa database to find all references to the definition across the workspace. The search is file-scoped: results group by FileId, and for each file, a list of ranges + NameRef nodes.

**Ancestor walk (lines 75-76):**
After finding each usage (a NameRef in some file), the algorithm walks upward using `sema.ancestors_with_macros(name.syntax().clone())` to find the enclosing function definition (`ast::Fn::cast() + sema.to_def()`). This is a second semantic query: for each usage's containing scope, resolve the function definition. The `.try_to_nav()` call (line 79) converts the hir::Function to a NavigationTarget, which is language-server-ready (file + full range + focus range).

**Key observations:**
- No precomputed index: The search happens at query time via `.usages()`, which likely walks the Salsa database's symbol table or reference chain
- Order preservation: FxIndexMap maintains insertion order (line 162); references are processed in the order returned by `.all()`, which is file-scoped (file traversal order)
- Cross-file resolution is complete: `.usages()` returns all references in all files, grouped by FileId

### outgoing_calls flow (call_hierarchy.rs:99-158)

Entry point: `outgoing_calls(db, config, FilePosition)` finds the function containing the cursor, walks its body for call expressions, and resolves each callee.

**Function locating (lines 113-115):**
```rust
sema.descend_into_macros_exact(token)
    .into_iter()
    .filter_map(|it| it.parent_ancestors().nth(1).and_then(ast::Item::cast))
```
Starting from the token at the cursor, this descends into any macros covering that token (for macro-generated functions), then walks ancestors to find the enclosing Item (Fn, Const, or Static). The result is a stream of possible containing items (usually one, unless the cursor is in a nested scope).

**Call discovery (lines 116-123):**
```rust
.filter_map(|item| match item {
    ast::Item::Fn(f) => f.body().map(|it| it.syntax().descendants()),
    ...
})
.flatten()
.filter_map(ast::CallableExpr::cast)
```
For each containing function, walk all descendants of its body and filter for CallableExpr (call expressions or method calls).

**Callee resolution (lines 124-151):**
```rust
match call_node {
    ast::CallableExpr::Call(call) => {
        let expr = call.expr()?;
        let callable = sema.type_of_expr(&expr)?.original.as_callable(db)?;
        match callable.kind() {
            hir::CallableKind::Function(it) => it.try_to_nav(&sema),
            ...
        }
    }
    ast::CallableExpr::MethodCall(expr) => {
        let function = sema.resolve_method_call(&expr)?;
        function.try_to_nav(&sema)
    }
}
```

For direct calls: `sema.type_of_expr()` infers the type of the called expression, then `.as_callable()` extracts the callable if the type is a function, enum variant, or struct constructor. For method calls: `sema.resolve_method_call()` resolves the method directly from the method name and receiver type.

**Semantic index seam (lines 128, 143):**
- Line 128: `sema.type_of_expr(&expr)?.original.as_callable(db)?` — type inference touches the HIR database to resolve types and callable kinds
- Line 143: `sema.resolve_method_call(&expr)?` — method resolution uses the Salsa database to find matching trait impls and method definitions

**Key observations:**
- One-step outgoing: Only direct calls in the function body are extracted; no recursive call graph walk
- Macro support: `descend_into_macros_exact()` handles macro-generated call sites, but the algorithm can miss calls inside macro invocations (test line 518-520 FIXME)
- Order preservation: Results are collected in order of body traversal (descendants iterator), aggregated into FxIndexMap (insertion order)
- Type-driven resolution: Unlike incoming_calls which searches symbolically, outgoing_calls uses type inference to resolve callees

### Ordering analysis

Both algorithms preserve source position order:
- **incoming_calls:** `.usages().all()` returns files in some order (likely module traversal order or cached symbol table order), and ranges within each file are processed in iteration order
- **outgoing_calls:** `.syntax().descendants()` walks the syntax tree in pre-order depth-first, preserving source order

No explicit sorting by FileId or TextRange is visible in either function. FxIndexMap (a hash map with stable iteration order) deduplicates targets but preserves the order of first insertion.

### No global index

Unlike tools that maintain a persistent call graph file (e.g., ctags, SCIP), rust-analyzer's call hierarchy is **entirely computed on demand** via semantic queries. There is no `.callgraph` or similar artifact. The Salsa database caches individual HIR queries (type inference, name resolution, macro expansion), but call hierarchies are not cached as a first-class object.

Implications:
- High latency on large projects (semantic queries are expensive)
- No offline query capability
- Correctness follows semantic analysis, not a static approximation
