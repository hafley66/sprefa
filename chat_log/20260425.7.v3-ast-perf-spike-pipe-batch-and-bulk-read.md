# Session: v3-ast-perf-spike-pipe-batch-and-bulk-read

## Goal
Land the sprefa-4m7.2.22 perf spike: get the v3 ast op through Op::pipe to
match the FINDINGS bench (W=8 = 3.64s on linux kernel printk scan).
Diagnose the residual gap between sprefa-run and the bench's tight
ScanBatch loop, fix in successive rounds without changing the smoke
surface, and bound peak RSS.

## Current State
Branch wip/kitchen-sink-react-hook-fix, sprefa-4m7.2.22 closed. Five
rounds of optimization landed; final number on .c+.h kernel corpus
(63374 files): **4.16s wall p50, 700 MB peak RSS** at CHUNK=2048.
vs FINDINGS bench W=8 3.64s (parity workload) we're +14% — exactly
the per-cursor dispatch tax that doc called out for the pure-Op-trait
shape. vs ast-grep CLI 0.42 (15.7s) we're 3.8x faster. Match count
parity confirmed (47, identical to ast-grep CLI on this corpus).

## Problem/Context
Card sprefa-4m7.2.22 was the labeled-spike followup to the
chat_log/20260420 perf probe work that proved the v3 effect_runtime
was bench-fast IN ISOLATION. Production sprefa never wired the levers:
ast op was inline lang.ast_grep, no prefilter, no jemalloc, single-
thread tokio current_thread, sequential Pipeline::Op runner. The
bench bin lives at v3/experiments/effect_proof/src/bin/ast_grep_v3_bench.rs;
it shows the recipe (BoundedWorkSteal + prefilter + jemalloc + W=8)
but never went through the Op trait. This session closed that loop.

## Solution/Approach

Five rounds, each isolated to confirm the lever before stacking.

### Round 1 — prefilter + jemalloc (the no-design-risk win)
Added `Pattern::fixed_string()` SIMD prefilter inside ast::pipe before
`lang.ast_grep` (FINDINGS §2.3). Pinned tikv-jemallocator as
#[global_allocator] in sprefa-run binary. Match count parity with
ast-grep CLI 0.42 confirmed. Wall: baseline 68.0s (no prefilter) →
13.16s (5.2× lever, FINDINGS reported 6.3× on slightly different
corpus). Single-thread tokio current_thread retained.

### Round 2 — multi-thread tokio + buffered cursor dispatch + ctx.put parse
- new_multi_thread tokio runtime in sprefa-run (1 line)
- AstParseEffect added to pipeline/src/effects.rs with `ast_parse` sync
  fn, registered with BoundedWorkSteal::<8 workers, cap=256> in
  sprefa-run; ast::pipe routes parse via ctx.put
- Pipeline::Op runner switched from serial for-loop to
  futures::stream::iter().buffered(1024)
- env knobs SPREFA_AST_WORKERS, SPREFA_AST_CAP

Wall 6.16s p50 — 2.07× from concurrency. CPU 11.1s user / 6.16s wall
= 1.8 cores effective; clearly not CPU-bound.

### Round 3 — Shape B (Op::pipe_batch override + rayon par_iter)
User ask: do we need to flip the trait to Vec<Cursor> -> Vec<Cursor>?
Yes for parity, but not all-at-once. Added optional `pipe_batch(
&self, ctx, cs: Arc<[Cursor]>) -> Vec<Vec<Cursor>>` to Op trait with
default impl using buffered(1024) over per-cursor `pipe`. Pipeline::Op
runner now calls pipe_batch unconditionally and appends PathSeg::Op
to outputs (ops never touch path tagging). AstGrepOp overrides
pipe_batch with rayon par_iter inside tokio::task::spawn_blocking,
bypasses ctx.put(AstParseEffect) entirely on the bulk path.
Refactored: scan_with_grep (used by single-cursor pipe) and
scan_one_inline + AstGrepOpRef (used by rayon path) share match logic.

Wall flat at 6.15s. CPU went up 11.1 → 13.3 (more parallel work) but
wall didn't move. Bottleneck wasn't compute parallelism.

### Round 4 — ReadBytesBatchEffect (D, the real win)
Diagnostic: fs+comment(:any) takes 5.10s on warm cache for 36k cursors,
0.79s user. fs+void takes 0.13s. Delta 4.97s = 135 µs/cursor of
ctx.put(ReadBytesEffect) tax. Cache hit ratio is 0% across runs
because the binary relaunches each trial — RtCtx is fresh, CacheLayer
empty. The CacheLayer adds zero benefit on single-process invocations.

Added ReadBytesBatchEffect { reads: Arc<[(repo, rev, path)]> } returning
Vec<Option<Arc<[u8]>>>. Handler par_iters reads on rayon's global pool
inside tokio::task::spawn_blocking. New `ensure_content_loaded_batch`
helper. ast::pipe_batch swapped futures::future::join_all of N
ensure_content_loaded for one ctx.put(ReadBytesBatchEffect).

Wall 6.15s → **2.62s p50** on .c only (36k files). 2.35× from D alone,
5× total from baseline. CPU 13.1s, RSS uncapped at 1.4 GB peak.

### Round 5 — Switch to .c+.h corpus + chunking for bounded RSS
fs glob doesn't support alternation (`|`, `{c,h}`, `[ch]`) at the
tree-sitter glob sub-grammar level. Worked around with two pipes in
the fixture; FsListFilesEffect's per-(repo,rev) cache makes the
second walk free, walls sum across pipes.

Added chunked processing inside pipe_batch via SPREFA_AST_CHUNK env
knob (default 2048). Each chunk: bulk-read → spawn_blocking → rayon
par_iter → drop chunk_groups (Arc<[u8]>s die at chunk boundary).

CHUNK sweep:
  256:  5.06s wall, 575 MB peak RSS
  512:  4.77s, 672 MB
  1024: 4.45s, 686 MB
  2048: 4.15s, 708 MB (sweet spot)
  8192: 4.12s, 878 MB
  unchunked: 4.13s, 1.4 GB

### Memory model confirmation
User asked about mmap / leaks / strings in mem. Answer:
- No mmap. std::fs::read returns Vec<u8> → Arc<[u8]>. Pure heap.
- Same as ast-grep CLI / biome / oxc — tree-sitter requires contiguous
  &[u8], no streaming-parse used.
- mmap doesn't save peak RSS (bytes still in physical RAM via page
  cache); only saves the kernel→userspace copy. ripgrep uses mmap for
  >16KB files with random access; for small kernel files (~30KB avg),
  read() is competitive. Andrew Gallant's blog post argues this.
- No leaks. Arc<[u8]> ref-counted; chunk drops at boundary; jemalloc
  arena retention is reuse, not leak.
- 700 MB peak at CHUNK=2048 = ~60 MB live data + parsed AstGrep trees
  in flight + jemalloc arena retention.

### N+1 audit
Walked the code paths once more. Only candidate worth touching:
Pattern::fixed_string() inside scan_one_inline — 63k calls, recomputes
from pattern tree per call. Hoisted out: `let fixed: Arc<str> =
Arc::from(pattern.fixed_string().as_ref());` once per chunk, capture
into closure. Wall didn't move (4.16s) — fixed_string is apparently
already O(1) or memoized internally. Kept the change anyway since it
costs nothing.

Other N+1 sites are either tiny (47 matches × HashMap alloc, ~bytes)
or intrinsic to ast-grep/tree-sitter (Parser::new per file, UTF-8
validation per file). The remaining 14% gap to bench is the per-cursor
dispatch tax FINDINGS §5.1 documented; closing it would require
abandoning the Op trait surface entirely.

### Telemetry
sprefa-run now prints `# cache: read[hits=H misses=M entries=N
hit%=P] listing[...]` to stderr after each seed run. Built CacheLayer
manually (not via register_pure sugar) so the run loop can clone the
handle and call .stats(). SPREFA_TELEMETRY=quiet suppresses.

## Key Insights
- Production sprefa was missing every lever the bench had wired. The
  bench validated effect_runtime in isolation; production code never
  routed through it for parse/read work. Closing this gap was the
  whole spike.
- Pipeline::Op::run was strictly sequential (`for c in inputs { pipe.await }`).
  Even with multi-thread tokio + ctx.put dispatch, only one pipe is
  in flight at a time. The runner was the actual concurrency bottleneck,
  not the effect runtime.
- ctx.put per cursor is ~140µs of pure dispatch overhead under tokio's
  buffered-future scheduling. For a 36k corpus that's 5s. The per-file
  ScanBatch shape (one ctx.put for the whole batch, handler par_iters
  internally) is what FINDINGS §5.2 measured at parity; D ports it.
- CacheLayer adds zero benefit across single-process sprefa-run
  invocations — every trial relaunches with empty cache. For LSP /
  daemon (long-running RtCtx) the cache will fire. Cache hit ratio
  telemetry is now visible to know which mode you're in.
- Op::pipe_batch override with rayon par_iter inside spawn_blocking is
  the v3 ScanBatch shape. Default impl preserves existing pipe(c)
  semantics — incremental adoption is fine, only ops with
  parallelizable inner work need to override.
- mmap is not the answer. ast-grep / biome / oxc all use std::fs::read.
  Tree-sitter needs contiguous bytes; copying into Arc<[u8]> is
  intrinsic. mmap saves only the kernel-userspace copy, not peak RSS.
- 700 MB peak at CHUNK=2048 is ~60 MB live + parsed trees + jemalloc
  arena retention. Bench's 161 MB peak came from W=8 BoundedWorkSteal
  cap=256 sliding window. CHUNK=256 in our shape gets close (575 MB).
  Wall/RSS curve is well-mapped and tunable.
- fs glob sub-grammar lacks alternation. Fixture works around with two
  pipes; FsListFilesEffect cache makes the second walk free.
- ScheduleWakeup-class N+1 audits are mostly red herrings at this
  point. Pattern::fixed_string is already memoized; per-match HashMap
  is 47 allocs; intrinsic costs are intrinsic.

## Open Questions
- The 14% gap to bench is the per-cursor dispatch tax for going through
  Op::pipe at all. Closing it means abandoning per-cursor pipe in favor
  of pipe_batch as the sole entrypoint, OR accepting Op::pipe is for
  semantics and pipe_batch is for perf. Neither is urgent; FINDINGS
  already documented this rationally.
- Should json op get the same pipe_batch treatment? Brace walker is
  fast, parse is tree-sitter — same shape applies. Likely worth a
  small follow-up spike.
- fs glob alternation feels like it should land soon; the two-pipe
  workaround is awkward in user-facing fixtures.
- LSP / daemon mode: CacheLayer SHOULD start hitting once RtCtx lives
  across requests. Worth measuring once the LSP wires sprefa-run-
  equivalent setup.
