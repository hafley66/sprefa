## Problem/Context

User pushed back on the v0 erasure shape recorded in the prior session
(`pub type NextValue = Arc<dyn Any + Send + Sync>`). The original
justification — "three runtime constructs collapse to this primitive
(parked writes, tag-subscribe, Pending captures)" — was a pattern-level
collapse, not a structural requirement. The shared mechanic is just
`oneshot::channel + HashMap<Key, Sender> + Drop guard`, which is
generic in T. Each consumer can have its own `EffectKind` instantiation
under the existing TypeMap.

User's proposed shape: separate trait with two associated-type slots, or
just `Yield<T>`. Chose the trait spelling because it documents the
marker and leaves room for future per-kind associated items.

## Solution/Approach

### effect_runtime/src/subjects.rs (full rewrite)

```rust
pub trait SubjectKind: Send + Sync + 'static {
    type Payload: Send + Sync + 'static;
}

pub struct SubjectKey<S: SubjectKind> { id: u64, _s: PhantomData<fn() -> S> }
// manual Clone/Copy/Eq/Hash/Debug because S doesn't impl them

pub struct Yield<S: SubjectKind> {
    pub key: SubjectKey<S>,
    pub lineage: Option<Lineage>,
}
impl<S: SubjectKind> EffectKind for Yield<S> {
    type Response = Result<Arc<S::Payload>, Unsubscribed>;
}

pub struct SubjectRegistry<S: SubjectKind> {
    next_id: AtomicU64,
    pending: Mutex<HashMap<SubjectKey<S>, Entry<S>>>,
}
impl<S: SubjectKind> Store for SubjectRegistry<S> {}

pub struct YieldBatcher<S: SubjectKind> { registry: Arc<SubjectRegistry<S>> }
impl<S: SubjectKind> Batcher<Yield<S>> for YieldBatcher<S> { ... }
```

`NextValue` alias deleted. `next(key, value)` is typed
`Arc<S::Payload>`. `Lineage = Arc<dyn Any>` kept (lineage erasure is
orthogonal — different consumers attach their own struct for
unsubscribe_where; the registry never inspects it). `subscribe()`
contract unchanged: synchronously inserts pending entry before
returning, future has Drop-guard that unsubscribes on drop.

Tests rewritten against a local `struct TestSubject; type Payload =
String;` so wake values are typed strings (`Arc<String>`). All 11 race
+ lifecycle tests preserved.

### pipeline/src/effects.rs

```rust
pub type TagRow = Vec<Arc<str>>;
pub struct TagWake;
impl SubjectKind for TagWake { type Payload = TagRow; }
```

`Bag.waiters` now `Vec<SubjectKey<TagWake>>`. `SnapshotOrSubscribed::
Subscribed(BoxFuture<Result<Arc<TagRow>, Unsubscribed>>)`.
`TagWriteBatcher::run` wraps `req.row` in `Arc<TagRow>` and broadcasts
to each waiter via `registry.next(k, wake.clone())` — Arc clone is
cheap; the row is shipped through the wake.

### pipeline/src/ops/tag.rs

`subscribe_stream` typed throughout (`SubjectRegistry<TagWake>`). Wake
arm of the unfold loop changed:

```rust
Ok(row_arc) => {
    let row: TagRow = (*row_arc).clone();
    let batch = rows_to_batch(&s.cursor, &s.holes, vec![row]);
    s.last_idx += 1;
    return Some((batch, s));
}
```

The "wake → continue → snapshot under store mutex → emit" loop
collapses to "wake → emit". Saves one store-mutex acquisition per
single-row wake (the canonical fast path). Multi-row catch-up still
works on the next iteration via snapshot_or_subscribe with the
advanced last_idx.

### server/backend.rs + bin/sprefa-run.rs

Three lines per registration site:
- `Arc::new(SubjectRegistry::<TagWake>::new())`
- `register::<Yield<TagWake>, _>(YieldBatcher::new(registry.clone()))`
- `use pipeline::effects::TagWake`

## Key Insights

1. **EffectKind already gave typed responses; the erasure was
   consumer-side.** `EffectKind::Response` is a typed assoc on the
   framework trait. The Box<dyn Any> erasure inside RtCtx is invisible
   (a HashMap<TypeId, dyn BatcherEntry> implementation detail). The
   `NextValue = Arc<dyn Any>` alias was a layer the Yield author added,
   not something the framework imposed.

2. **TypeMap dispatch on monomorphized types just works.** `TypeId::of::
   <Yield<TagWake>>() != TypeId::of::<Yield<OtherKind>>()`. Each
   instantiation gets its own registry slot, its own batcher. No
   framework changes needed; only consumer-side parameterization.

3. **`Arc<S::Payload>` is the right return shape.** Each waiter gets a
   cheap clone. For tag this means `Arc<Vec<Arc<str>>>` — Arc on the
   outer Vec, Arc on each inner str. Two refcount bumps per wake,
   shared by all waiters in the broadcast.

4. **Lineage stays Any-erased and that's fine.** Lineage is metadata
   for `unsubscribe_where` to filter on; consumers downcast inside the
   predicate. Different from payload — payload is the load-bearing
   shape, lineage is opt-in tagging.

5. **Question #1 closes by construction.** The original framing was
   "ship the row vs sentinel + re-snapshot." Once the payload is
   typed, sentinel is gone — there's no longer a meaningful unit
   payload. The fast-path lock-saving fell out for free.

6. **Manual trait impls for PhantomData<fn() -> S>.** Standard derive
   would require S: Clone/Copy/etc. The phantom is `fn() -> S` (not
   `S` directly) so SubjectKey<S> is Send+Sync regardless of S; manual
   impls satisfy bounds without leaking S requirements.

7. **`use effect_runtime::Unsubscribed` still needed.** Removed
   NextValue from re-exports but Unsubscribed stays — it's a unit
   error that's the same shape across all S, no need to parameterize.

## Open Questions

- Should there be a sugar register helper on RtCtxBuilder for "register
  store + Yield<S> batcher together"? Three-line ceremony at every
  runtime construction site (server + tests). Defer until a second
  SubjectKind lands so we know the right shape.

- Should TagStore parameterize on a SubjectKind too, so the tag layer
  is reusable for non-string payloads? Probably overkill; tag is
  string-relational by design. Defer.

- Multi-writer wake ordering: if writer A and writer B both fire while
  reader is suspended, the waiter list is drained on writer A and B
  finds no waiters. Reader resolves on A's wake with row_a, emits, then
  loops, snapshots, finds row_b, emits. Correct but wakes-vs-snapshots
  is now mixed depending on race timing. Acceptable; the loop's snapshot
  branch handles the catch-up regardless.
