## Solution/Approach
Three-layer artifact set, each layer cross-linking to the next:

1. **Design doc** (plugin-author-surface) — the full A-D op-author touchpoint table. Rows ordered by lifecycle: parse → lower → LSP (completion/hover/signature/code-actions) → runtime (pipe/content-contract/cancel/captures/slots/evidence) → side-effects (queue/approve/apply/cache/persist). Each row has op provides / framework consumes / v2 today / v3.
2. **Metric doc** (min-author-ops) — names the rule that justifies every v3 design decision. Measurable: files-created, files-modified, central enums touched. Ideal (1,0,0). Includes anti-goals so future readers do not misapply (do not collapse trait slots to reduce files; do not downcast at call site to "simplify"; do not add RuntimeConfig knob when op-local field suffices).
3. **Executable proof** (v3_effect_proof) — 4 tests + bash drill. Validates: typed E::Response, no Any at call site, two kinds coexist, unregistered panics clearly, adding a third effect is `.add` + edit + test + audit-green.

Three dyn boundaries confirmed Tier-1 (unavoidable, acceptable): BatcherRegistry, Captures vec, Slots typemap. Everything else is Tier-2 collapsible via associated types, Tier-3 structural (grammar/contract), or Tier-4 policy-deferred (cursor field ≥3-uses rule, RuntimeConfig scope).

## Key Insights
- Min-author-ops is a measurable goal (files-created / modified / central-enums-touched), not a taste judgement. The drill-audit produces a verdict per capability added.
- The three dyn boundaries (Captures, Slots, BatcherRegistry) are the entire type-erasure budget. Every associated-type move pulls capability out of central enums into that budget without growing it.
- "mod.rs one-line" is a rustc requirement; it does not count against min-author-ops. The meaningful metric is `lib.rs` staying untouched when new ops land.
- Empty `[workspace]` in a sub-crate's Cargo.toml is the escape hatch when the parent crate is treated as a workspace root even without a [workspace] section (cargo auto-discovered v2/ as workspace because we put the experiment inside it).
- The prototype's audit script catches its own doc-comments unless the test file avoids the words "Any", "downcast", "TypeId" as prose. Fixed by rephrasing test comments; a stricter audit could filter comment lines but prose-discipline is simpler.
- User reacted badly to fabricated v2 APIs (c.at(), c.narrow_to()). Grounding via v2/docs/README.md + v2/CLAUDE.md + the two v3 chat_logs before writing anything further is the posture, not the exception.
- User's framing "min the inputs" maps to min-author-ops (inputs = files an author must open). Named the principle in an appendix so future assistants can check their work against it.
- "Officially v3 plugin design" is the user's canonization move — they name things when they are ready to commit to them. Respect that and treat the named docs as locked, not exploratory.
- The prototype's framework:ops LoC ratio (126:68) is the inverse of the thesis — more framework than ops per line is *good* if framework is amortized across N ops. Target for v3 proper is framework LoC ~constant while ops LoC grows linearly with capability count.

## Open Questions
- Prototype extension vs v2 integration: do we stay in experiments/ and extend (add Op trait, CaptureKind trait, Diagnostic trait stubs) before touching v2/src/, or jump directly to integrating core/effect/ into v2?
- Does the Op trait want `type Effect` associated type (self-documenting single-effect ops) or stay unbounded with ops using ctx.put<E> ad hoc across multiple kinds? Earlier draft inconsistent on this.
- Opportunistic batching inside Batcher::run (recv + try_recv drain pattern from batching-jutsu) — prototype skipped this; when to add and as what knob (MAX_BATCH as the single knob per batching-jutsu Tier-2 shape)?
- Sub-lang trait: ast_grep/regex/sql/sem as registered SubLang impls — does this land in v3 core/effect/ or later as its own phase?
- Cursor-as-input to Op::pipe vs Vec<Capture>: the prototype skipped Op trait entirely. When added, does it take Stream<Cursor> (v2-shape) or something more abstract?
- For the sem integration worked example: does sem read via path (needs tmpfile for buffer-side edits) or via bytes + language hint? Content contract says PATH A→B→C; sem is external so PATH B (bytes) → tmpfile → sem is the likely wiring.
