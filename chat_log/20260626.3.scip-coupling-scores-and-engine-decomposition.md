## Problem/Context

or are those optimal couplings; if not why not, and can we measure it with

coupling scores + cohesion decomposition. Engine = the god-object in question

## Solution/Approach
Named the literature techniques and mapped each onto dl. Six analyses run in
sequence, each filtering the previous:

1. **Feature envy** (Marinescu): `scip_callee_type` extracted from `impl#[Type]`
   moniker segment (~20 lines Rust, doubles as caller own-type). Noisy alone.
2. **Ca/Ce/Instability** (Chidamber-Kemerer / Martin): type scorecard via
   `tc_edge` self-join. Engine = Ca13/Ce13/I=0.50 = sole god-object.
3. **Type reciprocity**: `tc_cycle(a,b) <- tc_edge(a,b), tc_edge(b,a)`. **0
   reciprocal pairs** — method-level type graph is a DAG; all envy is one-way
   severable, none is a true cycle.
4. **Collaborator LCOM4 threshold sweep**: blob at k=1 (75 methods), **shatters
   to 79 singletons at k>=2**. No sub-communities.
5. **Field LCOM4**: field monikers are `Engine#<name>` (`#` separator, isolable
   by regex in pure dl). Also blob — `Engine#db` touched by 71/75 methods.
6. **Field-coverage partitioning** (peel db): THE WINNER. 44 methods touch ONLY
   db = clean extractable data-access layer. 48 touch richer state (genuine
   mesh). 18 touch nothing (pure fns).

**Key methodological finding:** LCOM-clustering is the wrong frame for a session
object (hub fields transitively connect everything). Field-coverage PARTITIONING
(sort methods by self-state width; the floor falls out) found the seam that
clustering couldn't. This generalizes: any god-object with a universal
dependency field shows the same pattern.

## Key Insights
- **Engine is a god-SESSION, not a bag of concerns.** 44 of 110 methods touch
  only `self.db`; they're a clean extractable data-access layer. The other 48
  share `rels`/`root`/`repos` and form a real mesh. Split = extract the 44 db-
  only behind a Db collaborator; Engine -> 66 methods.
- **The seam came from field-COVERAGE partitioning, not clustering.** LCOM4
  blobbed at every threshold (collaborator AND field) because hub fields (db:
  71 methods, rels: 20, root: 18) transitively connect everything. The win was
  asking "how much state does each method touch" (coverage) not "do methods
  form groups" (clustering).
- **Engine = sole god-object by the metric.** Ca13/Ce13/I=0.50; everything else
  is a leaf (I~0). Type graph is a DAG (0 reciprocal pairs) — all coupling is
  one-way, severable; no type-level mutual cycles.
- **Field monikers use `#`, not `.`**: `Engine#db`, `ClosureCache#cond`.
  Isolable in pure dl via `field =~ /Engine#/` (methods are `impl#[Engine]x().`
  and never contain `Engine#`). No Rust field-extraction needed.
- **`scip_fn_edge` is a superset** — it emits every referenced symbol (fields,
  types, fns), not just fn calls. Enabled field-LCOM without new extraction.
- **dl limitation confirmed**: `!sym =~ /regex/` is invalid (`!` negates atoms,
  not constraints). Workaround: define a positive relation then `!rel(x)`.
- **Build loop**: `nohup cargo build > /tmp/log 2>&1 &` + poll. ~50-90s
  incremental. dl-language errors are <1s; only Rust changes pay the loop.
