## Problem/Context

**Rule semantics landed:**
- Top-level `rule(:foo, ${A?}, ${B?}) { body }` defs lower in pass-1, bind body+params on RelationStore, auto-fire once at top-level.
- `foo(args)` in pipes lowers to RuleCallOp via two-pass lower with rule-name awareness.
- Body terminal cursor's full capture set + synthetic cursor.repo/.rev/.fs becomes a RuleRow.
- RelationStore hoisted to run scope (above seed loop) so rule_rows accumulate across seeds for one drain.

**SQLite drain (v0/v1 parity for the flat-table layer):**
- One table per rule named `<sprf_stem>__<rule_name>`.
- Schema: `id INTEGER PRIMARY KEY AUTOINCREMENT` + paired (`<cap>`, `<cap>_norm`) TEXT per emitted column.
- Synthetic columns lead: repo, rev, fs (when present on cursor).
- `sprf_norm()` ported 1:1 from `crates/config/src/normalize.rs` — strip non-ASCII-alphanumeric + lowercase. Computed in Rust at INSERT.
- Per-`_norm`-column index.
- FTS5 trigram virtual table per rule with ai/ad/au sync triggers.
- PRAGMAs: WAL + synchronous=NORMAL + foreign_keys=ON.
- DROP+CREATE every run (incremental caching deferred).
- Default db path: `<sprf_stem>.db`; `--out` flag override.

**Design discussion (filed in cards, not yet implemented):**
- User clarification: shared strings/refs/files dedup tier IS desired (v0 optimization for cross-rev blob dedup); rule tables stay flat. Filed.
- User asks: ops able to determine cache key? Walked through 3 postures (framework-only / cacheability enum / cache_inputs). User counter-proposed: **output_fp model** — every op emits an output fingerprint after running; downstream cache keyed on upstream output_fp. This dominates posture 3 (correctness falls out of what was actually emitted, no manual ambient-input declarations). Two-layer composition: layer 1 = output_fp chain at stage boundary, layer 2 = v1's per-input content_hash + scanner_hash for expensive per-file ops.
- User extension: runtime should passively watch git checkouts (worktree changes, rev changes), selectively invalidate only rules whose dep chain saw input change. Composes naturally with output_fp: watcher emits Change events, dep-graph walk identifies invalidated rules, only those rerun.

## Solution/Approach

### What landed (architecturally)

```
ops/rule.rs (NEW)
  RuleCallOp { name, args }
    pipe: per cursor, materialize args → bind body params → run body sub-pipeline → drain terminal cursors → push_rule_row
    capture_row: repo + rev + fs (synthetic, lead) + every cursor.captures (in order)

relation_store.rs (extended)
  RuleRow = Vec<(Arc<str>, Arc<str>)>
  rule_rows:  Mutex<HashMap<Name, Vec<RuleRow>>>
  params:     Mutex<HashMap<Name, Vec<Arc<str>>>>
  bind_params / push_rule_row / rule_rows_snapshot / params methods

sprefa-run.rs (rewritten run loop)
  Pass 1: scan for rule defs → lower_rule_def → bind body+params on RelationStore → known_rules set
  Auto-fire: arity-0/1/2 rules fire once with empty-string-bound params
  Pass 2: lower_pipe with known_rules awareness (rule-call vs registry dispatch)
  After seed loop: dump_to_sqlite

dump_to_sqlite (NEW)
  per rule: collect column union (insertion-order preserving)
  DROP triggers + DROP fts + DROP table
  CREATE TABLE id PK AUTOINC + (col, col_norm) pairs
  CREATE INDEX per _norm col
  CREATE VIRTUAL TABLE fts5 + 3 sync triggers
  INSERT one row per RuleRow (raw value + sprf_norm(raw))
```

## Key Insights

1. **Rule body sink = full cursor capture set + cursor fields.** capture_row pulls repo/rev/fs as synthetic columns ahead of user captures. User explicitly asked "does cursor literally not have rev/repo/fs??" after first iteration walked captures only. Synthetic columns lead so they sit at stable positions across rows; user-bound captures override on name collision (HashMap dedup at drain time picks last).

2. **Two-pass lower handles forward refs.** Pass 1 collects all top-level rule names + binds body+params. Pass 2 lowers pipes with known_rules set populated. Self-recursion in body works because body's own rule name is added to body_known_rules before lowering. Cross-rule body refs punted (only top-level forward refs resolve).

3. **sqlx 0.8 sqlite, no UDFs.** sqlx-sqlite has no first-class UDF API; raw libsqlite3-sys would be needed for sprf_norm as SQL function. Punted: compute sprf_norm in Rust at INSERT, store the normalized value alongside raw. Trade: query-side `WHERE col = sprf_norm(?)` doesn't work without re-registering the UDF. v1's strings/refs/files tier is where the UDF mattered most; v3 flat tables work fine without it.

4. **sprf_norm body is dead simple.** strip non-ASCII-alphanumeric + lowercase. 5 lines. Suffix strip (norm2) is configurable, separate function — landed in v1 but punted in v3 (filed sprefa-9ma).

5. **FTS5 trigram + content= + auto-sync triggers gives free fuzzy search.** Verified `MATCH 'serv'` hits row with R='server'. v1 used this same pattern on the shared strings table; v3 puts it per-rule.

6. **Output_fp model dominates "op declares ambient inputs".** Author can't forget; correctness falls out of what was actually emitted; hard-to-enumerate ambient state captured automatically. Cost: every op runs (acceptable for cheap ops; per-input layer 2 cache handles expensive ops). Composes with watcher: change events fire fp recomputation; dep-graph walk invalidates only affected rules.

7. **RelationStore was per-seed; hoisted to run-scope.** SQLite drain happens after the seed loop, so it needs one accumulating store. SubjectRegistry also hoisted — Send/Sync, no conflict across seeds.

8. **Auto-fire of arity≥1 rules is mostly useless** (params bound to empty strings) but doesn't crash. Real value of arity≥1 is from explicit `foo($X, $Y)` call sites in other pipes. Smoke fixture exercises auto-fire path; real-world usage will have explicit calls.

## Open Questions

1. **Should sprefa-rhu close out as-is, or split into sub-cards?** Work landed. Predicate dispatch over rule rows (`<rule>?(...)`), self-recursion testing, and recursion-deadlock detection are not done — should those be sub-cards or just punted?

2. **Cache trait change requires user sign-off.** Phase A of sprefa-upb is framework-only and needs no trait change. output_fp model needs `fn output_fp(&self, batch) -> Option<[u8; 32]>` added to Op trait. User said "do not change op trait without asking" earlier in the chain.

3. **Rule body Pipeline shape: Fork vs Seq.** Currently if body has multiple top-level pipes, wrap in Pipeline::Fork; single pipe → Pipeline::Seq. Is broadcast-fan-out the right semantics for multi-pipe rule bodies, or sequential? V0 punt: Fork.

4. **Sub-grammar for rule body.** Body parses with host_parse_with_injections, which means injected pattern ops (re, glob) inside body work. But body cannot define nested rules (no recursion of rule defs in pass 1). Acceptable for v0.

5. **Watcher mechanism.** Inotify/fsevents per repo, periodic git fetch + diff, or .git/objects/pack watch only (memory note: project_v2_daemon_shape says watcher watches .git/objects/pack, ghcacher owns fetch). Filed in sprefa-3n6 as open question.
