## Key Insights
- "Build for the Phase F world" — caching read is correct because watcher will invalidate; not caching it would just force rework when F lands. Same logic applies to any decision that looks suboptimal pre-watcher.
- Three roots of time in the system: config edits, rev changes (branch fetch / fs event / commit), client requests (LSP messages, HTTP queries). Everything else is sync derivation of these.
- The pipeline is already an rxjs Observable chain (pipe_flat_map = mergeMap(64)). Daemon mode just keeps the upstream Subject alive instead of finishing.
- DiskFileSource's "rev is ignored" behavior means current sprefa-run is implicitly :wt-only. Renaming the default to "wt" is honest, costs nothing.
- buffer reads stay L1-only — buffer fingerprints change per keystroke; persisting to L2 would balloon the cache db with throwaway entries. Gate at runtime construction (which source stack is present), not per-cursor.
- Squigglies (publishDiagnostics, server push) are different from hover (textDocument/hover, client pull). Programmable squigglies = lsp[severity] sink op + diagnostics publisher subscribing to its output stream.
- 4-layer file stack for LSP: HEAD blob (immutable, hash=git OID free) → Index (mutable per stage, hash=git OID) → Worktree (mutable per FS event, blake3) → Buffer (mutable per keystroke, blake3, in-mem).
- git cat-file --batch beats git2 by 2.12x for bulk blob walk (FINDINGS §6.5, 1.98s vs 4.20s on Linux kernel). Don't use git2 for the future blob-reader.
- Phase 0 "no Op trait change in A-D" lock was correctly resolved by pulling Phase E forward as the canonical place where the additive cache_key method lands. C and D both consume it.

## Open Questions

- Should Phase F also invalidate by repo+rev (when a branch tip moves) in addition to by path (when worktree changes)? Probably yes — different watcher source feeds different eviction predicates.
- :HEAD:wt compound atoms: deferred per user. May come back if multi-overlay reads matter.
- Default behavior when daemon serves both LSP (buffer reads) and CLI (no buffer): single OpCache shared, or per-session? The buffer-no-L2 rule suggests per-session.
- Move runner/DocSession to pipeline: what's the cleanest seam? DocSession owns parsed CST + lowered ops + diag sinks. Pipeline crate doesn't currently know about LSP types — should it? Or invert: server holds DocSession, pipeline just runs the lowered Pipeline?
