## Problem/Context
sprefa is a Rust datalog DSL compiling to SQL over tree-sitter entity extraction. User wants to add partial call-tree analysis: "what does login() call in the order it appears, in these files" with a declarative ast-grep-shaped path syntax. Research established three bands:
- Band 1 lexical: sem tokenizes entity bodies, matches `name(` with word boundary, pure symbol-name resolution (~/projects/ext/sem crates/sem-core/src/parser/graph.rs extract_references_from_content, infer_ref_type).
- Band 2 syntactic/file-incremental: stack-graphs, tree-sitter locals.scm scope queries (@local.scope, @local.definition, @local.reference ship with every grammar — the unsung hero for free band-2 resolution).
- Band 3 semantic: rust-analyzer ra_ap_ide call_hierarchy, clangd, CodeQL, Glean, Joern, Kythe. Out of scope for sprefa.

Key insight: source-order call sequence is FREE from pre-order tree-sitter descendant traversal over `call_expression` nodes, pruned at nested function body boundaries. No CFG needed until you want branch-aware order (then/else/loop/try), and even that is pure syntactic classification (walk ancestors), not basic-block analysis.

ast-grep explicitly disclaims offline indexing: "always builds an AST in memory for each query." Therefore ast-grep is a pattern-match/extractor layer, not an index. sprefa owns the index; ast-grep rules become user-authored extractors that emit call_sites rows.

Class is Go-dominated not Rust-dominated — I initially said cymbal was Rust, user corrected, it's Go. Actual breakdown: Go (cymbal, grepai, SocratiCode), C (codebase-memory-mcp), Zig (codedb), Rust (sem, CodeRLM server, sprefa), Python (COMEX, graph-sitter, ACER). This makes the Rust<->Go interop question load-bearing.

Interop recommendation: SQLite file IS the FFI. sprefa writes .sprefa/index.db with WAL + user_version, any Go tool opens it read-only with modernc.org/sqlite (pure Go, no cgo). No protobuf, no cgo cdylib, no shared memory. The schema is the ABI. Secondary interop paths: long-lived subprocess + NDJSON (LSP pattern), MCP server, wazero+WASM if in-process embed needed, cgo only as last resort.

Extensibility seam options (pending survey data):
- Shell/template bridge: extractor subprocess, NDJSON stdin/stdout, ~2ms/file fork cost, amortize with long-lived workers. Universal, debuggable, Go tools plug in as `my-go-extractor < file > rows.ndjson`.
- WASM extractors: sprefa loads .wasm via wasmtime, sub-µs call overhead, sandboxed. Key win: ast-grep compiles to WASM, so ast-grep rule YAML files become a zero-compilation plugin surface.
- Hybrid: WASM fast-path for ast-grep rules + Rust extractors, shell bridge as escape hatch for arbitrary language tools.

Schema proposal for sprefa call_sites table:
```
call_sites(site_id TEXT PK, file_path, enclosing_entity, callee_name, callee_kind [free|method|macro|assoc], receiver_text, arg_count, ordinal INT (DFS preorder within enclosing body), depth INT, branch_path [then|else|loop|try|catch|NULL], start_line, start_col, end_line, end_col, resolution [local|imported|global|unresolved])
```
Query "what does login call, in order": SELECT callee_name FROM call_sites WHERE enclosing_entity = :id ORDER BY ordinal.

Path syntax sugar (layered, compiles to SQL):
```
fn('login') > calls-in-order > $c
fn('login') > calls > $c { branch: else }
fn('login') > calls+ > $c { depth<=3 }
$c < calls < fn('login')
```

## Key Insights
- Tree-sitter locals.scm is the unsung free band-2 resolution mechanism. Every mainstream grammar ships it with @local.scope, @local.definition, @local.reference captures. Using it costs zero engineering per language; sprefa should default to it before any custom scope resolver.
- Source-order call sequence is free from DFS pre-order traversal over call_expression nodes, pruned at nested function bodies. No CFG needed for linear order. Nobody in the peer class seems to preserve this (survey will confirm) — it's sprefa's opening.
- Branch path (then/else/loop/try) is "proto-CFG": syntactic ancestor classification, not basic-block dataflow. Still pure tree-sitter, per-file, fast. Gives ~90% of branch-aware questions without building a real CFG. COMEX (IBM tree-sitter-codeviews) does full CFG and only ships Java+C# after years — the cost-per-language curve is bad. Skip it.
- ast-grep is NOT an indexer. FAQ explicitly: "always builds an AST in memory for each query ... only indexes the AST itself, rather than variable scopes or type information." Correct role: pattern-extractor layer feeding sprefa's SQL store. Not storage, not query engine.
- SQLite file as the FFI beats every other interop option for tool composition across languages. This is how ctags, global, SCIP all ship — persistent file is the contract. modernc.org/sqlite is pure Go, no cgo. schema is ABI.
- Go ecosystem dominance in this class means Rust sprefa must NOT rely on in-process FFI for peer interop. Shared SQLite file + optional MCP/stdio subprocess covers all plausible cross-language consumption.
- sem's call extraction is ~120 lines of token-scan + substring-match after comment/string stripping + hardcoded common-local-name blocklist to kill false positives. Extremely cheap. Good baseline; sprefa can immediately beat it by using tree-sitter call_expression nodes instead of regex `name(`.
- codebase-memory-mcp (pure C, 66 langs, Cypher-like DSL, <1ms queries, sub-~/.cache SQLite) is the closest to sprefa's query-surface ambition and the one to watch most carefully in the survey. CALLS, HTTP_CALLS, ASYNC_CALLS edge kinds are interesting priors.
- cymbal (Go, cgo+SQLite+FTS5, FindTrace depth 3, FindImpact depth 2) is the closest architectural twin structurally. Worth the deepest read.
- grepai stores symbols in .gob (not SQLite), which loses join-ability. sprefa's SQL angle beats this structurally.
- tree-sitter-codeviews/COMEX (IBM, Python) is the only published CFG-over-tree-sitter framework. 15+ codeview combinations (AST/CFG/DFG). Java+C# only. Proof that full-CFG-per-language is expensive.
- Shell bridge vs WASM is not exclusive. Hybrid wins: WASM fast path for ast-grep YAML rules (zero user compilation), shell bridge escape hatch for "pipe any Go tool."
