## Key Insights
- tree-sitter optional('?') suffix on a token requires no GLR conflict declaration when adjacent (no whitespace between). `${X ?}` lexes differently from `${X?}` because extras (whitespace) can't span a token boundary.
- Carveout body grammar split via choice(alias(_brace_term_unbound, term_ref), pipe) works because _brace_term_unbound mandates the `?` and is therefore only a valid lex when followed by `?`. `${X}` (no `?`) cannot lex as _brace_term_unbound, falls through cleanly to pipe.
- BindingGraph is structurally a tree fold, not a graph algorithm. Only the rule-call-graph topo sort is graph-shaped, and that piece is deferred.
- Reserved synthesized names (REPO/REV/FS) modeled as env entries with writer_byte_range = None lets consumers distinguish "implicit cursor field source" from "concrete `${X?}` writer site" without two separate code paths.
- The current carveout-pipe-as-arg path emits a diagnostic value/carveout-pipe-unsupported when the body is a multi-step or slotted pipe. Source-op arg-pipes (sprefa-4iv, the `${repo({ > tag(:repo, ${R?}) })}` shape) will later remove that diagnostic and recurse into the inner pipe with its own BindingGraph analysis whose writers escape into the outer env.

## Open Questions
- BindingGraph fork merge: how to represent partial-binding diagnostics (X bound on arm 0, not on arm 1)? Diag at the Read site downstream of the merge, or at the Fork itself? Probably the merge site, to point users at the asymmetry.
- Should reserved REPO/REV/FS shadow-warn when a source op explicitly binds them? E.g. `repo(${REPO?})` is technically a shadow but is also the canonical introducer. Decision: keep as shadow warning for now; revisit when source-op arg-pipe contract (sprefa-4iv) lands.
- LSP wiring (sprefa-a3f): does host_parse return Vec<BindingDiagnostic> alongside Vec<ParseError>, or is it a separate step the server invokes after parse? Probably separate — sprefa_parse stays grammar-only, pipeline owns analysis.
