# Session: refactoring as an edit algebra (engine breakdown Stages 3 / 4 / 6a)

A working session that broke `engine.rs` down further, plus the discussion it
provoked about *how* one refactors — framed as an algebra of meaning-preserving
edits. Captured because the meta is the point: the mechanical half of refactoring
is now automatable, so the part worth writing down is the strategic half that
doesn't announce itself.

## The thing being practiced

A refactor is a **composition of edits, each of which provably preserves
meaning**. If every step preserves behavior, the composition does. That is the
whole trick. The skill is not "having good taste about file layout" — it is:

1. knowing which *edit operators* preserve meaning, and under what precondition;
2. factoring the work so each step is exactly one operator (never a move tangled
   with a semantic change);
3. building an **oracle** that makes "did this step preserve meaning?"
   falsifiable, before you make the first edit.

The "cleanliness" instinct — the one that feels vestigial, like ordering
punchcards — is really #2 and #3 wearing a costume. "Arrange the work so errors
stay localized and detectable." It atrophies now because the cut/paste got
automated and only the strategy is left to practice, and strategy is quiet.

## The edit operators used this session

Each is a function on the codebase with a **precondition** and an **invariant**
(what it provably leaves unchanged). The invariant is what the oracle checks.

| operator | example this session | invariant it preserves | how it's checked |
|---|---|---|---|
| **rename-symbol** | module `relkind` → `rels` | name resolution (every referent updated) | compiles + behavior |
| **split-module** | `relkind.rs` → `rels/{git,analysis,catalog,…}.rs` | module's item set + public surface | compiles, no API delta |
| **lift-to-child-module** | bucket-E methods → `engine/extract.rs`; `tick`/`tick_paths` → `engine/tick.rs` | method resolution + privacy (child reaches parent privates) | compiles, **zero body edits** |
| **widen-visibility** | `fn refresh_type_rels` → `pub(crate) fn` | monotone: only *adds* callers, removes none | safe by construction |
| **delete-dead-code** | unreachable `other =>` arm over `Value` (only `Text\|Int`); unused imports; needless `mut` | behavior — *because the code was never reached/needed* | compiler proves deadness |
| **repoint-fixture** | clone-oracle test path `src/engine.rs` → `src/engine/mod.rs` | the fixture's *denotation* ("a big real Rust file with fns X,Y") | structural assertions tolerate content shift |

Two of these are worth dwelling on because they're where the judgement lives.

### lift-to-child-module is the move that did the work

Rust privacy is module-scoped, and a **child module can access its ancestors'
private items**. That single fact is the lever:

- Put the lifted code in a *sibling* file (`crate::extract`, like `effect.rs`):
  every private field/type/helper it touches must be widened to `pub(crate)`.
  For the bucket-E bodies that's ~30 widenings — encapsulation erosion across
  the whole crate.
- Put it in a *child* file (`crate::engine::extract`, via `engine/mod.rs` +
  `engine/extract.rs`): the child sees `Engine`'s privates for free. Only the
  ~10 *entry* methods the parent's `tick` calls need `pub(crate)`. And lifting
  `tick` itself needs **zero** bumps — it's already `pub`, and it calls
  parent-private helpers as a descendant.

So the directory-module choice is **risk math, not aesthetics**: it's the
structure with the fewest `widen-visibility` operators, i.e. the fewest edits,
i.e. the fewest places to be wrong. (This is also why it is emphatically not a
new crate or a monorepo — `mod` is a namespace inside the one `sprefa-v5` crate;
Cargo.toml never moved. A directory just looks like a package.)

### delete-dead-code only counts if you *prove* the deadness

The unreachable arm was safe to cut **only after** confirming `enum Value` has
exactly `Text(String) | Int(i64)`, which makes `Text`+`Int` exhaustive and the
catch-all `other =>` unreachable. "The compiler warned about it" is the hint;
"I read the enum" is the proof. Deleting on the hint alone is how you turn a
warning into a behavior change.

## The two meta-disciplines

**A. Separate move from change.** Every operator above is *either* a pure
relocation (rename / split / lift) *or* a provably-null edit (widen / delete-dead
/ repoint). None mixes relocation with a semantic edit. The payoff: a pure
relocation **cannot** change behavior, so a green oracle is *conclusive* — not
"probably fine." The moment you let one commit both move a function and tweak its
body, a red oracle can't tell you which half broke, and you've lost the proof.

**B. Build the oracle before the first edit.** Here the oracle was three-layered:

- **docs byte-diff** — the data-derived docs (`rel_catalog`/`fn_catalog`/
  `op_catalog` → `relations.md` / `functions.md` / the README op-table) must
  *regenerate identical*. Run the generators, `git diff` must be empty. This is
  the user's stated guardrail ("auto docs / cli docs must not change") turned
  into a falsifiable check.
- **the test suite** — caught the one real break instantly (the clone-oracle
  fixtures read `src/engine.rs` by path; the rename moved it). That's the oracle
  earning its keep: a failure that points at exactly the unmodeled coupling.
- **the coupling gauge** (`coupling-metrics.dl`) — measures the refactor's own
  target. After a body *lift* it reads *flat* (coupling relocated, not reduced),
  which is the honest signal that this was approach B, not the registry-loop
  collapse of approach A.

Without the oracle you are editing and hoping. With it, refactoring becomes
mechanical: apply operator, check invariant, commit; repeat. The "rhythm."

## The dl question (can the engine read its own structure?)

The `lift.py` that found method spans (regex for `fn`, walk up for `///`,
brace-match down to `    }`) is a **structural read**, and that half is squarely
dl's job — and dl would do it *better*:

- `node(id, kind, file, lo, hi, parent)` + `child` — the real tree-sitter CST
  with byte spans. No `^    }` indentation heuristic that can lie.
- `type_entity(sym, name, kind, parent, file, line)` — methods directly,
  `kind=method`, `parent=Engine`.
- `doc_comment(repo, sym, line, text)` — the doc block per entity, so "method
  span including its doc" is a join, not a walk-up loop.

Reaching for Python on the *read* was reflex/affinity, and the lazier choice in
a repo whose whole premise is that dl answers "where is X" structurally.

The **write** half — "cut this 1024-line span out of file A, paste into file B
wrapped in `impl Engine {}`" — is genuinely *not* in dl today. The edit sink
(`ref` / `edit(ref_id, new_string_id)` / `--move` / `--fix`) is built for
in-place span rewrites (rename, use-path) and whole-file moves; a
*lift-span-to-new-file* primitive doesn't exist. `gen` could emit the new file
from queried spans, but "blank these ranges in the source" isn't a splice op.
Honest split: **dl for the read, a script for the surgery.** A latent feature:
an `extract`/`lift` edit operator would make the whole refactor a dl program.

### Stage 6 remainder — a deliberate stopping point

What's left in `engine/mod.rs` (5477 lines) is the Engine **core**: the struct,
ctor, the `pub(crate)` seam, and the source / derived / schema machinery
(`reconcile_sources`, `parse_file`, `rebuild_derived`, the SQL fixpoint,
`declare*`, `ensure_meta`). The proposal wants these split into
`source.rs`/`derived.rs`/`schema.rs` too — but those are **sibling** lifts (the
core methods call *each other* and are called from `tick.rs`), so each crossing
needs a `widen-visibility` operator. Measured cost: ~16 methods → `pub(crate)`
(`declare` is called 15× from `mod.rs`, the eval/rebuild methods 1–7× from
`tick.rs`).

That is exactly the encapsulation-widening the deferred `RelCtx` seam was meant
to bound. So this is a clean place to stop: the cleanly-separable *subsystems*
(rel families, bucket-E extractors, the tick orchestrator, the effect runtime
from Stage 5) are out; what remains is the genuine core, which arguably *belongs*
in the main engine file. Pushing further trades cleanliness for `pub(crate)`
churn — a different deal than the zero/low-churn lifts so far.

## Key insight, compressed

Refactoring is an algebra: a few meaning-preserving operators (rename / split /
lift / widen / delete-dead / repoint), composed under one rule — **never mix a
move with a change** — and checked by an **oracle built before the first edit**.
The directory-module lift is the high-leverage operator because child→parent
private access makes most `widen-visibility` operators unnecessary, so the move
is nearly edit-free and the green oracle is proof, not hope. "Cleanliness" was
always this discipline; it only felt like punchcard fussiness because the part
it protects — localized, detectable error — is invisible when it works.
