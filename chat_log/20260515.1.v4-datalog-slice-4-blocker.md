# v4 Datalog Slice 4 — Retract-Chain Blocker (2026-05-15)

## Status

Slice 4 (retract chain on source-change) **HALTED** before any code shipped. Slices 1, 2, 3, 5 ship clean.

## Goal

Per task:

> Source row deleted → walk `support_edges` → for each downstream owner, delete rows whose `support_id` matches → recurse.

Test: chain `a > b > c`. Delete row from `a`'s source. Assert downstream rows in `b` and `c` are gone.

## Substrate Survey

Two unrelated "support" tables exist in the v4 tree:

| Name | Schema | Owner | Where |
|------|--------|-------|-------|
| `runtime_edge` rows with `kind=support` | `(edge_uri_id, from_uri_id=owner, to_uri_id=row, label_id=table, ...)` | `RuntimeGraph` | `v4/src/runtime_graph.rs` |
| `support_edges` | `(parent_table TEXT, parent_id BLOB, child_table TEXT, child_id TEXT)` | fused-SQL execution path | created in `v4/src/app.rs:892`, populated by fused SQL emitted in `v4/src/compile/fuser.rs:627` |
| `mounted_query_support` | `(__support_cursor_id, support_table, support_row_id)` | mounted-SQL plumbing | `v4/src/mounted_query.rs:19` |

`runtime_edge.kind=support` models **owner → row** (one direction). Source rows themselves are not nodes; their identity is not in `runtime_node`. So the recursive walk "given a deleted source row, find the derived rows that depended on it" cannot be answered from `RuntimeGraph` alone today.

`support_edges` is the table that models the right shape (`parent ← child` linkage between row-ids across tables). It is the substrate slice 4 needs. But:

1. **Only the fused-SQL execution path writes to it.** `v4/src/app.rs::run_fused_sql` is the lone producer. Direct uses of `FactWrite` and non-fused rule execution do NOT touch `support_edges`.

2. **It lives in raw SQLite, not in FactStore.** Access requires downcasting `Arc<dyn FactStore<Cursor>>` to `SqliteFactStore<Cursor>` and calling `with_connection`. Works for the runtime path but the `MemFactStore` test harness has no equivalent.

3. **`parent_id` is `BLOB`; `child_id` is `TEXT`.** Recursing the chain means treating a deleted parent as a child at the next level, which means asking SQLite to compare a BLOB (the deleted `parent_id`) against `support_edges.child_id` (TEXT). Cross-type comparison is silent and lossy; type alignment is broken at the schema level.

4. **The insert is best-effort.** Comment in `app.rs:818-821`: "support_edges insert is best-effort: the live schema doesn't declare the table, so we `CREATE TABLE IF NOT EXISTS` it in the same transaction. Failures there are demoted to a warning so the primary fact insert still commits." Production rows can land in `<rule>_facts` without a paired entry in `support_edges`. Building a retract semantics on this would assume durable invariants that the producer does not guarantee.

## Sub-Failures

A test that "creates a chain a > b > c, deletes from a, asserts downstream rows gone" requires the fuser/compiler/execute_fused_rules wiring. Bypassing them and seeding the tables directly is possible but the BLOB/TEXT mismatch (#3) makes the recursive walk non-portable: it only works for the top-level call's TEXT child_id, then breaks on the next level when the deleted parent_id (BLOB) needs to be matched against the next level's child_id (TEXT).

Wrapping the recursion to convert BLOB → hex TEXT at each boundary is plausible but requires verifying that the fuser-emitted INSERT for the next level uses `hex(sprf_blake3_id(...))` for its `_id` — and the fuser source confirms it does not always do this. The TEXT/BLOB story is asymmetric between `support_edges` and `<rule>_facts._id` (the live-schema rewrite in `build_live_facts_insert` casts blake3 to hex TEXT for `_id`, but the corresponding `support_edges.parent_id` stays raw BLOB).

Implementing a working retract that respects all three impedance mismatches (FactStore abstraction crossing, BLOB/TEXT recursion, best-effort producer) is at least M-sized and trades against substrate cleanups the user has signaled higher priority for (`v4-deterministic-runtime-graph-reconciler-plan.md` Follow-Up Work, the chain "Direct filesystem watcher integration / Source edit migration / unmount policy for changed `source_hash`").

## Recommendation

Slice 4 should be reframed as a substrate cleanup before any retract logic:

1. **Align `support_edges` types.** Either both `parent_id` and `child_id` as TEXT (hex blake3) or both BLOB. Pick one and pin it in the CREATE TABLE in app.rs AND in the fuser-emitted INSERT.
2. **Declare `support_edges` through `FactStore`.** Make it visible through the trait so MemFactStore can host it for tests, and SqliteFactStore stops needing `with_connection` for cascading reads.
3. **Promote the producer from best-effort to mandatory.** Fail the primary insert if support_edges insert fails. This becomes possible once #1 + #2 land.
4. **Then build `RuntimeGraph::retract_source_row(child_table, child_id_blob_or_text)`** with the durable substrate underneath.

Estimated total: M (cleanups) + M (retract) ≈ L. Same effort the slice estimated, but layered so each step is independently testable.
