## Problem/Context
The N+1 is in the rule → FactWrite path. A FanoutOnce body that emits N=1000 cursors in a SINGLE `Node::Many` from one render call results in ~1000 insert_batch calls instead of 1. Average ~3-4 rows per call.

Telemetry from linux bench:
```
store insert_batch_calls=15150 insert_batch_rows=93258 avg_batch=6.2
sqlite_insert_exec_calls=15152 sqlite_insert_exec_rows=93258 transactions=15150
stage v4::rule::RuleInvokeComponent: calls=1 rows=1 wall_ms=634156.2
store_warnings small_insert_batches avg_batch=6.2
                n_plus_one_sqlite_insert_execs avg_rows_per_exec=6.2
```

Hypothesis: the queue's dispatch loop or FactWrite::render_batch is being entered with batch sizes of ~3-6 cursors instead of the full Node::Many size. Need to trace:
- `effect_runtime::v2::expand` and how Many gets sliced/queued.
- `FactWrite::render_batch` invocation cadence.
- Possibly the batch_cap inside `Rule::run_with` or `RuleInvokeComponent::run_rule` (lines 295-304 in v4/src/rule.rs).

`RuleInvokeComponent::run_rule` already sets `with_batch_cap(1 << 20)` so that's not the cap. The "strict" test uses `with_batch_cap(1 << 20)` directly and still failed → cap isn't the issue. The bug is upstream in how Node::Many gets fed into render_batch.

## Solution/Approach
1. Trace `effect_runtime::v2::expand` — find where Node::Many gets unpacked into queue rows, see if batching is preserved.
2. Trace `FactWrite::render_batch` callers to see what batch sizes it actually sees.
3. Possible fixes:
   - Make the queue dispatcher coalesce same-component contiguous rows into one render_batch call.
   - Make Node::Many emission keep the rows together.
   - Have FactWrite buffer rows until a barrier/flush.
4. Re-run the budget test as the success condition. Must drop to ≤ 2 calls (one for the Many, one for end-of-run flush).
5. Then re-run the linux bench, expect 10min → seconds.
