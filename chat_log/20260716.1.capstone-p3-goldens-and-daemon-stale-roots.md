## Solution/Approach
**The ledger entry "SERVED-COPY DIVERGENCE (Chris only)" is FALSE and should be deleted.**
`ensure_singleton()` (src/daemon.rs:2014) already pings the daemon, compares `build_id`
(`version:mtime_of_current_exe`, daemon.rs:1242), and self-restarts on mismatch:
```rust
Some(id) if id == build_id() => return Ok(()),
Some(_) => { eprintln!("[daemon] running binary changed — restarting daemon"); let _ = stop(); }
None => return Ok(()),   // only hole: a daemon whose ping predates the build_id field
```
Both ping handlers DO return build_id (daemon.rs:1494, 1516), so the check fires. The manual
`cargo install && dl daemon restart` ritual is unnecessary. The reason restarting "fixed" perf
before is that it drops accumulated stale roots — which is the REAL recurring bug.

Stopgap prune (daemon rewrites roots.json from memory, so stop/start must bracket the edit):
```
dl daemon stop; python3 -c "
import json, os, pathlib
p = pathlib.Path.home()/'.local/state/sprefa/roots.json'
r = json.loads(p.read_text()); keep = [x for x in r if os.path.isdir(x['root'])]
p.write_text(json.dumps(keep, indent=2)); print('kept', len(keep), 'of', len(r))
"; dl daemon start
```

## Key Insights
- **build_id match is the one-command divergence test**: `stat -c %Y ~/.cargo/bin/dl` vs the
  `build_id` in `dl daemon status`. Equal => divergence is not your problem. Stop re-diagnosing.
- **The engine already logs why call-delta bails** (`src/rels/extract_family.rs:277`
  `eprintln!("[call-delta] fallback reason={reason} scope=call-family")`). An EMPTY grep for it
  is itself strong evidence — it exonerates the whole call-delta path in one shot.
- **P1's schema_version bump is correct, not a bug.** Old build demands `!= 1` / writes `1`;
  new demands `!= 2` / writes `2` — mutually exclusive contracts. Two binaries on one DB would
  full-refresh every tick forever. Didn't happen here (single binary), but it is a real hazard
  if a stale daemon ever DOES survive alongside a fresh CLI.
- **P3 golden stability needed a normalizer** and this is non-obvious: `resolve_rev`
  (src/engine/repo.rs:6) maps any non-WORK rev to a commit SHA that moves every regen, and
  `sandbox()` embeds the pid. Both are normalized to `<BASE>`/`<ROOT>` by ONE helper shared by
  producer and consumer so they cannot drift. Verified by regen-twice + diff (note: plain
  `git diff --exit-code` is VACUOUS on untracked files — must `git add` first).
- `classify_call_kind` (src/engine/decls.rs:967) only fires on rusqlite-shaped bare names
  (`execute`/`execute_batch` -> write, `query_row`/`prepare`/... -> read). Arbitrary fn names
  yield NO call_kind rows — a fixture must name calls deliberately or call_kind is vacuous.
- Agent hygiene: a throwaway `git worktree add` under a watched root gets REGISTERED as a daemon
  root and survives `git worktree remove`. Don't create worktrees under a daemon-watched tree.
