## Problem/Context
Agent-verified (2026-04-17) the real bottleneck:
- `Reader::bytes(FilePath)` + `Reader::blob_oid(FilePath)` scalar methods on `GitBlobReader`. 1067 files × `Mutex<git2::Repository>` per call. WT fast path on bytes exists but `blob_oid` still takes the mutex.
- `ParseCacheReader` = three separate `RwLock<HashMap>` (cache + by_oid + by_hash). 2 write-locks per cache miss.
- blake3 is NOT in the hot path (oid fast path taken). Prior theory wrong.
- `op.ast.prefetch` uses `join_all` over 1067 `prep_cursor` futures — 1067-wide FuturesUnordered.
- Size-cap kills the two swc generated-visitor files (5.3M + 4.2M). Those dominated `find_all_and_build` in debug.

User took the design discussion hard: traits with scalar methods structurally invite N+1. LLMs can't count so the trait has to make scalar calls un-typeable. User also rejected my grand-unification dual-pair reframes (Source/Sink, Query/Mutation) as the same "pair-up binary unified for the 500-millionth time" junior move. Wanted practical type techniques grounded in what already works in the codebase.

## Solution/Approach
Two documents, not a rewrite yet:

1. **LAWS OF MIN** (CLAUDE.md § top): Reader/Store/MutationHandler collapse to one batch method each. `Box<[T]>` in, `Box<[T]>` out. Scalar caller builds a length-1 batch. Compile-time N+1 prevention. Six-point PR rejection checklist. Evidence-of-drift list with file:line.

2. **TYPE TECHNIQUES** (CLAUDE.md § follow-on): three lists (keep/reintroduce/reject) plus 8 rules of thumb. Drawn from practices already in the codebase (Arc<[T]>, concrete enums, newtype wrappers, one-owner batches, ops own diagnostics).

README has a loud banner pointing at CLAUDE.md.

## Tasks
- [ ] **Collapse Reader trait to one method.** Delete `bytes`, `bytes_range`, `blob_oid`, `files`, `parsed`, etc. New shape: `fn read(&self, req: &ReadBatch) -> ReadResult`. Length-1 batch for any scalar caller. Fixes `Mutex<Repository>` 1067× problem by holding it once per wave.
- [ ] **Collapse Store trait to one method.** `fn apply(&self, batch: &WriteBatch) -> ApplyResult`. Delete `register_expr_schema`, `flush_batch`, effect cache, scanner-hash methods. SQL moves into the single Store impl's private helpers.
- [ ] **Collapse MutationHandler to one method + enum policy.** `fn decide(&self, effects: &[Effect]) -> Box<[Decision]>` with `enum ApprovalPolicy { Auto, Cli, Lsp }` as a batch-header field. Three impl files (AutoApprove, InteractiveCli, LspPromptBridge) collapse to one match.
- [ ] Kill `Arc<RwLock<HashMap<K, Arc<OnceCell<Arc<V>>>>>>` in `ParseCacheReader`. Single `RwLock<HashMap<K, V>>` + partition-over-batch pattern.
- [ ] Replace `join_all` over per-file futures in `op.ast.prefetch` with one `parsed_many` call over the batch.
- [ ] Pre-build `HashMap<FilePath, [u8;20]>` at `files()` time and stash in `WorktreeProvisioner` so `blob_oid` serves without the repo mutex. Was called out by agent as a specific localized win.
- [ ] Audit 13 `RuntimeConfig { ... }` literal sites — `feedback_op_owned_annotations` / CLAUDE scaffolding convention says these should use `..RuntimeConfig::test_default()`. Currently hand-written.

## Key Insights
- **Structural fix beats disciplinary fix.** You can't code-review your way out of N+1 when the trait permits scalar calls. The trait has to make scalar calls un-typeable. LLMs definitely can't remember to batch across 15 callsites.
- **Agent-verified bottleneck ≠ my theory.** I guessed blake3 and sqlx; both wrong. Actual bottleneck is `Mutex<Repository>` on `blob_oid` per file. The parse cache's three-tier lock is cheap per-call (microseconds). Stop theorizing; run the span log.
- **Debug vs release measurement gap.** Debug is measuring itself (span overhead + checked arithmetic) more than measuring the logic. Real perf number is release. Biome 3k files/sec ≈ 0.33 ms/file; sprefa release 0.85 ms/file — ~3x gap, not 10x. Gap is architectural (cursor model + channels + cache) and closeable, not hopeless.
- **User rejects grand-unification moves.** Source/Sink, Query/Mutation, Fabric — all got rejected as "pair-up binary unified for the 500-millionth time." Build specific intent surfaces; don't pre-pair duals for symmetry's sake.
- **Size cap saved debug 3s but only ~50ms release.** The two swc generated visitor files (5.3M + 4.2M, 235/173 matches) dominated `find_all_and_build` in debug but not release. Cap is still the right call — it emits a warn diag with path+bytes+cap naming the reason.
- **`op fs 7466ms` in debug is downstream-cumulative**, not fs intrinsic. Every op's timing includes waiting for its batch to be consumed.
- **Pre-existing compile errors pattern.** `.entered()` held across `.await` makes futures non-Send. Fix = `.in_scope(|| ...)` for sync chunks, `.instrument(fut)` for async. Hit this at `src/_7_init_cursors.rs` and `src/server/_1_workspace.rs` this session.

## Open Questions
- Is MutationHandler collapse worth doing before the three handler impls have any real consumer? AutoApprove is the only used impl today. May be fine to leave the trait as-is until InteractiveCli/LspPromptBridge have bodies.
- Does collapsing `ParseCacheReader` to batch-only break the LSP hover path, which calls `parsed()` with a single file? Length-1 batch works in principle; need to check whether hover's call shape has cross-cutting concerns.
- Whether to keep the chrome-trace (`SPREFA_TRACE`) fork in `_telemetry.rs` or simplify to stderr span-log only. User found the flamegraph confusing; stderr span-log was what landed the diagnosis. Trace feature can stay as opt-in without cost.
