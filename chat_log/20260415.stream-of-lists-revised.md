# Stream-of-Lists — Revised Recommendation

Supersedes the analysis in
[`20260415.stream-of-lists-design.md`](./20260415.stream-of-lists-design.md).
That memo stands as-is for its walker-already-groups finding and
per-op migration inventory; this revision corrects one overreach.

## What the prior memo missed

`Cursor` already carries `SprfPath` (see `v2/src/_0_types.rs:75-85`): a
runtime trail of `PathSeg` entries (`Op`, `ForkArm`, `Iter`, `LeafArm`, …).
Every cursor has a unique path by construction. Two cursors are *siblings*
iff their paths match up to the last `Iter` or `ForkArm` segment.

```
fs(**/Cargo.toml) under rule(r):
  C0a  path = [Op(rule), Op(fs, step=0), Iter(0)]   ← sibling
  C0b  path = [Op(rule), Op(fs, step=0), Iter(1)]   ← sibling
  C0c  path = [Op(rule), Op(fs, step=0), Iter(2)]   ← sibling

  group key = prefix_up_to_last_iter(path)
            = [Op(rule), Op(fs, step=0)]
```

**Group identity is already encoded.** The prior memo proposed `BatchId`
as a shortcut; it would be a hash *derived from* `SprfPath`, not a new
concept. Dropping it.

## Collapsed option space

Prior: (A) scalar stream, (B) `Arc<[Cursor]>`, (C) `CursorBatch` with id.

Revised: **(A) vs (B)** only. (C) is (B) + a redundant tag.

## Side-by-side, with SprfPath grouping in both

|                                   | (A) today                                | (B) `Arc<[Cursor]>`                             |
|-----------------------------------|------------------------------------------|-------------------------------------------------|
| Sibling identity                  | ✅ path-prefix grouping                   | ✅ list-membership OR path-prefix               |
| Empty-seed signal                 | ❌ invisible (no cursor flows)            | ✅ `Arc<[]>` carries "this produced nothing"    |
| Walker flatten ceremony           | `ops/_5_json.rs:294` `flat_map(stream::iter)` | 0 — walker's grouped rows flow through      |
| Filter/map op boilerplate         | 0                                        | per-op `batch.iter().filter().collect()`        |
| Trait migration cost              | 0                                        | ~6 ops, mechanical rewrap per prior inventory   |
| Batch-scope op semantics          | clumsy (regroup by path first)           | natural (op chooses per-element or per-batch)   |
| "All or nothing" drop-semantics   | N/A (ops are per-cursor)                 | **opt-in**: per-element is still the default    |

### On the drop-all-if-one-bad question

The wrapper does **not** force batch-level semantics. Default filter shape
inside (B) stays per-element — `batch.iter().filter(keep).collect()`
shrinks the batch, keeps survivors. "Drop the whole batch on one miss"
is only what you get if an op *explicitly* chooses batch-scope. No op
today does. The nesting *enables* batch-level semantics without
requiring them.

## Revised recommendation

**Adopt (B) now.** Do not wait for ast-grep or any other trigger op.

Driving principle: minimize shotgun surgery. Migration cost scales
linearly with op count, and the trait-signature change is one-shot
regardless of when it lands. Deferring doesn't shrink the surgery, it
grows it.

```
Ops today      : repo, rev, fs, rule, read, json       = 6
Ops planned    : md, ast-grep, line, …                 = ~10 when flip forced

Pay now   : 6  × mechanical rewrap + 1 trait change
Pay later : 10 × mechanical rewrap + 1 trait change
            + every op drafted for migration the moment (B) lands
            + risk of interim features that entangle with (A) assumptions
```

New ops written against (A) between now and ast-grep get drafted into the
migration with zero grace period. Every week of delay enlarges the
future diff without shrinking today's.

### The structural-alignment argument (independent of op count)

The earlier "wait until batching is needed" framing conflated two
decisions:

- **Trait-shape alignment** — whether the stream layer matches the
  grouped-output shape of tree walkers. Decided on structural merit,
  not feature demand. (B) wins today: `walk/_3_walker.rs` already
  produces grouped `WalkOutcome.rows`, and `ops/_5_json.rs:294`
  immediately throws the grouping away.
- **Batch-scope op semantics** — whether any op explicitly wants
  all-or-nothing operation on a sibling group. Feature-dependent, opt-in
  within (B), doesn't force the trait shape on its own.

(B) is justified by the first even if the second never arrives.

### What changes in the current codebase under (B)

- `Op::pipe` signature: `BoxStream<'static, Cursor>` →
  `BoxStream<'static, Arc<[Cursor]>>`.
- Every op's `pipe` body: wrap today's `filter`/`map`/`flat_map` logic
  in `input.map(|batch| batch.iter().filter(...).collect::<Arc<[_]>>())`
  or equivalent. Mechanical per prior inventory.
- `walk/_3_walker.rs` consumer path (`_5_json.rs:294`) drops the
  `flat_map(stream::iter)` — grouped rows are now the stream item.
- Runner drive loop (`_5_op.rs` or wherever Pipeline::run iterates) —
  adapt to iterate `Arc<[Cursor]>` items. One-shot.
- Completion partial-eval (`analysis.rs::complete_in_paren`) — the
  `cursors_by_rule` collector flattens batches into `Vec<Cursor>` at
  the collection point. Unchanged downstream.
- Empty-batch handling convention: `Arc<[]>` items propagate.
  Diagnostics can now fire off "this seed produced nothing" as a
  first-class event (`fs/no-match`, `json/no-match` pipe directly from
  batch-is-empty checks instead of counting cursor absence).

## What stays from the prior memo

Still correct and load-bearing:

- The walker produces grouped output and json flattens it
  (`walk/_3_walker.rs WalkOutcome.rows` → `ops/_5_json.rs:294
  flat_map(stream::iter)`). This is a real cost under (A) — small, but
  real.
- Per-op migration inventory (everything is mechanical rewrap,
  fs/json are the two genuine beneficiaries).
- Future ops (ast-grep especially) shift the calculus toward (B).

## Out-of-scope future: path-aware syntax

Orthogonal to (A)-vs-(B): the `PathSeg` enum has room for a
`NamedArm { label, parse_site }` variant to support label-addressable
pattern arms (`@pkg_arm: json({…})` with downstream
`switch($PATH { @pkg_arm: … })`). That's a `PathSeg` addition, not a
`Cursor` field addition. Path is where structural decisions live;
captures + evidence are where matched values live. Not blocked by
either streaming model.
