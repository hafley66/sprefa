## Problem/Context
Sprefa (sprefactor) lineage: cross-codebase causal-link engine. write_cursor was committing direct to disk (Phase 0). User wants stage→approve→commit so refactor sessions can be inspected/diffed before splicing, reusing git as the diff oracle. The yield/SubjectRegistry primitive (already in production for RelationWake) is the natural pause/resume mechanism — symmetric to redux-saga effects. User explicitly chose: (Q1) no-checkout overlay; pending table is the overlay, worktree only at promotion; (Q2) timeout + LSP-diag surfacing of pending writes + referential integrity to .sprf op; (Q3) sqlite via existing store; (Q4) multi-repo sessions are best-effort, N independent commits; (Q5) virtual-doc + diags + code-actions all together; (Q6) no `write!` bang in Phase 1.

## Solution/Approach
Three-pass plan landed in chat_log/20260427.5 (Pass 1 v1 archaeology, Pass 2 v2 effects split + $wt overlay, Pass 3 reconcile). Phase 1 is pure runtime plumbing (yield/buffer/auto-approve in sink). Phase 2 (sprefa-04w) auto-worktree + refactor_pending sqlite + LSP code-action approval. Phase 3 = session grouping + promotion path. Cockpit slice (this session) flipped staged buffer rows into structs with content-hash ids and emits them as Info diags so SSE/CLI consumers render them in the same panel as parse + lsp diagnostics.

## Key Insights
- Yield primitive is fully battle-tested via RelationWake (production use in relation/probe.rs, relation/query.rs). Reusing it for WriteApproval was a 20-LoC subject-kind impl plus the registry threading.
- Pre-subscribe pattern (registry.subscribe BEFORE ctx.put) closes the race where the batcher could call next() before the op subscribes via Yield batcher poll. Op-side: `let fut = registry.subscribe(key, None); ctx.put(effect{approval:Some(key)}).await; fut.await;`
- Content-hash ids (blake3 first 12 hex of canonical fields) are stable across re-runs, so cockpit ids are addressable across sessions — foundation for `--approve-only id1,id2`.
- User vision is "cockpit": dense terminal display of pending state (writes, diags, cursors) with addressable handles. Better than mouse-driven UIs because AI has bit-level vision but humans need wide buffer + grep.
- Multi-seed write coordination (sprefa-5ld) is a real bug that emerged when running golden_kitchen_sink.sprf section 7. Each seed re-runs the full pipeline; without per-file write coordination + byte_range invalidation, multi-seed write_cursor demos clobber the target file.
- Disk-mode fs (no repo/rev prefix) is required for write_cursor to splice today; repo/rev path goes through git blob layer. Phase 2 (sprefa-04w) addresses via auto-worktree materialization.
- sprefa-server is a daemon spawned by sprefa-run via auto-spawn; stale server processes (after rebuilds) cause "did not become reachable" errors. Always pkill -9 -f sprefa-server + rm ~/.cache/sprefa/{server.json,sprefa.sock} after rebuilding the binary.

## Open Questions
- WritePolicy threading: should it be a RunRequest field or HTTP header / env var? RunRequest is cleaner but touches sprefa-run.rs CLI which has parallel-session edits.
- Rejection payload: when a write is rejected, should the op see `Err(Arc::from("rejected by policy"))` or a typed sentinel? Today's WriteApproval payload is `Result<(), Arc<str>>` — string is enough for first iteration.
- Should rejected-by-policy writes still appear in the staged buffer for the CLI to print, or only successful approvals? User intuition: print all (so user sees what was requested even when nothing splices).
- Multi-seed coord (sprefa-5ld): does the fix live in run.rs (post-seed write coordination across seeds) or in the WriteRangeBatcher (per-file lock + byte_range invalidation)? Probably batcher-level.
