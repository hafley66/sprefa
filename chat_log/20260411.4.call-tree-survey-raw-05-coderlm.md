## Analysis

### Call Extraction Mechanism

Call extraction happens at two layers:

**Rust side (files:25-27):**
- `/server/src/symbols/queries/{rust,python,typescript,go,java,scala}.rs` define hardcoded tree-sitter `CALLERS_QUERY` strings
- `/server/src/ops/symbol_ops.rs:138-204` implements `find_callers_ast()` which parses source with tree-sitter, runs `config.callers_query`, iterates captures matching `@callee` capture index, and extracts line number and text
- Fallback regex via `find_callers_regex()` at :206-245 matching `symbol_name` as literal string in source lines

**Python side (files:43):**
- `/plugin/skills/coderlm/scripts/coderlm_cli.py` invokes HTTP endpoints which call Rust extraction

### Tree-Sitter Usage

- Tree-sitter used for all supported languages (Rust, Python, TypeScript/JavaScript, Go, Java, Scala)
- Hardcoded per-language query strings in `symbols/queries/*.rs`:
  - `SYMBOLS_QUERY` — extracts function/class/struct/enum/trait definitions
  - `CALLERS_QUERY` — extracts call-expression nodes; captures callee identifier
  - `VARIABLES_QUERY` — extracts local variable bindings within scope
- No `locals.scm` file; queries are inline strings in Rust code
- Custom scope resolver: `/server/src/ops/symbol_ops.rs:405-457` uses `cursor.set_byte_range(fn_start..fn_end)` to restrict variable extraction to function scope

### Storage Format

- In-memory concurrent store: `DashMap<String, Symbol>` (primary) + secondary indices `by_name` and `by_file` (both `DashMap<String, HashSet<String>>`)
- Optional JSON persistence: `.coderlm/annotations.json` in project root stores agent-set definitions and marks (not symbols)
- No native format; symbols serialized to JSON for HTTP responses
- Schema: `Symbol` struct with explicit byte_range, line_range (1-indexed), parent reference, signature (first line only)

### Source-Order Preservation

- Byte and line ranges explicitly stored in `Symbol { byte_range: (usize, usize), line_range: (usize, usize) }`
- Callers returned in file-traversal order (`file_tree.files.iter()` without explicit sort) with line numbers preserved
- Variables extracted in source order (matches returned sequentially from tree-sitter query cursor)
- Sorting occurs in caller display (`symbol_ops.rs:28` sorts by file then line_range.0) but underlying data preserves source order

### Split: Rust vs Python

**Rust (server):**
- File indexing and scanning (walker with `.gitignore` support via `ignore` crate)
- Filesystem watching (notify crate with 500ms debounce)
- Tree-sitter parsing and symbol extraction
- Symbol table management and HTTP API endpoints
- Session/project lifecycle

**Python (CLI):**
- Subprocess wrapper calling HTTP endpoints
- User-facing skill interface for Claude Code
- Query composition and human-readable output formatting
- No dependencies (stdlib only)

### Extensibility Seams

1. **Language support:** Add language in `Language` enum (`file_entry.rs:7-27`), implement config in `symbols/queries/new_lang.rs`, register in `queries::get_language_config()` (queries/mod.rs:11-22)
2. **Query customization:** Hardcoded query strings can be edited in `symbols/queries/*.rs` without recompilation not possible (baked into binary); would require runtime query loading
3. **API endpoints:** New routes added in `server/routes.rs:56-90`; new operations added as functions in `ops/*.rs` modules
4. **Storage:** Symbol table is pluggable (trait-like but not formalized); could swap DashMap for persistent DB by changing `SymbolTable` impl
5. **Filesystem watcher:** Event handler at `watcher.rs:61-96` can be extended with new event kinds or filtering logic

### Cross-File Resolution

- No transitive type resolution (e.g., can't follow type hierarchies across files)
- Explicit lookup via `SymbolTable::get(file, symbol_name)` — caller must provide exact file path and symbol name
- `find_callers()` scans all files looking for call sites; no import-aware filtering or module-qualified name resolution
- Symbol parent references (e.g., struct for a method) stored but not used for call resolution

### Locals Resolution Detail

- `/server/src/ops/symbol_ops.rs:375-401` `list_variables()` extracts variables within a single function
- For tree-sitter languages:
  - Parses full file into tree
  - Runs `VARIABLES_QUERY` on entire tree
  - Restricts matches to byte range of target function (`cursor.set_byte_range()` at :437)
  - Deduplicates and filters "self" and "_"
- For regex languages: pattern matching on function body slice
- No type inference; names only
