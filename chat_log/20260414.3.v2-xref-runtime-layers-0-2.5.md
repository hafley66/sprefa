## Problem / Context

Original plan listed five layers. This session resolved several semantic ambiguities through user feedback:

1. **LSP/CLI are pure transports** — no language semantics in those crates. ResultStore + analysis live in core. Saved as `project_v2_runner_owns_analysis.md`.
2. **`$VAR` ≡ `${VAR}`** — synonymous capture forms. Braces only required for disambiguation (`${rule.$VAR}` xref form). Saved as `project_v2_capture_syntax.md`.
3. **Row-based ResultStore, not value-set-based** — store full `Vec<CaptureMap>` per rule, not distinct values. Cartesian over rows, not over value domains.
4. **Cartesian over multi-xref targets** with explosion guard — initially user said zip, then corrected to cartesian with limit + Warn.
5. **Output-candidate dedup**, not source-row dedup — per-input-cursor `HashSet<tuple>` of seeded `(var, value)` pairs in xref declaration order.
6. **Empty source set is meaningful** — emit `xref/empty-join` Hint at xref byte_range, drop cursor. Filters culling all candidates is a separate non-signal.
7. **Adapter scoping option (b)** for crossref collection — additive `crossrefs` field on OpInvocation, not full SlotRef refactor of every op's paren consumption. User: "b might be redundant but its fine for now."

## Solution / Approach

Architecture today:

- **Parse time** — host parser scans paren/bracket/brace slots for `${rule.$VAR}` tokens, populates `OpInvocation.crossrefs`. Capture vs xref disambiguated by `.` in inner.
- **Lower time** — `lower_chain` wraps `Arc<dyn Op>` in `LoweredOp` with `Arc<[CrossRefOccurrence]>` from `inv.crossrefs`. `RuleFactory::parse` collects de-duped target rule names into `RuleHandle.depends_on`. `_11_dag::build` runs Kahn's; cycle → `xref/cycle` diag.
- **Runtime** — `Pipeline::run_with_step` splices `expand_xrefs(input, lop.xrefs.clone(), ...)` ahead of `op.pipe`. Adapter cartesian-products source rows from `ctx.result_store.rows_of(rule)`, dedups output tuples, seeds captures on cloned cursors. Walker constrains-when-prebound on those seeds.
- **Runner write path** — NOT YET WIRED. ResultStore is read-only at runtime today. Needs Layer 5.

## Key Insights

- **Cross-ref is universal syntax.** One framework adapter (`expand_xrefs` in `_5_op.rs`) covers every op. Ops never touch xref code. The wrapper-not-trait-method choice (`LoweredOp`) preserves this cleanly.
- **Constrain-when-prebound is the unifying mechanism.** `$VAR`, `${VAR}`, and `${rule.$VAR}` all lower to `Leaf { capture: Some(VAR) }`. The walker auto-gates against any pre-bound value. Cross-ref seeding becomes "just another way to pre-bind a capture."
- **Row-based ResultStore + cartesian + dedup beats value-set semantics.** Source rows preserve full capture maps so multi-var pulls from one source rule (`${a.$X}` and `${a.$Y}` on same op) get aligned tuples instead of independent expansions.
- **Output-candidate dedup makes the explosion guard linear in distinct seeded tuples**, not raw cartesian product. 100 source rows × 5 distinct values = 5 candidates, not 100.
- **Walker's `rule` component is purely declarative at parse time.** It feeds the DAG and `expand_xrefs.crossrefs` discovery, but the lowered `SelectStep::Leaf` only carries `var`. The seed wiring is what connects walker to source data, via `OpInvocation.crossrefs`.
- **Doc-comment heaviness was specifically requested** by the user this session. Comments on `ResultStore`, `LoweredOp`, `CrossRefOccurrence`, `OpCtx.result_store/xref_seen` cover role + lifecycle + what-it-is-NOT, not just what.

## Open Questions

- **Provenance multi-cursor seeding** — `$$repo` is per-cursor (already on Cursor.repo), but if there are 5 input cursors with 3 distinct repos, does an op with a `$$repo($R)` annotation expand cartesian across all 3 distinct repos × 5 input cursors? Or stays bound to its own cursor's repo? User earlier flagged both xref and provenance are late-bound; cartesian seems wrong here since each input cursor has exactly one repo.
- **Fork arms × xrefs** — current `Pipeline::run_with_step` runs adapter per-Pipeline::Op. Forks split before, so each arm independently expands. Probably fine, but no test covers it.
- **Cycle diag anchor** — single XRefDiag::Cycle per cycle, anchored at first rule. Should it fire one diag per rule in the cycle for better LSP UX? Or one diag with multi-site spans?
- **ResultStore concurrent writes** — current `Mutex<HashMap>` + per-rule `Mutex<Vec>`. Appears in critical path of every emitted cursor at runtime. May need lock-free upgrade (DashMap) when Layer 5 lands and runner is parallel. User memory says no new deps without asking.
- **Walker `SelectStep::CrossRef` as a real variant** — today lowering to `Leaf { capture }` works, but loses the `rule` component. If we ever want walker-level diagnostics anchored at the xref site (vs the leaf node), need a real variant.
