## Solution / Approach

### Sequencing sequential, not parallel worktrees

A (sprefa-run only) → D (trait + per-op adds) → E (new file + new
CLI flag) → B (FsOp constructor change). Sequential merge order
avoided the one collision: B changes FsOp::from_source signature,
D and the E test-scaffolding both reference it. Running B last meant
D's test already matched the new shape by the time B edited it.

### Per-seed RtCtx over multi-repo batcher

A single `FsListFilesBatcher` wraps one `Arc<dyn FileSource>`, and
`DiskFileSource` is anchored to one (root, rev). Multi-seed therefore
builds one RtCtx per seed. A `MultiDiskFileSource` dispatching on
(repo, rev) → per-seed walker is the cleaner shape but requires a
new reader type; parked.

### Config-module lives in server, not pipeline

`Config` is driver-shaped (seeds, roots, toml file layout). Keeping
it in the server crate means pipeline stays parse-agnostic and
reader-agnostic. If a future LSP wants workspace config it
re-exports `server::config` or a peer crate lifts it out. The Open
Question from the prior chat log about lowerer-location is
unanswered but the config split is settled.

### arg_spec default-empty, opt-in override

Zero churn for ops that take no args or opaque bodies. Only `fs`,
`repo`, `rev` opt in. Trait-default posture matches the existing
`language()`/`highlights()` defaults in Op so the surface reads
consistently.

### Effect caching via register_pure

Picked `register_pure::<FsListFilesEffect, _>(1024, batcher)` over
the raw `register` path. This wraps the batcher in a CacheLayer that
the effect runtime already maintains with domain-aware invalidation
(`"fs"` domain). Future `WriteBytes`/`Checkout` effects can tag
`DOMAIN = "fs"` to automatically invalidate stale listings without
the ops knowing.

## Key Insights

1. **`register_pure` earns its cache for free at call-site scale.**
   The LRU inside CacheLayer plus domain invalidation is the exact
   primitive that makes repeat `fs(...)` call-sites amortize a single
   walk across an entire sprf source. Zero op-side caching code.

2. **Trait-default-empty + per-op opt-in is the right ergonomics
   knob.** `arg_spec` joined `language`/`highlights` as a trait
   method with a default empty return. Ops that care override; ops
   that don't get zero churn. Five of eight ops needed no edit.

3. **Driver controls RtCtx shape, not the op.** With the source
   attached to the batcher at RtCtx construction (not to the op
   instance), the op becomes stateless beyond its mode. Same op
   instance runs identically across seeds; the ctx differs.

4. **Sequential over parallel when the merge surface overlaps.**
   Wave 1+2 had four tasks, two of which both touched FsOp's
   constructor / test shape. Sequential in one session zero
   merge cost; parallel worktrees would have needed a rebase pass.

5. **Hook noise vs hook correctness.** The semgrep
   post-tool-cli-scan printed blocking-shaped error traces but the
   actual file writes committed. Learned to grep-verify edits
   rather than trust the hook's "blocked" output. Later resume
   reported `Semgrep 1.157.0 (compatible)` so the token state
   self-resolved.

3. `.sprefa.toml` ancestor walk — add in the Wave 4 init_cursors
   pass or defer? Cheap to add (std::fs::canonicalize ancestors
   loop). Useful the moment smoke runs move out of `v3/`.

4. `rule(name){...}` as a registry op — once arg_spec supports a
   `Pipeline` variant the driver-level sugar can become a proper
   higher-order op. Unblocks `cache(rule(x), 1h)`.

5. `Config::seeds` vs `Vec<(repo, rev)>` at the init_cursors
   boundary. Latter is more flexible (programmatic seeds beyond
   the TOML file), former is more type-honest about where the
   data came from. Likely both via a From impl.

   parked. Drop vs keep decision when a foundational type
