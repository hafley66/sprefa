## Goal
Ship `repo.norm(...)` / `rev.norm(...)` as the fuzzy-match variants of the demand-scan annotations, on top of the aggressive normalize rewrite from the previous session. ## Current State
Shipped and committed as `2629c3d` ("aggressive normalize + .norm scan annotations"). Workspace builds clean; workspace tests all green (kitchen sink 65/65, sprf 15/15, schema 58/58, scan discovery 4/4, plus unit tests in _2_pattern and _3_lower).

## Problem/Context
Previous session finished the aggressive `normalize()` rewrite (strip non-alphanumerics, lowercase) and landed the `sprefa_config::normalize` canonical impl. Two queued items remained: a default word tokenizer floor for any text file, and `.norm` modifier on repo/rev scan annotations. User chose the `.norm` work first. The motivation: naming convention drift between config files and actual repos (`Auth-Service` in a values.yaml vs `auth_service` as the repo name) was producing spurious demand-scan targets.

## Solution/Approach
Threaded a new `norm: bool` bit through the demand-scan plumbing without changing the string-typed `scan: Option<String>` field carrier — extended the string convention to recognize `"repo.norm"` / `"rev.norm"` in addition to `"repo"` / `"rev"`, and split the suffix at the ScanTarget/ScanPair boundary.

Key design calls:
- Parser: new `Tag::RepoNorm` / `Tag::RevNorm` variants; `_1_parse::try_parse_tag` consumes optional `.norm` modifier before the `(`.
- json body: `_2_pattern::parse_pattern` recognizes `repo.norm(...)` / `rev.norm(...)` alongside the existing `repo(...)` / `rev(...)` wrappers.
- ScanAnnotation gains `norm: bool`; `_3_lower::collect_scan_annotations` + the inline-annotation loop emit `"repo.norm"` / `"rev.norm"` strings.
- `RuleTableDef::scan_targets` / `scan_pair` call a new `split_scan(raw)` helper that splits `".norm"` suffix into `ScanTarget { kind, norm }` / `ScanPair { repo_norm, rev_norm }`.
- New `sprf_norm(text)` SQLite UDF (`crates/schema/src/udfs.rs::register_sprf_norm`) calls `sprefa_config::normalize`. Registered via the existing `register_all` path on pool creation.
- `Store` trait methods `unscanned_repos` / `unscanned_revs` gain a `norm: bool` param, `unscanned_rev_pairs` gains `(repo_norm, rev_norm)`. `SqliteStore` branches the SQL between `s.value NOT IN (SELECT name FROM repos)` and `s.norm NOT IN (SELECT sprf_norm(name) FROM repos)`, and for pairs independently on each side.
- Discovery semantics: captured raw `value` is still returned as the scan target; `.norm` only loosens the "already-satisfied" filter (captures whose norm matches any known repo's norm are filtered out). Discovery stays intentionally broad for unmatched captures.

## Key Insights
- The `scan: Option<String>` field carries "repo" / "rev" / "repo.norm" / "rev.norm" — no type-signature churn across the layers. Suffix is parsed at the ScanTarget/ScanPair boundary only.
- SQLite UDF route beat adding `norm` columns to `repos` / `repo_revs`. `sprf_norm(name)` lets the SQL compare normalized forms without a schema migration or backfill. UDF registration is already wired in `migrations.rs::register_all` on pool creation, so tests that use `make_db()` get it for free.
- The `.norm` annotation is semantically a filter-loosener, not a target-rewriter: discovery still returns raw captured values, `.norm` only drops captures whose normalized form matches any known repo.
- `_1_parse::try_parse_tag` needed to carefully allow `.norm` only when followed by `(` or `[`, otherwise a glob with a dot could be mistaken for a tag.
- Kitchen sink pattern: fixture in `crates/sprf/tests/fixtures/kitchen_sink.sprf` + assertion in `crates/sprf/tests/kitchen_sink.rs` using `rule(name)` helper. Adding the two rules bumped fixture rule count naturally; `parses_without_error` threshold (`>= 35`) stayed satisfied.
