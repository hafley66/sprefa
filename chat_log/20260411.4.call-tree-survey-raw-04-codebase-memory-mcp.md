## Analysis

### Full Extraction Pipeline

The codebase-memory-mcp extraction pipeline operates in **multi-pass stages**, each with a specific responsibility. The orchestration is in `src/pipeline/pipeline.c` (main entry: `cbm_pipeline_index_repository()`), and incremental re-indexing is delegated to `src/pipeline/pipeline_incremental.c`.

#### Stage 0: File Discovery

**File:** `src/discover/discover.c`

File discovery respects three layers of ignore patterns:
1. Hardcoded: `.git`, `node_modules`, `__pycache__`, `.svn`, `vendor`, `build`, `dist`, `.next`, `.nuxt`, `target` (foundation/constants.h)
2. `.gitignore` hierarchy: Recursively walked from repo root
3. `.cbmignore`: Project-specific, gitignore syntax (discover.c, userconfig.c)

Symlinks always skipped. Result: `cbm_file_info_t` array with absolute paths and relative rel_path from repo root.

#### Stage 1: Lexical Extraction (per-file)

**File:** `src/pipeline/pass_definitions.c`, `internal/cbm/cbm.h:395`

Entry: `cbm_extract_file(source, source_len, language, project, rel_path, timeout_micros, extra_defines, include_paths)`

Returns `CBMFileResult` struct containing:
- `CBMDefArray defs` — Functions, classes, methods, enums (internal/cbm/cbm.h:235-239)
- `CBMCallArray calls` — Raw call sites extracted from AST
- `CBMImportArray imports` — Module imports with local_name and module_path
- `CBMUsageArray usages` — Variable/symbol references
- `CBMStringRefArray string_refs` — URL/config string literals from AST walk
- `CBMInfraBindingArray infra_bindings` — Topic/queue → URL from YAML/HCL/JSON configs
- `CBMChannelArray channels` — Pub/sub participation (Socket.IO, EventEmitter)
- Other arrays: `throws`, `rw`, `type_refs`, `env_accesses`, `type_assigns`, `impl_traits`, `resolved_calls`

Each language has a dedicated grammar_*.c (66 files in internal/cbm/). The grammars are vendored tree-sitter parsers (one C file per language, ~200 lines typically). Tree-sitter node kinds per language:
- **C/C++:** function_definition, declaration, call_expression
- **Python:** function_definition, class_definition, call
- **JavaScript/TypeScript:** function_declaration, method_definition, call_expression
- **Go:** function_declaration, method_declaration, call_expression
- **Rust:** function_item, impl, call_expression

Per-language extractors walk the AST and populate arrays. No explicit Locals.scm visible; each grammar implements its own scope-aware extraction.

#### Stage 2: DEFINITIONS Pass

**File:** `src/pipeline/pass_definitions.c`

Workflow:
1. For each extracted definition, compute FQN via `cbm_pipeline_fqn_compute(project, rel_path, name)` — typically `project.path.module.name`
2. Upsert node into graph buffer: `cbm_gbuf_upsert_node(gbuf, label, name, qn, file_path, start_line, end_line, properties_json)`
3. Create DEFINES edges: File → Function, Class → Method, Module → Class
4. Build registry: FQN → node_id mapping for call resolution later

Graph buffer is in-memory (internal/cbm/graph_buffer.h), later merged to SQLite.

#### Stage 3: IMPORTS Pass

**File:** `src/pipeline/pass_definitions.c`

For each extracted import, create IMPORTS edge:
- Source: File node
- Target: Module node (resolved via registry if available)
- Properties: JSON `{"local_name":"alias","module_path":"target.path"}`

These edges are critical for call resolution: import map is built by scanning IMPORTS edges and matching local names to target QNs (pass_calls.c:76-167).

#### Stage 4: CALLS Pass (Call Resolution)

**File:** `src/pipeline/pass_calls.c`

This is the core mechanism for CALLS/HTTP_CALLS/ASYNC_CALLS/CONFIGURES edges.

**Resolution Algorithm:**

1. **Extract calls** from cached result or re-parse file (pass_calls.c:347-400)
2. **Build import map** (pass_calls.c:94-167):
   - Fast path: From cached CBMFileResult.imports array
   - Slow path: Scan graph buffer IMPORTS edges, parse JSON properties
   - Result: Two parallel arrays: `local_name[]` and `target_qn[]`
3. **Resolve each call** via `cbm_registry_resolve(registry, callee_name, module_qn, imp_keys, imp_vals, imp_count)`:
   - Try importing local_name in import map → target_qn
   - Try same module (same module_qn prefix)
   - Try exact suffix match in registry
   - Return: `cbm_resolution_t` with `qualified_name`, `confidence` (0.0-1.0), `strategy` (label), `candidate_count`
4. **Classify resolved call** (pass_calls.c:275-308):
   - Check if target matches service patterns (HTTP handler, async broker, config key) via `cbm_service_pattern_match(qualified_name)`
   - If `CBM_SVC_ROUTE_REG`: Create Route node, emit HANDLES edge (route registration pattern, e.g., `app.post("/api/orders")`)
   - If `CBM_SVC_HTTP` or `CBM_SVC_ASYNC`: Extract first_string_arg as URL/topic, create Route node, emit HTTP_CALLS or ASYNC_CALLS edge
   - If `CBM_SVC_CONFIG`: Emit CONFIGURES edge (config key access)
   - Otherwise: Emit CALLS edge
5. **Emit edge** with properties JSON: `{"callee":"...", "confidence":0.92, "strategy":"import_map", "candidates":3}` or `{"url_path":"/api/users", "method":"POST", "broker":"pubsub"}`

Service patterns defined in `internal/cbm/service_patterns.c`. Examples:
- HTTP: `func_name` contains "http" + first arg is string literal starting with "/" or "://"
- Async: `func_name` matches Pub/Sub patterns (publish, emit, send to queue, Kafka producer)
- Config: Reading environment variables, config files

#### Stage 5: SEMANTIC Pass (Type-Inferred Edges)

**File:** `src/pipeline/pass_semantic.c`

For Go/C/C++ only, LSP-style type inference:
- Infer method receiver types
- Track variable assignments to types
- Enhance CALLS edges with type-dispatch confidence
- Optional per-language (Go → high confidence, C → medium)

Result: Updated CALLS edges with confidence > 0.9 for type-aware resolution.

#### Stage 6: ROUTE_NODES Pass

**File:** `src/pipeline/pass_route_nodes.c`

Post-merge: HTTP_CALLS and ASYNC_CALLS edges already populated. This pass:
1. Scans all HTTP_CALLS edges
2. For each edge with url_path + method in properties JSON:
   - Create Route node: label=Route, name=URL, qn=`__route__{METHOD}__{URL}`
   - Repoint edge target to Route node
3. Similarly for ASYNC_CALLS with broker + topic

Route nodes become first-class entities in the graph for cross-service link analysis.

#### Stage 7: TESTS Pass

**File:** `src/pipeline/pass_tests.c`

Identify test functions (is_test flag from extraction) and map them to production functions via existing CALLS edges. Create TESTS edges: test_func → production_func.

#### Stage 8: Infrastructure Scanning (IaC)

**File:** `src/pipeline/pass_infrascan.c`, `pass_k8s.c`, `pass_configlink.c`

- **Dockerfiles, Kubernetes manifests, Kustomize overlays**: Indexed as graph nodes
- **Resource nodes** for K8s kinds (Deployment, Service, ConfigMap) with CONFIGURES edges to referenced config keys
- **Module nodes** for Kustomize overlays with IMPORTS edges to included resources

#### Final: Graph Buffer → SQLite

After all passes, the in-memory graph buffer is dumped to SQLite:
```sql
INSERT INTO nodes (project, label, name, qualified_name, file_path, start_line, end_line, properties)
  VALUES (?, ?, ?, ?, ?, ?, ?, ?);
INSERT INTO edges (project, source_id, target_id, type, properties)
  VALUES (?, ?, ?, ?, ?);
```

SQLite schema (src/store/store.c, DDL section):

```sql
CREATE TABLE IF NOT EXISTS projects (
  name TEXT PRIMARY KEY,
  indexed_at TEXT NOT NULL,
  root_path TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS nodes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project TEXT NOT NULL REFERENCES projects(name) ON DELETE CASCADE,
  label TEXT NOT NULL,
  name TEXT NOT NULL,
  qualified_name TEXT NOT NULL,
  file_path TEXT DEFAULT '',
  start_line INTEGER DEFAULT 0,
  end_line INTEGER DEFAULT 0,
  properties TEXT DEFAULT '{}',
  UNIQUE(project, qualified_name)
);

CREATE TABLE IF NOT EXISTS edges (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project TEXT NOT NULL REFERENCES projects(name) ON DELETE CASCADE,
  source_id INTEGER NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  target_id INTEGER NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  type TEXT NOT NULL,
  properties TEXT DEFAULT '{}',
  UNIQUE(source_id, target_id, type)
);

CREATE TABLE IF NOT EXISTS file_hashes (
  project TEXT NOT NULL REFERENCES projects(name) ON DELETE CASCADE,
  rel_path TEXT NOT NULL,
  sha256 TEXT NOT NULL,
  mtime_ns INTEGER NOT NULL DEFAULT 0,
  size INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (project, rel_path)
);

CREATE TABLE IF NOT EXISTS project_summaries (
  project TEXT PRIMARY KEY,
  summary TEXT NOT NULL,
  source_hash TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Indexes on (project, label), (project, qualified_name), (source_id, type), (target_id, type) are implicit via prepared statements.

### Cypher-Like DSL Grammar and Execution

**File:** `src/cypher/cypher.c`, `src/cypher/cypher.h`, `tests/test_cypher.c`

#### Lexer (cypher.c:43-300)

Tokenizes Cypher input. Token types (cypher.h:21-127):

**Keywords:** MATCH, WHERE, RETURN, ORDER, BY, LIMIT, AND, OR, AS, DISTINCT, COUNT, CONTAINS, STARTS, WITH, NOT, ASC, DESC, ENDS, IN, IS, NULL, XOR, SKIP, UNION, UNWIND, SUM, AVG, MIN, MAX, COLLECT, CASE, WHEN, THEN, ELSE, END, CREATE, DELETE, etc. (recognized but unsupported write operations)

**Operators:** =, !=, <>, =~, >=, <=, >, <, .., [, ], (, ), {, }, :, ., -, *, |, ,

**Literals:** Identifiers (alphanumeric + _), strings ("..." or '...'), numbers (integers, floats)

Lexer produces token array: `cbm_token_t[]` with type, text, position.

#### Parser (cypher.c:400+)

Recursive descent parser. Produces AST:

**Pattern:** Alternating nodes and relationships:
```
node0 rel0 node1 rel1 node2 ...
```

**Node pattern** `(var:Label {prop:"value"})`:
- `variable`: optional identifier (NULL if anonymous)
- `label`: optional label (Function, Class, Module, Route, etc.)
- `props`: inline property filter array

**Relationship pattern** `-[:TYPE*1..3]->`:
- `variable`: optional
- `types`: array of edge type names (CALLS, IMPORTS, HTTP_CALLS, etc.) separated by `|`
- `direction`: "outbound" (->), "inbound" (<-), "any" (- without arrows)
- `min_hops`, `max_hops`: for *min..max syntax

**WHERE clause:** Expression tree:
```
EXPR_CONDITION (leaf)
  ├ variable.property
  ├ op: "=", "<>", "=~", ">", "<", ">=", "<=", "CONTAINS", "STARTS WITH", "ENDS WITH", "IN", "IS NULL", "IS NOT NULL"
  └ value
EXPR_AND, EXPR_OR, EXPR_NOT, EXPR_XOR (interior nodes)
```

**RETURN clause:**
- Items: variable, variable.property, COUNT(var), SUM(var), etc.
- Aliases: AS name
- Modifiers: DISTINCT, LIMIT N, ORDER BY expr ASC/DESC, SKIP N

#### Example Queries (from test_cypher.c)

```cypher
MATCH (n:Function)
```
Single node pattern, no filters.

```cypher
MATCH (f:Function)-[:CALLS]->(g:Function)
WHERE f.name =~ ".*Order.*"
RETURN f.name, g.name LIMIT 10
```
Two-node pattern with CALLS relationship. WHERE filters by name regex. Returns two columns, limited to 10 rows.

```cypher
MATCH (f:Function)-[:CALLS*1..3]->(g:Function)
```
Variable-length path: f reaches g via 1-3 CALLS edges.

```cypher
MATCH (f:Function)-[:CALLS|HTTP_CALLS]->(g)
WHERE g.label = "Route"
RETURN COUNT(f) AS callers
```
Multiple edge types, WHERE on target label, COUNT aggregation.

```cypher
MATCH (f:Function) WHERE f.name = "Foo" RETURN f.name
```
Single-node match with equality filter.

#### Executor (cypher.c:700+)

**Entry:** `cbm_cypher_execute(store, query, project, max_rows, out)`

1. Lex query string
2. Parse into AST
3. Plan query: identify variable bindings, join strategy
4. Execute against SQLite:
   - For each MATCH clause: Build SQL SELECT with JOINs on nodes/edges tables
   - WHERE conditions: Translate to SQL WHERE clauses (regex =~ becomes REGEXP, CONTAINS becomes LIKE, etc.)
   - RETURN items: Project columns, apply aggregates (COUNT, SUM, AVG, MIN, MAX, COLLECT)
   - ORDER BY, LIMIT: Standard SQL
5. Collect rows into `cbm_cypher_result_t` (columns + rows array)

Key insight: **No custom query engine**. Cypher is translated directly to SQL with SQLite operators:
- Regex =~ → SQLite REGEXP function (requires compilation with regex support)
- CONTAINS → LIKE '%substring%'
- Joins: `nodes n1 JOIN edges e ON e.source_id=n1.id JOIN nodes n2 ON e.target_id=n2.id`

#### Supported Subset

Supported:
- MATCH with labels, properties, variable-length paths
- WHERE with AND/OR/NOT/XOR, comparisons, regex, CONTAINS, IN
- RETURN with projection, aggregates (COUNT, SUM, AVG, MIN, MAX, COLLECT), DISTINCT, AS aliasing
- ORDER BY column ASC/DESC
- LIMIT/SKIP for pagination
- OPTIONAL MATCH (soft dependencies)
- WITH for intermediate results (chained queries)
- UNION (UNION/UNION ALL)
- UNWIND for list expansion

Unsupported (recognized but return error):
- CREATE, DELETE, DETACH, SET, REMOVE, MERGE (write operations)
- FOREACH, CALL procedures
- Complex path predicates (WHERE on relationship properties only via edge.properties JSON parsing)

### Edge-Kind Taxonomy

**File:** src/pipeline/pass_calls.c, src/store/store.h, README.md:325

Complete edge types:

1. **CALLS** — Direct function/method call. Properties: `{"callee":"name", "confidence":0.92, "strategy":"import_map", "candidates":3}`
2. **HTTP_CALLS** — REST endpoint invocation. Properties: `{"callee":"...", "url_path":"/api/users", "method":"GET", ...}`
3. **ASYNC_CALLS** — Message queue/pub-sub send. Properties: `{"callee":"...", "url_path":"topic.name", "broker":"pubsub", ...}`
4. **CONFIGURES** — Config key read/write. Properties: `{"callee":"...", "key":"db.host", "confidence":0.85}`
5. **CONTAINS_PACKAGE** — Package structural. Source: Project, Target: Package
6. **CONTAINS_FOLDER** — Folder containment. Source: Folder, Target: Folder
7. **CONTAINS_FILE** — File containment. Source: Folder, Target: File
8. **DEFINES** — Entity definition. Source: File, Target: Function/Class/Method/etc.
9. **DEFINES_METHOD** — Method definition. Source: Class, Target: Method
10. **IMPORTS** — Module import. Source: File, Target: Module. Properties: `{"local_name":"alias","module_path":"target.path"}`
11. **IMPLEMENTS** — Class implements interface. Source: Class, Target: Interface
12. **HANDLES** — Route handler mapping. Source: Handler function, Target: Route node
13. **USAGE** — Variable/symbol usage. Source: Function, Target: Variable
14. **WRITES** — Variable write. Source: Function, Target: Variable
15. **MEMBER_OF** — Class membership. Source: Field/Method, Target: Class
16. **TESTS** — Test function. Source: Test function, Target: Production function
17. **USES_TYPE** — Type reference. Source: Function, Target: Type/Class
18. **FILE_CHANGES_WITH** — Co-changing files (git historical analysis). Source: File, Target: File

### How 66 Languages Are Supported

**File:** internal/cbm/cbm.h:11-80, internal/cbm/grammar_*.c (66 files)

Each language compiled as a separate translation unit (grammar_c.c, grammar_python.c, etc.). Each includes the vendored tree-sitter parser.c:

Each grammar_*.c also exports per-language extraction functions (implicit via the module system):

Example extraction path (C):
1. `ts_parser_parse_string()` → TSTree
2. Walk root → function_definition nodes
3. For each function_definition: extract name, signature, line range
4. Emit CBMDefinition, add to CBMDefArray
5. For each call_expression child: extract callee_name, args, emit CBMCall

The 66 languages cover most mainstream + scientific + IaC languages. Tier scoring (README.md:400-406):

### MCP Server Interface

**File:** src/mcp/mcp.c, src/main.c

MCP tool definitions (mcp.c, tool list):

1. **index_repository** — Trigger indexing of a directory
2. **search_graph** — Structured search by label, name pattern, file pattern, degree filters
3. **query_graph** — Cypher query execution
4. **trace_path** — BFS traversal (who calls, what calls)

### Incremental Indexing Model

**File:** src/pipeline/pipeline_incremental.c

Operates on existing SQLite DB (disk-backed).

**Workflow:**

1. Load stored file_hashes table for the project
2. Discover current files on disk
3. Classify via mtime+size comparison (pipeline_incremental.c:76-121):
   - New files (not in stored hashes): mark as changed
   - Unchanged: mtime_ns and size match stored values
   - Changed: mtime_ns or size differ, or file deleted on disk
4. Delete nodes for changed files (cascades edges via ON DELETE CASCADE)
5. Re-parse only changed files through multi-pass pipeline
6. Merge new nodes/edges into disk DB using REPLACE or INSERT
7. Update file_hashes with new mtime_ns + size

**Advantages:**
- No git operations required (portable to any VCS or non-VCS usage)
- File metadata comparison is O(file_count) with hash table lookup
- Unchanged files' graph data untouched (efficient)
- Deleted files handled via cascade delete

**Limitations:**
- Does not detect branch changes (always assumes working directory = true source)
- mtime can be unreliable on some filesystems (but size collision is rare)

### Partial Call Tree Expressions in DSL

**File:** src/cypher/cypher.h:164-172, tests/test_cypher.c:222-248

Variable-length paths enable partial tree expression:

```cypher
MATCH (root:Function {name:"main"})-[:CALLS*1..5]->(leaf:Function)
RETURN DISTINCT leaf.name
```

This captures all functions reachable from `main` via 1-5 hops in the call graph.

**Depth filtering via RETURN:**
```cypher
MATCH path = (f:Function)-[:CALLS*]->(g:Function)
RETURN f.name, g.name
LIMIT 100
```

**BFS traversal tool** (trace_path):
```
trace_path(function_name="main", direction="outbound", depth=3)
```

Returns visited nodes + hop counts, enabling partial reconstruction of call trees up to depth N.

**Community clustering** (get_architecture):
Runs Louvain clustering on the CALLS graph to identify functional modules (isolated component subgraphs).

### Key Implementation Details

1. **Memory management during indexing:**
   - Graph buffer allocated on heap (arena allocator in foundation/arena.h)
   - Input files read and parsed in LZ4-compressed chunks
   - Parse trees freed immediately after extraction (TSNode lifetime scoped to pass)
   - Result: Peak RAM = ~2-3x largest file, not cumulative

2. **Confidence scoring in call resolution:**
   - Registry lookup returns confidence 0.0-1.0 based on strategy:
     - import_map: 0.95 (direct import match)
     - same_module: 0.90 (no ambiguity)
     - suffix_match: 0.70 (multiple candidates)
     - unresolved: 0.0 (no target found)

3. **Property JSON in edges:**
   - Stored as TEXT in SQLite `edges.properties`
   - Parsed on-demand in queries (no jsonb indexing)
   - Custom JSON escape function: `cbm_json_escape()` for embedded quotes

4. **File path canonicalization:**
   - All file_path values are relative to repo root
   - FQN computed as `project.rel_path_with_slashes_to_dots.entity_name`
   - Example: `myproj.src.handlers.process_order` (file: src/handlers.js, function: process_order)

5. **Test detection:**
   - Extraction marks `is_test` flag on functions matching pattern:
     - Name contains "test", "Test", "TEST", "_test", "test_"
     - File path contains `_test.`, `.test.`, `_spec.`, `spec/`
     - Language-specific: pytest decorator @pytest.mark, JUnit @Test, etc.
