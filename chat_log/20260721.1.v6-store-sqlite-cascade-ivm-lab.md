# Session: v6-store-sqlite-cascade-ivm-lab

## Goal
Feasibility lab (NOT the v5 `dl` engine, NOT the 9-table spine): prove that an
on-disk SQLite weight-cascade can do Feldera-style Z-set retraction/IVM over code
facts with DELTA-PROPORTIONAL work and BOUNDED memory, avoiding the resident
35GB-swap death that killed v5. Head-to-head vs the resident IVM engines
(differential-dataflow, DBSP/Feldera) for correctness + speed + the memory-wall.
Crate lives at `v6/sprefa-store/`.

## Current State (all green)
- 4 engines byte-identical on a 3-relation graph vs an independent BFS oracle:
  sqlite-mem, sqlite-disk, dd (0.25), dbsp (0.323). Enforced in tests/head_to_head.rs.
- Retract OPTIMIZED: 5M nodes / 250k killed: 2.26s -> 1.90s (one txn) -> 1.28s
  (soft-delete + transition guard, NO DELETEs). 29 stmts / 3 rounds, delta-proportional
  (~0.009 ms/killed, flat across scale). dd/dbsp retract ~290ms (still ~4x faster, resident).
- WALL PROVEN: 1500MB budget @ 5M nodes -> sqlite COMPLETES, dd AND dbsp both ABORT (exit 134).
- SQLite stretched solo to 10M nodes (retract 5.4s, setup 27s->8.5s after txn+CHUNK=4000).
- Datalog ops suite green small: join, union+distinct, antijoin/negation, agg(group+count),
  3-way join, recursion (tests/datalog_ops.rs, SQLite vs Rust oracle).
- WITH RECURSIVE recompute MEASURED + REJECTED: byte-identical but path-explosion,
  720x slower @16k (6.4s vs 8.9ms), timeout @50k+. Kept as examples/sqlite_recursive.rs baseline.
- memcap: counting #[global_allocator] (setrlimit is a NO-OP on macOS, proven) that
  aborts past a heap cap instead of swapping. tests/memcap.rs (4 tests) green.

## Solution/Approach
- cx_row(tag,id,weight) PK WITHOUT ROWID; cx_dep(4-tuple) PK WITHOUT ROWID (prefix-ordered
  parent... for delta traversal); cx_frontier/cx_next/cx_hits working tables.
- Delta-proportional retract: per round build cx_hits (frontier CROSS JOIN cx_dep, GROUP BY
  child), UPDATE weights (IN-list from tiny cx_hits), cx_next = transition-crossers
  (weight<=0 AND weight+dec>0). CROSS JOIN forces small-drives-big (no stats on transient tables).
  Verified via EXPLAIN QUERY PLAN: every step SCAN<small> -> SEARCH<big> USING PRIMARY KEY.
- Soft-delete: dead rows stay at weight<=0, survivors = weight>0 (killed both big DELETEs).
- dropped now-dead cx_dep_by_child index; whole retract + inserts in ONE transaction (max_connections=1).

## Key Insights
- The whole thesis in one measurement: weight cascade is delta-proportional + node-oriented
  (work ∝ change); WITH RECURSIVE is recompute + path-oriented (720x slower, path explosion on fan-in).
- setrlimit does NOT bite on macOS (RLIMIT_AS no-op, RLIMIT_DATA bypassed by mmap malloc) —
  proven empirically; the counting global allocator is the real guardrail.
- peak RSS at scale is INPUT-dominated (all engines build same edge vecs) -> the memcap
  heap-budget WALL is the trustworthy memory signal, not RSS.
- transaction wrapping barely helped retract (only 35 stmts); the big win was removing DELETEs
  from WITHOUT ROWID b-trees (soft-delete + transition guard = each node dies once).
- survivor-set ≡ reachability-from-surviving-roots (proven) — but the DELTA (who dies) needs
  COUNT aggregation which recursive CTE forbids, so CTE can only recompute, not do incremental cascade.
