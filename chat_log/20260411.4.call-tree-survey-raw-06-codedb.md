## Analysis

codedb is a pure-Zig code intelligence server with zero GC and no parser library dependencies. It trades deep syntax understanding for speed via three indexing layers:

### Parser Strategy
codedb eschews tree-sitter bindings entirely. Instead, it implements **custom line-by-line regex/string-matching parsers** in Zig for 12 languages. Each language has a dedicated parse function (parseZigLine, parsePythonLine, parseTsLine, etc.) at `/Users/chrishafley/projects/ext/codedb/src/explore.zig:357-391`. Pattern matching is hand-rolled: `startsWith(line, "pub fn ")`, `extractIdent()`, `extractStringLiteral()`. This avoids FFI overhead but misses multi-line constructs and full syntax tree shape.

### Call Extraction
**No call-graph extraction exists.** The tool only extracts:
- **Symbols** (functions, structs, enums, imports, classes) with line ranges
- **Imports** (file-level dependencies) via regex on import statements
- **Enclosing scope** for search results (which symbol contains line N)

The dependency graph is stored in `explorer.dep_graph: StringHashMap<ArrayList<[]const u8>>` at `/Users/chrishafley/projects/ext/codedb/src/explore.zig:131`. It maps file path → import paths only. See `rebuildDepsFor()` at line 1738: it iterates `outline.imports` and builds an adjacency list.

### Storage Format
Two storage modes:

1. **In-memory**: StringHashMap of `FileOutline` structures (path, language, symbols, imports).
2. **Disk snapshot** (`.codedb` binary, format v2):
   - Header: magic "CDB\x01", version u16, flags, git HEAD SHA, section count (52 bytes reserved)
   - Section table: each section has ID (u32), offset (u64), length (u64)
   - Sections: TREE (JSON file list), OUTLINE (legacy JSON), CONTENT (file bodies), FREQ (256x256 trigram histogram), META (JSON metadata), OUTLINE_STATE (binary symbol state)
   - See `/Users/chrishafley/projects/ext/codedb/src/snapshot.zig:6-46` for format spec.

Trigram and word indices can optionally cache to disk at `~/.codedb/projects/{hash}/trigram.index` and `word.index` for warm startup.

### Source-Order Preservation
Yes. Every symbol records `line_start: u32, line_end: u32`. The Explorer walks lines sequentially during indexing. The trigram index uses `DocPosting { doc_id: u32, loc_mask: u8 }` to track position within documents. See `/Users/chrishafley/projects/ext/codedb/src/index.zig:420-424`.

### Language Support
12 languages detected by file extension at `/Users/chrishafley/projects/ext/codedb/src/explore.zig:101-116`. Each has a language-specific parse function. For example:
- **Zig** (line 1034): matches `pub fn `, `const `, `test `, checks for `struct {`, `enum {`, imports
- **Python** (line 1098): `def `, `class `, `import `, docstring handling
- **TypeScript/JavaScript** (line 1162): `function `, `const `, `class `, `export`
- **Rust** (line 1216): `fn `, `pub fn `, `struct `, `impl `, attributes
- **PHP** (line 1306): class/method tracking with brace depth
- **Go** (line 1370): `func `, `import (`, type declarations
- **Ruby** (line 1428): `def `, `class `

All use line-level regex. No incremental parsing across scope boundaries.

### Interop Model
Three surfaces:

1. **MCP (primary)**: JSON-RPC 2.0 over stdio. Exposes 16 tools (codedb_tree, codedb_outline, codedb_symbol, codedb_search, codedb_word, codedb_deps, codedb_read, codedb_edit, codedb_changes, codedb_status, codedb_snapshot, codedb_bundle, codedb_remote, codedb_projects, codedb_index). Implemented in `/Users/chrishafley/projects/ext/codedb/src/mcp.zig`.
2. **HTTP**: Daemon on localhost:7719. Routes include /tree, /outline, /symbol, /search, /word, /hot, /changes. See `/Users/chrishafley/projects/ext/codedb/src/server.zig`.
3. **CLI**: Commands `codedb tree`, `codedb outline`, `codedb find`, `codedb search`, `codedb word`, `codedb hot`, `codedb serve`, `codedb mcp`.

All use native Zig JSON serialization (no external JSON lib). MCP startup registers as singleton with PID lock + 10min idle timeout.

### Index Architecture
Three concurrent indices:

1. **Trigram Index** (`TrigramIndex` at `/Users/chrishafley/projects/ext/codedb/src/index.zig:511-532`):
   - Maps u24 trigram → PostingList (sorted vec of DocPosting { doc_id, next_mask, loc_mask })
   - Supports mmap-backed variant (`MmapTrigramIndex`) for large repos
   - Enables substring search: extract query trigrams, intersect posting lists, verify with regex
   - Benchmarks show 1,340x speedup vs ripgrep on warm corpus

2. **Word Index** (`WordIndex` at line 12-401):
   - Inverted index: word → vec of (path, line_num) hits
   - O(1) lookup via StringHashMap
   - Persists to disk as binary (file table, word list, hit list with doc ID + line)
   - Deduplicates by (path, line_num)

3. **Sparse N-gram Index** (`SparseNgramIndex`):
   - Mentioned but not detailed; likely for larger pattern matching

### Edit Tracking
`Store` at `/Users/chrishafley/projects/ext/codedb/src/store.zig` maintains:
- `files: StringHashMap<FileVersions>` (per-file version history, capped at 100)
- `seq: atomic u64` (global monotonic version counter)
- `data_log: File` (append-only diff log)

Each edit records `{ seq, agent, op (snapshot|insert|replace|delete|tombstone), hash, size, data_offset, data_len }`.

### Incremental Indexing
- `indexFile()` → full index (outline + word + trigram)
- `indexFileOutlineOnly()` → skip word/trigram (fast snapshot restore)
- `indexFileSkipTrigram()` → outline + word, trigram deferred
- `rebuildTrigrams()` and `rebuildWordIndex()` → lazy rebuild from content cache

Watcher polls files and enqueues changes. Edit API applies line-range ops atomically with version tracking.

### No Call Graph
The tool extracts **zero call edges**. It only knows:
- What symbols exist in each file
- What files import what modules
- What text appears where (via trigram search)

It cannot answer "who calls this function?" or "what is the data flow through this code?". This is by design—the tool is targeted at AI agents needing fast structural lookup + search, not static analysis.
