## Design decisions locked this session

### Effects split from pipe ops
- **Reads = pipe ops.** `read` enriches the cursor (`cursor.content`).
  Downstream ops filter/transform against it. Same shape as any other
  cursor enrichment.
- **Writes ≠ pipe ops.** Writes are effects. Future model: effect-ops
  push onto `cursor.effects: Vec<Effect>` and pass cursor through. A
  separate flush phase after the pipeline drains applies them via
  `CheckoutRegistry` + worktree provisioning. Reasons:
  - dry-run/preview mode via suppressing flush (keeps pipe pure);
  - atomicity (no half-written state on pipeline error);
  - batching / dedup across cursors (multi-writer to same file);
  - checkout-registry lookup is infrastructure, not cursor data.
- Effect enum shape (sketch):
  ```rust
  enum Effect {
      WriteFile { path: Arc<str>, content: Arc<Bytes> },
      EditFile  { path: Arc<str>, edit: Edit },
      Notify    { message: Arc<str> },
  }
  ```

### Read scheduling — what Reader owns, what Runner owns
- **Reader owns dedup.** `shareReplay(1)` keyed `(repo, rev, file)` for
  in-flight coalescing. Same (repo,rev,file) asked by N concurrent ops
  → 1 blob read.
- **Runner owns pass ordering.** Pass A (discovery: `fs/repo/rev`) then
  Pass B (extraction: `bytes/parsed`). §11 of `v2/README.goals.md`.
- **`unscanned()`** is the pre-warm signal from Runner to Reader. Still
  `unimplemented!()` in `GitBlobReader` — lands with the Runner.
- **Op::pipe is oblivious.** Ops just call `ctx.reader.bytes(...).next().
  await`. Batching, caching, prefetch, buffer overlay, WT overlay — all
  Reader-side concerns invisible to ops.

### Composable sub-pipes interact with the 2-pass model
- 2-pass is an **optimization for the flat case**, not a hard contract.
- Correlated sub-pipes (where sub-pipe's fs(...) depends on parent's Pass
  B output) can't pre-warm; fall back to on-demand reads.
- What holds: the Reader cache key `(repo, rev, file)` — nested levels
  share the same dedup regardless of topology.
- Pass ordering becomes per-level, falls out of stream topology without
  explicit Runner logic.

### Memory budget on 16GB
- `Arc<Bytes>` on `cursor.content` → drops when cursor drops at sink.
  No persistent Reader cache needed for raw bytes.
- Git2 blob read cost: mmap'd pack file → OS page cache → memcpy to
  new heap `Bytes`. Re-read of same file is warm if pages still cached.
- **Page cache thrashing at 500 repos on 16GB is real.** Can't hold all
  pack files simultaneously. Mitigation: **sequential repo processing**
  (not 500-way fan-out). Process repo 1 fully → drop content → move on.
- **Fork's `block_on(input.collect())`** is a buffering hazard. Currently
  only materializes metadata cursors (no content yet at fork time — that
  comes from `read` downstream). Keep it that way; never buffer cursors
  carrying content.
- **`parsed()`** (tree-sitter) is where a bounded LRU by content_hash
  matters. Raw bytes: skip the cache, re-read.

### Reader caching guidance
- **Now:** no cache. `GitBlobReader::bytes` does fresh lookups.
- **Next:** in-flight dedup via `HashMap<(repo, rev, path),
  Shared<Future>>` when concurrent ops start hitting the same file.
- **Later:** pre-warm via `unscanned()` + `madvise(MADV_WILLNEED)` if
  profiling shows disk-IO on hot path.

### Async / runtime / parallelism
- Reader trait already async-shaped (`BoxStream<'static, _>`). Ops
  already `Send + Sync`. Cursor already `Clone`. Future-ready.
- Current `block_on` sites all live in Runner-equivalent glue (RuleOp
  seed, Fork replay, test driver). They vanish when the Runner lands.
- Real parallelism plan (when Runner is written):
  1. tokio multi-thread runtime.
  2. Replace Fork's collect-then-replay with `tokio::sync::broadcast` +
     `futures::stream::select_all` for arm merge.
  3. `buffer_unordered(N)` on IO-heavy streams for concurrent op exec.
  4. `spawn_blocking` around git2 (worth it only for expensive work,
     not cheap blob reads — roughly >100µs inner work).
  5. Rayon thread pool for CPU-bound op bodies (tree-sitter, hashing).
  6. Bounded channels everywhere for backpressure.
- Op trait, op bodies, Reader trait, Cursor — none change when this
  lands. Only the Runner glue.

### Ghcacher decoupling + `$wt` overlay
- `CheckoutLocator` trait is the seam. 3 impls planned:
  - `ConfigLocator` (current) — static toml.
  - `GhcacheLocator` (behind `ghcache` cargo feature) — wraps
    `ghcache_client::Client::checkouts()`. ChangeEvent subscription
    for invalidation.
  - `DaemonLocator` — future.
- `$wt` rev-name suffix (not `:wt`, not an operator). Safe because git
  refnames reject `$`. Live WT overlays base rev via per-file git2
  `StatusOptions` classification: dirty → disk, clean → delegate to base
  Reader.
- LSP `BufferOverlay` sits on top of WT overlay. Same interface; invisible
  in CLI runs.
- Writes auto-provision `git worktree add /sprf/worktrees/{repo}/{rev}`
  on missing registry entry, emit `RunEvent::WorktreeProvisioned`.
  `$wt` writes gated behind `write[allow=wt]`.
