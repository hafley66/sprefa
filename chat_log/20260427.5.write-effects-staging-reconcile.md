## v1 write model (RIP)

**One-line:** No write/refactor effects. v1 is extraction + SQLite indexing only.

**Why it's dead:**
- Scope was query-extraction into rule tables + cross-repo xref resolution (cache/extract/rules/sprf).
- Write mechanics never landed. Project pivot from "automatic refactor engine" → "causal linking engine" made v1 obsolete.
- All writes funneled through shell escape hatches + manual user edits. No structured effect types.

**What's worth lifting:**
- SQLite schema / per-rule table shape from `schema/` + `RuleTableSpec` / `ColumnKind` enum — v2 ported this.
- Transactional batching model (flush entire batch or nothing). v2's `Writer::rewrite_files` + `Writer::shell_batch` follow the same atomic-by-run-phase discipline.

**Key files (gone):**
- `crates/{extract, rules, schema, sprf}` — extraction + index, no writes.
- No `_4_writer.rs` equivalent. v2 added it from scratch.

## v2 write model (landed, Phase 2 incomplete)

**One-line:** Reads as pipe ops; writes/edits/mutations as deferred effects queued on cursor, flushed after pipeline drain.

**Architecture (from `project_v2_effects_split.md`):**
- Effects attach to `Cursor.effects: Vec<Effect>` (not yet; Phase 2 will add).
- Op::pipe returns early; mutation ops send on `OpCtx.mutations` mpsc instead.
- `MutationHandler` (trait) consumes the mpsc: `AutoApprove` (tests), `InteractiveCli` (CLI), `LspPromptBridge` (LSP).
- Approval is binary: one `oneshot::Sender<Approve>` per mutation. Handler prompts, sends `Yes/No`, framework routes approval to the op.
- **Phase 2 target:** Merge approval with dry-run buffer phase (inspect the effect's preview before applying).

**Effect types (v2/src/_4_writer.rs):**
```rust
pub struct FileEdit {
    pub repo, rev, fs, byte_range, replacement, kind, parse_id
}
pub struct ShellCall { ... }
pub enum EffectStatus { Ok, Err, Pending }
```
Phase 2 will refactor to one writer trait method per effect kind.

**Reads vs writes split (locked, `project_v2_effects_split.md`):**
| Layer | Role |
|---|---|
| Pipe ops | Reads only; enrich cursor |
| Mutation ops | Queue effects on mpsc; frame approves/rejects per channel |
| Post-drain flush | `Writer::rewrite_files(edits)`, `Writer::shell_batch(calls)` |
- Dry-run = skip flush phase. Entire pipeline unchanged.
- Atomicity = flush transactional per batch.

**$wt overlay + auto-worktree (`project_v2_wt_overlay.md`):**
- Rev suffix `{base}$wt` for working-tree overlay.
- Reader stack (3 layers):
  1. `GitBlobReader` — git2 against object DB (any rev, no checkout).
  2. `WorkTreeOverlay` — for `$wt` revs; git2::StatusOptions classifies per-file.
  3. `BufferOverlay` — LSP open-buffer map `(repo, rev, path) → Bytes`.
- `CheckoutLocator` trait decouples path resolution.
- **Write-side:** `CheckoutRegistry` auto-materializes missing `(repo, rev)` via `git worktree add` on first write attempt.
- Gating: `write[allow=wt]` bracket required to write user's live checkout; `write[allow=mirror]` to overwrite daemon-synced rev.

**Conflict resolution (v2, not yet coded):**
- Overlapping byte-ranges in one file → error or merge-strategy (TBD; probably Conflict diag).
- Two effects targeting same `(file, byte_range)` → detected at flush, error on de-prioritized one.
- Ordering: applied in cursor-sequence order (deterministic per pipeline run).

**Key files:**
- `v2/src/_4_writer.rs:RuleTableSpec, FileEdit, ShellCall, Writer trait`.
- `v2/src/mutations.rs:MutationRequest, MutationEffect, MutationHandler, await_approval`.
- `v2/src/readers/` — Reader trait family (GitBlobReader, WorkTreeOverlay, BufferOverlay).

**Open: Phase 2 will**
- Wire `Writer::rewrite_files` + `Writer::shell_batch` bodies.
- Add `MutationEffect::preview_markdown()` for LSP code-action context.
- Merge approval + dry-run: buffer writes before asking, show diff/shell-output preview.
- CheckoutRegistry + auto-$wt materialization.

## v3 today (landed, Phase 1)

**Core doctrine:** Reads and writes both dispatch through `RtCtx.put(Effect).await` → `Batcher<E>`.

**Effect shapes (v3/crates/pipeline/src/effects.rs):**

| Effect | Response | Sink | Pure | Domain |
|---|---|---|---|---|
| `FsListFilesEffect` | `Vec<Arc<Path>>` | FileSource | Yes | "fs" |
| `ReadBytesEffect` | `Option<(Arc<[u8]>, hash?)>` | FileSource | Yes | "fs" |
| `ReadBytesBatchEffect` | `Vec<ReadResponse>` | FileSource+rayon | Yes | "fs" |
| `PrintEffect` | `()` | Stdout/Buffer | No | N/A |
| `WriteFileEffect` | `Result<(), Arc<str>>` | Disk/Buffer | No | (future "fs") |
| `WriteRangeEffect` | `Result<(), Arc<str>>` | Disk/Buffer+Mutex | No | (future "fs") |
| `AstParseEffect` | `Arc<AstGrep>` | BoundedWorkSteal | No | N/A |
| `Yield<S>` | `Result<Arc<S::Payload>, Unsubscribed>` | SubjectRegistry | No | N/A |

**Sink duality (design pattern all write effects):**
```rust
pub enum WriteFileSink {
    Disk,
    Buffer(Arc<Mutex<Vec<...>>>),
}
pub struct WriteFileBatcher {
    sink: WriteFileSink,
}
```
Test-time: register with `WriteFileBatcher::buffer()` → get `Arc<Mutex<Vec<...>>>` to inspect after run.
Live: register with `WriteFileBatcher::disk()` → writes hit filesystem immediately.

**Yield primitive (effect_runtime/subjects.rs, locked 2026-04-26):**
- Op calls `ctx.put(Yield::<S> { key, lineage }).await` and suspends.
- Outside code drives `registry.next(key, value)` to resume, or `registry.unsubscribe(key)` to cancel.
- Vocab: Yield / Next / Unsubscribe (RxJS lineage, no "park"/"wake").
- Lineage tag (boxed `Any`) allows bulk `unsubscribe_where(predicate)` on cursor invalidation.
- **Three planned consumers:** parked-write effects (RelationWake), tag-subscribe, Pending captures.

**How v3 runs today (v3/crates/server/src/run.rs:288):**
```rust
fn build_seed_ctx(...) -> RtCtx {
    RtCtxBuilder::new()
        .register_pure::<FsListFilesEffect, _>(FsListFilesBatcher::new(...))
        .register_pure::<ReadBytesEffect, _>(ReadBytesBatcher::new(...))
        .register::<WriteFileEffect, _>(WriteFileBatcher::disk())
        .register::<WriteRangeEffect, _>(WriteRangeBatcher::disk())
        .register::<Yield<RelationWake>, _>(YieldBatcher::new(subject_registry.clone()))
        .build()
}
```
**Today:** WriteFile/WriteRange go straight to disk. No approval loop.

**What's parked (not wired yet):**
- Buffer batcher for `WriteFileEffect` / `WriteRangeEffect` (code exists, unused).
- `RelationWake` (Yield payload) type + Relation store (partial stubs in spine/).
- Approval/staging loop: inspect buffer before flush.
- `write_cursor!` / `write_file!` bang variants (syntax not parsed yet).

## Reconciled design: stage→approve→commit

**Design intent:**
- `write` (default): queue to buffer batcher, await `Yield<RelationWake>` from external approval.
- `write!` (bang): skip buffer, direct to `WriteRangeBatcher::disk()` or `WriteFileBatcher::disk()`.
- Buffer batcher collects writes + diff-previews them.
- LSP/CLI host inspects buffer and fires `registry.next(key, Approve)` or `registry.unsubscribe(key)` to reject.

**Stage phase (inside op, before Yield):**
- Op creates `WriteRangeEffect` or `WriteFileEffect` with full metadata.
- Op gets `SubjectKey<RelationWake>` from `cx.store::<SubjectRegistry<RelationWake>>().fresh_key()`.
- Op calls `cx.put(WriteRangeEffect { ... }).await` → hits buffer batcher.
- Buffer batcher (registered as `WriteRangeBatcher::buffer()`) accumulates into `Arc<Mutex<Vec<...>>>`.
- Batcher returns `Ok(())` immediately (buffered, not yet applied).
- Op then calls `cx.put(Yield { key, lineage: Some(cursor_lineage) }).await`.

**Approve phase (outside op, in host):**
- Host drains all ops. Buffer batchers now hold full write collections.
- Host calls `buffer.lock().unwrap()` on each sink to inspect.
- Host builds a summary: "edit A at file:L, edit B at file:M, would conflict? yes/no".
- Host prompts user (LSP code-action, CLI stdin, or AutoApprove).
- Host drives `registry.next(key_a, ())` to approve (op resumes), or `registry.unsubscribe(key_a)` to reject (op errors).

**Commit phase (inside op, after Yield):**
- Op's `Yield` resolves `Ok(())`.
- Op resumes: "approval granted, now commit to actual sink".
- Op calls `cx.put(WriteRangeEffect { ... }).await` again, but this time on a `WriteRangeBatcher::disk()`.
- **Alternative:** After Yield, op doesn't re-put; the host (post-approval) iterates the approved buffer and flush-applies them all at once via a bulk `WriteFinalBatcher`.

**Data flow diagram:**
```
Cursor → Op
         │
         ├─ read_bytes (→ cache, pass cursor through)
         ├─ re/ast/json match (→ emit captures, narrow cursor)
         │
         ├─ write_cursor(target_cursor) [default: staged]
         │  │
         │  ├─ Step 1: ctx.put(WriteRangeEffect) → WriteRangeBatcher::buffer()
         │  │  Returns: Ok(()) — buffered, not yet on disk
         │  │
         │  ├─ Step 2: key = registry.fresh_key()
         │  │  ctx.put(Yield { key, lineage: cursor_lineage }).await
         │  │
         │  └─ Suspends: awaiting external approval
         │
         └─ Or: write_cursor!(target_cursor) [bang: unconditional]
            │
            └─ ctx.put(WriteRangeEffect) → WriteRangeBatcher::disk()
               Returns: Ok(()) — immediately on disk, no approval

Pipeline drain:
  │
  ├─ All ops exit (including those parked on Yield)
  │
  └─ Host (LSP server / CLI runner / test harness)
     │
     ├─ Inspect buffer sinks: buffer.lock().unwrap() per WriteRange/WriteFile effect
     │
     ├─ Diff-preview / conflict check:
     │  ├─ WriteRangeEffect (a, file, byte_range_1, new_bytes_a)
     │  ├─ WriteRangeEffect (b, file, byte_range_2, new_bytes_b)
     │  └─ Overlap check: [1.start, 1.end) ∩ [2.start, 2.end) ≠ ∅ → Conflict diag
     │
     ├─ Present diff to user:
     │  ├─ LSP: code-action or textDocument/edit (v3 future)
     │  ├─ CLI: pretty-printed diff, "Apply? [y/N]"
     │  └─ Test: AutoApprove → implicitly yes
     │
     ├─ On approval:
     │  └─ registry.next(key_a, ()), registry.next(key_b, ()), ...
     │     → ops resume from Yield, exit cleanly
     │
     └─ On rejection:
        └─ registry.unsubscribe(key_a), ...
           → ops resolve Err(Unsubscribed), unwind (or catch + exit cleanly)
```

## Conflict resolution rules

**Overlapping byte-ranges in same file:**
```rust
fn detect_overlap(edits: &[WriteRangeEffect]) -> Vec<(usize, usize)> {
    // Group by file
    // For each file, sort edits by byte_range.start
    // Check consecutive pairs for range overlap
    // Return conflict indices
}
```
**Resolution:**
- Two edits with overlapping ranges in the same file → emit `Conflict` diagnostic.
- User must either:
  - Reorder the ops so they don't overlap (adjust regex, narrow cursor).
  - Manually merge the intended changes and re-run.
  - Use `:wrap` mode to layer multiple edits (planned; needs spec).
- No silent rebase or auto-merge (too easy to corrupt).

**Ordering:** Edits within a file applied in `byte_range.start` order (ascending). This is stable per run; ops execute in deterministic order.

**Cross-file:** No ordering constraints. Multiple files can be written in parallel post-approval (future: par_iter on approved buffer).

**Write→Read freshness:** WriteRange/WriteFile tagged with domain "fs" (future). Cache-invalidate matching FsListFilesEffect + ReadBytesEffect keys when approval fires.

## Surface syntax

**Grammar additions (v3/crates/sprefa_parse/parse.md):**

Current:
```
op_invocation := IDENT [ paren_slot ]
paren_slot := '(' [ arg_expr { ',' arg_expr } ] ')'
```

Proposed:
```
op_invocation := [ '!' ] IDENT [ paren_slot ]
                                ↑
                          bang sigil (optional)
```

Examples:
```sprf
write($TARGET)          # default: stage to buffer, await approval
write!($TARGET)         # bang: bypass buffer, direct to disk

write_file($PATH)       # stage to buffer
write_file!($PATH)      # bang: direct to disk

write_cursor($C)        # stage
write_cursor!($C)       # direct
```

**Lowering (host_parse → host grammar):**
- Parser captures `has_bang: bool` on `op_invocation` CST node.
- Lowerer passes `WriteMode::Staged` vs `WriteMode::Direct` to the write op's `Operator::pipe()`.

**Op-side (ops/write.rs):**
```rust
pub enum WriteMode {
    Staged,   // buffer + yield
    Direct,   // write to disk immediately
}

pub struct WriteOp { mode: WriteMode, ... }

impl Operator for WriteOp {
    async fn pipe(&self, mut cs: BoxStream<Arc<[Cursor]>>, cx: &RtCtx) -> BoxStream<Arc<[Cursor]>> {
        // ...
        if self.mode == WriteMode::Direct {
            // write_cursor!(...)
            cx.put(WriteRangeEffect { ... }).await;
            // pass cursor through, no yield
        } else {
            // write_cursor(...)
            let _ = cx.put(WriteRangeEffect { ... }).await; // buffered
            let key = cx.store::<SubjectRegistry<RelationWake>>()
                .ok()? // or panic, depending on design
                .fresh_key();
            let lineage = Some(Arc::from(CursorLineage { ... }));
            match cx.put(Yield { key, lineage }).await {
                Ok(()) => { /* approval → continue */ }
                Err(Unsubscribed) => { /* rejection → unwind */ }
            }
        }
    }
}
```

- Host (LSP server / CLI runner) holds buffer sink refs after seed drain.

## Open questions

1. **Approval path:** Should host iterate buffer sinks and bulk-flush, or should ops themselves call `ctx.put(...)` again (disk batcher) after Yield resolves?
   - Bulk flush is simpler + more efficient (single pass).
   - Op-side re-put gives op a chance to inspect approval result + conditionally mutate.
   - **Suggested:** Bulk flush v3-now; gate re-put as v3.1 refinement.

2. **Lineage granularity:** Currently cursor-level. Should we tag by (op_id, cursor_id) or by (rule_name, step_index)?
   - Cursor-level allows precise teardown on capture narrowing.
   - Rule-level is easier for user reasoning.
   - **Suggested:** Lock on cursor-level; plan rule-level as "lineage filtering" feature.

3. **Conflict mode:** Silent rebase, error, or user-chosen merge strategy?
   - Silent rebase risks data corruption if overlaps are unintended.
   - Error stops the run; user must fix the rule.
   - User-chosen needs a 4th approval mode (approve, reject, or resolve-strategy).
   - **Suggested:** Error v3-now; merge-strategy future card.

4. **Cross-file ordering:** Should approved writes to different files run in parallel post-approval?
   - Yes, parallelism is good + safe (no overlap possible between files).
   - Batcher can use rayon `par_iter` on approved edits.
   - **Suggested:** Design for parallel; implement passthrough v3-now (eager serial), optimize in v3.1.

5. **$wt auto-materialize:** When should user checkouts be auto-created?
   - On first write attempt (v2 plan).
   - On approval (gives user a chance to reject before materialization).
   - On op registration (eager).
   - **Suggested:** On approval (after user says yes, before commit).

6. **LoC budget:** Phase 1 is ~500 LoC. Phase 2 (approval loop + diff) is estimated ~800 LoC. Phase 3 (session + $wt) is ~600 LoC. Fits the green-commit 1500–2500 LoC migration bill.

## Addendum — worktree as staging filesystem + own-db diff log

User extension folded in 2026-04-27. Generalizes the staging story:
the buffer batcher is the *in-memory* stage; an auto-materialized git
worktree is the *on-disk* stage; a sprefa-owned diff table is the
*persistent* stage. All three layers track the same logical "pending"
set, addressable by a refactor-session id.

### When to materialize a worktree

Write effects fall into two source classes:

- **Disk-mode source** (cursor came from bare `fs(glob)` under `--root`): the WriteRangeEffect already has a live working-copy path. Buffer batcher + user approval suffices. No worktree needed.
- **Repo/rev-mode source** (cursor came from `repo() > rev() > fs()`): the cursor's path resolves through the git blob layer. The WriteRangeEffect has nowhere to splice. Today: silent no-op (sprefa-e7x). Future: auto-create a worktree at the resolved rev, rewrite the effect's path to the worktree path, splice there.

Materialization is lazy and per-rev: first WriteRangeEffect that targets `repo=R, rev=V` triggers `git worktree add .sprefa-staging/<R>-<V>-<session>` and registers the path in `CheckoutRegistry`. Subsequent effects on the same (R, V) reuse the worktree. Cleanup on session commit/abort.

### Pending semantics

Effects against an auto-worktree are *pending* until session commit:

- **Visible to user** as a real on-disk diff (`git -C <worktree> diff`) for any tool that already speaks diff (vim, IDE, gh).
- **Tagged in sprefa's own db** (the sqlite drain extended with a `refactor_pending` table) so the LSP, hover, and re-runs of the same .sprf can see "this byte_range has a pending edit by session S, op O at .sprf:line:col". Hover surfaces this; re-runs read-through-overlay so dependent ops see the post-edit bytes.
- **Conflict surface widens** to include cross-session collisions, not just intra-session range overlap. The pending table is the resolution oracle.

### Own-db diff log shape

One row per WriteRangeEffect, written at stage-time (not commit-time):

```
refactor_pending(
  session_id    TEXT,
  op_source     TEXT,   -- .sprf path:byte_range of the originating op
  repo          TEXT,
  rev           TEXT,
  file_path     TEXT,   -- repo-relative
  byte_range    BLOB,   -- (start, end)
  before_bytes  BLOB,
  after_bytes   BLOB,
  worktree_path TEXT,   -- materialized staging path, NULL for disk-mode
  state         TEXT,   -- pending | committed | aborted | rolled_back
  created_at    INTEGER,
  resolved_at   INTEGER NULL
);
```

- `before_bytes` is captured BEFORE the splice, so rollback never re-reads from disk (the user might have hand-edited the worktree; we want to undo to our recorded baseline).
- `after_bytes` is the rendered/derived bytes the op wanted to write.
- Rollback path: walk pending rows for a session in reverse byte_range order, restore `before_bytes`, mark `rolled_back`. Same inversion v1's transactional batcher did per the PASS 1 archaeology.
- Git-side rollback is `git worktree remove --force` for the no-commit case, or `git revert <session-commit-sha>` after promotion.

### Promotion path

A session ends one of three ways:

1. **Discard** — drop buffer batcher, `git worktree remove`, mark pending rows `aborted`. No git history touched.
2. **Materialize-only** — flush buffer to worktree, leave worktree on disk with pending rows. User can keep iterating; commit by hand later.
3. **Promote** — flush buffer, `git -C <worktree> commit -m "<session label>"`, mark pending rows `committed` with the resulting sha, optionally cherry-pick / merge into the live branch.

`write!` (bang) bypasses (1)/(2) and goes straight to disk-or-promote, with no pending row written. The bang is the "I trust this, no diff review" signal.

### Wiring deltas vs the Phase 1/2/3 outline above

- **Phase 1c** gains: pending-table writer hooked into `WriteRangeBatcher::buffer()` flush. Disk-mode effects skip the table; only worktree-routed effects record.
- **Phase 2** (approval loop) gains: read-through-overlay so re-running the same .sprf during an open session sees post-edit bytes. Implementation: extend the v2 3-layer Reader stack (blob / WT / buffer) per `project_v2_wt_overlay.md` with a fourth `pending` layer that consults the table.
- **Phase 3** (session + $wt) is largely this addendum. The session id ties everything together.

### Why this wins

- **Reuses git** — diff rendering, conflict detection, rollback are shelled out to `git`. No need to rebuild diff UI.
- **Audit trail** — every refactor session leaves a queryable trail in sprefa's own db, independent of git history. Useful when a session is discarded (git would have nothing).
- **Multi-session safe** — two sessions targeting overlapping bytes get caught by the pending table before either splices.
- **Composes with hover** — LSP hover can show "this byte is pending by session S — defined at .sprf:line:col" on top of the existing capture-binding hover.

### Decisions locked 2026-04-27

**Q1 — Storage model: no-checkout overlay; worktree only at promotion.**

The pending table IS the overlay. Stage time writes nothing to the filesystem.

- `before_bytes` is NOT copied into the table. Stored as the tuple `(repo, rev, path)`; re-derived on demand via `git cat-file blob <rev>:<path>`. Git is already a content-addressed store; do not duplicate it.
- `after_bytes` is sprefa-derived (no git equivalent), stored inline in `refactor_pending`.
- Diff for view is computed on demand: `diff -u <(git cat-file blob <rev>:<path>) <(after_bytes)`. Or, more often, computed in-process from the two byte buffers and rendered for hover/LSP.
- Worktree is materialized ONLY at promotion, and ONLY for non-HEAD or dirty-tree cases. Promotion path:
  ```
  git worktree add --detach <staging-dir> <rev>
  for each pending row in session: splice after_bytes at byte_range
  git -C <staging-dir> commit -m "<session label>"
  git worktree remove <staging-dir>
  ```
  When source rev is `:HEAD` and the live tree is clean, promotion splices into the working copy directly and skips the worktree entirely.
- Worktree location when materialized: `~/.local/state/sprefa/staging/<repo-hash>-<rev>-<session>/`. Ephemeral, removed after commit. Never touches the user's repo dir.

This collapses Q1 + Q3 + most of Q5 into a single primitive: the pending table.

**Q2 — Timeout + referential integrity.**

- All pending sessions have a TTL. Default policy TBD (suggest 14 days).
- Pending writes never approved before TTL expiry emit a diagnostic per row at TTL-warn (e.g. 7 days) and are auto-discarded at TTL-hard.
- Pending writes are also surfaced alongside live diagnostics on every LSP run: "N pending writes in session S — file:byte_range — diff available". The user sees them in the same panel as compile errors.
- **Referential integrity**: if the originating op (op_source = .sprf path:byte_range) is deleted or its enclosing rule rewritten such that the op no longer exists in the parsed .sprf, the pending row is auto-discarded. Same lifecycle as a foreign key cascade. The .sprf is the parent; pending rows are children.

**Q3 — Storage: store abstraction, sqlite first.**

- `refactor_pending` lives in the existing sqlite drain. Reuses the connection, the migration story, and the dump-to-sqlite plumbing already in `v3/crates/server/src/run.rs`.
- `before_bytes` is NOT stored (Q1 lock). Only `after_bytes`, which is sprefa-derived and small (rendered patch). No CAS table needed.
- If `after_bytes` ever balloons (large render outputs), wrap it behind the existing store trait so swapping to a CAS or filesystem-backed blob store is one impl change.

**Q4 — Multi-repo sessions: best-effort, no atomicity.**

- One session id MAY span writes across multiple repos. No two-phase commit, no rollback-across-repos guarantee. "Best effort."
- Every cross-repo write yields and emits an LSP diagnostic anchored at the originating op's source span: "approval pending — repo R, file F, byte_range BR, diff: <…>".
- The core mechanic of a write effect (in Rust) is: `WriteEffect → yield Pending → SubjectRegistry stores it → LSP diagnostic stream surfaces it → user resolves via code-action → registry.next() resumes the op`. This is the contract.
- Promotion of a multi-repo session = N independent `git commit` operations, each with a back-reference to the session_id in the commit trailer. Cross-link is in the sprefa db, not in git.

**Q5 — LSP integration: all-of-the-above, first pass.**

- Virtual document for read-through (op re-runs see post-edit bytes).
- Disk-overlay diagnostics for surfacing pending writes alongside live diags.
- Code-actions for accept/reject per range.
- All three land together in Phase 2. None is optional.

**Q6 — `write!` bang: deferred.**

- No bang in Phase 1. Land yield + store + approval first.
- Revisit once the staging loop has run end-to-end and the cost of "always yield" is felt in real usage.
