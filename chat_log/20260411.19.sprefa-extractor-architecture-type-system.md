## Problem/Context
User's frustration with the 12 surveyed tools crystallized into an architectural stance: every peer tool ends up as "hardcoded graph algos in SQLite" with two query surfaces (imperative extractor + structured query thing) that cannot see each other. sprefa's differentiator is collapsing classification, resolution, and extraction into one relational language over one generic schema, so each new language is a trait impl rather than a query-surface rewrite.

The immediate triggering question was whether to reuse any of the 12 tools. Initial sycophantic answer ("three-layer compose") was correctly rejected; the real reuse story is narrower. Subsequent deep-dives:
- codebase-memory-mcp is impressive standalone but wrong as a dependency (18-edge-type taxonomy baked in, ordinal column missing from persisted edges, Cypher layer dead weight).
- Its service_patterns.c classification is a hardcoded strstr allowlist against resolved FQNs (~140 library entries). The idea ports cleanly to sprefa as a default rule file, the C code does not.
- SocratiCode is mostly useless for call graphs (AGPL, import-level only, embedding-first) but contributes RRF as a merge technique.
- Nobody in the survey enumerates Lodash-style type paths. Four capture dimensions are entirely green field: type paths, normalized visibility, string literals as first-class rows, file tree as facts.

Hard user feedback captured: stops reading at the word "not" in descriptive prose. Negative parallelism is a hard-block, not a style preference. Existing `feedback_no_negative_parallelism.md` memory needs strength escalation.

## Solution/Approach
Extractor trait with three cost tiers (PerFile, PerRepo, External). 10-12 extractor impls cover the target languages. Every extractor writes into the same fact tables, rows carry a `source` column identifying which extractor produced them. Queries filter or union across sources.

Heavyweight per-language extractors: oxc (JS/TS/TSX/JSX, highest leverage), ruff_python_parser (Python), syn (Rust structural), tree-sitter-go + custom walker (Go). One TreeSitterUniversalExtractor handles the 20-language long tail via per-language .scm query files. Opt-in band-3: ra_ap_ide (Rust semantic), clangd (C/C++), gopls (Go). External adapters wrap cymbal, sem, and codebase-memory-mcp as data providers. A base file walker always runs first, populating file_tree, string_literals, and lexical imports/exports.

Fact schema tables: files, file_tree, entities (with normalized 5-value visibility column), imports, exports, string_literals, call_sites (with the sprefa-specific ordinal + branch_path columns), function_signatures, function_params, types, type_fields, type_paths.

Type system is three tables: types (named, with is_anonymous flag), type_fields (owner + ordinal + field type), type_paths (precomputed Lodash-style enumeration with depth + flag columns has_array_segment, has_optional_segment, has_anonymous_segment, traverses_cycle). Function signatures represented as `types` rows with kind='function_sig' so they participate in path enumeration alongside struct fields. Path enumeration algorithm is a cycle-safe DFS with bounded depth, skips primitives, optionally skips anonymous types.

AST handles ~90% of extraction, regex is a narrow supplementary layer (pre-AST detection, post-AST string content filtering, unstructured config files), statistical techniques sit above the deterministic layer as confidence scores and fuzzy rename detection. Statistical techniques never produce base facts.

Reuse calls (honest, non-sycophantic): depend on oxc, ruff_python_parser, syn, tree-sitter, stack-graphs (optional), ra_ap_ide (optional). Fork sem-core's `extract_references_from_content` (line 848) and `infer_ref_type` (line 914) with MIT attribution. Wrap cymbal / sem / codebase-memory-mcp as external adapters (~200-400 lines each). Skip SocratiCode (AGPL), grepai, codedb, CodeRLM, tree-sitter-codeviews, graph-sitter, ACER.

## Key Insights
- **The 12 peers share one architectural defect: two query surfaces** (imperative extractor + structured query) that cannot see each other. Every hardcoded dispatch table is a symptom.
- **Type paths are green field.** Nobody enumerates Lodash-style paths. The schema is 3 tables, the algorithm is 40 lines of cycle-safe DFS.
- **codebase-memory-mcp's "66 languages" is thin.** Self-reported tier scoring admits Haskell and OCaml are "Functional" (minimal). Python sits in "Good" while Lua and Perl are "Excellent" — a signal the scoring is authored-effort based, not benchmark based.
- **codebase-memory-mcp's service_patterns is a hardcoded substring allowlist** matched against resolved FQNs via strstr. ~140 entries in static C arrays. Closed-world, requires recompile to add libraries. Port as sprefa tag rules, not as C code.
- **Embeddings are useless for static call graphs.** Structural lookup vs semantic similarity are different problems. SocratiCode's "polyglot 13 languages" comes from the embedding model treating all source text as vectors, not from any clever per-language logic. RRF (Reciprocal Rank Fusion) is the one transferable technique.
- **oxc is the highest-leverage single dependency for sprefa.** Covers JS/TS/TSX/JSX in-process with built-in name resolution, semantic layer, and module resolution (tsconfig paths, Node resolution). One crate dependency replaces three subprocess options.
- **Four capture dimensions are entirely green field across the 12 surveyed tools**: type paths, normalized visibility flags, string literals as first-class rows, file tree as queryable facts.
- **sem-core is the only reasonable "fork-and-adapt" source.** MIT, library-shaped, 22 languages, tree-sitter native. Shape differs from sprefa (no ordinal, no branch_path) but the 22-language visitor logic is directly adaptable.
- **stack-graphs is the right optional cross-file resolver** when languages with .tsg rules exist (Python, TS, JS, Java). Published crate, library-first design, push/pop partial path model.
- **ra_ap_ide is the right opt-in for Rust semantic** at the cost of full Salsa + HIR dependency. Two-tier Rust: syn for structure, ra_ap_ide for opt-in semantic work.
- **Classification (HTTP/async/config) is downstream of scope resolution**, collapses to a single query once FQNs exist. No extra query surface needed.
- **The Extractor trait is the composition surface.** Adding a new language is a trait impl. New languages should never require fact schema changes.

## Open Questions
- Concrete anonymous-type policy: synthesize or text-only? Default to synthesize, evaluate bloat on real repo.
- max_type_path_depth default: 5 or 10? Needs fixture-based tuning.
- External adapter caching: repo-state hash definition (tree hash? mtime aggregate? git HEAD + dirty bit?)
- Watcher invalidation granularity: per-file is simple, per-entity is lossless but needs entity-range tracking.
- Rust semantic: fork ra_ap_ide logic or depend on the crate directly? Crate is heavy, dependency chain includes Salsa.
- Datalog surface grammar: concrete syntax still sketch-level. Needs a formal spec before query compiler work starts.
- How do extractors coordinate on ID generation? Global counter via SQLite autoincrement, or per-extractor namespace with a translation layer?
- Should `confidence` column live on call_sites and type_fields from day one, or added later when statistical techniques land?
