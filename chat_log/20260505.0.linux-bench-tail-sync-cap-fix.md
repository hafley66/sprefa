## Problem/Context
User remarked 4.5s baseline left no margin. Investigation:
- `time` walk via find: ~5ms (linux fixture is git-checkout, ~63k files)
- 8 physical cores, workers=8 already saturating
- Walk-only timing instrumentation: 0.22-0.65s walk inside FsComponent::dispatch
- AstNm per-batch instrumentation showed:
  - 16 batches of up to 4096 cursors at cap=4096
  - sum_read across 8 workers = 8.27s (1.03s wall ideal)
  - sum_parse = 18.92s (2.36s wall ideal)
  - sum_match = 2.10s (0.26s wall ideal)
  - walk 0.22s + parallel CPU 3.65s = ~3.87s lower bound
- 2.3s "missing" time = inter-batch tail sync. Each `par_render` call blocks driver thread on the slowest file before next batch can pull. With 16 batches, 16 tail-sync points, N-1 workers idle waiting per tail.

## Solution/Approach
Change substrate's `ExpandOpts::with_batch_cap()` from `batch` (=4096 default) to `batch.max(65536)`. One mega-batch eliminates tail-sync points; rayon work-stealing handles all 63k files at once.

Comment in v4_bench.rs explains the lever. FsComponent's internal flush threshold (`self.batch`) stays at 4096 — controls memory pressure during walk, not parse-batch granularity.

## Key Insights
- **batch_cap drives tail-sync frequency, not memory.** Smaller cap = more sync points = N-1 workers idle on each batch's tail. For one-shot scan, ONE mega-batch is optimal. For LSP/incremental, smaller caps preserve latency.
- **The 3.87s lower bound is parse-bound.** ~5% of 63k files pass the "printk" prefilter. Tree-sitter parse on those 3-4k files is the dominant cost. Multi-rule scans share the parse, so per-rule cost amortizes.
- **Walk overhead is negligible at this scale.** 0.22s of 4.0s. Parallelizing via WalkParallel would save <200ms; not worth the restructure now. Pipelining walk + parse via thread split could save it without a parallel walker, but again, marginal.
- **Per-thread sum / 8 worker count = wall lower bound** for embarrassingly parallel rayon work. Useful framing for whether a workload is already at the parallel floor.
- **The `--batch` CLI flag was overloaded**: controlled both FS flush threshold (memory pressure during walk) AND expand batch_cap (tail-sync frequency). Decoupled by clamping cap to >= 65536 in substrate path.

## Open Questions
- Should DEFAULT_BATCH_CAP in expand.rs be raised? Currently 256. For scan workloads it's pessimal. For LSP it's reasonable. Consider per-mode default.
- Pipeline walk-with-parse: spawn FS into a thread, return a "source-active" sentinel from dispatch, expand polls. Worth ~200ms; adds substrate complexity. Deferred until LSP integration forces a non-blocking source shape.
- prefilter pass rate (5%): is there a stronger prefilter? `Pattern::fixed_string` returns longest literal substring; ~6 chars for printk. Could AND multiple literals, but ast-grep doesn't expose that.
