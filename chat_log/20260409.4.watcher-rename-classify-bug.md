# Session: watcher-rename-classify-bug

## Goal
Dogfood the sprefa rewriter by renaming crates/rules/src/ files to numeric-prefix ordering, using the watcher daemon to auto-rewrite all references.

## Current State
Committed 7e2f270: new `rust_sequential_multi_rename` test proving the plan+apply layer handles sequential renames correctly (440 tests pass). Dogfood attempt failed -- the watcher never fires rewrites because rename events are misclassified.

## Problem/Context
1. Attempted live dogfood: start watcher, `mv types.rs _0_types.rs`, expect auto-rewrite of all `crate::types` refs across the workspace.
2. Watcher classified the rename as Delete + ContentChange instead of correlating it as a Move. `created_count=0` in classify_batch logs -- the Create side of the macOS rename event was never registered.
3. Without Move classification, no rewrite plan is generated, so files are left with stale refs.
4. The plan+apply layer itself works correctly for sequential renames (proven by the new test). The bug is exclusively in `classify_batch` in `crates/watch/src/watcher.rs`.

## Solution/Approach
The macOS FSEvents rename path in `spawn_notify_watcher` (line 162) handles `RenameMode::Both` by emitting Removed + Created. But `classify_batch` then fails to see the Created event as a new file -- likely because the file already exists in the DB (the scanner indexed it), so `classify_batch` promotes it from Created to Modified (line 278-284). This strips it from the `created` map, so content-hash correlation against `removed_info` never happens.

Probable fix: when a path appears in both `created` and `removed` maps AND the content hash matches a different removed path, it should be classified as a Move regardless of DB existence.

## Key Insights
- macOS FSEvents fires `Modify(Name(Both))` for renames, which the watcher splits into Removed + Created. But classify_batch's "promote create->modify when file exists in DB" logic (line 278-284) defeats move correlation.
- The plan+apply layer handles stale DB refs gracefully: the DB query finds affected files by old ref values, and syn operates on actual file content. Sequential renames work at the planner level.
- The numeric prefix ordering for crates/rules/src/ is: _0_types, _1_pattern, _2_graph, _3_schema, _4_file_match, _5_git_match, _6_walk, _7_ast, _8_emit, _9_extractor (topological dependency order).

## Open Questions
- Should the "promote create->modify" heuristic be skipped when there's a matching Removed in the same batch? Or should move correlation run before the promote step?
- The decl-rename reverse direction (user edits `mod types;` directly) is still unimplemented
