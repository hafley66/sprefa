## Goal
Analyze sprefa codebase architecture and identify opportunities for conceptual unification/evolution.

## Current State
Completed deep read of 14 crates, 60+ source files. Identified 5 key architectural tensions and unification opportunities.

## Key Insights

### 1. Two Rule Representations (sprf DSL vs JSON/YAML)
- sprf uses custom parser (_1_parse.rs)
- JSON uses serde directly
- Both lower to SelectStep but via different paths
- **Opportunity**: Make sprf emit Rule types directly, eliminate parallel structures

### 2. Pipeline Phase Naming
- _0_ast, _1_parse, _2_pattern, _3_lower — numbered not semantic
- **Rename to**: syntax, elaborate, lower, stable_hash

### 3. Extractor vs Rule Boundary
- Built-in extractors (JS, RS) implement Extractor trait
- User rules drive walk engine
- **Unification**: Implement Extractor for Rule — everything becomes uniform

### 4. Context Steps Duality
- Repo/Rev/Folder/File vs Key/Object/Array in same enum
- Runtime dispatch via is_context_step()
- **Unification**: Two-phase selection — ContextSelector (pre-parse) then StructuralSelector (tree walk)

### 5. Watch/Scan Duality
- Watch (incremental) and scan (batch) share 80% logic
- Different entry points, different planners
- **Unification**: Scan = Watch with full-rebuild delta. One planner, two delta sources.

## DSL Pattern Recognition

The sprf language is essentially **jq plus filesystem scoping**:
```
selection = file-pattern > parser > query
context   = repo(rev(folder(...)))
rule      = context { selection* }
```

The `>` operator is function composition. `{ }` blocks are monadic binds (context carriers).

Everything else (14 crates, 60 files) is implementation detail around:
- Fast (caching)
- Incremental (watching)
- Multi-language (ast-grep integration)

## Evolution Path

### Short-term
- Rename sprf phases to semantic names
- Document the Context/Structural split explicitly

### Medium-term
- Unified Extractor trait implementation for Rule
- Merge scan/watch planners

### Long-term
- Query planner optimization (pushdown, caching)
- Potential LLVM-style IR for cross-rule optimization
