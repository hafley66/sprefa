## Key Insights
1. Spec fixtures vs verified parse: fixtures are forward-looking docs; the parse-status pin in spec_fixtures_parse.rs makes them dual-purpose (doc + tripwire). When a grammar landing accidentally enables a future fixture, the test fails with a "move it into the PARSES TODAY list" instruction. Self-updating spec.
2. Kitchen sink + spec_fixtures_parse = two complementary surfaces. Kitchen sink asserts op-shape parses (using simplified syntax that lands today). Fixtures preserve target syntax verbatim (with rough edges) for when the grammar catches up.
3. The op_invocation node text spans `name + brackets + parens + braces` together. Filtering invocations by `starts_with("write_cursor")` works because the name prefix is consistent across paren slot variations.
4. expect-with-format-string when the formatted value is !Display fails to compile only when the format actually references self. Using std::any::type_name::<E>() is the type-name escape hatch when the runtime value can't be Display-printed but the generic parameter carries enough identity.
5. Always ask before reverting an uncommitted user change. The broken-looking edit was an in-flight debug attempt with intent worth preserving.

## Open Questions
1. Should the dotted carveout grammar (${X.field?}) be one card or split (e.g. lex pass for the dot-id chain vs lower pass for capture-field resolution)? Probably one — dotted access is purely surface syntax sugar over a Value::Atom field-walk.
2. @begin/@end as marker identifiers: is `@` a new sigil token, or do these become reserved keywords inside `comment(...)` bodies only? Op-internal sub-grammar is simpler — comment body has its own lexer, no host change needed.
3. Backtick string: token-precedence vs the existing `${...}` carveout. Inside backticks, ${...} should re-enter the carveout. tree-sitter conflict declaration may be needed.
4. write_cursor mode atom set: just {:replace, :append, :prepend, :wrap} or also {:line_above, :line_below, :inside_braces}? Probably YAGNI past the four core.
5. Will the LSP crash turn out to be one of the existing batchers (FsListFiles, ReadBytes, Print) failing to register, or a new one I haven't seen? The type_name will tell us.
