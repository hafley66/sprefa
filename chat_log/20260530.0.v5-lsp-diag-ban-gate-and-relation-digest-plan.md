## Solution/Approach
Relation input-digest skip (Axis-A reconcile scaling = v4's Replay short-circuit at RELATION granularity, NOT v4's row-granular MEMO_DEPS which was the RAM-cost trap). A file edit changes bytes always but rows only sometimes; comment edit re-extracts identical rows yet currently triggers rebuild. Fix: after extraction, compute per-relation digest = XOR-fold of __src over rel_<R> (order-independent; PK on user cols makes it a set so no dup cancels); if equal to stored digest, prune from changed_source_rels. Store in SQLite _reldigest(rel,digest) — durable across daemon restarts, no RAM cache (v4 over-built persistent runtime_* graph; v5 keeps durability in SQLite, wiring in process RAM).

## Key Insights
- v5 fixpoint ALREADY has hard round cap (engine.rs:702 iters>100_000 bail) = v4's no-hang lesson present.
- diag cols mapped BY NAME (path/line/msg required; col/end_line/end_col/severity/code/hint optional) so .dl author orders freely.
- LSP gotchas found+fixed: (1) MUST strip `?` queries in LSP mode — run_query println!s to stdout which IS the protocol channel, corrupted stream + deadlocked cold tick; (2) lsp-server initialize() blocks until `initialized` notification (test-harness gotcha, not code bug). didChange IGNORED (unsaved buffer=RAM-only data-model level, deferred); save-driven disk-truth.
- ban gate is STRUCTURAL not textual: dbg! in comment/string does NOT trip it (the property grep can't have) — proven in ban_gate.rs.
- $M vs $$$M: single metavar = one node, $$$ = variadic arg list (panic!("x",y) needs $$$M).
- k8s-apply mental model is correct: .dl=desired-state manifest, tick=reconcile loop, fs/git=observed state, SQLite=etcd, LEVEL-triggered (hash diff) with edge-triggered wakeup (fs event). SQL-UDF model also correct: load-once wires a program (parse/lower/stratify/closure_map/auto_indexes/affected_derived dep graph), tick runs the wired graph not the text.
- Scaling meta-lesson: v4 proved durability+resumability+scoped-reconcile are right GOALS and row-granular memo-deps + persisted graph DB are the WRONG way to pay. Two digests (one per relation's source hashes = Axis A; one per edge set = Axis B) are the whole scaling story, both cheap.
