# PR causal-map animation idea (design notes, NO impl)

Status: **idea only.** A scaffold crate was written at
`~/projects/sprf-prmap/` during discussion but it is throwaway,
unverified, not wired to anything. Delete it or ignore it. Nothing was
added to `sprefa/v4`.

## Origin question

Which is the Next.js / animated-over-time code tool: Code Hike or Code
Surfer? Goal: use that kind of fancy animated code presentation for
PR / code-mapping, so a human or AI explains a PR and you can see why
each file is needed and how files connect. Also want a legible
graph-theory picture (mermaid / D2) of what is being animated. Final
framing: take advantage of the human visual cortex for explaining
design docs / API plans to coworkers.

## Tool landscape (researched)

- **Code Hike** is the current, Next.js/MDX one. Scrollytelling +
  Spotlight. v1.0 (Aug 2024) added Blocks (markdown -> Zod-validated
  React props), headless codeblocks, component annotations. Has an
  official Remotion -> video path.
- **Code Surfer** is the older, dead one (MDX-Deck/Gatsby era,
  slide-morph). Same author (pomber). Not the one to use.
- Smooth "code A morphs into code B" = **Shiki Magic Move** (powers
  Slidev). Live-render only.
- Recorded/exported video: **Remotion**, **Motion Canvas** (has a Code
  node that auto-tweens between code states), **code-video-generator**
  (Manim). Everything else is live-render only.
- **D2 (terrastruct)** is the only diagram-as-code tool with native
  board-to-board animation: `d2 --animate-interval=Nms` packs multiple
  "boards" into one animated SVG. Mermaid has no native animation.
- AI PR tools that already emit diagrams: Qodo PR-Agent (OSS, Mermaid
  LR flowchart, self-hostable — best for piping elsewhere), CodeRabbit
  (Mermaid sequence in PR comment), Greptile (repo call graph). None
  emit D2. Not worth adopting: they build their own graph and would
  compete with sprf's graph rather than feed it.
- CodeTour (Microsoft) is the existing "recorded step-through of a PR"
  tool if a guided-tour artifact is wanted.

## Core design idea

sprf already IS the graph source. `rev` over two revisions + `diff` +
blast-radius / implements / tests rule rows = the causal edge list,
with source coords. No tree-sitter / external tool needed. Two
topological orderings = two queries over the same rows.

Graph-theory framing (the legible part):

> One labeled DAG `G = (N, E)` from sprf rule rows. A level function
> `ℓ: N -> ℕ` (decl 0, impl 1, test 2, dependent 3) induces a nested
> chain of induced subgraphs `G0 ⊆ G1 ⊆ … ⊆ G` (a filtration). The
> animation is just walking the filtration. Never a new graph — only
> sublevel sets of the same graph revealed over time.

Why it stays legible: every board is an *induced* subgraph (no dangling
edges) and every diagram node id is content-addressed on code location
(`blake3(repo,file,lo,hi,kind)`), stable across boards. Stable ids are
why D2 morphs a node in place (object permanence for the viewer) and
why a click maps back to a byte range (`vscode://file/...`). That
round trip — diagram node <-> code range, both ways, through one
content-addressed id — is the entire "tie animation to code"
mechanism.

The user's narrative beats map onto the filtration:

| beat | board |
|---|---|
| declare generic idea | decls only |
| down in specificity, side-by-side why/what | decl \| impl split |
| tests unlocked | + test nodes |
| what depends on this type next | + downstream dependents highlighted |

## The "we're becoming a notebook" insight

A notebook = a fileset + an index, not a renderer. So the operator
should NOT render. It should be a barrier that buffers upstream rule
rows and emits **one cursor per output file** (value = bytes, FS term =
path); existing `> write` materializes the bundle. This matches the v4
self-doc cursor contract and reuses `write` instead of special-casing
rendering.

Render-sink ladder (nested supersets — stop by choosing a tier):

| tier | files | external dep |
|---|---|---|
| mermaid | index.md | none |
| d2 | + graph.d2, graph.svg (animated) | `d2` on PATH |
| codehike | + page.mdx, nodes.json | Next.js app |
| video | + Root.tsx, render.sh | Remotion |

Proposed operator surface (sketch only):
`prmap(:tier, :ordering, :out)` — barrier component, buffers graph
rows, builds the DAG, walks the filtration, emits the fileset.

## The honest gap (why this is idea-only)

Pipeline has three parts; only the middle was sketched:

1. PR diff -> node/edge rows (KIND/NAME/FILE/LO/HI, FROM/TO/REL).
   **Not built. This is the real intelligence and it's sprf rules,
   not Rust.**
2. Rows -> animated notebook fileset. Sketched in throwaway crate.
3. A host that registers the operator + runs it. Not built.

`prmap` is deliberately dumb about the codebase so it never competes
with sprf's graph. The rule layer (#1) is the actual work and the
right place to start if/when this is picked up.

## Open verification debts (if ever built)

## Decision

No implementation now. Captured as a direction. Revisit by starting
with the rule layer (#1), not the renderer.
