## Mechanical primer (verbatim, for future re-read)

> The core split is: **`pipe` is async, runs in the streaming runner,
> has reader access. `completion_witnesses` is sync, called per
> output-cursor after `pipe` drains, no reader, no ctx.** The question
> is where the parsed tree lives between those two phases.

### 1. Reader: sync or async?
Async by shape. `BoxStream` / `BoxFuture`. Ops `.await` inside `pipe`.
What's **not** reactive: `DocSession::complete_in_paren` calls
`run_pipelines` which calls `block_on`. LSP `completion()` is async
externally but we haven't pushed the reactive boundary all the way
through yet.

### 2. Why Cursor exists
A cursor is **"a position in the (repo × rev × path × key-path) lattice
that's been narrowed by everything upstream."** Ops filter, bind, or
fan out cursors. Everything pivots on this. `fs`, `captures`, `fks`,
`evidence`, `content`, `path`.

### 3. Pipes are streams of cursors
`impl Op { fn pipe(input: BoxStream<Cursor>, ctx: OpCtx) -> BoxStream<Cursor> }`.
Stream in, stream out. Fan-out and filter are the same primitive:
`input.flat_map(...)`.

### 4. Witnesses: ops explain themselves
`fn witness(&self, c: &Cursor) -> Option<Arc<str>>;`
"Given a cursor that passed through me, what's the human-readable value
I pinned on it?" One op-author-written function unlocks hover,
completion, diagnostics.

### 5. Why witness_insert needs to exist
`witness` is 1 cursor → 1 string. For repo/rev/fs, label == insert. For
json, label (jq-path `.deps.foo`) ≠ insert (sprf pattern
`{ deps: { foo: $FOO } }`). Added `witness_insert(c)` defaulting to
echoing `witness(c)`. (Chose option (ii), not the subagent's proposed
`completion_witnesses`. Forking lives in `pipe`, not in witness.)

### 6. Partial parsing vs partial running
**Partial parsing**: `host_parse_tolerant(src)` returns Pipeline from
mid-typed source. LSP is read-only; mid-typed is the normal case.
**Partial running**: `truncate_and_substitute` rewrites the pipeline so
the op-under-cursor becomes its `wildcard_instance`, everything
downstream is dropped. Runs same runner as `ensure_run`. Both needed;
neither replaces the other.

### 7. Diagnostics: per-cursor is correct
`fs/no-match` fires per (repo, rev) that found zero files. The
**runtime layer** is correct to report per-cursor; the **LSP layer**
aggregates because the user sees one source span. That's why
`successful_sites()` + the severity downgrade live in
`sprefa_v2_lsp::publish`, not in the op's diagnostic.

### 8. Single vs multiple runs
Today: one run per `ensure_run`, cached in `last_run`. Future multi-run
cases: completion partial-eval (second run, rewritten pipeline, scoped
to one rule, thrown away), scan-check loop (`_14_scan_loop.rs` runs
repeatedly feeding back into Config until fixed point), cross-rule
`${other.$X}` refs (topological ordering, multi-phase but "one run").

### 9. Reader vs Writer vs Runner sagas
Designed, not fully built:
```
 READER → OP PIPE → EFFECT QUEUE (accumulates writes without applying)
                         │
                    after drain
                         ▼
                      WRITER (apply, transactional)
```
Saga = compose multiple read→write→read iterations when one write
changes subsequent reads. md/ast-grep ops will all be **readers**.

### Why all this machinery exists
Ops are black boxes to the runner. The LSP needs to interrogate what
each op did (hover, complete, diag) *without the runner knowing
anything op-specific*. Witnesses, witness_insert, wildcard_instance,
parse_site, evidence — those are all "op declares its own
interpretation" slots. Runner stays ignorant; ops stay extensible.

## Open tension: tree-walker composition needs a cursor slot

Forward-looking. Not yet resolved.

json op parses JSON/YAML/TOML → `AnyDataNode` tree → walker matches
patterns. ast-grep op (planned port from v1) will do the same with
Rust/TS/etc. ASTs via ast-grep's own matcher. Possibly tree-sitter
under the hood for broader language support.

**Composition question**: can you nest `json > json`? Conceptually: yes,
the first json selects a subtree, the second walks inside it. Today's
cursor carries `content: Option<Arc<bytes::Bytes>>` — raw file bytes.
Not a tree. The walker re-parses each time.

For nesting to compose, **the cursor needs a slot for parsed tree
data** that downstream tree-walker ops can read. Same requirement for
ast-grep nested inside json nested inside md.

### The abstraction question

- Name the slot after the op? (`cursor.json_tree`, `cursor.ast_tree`, …)
  → Bloats Cursor per op. Non-composable.
- Name it after the **kind of data**? (`cursor.tree: Option<Tree>`)
  → Requires unifying `AnyDataNode`, ast-grep's AST, tree-sitter nodes
  under one `Tree` trait. Doable but invents an abstraction.
- Make it **operator-owned** (the way we moved diagnostics, completions)?
  → Runs counter to "cursor is universal." But matches the ops-own-
  everything principle. Storage could be a typed slot map keyed by
  op-declared tag.

Tension: json and ast-grep are **foundational** enough that their
"parsed tree" might deserve a Cursor field. But the **abstract** version
(any tree parser) might not. Tree-sitter keeps surfacing as the
potential generalization but brings its own API surface.

**Status**: Left unresolved. Revisit when:
- First ast-grep prototype lands and we see what shape its match
  evidence wants to ride on.
- We attempt `json > json` nesting and hit the re-parse cost.
- md op parses and wants to expose section trees.

## Key Insights

- **SprfPath already encodes group identity.** The prior memo's `BatchId`
  proposal was redundant. Grouping by `path.prefix_up_to_last_iter_or_forkarm()`
  recovers sibling batches for free.
- **Shotgun surgery grows with op count.** Migration cost scales
  linearly. 6 ops today, ~10 when trigger forces the flip. Pay now.
- **Implicit forking lives in patterns.** `json({a:{x:$X}, b:{y:$Y}})`
  is sugar for a brace block with two json arms. The walker already
  produces grouped output (`WalkOutcome.rows`); json immediately
  flattens it. (B) preserves at the stream layer what the code is
  throwing away.
- **Label ≠ insert is the *only* asymmetry** between json and
  fs/repo/rev. Adding `witness_insert` closed that gap in 3 lines; no
  new `completion_witnesses` method needed.
- **Tree-walker nesting is unsolved.** Either a dedicated Cursor slot
  per op (bloat), a universal `tree` field (requires tree-type
  abstraction), or op-owned slotmap (principled, more machinery).
