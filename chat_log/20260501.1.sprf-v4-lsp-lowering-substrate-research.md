# Session: sprf-v4-lsp-lowering-substrate-research

## Goal
Research the ecosystem of "make a programming language with tree-sitter + LSP + lowering" tools, then design the smallest typed trait model for sprefa's multi-DSL situation. Decide where Salsa, effect_runtime, and timely/DD each fit. Capture all of it as project-local skills tagged for v4 planning.

- v3 has: tree-sitter host grammar + injected sub-grammars (`sprefa_parse`), `pipeline::Op` runtime trait, `pipeline::lower` semantic IR (Pipeline/OpCall/Term/Rule/EntityRef), `effect_runtime` (PureEffect + Batcher + CacheLayer + DomainInvalidate + CancellationToken), tower-lsp server with `OnceCell`-based per-file lowered cache.
- 12 sprf-* skills written under `.claude/skills/`, all tagged `[v4 planning]` in description frontmatter.
- User is already lab'ing timely/DD in another session (parallel track).

## Problem/Context
sprefa needs multi-DSL semantic features (regex, glob, ast-grep, sql-tag, pipeline, future) without each DSL reinventing CST→IR→diagnostics+hover+completion plumbing. Workload is heterogeneous: many tiny precise rules, full-repo language checks, cross-repo rules, full-repo string indexing, auto-refactoring writes. Need to pick the right incremental substrate per workload and not over-couple.

## Solution/Approach
Three-trait collapse for multi-DSL:
- `DslGrammar` (sub-language registration: language, highlights, injections)
- `Lower` (CST → typed State + diagnostics; declares `potential_kinds` bitset + `required_substrings` AC prefilter + typed `Services` DI bag)
- `Surface` (State → IDE facts: hover, diags, tokens, symbols, complete, actions; lazy projections)

Substrate map:
- Salsa: skip the crate. Macro-coupled (no trait abstraction possible). Only worth it for one tracked query: pure `lower(parse_tree) -> Pipeline`, only if ≥3 consumers. For sprefa today, hand-rolled `OnceCell` is sufficient.
- effect_runtime: own writes (StagingBatcher), journaling (JournalLayer for rewind/forward), pure-compute caching (existing CacheLayer). Add scope-tracked dep edges (~150 LoC) for early cutoff.
- timely/DD: own cross-file/cross-repo relational state (tag insert/select/semi-join, rule outputs).

LSP staged writes: pure effect interpreter swap + three rendering tiers (inlay → code lens → code action → applyEdit). Volar virtual-file pattern for semantic features inside injected DSL bodies (defer until needed).

500-repo Salsa ramifications documented: single-writer lock bottleneck, cancellation thunderstorm, no disk persistence, durability tiers as the only real scaling lever.

## Key Insights
- "Pull" Salsa is not free; it has global revision counter, single-writer lock, cancellation thunderstorm — all of which couple unrelated work at scale.
- Salsa macros (`#[tracked]`) prevent trait-shaped abstraction. The runtime hooks happen *before* user fn body, on the database, with call-stack knowledge. No way to factor as `trait Memoizable<I,O>`.
- biome's `Queryable + Rule + Services` split is the cleanest precedent for multi-DSL lowering. ast-grep's prefilter is the cleanest dispatch trick. ra's `Semantics` god-object is the anti-pattern.
- Pure effects + interpreter swap = staging, dry-run, journaling, memoization all become composable batcher layers (~50–150 LoC each). One call site, swap policy.
- sprefa is **batch-shaped**, not interactive-shaped. Most workloads (tiny rules, whole-repo passes, cross-repo, indexing, writes) don't benefit from Salsa at all.
- The one place Salsa earns its keep: pure `lower(parse_tree) -> Pipeline` as a single tracked query — only worth wiring if ≥3 independent consumers exist.
- UTF-16 column math is a four-day debugging session if hand-rolled. Always use `line-index` or `lsp-positions`.
- helix and zed do NOT lift injections to semantic layer — only Volar does it (virtual file + offset map). stack-graphs does it for name-res only.
- rowan green/red pattern is "persistent value + ephemeral cursor" — same shape as immer/im::Vector. v3 doesn't need rowan unless it stops using tree-sitter directly.
- Salsa vs timely vs effect_runtime: pull/coarse vs push/delta vs saga/effect — three regimes, three substrates, sprefa wants all three because the language has all three flavors of computation.

## Open Questions

- When does the `OnceCell` per-file lowered cache become insufficient → time to wire Salsa? (Trigger: ≥3 independent consumers of lowered IR for the same file.)
- Will tag relations need recursion, forcing the timely/DD substrate sooner than expected?
