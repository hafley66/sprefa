## Solution/Approach
Architecture research (two parallel Explore agents, one per v3/v4):
- v3 (frozen 2026-05-20): pull-based cursor-stream engine. `Cursor` is the sole
  flowing value (pipeline/src/_0_cursor.rs:128); `Op::pipe_flat_map` defaults to
  mergeMap(64); `Pipeline::{Op,Seq,Fork}`; `RelationStore`/`Bag` row-bags. NO
  FactStore/RuntimeGraph/owner/source/supports/witness in code (that vocabulary
  only in docs/PRIOR_ART.md, never implemented). No retraction, re-executes from
  root every run.
- v4 (frozen 2026-05-31): generalizes Cursor to `FactStore<Cursor>` keyed by
  `Ref`/`StringId` into `_refs`/`_strings`, and `Coord{repo,rev,fs,lo,hi}`
  (lib.rs:107-130) — the direct ancestor of v5's ref-spine (same names: Coord/
  WhereBytes/StringId). Stratified SQL fixpoint (Tarjan SCC + negation check).
  Real incremental retraction via `SupportLedger(cursor_id,table,row_id,mult)` +
  DRed `cascade_retract` (mounted_query.rs:860-907): delete a row iff
  sum(mult)==0. Stopped mid-LSP-phase-6, incremental recompute gated behind
  SPREFA_REC_INCREMENTAL, never finished.
- v5: drops cursor-stream runtime and DD vocabulary entirely; rules lower
  straight to SQL; SQLite is the only store; type_edge/type_entity/doc_comment/
  call_edge are lazy built-in extractors (syn/oxc/tree-sitter).

Measured via dl itself (built v5/target/debug/dl, used
`scan("WORK","**/*.rs",p,rev), match(p,rev,/./,l)` trigger pattern):

## Key Insights
- `closure()`/`scc()` in the dl engine ALWAYS read a relation's first two
  DECLARED columns as the edge pair (cols[0]/cols[1]), regardless of total
  arity or which positions are bound in a given rule. Any future column
  additions to an existing edge-shaped relation MUST append after the pair,
  never prepend, or every closure/scc consumer breaks silently with wrong
  semantics (not a compile error).
- `_` (and pinned literal head terms) are silently OMITTED from `?` query
  output entirely — not printed as `_` or echoed back. This is what made the
  mechanical arity-bump sweep safe across 14+ files without touching existing
  string-match test assertions.
- `type_link` already solved repo-scoping for the resolved/SCIP-backed graph
  (src/dst are `{repo}::{sym}`-prefixed) — only the legacy name-keyed
  `type_edge`/`type_edge_rev` had the gap. Worth remembering before assuming a
  cross-repo dl query needs new engine work: check type_link first.
- v4's `Coord`/`WhereBytes`/`StringId` (lib.rs:107-130) are the direct,
  same-named ancestor of v5's ref-spine (C0-C5 arc) — v5 reimplemented this
  natively in SQLite rather than inventing it fresh.
- v3/v4 never had FactStore/RuntimeGraph/owner/source/supports/witness
  vocabulary IN CODE despite docs/PRIOR_ART.md referencing differential
  dataflow — confirms [[feedback_no_dd_vocabulary]] was about doc/conceptual
  framing, not a refactor of real implemented types.
- Doc coverage and god-object fan-out queries (`type_entity` minus
  `doc_comment`; `fan(f,n) <- type_edge(f,t,_); god(f,n) <- fan(f,n), n>K`)
  generalize to ANY Rust/TS/Kotlin subtree, live or frozen/dead, via the
  `scan("WORK","<glob>",p,rev), match(p,rev,/./,l)` trigger pattern — this is
  the actual reusable recipe for "shorten codebase archaeology with dl".
- Cost comparison observed this session: two Explore agents reading v3/v4 by
  hand took ~70-98s each for qualitative summaries; three isolated `dl`
  god-object runs took ~15-20s each for exact, falsifiable numbers. dl wins on
  "what/where", agents still required for "why" (semantics like
  SupportLedger/DRed can't be inferred from fan-out counts alone).
- Working in a worktree off a non-bare local sibling repo: `git fetch
  /path/to/main/repo main:refs/remotes/local/main` then `git rebase
  refs/remotes/local/main` works fine for picking up upstream changes without
  needing the actual `origin` remote.
- Always `git commit` before attempting `git rebase` in a worktree — forgot
  once this session, rebase refused with "you have unstaged changes."
