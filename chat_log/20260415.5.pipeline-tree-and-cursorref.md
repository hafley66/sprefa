## 1. The Two Trees

The system carries two distinct address spaces simultaneously. Confusing them is the source of every complexity downstream. Name them explicitly and keep them separate.

### Pipeline Tree

Address space of runtime execution state. `SprfPath` is the coordinate. Nodes are op-hops, iter positions, and fork arms. Captures hang off leaf nodes.

Every cursor that exits the pipeline carries its full address in `cursor.path: SprfPath`. The path is a sequence of `PathSeg` variants: `Op { name, parse_site, step }`, `Iter { index }`, `ForkArm { index, parse_site }`, `Named`, `LeafArm`. The framework stamps these in `Pipeline::run_with_step`.

```
Pipeline Tree for: rule > fs(**/*.json) > json({ code: $CODE }) > ast-grep(&.$CODE, pat)

rule (PathSeg::Op)
  └─ fs (PathSeg::Op)
       └─ Iter[0] (PathSeg::Iter) ← foo.json
       │    └─ json (PathSeg::Op)
       │         └─ Iter[0] (PathSeg::Iter) ← first match row
       │              captures: { CODE: Capture{value:"…", byte_range: 42..87} }
       │              └─ ast-grep (PathSeg::Op)   ← CursorRef: input redirected to CODE span
       │                   └─ Iter[0] ← first pattern match inside CODE's bytes
       │                        captures: { $NAME_MATCH: … }
       └─ Iter[1] (PathSeg::Iter) ← bar.json
            └─ …
```

Every node in this tree is indexed by its full `SprfPath` prefix. Sibling cursors share a common prefix truncated at their divergence depth.

### Content Tree

Address space of source bytes. Nodes are document-level parse-tree elements: JSON values, AST nodes, markdown sections, etc. Captures on pipeline-tree leaves POINT INTO content-tree nodes.

```
Content Tree for foo.json (one file, two parsers)

foo.json (raw bytes, content: Arc<Bytes>)
  └─ JSON tree (AnyDataNode, stored in JSON_TREE slot)
       └─ .code value (AnyDataNode::String, byte span 42..87)
            └─ TS AST tree (AstGrepTree slot, stored after &.$CODE redirect)
                 └─ FunctionDecl node (byte span 0..45 relative to CODE start,
                                       42..87 absolute in file)
                      captures: { NAME_MATCH: "myFunc" }
```

### Side-by-side diagram

```
PIPELINE TREE                             CONTENT TREE

rule                                      foo.json bytes
  └── fs[Iter:0=foo.json]                   └── JSON root (AnyDataNode)
        └── json[Iter:0=first-match]  ───►        └── .code  (byte 42..87)
              captures: { $CODE }                        │
              byte_range: 42..87                         └── TS AST
              slots: { JSON_TREE }                             └── FunctionDecl
                └── ast-grep[Iter:0]  ───────────────────►          byte: 42..87 abs
                      captures: { $NAME }
                      byte_range: 42..52
                      slots: { JSON_TREE, AST_GREP_TREE }
```

Arrow direction: pipeline-tree capture's `byte_range` is a pointer into a content-tree node. The capture's `value` (Arc<str>) is the extracted text at that content position. The slot carries the full parsed subtree for that content node.

This split is load-bearing because:
- Span arithmetic always lives in the **content** domain (absolute byte offsets into `content`).
- Address / routing always lives in the **pipeline** domain (`SprfPath` prefix queries).
- `CursorRef` (`&.$X`) translates: "take a content-tree pointer from a pipeline-tree node and use it as input source for the next op."

## 2. Span Recursion Rule

Formal rule for `span(node)` at any pipeline tree position:

**Leaf cursor with captures (walker row):** The authoritative span is the walker's match anchor span — the node the walker pinned. Capture union is secondary. Formal: `span(leaf) = cursor.byte_range` (set by the walker to the matched node's absolute byte span). This is the "true subtree-root span."

**Interior pipeline-hop node (all cursors sharing a common SprfPath prefix):** Union of `byte_range` across all descendant leaf cursors sharing that prefix. `span(prefix_P) = union { cursor.byte_range for all cursor where cursor.path starts_with P }`.

**Walker-emitted row with an explicit anchor field:** The anchor takes precedence over the capture union. This is the "true subtree-root span debt" noted below.

**Fork arm node:** Union of leaf spans within the arm. Cross-arm union is the span of the fork's parent op.

### The match_span debt

In `_5_json.rs`, `MatchResult.match_span` is touched in commit 2 to set `cursor.byte_range`. The current implementation sets `byte_range` to the span of the _matched pattern's captures union_, not the span of the root node the walker anchored to. These are different when a pattern like `{ code: $CODE }` matches an object: the object's span is wider than `$CODE`'s span alone.

Until the walker surfaces the anchor-node span separately, `byte_range` on json output cursors is "captures-union span," not "subtree-root span." This is documented debt: the fix is to have the walker emit both the anchor span and the per-capture spans, and have json set `byte_range = anchor_span`, not `captures_union`.

## 3. Runtime SprfPath Addressing

Proposed query syntax for addressing any node or capture in the pipeline tree at runtime. This is consumed by `CursorRef` resolution, LSP hover, diagnostic anchoring, and the planned reactive re-eval system.

### Anchors

- `$ROOT` — the root rule cursor (before any ops).
- `$SELF` — the current cursor's own path.
- `$PARENT` — one segment up from `$SELF`.

### Indexed path expressions

```
$ROOT.fs[0].json[1]          — fs first iter, json second iter
$ROOT.fs[0].json[1].$NAME    — capture $NAME on that specific cursor
$ROOT.fs[*].json[*].$NAME    — wildcard: all iter positions
$ROOT.fs[0].json.$CODE       — elide [0] when exactly one match (sugar)
```

Eliding `[0]` is valid syntactic sugar. The resolver errors if there is more than one match and the index is elided (ambiguity error, not silent first-pick).

### Functions over addressed nodes

```
span($PATH)                  — byte range at that pipeline-tree node
bytes($PATH.$NAME)           — Arc<[u8]> slice at that capture's byte_range
value($PATH.$NAME)           — Arc<str> from Capture.value
```

### Precedence / ambiguity rules

1. Bare `$NAME` with no dot prefix — resolved against the current cursor's captures (existing behavior, unchanged).
2. `&.$NAME` — CursorRef: resolved against the current cursor's captures (implicit `$SELF.$NAME`).
3. `&.$ROOT.path.$NAME` — CursorRef: explicit pipeline-tree address.
4. `$ROOT.…` in non-`&` position — future: value cross-reference, not yet designed.

Disambiguation: `$` prefix always means "pipeline-tree reference or capture binding." `&` prefix before a path expression always means "input-redirection directive." They are syntactically distinct; no precedence conflict.

### Relationship to labeled arms

`@pkg_arm: json({ … })` produces a `PathSeg::Named { name: "pkg_arm", … }`. The runtime addressing becomes `$ROOT.pkg_arm.$NAME`. Labels are sugar for stable named `SprfPath` segments. The addressing syntax subsumes labels: `switch($PATH { @arm: … })` resolves `$PATH` as a pipeline-tree query and `@arm` registers a `Named` seg. This means "switch on which pipeline-tree address the cursor comes from" — which is the correct semantic.

## 4. CursorRef `&.$X` Directive

### Parse-time representation

New variant in whatever type holds an op's compiled arguments. Currently, op arguments live in `OpInvocation` slots (`ParenSlot`, `BraceSlot`, `BracketSlot`) as raw `Arc<str>` source. The right place to add the representation is in the **compiled** (lowered) form, not the raw source slots.

Proposed addition to `_5_op.rs`, alongside `OpInvocation`:

```rust
/// A parse-time argument that can be either a literal value or a
/// redirection to a prior cursor's capture. Emitted by the host parser
/// when it sees `&.$NAME` or `&.$ROOT.path.$NAME` syntax in an op's
/// paren argument position.
#[derive(Debug, Clone)]
pub enum OpArg {
    Literal(Arc<str>),
    CursorRef(SprfPathPattern),
}

/// A pipeline-tree path pattern. Segments are either exact names, integer
/// indexes, or wildcards.
#[derive(Debug, Clone)]
pub struct SprfPathPattern {
    pub anchor: PathAnchor,
    pub segs:   Vec<PathPatternSeg>,
}

#[derive(Debug, Clone)]
pub enum PathAnchor { Root, Self_, Parent }

#[derive(Debug, Clone)]
pub enum PathPatternSeg {
    Name(Arc<str>),
    Index(u64),
    Wildcard,
    Capture(Arc<str>),   // terminal: `.$NAME`
}
```

`SprfPathPattern` is not `SprfPath` (which is a runtime address). It is a query pattern over the runtime address space — the distinction between a regex and a string.

At host parse time, `&.$CODE` becomes `OpArg::CursorRef(SprfPathPattern { anchor: Self_, segs: [Capture("CODE")] })`. `&.$ROOT.fs[0].json.$CODE` becomes the full anchored form.

### Resolution at runtime

Before `op.pipe` runs, the framework walks `OpArg` entries in the op's compiled arguments looking for `CursorRef` variants. For each CursorRef, it:

1. Resolves the `SprfPathPattern` against the current cursor's `path` and the `ResultStore` (for `$ROOT`-anchored refs) or directly against the cursor's captures (for `$SELF`-relative).
2. Looks up the referenced capture or cursor position.
3. Produces a `ResolvedRef`: either a byte-range + content pointer, or a string value.

The resolved ref is handed to the op as part of its constructed argument — the op never sees an unresolved `CursorRef` in its `pipe` call. The framework resolves before calling `pipe`.

The cursor handed to the op may have its `content` or `byte_range` or both overridden depending on what the op declared it needs. Concretely:

```
Before pipe:
  cursor.content    = Arc<Bytes> of foo.json (whole file)
  cursor.byte_range = Some(42..87)           (json narrowed to $CODE's span)
  cursor.slots      = { JSON_TREE }

Op arg: &.$CODE (CursorRef to $CODE capture)

Framework resolves:
  capture = cursor.captures["CODE"]
  byte_range = capture.byte_range  (42..87, same in this case)

Cursor handed to ast-grep:
  cursor.content    = unchanged (same Arc<Bytes>)
  cursor.byte_range = Some(42..87)   ← overridden to $CODE's span
  cursor.slots      = { JSON_TREE }  ← preserved
```

### Which fields are redirectable

**First-class (commit-shaped):**
- `byte_range`: redirect to the capture's byte span. This is the 90% case. `active_bytes()` returns `content[byte_range]` which is the redirected subtring.
- `content` replacement: for captures whose value is a self-contained embedded document (e.g. a JSON-in-JSON field that is itself valid JSON bytes), the redirect could substitute a new `Arc<Bytes>` synthesized from the capture value. Deferred — current `byte_range` narrowing handles the structural case. Needed only when the embedded content has different escaping from the host document (e.g. a JS template literal with `\n` escapes that need un-escaping before TS parsing).

**Deferred:**
- Slot redirect: `&.$S` pointing at a captured subtree's slot. Design is open (see open questions). Not first-class in commit 1 of CursorRef.

### Op opt-in mechanism

Ops declare which of their paren argument positions accept `CursorRef` via an associated method on `Op`:

```rust
fn redirectable_inputs(&self) -> &'static [&'static str] { &[] }
```

The names correspond to the op's declared input slot names. `ast-grep` declares `&["source"]`. If a `CursorRef` is applied to an op that doesn't include the target in `redirectable_inputs`, the host parser emits a parse-time error:

```
error[cursorref/not-accepted]: op `line` does not accept &-redirection on input `src`
```

This is the right level for the error: parse-time, before any runtime. The alternative (a trait method returning bool per name) was rejected in favor of the slice for scan-ability from the LSP (can complete `&.` in an op's paren by consulting `redirectable_inputs`).

The empty default `&[]` means existing ops are zero-change until they opt in.

### Error modes

| Condition | Diag code | Severity |
|-----------|-----------|----------|
| Referenced capture not in scope at the op's pipeline position | `cursorref/unresolved` | Error |
| Referenced span is in a different `fs` than the current cursor | `cursorref/cross-file` | Error |
| Referenced capture's value is not byte-range-backed (e.g. a number capture without `byte_range`) | `cursorref/no-span` | Error |
| `SprfPathPattern` matches zero cursors at runtime | `cursorref/empty-resolve` | Warn (same as xref/empty-join) |
| `SprfPathPattern` with wildcard matches >N cursors (cartesian) | `cursorref/cartesian-limit` | Warn |

`cursorref/cross-file` fires when `cursor.fs` at the redirected position differs from the current cursor's `fs`. This is a design error: `byte_range` is an index into `content`, and `content` is per-file. Cross-file span references have no valid interpretation under the current model. Future: could be relaxed if we introduce a "content overlay" mechanism, but default should be an error.

### Interaction with SlotKey reuse

If `&.$S` points to a capture that lives inside the same JSON subtree that `JSON_TREE` slot covers, the redirect should preserve the slot. Reasoning: the `JSON_TREE` slot's `AnyDataNode` root is the whole-file parse. Narrowing `byte_range` to `$S`'s span does not invalidate the slot — nodes within the slot's tree still have correct absolute positions. The downstream op (e.g. inner `json`) can still walk the slot's tree with a `byte_range` filter to restrict traversal to `$S`'s window.

Rule: `CursorRef` resolution **preserves all existing slots** unless the op explicitly replaces one. The only thing the framework changes is `byte_range` (and optionally `content`). Ops that need to invalidate an upstream slot do so in their own `pipe` logic.

## 5. Case Studies

### 5.1 `fs > read > json({ code: $CODE }) > ast-grep(&.$CODE, pat)`

`$CODE` is a JSON string field whose value is TypeScript source. The capture value is the unescaped string content (JSON op unescapes string values). The capture's `byte_range` spans the quoted string value in the JSON file including the quotes.

Decision: ast-grep receives `content` = the whole file bytes, `byte_range` = `$CODE`'s span excluding the quotes (or including — needs a "trim-delimiters" flag, see open questions). `active_bytes()` returns the raw TS source bytes. ast-grep parses `active_bytes()` with the TypeScript grammar.

This means ast-grep match offsets are relative to `byte_range.start`. When ast-grep stamps its own `byte_range` after a match, it offsets back to absolute: `absolute_span = byte_range.start + match_relative_start .. byte_range.start + match_relative_end`.

Whether to parse the JSON-escaped form or the unescaped form: parse the unescaped bytes. The JSON op (or the framework `CursorRef` resolver) synthesizes new `Arc<Bytes>` from `Capture.value` as the actual bytes ast-grep receives. This is the one case where `content` is replaced, not just `byte_range` narrowed: the JSON-escaped form may differ from the semantic bytes (backslash escapes). `byte_range` is then set to `0..value.len()` relative to the new content. The parent `content` (foo.json bytes) is carried as a separate field for hover/goto anchoring. This is the "embedded content replacement" path mentioned in section 4 — it belongs in CursorRef commit 1 as the primary value-as-source case.

Hop-by-hop:

| Hop | content | byte_range | slots | captures |
|-----|---------|------------|-------|----------|
| after json | foo.json bytes | 42..87 (CODE span) | JSON_TREE | { CODE: "…ts…" } |
| CursorRef resolution | Arc<Bytes> of TS source | 0..45 | JSON_TREE | { CODE: "…ts…" } |
| after ast-grep | Arc<Bytes> of TS source | 3..18 (match) | JSON_TREE, AST_GREP_TREE | { CODE: "…", NAME: "myFunc" } |

### 5.2 `fs > read > md({ fence(lang:ts): $BODY }) > ast-grep(&.$BODY, pat)`

From the prior memo's case study 4.3, now reframed under `CursorRef`:

- `md` narrows `byte_range` to the fence body (inside the backticks). Stamps `MD_TREE`, `LANG`.
- `&.$BODY` resolves to `$BODY`'s span inside the file — which is the same span `md` already set as `byte_range`. So the CursorRef here is a no-op on `byte_range` (the cursor is already narrowed to exactly `$BODY`). Its value is to be explicit in source: the reader sees `ast-grep(&.$BODY, pat)` and knows which content scope ast-grep is parsing. Without `&.$BODY`, the convention relies on implicit narrowing.
- The fence body is raw bytes (not escape-processed), so `content` does not need replacement — `active_bytes()` is correct directly.

This is the "structural narrowing" case: `&.$BODY` is documentation-as-syntax. The framework resolves it to the same `byte_range` that the upstream op already set, and sets it again (idempotent).

### 5.3 `fs > read > json({ a: $A, b: $B }) > switch($A { "foo": line(re: /x/, src: &.$B) })`

After `json`, cursor has `captures = { A: "foo", B: "…" }`.

`switch($A { "foo": … })` dispatches on `$A`'s value. The `"foo"` arm fires. The cursor entering the arm still carries `$B`.

`line(re: /x/, src: &.$B)` redirects line's source input to `$B`'s byte span.

Question: does `$B` survive the switch dispatch? Yes — all captures from upstream are carried through by the cursor clone. The switch is a `Pipeline::Switch` (currently `unimplemented!`) that produces a new `ForkArm`-tagged cursor per matching arm, but the capture map is preserved from the pre-switch cursor. `$B` is accessible inside the arm.

The resolution of `&.$B` uses `SprfPathPattern { anchor: Self_, segs: [Capture("B")] }` which resolves directly against `cursor.captures["B"]` — no pipeline-tree walk needed for `$SELF`-relative refs. This is the fast path.

### 5.4 `fs > read > json({ deps: $D }) > json(&.$D, { name: $N })`

Compare against nested json via positional chaining.

**Nested via positional chaining** (prior art, memo 4.2 path A): inner json reads `JSON_TREE` slot, restricts traversal to nodes within `byte_range`. `byte_range` is already set to `$D`'s span. Inner json uses the same `Arc<AnyDataNode>` but restricts its walker start to the node containing `$D`'s span.

**Via CursorRef** `json(&.$D, { name: $N })`: explicit redirection. Framework resolves `&.$D` to `$D`'s byte span, sets `byte_range = D.byte_range`. Inner json then uses slot-reuse path (JSON_TREE present, traverse within `byte_range`). Mechanically identical to positional chaining for JSON-in-JSON where `$D` is a JSON object or array value.

CursorRef form is cleaner when `$D` is a string containing embedded JSON (not a native JSON node) — then inner json would need to re-parse `active_bytes()` from scratch rather than sub-walking `JSON_TREE`. That's the non-trivial case CursorRef enables and positional chaining cannot express.

Preference: positional chaining (`json > json`) for native JSON nesting (cleaner DSL). CursorRef (`json(&.$D)`) for embedded-string JSON or cross-language parse.

## 6. Generic-Unlock Matrix

| Feature | Mechanism |
|---------|-----------|
| Cross-op back-references | `&.$ROOT.op[n].$NAME` addresses any prior capture by pipeline-tree coordinate |
| Named-arm switch | `@label` registers `PathSeg::Named`; `$ROOT.label.$X` is the addressing sugar |
| Hover/goto-capture | `span($ROOT.fs[*].json[*].$NAME)` — wildcard query against ResultStore to find all cursors bearing a capture |
| Diagnostic location precision | Attach diag at `SprfPathPattern` → resolves to exact pipeline-tree position + content span |
| Reactive re-eval | CursorRef edges are explicit data-flow edges; changing a node at path P re-runs all ops whose `&.$PATH` resolves through P |
| Stream composition / fan-out from capture list | `json({ deps: $LIST[]:* }) > ast-grep(&.$LIST_ENTRY, pat)` — each list element is a separate CursorRef; yields one ast-grep invocation per entry |
| LSP completion on `&.` | `redirectable_inputs()` + pipeline-tree address space → popup shows capture names + pipeline-tree positions in scope |
| Assumption-check edges | CursorRef edges are the "scan pointer" edges from `project_scan_pointer_runtime.md`; `Capture.scan_pointer` is a CursorRef expressed as a string address |
| Embedded-language parsing | `md > ast-grep(&.$FENCE_BODY)`, `json > ast-grep(&.$CODE_FIELD)` — any string capture becomes a parseable source |
| Span-accurate rewrite effects | A rewrite op targeting `&.$X` knows its byte range in the original file because `content` + absolute `byte_range` are preserved even when `active_bytes()` returns a sub-slice |

## 8. Open Questions

### 8.1 Quote-stripping in embedded content

When `$CODE` captures a JSON string value, does the CursorRef resolver produce the JSON-escaped bytes (with surrounding `"`) or the unescaped semantic bytes? The TypeScript parser needs unescaped bytes. This means the resolver must know that `$CODE` came from a JSON string context and call `AnyDataNode::string_value()` to get the unescaped form. How does the resolver know the capture's content type? Options:
- Add a `content_kind: CaptureKind` enum to `Capture` (string, number, bytes, etc.). The json op stamps it on emission.
- Resolve via the `JSON_TREE` slot: look up the node at `$CODE`'s byte_range and call `as_str()` on it.
- Require the op receiving the CursorRef to specify in `redirectable_inputs` whether it wants raw bytes or string-value. A richer descriptor than `&'static [&'static str]`.

The second option (resolve via slot) is the most principled and requires no changes to `Capture`. The resolver checks: if the current cursor has `JSON_TREE` and the referenced byte_range falls within a string node in that tree, call `as_str()` and synthesize new `Arc<Bytes>`. If no slot is present, use raw bytes.

### 8.2 Absolute byte_range after content replacement

When `content` is replaced (embedded-string case), `byte_range` is reset to `0..new_len`. But for hover/goto and diagnostic anchoring, the original file position must be recoverable. Proposed: add `origin_byte_range: Option<Range<usize>>` to `Cursor` alongside `byte_range`, set when content is synthesized. The framework and LSP use `origin_byte_range` for source location; `byte_range` is the scan window. This is a separate field because the invariant "byte_range indexes into content" must be maintained.

### 8.3 Slot redirect: can `&.$S` redirect a slot rather than bytes?

Example: `json(&.$D, { name: $N })` where `$D` is a JSON object node. Could the framework redirect the `JSON_TREE` slot to a sub-rooted `AnyDataNode` rooted at `$D` instead of passing full-file bytes + byte_range window? This would give the inner json op a cleaner traversal (no range check needed) and matches the "preserve slot, sub-root it" idea from section 4. Design is open: requires the resolver to know how to sub-root a slot value, which requires a per-slot-type callback. Not first-class in commit 1. Deferred to "slot redirect protocol" future memo.

### 8.4 Cartesian explosion with wildcards

`&.$ROOT.fs[*].json[*].$CODE` when used inside a later op creates a M×N cursor expansion: for every prior cursor matching the wildcard, one redirected input. This is the same problem as xref cartesian limit. The same guard (`xref_cartesian_limit`) should apply. But the cursor shape is different from cross-rule xref: here the inputs are from the same pipeline branch, not a foreign rule. The guard must distinguish between "redirect from same branch" (likely fine) and "redirect from arbitrary upstream branch" (cartesian risk). Open question: does the resolver need a separate limit or is the xref limit reused?

### 8.5 `byte_range` monotonicity vs CursorRef override

The current `byte_range` narrowing protocol (memo 4 section 3.3) states narrowing is monotonic within a file — ops narrow further or stay at current window. CursorRef breaks this if `&.$X`'s span is wider than the current `byte_range`. Example: `json` narrows to `$A`'s span (10..50), then `&.$B` redirects to `$B`'s span (5..80) which is wider. The framework should allow this: CursorRef is explicitly setting a new scope, not continuing a narrowing chain. The monotonicity rule applies to implicit narrowing (op-driven), not explicit redirection (user-driven). Rule update: "byte_range monotonicity applies absent a CursorRef; a CursorRef resets the monotonicity baseline."
