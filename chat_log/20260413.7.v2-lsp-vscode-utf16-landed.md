## Problem/Context
Hover was drifting onto wrong lines in VS Code (screenshot showed `rule/unknown-body-op` diag squiggle landing on `# ── File completions ──` comment). Initially suspected parser comment-handling bug. Traced through `skip_trivia` in `_8_parse.rs` — `#` comments correctly swallowed at both top-level and brace-body entry via `host_parse_inner`. Real cause: em-dashes (`──` = U+2500, 3-byte UTF-8, 1-utf16-unit) earlier in file shifted all downstream ranges when LSP used char-count approximation instead of utf16.

User directive on fix: hand-roll utf16, no new crate dep, put it in lib (common code for any future consumer, not just the LSP bin). Done.

Second issue surfaced at session end: `${base_rule.$TAG}` cross-ref inside json body. User correctly called out — cross-ref has two layers, only hover landed:
- HOVER cross-ref: DocSession.hover_at resolves `${rule.$VAR}` → target op's hover_capture. Works.
- SEMANTIC cross-ref: walker using `${base_rule.$TAG}` as a runtime filter. Walker's `parse_segment_pattern` only handles `${IDENT}`, not `${IDENT.$VAR}`. Rejected as parse error at walker level. Not implemented.

## Solution/Approach
Minimal, honest fixes:
- v1 extension already parameterized by `sprf.serverPath`. No new extension needed. One settings.json edit.
- `v2/src/position.rs` module with plain-u32 signatures (no tower-lsp types) so it stays reusable. LSP bin imports and wraps with `Position { ... }` at the boundary.
- utf16 per-char increment uses `ch.len_utf16() as u32`. Overshoot-check added: if consuming next char would cross `utf16_col`, return current byte index (rounds down into char start). This passes the mid-surrogate test that initial impl failed.
- Debug loop: wrote 6 tests first, one failed, diagnosed increment-ordering bug, added overshoot-check, all green.

Initial test failure case: `position_to_offset("x🦀y", 0, 2)` returned 5 instead of 1. Loop was checking `cur_col >= utf16_col` BEFORE incrementing, then incrementing past the target. Fix: add a second check `cur_col + step > utf16_col` that rounds down at the char whose consumption would overshoot.

## Key Insights
- **User-space reuse of the v1 extension is zero-cost** when the extension parameterizes the server binary path. Worth noting as a pattern when forking/rewriting a subsystem.
- **UTF-16 position bug hid as parser bug.** When diagnostics drift onto wrong lines, suspect position translation BEFORE suspecting parse logic. Multi-byte chars earlier in the file (em-dash, box-drawing chars, emoji) shift all downstream ranges.
- **Overshoot-check pattern for surrogate-aware position math:** `if cur_col + step > target { return i; }` rounds the position down into the current char's start rather than advancing past it. Without this, a column landing inside a surrogate pair skips the char entirely.
- **ASCII approximation is fine until a file has em-dashes.** Common .sprf files will hit this the moment anyone writes a section divider comment.
- **Cross-ref is two separate features.** Hovering on a cross-ref and USING a cross-ref to filter runtime matches are different layers. Hover is pure in-memory post-run; semantic filter requires run ordering + result sharing. Easy to conflate.
- **v1 VS Code extension is already built** (`out/` dir committed). No npm install needed if the compiled bundle is fresh.
- **User hit a settings.json routing issue** (workspace settings.json was overriding user settings.json). Checking both files before reload-window is the general diagnostic path.

## Open Questions
- Should `${rule.$VAR}` semantic cross-ref use a set-membership filter or a direct-join? Set filter is simpler (just `HashSet<Arc<str>>` per cross-ref slot). Join semantics (where derived_rule.$TAG aligns to a specific base_rule row) would need row-id tracking. Defer to when a real use case forces it.
- Walker's `parse_segment_pattern` supports `${IDENT}` for capture interpolation within a string template. Is `${IDENT.$VAR}` a sibling pattern at the segment level, or a separate leaf kind (since it's a reference into another rule's output set)? Probably sibling syntax, different semantics.
- Do we want the LSP to highlight `${rule.$VAR}` when the target rule's runtime evaluation has zero matching rows? This is a useful "nothing to reference" warning. Needs hover_* to know about emptiness — current render probably handles it via hover_capture returning a placeholder.
- LSP smoke test uses subprocess + stdio JSON-RPC. Slow. `tokio::io::duplex` + in-proc LspService would be faster but needs more wiring. Maybe next session.
