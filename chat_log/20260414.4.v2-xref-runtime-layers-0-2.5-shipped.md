## Problem / Context

User design corrections that shaped the architecture:
- LSP/CLI are pure transports — no language semantics in those crates. ResultStore + analysis live in core.
- `$VAR` ≡ `${VAR}` synonymy. Braces only required for disambiguation (`${rule.$VAR}` xref form, adjacency).
- Row-based ResultStore, not value-set-based. Stores per-rule `Vec<CaptureMap>`.
- Cartesian (not zip) across multi-xref targets. Explosion guard with Warn diag.
- Output-candidate dedup, not source-row dedup. Per-input-cursor `HashSet<tuple>`.
- Empty source set is meaningful — `xref/empty-join` Hint at byte_range, drop cursor. Filters culling all candidates is a separate non-signal.
- Option (b) additive `crossrefs` field on `OpInvocation` rather than full SlotRef refactor.

User delegation patterns:
- Subagent for Layer 2 with mandatory pre-set test plan.
- Subagent prompt scoped tight — no runner work, no LSP/CLI, no new deps.
- Doc comments on important types as a separate explicit pass after impl landed.

## Solution / Approach

Architecture today:
- **Parse time** — host parser scans paren/bracket/brace slots for `${...}` tokens via raw text scan (`_8_parse.rs::scan_slot_crossrefs`). Capture vs xref disambiguated by `.` in inner.
- **Lower time** — `lower_chain` wraps `Arc<dyn Op>` in `LoweredOp` with `Arc<[CrossRefOccurrence]>` from `inv.crossrefs` (via `From<Arc<T>>` impl, no per-op change). `RuleFactory::parse` collects de-duped target rule names into `RuleHandle.depends_on`. `_11_dag::build` runs Kahn's; cycle → `xref/cycle` diag in `DocSession::load`.
- **Runtime** — `Pipeline::run_with_step` splices `expand_xrefs(input, lop.xrefs.clone(), ...)` ahead of `op.pipe`. Adapter cartesian-products source rows from `ctx.result_store.rows_of(rule)`, dedups output tuples in xref declaration order, seeds captures on cloned cursors. Empty target → drop + Hint. Distinct tuple count > limit → drop + Warn. Walker constrains-when-prebound on those seeds, so non-matching branches prune cleanly.
- **Runner write path** — NOT YET WIRED. `_7_runner.rs` is skeletal. ResultStore is read-only at runtime today.

## Key Insights

- Cross-ref is universal syntax. One framework adapter (`expand_xrefs`) covers every op. Wrapper-not-trait-method (`LoweredOp`) preserves Op trait cleanliness.
- Constrain-when-prebound is the unifying mechanism. `$VAR`, `${VAR}`, `${rule.$VAR}` all lower to `Leaf { capture: Some(VAR) }`. Walker auto-gates against any pre-bound value. Cross-ref seeding becomes "just another way to pre-bind a capture."
- Row-based ResultStore + cartesian + dedup beats value-set semantics. Multi-var pulls from one source rule (`${a.$X}` and `${a.$Y}` on same op) get aligned tuples instead of independent expansions.
- Output-candidate dedup makes explosion guard linear in distinct seeded tuples, not raw cartesian product. 100 source rows × 5 distinct values = 5 candidates.
- Walker's `rule` component is purely declarative at parse time (drives DAG and `OpInvocation.crossrefs` discovery). Lowered `SelectStep::Leaf` carries only `var`. Seed wiring connects walker to source data via `OpInvocation.crossrefs`.
- Subagent delegation works well when: (a) brief is self-contained with full prior-state recap, (b) test plan is mandatory and pre-set, (c) guardrails enumerate explicit do-nots (no runner work, no new deps).
- v1's `crates/rules/src/graph.rs` Kahn implementation translated cleanly. v2 deviates only in: separating `Ordered{levels}` vs `Cycle{path}` as enum variants instead of error, and skipping unknown-producer edges (already diag'd elsewhere in v2).

## Open Questions

- Provenance multi-cursor seeding: `$$repo` is per-cursor (`cursor.repo`), but if 5 input cursors have 3 distinct repos, does an op with `$$repo($R)` cartesian over distinct repos? Probably 1:1 since provenance is inherent to the cursor.
- Fork arms × xrefs: current `Pipeline::run_with_step` runs adapter per-`Pipeline::Op`. Forks split before, so each arm independently expands. No test coverage.
- Cycle diag anchor: single `XRefDiag::Cycle` per cycle vs one per rule in cycle vs multi-site? LSP UX trade-off.
- ResultStore concurrent writes: `Mutex<HashMap>` + per-rule `Mutex<Vec>` in critical path of every emitted cursor. May need `DashMap` upgrade when Layer 5 lands and runner is parallel.
- Should walker's lowered `Leaf` retain `rule` component for diag purposes? Today it doesn't; `xref/empty-join` etc. fire from `expand_xrefs` against `OpInvocation.crossrefs`, so the walker doesn't need it. But walker-anchored xref diags would.
