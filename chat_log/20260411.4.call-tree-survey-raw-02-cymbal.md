## cymbal

- language: Go 1.25
- runtime: CGO required (SQLite + tree-sitter bindings)
- build: `CGO_ENABLED=1 CGO_CFLAGS="-DSQLITE_ENABLE_FTS5" go build -o cymbal .`
- license: MIT (George Dikeakos, 2026)
- store: SQLite3 with FTS5 extension
- store_file_path: `~/.cache/cymbal/repos/<hash>/index.db` (Linux), `~/Library/Caches/cymbal/repos/` (macOS), `%LOCALAPPDATA%\cymbal\repos\` (Windows); overridable via `CYMBAL_DB` env or `--db` flag
- schema_shape: 7 tables (meta, files, symbols, imports, refs, symbols_fts virtual); 7 indexes + 2 triggers; file-scoped refs with line numbers
- extractor: tree-sitter AST walk via language-specific node-type dispatch
- languages_supported: Go, Python, JavaScript, TypeScript, TSX, Rust, C, C++, C#, Java, Ruby, Swift, Kotlin, Scala, PHP, Lua, Bash, YAML, Elixir, HCL/Terraform, Protobuf, Dart, Apex (22 total)
- locals_resolution: Syntactic; line-based symbol scope via start_line/end_line range queries (EnclosingSymbol)
- call_edge_model: Name-based matching; refs table stores (file_id, line, name, language); edges reconstructed post-hoc via EnclosingSymbol(file, line) lookup
- call_order_preserved: Yes; line numbers stored per ref in refs table (parser.go:331, store.go:57-62)
- branch_path_preserved: No; single file path per ref, no branch/commit info tracked
- cross_file_resolution: Yes; imports table exists but not directly wired to call-graph traversal; FindImporters traverses separately via file import matching
- query_surface: FindTrace (downward BFS, 3-5 depth limit), FindImpact (upward BFS, 2-5 depth, up to 100 results), FindReferences (simple name match), Investigate (adaptive result selection), SearchSymbols (FTS5 prefix + exact match), SymbolContext (bundled: source + type refs + callers + imports)
- interop: JSON output flag on all commands; library API via four exported packages (index, parser, symbols, walker)
- incremental: Yes; per-file mtime+size fast-path (index.go ~22-27ms when unchanged); auto-reindex on dirty files before queries
- loc_approx: 1800+ LOC (parser.go 1200+, store.go 1300+, index.go 600+)
- core_files: `/index/index.go`, `/index/store.go`, `/parser/parser.go`, `/symbols/types.go`, `/walker/walker.go`, `/cmd/*.go`
- call_extraction_mechanism: Language-specific dispatcher (parser.go:301-320) → node-type checks → ChildByFieldName lookups; stored as (name, line) with language tag; Go/JS/TS/Rust/C/C++ check `call_expression` (parser.go:324), Python checks `call` (parser.go:338), JVM langs check `method_invocation` (parser.go:352), Ruby checks `call` or `method_call` (parser.go:363), Elixir checks `call` (parser.go:388)
- partial_tree_support: No; requires full file parse; no incremental tree deltas or range parsing
- unique_ideas: (1) Builtins/stdlib filtering in FindTrace (parser.go:1256-1279) — hardcoded skip list for common false positives; (2) EnclosingSymbol (store.go:1168-1181) — finds narrowest (smallest line-span) symbol containing a given line, enables caller inference without explicit call-target annotation; (3) JIT freshness — mtime+size check auto-triggers reindex, no manual indexing or watch daemons; (4) Dual call-chain queries — trace (downward callees) and impact (upward callers) with separate BFS logic (store.go:1195, 1319); (5) FTS5 triggers on symbol_ai/ad — automatic full-text index sync on insert/delete
- wasm_embeddable: No; requires CGO and C FFI for tree-sitter + SQLite
- stdin_stdout_friendly: Yes; all commands support `--json` for machine-readable output; JSON marshaled via encoding/json; used in library mode for agent integration

## Analysis

### Call Extraction & Visitor Pattern

cymbal walks tree-sitter ASTs via recursive `symbolExtractor.walk()` (parser.go:126-160). Per-node dispatch checks three categories: (1) imports via `extractImport()`, (2) call expressions via `extractRef()`, (3) symbol definitions via `nodeToSymbol()`. The walk is preorder: parent checked before children, enabling parent-tracking for nested scopes.

Call extraction is language-specific. The dispatcher `extractRef()` (parser.go:301-320) maps language → extractor function:
- **Go/JS/TS/Rust/C/C++**: `extractRefCallExpr()` checks `node.Type() == "call_expression"`, extracts function via `ChildByFieldName("function")`, resolves final name through `extractCallName()` (parser.go:420-460). For C/C++, handles `::`, `->`, `.` chaining and template specialization (`std::max<int>` → `max`).
- **Python**: `extractRefPythonCall()` checks `node.Type() == "call"`.
- **JVM (Java/Scala/Apex)**: `extractRefJVM()` checks `node.Type() == "method_invocation"`, extracts `name` field directly.
- **Ruby**: `extractRefRuby()` accepts `call` or `method_call` node types, extracts `method` field (parser.go:363).
- **Elixir**: `extractRefElixir()` checks `call`, then traverses children to find identifier or dot-separated members (parser.go:387-412).
- **Dart**: `extractRefDart()` reconstructs calls from sibling sequences (parser.go:1067+, comment notes Dart encodes calls as sibling chains, not nested AST).

**Resolution model**: Lexical only. Each ref stores (file_id, line, name, language) in the refs table (store.go:57-62). No scope chain, no binding resolution, no function signature matching. Semantic call-target inference happens post-hoc: FindImpact calls `EnclosingSymbol(file, line)` to find which symbol encloses the call site (store.go:1349), then traverses upward to callers.

**Source order preservation**: Yes. Parser.go:331 captures `int(node.StartPoint().Row) + 1` as the line number. refs table has explicit `line` column (store.go:60). FindTrace/FindImpact query results are ordered by depth level in BFS order, but individual results within a depth preserve file/line ordering via SQL `ORDER BY f.rel_path, r.line` (store.go:932).

### FindTrace Implementation

`FindTrace()` (store.go:1195-1316) performs downward call-graph traversal (callees of a function):

1. **Resolve root symbol**: Query symbols table for exact name match, extract file path and line range (start_line, end_line).
2. **Find callees**: For each symbol location, query refs table: all refs whose line falls within [start_line, end_line] and file matches. These refs represent calls made by that symbol.
3. **Filter builtins**: Hardcoded skip list (parser.go:1256-1279) removes false positives: Go builtins (`len`, `make`, `append`), stdlib methods (`Error`, `String`, `Close`, `Read`, `Write`, `Lock`, `Unlock`), type casts (`int`, `float32`, `string`, `bool`). Skip single-letter or 2-char names (assumed loop vars or generics).
4. **BFS traversal**: For each depth d in [1, depth_limit], resolve callees of current level to get next level. Dedup with `seen` map (key: `caller + "→" + callee`). Emit TraceResult with depth field.
5. **Termination**: Stop at depth limit (default 3, max 5) or result limit (default 50, configurable).

**Edge model**: Each TraceResult is a (Caller, Callee, File, Line, Depth) tuple. File and Line pinpoint the call site. Caller and Callee are symbol names, not file-qualified or fully-resolved.

### FindImpact Implementation

`FindImpact()` (store.go:1319-1381) performs upward transitive-caller analysis (what calls this symbol):

1. **Initialize**: Start with input symbol name.
2. **Find references**: Query refs table for all refs matching the symbol name. For each ref (file_id, line, name):
   - Call `EnclosingSymbol(file, line)` to find the function/scope containing that line.
   - Skip if enclosing symbol is empty, matches the input symbol itself, or is already seen (dedup by caller + file path).
3. **BFS levels**: For each depth d, collect all unique callers from current symbol set. Append to results with depth d.
4. **Termination**: Stop at depth limit (default 2, max 5) or result limit (default 100).

**EnclosingSymbol query** (store.go:1168-1181): Find the narrowest symbol by selecting the symbol with smallest (end_line - start_line) span that encloses the query line. Uses `ORDER BY (s.end_line - s.start_line) ASC LIMIT 1`.

### SQLite Schema

```sql
CREATE TABLE IF NOT EXISTS files (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  path       TEXT UNIQUE NOT NULL,
  rel_path   TEXT NOT NULL,
  language   TEXT NOT NULL,
  hash       TEXT NOT NULL,
  indexed_at DATETIME NOT NULL,
  mtime      DATETIME,
  mtime_ns   INTEGER,
  size       INTEGER
);

CREATE TABLE IF NOT EXISTS symbols (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  file_id     INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,
  kind        TEXT NOT NULL,
  start_line  INTEGER NOT NULL,
  end_line    INTEGER NOT NULL,
  start_col   INTEGER,
  end_col     INTEGER,
  parent      TEXT,
  depth       INTEGER DEFAULT 0,
  signature   TEXT,
  language    TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS refs (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  file_id   INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
  line      INTEGER NOT NULL,
  name      TEXT NOT NULL,
  language  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS imports (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  file_id   INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
  raw_path  TEXT NOT NULL,
  language  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

CREATE VIRTUAL TABLE IF NOT EXISTS symbols_fts USING fts5(
  name,
  kind,
  content=symbols,
  content_rowid=id
);

CREATE TRIGGER IF NOT EXISTS symbols_ai AFTER INSERT ON symbols BEGIN
  INSERT INTO symbols_fts(rowid, name, kind) VALUES (new.id, new.name, new.kind);
END;

CREATE TRIGGER IF NOT EXISTS symbols_ad AFTER DELETE ON symbols BEGIN
  INSERT INTO symbols_fts(symbols_fts, rowid, name, kind) VALUES('delete', old.id, old.name, old.kind);
END;

CREATE INDEX IF NOT EXISTS idx_symbols_name ON symbols(name);
CREATE INDEX IF NOT EXISTS idx_symbols_kind ON symbols(kind);
CREATE INDEX IF NOT EXISTS idx_symbols_file ON symbols(file_id);
CREATE INDEX IF NOT EXISTS idx_files_path ON files(path);
CREATE INDEX IF NOT EXISTS idx_imports_raw ON imports(raw_path);
CREATE INDEX IF NOT EXISTS idx_imports_file ON imports(file_id);
CREATE INDEX IF NOT EXISTS idx_refs_name ON refs(name);
CREATE INDEX IF NOT EXISTS idx_refs_file ON refs(file_id);
```

**Key design**:
- symbols.parent is TEXT (symbol name, not ID), enabling parent-tracking across file boundaries without join.
- symbols.start_line/end_line define scope, used for EnclosingSymbol range queries.
- refs stores only (file_id, line, name, language), not call targets — targets inferred via EnclosingSymbol.
- FTS5 virtual table mirrors symbols(name, kind) for full-text search; triggers keep it in sync on insert/delete.

### Indexing & Batch Write

Index (index.go) walks file tree (walker package), parses each file (parser.ParseFile), and batches results into SQLite.

**Batching**: flushBatch() (index.go:126+) prepares statements once per batch (PrepareBatchStmts), uses SAVEPOINTs per file so one failure doesn't corrupt the whole batch. Batch size determined by row count (symbols + imports + refs).

**Incremental refresh**: Before each query, ensureFresh() checks file mtimes. If a file is modified, it's re-parsed and re-indexed. mtime+size lookup takes ~10-24ms when nothing changed (index.go line comments).

### Query Surface & Command Mapping

High-level commands (cmd/*.go) wrap store functions:

- **trace**: calls index.FindTrace(dbPath, symbolName, depth, limit); outputs TraceResults grouped by depth.
- **impact**: calls index.FindImpact(dbPath, symbolName, depth, limit); outputs ImpactResults grouped by depth, with source context lines.
- **refs**: calls index.FindReferences(symbolName, limit); simple symbol name lookup.
- **search**: FTS5 search via SearchSymbols (exact or prefix) or full-text grep via SearchText.
- **show**: calls SymbolsByName(name); outputs source lines for a symbol.
- **investigate**: adapter command that calls different handlers based on symbol kind (function → trace + refs, type → members + refs, etc.).
- **context**: calls SymbolContext(); returns bundled (source + type refs + callers + imports).
- **importers**: calls FindImporters() or FindImportersByPath(); separate BFS for import graph.
- **structure**: structural analysis (RepoStructure); computes top-by-refs, entry points, package graph.

All commands accept `--json` flag for JSON marshaling via encoding/json.

### Extension Points

1. **Language support**: Add tree-sitter grammar to languages map (parser.go:35-58), then add node-type checks in extractRef/extractImport dispatchers.
2. **Symbol kinds**: classifyNode() (parser.go:462+) maps node types to kind strings (function, type, variable, etc.). Language-specific classifiers exist.
3. **Query customization**: FindTrace/FindImpact are store methods; callers can fork and modify BFS logic, depth limits, filtering rules.
4. **Store plugin**: Store struct exposes db (*sql.DB), enabling custom SQL queries alongside cymbal's built-in queries.

### Partial Tree & Incremental Parsing

No support. Parser requires full file contents (ParseFile, ParseBytes, ParseSource). No range-based delta parsing. However, file-level incremental indexing is automatic: only changed files are re-parsed via mtime check.

### Performance Characteristics

- **Parsing**: ~9-27ms per query on repos with 1-10K files (README benchmarks vs ripgrep).
- **Reindex (nothing changed)**: ~8-20ms fast path via mtime+size.
- **Reindex (1-5 files changed)**: ~22-43ms.
- **Index size**: Not specified, but typical SQLite index for a large repo is 100-500 MB.
- **Token efficiency**: 17-100% fewer tokens than ripgrep for targeted lookups; refs queries show 3-100% savings.

### Agent Integration

Designed explicitly for AI agents. README includes boilerplate system prompt sections for native and Docker installations. Library API exported (four packages) for programmatic use. All commands produce JSON.

### Uniqueness Relative to Similar Tools

1. **Per-file, name-based refs** — unlike LSP (which tracks file+line→name bindings), cymbal stores just (file, line, name) and infers scope post-hoc. This trades semantic fidelity for simplicity and cross-language portability.
2. **Narrowest-scope symbol selection** — EnclosingSymbol uses line-span magnitude to break ties, ensuring nested function/method calls resolve to the most specific enclosing scope.
3. **Builtin filtering** — FindTrace explicitly skips hardcoded stdlib/builtin names, reducing noise in call traces.
4. **JIT freshness** — auto-reparse on mtime+size change, no manual reindex or watch daemons.
5. **Dual direction** — FindTrace (downward, what-does-it-call) and FindImpact (upward, what-calls-it) as first-class queries, not derived from a single call graph representation.
