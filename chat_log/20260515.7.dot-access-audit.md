# Dot-Access Audit: v4 Hole Syntax

**Date:** 2026-05-15
**Scope:** read-only audit of `/Users/chrishafley/projects/sprefa/v4/src/`

---

## TL;DR (5 bullets)

1. Dot-access is parsed universally in `default_plain_dsl_parse` (op_def.rs:301), but the SEMANTIC implementation lives entirely in `Cursor::get` (lib.rs:513) as a flat-key compatibility shim — not a real tree walk. `${X.field}` resolves to `cursor.get("X.field")`, which mangles to `X_FIELD` via a `format!("{}_{}", stem, field.to_ascii_uppercase())` fallback.
2. `str`, `sh`, `path`, `json` (slow path), `ast` (slow path) ACCEPT dot-access by routing through `render_segments` / `render_segments_no_diag`; `glob` and `re` both hard-reject it at lower time (`ops.rs:710`, `ops.rs:1388`). `where` / `sql_where` strip the `?` suffix but pass the raw name (including a `.`) directly to `cursor.get`, so dot-access WORKS there incidentally via the same shim.
3. The ONLY tested `${&.field}` form is `${&.value}` in sql (ops.rs / sql.rs:897), which is special-cased to `"input"."value"`. All other `${&.field}` forms are rejected by sql; in `str`/`sh` they route through `cursor.get("&.field")` which hits the `&` branch in `Cursor::get` and translates `field` to `UPPERCASE` then self-recursion.
4. `${X.foo.bar}` (nested) is NOT supported. `parse_term_shape` (op_def.rs:428) consumes exactly one `.IDENT` segment; a second `.` causes `j != bytes.len()` → `None` → SubPipe fallback. At runtime the SubPipe body `X.foo.bar` is re-parsed as a sprf pipe fragment and fails.
5. `FormatComponent` (v2_ops.rs:1381) has its own regex-based hole scanner that does NOT handle dot-access: `r"\$\{([A-Za-z_][A-Za-z0-9_]*)\}"` — a third inconsistent implementation. This means `format` silently drops `${X.field}`.

## Phase 1 — Where Is Dot-Access Parsed?

### `parse_term_shape` — `op_def.rs:428`

```
Grammar:
  inner   = "&.field"
           | IDENT
           | IDENT "?"
           | IDENT ".field"
           | IDENT "?." field   ← parsed, rejected upstream
```

- Parses `IDENT` / `&` as stem.
- Parses optional `?` → `InterpMode::Bind`.
- Parses optional `"." IDENT` → `field: Some(Arc<str>)`.
- Requires `j == bytes.len()` — strictly no trailing characters.
- Single-level field only. No `a.b.c`.

Called by `default_plain_dsl_parse` (op_def.rs:301) which is the universal host pre-pass invoked for every DSL body at walk time.

### `Cursor::get` — `lib.rs:513`

The actual field-access implementation:

```rust
pub fn get(&self, name: &str) -> Option<&str> {
    // 1. Exact match on focal term (&) or "&.value"
    if name == FOCAL_TERM || name == "&.value" {
        return Some(self.focal().value.as_ref());
    }
    // 2. Exact match on a named term
    if let Some(term) = self.terms.iter().find(|t| t.name.as_ref() == name) {
        return Some(term.value.as_ref());
    }
    // 3. Dotted compatibility shim
    if let Some((stem, field)) = name.split_once('.') {
        if stem == "&" {
            // &.value → focal; &.OTHER → cursor.get(OTHER.to_uppercase())
            return match field {
                "value" => Some(self.focal().value.as_ref()),
                other => self.get(other.to_ascii_uppercase().as_str()),
            };
        }
        if field == "value" {
            return self.get(stem);  // X.value → X
        }
        // X.field → X_FIELD
        let key = format!("{}_{}", stem, field.to_ascii_uppercase());
        return self.get(key.as_str());
    }
    None
}
```

**Key facts:**
- `${X.field}` concatenates to `"X.field"` as the lookup key.
- First tries to find a term literally named `"X.field"` (none ever set this way today).
- Falls through to split-on-`.` shim: `X.field → X_FIELD`.
- This is a flat-namespace CamelCase→SCREAMING_SNAKE translation, not structural navigation.
- `${&.value}` → focal value (two code paths, same result).
- `${&.other}` → `cursor.get("OTHER")` — i.e., any focal coord field normalized to CAPS.

**Semantic model for accepted DSLs:**

`${X.field}` does NOT navigate structure. The resolution chain is:
1. Look for a term literally named `"X.field"` (never exists in practice).
2. Fall through to: `X_FIELD = cursor.get("X_FIELD")` (i.e., look for a term whose name is `X` with underscore-separated `FIELD`).

This means `${X.field}` is today purely syntactic sugar for `${X_FIELD}` with the field component uppercased.

## Phase 3 — Where Would `${X?.field}` Make Sense?

Currently rejected at `op_def.rs:326–328`:
```rust
let illegal = (is_focal && field.is_none())      // ${&}
    || (is_focal && matches!(mode, InterpMode::Bind))  // ${&?...}
    || (matches!(mode, InterpMode::Bind) && field.is_some());  // ${X?.field}
```

### Possible semantics for `${X?.field}`

**Option A: Bind X, then access .field of the bound value**
- Parse: `X?` binds the focal value to `X`, THEN `.field` accesses a property of the thing just bound.
- Problem: The bind (capture) writes `cursor.get("&")` to `cursor["X"]`. If `.field` then accesses `cursor["X"].field`, that requires a second level of indirection — the cursor value is a flat string, not a struct.
- Verdict: Wrong. Cursor terms are flat strings. There's no object to navigate.

**Option B: `${X?.field}` means "bind X.field = focal value"**
- Introduces a new term named `"X.field"` (or `"X_FIELD"`) bound to the focal cursor value.
- No other bind form does this; it would be the first field-qualified binder.
- The binding graph currently ignores `field` for bind mode — it would need to track `"X_FIELD"` as a new distinct term.
- Possible but weird. Naming a bound term `X_FIELD` when the source wrote `X?.field` is confusing.

**Option C: `${X?.field}` is a syntax error (current)**
- Simplest rule: bind mark and field access are mutually exclusive.
- Rationale: `?` introduces a new name. Field access reads an existing one. These purposes don't compose on the same token.
- This is the status quo and it's defensible.

**Option D: `${X.field?}` — alternative postfix ordering**
- Postfix `?` after the field: "read X.field and bind the result to some implicit name."
- But binding requires a name to write to — what's the target? `X_FIELD`? Awkward.
- Would need syntax like `${X.field as Y?}` which is a different feature entirely.

**Recommendation:** Keep `${X?.field}` rejected. If the need is "capture a field value under a new name," express it as two steps: `${X?}` to capture, then a downstream `str` or `where` to project the field.

## Phase 4 — Dot-Access in the Broader Grammar

### 4.1 Nested dot-access `${X.foo.bar}`

**Current state:** NOT supported.

`parse_term_shape` at op_def.rs:458–468 parses exactly one `.IDENT` suffix. After consuming `X.foo`, `j` sits at the `.bar` substring. The `j != bytes.len()` check at line 471 fails, so `parse_term_shape` returns `None`. The whole `${X.foo.bar}` is then classified as a SubPipe by the fallback at op_def.rs:352–368. The SubPipe body is `X.foo.bar`, which is re-parsed as a sprf pipe fragment and fails at walk time (no op named `X` exists).

To support nested dot-access, `parse_term_shape` would need to collect a Vec of field segments, and `Cursor::get` would need a recursive or iterative lookup.

### 4.2 Indexing `${X[0]}`, `${X["key"]}`

**Current state:** Not supported, not even parsed. `[` is not in `parse_term_shape`'s grammar; the whole hole falls to SubPipe. At runtime, the inner text `X[0]` fails as a pipe fragment.

### 4.3 Method calls `${X.length()}`, `${X.upper()}`

**Current state:** Not supported. `(` is not in `parse_term_shape`; falls to SubPipe. `X.length()` fails as a pipe fragment.

The partial substitute today: SubPipe form `${ term(:X) > transform }` — the SubPipe path handles `${ <pipe> }` as a full sprf expression. This is the intended mechanism for computed values.

### 4.4 Pipe-through `${X | length}`

Not the model (per user). The intended surface is JS template literal style: `${...}` is purely interpolation, not a transformation pipeline.

### 4.5 Where Is the Line?

The tension: dot-access is a "mini-expression," but the grammar should not become a sub-language. The conservative boundary:

- ALLOWED: `${X.field}` (property access, single level), `${X.foo.bar}` (chained, still read-only navigation).
- NOT ALLOWED: `${X.length()}` (method invocation), `${X[0]}` (index access with computed key), `${X + 1}` (arithmetic), `${ X | op }` (pipe).

Rationale: property access (`a.b.c`) navigates structure without changing it. Method calls and operators transform values, which is what SubPipe `${ ... }` is for.

## Phase 5 — Precedence Sketch

### Current tokens inside `${...}`

| Token | Meaning |
|-------|---------|
| `IDENT` | term name stem |
| `&` | focal cursor self-reference |
| `?` | postfix bind marker |
| `.IDENT` | postfix field access |

### Current postfix exclusion rule

`?` and `.field` are mutually exclusive (enforced by the `illegal` bitmask, not by grammar).

### Proposed grammar (composable dot-access)

```
hole       = "${" expr "}"
expr       = primary postfix*
primary    = "&" | IDENT
postfix    = "?" | ("." IDENT)+
```

Note: `"." IDENT` repeats to allow chaining. `?` is a single-occurrence postfix.

### Mutual exclusion table

| Form | Parses as | Meaning | Accept? |
|------|-----------|---------|---------|
| `${X}` | primary | read term X | YES |
| `${X?}` | primary + `?` | bind X = focal | YES |
| `${X.field}` | primary + `.field` | read X's field | YES |
| `${X.a.b}` | primary + `.a` + `.b` | read X's nested field | proposed YES |
| `${&.field}` | `&` + `.field` | read focal's field | YES |
| `${X?.field}` | primary + `?` + `.field` | ambiguous; rejected | NO |
| `${&}` | `&` alone | ambiguous; rejected | NO |
| `${&?}` | `&` + `?` | bind focal = focal (nonsense) | NO |
| `${&?.field}` | `&` + `?` + `.field` | nonsense | NO |

### Ordering rule

The grammar above allows `?` before `.field` syntactically. The semantic constraint is:
- `?` is a Bind marker — it writes a value, it doesn't navigate.
- `.field` is a Read accessor — it navigates from an existing value.
- After a `?`, there's no existing value to navigate (the bind target isn't yet in scope within the same hole).

**Enforce:** `?` must be the LAST postfix if present. No `.field` after `?`. Grammar:

```
expr       = primary ("." IDENT)* ("?")?
           | primary "?"
```

Or equivalently:

```
expr       = primary dotchain opt_bind
           | primary opt_bind
dotchain   = ("." IDENT)+
opt_bind   = "?"?
```

With the constraint: `opt_bind` AND `dotchain` cannot both be present.

This is the current code's `illegal` mask, stated as a grammar rule instead of a runtime check.

### Recommended final grammar

```
hole       = "${" expr "}"
expr       = "&" "." IDENT ("." IDENT)*
           | IDENT "?"
           | IDENT ("." IDENT)+
           | IDENT
```

Four cases, no overlap, precedence unambiguous:
1. Focal with field chain: `&.field[.field]*`
2. Bind: `IDENT?`
3. Read with field chain: `IDENT.field[.field]*`
4. Bare read: `IDENT`

## Phase 6 — Per-DSL Splice Policy for Dot-Access

### What "splice policy" means

When a DSL body contains `${X.field}`, the DSL's lower function decides how to interpret the resolved string. Today most DSLs route through `cursor.get("X.field")` (the shim). A generic dot-access operator would expose this to per-DSL override.

| DSL | Natural meaning of `${X.field}` | Current status | Recommended splice |
|-----|---------------------------------|----------------|-------------------|
| `str` | String interpolation, field = sub-property | WORKS (shim) | Keep: `cursor.get("X_FIELD")` shim, or real nested JSON if cursor values are JSON strings |
| `sh` | Same as str, shell-quoted | WORKS (shim) | Same as str |
| `path` | Path segment interpolation | WORKS (shim) | Same as str |
| `glob` (static) | Field is part of glob pattern literal | REJECTED | Should work same as dynamic path: `cur.get("X.field")` shim, regex-escaped |
| `glob` (dynamic) | Already works via `build_dynamic_glob_regex` | WORKS | No change needed — already handles field |
| `re` (static) | Field would be embedded as regex fragment | REJECTED | Offer same as dynamic: `render_segments` output regex-escaped |
| `re` (dynamic) | Likely works via `render_segments_no_diag` | PROBABLY WORKS | Confirm and document |
| `ast` | `${X.field}` in an ast-grep body is parsed by ast-grep as literal text. It may confuse ast-grep's metavar scanner. | AMBIGUOUS | Reject at lower time with a clear error: "use `${X_FIELD}` not `${X.field}` in ast bodies" |
| `ast_yaml` | Same issue | AMBIGUOUS | Same: reject, document |
| `json` | Could navigate JSON tree by field path. But today cursor values are flat strings, not parsed JSON. | NOT APPLICABLE | Future: if cursor values support structured types, `${X.field}` could mean `jq .field` on X. Today: render as string then use in pattern |
| `sql` | Column reference. `${X}` → `"input"."X"`. `${X.field}` is ambiguous: is `X` a table alias and `field` a column? | REJECTED ("field interpolation must be explicit SQL") | Reasonable rejection. When needed: write raw SQL `"X"."field"` |
| `where` / `sql_where` | Predicate term. `${X.field}` passes `"X.field"` to `cursor.get` which falls through to `X_FIELD`. Works incidentally. | INCIDENTAL | Make intentional: document that `${X.field}` in `where` resolves `X_FIELD` |
| `format` (FormatComponent) | Regex `[A-Za-z_][A-Za-z0-9_]*` excludes `.` → silently dropped | BROKEN | Fix regex or migrate `format` to `render_segments` |
| LSP diag templates | Works via `cursor.get("X.field")` shim | WORKS | No change |

### Inconsistency summary for glob static vs dynamic

The static glob path (ops.rs:710) rejects dot-access with a LowerError. The dynamic glob path (`pipeline.rs:278`) ACCEPTS it and resolves `cur.get("X.field")`. This means:

- `glob\` ${X.field}/file \`` with no SubPipe → static path → ERROR.
- `glob\` ${ term(:Y) }/file \`` (SubPipe present) → dynamic path → dot-access on OTHER terms WORKS.

A user adding a SubPipe to fix one thing accidentally unlocks dot-access on everything else. This is a trap.

## Phase 7 — Analogue Mapping

### Structured data navigation analogues

| Surface | Notation | Semantics |
|---------|----------|-----------|
| jq | `.foo.bar` | Navigate JSON tree; each segment is an object key |
| awk | `$0`, `$1` | Positional fields in a flat record; no nesting |
| bash | `${arr[key]}` | Array/dict index; not dot-access |
| JS | `obj.foo.bar` | Property chain; each segment looks up in the parent object |
| Python | `obj.foo.bar` | Attribute access; structural |

The sprefa cursor is a **flat string-value dictionary**, not a JSON tree. Current `${X.field}` semantics map closest to:

- **awk's `$N` but named**: `${X.field}` = "get the value of the term whose canonical name is `X_FIELD`."
- Not at all like jq's `.foo.bar` (tree navigation) or JS's `obj.foo.bar` (nested objects).

If the user wants jq-like semantics ("a cursor's focal value is a JSON string; `${X.field}` means parse X as JSON and return `.field`"), that requires:
1. Cursor focal values to carry parsed JSON (not flat strings).
2. `Cursor::get` to deserialize on demand.
3. Cache invalidation.

That's a larger model change. The closest analog given the current flat-string model is:

**Recommended surface today: treat `${X.field}` as `${X_FIELD}`** — documented explicitly. This is awk-style (field separator = `_`, names = SCREAMING_SNAKE). Users coming from awk would recognize it. Users coming from jq would be surprised and should be warned.

The wording in user-facing docs: `${X.field}` is shorthand for `${X_FIELD}` — the cursor does not navigate structure. To navigate JSON, use a `json` DSL step that binds sub-fields explicitly.

## Top 3 Inconsistencies

### 1. `glob` static vs dynamic split on dot-access

**Static glob** (`ops.rs:710`): `field.is_some()` → LowerError, dot-access rejected.
**Dynamic glob** (`pipeline.rs:278`): `cur.get("X.field")` → accepted and resolved.

Same DSL, same syntax, different result depending on whether the body has a SubPipe carveout. No user-visible indication of which path applies.

Fix: Remove the `field.is_some()` guard from `glob_body_to_regex` (the static path). Resolve `${X.field}` identically to the dynamic path: regex-escape `cur.get("X.field")`.

### 2. `FormatComponent` does not parse dot-access

`v2_ops.rs:1381`: `regex::Regex::new(r"\$\{([A-Za-z_][A-Za-z0-9_]*)\}")` — the character class excludes `.`. `${X.field}` in a `format` body: the outer `\$\{...\}` match succeeds (braces captured) but the capture group `[A-Za-z_][A-Za-z0-9_]*` stops before the dot. The actual replacement regex fails to match the full `${X.field}` span. Result: `${X.field}` is emitted verbatim into the output. Silent data corruption, no error.

Fix: Migrate `FormatComponent` to use `render_segments` / `default_plain_dsl_parse` rather than its own regex. This brings it onto the same path as `str`, `sh`, and `path`.

### 3. `where` / `sql_where` silently passes `"X.field"` as a flat name

`where_eval.rs:100–105`: extracts the hole body verbatim (just strips `${`, `}`, optional `?`). `${X.field}` becomes `Hole("X.field")`. At eval time, `cursor.get("X.field")` is called, which succeeds only if the shim in `lib.rs:522` kicks in (splits on `.`, derives `X_FIELD`).

The problem: the predicate parser has no knowledge that `X.field` is a dotted access. It cannot type-check it or provide LSP completions for the field part. The `SqlWhereDsl` completion list at `sql_where/mod.rs:62–64` only offers bare `${capture}` forms — there's no surface in the completions for `${X.field}`.

Fix: Either (a) expand `where_eval`'s `Hole` node to carry an optional field chain, or (b) pre-process `${X.field}` through `default_plain_dsl_parse` before the predicate scanner, then substitute the resolved term name. Option (b) is lower effort.
