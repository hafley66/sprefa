## Problem/Context
- sprf today has NO: seq() literal, block {} except rule body, include/import, macro/quote/splice/reflect. `${}` only in DSL bodies. Statement = `pipe ;`. `rule(:name, COLS) {body}` head/body forms. `r?()` reads rule's return-memo table. Op names allow dots. tree-sitter CST drives `ast(:lang)`. json op EXISTS (confirmed by user).
- User locked model: a rule is a FUNCTION (call/return/yield), never a channel/send. See memory feedback_rule_is_function_not_channel.
- ext/sem = tree-sitter + declarative per-language LanguageConfig (entity_node_types etc.) -> SemanticEntity (id,kind,name,parent_id,structural_hash). No types, no resolver, no quicktype. The pattern to lift.
- SCIP-as-runtime was considered then CUT by user ("scratch scip actually running things"). SCIP symbol descriptor string = a nested keyed scope path; that fact informed the scope-tree IR view.
- User reframed final ask: NOT pick a per-language artifact; want ONE 80/20 parser algorithm that lowest-common-denominators EVERY language INTO one IR, then IR -> sprf macro to expand those types.

## Solution/Approach
One IR, three views (not competitors):
- IR-B algebraic core (value model): TyDef = Record|Variant|Func|Alias|Prim. TyRef = Nominal{path,args}|Prim|Tuple|Unknown(raw). TyRef is a TREE not a string (= the reason it is an IR not ctags). ~= quicktype internal type graph.
- IR-C scope tree (addressing): ScopePath=[Seg], Seg=(name,SegKind in mod|type|term|method|tyvar|param). scope(PARENT,NAME,SegKind) nests -> rules nest.
- IR-A relational storage (sprf rows): ty(PATH,KIND,NAME); fld(OWNER,NAME,REF_ID,ORD); tref(REF_ID,HEAD_PATH,ARG_REF_IDS); rel(PATH,REL,TARGET) implements|extends|embeds (NO :references, cut); meta(PATH,KEY,VAL) = the 20%.
80/20 algorithm: per lang declare ~6 things (~20 lines, sem-LanguageConfig + type-bearing nodes): record_nodes/variant_nodes/func_nodes/ref_node/member_field. Walk tree-sitter -> emit IR-B keyed by IR-C path. 80% captured = record/variant/func/alias/prim + nominal-ref tree. 20% dropped to meta (visibility, generic bounds, lifetimes, decorators, conditional/mapped TS types, macro-gen types). Resolution explicitly OUT: tref stores written token tree, unresolved (accepted SCIP wall = no use/reference/call graph).
Macro = `text -> host_parse -> CST splice` op (call it `use`/generate) driven by generator pipe over IR-A rows. IR->sprf map IS the trichotomy: ty(:record)->rule(:P,F?) [or seq() if anon] ; ty(:variant)->block{} (sum/select; match desugars to seq scanned in order) ; ty(:func)->rule(:P,A?,RET?) ; tref Nominal -> reference by ScopePath.
Language feature spec from user: seq := '(' elem (',' elem)* ')', elem := (KEY ':')? pipe (same syntax/semantics as op-call paren args; reuse split_paren_args; one grammar change = parens with comma or key: survives as value, not flatten into pipe at parse.rs:106-115). scope = ordered key->Value, Value in Op|Pipe(ops())|Seq()|Rule|Sym. symbol_table = this scope object, NOT a rule mutating a facts table, NOT a Term owning a table. block {} = one-at-a-time/select. seq = all/ordered/keyable named tuple = product; block = sum; rule = nominal relation/function.

## Key Insights
- sem already proved the LCD pattern for entities (tree-sitter + declarative node-type map). The 80/20 here = lift it from entities to TYPED IR by adding ~6 type-bearing node kinds per language.
- SCIP symbol descriptor string IS a nested keyed scope path; that is why scope/symbol-table should be a scoped value object, not table mutation.
- tref-as-tree (not string) is the dividing line between a real IR and the rejected string-split doc.
- The rule vs seq() vs block {} question dissolves into product/sum/nominal: rule=nominal relation/function, seq()=product/named-tuple, block{}=sum/select, match=seq scanned in order. record->seq vs record->rule is the ONLY genuinely ambiguous mapping; rest forced.
- Resolution (use/reference/call graph) is the hard wall without SCIP/stack-graphs; user accepted losing it. Static type artifacts give nominal+structural+implements edges only.
- Pivot IR honest options: rustdoc-JSON-shaped (rich, has trait/impl edges, Rust-flavored, best for sprefa self-dogfood, zero infra via `cargo rustdoc -- -Zunstable-options --output-format json`) vs JSON Schema (polyglot via quicktype/typeconv, lossy: no methods/traits/generics).
- json op already exists -> JSON ingest is NOT a blocker (prior fork killed).
