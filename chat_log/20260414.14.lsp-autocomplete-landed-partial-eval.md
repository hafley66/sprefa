## Problem/Context
Previous session (20260414.13) planned the work in rx-operator shape (switchMap parse / mergeMap runner / map rewrite / tap lsp-glue) with a DocSession integration gate before any tower wire. This session executed that plan.

Key discoveries during integration:
1. Agent worktrees silently wrote to main working tree (isolation=worktree was a no-op), so no merge conflicts — all four lanes landed in place.
2. truncate_and_substitute walks Pipeline surface only; for rule-body substitution it must be handed the body directly with a body-relative path. But running body standalone loses RuleOp's reader-side seed (cartesian of all repos × revs via reader.repos() / reader.revs()). Solved by adding Op::with_body(new_body) trait slot — RuleOp overrides to rebuild itself around the rewritten body, preserving seeding.
3. Body shape varies: Fork-of-Seq (multi-arm), bare Seq (single arm), bare Op (single op). op_path encoding [fork_idx, op_idx] needs an adapter that mirrors resolve_body_op.
4. Tolerant parse works at top level, but RuleFactory::parse still uses strict host_parse_arm_brace. Mid-editing syntax inside a rule body (e.g. `rev(ma|` inside `rule(r){ ... }`) aborts at rule-body lowering with `rule/body-parse` diag — the inner tolerant mode never fires. This is the ignored test gap.

## Key Insights
- **Agent worktrees are a silent no-op for now**: isolation=worktree wrote directly into the main working tree. Watch for this — no merge step needed but also no isolation gained. Agent B even observed partial D-lane state on "its" worktree base because it was really just reading HEAD through the same filesystem.
- **Op::with_body is an op-owned slot, not a framework feature**: RuleOp needed to seed cursors from the reader. Running body standalone after truncate_and_substitute lost that. Instead of teaching the rewriter about RuleOp, added a default-None trait method and let RuleOp override. Same pattern as body_pipeline. No central enum, no downcast.
- **Body shape adapter is necessary, not incidental**: Real bodies collapse to Op / Seq / Fork depending on how many arms and how many ops. op_path's [fork_idx, op_idx] encoding has to be adapted to the actual body variant before calling into the surface-only rewriter. The adapter mirrors resolve_body_op exactly.
- **Parser tolerance is a mode, but it only propagates one level deep today**: host_parse_tolerant covers the top-level grammar, but op-owned parse (RuleFactory::parse invokes host_parse_arm_brace) still uses strict. That's why mid-editing inside `rule(r){ ... }` breaks completion. Fix is a ParseMode field on ProgramCtx so ops can consult it.
- **Integration gate worked as planned**: every correctness claim verified at the DocSession boundary in cargo tests, zero tower involved. The rx-lane plan's split of "correctness at integration, smoke as finale" held up end to end.

## Open Questions
- Is ProgramCtx the right carrier for parse_mode? Alternatives: separate entry point pair `lower_rules_strict` / `lower_rules_tolerant`, or a thread-local/RefCell on the parser. ProgramCtx feels right because it's already the per-parse-pass configuration object and ops already take &mut ProgramCtx — they can read the mode naturally.
- When parse_mode is Tolerant and host_parse_arm_brace_abs_tolerant produces errs, where should those diags surface? Today host_parse_arm_brace strict errors become RuleDiag::BodyParse wrapping the first error. Tolerant mode produces (pipes, errs) — RuleFactory should emit per-error RuleDiag::BodyParse entries but still proceed with the partial body pipes, not bail.
- Should any tolerance also apply to brace ops beyond rule (e.g. walker bodies, future marker/md ops)? Probably yes, same pattern — mode flows through ProgramCtx, ops opt in via their own call site.
- Does the auto-cleanup of agent worktrees deserve a tooling followup? If isolation=worktree silently degrades to in-place edits, any parallelism assumption is wrong. For now: spawn agents sequentially or accept that lanes must be conflict-free by construction.
