# Session: v4-poc-engine-pipeline-buffer-perf

## Goal
Build a v4 POC that exercises all 7 layers (Action / Cursor / Store / Hooks / Effect / Op / Reducer) against a real workload (linux kernel ast-grep scan, 63k .c/.h files), and close the perf gap to v3's baseline (~3.64s for `printk($$$)` at W=8) by fixing pipeline serialization in the Op runtime.

## Problem/Context
The +81% gap is **pipeline serialization, not Op-trait overhead**. Today's `drive(chain, hooks)` chains ops by calling `op.run(...)` synchronously down the chain — each op's output stream feeds the next op's input directly. When AstNm awaits `input.next()`, Fs runs until it has a 256-batch then yields and suspends; AstNm runs spawn_blocking + rayon par_iter on that batch (25ms+), then awaits next; Fs wakes, walks again, yields. **Zero overlap between enumeration and parsing.** Plus Fs's `WalkBuilder` iterator is sync I/O blocking the tokio worker thread.

The honest math: 11% is the real "tokio overhead vs raw rayon" cost (from the bypass test). The other ~70% is recoverable architectural slack from the alternation deadlock + Fs blocking the runtime.

## Solution/Approach
Two additive fixes, both inside lib.rs (no Op-trait API change):

1. **Buffered channels between ops in `drive`.** Replace the synchronous chain with one tokio task per op, connected by `tokio::sync::mpsc::channel(cap=8)`. Use `tokio_stream::wrappers::ReceiverStream` to convert the receiver to a `Stream`. Each task: `op.run(hooks, ReceiverStream)` produces a stream, drains it, sends each batch into the next op's tx. Producer can be N batches ahead of consumer.

2. **Fs in spawn_blocking.** Replace `Box::pin(async_stream::stream! { ...WalkBuilder... })` with a pattern that spawns the WalkBuilder loop in `tokio::task::spawn_blocking`, has it `tx.blocking_send(...)` batches into a tokio mpsc, and the op returns `ReceiverStream::new(rx).boxed()`. Removes the runtime-blocking sync I/O.

Together expected to land near the +11% floor.

## Key Insights
1. **The 11% bypass number was misleading.** That bench fanned files into a Semaphore directly, never went through the Op trait. The honest "real engine" delta starts at +81%. State that explicitly when reporting.
2. **CQRS-shaped engine: Mutations in Out, Queries+Yields on Hooks/Ctx.** This was the conclusion of the long architecture conversation that preceded this session. Effects-bus-and-stream-emit was double-bookkeeping; the split resolves it.
3. **Cursor as dynamic-scope term-bag is load-bearing.** Each op sets whatever terms make sense (FS, REV, NAME, etc.). Latest write wins. Hash/Eq via sorted Vec<(Arc<str>, Arc<str>)>.
4. **Store trait IS the relational substrate, DD is one impl.** Today's MemStore (HashMap + tokio::broadcast); future DdStore on its own thread, LspBufferStore overlay, GitStore. Ops never touch DD directly.
5. **Naive `rederive` blew up at scale.** Original impl re-materialized full rule output on every insert; replaced with `Store::commit(gen)` that drains a dirty-set at action boundary. Still single-threaded HashMap-build at commit time though — full mode hung on `return $X;` (1.1M rows) and was killed. Real fix is incremental rederive (DD-style +1/-1 diffs against previous output); deferred.
6. **Stream vec-of-cursor batches, not per-cursor.** Earlier per-cursor wakeups were O(rows). Refactored to BoxStream<Vec<Cursor>> with BATCH=256 (Fs) / batch-passthrough (other ops). Wake count is O(batches) now.
7. **rayon belongs in AstNm, not the bench.** The bench was being made faster instead of fixing the real engine. Fixed: AstNm uses spawn_blocking + rayon par_iter on the batch internally. Bench drives real ops.
8. **Pattern::fixed_string prefilter is load-bearing.** memchr-speed `String::contains` on the literal token short-circuits non-matching files before tree-sitter touches them. v3 does this; we adopted it in AstNm.
9. **React-named: Action, Reducer, dispatch, Store, select, Hooks, Effect, use_*().** Vocabulary borrowed wholesale. Runtime shape is its own thing (async streams + relational store), not a fiber tree.
10. **Linux fixture lives at `/Users/chrishafley/projects/sprefa-archive-20260428/v2/tests/smoke/.fixtures/linux`** (63482 .c + .h, 2GB). The v3 symlink at `v3/tests/smoke/.fixtures/linux` was repointed in this session to that absolute path. v3's `effect_proof` bench Cargo workspace inheritance is broken because the crate is `exclude`d from v3 workspace; can't run the v3 baseline standalone without patching its Cargo.toml.

## Open Questions
- Can the v4 engine close the gap to within +15% of v3 with just buffered channels + spawn_blocking? Or do we hit a tokio-task-per-op overhead floor? Answer empirically after the fix.
- For insert mode the 8.86s is suspicious — only 47 inserts, why is it 2.27s slower than bare? Lock contention on `MemStore::facts` RwLock seems too high for 47 inserts. May be the broadcast::send stall, or rederive even with commit deferral. Profile.
- Do we want the user-facing `Op::run` signature to take BoxStream and return BoxStream forever, or migrate to an explicit `(Cx, in_stream) -> out_stream` shape where ops never own their async runtime? Current shape works but the buffered channels live in `drive()`, not in `Op::run` — so authors don't have to think about it. Probably fine.
- Should `Fs` and `AstNm` register into a shared spawn_blocking pool rather than each spawning their own? Today rayon is global (set once via `ThreadPoolBuilder::build_global`), tokio's blocking pool is the default. Likely fine but worth measuring.
- Is `tokio_stream::wrappers::ReceiverStream` the right adapter, or should we hand-roll with `poll_recv`? ReceiverStream is one extra dep but the right shape; fine.
