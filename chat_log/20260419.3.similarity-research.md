# Similarity research: sprf v3 vs prior art

Five parallel deep-research agents assessing structural and intentional
similarity between sprefa v3 design and selected prior-art systems.
Reports below preserved verbatim from each agent. Synthesis at end
once all complete.

---

## 1. Glean (Meta) — similarity 62/100

### Glean overview

Meta-built fact store for code. Indexers (per-language) emit
immutable, deduplicated facts into RocksDB; facts are typed by
user-defined Predicates organized into versioned Schemas; queried
with Angle (Datalog-like logic language, currently non-recursive).
Powers Meta's IDE/code-search via Glass (language-agnostic symbol
server) and a generic LSP server. Open-source on
`facebookincubator/Glean`, Haskell-implemented, Thrift API.

### Structural overlap

| sprf v3 piece                                          | Glean analogue                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `.sprf` rule materialized to per-rule SQLite table     | Stored derived predicate (`stored {...} where ...`), facts written to RocksDB                           |
| Rule body (pipeline of ops)                            | Angle query body in a derived predicate definition                                                      |
| Cursor (content, byte_range, fs/repo/rev, slots, captures) | Fact = key (typed term) + optional value, with fact ID; src.File / src.Range as standard locator types |
| Per-op tree-sitter sub-grammar = typed shape per op    | Per-language schema (e.g. `flow.*`, `cxx.*`) defining typed predicates per language                     |
| `${UPPER}` bind, lowercase op                          | Angle conventions: uppercase variables, lowercase predicate names, dotted field walks                   |
| Walker `;` Fork (alternation)                          | Angle `|` alternation inside derived predicate bodies                                                    |
| Walker `>` Seq (compose)                               | Angle conjunction (`;` statement-sep, comma-conjoin in body)                                             |
| Cross-codebase edge thesis (.sprf owns the edge)       | `codemarkup` schema — language-neutral abstraction layer authored as derived predicates                  |
| Terminal SQLite, raw SQL CTEs over per-rule tables     | RocksDB + Angle as the query door; on-demand vs stored derived predicates pick materialization strategy |
| sprf rev pinning (fs/repo/rev triple per cursor)       | Glean DB is per-revision; databases are immutable, indexers run per snapshot; "stacked" DBs layer changes |
| LSP-as-op (planned)                                    | Glass + generic LSP server already factored this way: thin LSP shell over fact queries                   |

Strong shape match: **decl-language + derived-view layer + per-language fact schemas + LSP-on-top**.

### Divergent intent

**Glean optimizes for:**
- Whole-codebase, server-deployed, replicated read-mostly query service. Multi-client, Thrift-over-network.
- Indexer-once, query-many. Indexers are heavyweight compiler-backed (clang AST, Hack typechecker, GHC, etc.).
- Schema as the universe; data must conform. Schema migration is a first-class workflow (`derive ... default`).
- Non-recursive Angle (per docs). Recursive joins explicitly avoided in the query layer.

**sprf optimizes for:**
- Author-checked-in expectations as the source unit. The .sprf file is the artifact, not the DB.
- Drift detection: rule both extracts and asserts. Glean has no equivalent — facts are descriptive, not prescriptive.
- Cheap indexers via tree-sitter + ast-grep; no per-language compiler dependency.
- Cross-repo edges as a primitive (fs/repo/rev triple on the cursor). Glean DBs are typically per-repo-per-revision; cross-repo edges live in higher-layer products (Glass), not in the schema.
- Effects (`sh[r]`, `sh[w]`) embedded in the rule. Glean has no shell/effect notion; it's a read-only fact store.
- Recursive transitive joins via SQLite CTEs. Datalog-shaped semantics without the non-recursion ceiling.

### What sprf could borrow concretely

- **Stored vs on-demand derived predicates** as a posture for sprf rules. Annotation on the rule (`@stored` / `@on_demand`) controls whether the per-rule SQLite table is materialized eagerly or computed at query time. Same rule text, two execution modes.
- **`default` derivation for schema migration.** sprf rules will evolve; a rule can declare a fallback derivation that activates only when the new column has no rows. Smooths .sprf renames across repo history.
- **Language-neutral derived layer (`codemarkup`).** Per-op tables are language-specific; a small set of cross-language rules (defs, refs, callers) re-derived from them gives clients one schema to query. This is the "tools build on derived views" pattern Glean explicitly markets.
- **Schema versioning syntax (`schema lang.2 : lang.1 { ... }`).** Inheritance + version number on the schema name. Useful when sprf rules are shared across `.sprefa.toml` ancestor chains.
- **Glass split.** A thin language-neutral symbol server over the fact store, separate from the LSP. sprf already plans LSP-as-op; Glass is the missing middle layer (HTTP/RPC API for non-LSP clients).
- **Fact ID = stable 64-bit identity, dedup at storage.** sprf cursors are streamed but anonymous; assigning a content-addressed fact ID at the SQLite write boundary makes recursive CTEs and cross-rule joins much cheaper.
- **Indexer/query separation.** Glean's indexer step is offline and write-only; the server is read-only. sprf currently runs both in the same process; splitting gives multi-client query for free.
- **Backfill workflow.** `glean derive` is an explicit batch trigger for stored predicates, distinct from indexing. sprf needs the same: rule-level "rematerialize this table" command.

### What sprf would lose by adopting Glean's model

- **The .sprf-as-source-of-truth thesis.** Glean schemas describe what indexers produce; they don't assert what should hold. Adopting Glean's predicate model means dropping the drift-warning property unless layered on top.
- **Shell effects.** Glean is pure read; `sh[r]`/`sh[w]` has no home. Effects would have to live entirely outside the fact store.
- **Recursive queries.** Angle is non-recursive. Transitive call/import chains are a use case sprf currently gets free from SQLite CTEs.
- **Cheap indexing.** Glean's indexers are per-language compilers. Tree-sitter + ast-grep granularity is alien; the Glean schema design assumes typed AST predicates derived from a real frontend.
- **Tree-sitter sub-grammars per op.** Glean has no equivalent of injecting a sub-language at a brace. Schema is one global type universe; ops-as-grammars would be a foreign concept.
- **Single-process simplicity.** Glean is a Thrift server, RocksDB, Haskell. The deployment story is heavy.
- **Cross-repo-as-primitive.** Glean handles cross-repo via Glass and per-repo DBs joined externally; sprf's fs/repo/rev triple in the cursor row is a tighter primitive.

### Similarity index — 62/100

Thesis match is high (typed facts + derived views + per-language schemas + LSP-on-top + author-defined predicates), mechanism match is medium (Datalog/Angle vs streaming-cursor/SQL, RocksDB vs SQLite, Haskell server vs single-process daemon, indexer-once vs reactive watcher). sprf's drift-as-spec posture and embedded shell effects have no Glean counterpart; Glean's schema versioning and derived-predicate ergonomics have no sprf counterpart yet. Closer to a thesis sibling than a mechanism clone.

### One question Glean has answered that sprf should answer

**"What is the migration story when a rule's shape changes?"**

Glean's `derive ... default` plus schema inheritance (`schema lang.2 : lang.1`) gives a worked answer: old clients keep working against new DBs, new clients keep working against old DBs, the derivation runs only when the target column is empty. sprf rules will be edited continuously by the user; without a defaulting/derivation layer, every rule edit invalidates the per-rule SQLite table and breaks downstream queries. Glean's two-knob design (`stored` vs on-demand, plus `default`) is the explicit answer sprf has not yet specified.

## 2. Racket `#lang` — similarity 38/100

### Racket `#lang` overview

A `#lang foo` line dispatches the source file to the module
`foo/lang/reader`, which exports `read` and `read-syntax`. That
reader consumes the rest of the file and returns a `(module name
lang-mod body...)` syntax object. The expander then expands the body
in the language `lang-mod`, which provides the initial bindings
(including `#%module-begin`, the wrapper macro that gets to rewrite
the entire module body). Languages can themselves be implemented in
other `#lang`s, producing an unbounded language tower
(Tobin-Hochstadt et al., "Languages as Libraries," PLDI 2011; Flatt,
"Creating Languages in Racket," CACM 2012).

### Structural overlap

| sprefa v3 mechanism                                          | Racket counterpart                                                              |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| `tree-sitter-sprefa` host grammar parsing outer pipeline     | Racket reader producing the outer s-expression skeleton                         |
| Per-op tree-sitter sub-grammar injection                     | Per-`#lang` reader extension; `#reader` form for inline language switch         |
| Op brace = recursive entry into a different grammar          | Module language + `#%module-begin` controlling what bodies mean                  |
| Cursor stream (data) flowing through ops                     | Syntax object (data) flowing through expander passes                             |
| `${UPPER}` bind / `&{slot}` reference in pattern position    | `syntax-parse` pattern variables with `~datum`, `~bind`, `~var`                  |
| Reusable named pipelines `(NAME) > op > op` invoked as `${NAME}` | `define-syntax-rule` / `define-syntax` / module-imported macros            |
| Expression-as-matcher (same grammar at top and inside `${...}`) | Quasiquote/unquote symmetry; phase-tower reuse of the same expander           |

The reader-extension axis is the closest mechanical match.
Racket's reader-per-language is exactly what tree-sitter sub-grammar
injection is doing, only Racket dispatches lexically by
`#lang`/`#reader` while sprefa dispatches by op identifier in the
host grammar.

### Divergent intent

Racket optimizes for **compile-time program transformation**.
Everything `#lang` produces is a syntax object that is then expanded,
type-checked (in Typed Racket), and compiled. The tower is about
authoring DSLs whose programs become Racket programs.

sprefa optimizes for **runtime cursor-stream evaluation against
external corpora**. The "program" is a query plan; ops are streaming
transducers; bytes flow from a Reader through ops into a SQLite
store. The grammar tower exists so that `walker{...}` body is parsed
by walker's grammar.

Racket has no notion of cursor, no streaming dataflow, no
Reader-cache layer, no per-rule materialized table. sprefa has no
notion of phase tower, no module-begin rewrite hook, no compile-time
hygienic identifier capture across module boundaries.

### What sprf could borrow concretely

- **Reader/expander split.** Today each tree-sitter sub-grammar both
  *parses* and *interprets* its body inside the op's `pipe()`.
  Adopting a Racket-style two-phase split (sub-grammar parses to an
  op-specific AST; a separate "lower" phase transforms it to the
  runtime instruction stream) gives a stable surface for static
  analysis, hover, and partial evaluation.
- **`#%module-begin` analog per op.** A registered hook on each op
  that gets to see the *entire* parsed body before lowering. This is
  where op-owned diagnostics, op-owned slot inference, and projection
  extraction can hang without the framework knowing op internals.
- **`syntax-parameter` for `&` (current cursor).** `&` changes
  meaning by host context (top-level pipeline vs `${...}` expansion
  vs cursor-ref body). Racket solved this exact problem with
  `syntax-parameterize`: a single identifier whose meaning is rebound
  by the enclosing form. The named-pipeline `(NAME) > op > op`
  definition can `syntax-parameterize` `&` to refer to the
  invocation-site cursor rather than the definition-site cursor.
  This is the cleanest known solution to "what does `this` mean in a
  reusable block."
- **Scope sets for `${UPPER}` capture.** Flatt's "Binding as Sets of
  Scopes" (POPL 2016) is the model that lets a macro-introduced
  `${X}` not collide with a same-named `${X}` at the call site. If
  named pipelines are first-class and can be passed/composed, the
  hygiene problem is real; scope sets are the answer Racket converged
  on after 30 years of macro-system work.
- **Phase separation.** Racket's phase 1 (compile time) vs phase 0
  (runtime) cleanly separates "grammar-level rewriting" from "stream
  evaluation." sprefa's `re{...}` *pattern compilation* vs *match
  execution* maps onto this; making it explicit gives a place to
  memoize compiled patterns across pipeline runs.
- **`syntax/parse` as an authoring template.** When defining a new
  op's sub-grammar lowering, `syntax-parse`'s declarative pattern +
  `~commit` + `~fail` + class definitions are the most polished
  pattern-DSL in any language. Worth studying before hand-rolling the
  op body parser API.

### What sprf would lose

- **Streaming.** Racket's expander is a tree rewriter, not a stream
  processor. A naive port collapses the cursor stream into a
  fully-materialized syntax object before any op runs. The 16GB /
  500-repo budget does not survive this.
- **Runtime-driven Reader.** Racket has no equivalent of
  `reader.bytes(c.fs)` because everything is in-memory source. The
  fs/repo/rev fields on the cursor have no Racket counterpart.
- **Tree-sitter recovery.** tree-sitter's ERROR/MISSING node story is
  a hard requirement for the LSP partial-parse mode. Racket readers
  throw on ill-formed input.
- **Performance posture.** Racket's expander is correctness-first,
  not throughput-first. Adopting its data structures wholesale
  forfeits the bench numbers from chat_log/20260418.

### Hygiene check — named-pipeline as first-class value

Racket's answer to "block of code with free variables that gets
invoked elsewhere with proper variable capture" has three layers:

1. **`syntax-rules` / `syntax-case` / `syntax-parse`** —
   pattern-template macros where every introduced identifier carries
   a *scope* tag. Identifiers from the macro definition site and
   identifiers from the use site live in disjoint scope sets, so
   `(let ([x 1]) (my-macro x))` cannot accidentally capture an `x`
   introduced by `my-macro`'s template.
2. **`syntax-parameter` + `syntax-parameterize`** — the *deliberate*
   opposite: an identifier whose meaning is intentionally rebound by
   enclosing context. This is what `it` in anaphoric macros, `this`
   in class bodies, and `break`/`continue` in loop macros use.
   Direct fit for sprefa's `&` semantics.
3. **First-class compiled syntax via `local-expand` and
   `syntax->datum`** — a macro can take a syntax object, expand it,
   inspect the result, re-emit it. Combined with scope sets (POPL
   2016), this lets a "named pipeline" be stored, passed, composed,
   and invoked at a different site without leaking definition-site
   bindings.

Direct mapping to the sprf question:

- If `(NAME) > op > op` is **macro expansion**: hygiene gives free
  `${X}` inside the body the binding from the *definition* site by
  default; `syntax-parameter` gives selected identifiers (`&`,
  possibly `${THIS}`) the binding from the *use* site.
- If `(NAME)` is a **first-class compiled pipeline value**: needs
  runtime cursor-environment passing and explicit captured-binding
  tracking. Racket's `compile-time` vs `runtime` phase split is what
  makes the macro path strictly more powerful for the static cases
  and the runtime path strictly more flexible for dynamic
  composition. They are not exclusive; Racket ships both and lets
  the author pick.

Pre-cooked recommendation: macro expansion as the default surface;
first-class pipeline values as an opt-in (e.g. `(NAME!)` or a
separate sigil) when runtime composition is needed. This matches
Racket's split between `define-syntax` and `(lambda (stx) ...)`.

### Similarity index — 38/100

The grammar-injection axis is a strong match (call it 80% overlap)
and the named-pipeline-with-hygiene problem maps almost directly
onto Racket's solved territory. But the runtime model — cursor
streams, external Readers, fs/repo/rev provenance, materialized
SQLite tables, partial-parse LSP mode — has no Racket analog and
constitutes the majority of sprefa's surface area. Weighted by code
volume in v2 today, the overlap shrinks. Intellectual lineage is
real; mechanism reuse would be partial.

### One question Racket has answered that sprf should answer

**"When a reusable named block is invoked at a use site, which
identifiers inside the block see definition-site bindings and which
see use-site bindings?"**

Racket's answer: by default, every identifier sees definition-site
bindings (full hygiene via scope sets); identifiers explicitly
declared as `define-syntax-parameter` see use-site bindings;
identifiers under `~datum` or assembled via `datum->syntax` with an
explicit context syntax object can be steered manually. The decision
is per-identifier, declarative, and checkable at compile time. Any
sprf design that ships `(NAME) > op > op` plus `${NAME}` invocation
without picking a position on this question will rediscover the
unhygienic-macro pain that motivated the entire 1986–2016 hygiene
literature.

- [Racket Guide §17.3 Defining new #lang Languages](https://docs.racket-lang.org/guide/hash-lang_reader.html)
- [Racket Reference §12.5 Syntax Parameters](https://docs.racket-lang.org/reference/stxparam.html)
- Tobin-Hochstadt, St-Amour, Culpepper, Flatt, Felleisen, "Languages as Libraries," PLDI 2011
- Flatt, "Creating Languages in Racket," CACM 55(1), 2012
- Flatt, "Binding as Sets of Scopes," POPL 2016

## 3. Salsa — similarity 38/100

### Salsa overview

Demand-driven incremental computation framework. Inputs are typed
structs marked `#[salsa::input]`; derived computations are
`#[salsa::tracked]` functions whose return values are memoized in a
`Database`. A red-green algorithm tracks per-query dependencies
against a global revision counter; on input mutation, downstream
queries are marked maybe-dirty and re-verified lazily on next pull.
Side-channel data flows through `#[salsa::accumulator]`. Cancellation
is a panic-unwind triggered when a writer needs the database lock
while readers hold it. Salsa 3.0 (2025, in-port for rust-analyzer)
adds parallel query execution, reference returns instead of clones,
and a more aggressive interning scheme.

### Structural overlap

| Salsa                             | sprefa v3                                            | Match quality                                                          |
| --------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| `#[salsa::input]` struct          | `Cursor` source data (bytes, fs/repo/rev)            | Partial. Cursor is a stream element, not a typed input slot.           |
| `#[salsa::tracked] fn`            | `Op::pipe(...)`                                       | Partial. Salsa fn is `(Db, K) -> V`; sprf op is `Stream -> Stream`.    |
| `#[salsa::interned]`              | (no equivalent yet)                                   | Gap. sprf has no canonical-id machinery for repeated values.            |
| `#[salsa::accumulator]`           | `OpCtx.diags` sink, effect descriptors                | Strong. Both are structured side channels separate from main return.    |
| Database revision counter         | Reader cache + reparse trigger                       | Weak. sprf reparse is whole-file scoped, not query-graph scoped.        |
| Memo + red-green verify           | Cargo-fingerprinted `sh[r]` effect cache             | Partial. Same intent (skip if inputs unchanged) at different granularity. |
| Cancellation via panic-unwind     | `CancellationToken` + `TaskGuard` drop                | Strong. Same mechanic, idiomatic-Rust variant.                          |
| LRU on memo tables                | (none)                                                | Gap.                                                                    |
| Cycle detection                   | (none documented in v3 brief)                         | Gap.                                                                    |

The closest mechanical analog: a `tracked fn parse(file: FileId) ->
Tree` in Salsa maps onto an sprf parse op consuming a cursor and
emitting a parsed cursor. Salsa stores the result by key in the DB;
sprf streams it once and relies on the reader cache plus per-tick
effect batching.

### Divergent intent

**Salsa**: optimize latency for one developer editing one file in
one project. The unit of work is a single query keyed by typed
identity. Pull-based: the IDE asks "what's the type at offset 312?",
the DB walks the dependency graph backward.

**sprefa v3**: optimize throughput for cross-codebase invariant
checking over N repos at M revisions, materializing typed edges to
SQLite. Push-pull-dam streaming: pipelines run end-to-end, results
land in tables, queries run against the tables.

What each gives up:
- Salsa gives up bulk throughput, cross-process result sharing, and
  a queryable result store. The DB is in-memory and per-process.
- sprf gives up fine-grained per-query incrementality. Edits
  invalidate at the pipeline-instance granularity, not the
  value-derivation granularity.

### What sprf could borrow concretely

**a) Interned-id layer for cursor identity.** Salsa interns produce
stable `Id`s with `==` in O(1). sprf cursors currently carry
`(fs, repo, rev, byte_range)` tuples. An interned `CursorKey` would
let the effect batcher dedupe sub-ms without hashing the tuple each
tick.

```rust
#[salsa::interned] struct CursorKey<'db> { fs: FileId, rev: RevId, range: ByteRange }
```

**b) Tracked parse layer beneath the stream.** The reader cache is
hand-rolled. A Salsa-style:

```rust
#[salsa::tracked]
fn parse_tree(db: &dyn Db, file: FileId, rev: RevId) -> Arc<Tree>
```

would give automatic invalidation on `set_file_bytes(file, ...)`.
The sprf pipeline would call it from any op that needs a tree;
reparse discipline becomes a property of the DB rather than custom
CancellationToken plumbing.

**c) Accumulator pattern for diagnostics.** `OpCtx.diags` is already
accumulator-shaped. Formalizing as `#[salsa::accumulator] struct
Diag { ... }` makes "all diags produced while computing X" a
first-class query without an explicit sink.

**d) Durability levels for repos.** Salsa's
`Durability::HIGH/MEDIUM/LOW` lets the cache skip dependency walks
for inputs that rarely change. sprf has the same shape: `rev` of a
vendored dep changes once a quarter; user repo HEAD changes per
keystroke. A durability axis on `Reader` reads would skip a lot of
verification.

**e) Cycle handling.** sprf cross-codebase edges can cycle (repo A
depends on repo B, B's tests depend on A). Salsa 3.0 has a
documented cycle strategy (panic, fixpoint, or recover). v3 design
brief lists no policy.

### What sprf would lose by adopting Salsa

- **Streaming.** Salsa queries return owned values keyed by typed
  input. There is no `Stream<T>` query. A pipeline that emits 50k
  cursors becomes one query returning `Vec<Cursor>` (or
  `Arc<[Cursor]>`), losing back-pressure.
- **Effect ordering.** Salsa is pure pull. The `sh[w]` write-effect
  contract (approval-gated, fingerprinted, batched per tick) has no
  Salsa primitive.
- **Cross-process result sharing.** Salsa DB is in-memory. The
  SQLite per-rule table layer has no Salsa equivalent.
- **Bulk-parse phase 1 throughput.** Salsa's per-query overhead
  (memo lookup, dependency edge record, revision check) is
  meaningful when the query body is a 5us tree-sitter parse.
  biome/oxc parity demands the parse op stay close to a tight rayon
  loop.

### Compatibility check

Conflicting evaluation models, but composable at a seam.

Salsa is pull-memoization keyed by typed input identity. sprf is
push-pull-dam streams driven by source events. Trying to make Salsa
the runtime under sprf would require turning every cursor into an
interned `Id` and every op into `tracked fn op(db, cursor_id) ->
Vec<cursor_id>` — collapsing the stream into materialized vecs at
every step. This loses the "never buffer cursors with content"
memory rule.

Composable seam: Salsa as the **read layer** under the `Reader`
trait (tracked `parse_tree`, `file_bytes`, `repo_index`), with the
streaming pipeline running on top. The pipeline pulls from
Salsa-tracked queries; cancellation comes from the Salsa revision
bump triggering the existing `CancellationToken` path. Effect
descriptors and SQLite materialization stay outside Salsa.

Rust-analyzer itself is structured this way: `base_db` and `hir_def`
are Salsa; `ide` boundary catches the cancel panic and converts to
`Result`. The actual completion algorithm runs as normal Rust over
Salsa-fetched data. sprf's mapping: reader/parse-cache = Salsa;
pipeline/effect/store = not Salsa.

### Similarity index — 38/100

- Strong overlap on cancellation (5/5), accumulator-shaped
  diagnostics (4/5), demand-driven invalidation intent (3/5).
- Weak overlap on data model: Salsa's typed-key memo table vs sprf's
  polymorphic cursor stream (1/5).
- No overlap on streaming, effect batching, write effects, or
  cross-process result store.
- Both are reactive incremental engines for code analysis with
  cancellation, which puts the floor above 25. Different evaluation
  models (pull memo vs push-pull-dam stream) and different scope
  (one project vs N repos) keep it well below 60.

### One question Salsa has answered that sprf should answer

**How is per-query revision-versus-content invalidation
distinguished?**

Salsa's red-green: when input X bumps the revision, downstream query
Q is marked **red** (maybe-dirty). On next fetch, Q's inputs are
re-verified; if every input's *output hash* still matches what Q saw
last revision, Q stays cached even though the revision number
advanced. This is the "early cutoff" optimization that makes editing
whitespace in one file not re-typecheck the world.

sprf v3 has no documented analog. When a file's bytes change, every
pipeline that reads that file reruns. If the byte change is
whitespace and every downstream op produces the same cursors, sprf
still reruns the whole pipeline and rewrites SQLite. The design
needs an answer to: at what granularity does sprf compare new-output
to last-output and short-circuit downstream? Per-cursor hash? Per-op
output digest? Per-rule table-write fingerprint? Salsa's answer is
"per query return value, by `Hash`". sprf's answer is unspecified,
and the cost of getting it wrong scales with N repos × M revisions ×
pipeline depth.

## 4. CodeQL — similarity 35/100

### CodeQL overview

GitHub's static analysis platform. A logic-programming query
language (object-oriented Datalog) runs against a pre-extracted
relational snapshot of source. Per-language extractors (cpp, java,
javascript, python, go, ruby, swift, csharp) emit a CodeQL database
(TRAP files compiled to a relational store). Queries declare classes
(constrained sets of database rows) and predicates (derived
relations); evaluation is bottom-up fixpoint.

### Structural overlap

| sprf v3                                                        | CodeQL                                                        | Notes                                                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Per-op tree-sitter sub-grammar (`ast[rust]`, `ast[ts]`)         | Per-language extractor producing TRAP                         | Both fan out grammar work per language; CodeQL extractors are heavier          |
| Cursor stream (bytes, byte_range, fs/repo/rev, slots, captures) | Element rows in DB tables (`@locatable`, `@element`)          | sprf streams; CodeQL materializes                                              |
| Per-rule SQLite tables, raw SQL terminal                        | Per-query result table; QL compiles to RA evaluated against the DB | sprf exposes SQL as user surface; CodeQL hides the relational engine        |
| `${UPPER}` decl/ref, `&{slot}` structural address               | QL variable bindings inside `from ... where ... select`       | Both bind once, constrain by predicate join                                    |
| `>` Seq, `;` Fork composition                                    | Predicate conjunction / disjunction; class hierarchy          | sprf is pipeline-shaped, CodeQL is set-shaped                                  |
| `.sprf` checked-in expectation file                             | `.ql` query, `.qll` library, `qlpack.yml`                     | Both treat the artifact as the deliverable, runnable in CI                     |
| Terminal SQLite sink                                             | BQRS result file, SARIF export                                | Both separate evaluation from result transport                                 |

The strongest overlap: both reduce code to relations and write
declarative joins over those relations. The "checked-in artifact"
framing is shared with CodeQL's `code scanning` packs.

### Divergent intent

CodeQL: deep semantic analysis of one codebase per database. Type
resolution, control flow graph, data flow library, call graph,
points-to. Targets vulnerability classes (CWE) and quality rules.
The DB build is a heavy step (`codeql database create` runs the
actual compiler [staleness risk: build-mode `none` indexing has
expanded since 2023, may cover more languages now]).

sprf: shallow structural matching across many codebases, expressed
as expectations that hold or break under revision drift. The
cursor's `(fs, repo, rev)` triple is load-bearing; CodeQL has no
equivalent first-class field.

What each gives up:
- CodeQL gives up cross-repo reach and revision-pair comparison;
  databases are per-repo per-build.
- sprf gives up type resolution, dataflow, control flow. A query
  like "is this tainted user input flowing to exec()" is native
  CodeQL and out of scope for sprf's grammar-level matching.

### The OO-datalog idea

CodeQL's core insight: a class is a unary predicate (a set defined
by membership condition). A subclass refines membership with
additional constraints. Predicates can be recursive subject to
monotonicity (no negation through recursion in the standard
fragment); evaluation is bottom-up fixpoint with magic-set
transformation.

Mapping onto sprf:

- sprf's per-rule SQLite table = CodeQL's predicate extension. Both
  are sets of tuples.
- sprf's pipeline `ast[rust] > kind[fn] > name[$X]` = a chain of
  constraining predicates that could be expressed as `class
  FnNamedX extends Function { FnNamedX() { this.getName() = X } }`.
- sprf's `;` Fork to multiple downstream ops = predicate
  disjunction or class union.
- sprf's transitive joins via recursive CTE in SQL = CodeQL's
  recursive predicate.

A datalog-shaped IR between sprf surface and SQLite emit is
plausible. The pipeline desugars to:

```
rule(X, Y) :- ast_rust(C), kind_fn(C), name(C, X), uses(C, Y).
```

Then the IR can target SQLite (recursive CTE), Soufflé (parallel
Datalog), or a custom semi-naive evaluator. The benefit: query
optimizer can reorder joins, push selections, hoist common
subexpressions across rules. The cost: the IR becomes a second
language to maintain, and Fork's sequential streaming semantics may
fight set-based rewriting (cursor order, slot mutation).

The OO part (class hierarchy, `extends`, member predicates) is what
makes CodeQL libraries composable. sprf's "ops own everything"
posture leans the same direction; ops are effectively classes that
own their projection schema.

### What sprf could borrow concretely

- **Library import system**: `qlpack.yml` + `import` brings
  reusable predicates. sprf has no module system spec yet; CodeQL's
  pack/import mechanism is mature.
- **Predicates with multiple bindings**: CodeQL predicates take
  any-arity tuples and any binding mode (`bindingset[x]`). sprf's
  `${X}` is single-binding per name; multi-arity relations require
  designing the term language.
- **Taint tracking library**: `TaintTracking::Configuration` +
  `isSource`/`isSink`/`isAdditionalTaintStep`. The
  source/sink/sanitizer triple is portable to sprf as an op family.
- **`@kind path-problem` query format**: structured result with
  source, sink, and intermediate path nodes. sprf's slot model
  could carry a path slot for the same shape.
- **`bindingset` annotations**: declare which predicate arguments
  must be bound at call site. Helps the planner; sprf would need
  this once joins get expensive.
- **Result caching at predicate granularity**: CodeQL caches
  predicate extensions across runs.
- **AST + dataflow + type info in one query**: CodeQL's
  `Expr.getType()`, `Callable.getACallee()` give cheap access.
  sprf's planned type-graph layer is in the same direction.

### What sprf would lose by adopting CodeQL's model

- **Closed-world assumption**: Datalog evaluates over a fixed DB.
  sprf's streaming cursor model with `(rev)` in the key is
  open-world by construction; same code at two revs is two cursor
  populations. Forcing a closed DB breaks revision-pair comparison.
- **Heavy extractor toolchain**: CodeQL extractors run the build.
  sprf reads `.git/objects/pack` and parses with tree-sitter;
  orders of magnitude lighter, scales to 500 repos on 16GB.
  Adopting extractor-style would kill that budget.
- **Restrictive query language**: QL is total, monotone (mostly),
  strongly typed. SQL's escape hatches (window functions, JSON,
  user-defined functions) vanish.
- **Single-language-per-DB**: CodeQL DBs are typed per language
  [staleness risk: multi-language DBs landed for some
  combinations]. sprf's `(fs, repo, rev)` cursor crosses languages
  naturally.
- **Effect model**: sprf's `sh[r]`/`sh[w]` first-class effects have
  no CodeQL analog; CodeQL queries are pure read-only against the
  DB.

### Cross-repo posture

[staleness risk: this section is the most likely to be outdated]

As of training cutoff, CodeQL's cross-repository story is:
- **Per-repo databases**: native unit. One DB per repo per language
  per build.
- **MRVA (Multi-Repository Variant Analysis)**: GitHub feature that
  runs the same query against many CodeQL DBs in parallel, aggregates
  results in the VS Code extension. Surfaces "this CWE pattern across
  N repos" but each query still runs DB-local; results are joined
  client-side, not in QL.
- **No native cross-DB joins**: a QL predicate cannot reference
  rows from another DB. Cross-repo edges (function in repo A calls
  function in repo B) require external glue.
- **Code scanning**: per-repo CI integration; results land in the
  repo's security tab.

sprf's `(fs, repo, rev)` as a first-class cursor field is the
inverse posture: cross-repo is the default unit, single-repo is a
degenerate case. A CodeQL query saying "rust type `Foo` in repo A is
used as entity in TS schema in repo B" requires custom tooling
outside QL; sprf expresses it as one rule.

### Similarity index — 35/100

Justification:
- +20 for relational core (both reduce code to tables, declarative
  joins).
- +10 for checked-in artifact framing (`.ql` packs ↔ `.sprf`
  files).
- +5 for per-language extractor architecture parallel.
- −20 for closed-world (CodeQL) vs streaming open-world (sprf).
- −15 for single-repo (CodeQL) vs cross-repo first-class (sprf).
- −10 for analysis depth (CodeQL has CFG/dataflow/types; sprf is
  grammar-level + planned type graph).
- −5 for query surface (QL vs SQL+pipeline DSL).
- +5 for OO-datalog ideas being portable as a future IR.

The 35 reflects "shared substrate, different applications." CodeQL
is closer to a competitor in the "structural pattern across code"
niche than to an inspiration, but the cross-repo axis and
lightweight extraction are large enough deltas that direct
competition is partial.

### One question CodeQL has answered that sprf should answer

**How does a rule depend on another rule, and how is that dependency
surface checked at author time?**

CodeQL's answer: `qlpack.yml` declares dependencies; `import` brings
predicates into scope; the QL type system checks predicate signatures
at compile time; a predicate's `bindingset` declares which arguments
must be bound by the caller; libraries version via the pack
manifest. Result: a query author composes 50-line queries on top of
thousands of lines of library predicates, with type errors caught
before evaluation.

sprf's current design has rules emitting per-rule SQLite tables that
downstream rules can `JOIN`, but the contract between producer and
consumer rules is the SQL schema, checked at SQL parse time, after
the upstream rule has already run. There is no declared rule-to-rule
dependency, no signature check at .sprf parse time, no library/pack
model for reusing rule sets across projects. As cross-codebase
invariants accumulate, this is the ergonomics gap CodeQL has the
strongest prior art on.

## 5. CUE — similarity 35/100

### CUE overview

Constraint-based configuration/data-validation language by Marcel
van Lohuizen (ex-Go team). All values, including types, inhabit a
single bounded lattice; the meet operator `&` is unification
(greatest lower bound), `|` is disjunction (least upper bound).
Unification is commutative, associative, idempotent, so evaluation
order is irrelevant. Surface syntax is JSON-shaped: structs, lists,
scalars, plus disjunctions, regex bounds (`=~`), pattern constraints
`[pattern]: T`, and definitions (`#Foo`) which recursively close
their structs.

### Structural overlap

| Axis                     | CUE                                          | sprefa v3                                                |
| ------------------------ | -------------------------------------------- | -------------------------------------------------------- |
| Bind site                | `name: T` field decl                         | `${NAME}` term decl                                       |
| Constraint composition   | `string & =~"^[a-z]+$" & len > 3`            | `${KEY > re{...} > json(...)}` (chain proposal)           |
| Reference                | lexical lookup against enclosing struct      | in-scope Decl set, any depth/origin                       |
| Match-as-template        | open struct = template                       | walker pattern `json({${K}: ${V}})`                       |
| Pattern on labels        | `[=~"^dep"]: T`                              | `${KEY > re{(d|devD)ependencies}}`                        |
| Bottom                   | `_|_` on conflict                            | `Tri::Refuted` from assumption checker                    |

The bind/match/constrain axis maps cleanly. CUE's `field &
constraint & constraint` chain is structurally the same shape as the
retracted sprf `${X > re{...} > json(...)}` chain. CUE's
`[=~"regex"]: T` is the closest published prior art to sprf's
pattern-with-guard `${KEY > re{...}}`. Both languages collapse "is
this thing a value?" and "is this thing a constraint on a value?"
into one syntactic position.

### Divergent intent

CUE: closed-world, finite value lattice, single evaluation produces
normalized JSON or bottom. No streams, no external addressing, no
notion of "where in some external repo did this come from". Every
reference resolves inside the loaded module set; cycles allowed
because the lattice is monotone.

sprefa: open-world streams of `Cursor{(fs, repo, rev), byte_range,
content, captures}`. Cursors flow through `BoxStream`, get
materialized to SQLite. Bindings cross repo/rev boundaries within
rule scope. The "address" is a structural triple, not a logical
name. Resolution is not lattice-monotone; it is a temporal walk over
commit history with `Tri` updated by an assumption checker.

CUE optimizes for: convergence, compositional override-without-
clobber, schema = template duality, validating finite inputs.
sprefa optimizes for: streaming throughput over many repos × many
revs, partial failure isolation per cursor, deferred effect
batching, cross-codebase edge materialization.

### What sprf could borrow concretely

- **Lattice-of-values mental model.** sprf already has Tri
  (Unverified/Verified/Refuted). Promoting Tri to a 4+ point lattice
  with explicit meet/join would let multiple assumption checkers
  contribute monotonically without the current "last writer wins"
  risk. CUE's "value is always final, can only be made more
  specific" rule answers the sprf design question of whether a
  downstream op may relax an upstream Tri. Answer in CUE shape: no,
  only narrow.
- **Bidirectional unification as the resolution rule.** CUE never
  distinguishes "decl site" from "ref site"; both sides unify the
  same way. sprf currently distinguishes Decl and Ref. The
  collapsed-term model in MEMORY (`project_term_unification`) is
  already moving CUE-ward. The endpoint is: a Decl is a Ref with no
  incoming binding yet, and the operator that binds is unification,
  not assignment.
- **Definitions-as-templates.** CUE's `#Foo` doubles as schema and
  as boilerplate. sprf rule files could expose reusable cursor-shape
  templates the same way: `#PackageJsonDep: json({${KEY > re{...}}:
  {${NAME}: ${VERSION}}})` reusable across rules.
- **Closed vs open structs.** Direct analog for sprf: closed cursor
  pattern (must match exactly the listed slot keys) vs open (extra
  slots allowed). Currently sprf has no syntax for this; CUE's
  `close()` and `...` give a ready vocabulary.
- **`...T` for "everything else has shape T".** Maps to the
  unmatched-key case in walker patterns.
- **Disjunction with default `*`.** Maps to "try this op variant
  first, fall through to the next" without writing N rules.

### Constraints-as-types: CUE's answer to `${X > re{...}}`

In CUE:
```
KEY: string & =~"^(d|devD|peerD|optionalD)ependencies$"
```
The field name `KEY` is bound and constrained in the same
expression. There is no separate "guard" concept: `string` is a
constraint, `=~"..."` is a constraint, `&` composes them. The
result is itself a value living in the lattice.

The sprf retracted form `${KEY > re{...}}` is the same shape with
different syntax. The CUE answer to the question "should
constraint-chain be a first-class form or recursive pipeline at
expansion sites?" is: make it first-class because it composes via
the same operator that does everything else (`&`). If sprf adopts a
single `&` style meet operator across `Tri`, slot values, and
capture predicates, the chain form becomes free; if it stays with
pipeline-only, every constraint site needs a sub-pipeline.

Concrete sprf design implication: pick whether `>` (current pipe) is
`&` (meet, order-independent) or `;` (sequence, order-dependent).
CUE shows the cost of conflating them is high. The split sprf
already has between `>` (Seq) and `;` (Fork) is one axis short of
CUE's lattice algebra.

### What sprf would lose by going CUE-style

- **Streaming.** CUE evaluates a finite term to a normal form.
  There is no `BoxStream`. Adopting CUE wholesale forces buffering
  every cursor before resolution.
- **External addressing.** CUE has no concept of `(fs, repo, rev)`.
  Cursors as first-class values do not fit the JSON-shaped lattice
  without inventing a `#Cursor` definition that re-encodes them,
  which loses the reader/writer separation.
- **Effect ordering.** CUE is pure. sprf v3 has `sh[]`, edits,
  deferred effects with batching. Lattice unification cannot express
  "run X, then if Y holds, run Z".
- **Open-world rev walking.** CUE assumes the value set is loaded
  and finite. sprf walks history, where the set grows during
  evaluation.
- **Per-cursor partial failure.** CUE bottom poisons the whole
  expression. sprf must isolate failure to one cursor and keep the
  stream alive.

### Similarity index — 35/100

High overlap on the inner expression algebra (bind + constrain +
match), low overlap on the runtime (closed lattice eval vs open
streaming pipeline). The mental model for what `${X > re{...}}`
*means* is ~70% CUE; the model for what a sprf rule *does* is ~10%
CUE. Weighted toward execution model because that drives the bulk
of sprf's code.

### One question CUE has answered that sprf should answer

**"When two sources both bind the same name, what happens?"**

CUE: unify them. Result is the meet. If incompatible, bottom.
Order-independent. This collapses inheritance/override/merge debates
into one rule.

sprf v3 currently has multiple half-answers: assumption checker
writes Tri (last writer? meet?), cursor.captures merging on Fork
joins (undefined), cross-rev binding persistence (scope-bounded but
merge rule unspecified). The CUE answer — "always meet, never
overwrite, bottom on conflict, expose bottom as a per-cursor
diagnostic rather than a global error" — is directly portable and
removes a class of ordering bugs before they exist.

## Synthesis

Five systems, five similarity scores: Glean 62, Racket 38, Salsa 38,
CUE 35, CodeQL 35. The spread is narrow (35-62) because every
candidate matches sprf on one axis and diverges on another. None is
a clean clone; none is unrelated.

### Where each lands relative to sprf

| System  | Score | Closest mechanism overlap                                  | Where it diverges                                              |
| ------- | ----- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| Glean   | 62    | Whole thesis: typed facts + derived views + per-language schema + LSP-on-top | Pure read store; no shell effects; non-recursive query layer |
| Racket  | 38    | Reader-extension axis (per-`#lang` ↔ per-op grammar) + hygiene literature | No streaming, no Reader, no fs/repo/rev, no LSP-grade recovery  |
| Salsa   | 38    | Cancellation, accumulator, demand-driven invalidation       | Pull memo vs push-pull stream; no cross-process result store    |
| CodeQL  | 35    | Relational core + `.ql` pack as artifact + OO-datalog       | Closed-world, single-repo, heavy extractors                     |
| CUE     | 35    | Bind+constrain+match expression algebra; lattice for Tri    | Closed lattice eval, no streaming, no effects                   |

### Cross-cutting observations

1. **No system covers the whole sprf surface.** Each prior art
   handles 30-60% of the design. The composition sprf is reaching for
   (streaming + per-op grammars + cross-repo + effects + materialized
   tables + LSP) is genuinely novel as a single artifact, even though
   each piece has prior art.

2. **The thesis lives at Glean's address.** "Typed facts about code,
   per-language schemas, derived views, language-neutral middle
   layer, LSP on top" is what Glean already shipped. sprf's
   distinctive deltas vs Glean: cross-repo first-class, drift
   detection (rules assert AND extract), lightweight tree-sitter
   indexers, recursive SQLite queries, embedded shell effects.

3. **The mechanism lives at Racket's address.** Per-op grammar +
   recursive injection + named pipelines + hygiene is solved
   territory in Racket, with 30+ years of refinement. sprf is
   rediscovering the syntax-parameter / scope-set tradeoffs the
   Racket community has already mapped.

4. **The runtime lives at Salsa's address.** Demand-driven
   invalidation, cancellation, accumulators, cycle handling are all
   things rust-analyzer already proved out for code-analysis
   workloads. The push-pull-stream vs pull-memo split is the actual
   architectural fork; Salsa's seam pattern (Salsa underneath
   Reader/parse, streams above) is a real option.

5. **The expression algebra lives at CUE's address.** Bind +
   constrain + match as one operation, lattice-with-meet,
   bidirectional unification — CUE has the cleanest answer to "when
   two sources bind the same name, what happens?" that sprf hasn't
   committed to.

6. **CodeQL is the competitor framing.** Same niche (queries over
   code as a shippable artifact), wholly different posture
   (closed-world, single-repo, deep semantics vs open-world,
   cross-repo, structural). Worth knowing the design choices CodeQL
   made on rule-to-rule dependency, library packs, and binding
   modes since sprf will need answers in the same shape.

### Five concrete questions the survey forces on sprf design

Each prior art's "one question they've answered well":

1. **Glean**: rule-shape migration. What happens when a rule's
   schema changes? (`stored` vs on-demand, `default` derivation,
   schema versioning.)
2. **Racket**: hygiene for named pipelines. When `${NAME}` is
   invoked at a use site, which identifiers see definition-site
   binding vs use-site binding? (Per-identifier `syntax-parameter`
   declaration.)
3. **Salsa**: revision-vs-content invalidation granularity. At what
   level does sprf compare new-output to last-output and short-
   circuit downstream? (Per-query return-value Hash early-cutoff.)
4. **CodeQL**: rule-to-rule dependency surface. How is "rule B
   joins rule A" declared and checked at .sprf-parse time? (Pack
   manifest, import, signature check, `bindingset`.)
5. **CUE**: name-collision merge rule. When two sources bind the
   same name, what happens? (Always meet, never overwrite, bottom
   on conflict, per-cursor diagnostic.)

These five are the load-bearing design holes the survey surfaced.
None decides them; each names them. Worth having an answer (even
"punted") on each before v3 lands.

### Honest limits of this synthesis

- Five candidates is a sample, not a survey. Other systems (Soufflé,
  Differential Datalog, Stack Graphs, Unison, Pkl) might score
  higher on some axes if assessed.
- Similarity scores are subjective and weighted by mechanism volume,
  not by relevance to sprf's biggest design risks.
- Each agent had limited time per system; deeper reading would shift
  some scores.
- The "one question to answer" lens biases toward problems each
  system has explicitly addressed; sprf-specific problems with no
  prior art (cross-repo edges as first-class, drift detection in the
  rule itself) get less play than they deserve.

The session's net read: sprf is closer to a Glean variant with
Racket's grammar layering, Salsa's reader incrementality, CUE's bind
algebra, and a SQL terminal that CodeQL would never adopt. None of
those four are silver bullets; all four are worth keeping near the
desk.
