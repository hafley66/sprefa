## Problem/Context
First linux bench surfaced two reconcile bugs simultaneously:
1. correctness: 1081 vs 16627 matches (94% drop)
2. perf: 8.114s vs 4.451s baseline (1.8x cold)

Hypothesis at first was per-child blake3 cost or Mutex contention. Wrong. Diff against biome (4079 files, no regression there) showed the bug is corpus-size-dependent.

### Root cause (turned out to be one bug)
`FsComponent::dispatch` flushes its buffer multiple times during a single dispatch (linux 63k / batch 4096 ≈ 16 flushes). Each `splice_into` call invokes `flatten` which assigns `batch_idx = 0..N` from scratch, so children from flush 2..16 collide on path with flush 1 children.

System invariant: `row.path` uniquely identifies sibling position under a parent.

- Invisible for splice (doesn't read path) and content-keyed Memoize (cache key is content_hash).
- Fatal for position-keyed reconcile: `Memoize::dispatch` calls `idx.take(&row.path)` for path=[0]. Flush 1 puts children at idx[[0]]. Flush 2 dispatch take()s those as "prior", `diff_children` finds different content_hashes (different files), marks them doomed, cascade_deletes already-enqueued match cursors before Count fires.

Same root cause explains the 2x cold cost: cascade_delete spam.

## Solution/Approach
Add path-offset variants to flatten/splice helpers; document path-uniqueness invariant.

- `flatten_at(node, parent, next_depth, expand_tick, batch_idx_start: u32) -> Vec<QueueRow>`
- `splice_into_at(parent, node, next_depth, expand_tick, queue, batch_idx_start) -> usize` returns count
- `splice_into_recorded_at` similarly
- `splice_into` and `flatten` keep their old signatures, delegate with offset 0
- `FsComponent::dispatch` threads `next_idx: u32` across flushes; `flush(buf, &mut next_idx)` adds returned count

Audit of other splice_into call sites (chan.rs::Next, component.rs default dispatch, memoize.rs no-children branch, tests.rs SwitchMap): all single-call-per-row, no collision risk. Only Fs needed the fix.

## Key Insights
- **Path-uniqueness is a system invariant.** `row.path = parent.path + [batch_idx]`. Any caller that emits children for one parent across multiple splice calls must thread a continuous offset. Splice didn't enforce or expose this; bug was latent until reconcile was added.
- **Content-keyed memo and position-keyed reconcile read DIFFERENT row attributes.** Memoize's cache key is content_hash; reconcile's identity is path. A bug in one identity dimension is invisible to consumers using the other.
- **cascade_delete is the expensive shape under reconcile path bugs.** ~60k spurious cascades on linux. Per-child blake3 is in the noise — was never the cost.
- **biome (4079 .rs in single FS flush) hid the bug.** One flush = no collision. Scale-dependent bug. Linux's 63k+ file count = 16 flushes was needed to surface it.
- **Reconcile share+scan trial 2+ == 0 matches is a separate, pre-existing, documented design pitfall** (with_prior_children docstring). Not a path-collision bug. Kept-children optimization assumes downstream parks persist across re-renders, which is true for LSP/watch and false for scan.
- **Bench-trial-2 0-match was previously 1081** (pre-fix). Now it's 0. The path-collision made trial 2 LOOK partially-broken instead of fully-broken. Fix exposes the real share+scan limitation cleanly.
