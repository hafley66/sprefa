# LO / HI / `_where_bytes` Audit — v4

**Date:** 2026-05-15  
**Scope:** `/Users/chrishafley/projects/sprefa/v4/src/`, `v4/tests/`, `v4/bench/`, `v4/examples/`  
**Mode:** Read-only.

---

## TL;DR (5 bullets)

1. **LO and HI are plain-string cursor terms** on every producer as of today; no producer calls `set_at` for them. They carry raw `u64` byte offsets serialized as decimal strings.
2. **Three real consumers exist** outside tests: `lsp.rs` span fallback, `v2_ops.rs` write_cursor fallback, and `where_eval.rs` numeric comparison. All three parse LO/HI as `u32`/`usize` from the string value.
3. **The compile pipeline still types LO/HI as `WhereBytesId`** in `binding_graph.rs:1241`, `fuser.rs:152-153`, and `ops.rs:1590-1591`. This is wrong: the runtime writes strings, but the fuser emits `INTEGER NOT NULL REFERENCES _where_bytes(id)`.
4. **MATCH carries the real provenance.** `set_at("MATCH", ...)` interns a full `WhereBytes` row (string + coord); `MATCH.lo`/`MATCH.hi`/`MATCH.fs` are derived projections the runtime also writes. LO/HI duplicate that information redundantly.
5. **The clearest fix** is to change `IdKind::WhereBytesId` to `IdKind::Int` for LO/HI columns. Zero schema churn in `_where_bytes`; the FK constraint becomes a raw integer; consumers continue reading decimal strings.

## Phase 2 — `_where_bytes` Usage

### Table schema

Declared at `v4/src/store.rs:190-193`:

```
_where_bytes(id, string_id, file_id, lo, hi, repo, rev)
```

`id` is a `u64` blake3 hash over `(string_id, repo, rev, file_id, lo, hi)`. The `lo`/`hi` columns here are `u32` byte offsets stored as strings in the Cursor row used to insert; SQLite stores them as integers via the TEXT-to-INTEGER affinity.

### WhereBytes struct (`v4/src/lib.rs:116-123`)

```
pub struct WhereBytes {
    pub string: StringId,   // FK into _strings
    pub repo:   RepoId,
    pub rev:    RevId,
    pub file:   FileId,
    pub lo:     u32,        // byte offset, 0-based, inclusive
    pub hi:     u32,        // byte offset, 0-based, exclusive
}
```

This is content-derived: same (string, repo, rev, file, lo, hi) always yields the same `WhereBytesId`. Unlike `Ref` (which is coord-only), `WhereBytesId` folds the matched string value into the hash, so two matches at the same span with different text get different ids.

### FK columns in `<rule>_facts` tables

The fuser at `v4/src/compile/fuser.rs:400-420` generates `CREATE TABLE IF NOT EXISTS <rule>_facts` DDL. For any column whose `TypeLattice` is `WhereBytesId`, it emits:

```sql
LO INTEGER NOT NULL REFERENCES _where_bytes(id),
HI INTEGER NOT NULL REFERENCES _where_bytes(id)
```

This means the LO/HI columns in fact tables are declared as FK references into `_where_bytes`. **But** the runtime writes raw decimal byte offsets into these columns (via `child.set("LO", r.start.to_string())`), not `WhereBytesId` hash values. The FK constraint is therefore broken by design: the integer `12345` stored in `hits_facts.LO` is a byte offset, while `_where_bytes.id` stores blake3 hashes. These are incommensurable.

This is the central type lie: `TypeLattice::WhereBytesId` / `IdKind::WhereBytesId` claims the column holds a `_where_bytes` FK, but the runtime writes a raw integer.

### `IdKind::WhereBytesId` vs `IdKind::Int` — where honesty fails

```
binding_graph.rs:1241   ("ast","LO") | ("ast","HI") => TypeLattice::WhereBytesId
fuser.rs:152-153        (Col::from("LO"), IdKind::WhereBytesId)
                        (Col::from("HI"), IdKind::WhereBytesId)
ops.rs:1590-1591        (Col::from("LO"), IdKind::WhereBytesId)
                        (Col::from("HI"), IdKind::WhereBytesId)
```

These four sites all claim LO/HI carry a `_where_bytes` FK. Post the LO/HI `set_at` → `set` cut, they carry raw byte offsets. `IdKind::Int` is the correct label.

## Phase 3 — What "byte index" means

### How ast emits range (`v4/src/v2_ops.rs:887-934`)

```rust
let hits: Vec<Node<Cursor>> = ranges.into_iter().map(|r| {
    let mut child = c.clone();
    child.set("LO", (r.start as u64).to_string());
    child.set("HI", (r.end as u64).to_string());
    // ...
    child.set_at("MATCH", slice, coord, store);  // coord.lo = r.start as u32
}).collect();
```

`r` is an `ast_grep` `Range` (Rust `std::ops::Range<usize>`). The `start`/`end` are byte offsets as returned by tree-sitter's byte-range API. tree-sitter always provides UTF-8 byte offsets, not character/codepoint offsets.

### WhereBytes lo/hi fields (`v4/src/lib.rs:121-122`)

```rust
pub lo: u32,   // byte offset, 0-based, inclusive start
pub hi: u32,   // byte offset, 0-based, exclusive end
```

`hi - lo` = byte length of the matched text. `src.get(lo..hi)` gives the matched slice.

### Answers

| Question | Answer |
|---|---|
| Integer byte offsets vs character offsets? | **Byte offsets** (UTF-8). tree-sitter and `regex` both produce byte ranges. |
| Relative to file start or chunk? | **Relative to file start**, 0-based. `src = full file content as &str`; `r.start` is the offset from byte 0. `CommentComponent` is the exception: its lo/hi are relative to `cursor.value` (not the original file), since it operates on a string passed through the cursor. |
| LO < HI always? | **Yes for non-empty matches.** LO == HI is theoretically possible for zero-length tree-sitter matches (e.g., empty captures), but no current pattern intentionally produces them. `source_aware_ast_smoke.rs:66` asserts `where_bytes.hi > where_bytes.lo`. |

## Phase 4 — Recommendations

### 1. Should LO/HI exist at all?

**Verdict: retain, but as integers.**

MATCH's `_where_bytes_id` carries `lo`/`hi` derivable via `where_bytes_of(id).lo/.hi`. However:

- Multiple `.sprf` programs use LO/HI directly in message templates: `${FS}:${LO}`, `${FILE} byte ${LO}..${HI}`. These are display-side uses that do not need a FK join.
- The `where \`${LO} > 100\`` predicate in `linux-tiny-where-mid.sprf` and `${LO} != ${OTHER_LO}` in the join bench do arithmetic comparisons on raw integers. These work because LO is a decimal string that the where-eval parser handles numerically. Replacing this with a `WhereBytesId` would require a UDF to extract lo from the FK.
- `lsp.rs` and `write_cursor` use LO/HI as a **fallback** when `c.at` is synthetic. These are legacy paths that will remain needed for hand-built cursors and tests.

Eliminating LO/HI entirely would require: replacing all `.sprf` message templates using `${LO}`/`${HI}` with `${MATCH_LO}`/`${MATCH_HI}` equivalents, and changing `lsp.rs` + `write_cursor` to only use the `at` coord path.

LOC delta if eliminated: ~40 lines removed (producers) + ~15 lines changed in consumers + ~10 `.sprf` template edits. Medium complexity, high breakage of user-visible naming.

**Retain LO/HI.**

### 2. Raw INTEGER vs FK to `_where_bytes`?

**Verdict: raw INTEGER.**

The `set_at` → `set` cut was the right call. The `_where_bytes` FK for LO/HI added:

- One `intern_where_bytes` call per match with no string (coord-only intern, cheaper but still a hash + hashmap lookup)
- One extra row in `_where_bytes` for every lo-value and every hi-value separately (two rows per match, neither carrying the matched string since that's on MATCH)
- FK integrity in SQLite that is semantically meaningless: "LO = 12345" does not mean "there is a `_where_bytes` row with id 12345 at that exact span". It happened to work because the coord-only WhereBytesId was derived via `blake3(repo,rev,fs,lo,hi)` which maps to a real row, but the LO column value was the *position*, not the id.

Current state post-cut: LO/HI are `INTEGER NOT NULL REFERENCES _where_bytes(id)` in DDL (wrong) but store raw offsets (correct behavior). The FK constraint is unsatisfiable if SQLite enforces it (it doesn't by default, since `PRAGMA foreign_keys = OFF` is typical in embedded use).

**Fix the DDL** to drop the FK: change `IdKind::WhereBytesId` to `IdKind::Int` for LO/HI. The generated DDL becomes `LO INTEGER NOT NULL` (no REFERENCES clause). That matches reality.

LOC delta: 4 sites, ~8 lines changed. Zero behavior change at runtime.

### 3. Should `WhereBytesId` be split into coord-only vs coord+string?

**Verdict: the split already exists informally.**

`WhereBytesId::of(w)` includes the string in the hash when `w.string != StringId::EMPTY`.  
`WhereBytesId::coord_only(w)` (`lib.rs:210-212`) hashes only the coord fields.

These two constructors already implement the split. What is missing is a distinct type so the compiler enforces which variant is in use. MATCH always uses the full `of(w)` path (string present). LO/HI used to use `coord_only` when they were interned at all.

A formal `CoordId` type wrapping `u64` for coord-only spans would eliminate the ambiguity. LOC delta: ~50 lines (new type + conversions). Low priority.

### 4. Should `IdKind::WhereBytesId` be replaced with `IdKind::Int` for LO/HI?

**Verdict: yes, do this.** This is the clearest and lowest-risk fix.

Sites to change:

| File:line | Change |
|---|---|
| `v4/src/compile/binding_graph.rs:1241` | `TypeLattice::WhereBytesId` → new `TypeLattice::Int` or keep `WhereBytesId` for MATCH only; LO/HI → plain `TypeLattice::Bytes` or `TypeLattice::String` with numeric coercion |
| `v4/src/compile/fuser.rs:152-153` | `IdKind::WhereBytesId` → `IdKind::Int` |
| `v4/src/compile/lower/ops.rs:1590-1591` | `IdKind::WhereBytesId` → `IdKind::Int` |
| `v4/src/compile/fuser.rs:379-388` | `id_type_for` and `intern_table_for` must handle `IdKind::Int` → `"INTEGER"` with no REFERENCES clause |

Consumer changes required:

- `v4/tests/liftable_classify_target.rs:54-59` — asserts `IdKind::WhereBytesId` is present in ast schema. This test would need to be updated to assert `IdKind::Int` for LO/HI, or assert only that MATCH/FILE columns carry `WhereBytesId`.
- `v4/tests/term_flow_graph_target.rs:153-155` — asserts `lo.value_lattice` is `WhereBytesId | Tokens | Tree`. This would become `String | Bytes` or a new `Int` variant.
- `v4/tests/liftable_classify_target.rs:43` — comment "LO/HI must use WhereBytesId" would become incorrect documentation.

LOC delta: ~4 production sites + ~3 test sites. Total ~20 lines.

**Top recommendation: change `IdKind::WhereBytesId` to `IdKind::Int` for LO/HI** (Q4). It's 4-site compile path fix, removes a false FK constraint from generated DDL, correctly reflects that LO/HI hold raw byte offsets.

## Phase 5 — Five LO/HI Usage Stories

### Story 1: `bench/linux-tiny-where-mid.sprf` — numeric filter

```sprf
rule(:hits_filtered, FS?, LO?) {
  fs(glob`**/*.c`) > ast(:c)`printk($$$)` > where`${LO} > 100`
};
```

**Producer:** `AstNmComponent` writes `child.set("LO", r.start.to_string())`.  
**Consumer:** The `where` op's `where_eval.rs` parser evaluates `${LO} > 100` by calling `c.get("LO")?.parse::<f64>()` (numeric coerce path). Passes if byte offset > 100.  
**LO as raw int vs WhereBytesId FK:** Works correctly only as a raw integer. If LO held a `WhereBytesId` (a blake3 truncated hash), the comparison `hash_value > 100` would be meaningless. The where-eval path has a test at `where_eval.rs:577-582` that exercises exactly this: `${LO} > 100` with `cur(&[("LO","200")])` passes and `cur(&[("LO","50")])` fails.

### Story 2: `bench/linux-join.sprf` — self-join on LO

```sprf
rule(:hits, FS?, LO?) {
  fs(glob`**/*.{c,h}`) > ast(:c)`printk($$$)`
};

rule(:hit_pairs, FS?, LO?, OTHER_LO?) {
  hits(FS?, LO?) > hits(FS?, OTHER_LO?) > where`${LO} != ${OTHER_LO}`
};
```

**Producer:** `AstNmComponent` → `hits_facts.LO` stores byte offset.  
**Consumer (full-SQL kind):** The fuser emits a JOIN between two instances of `hits_facts` on `FS`, with a WHERE clause `LO != OTHER_LO`. The join predicate P2 (predicate pushdown) moves this into the ON clause. The comparison is integer inequality on raw byte offsets.  
**LO as raw int vs WhereBytesId FK:** If LO were a `WhereBytesId`, the `!=` comparison would still work (comparing two opaque integers), but the semantic would be "different identity hash" not "different byte position". Two matches at different positions that happen to hash-collide (birthday problem) would be incorrectly considered equal. As raw integers, equality means same byte offset, which is the correct notion for deduplication.  
**Note:** The `linux-tiny-join.sprf` bench is identical in structure.

### Story 3: `examples/dev-rust-panic-map.sprf` — display in LSP warning

```sprf
rule(:panic_sites, FS?, LO?, HI?);

fs
  > glob`**/*.rs`
  > ast(:rs)`panic!($$$ARGS)`
  > panic_sites(FS, LO, HI)
  > lsp_warn(:panic_site)`panic! call at ${FS}:${LO}`;
```

**Producer:** `AstNmComponent` → LO = byte offset of `panic!(...)` match start.  
**Consumer:** `lsp_warn` renders the template `panic! call at ${FS}:${LO}`. `c.get("LO")` returns the decimal string "12345" which is embedded verbatim in the diagnostic message. The LSP span itself comes from `c.at` (the focal coord stamped by `stamp_source_value`), **not** from LO/HI; the `span_from_legacy` fallback is only reached if `c.at == Ref::SYNTHETIC`.  
**LO as raw int vs WhereBytesId FK:** If LO held a WhereBytesId (a large hash integer), the message would read `panic! call at src/foo.rs:14368218745828381696` instead of `panic! call at src/foo.rs:12345`. Display would break. Raw integer is mandatory for this use.

### Story 4: `examples/dogfood-comment-region-lsp.sprf` — comment region span display

```sprf
rule(:doc_regions, FS?, LO?, HI?);

path`v4/docs/v4-self-doc-architecture.md`
  > read
  > comment(`<!-- sprf:self-doc:start -->\n`, `\n<!-- sprf:self-doc:end -->`)
  > doc_regions(FS, LO, HI)
  > lsp_info(:self_doc_region)`self-doc generated region ${FS}:${LO}-${HI}`;
```

**Producer:** `CommentComponent` (`v2_ops.rs:2868-2869`) — LO/HI are byte offsets **within `cursor.value`** (the file's content as loaded by `read`). The comment op does not work off a file path; it slices `hay[lo..hi]` from the parent cursor's value string. The focal coord inherits `parent_fs` from `c.at`, but lo/hi are relative to `cursor.value`, not necessarily file-start — unless `read` placed the entire file in `value` starting from offset 0 (which it does for whole-file reads).  
**Consumer:** Template display and `lsp_info` span fallback. The diagnostic message renders LO/HI as human-readable byte positions.  
**LO as raw int vs WhereBytesId FK:** Same as Story 3 — display requires readable integers.

```sprf
  > render.markdown`    <section class="node">
      <strong><a href="../../${FILE}">${NAME}</a></strong>
      <div class="edge">${FILE} byte ${LO}..${HI}</div>
    </section>
`
}
```

**Producer:** `AstYamlComponent` (`v2_ops.rs:1033-1034`) — LO/HI set from `r.start`/`r.end`.  
**Consumer:** Template rendering; `${LO}` and `${HI}` become HTML text. The HTML comment reads `v4/src/lib.rs byte 4096..4612` — a human-readable byte range link. LO and HI are stored in `source_type_defs_facts` and `runtime_nodes_facts` as INTEGER columns. No join on LO/HI; they flow through as opaque values.  
**LO as raw int vs WhereBytesId FK:** Same constraint as Stories 3/4. If LO/HI were hashes, the HTML output would contain garbage numbers. Raw integers are the only sensible choice for this display-side use.

## Appendix: `_where_bytes` table structure

```
_where_bytes
  id         u64  — blake3(string_id, repo, rev, file_id, lo, hi)[0..8] BE
  string_id  u64  — FK _strings(id); 0 = no string (coord-only)
  file_id    u64  — FK _files(id); 0 = synthetic
  lo         u32  — byte offset inclusive start
  hi         u32  — byte offset exclusive end
  repo       u64  — FK _repos(id)
  rev        u64  — FK _revs(id)
```

Row 0 is the SYNTHETIC sentinel (all zeros). Dedup: `intern_where_bytes` checks `seen_refs` bitset before insert.

The `find_where_bytes_covering(file, byte)` method (`store.rs:685`) queries rows where `lo <= byte && byte < hi` for a given file — this is the only "lookup by coordinate" path and is used by the LSP click-to-span flow. It has nothing to do with LO/HI cursor terms.
