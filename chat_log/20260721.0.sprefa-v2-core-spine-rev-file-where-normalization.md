## Problem/Context
Core defect confirmed from the live db schema: repo / rev / file were NEVER
normalized into dimension tables. Every fact family stamps repo_sid / rev_sid /
file_sid as separate REFERENCES _strings(id) columns on every row, plus indexes.
Cardinality proof: _call_def has 1 distinct repo_sid and 2 distinct rev_sid, yet
rev_sid is stamped + indexed on ~1.5M fact rows across families. _strings is the
only clean surrogate; _df_node_dict is the only real dimension table; _repo /
_ref / _rev_log exist as EMPTY unused skeletons. _file and _files are two
competing file models, both TEXT-keyed. _where_bytes has the right core columns
(string_id, file_id, lo, hi) but is polluted with id TEXT PK + denormalized
repo TEXT / rev TEXT / path TEXT columns.

## Solution/Approach
NON-NEGOTIABLE schema laws set by user: integer surrogate FK ids only; a string
lives in exactly ONE dimension row and is never repeated on facts; a FK stands
alone with NO denormalized twin column (no rev_id + rev TEXT side by side). User
makes the table/column NAMES; use the v0 names, do not invent. Recover the v0
spine from the archive rather than re-deriving.

## Key Insights
- rev has near-zero cardinality (1 repo, 2 revs in this db) but is the most
  repeated + indexed column in the db. A rev(id, repo_id, hash) table turns a
  ~5-byte sid on ~1.5M rows into a 1-2 byte rev_id. Biggest single column win.
- scip is NOT a substitute for dataflow (9% coord overlap; no flow edges). It
  should reference the shared coordinate/where + rev tables like every family,
  not be a parallel coordinate universe.
- `where` (the v0 name for the byte-span/coordinate table) points to the physical
  file. Files keyed by git oid OR content hash. There is a file table in v0.
- The dense sym_alloc pattern (0.12.0) is the reusable allocator template for
  every new dimension: load-once, single-writer, persist-at-flush.
