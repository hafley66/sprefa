# 20260514.7 — fused-SQL execution wiring blocker

## Three blockers, escalating severity

### 1. Default store is MemFactStore, not SqliteFactStore

The bench command in the task spec:

```
./v4/target/release/sprefa-run v4/bench/linux-tiny-join.sprf --root … --telemetry --batch 65536
```

omits `--fact-db`, so `SprfState::new` falls through to `MemFactStore::new()`. The fused-SQL path can never fire — the spec itself says to skip SQL execution for MemFactStore. To exercise the new path the bench must pass `--fact-db /tmp/foo.db`.

### 2. Live SQLite schema mismatch

Live `<rule>_facts` from `SqliteFactStore::declare`:
- `_id TEXT NOT NULL UNIQUE` (hex-encoded blake3 of canonical row)
- `<col>_id INTEGER NOT NULL REFERENCES sprf_strings(id)` per declared column

Fuser-emitted SQL assumes:
- `_id BLOB PRIMARY KEY` (raw 32-byte sprf_blake3_id)
- Each column stored as INTEGER directly named `<col>` (not `<col>_id`)
- A `support_edges` table that the live store doesn't declare

The runner can rewrite source references through TEMP VIEWs (`hits_facts` → `hits` view exposing user-named text columns), and rewrite the INSERT projection to wrap each text expression in `(SELECT id FROM sprf_strings WHERE value = …)`. The `_id` mismatch can be papered over with `hex(sprf_blake3_id(...))` to land in the TEXT column.

This is the rewriting I implemented in `run_fused_sql`.

### 3. Fuser SQL has invalid column references — STOPPER

For the bench fixture:

```
rule(:hit_pairs, FS?, LO?, OTHER_LO?) {
    hits(FS?, LO?) > hits(FS?, OTHER_LO?) > where ${LO} != ${OTHER_LO}
};
```

`fused_statements()[0]` emits:

```sql
INSERT OR IGNORE INTO hit_pairs_facts (_id, FS, LO, OTHER_LO)
SELECT sprf_blake3_id('hit_pairs', r0.FS, r0.LO, r0.OTHER_LO) AS _id,
       r0.FS AS FS, r0.LO AS LO, r0.OTHER_LO AS OTHER_LO
FROM hits_facts r0
JOIN hits_facts r1 ON r0.FS = r1.FS AND r0.LO = r1.LO AND r0.LO <> r0.OTHER_LO
```

Three problems:
1. **`r0.OTHER_LO` does not exist.** Source table `hits_facts` declares only `FS, LO`. `OTHER_LO` is the binding name from the SECOND `hits(FS?, OTHER_LO?)` call, where the column read from `hits_facts r1` is `LO`. So `r0.OTHER_LO` and `r0.LO <> r0.OTHER_LO` are bogus.
2. **`r0.LO = r1.LO`** in the JOIN ON collapses the self-join to identity — the WHERE was supposed to be `r0.LO <> r1.LO` (the user's pushed-down predicate referencing OTHER_LO which lives on r1).
3. **The predicate `LO != OTHER_LO`** never gets resolved against the second alias.

Root cause in `fuse_full_sql` (v4/src/compile/fuser.rs ~456):
- `select_cols` projects every live capture from `aliases.first()` only (line 555), so OTHER_LO is incorrectly emitted as `r0.OTHER_LO`.
- The JOIN ON loop tries to emit shared-key equality for every binding by column name, but the second rule call binds `LO` (the source column) to `OTHER_LO` (the cursor capture). The fuser stores the rule-arg col name as the source column (per `classify_rule_call`), so the alias→col mapping cannot reconstruct "alias r1's LO is bound to OTHER_LO."

Fixing this requires the fuser to track per-alias bindings (alias r1: source col `LO` → cursor capture `OTHER_LO`). The current `binds: Vec<(Col, TermBind)>` stored on `Liftable::RuleQuery` carries the source col, but the fuser's emission code consults `live_cols(body)` and projects them positionally from `aliases.first()`, losing the capture→source-col indirection.

**This is a fuser logic bug, not a runtime wiring problem.** The task constraints forbid changing fuser logic, so I cannot fix it in this turn.

## Resolution chosen

1. Add the runner wiring (`run_fused_sql` in `v4/src/app.rs`) so the seam exists. When the SQL the fuser produces is structurally valid, it executes against the live schema via the rewriter described in §2. When SQL execution fails (as it does today for the bench fixture, per §3), we log a warning and fall through to legacy expand so behavior is unchanged from before this patch.

2. Add the `SqliteFactStore::with_connection`, `bump_table_version`, `mark_table_dirty`, `record_sqlite_insert_exec` public APIs needed by the wiring.

3. The `fuser_kinds_target` tests still pass (they assert on SQL string shape, not execution).

4. Bench result for `hit_pairs` stays at 0 rows until the fuser is fixed. The wiring is in place; once §3 lands, removing the fall-through is one diff.

## Files to fix in a follow-up

`v4/src/compile/fuser.rs::fuse_full_sql` — track per-alias source-col → cursor-capture bindings; project columns through the correct alias; emit JOIN ON predicates that use shared-binding equality (not shared source-col name); resolve `${CAPTURE}` references in `where`/Pure filters against the alias that binds that capture.

Then in `v4/src/app.rs::run_fused_sql`, the fall-through-on-error branch becomes a hard error.
