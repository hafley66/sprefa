## Solution/Approach

### Parse layer

One entry point. One return type. Tree-sitter does the recovery work;
the wrapper just walks the CST to project `OpInvocation`s and to collect
`ERROR`/`MISSING` diagnostics.

Critical detail learned the hard way: `descendant_for_byte_range` returns
the *smallest* node covering a range. When an `op_invocation` wraps just
an `identifier`, the byte ranges coincide, so the lookup returns the
identifier — wrong. Fix: walk `parse_site.path` from the root via
`named_children().nth(idx)`. Index discipline: `enumerate()` across all
named children (NOT filtered) so the index matches `named_child(idx)`.

### Op surface

`pipeline::Op` already had `name() + pipe(ctx, cursor) -> BoxFuture<Vec<Cursor>>`.
This slice just authors three ops against it. Each op is one file. The
ops own their ergonomics (name, args, pipe behavior); framework just
dispatches.

`last_bound` mechanic: every op that names a span (`> $TARGET`,
`tag(:foo, $X)`, etc) sets `last_bound`. Every op that consumes "the
last thing" (`$$`) reads it. This avoids the Java-ism of dragging an
explicit "current binding" arg through every chain.

### Carveouts (definition pass, no code yet)

`${pipeline}` and `&{pipeline}` already have first-class CST nodes via
`carveout_expr`. Lowering target is `Term::Carveout(Box<Pipeline>)`
(already declared in `pipeline/lower.rs:68`). Runtime semantics:

1. Outer op's sub-grammar parses slot body with carveout ranges
   *excluded* (`set_included_ranges`). Outer pattern sees holes.
2. CarveoutOp runs the inner Pipeline against a derived sub-cursor.
3. Inner cursors' active bytes splice into the outer slot's holes.

`${...}` = HostExpr (value substitution). `&{...}` = Address
(`Term::CursorRef(PathExpr::Computed(Box<Pipeline>))`). Single-level
only. `PathSeg::Carveout` opaque.

## Key Insights

1. **descendant_for_byte_range collapses on single-child wrappers.**
   When an `op_invocation` wraps just an identifier with the same byte
   range, the lookup returns the identifier. Always reconstruct nodes
   by walking the named-child path from root.

2. **enumerate() must be over the unfiltered named_children iterator.**
   Filtering before enumerate produces an index that doesn't match
   `named_child(idx)`, because line_comments are also named.

3. **Tree-sitter recovery replaces all custom parse-error machinery.**
   `synth_fragment_op` / `synth_empty_fragment` / `ParseMode::Tolerant`
   are gone. The CST is always returned; LSP just walks ERROR/MISSING
   nodes for diagnostics.

4. **MISSING node kind is the "expected" token.** Tree-sitter sets
   `node.kind()` on a MISSING node to the expected token (e.g. `}`,
   `>`, `identifier`). This is the structured "expected" hint LSPs
   need; no need to reverse-engineer from messages.

5. **Tree owns the source-of-truth, slots are gone.** Ops don't get
   `ParenSlot { src, byte_range }` anymore. They call
   `OpInvocation::node()` and walk via `child_by_field_name("paren")`,
   then walk further via field accessors and named-child iteration.
   No byte rescanning; tree-sitter already did that work.

6. **TreeCursor borrows the Tree; scope walks before moving the Arc.**
   `Arc::new(tree)` then `tree.root_node().walk()` then trying to
   move `tree` into `ParsedSource` fails. Wrap walks in a block so
   the cursor drops first.

7. **last_bound is the bash $? of sprf.** Every op that names a span
   sets it; `$$` reads it. Removes the need to drag an explicit
   "current binding" through chain ergonomics.

8. **ParseError must carry byte_range AND structured kind.** Offset +
   string is an LSP regression vs v2. Saved as durable feedback memory.

## Open Questions

1. **CarveoutOp execution model** — does the outer op see the inner
   pipeline's *output cursors* (multi-cursor splice) or just the bytes
   of the first/joined cursor (single-substring splice)? Likely the
   former for join semantics, but downstream pattern matchers (regex,
   ast-grep) want a single byte sequence to match against. Decide at
   implementation time.

2. **`set_included_ranges` plumbing** — when a slot body has multiple
   carveouts, the outer sub-grammar needs the complement ranges. Where
   does this live: in the outer op (each op knows its carveouts and
   reparses its slot body itself), or in a shared helper that takes
   `(Node, &[carveout_range])` and returns a sub-tree? Current best
   guess: helper in `pipeline::ops::carveout_helpers` so each outer
   op is one line of "exclude carveouts, parse with my sub-grammar."

3. **Op registry shape** — `HashMap<&'static str, Arc<dyn Op>>` vs
   `HashMap<&'static str, fn(...) -> Box<dyn Op>>` (factory). Need to
   decide before lowering can run. Factory is more flexible (can
   inject parse_site / args). Direct dyn is simpler. Punt to lower
   session.

4. **Tree lifetime through Pipeline** — `OpInvocation` carries
   `Arc<Tree>`. When lowering produces `Pipeline::Op(Box<dyn Op>)`,
   how does the Op see the originating CST node at run time? Option
   A: each op factory captures the relevant `OpInvocation` at lower
   time and stores its own `Arc<Tree>` + node-id. Option B: a runtime
   `OpCtx` carries the tree. A is per-op clean; B is global. Likely A.

5. **DeprecatedScanSigil migration diag UX** — emit at parse-collect
   time (we know the kind from CST) or lazily at op-execution time?
   Parse-time is faster feedback; lower-time can attach more context.
   No strong opinion yet.
