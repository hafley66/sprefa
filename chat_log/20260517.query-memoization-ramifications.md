# Query memoization ramifications — identical `r?()` reuse

Date: 2026-05-17
Branch: `worktree-agent-a63881e8d3a668444`
Fix commits: `aa2dac71` (RED test), `34eec5a7` (fix)

## The defect, restated

Two syntactically-identical rule QUERY occurrences (`r?(...)`) over the
same seed batch lowered to the same SQL string. The durable mount in
`mounted_query` is keyed `(mount_id, input_key)` where
`mount_id = blake3(sql)` and `input_key = blake3(seed cursors)`. The
two occurrences collided on one mount. `record_sql_outputs` then ran
its `nodes_added_since(existing_cursor_ids)` diff: the first occurrence
wrote the OUTPUT rows, so the second occurrence saw every cursor id
already present and was deduped to zero rows. Silent — no diagnostic.

Reproduced at two scopes (both in `v4/tests/query_reuse_target.rs`):

- Two `r?()` sub-pipes in one `render.markdown` body — second block
  empty.
- Two sequential identical `r?()` statement pipes — second `write_file`
  target never created.

The "added since existing" diff is the correct mechanism for a
*reactive re-run* of the same logical mount across generations (rows
already flowed downstream last generation must not re-flow). It is
wrong as a dedup across two distinct lexical query sites.

## The fix

Tag each lexical query / `sql` site with a stable per-compile ordinal
(`LowerCtx::next_query_site()`), emitted as a leading `-- sprf-site:N`
SQL line comment by `sql::with_query_site_tag`. `sql_tokens` and SQLite
both skip the comment; `referenced_fact_tables` is unaffected. Distinct
sites now hash to distinct `mount_id`s, so each site owns its own mount
lineage and yields the full materialized set. Per-site cross-generation
incremental dedup is preserved (one site always carries the same tag).

The tag rides *inside* the persisted SQL text, so the reactive replay
path (`runtime_replay.rs`, which reconstructs `mount_id` via
`mount_id_for_sql(snapshot.sql)`) stays consistent without threading a
side channel.

## Correctness — when is reuse safe?

**Within a single run.** Facts are append-only within one run pass.
Each `r?()` site is a pure read over the materialized `<r>_facts`
table snapshot. Two sites, or one site re-dispatched, observe a
consistent table state for a given generation. Reuse of a materialized
result set across two *identical* sites is safe because the query is a
pure function of `(sql, referenced-table contents, seed batch)`. The
fix does not actually share one result buffer between the two sites; it
gives each its own mount so each independently materializes the same
rows. That is the conservative form of "reuse": same answer, no
cross-site coupling, no shared mutable cursor stream.

**Across generations (reactive / incremental).** The
`FactRuntimeGraph` dirty sweep re-runs a mount when a subscribed source
table changes (`notify_table_inserted` → owner dirty → replay). The
per-site `mount_id` is stable across generations because the site
ordinal is deterministic (single-threaded, deterministic lowering, new
`LowerCtx` per compile ⇒ Nth site always ordinal N). So generation G+1
of *site k* still keys to the same mount as generation G of *site k*,
and the `added since` diff still suppresses already-emitted rows for
that site. Invalidation is unchanged: the memo (the OUTPUT/CURSOR mount
rows) is overwritten by `record_mount` + `delete_matching` +
`insert_batch` on every run of that site at the new generation;
retraction of removed rows flows through `retract_supported_rows` and
`dirty_tables_for_sql_outputs` exactly as before.

**When must the memo be invalidated?** Same triggers as before the fix
— this change does not introduce a new cache, it de-collides an
existing one:

- Source table delta touching a `referenced_table` of the site →
  owner dirtied → replay re-materializes that site's mount, diffs vs
  prior OUTPUT, retracts dropped rows.
- Generation advance: OUTPUT rows are re-stamped with the new
  generation each replay.
- Seed batch change: different `input_key` ⇒ different mount slot ⇒
  independent materialization (already correct pre-fix).

## Key design — what is in the hash

`mount_id = blake3(sql_text)` where `sql_text` now begins with
`-- sprf-site:N\n`. The effective key is therefore:

| Component                     | Source                                  |
|-------------------------------|-----------------------------------------|
| rule name + projection shape  | already encoded in generated SQL select |
| arg arity                     | SQL column list / WHERE predicates      |
| grounded-arg literal values   | `quote_sql_literal` in WHERE clause     |
| which positions are holes     | Project vs BoundLiteral/BoundTerm modes |
| lexical occurrence ordinal    | `-- sprf-site:N` prefix (new)           |
| seed batch contents           | `input_key = blake3(seed cursors)`      |

Grounded args differ in the SQL literal text, so two `r?(:"a", V?)`
vs `r?(:"b", V?)` already hash apart even at the same site. Holes vs
grounded args differ in select/predicate shape, also already in the
SQL. The only thing the SQL string failed to distinguish was *which
lexical occurrence* — that is exactly what the site tag adds.

**False-sharing risk:** eliminated for the reported class (identical
text, same site impossible — one site == one ordinal). Residual: if a
future change makes site ordinals non-deterministic across runs (e.g.
parallel lowering, or `LowerCtx` reuse across compiles), replay would
reconstruct a different `mount_id` and lose incremental continuity for
that site. Guard: the ordinal counter must stay single-threaded and
per-compile. Documented on the `query_site` field.

**Collision risk:** blake3 over `(site-tag, sql, → mount_id)` plus
blake3 `input_key`. 256-bit; collision is not a practical concern.

## Memory cost at 500-repo polyglot scale

Consulted `sprf-dd-memory-tiering-500`. The mount tables
(`mounted_query_output`, `_cursor`, `_mount`, `_input`, `_dep`,
`_support`) are exactly the "computed rules / references" class the
skill says **belongs in the retraction-aware tier** — they carry
support edges and drive `retract_supported_rows`. They are *not* raw
string bytes, so they do not hit the 30 GB raw-string pathology
directly; `_cursor` blobs are the one place full cursor content is
hex-encoded and persisted.

Footprint delta from this fix: the site tag adds one short prefix to
each distinct query's SQL and **multiplies the number of distinct
mounts by the number of lexical occurrences of otherwise-identical
queries**. In practice the duplication factor is small (the arch-d2-map
case had 2). Upper bound estimate per duplicated site:

```
per mount row set ≈ (rows × cursor_blob_hex) + (rows × OUTPUT row)
                   + 1 MOUNT + N_inputs INPUT + N_dep DEP
```

At 500 repos, the dominant term is `_cursor` blob hex (2× raw cursor
bytes due to hex). The skill's compaction policy applies directly:

> `set_logical_compaction(now() - K_GENS) every M gens`, K=5, M=10.

The mount tables have no compaction today — they are overwrite-on-rerun
keyed by `(mount_id, input_key)`, so a *single* site's footprint is
bounded by its current result set, not history. The fix does not change
that bound per site; it changes the *count* of sites. Recommended
bound/eviction:

- **Per-(mount_id) cap**: keep the existing
  `MAX_RUNTIME_SQL_SUPPORT_ROWS = 10_000` skip-persist gate (large
  result sets fall back to non-persisted, fully recomputed each run).
- **Eviction**: add an LRU over `mount_id` keyed by last-touched
  generation; evict mounts whose owner has had no dirty sweep within
  `K_GENS` (mirrors the skill's logical-compaction window). Evicted
  mounts recompute on next demand — same correctness, bounded RSS.
- Cursor blobs should follow strategy 4 (tiered): store the cursor
  *content hash* in OUTPUT and page full blobs to a cold table / LRU,
  not hex inline. Out of scope for this fix; flagged.

Estimated incremental RSS from the fix alone at 500-repo scale: small
(a multiplier on an already-bounded per-site set; typical duplication
factor < 3). The pre-existing uncapped `_cursor` hex blob growth is the
real scaling risk and is independent of this change.

## DD analogy

Query reuse == sharing a Differential Dataflow **arrangement**: an
arrangement is a materialized, index-organized, retraction-aware view
of a collection that multiple downstream operators can `import` and
share instead of re-deriving. The mount table is the sprefa analogue —
a materialized result keyed by query identity, with support edges
playing the role of arrangement reference counts and
`retract_supported_rows` playing the role of arrangement compaction /
trace advance.

Where it breaks: in DD, two identical `arrange` calls on the same
collection are *deduplicated by the dataflow builder into one shared
arrangement* — sharing is the correct default and is safe because DD
tracks multiplicities (a row present "twice" has multiplicity 2, not a
lost row). sprefa's mount keyed purely by SQL text accidentally
replicated DD's "share identical arrangements" behavior **without DD's
multiplicity bookkeeping**: the second consumer got the *delta since
the first materialized* (≈ zero) instead of the full arrangement
contents. DD consumers always see the full arrangement on import; the
delta-only view is `arrange().stream` for *new* updates, which is the
reactive-replay case, not the fresh-import case. The fix restores the
"each consumer imports the full arrangement" semantics by giving each
lexical site its own mount, rather than implementing true multiplicity-
aware sharing. True sharing (one mount, fan-out to N consumers, refcount
by support edges) is the DD-faithful design and is the recommended
follow-up if the site-count multiplier becomes a memory problem.

## Interaction with invoke/owner memo and `r!()` bypass

- `RuntimeGraph::rule_memo_owner` (OwnerNode memo by
  `(rule_name, arg_keys)`) is a *different* memo for *bodied* rule
  invocation owners, not the SQL query mount. The `r?()` query path
  declares its owner via `declare_owner("sprf://ast/sql/{mount_id}")`
  — that owner URI now also varies per site (mount_id includes the
  tag), so two query sites get distinct owners and distinct support
  sub-graphs. No double-caching: the mount memo and the invoke/owner
  memo key on disjoint URI namespaces (`sprf://ast/sql/…` vs the bodied
  rule owner URIs).
- `r!()` force and `r()` call route through `rule_body_call_pipe` /
  `rule_apply_write_pipe` → `RuleInvokeComponent` / `FactWrite`. They
  never construct `SqlQueryComponent`, so `with_query_site_tag` does
  not touch them. `r!()` force bypass of content-dedup (via the
  `_call_seq` stamp) is unchanged and still correct.
- No new cache layer was introduced; the change de-collides the
  existing `mounted_query` mount key. So there is no new double-caching
  surface.

## Recommendation — scope

**Per-pipe (per lexical site), with epoch-stable identity.** This is
what the fix implements and it is the right scope:

- *Per-run* (regenerate every run, no memo) would lose the incremental
  replay benefit that `mounted_query` exists to provide.
- *Global-with-epoch* (one shared mount for all identical sites,
  refcounted by support edges, DD-faithful) is the theoretically
  cleanest and lowest-memory option, but requires multiplicity-aware
  fan-out so each consumer sees the full set — that is the DD
  arrangement-sharing design and a larger change. Defer until the
  site-count memory multiplier is shown to matter at 500-repo scale by
  the pinned perf test in `sprf-dd-memory-tiering-500`.
- *Per-pipe with stable ordinal* gives correctness now, preserves
  cross-generation incremental dedup, and keeps replay deterministic.
  Memory cost is a bounded multiplier on an already-bounded per-site
  set.

Two-line summary: keep per-lexical-site mounts (the fix); the
DD-faithful single-shared-arrangement-with-refcount design is the
follow-up only if the site multiplier breaches the RSS budget under
the pinned perf test.
