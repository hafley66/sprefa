# Session: path-tag-or-branching

## Goal
Design OR-branching primitive for sprefa rules that disambiguates branches, supports nesting, and reuses existing language mechanisms instead of adding new flow-control keywords.

## Current State
Spec written to `docs/labeled-branches-path-capture.md`. Implementation deferred until (1) unified parser for LSP+runtime lands, (2) operator registry refactor makes tags pluggable. `path()` will land as a registry entry, not a hardcoded AST variant.

## Problem/Context
Block semantics (NOTES.md Feature 5) needed an OR disambiguator. Existing `{ A; B; C }` already monomorphizes into N rules (`_3_lower.rs:280`) but branches are anonymous — downstream can't tell them apart, nesting produces anonymous cartesian products, no match-style dispatch.

Early drafts proposed `label:` prefix syntax on slots. User rejected: reuse existing block-keys mechanism (like `json({k:...;k:...})`).

## Solution/Approach
New `path()` tag with two EXCLUSIVE forms:

- **Form A** `path(PATTERN)` — 1 arg, no block — filter mode. Reuses `fs()` pattern grammar (glob, `re:`). Filters cursors by accumulated `$_path`.
- **Form B** `path() { k: ...; k: ... }` — no arg, with block — branching mode. Each block key appends a segment to the cursor's virtual path. Reuses existing block-keys parse mechanism from `json()`.

`path(PAT) {}` is a parse error.

Virtual filesystem framing: accumulated path is `/`-separated, shaped like a real filesystem path, so fs-pattern tags work uniformly on disk paths and eval-tree paths. This is the first homoiconicity crack.

`$_path` synthesized capture on each monomorphized rule, column in `{name}_data` table. Downstream `check` SQL or `path(PAT)` filter both dispatch on it.

AND/OR mapping (from rxjs analogy in prior session):
- `A > B` = AND (same row) ≈ combineLatest
- `path() {;}` = OR keyed ≈ mergeByKey (key = `_path`)
- SQL union on `_path` IS the mergeByKey

## Key Insights
- `{;}` is already OR via monomorphization; just lacked keys. Don't invent new flow control.
- Block-keys mechanism from `json()` is the reuse target, not a new `label:` prefix.
- `path()` two forms mirror `fs()`/`file()`/`folder()` shape — 1 arg pattern filter vs no-arg+block.
- Virtual filesystem framing unifies eval-tree paths with real fs paths under one pattern grammar. This is the homoiconicity seed.
- `mergeByKey` from prior rxjs analysis = SQL union on `_path`. No new runtime machinery needed.
- `check` SQL and `path(PAT)` filter are two dispatch layers; pick by fit.
- User wants rules-as-expressions long term (rule inline where tag can appear). `path()` is step 1.

## Open Questions
1. Unkeyed branches inside `path() {}`: error, or auto-index (`_0`,`_1`)? Auto-index keeps `_path` non-null.

3. Can `path()` appear inside `check` SQL, or rule-only? Rule-only for v1.
