# Effect-batching prior art: Haskell origins + Rust landscape

Research notes for sprefa v3 runtime design. Maps the
`EffectKind` + per-kind `Batcher<E>` + effect-tick runner pattern
to its Haskell lineage and to the Rust crates that implement
parts of it today.

---

## The core insight (one paragraph)

Batching opportunity **equals** applicative (parallel) composition.
Batching impossibility **equals** monadic (sequential) dependency.
If two fetches do not depend on each other (`liftA2 f fetchA fetchB`),
a framework can reorder them, collapse duplicates, and dispatch them
as one batch per source. If they depend on each other
(`fetchA >>= \a -> fetchB a`), the second cannot start until the first
returns, and no batching is possible across that boundary. Haxl's
implementation observes this statically: inside one "round" every
applicative branch gets flattened into one batch per DataSource, then
the round steps forward. Same machine as redux-saga ticks, RxJS frames,
and the v3 sprefa batcher window.

Primary source: Marlow, Brassel, Mainland, Marlow, Peyton Jones,
Rosen. *There is no Fork: an Abstract of a Monad for Concurrent
Data Access.* ICFP 2014.
<https://simonmar.github.io/bib/papers/haxl-icfp14.pdf>

## Haskell lineage

### 1. Haxl (Facebook, 2014)

The canonical "batching as a language feature" system.
Programs are written in the `Haxl` monad. Each data source
declares a `DataSource` instance: effect type + `fetch` function
that takes `[BlockedFetch req]` and fulfills them in parallel.
Framework does:

- caching (same `req` returns same `rsp` within a run)
- batching (collect all blocked fetches per round, dispatch per source)
- concurrency (sources run in parallel, not blocks within a source)

Citations:
- Paper: <https://simonmar.github.io/bib/papers/haxl-icfp14.pdf>
- GitHub: <https://github.com/facebook/Haxl>
- Hackage: <https://hackage.haskell.org/package/haxl>
- Simon Marlow's blog series:
  <https://simonmar.github.io/posts/2015-10-20-Fun-With-Haxl-Part-1.html>

### 2. Free monads + interpreters (Swierstra 2008)

*Data Types à la Carte.* Effects are ADT constructors; programs
are trees of those constructors; interpreters fold the tree.
Foundational paper for every effect system that followed, including
redux-saga's JS port of the idea.

Citation:
- Swierstra. *Data types à la carte.* JFP 2008.
  <https://www.cs.ru.nl/~W.Swierstra/Publications/DataTypesALaCarte.pdf>

### 3. Extensible-effects family (2013–2024)

Each effect is its own GADT; handlers compose; a function's type
lists which effects it may invoke. Evolution:

- **extensible-effects** (Kiselyov, Ishii 2013):
  *Freer monads, more extensible effects.*
  <https://okmij.org/ftp/Haskell/extensible/more.pdf>
- **freer-simple** (Sandy Maguire et al., mid-2010s):
  Hackage <https://hackage.haskell.org/package/freer-simple>
- **polysemy** (Sandy Maguire, 2019):
  GitHub <https://github.com/polysemy-research/polysemy>;
  talk: <https://reasonablypolymorphic.com/blog/polysemy/>
- **fused-effects** (Rob Rix, 2019):
  GitHub <https://github.com/fused-effects/fused-effects>;
  paper: Wu & Schrijvers,
  *Fusion for Free: Efficient Algebraic Effect Handlers.* MPC 2015
  <http://www.cs.ox.ac.uk/people/nicolas.wu/papers/MPC15.pdf>
- **eff** (Alexis King, 2020):
  blog: <https://lexi-lambda.github.io/blog/2020/01/19/alexis-king-s-paper-on-algebraic-effects-in-haskell/>;
  GitHub <https://github.com/hasura/eff>

All of these let a function signature like
`(Member ReadBytes r, Member WriteRows r) => Sem r A`
literally enumerate the effect kinds the function uses.
Exact analogue of sprefa's `Op` associated type `type Effect o`.

### 4. Arrows and Applicative batching

McBride & Paterson, *Applicative programming with effects.* 2008.
<http://www.staff.city.ac.uk/~ross/papers/Applicative.pdf>

The typeclass distinction `Applicative` (parallel) vs `Monad`
(sequential) is the formal underpinning of "when does batching work?".
Hughes's *Generalising monads to arrows* (2000)
<https://www.cse.chalmers.se/~rjmh/Papers/arrows.pdf>
made static-dataflow-vs-dynamic-dataflow explicit in types.

### 5. Build Systems à la Carte (Mokhov, Mitchell, Peyton Jones 2018)

Formalizes why batching is free in applicative build systems
(Bazel, shake's applicative mode) and blocked in monadic ones
(make, shake's monadic mode). Directly applicable to sprefa's
"static deps batch, dynamic deps sequence" question.

Citation:
- Paper: <https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems.pdf>
- GitHub: <https://github.com/snowleopard/build>

### 6. Differential / Timely Dataflow (Abadi, McSherry et al. 2013–)

Same applicative-collapse insight applied to stream deltas with
explicit windowing. Batching emerges from the dataflow graph shape,
not from a monad.

Citations:
- Timely dataflow paper:
  *Naiad: a timely dataflow system.* SOSP 2013.
  <https://www.microsoft.com/en-us/research/wp-content/uploads/2013/11/naiad_sosp2013.pdf>
- Rust implementations:
  <https://github.com/TimelyDataflow/timely-dataflow>
  <https://github.com/TimelyDataflow/differential-dataflow>
- Used in production by Materialize:
  <https://materialize.com/>

### Hand-written (what ripgrep / rust-analyzer actually do)

Most production Rust CPU/IO-bound tools skip all effect frameworks
and hand-write `futures::stream` + `tokio::sync::Semaphore` +
`FuturesUnordered` + `tokio::sync::mpsc`. No batching abstraction;
batching is a manual chunk-iteration plus `buffer_unordered(N)`.

Examples:
- ripgrep parallel walker:
  <https://github.com/BurntSushi/ripgrep/blob/master/crates/ignore/src/walk.rs>
- rust-analyzer salsa + custom dispatch:
  <https://github.com/rust-lang/rust-analyzer>
- sled lock-free tree:
  <https://github.com/spacejam/sled>

## Frontend reference points (for analogies)

The JS ecosystem reified these patterns before Rust did. sprefa v3's
design is recognizably the Rust-port of these shapes:

| JS / web | concept | Rust equivalent |
|---|---|---|
| redux action | reified effect ADT | `trait EffectKind` + per-op struct |
| redux middleware | per-effect interpreter | `Batcher<E>` |
| redux-saga `put/take/call` | yield effect, receive response | `ctx.put<E>(e).await -> E::Response` |
| redux-saga tick | one round of the effect scheduler | batcher throttle window |
| RxJS `Observable` | stream of values | `futures::Stream` / `rxRust` Observable |
| RxJS `Subject` | fan-out channel | `tokio::sync::broadcast` |
| RxJS `BehaviorSubject` | cached-last + fan-out | `tokio::sync::watch` |
| RxJS `throttleTime` | window + leading/trailing | `tower::Buffer` / `tower-batch-control` window |
| RxJS `shareReplay(1)` | multicast last value | `watch::Receiver::borrow()` |
| Facebook DataLoader | per-key batch coalescing | Haxl `DataSource` / sprefa `Batcher<E>` |
| Apollo Link | stackable middleware per GraphQL op | `tower::ServiceBuilder` |

Citations:

## Reading order for grokking the design end-to-end

1. **Haxl paper** — 20 pages, the machine.
2. **Build Systems à la Carte** — formalizes the applicative/monadic
   batching split.
3. **tower's "Inventing the Service trait" blog post** — the exact
   Rust-idiom version of "effect = `fn(Req) -> Future<Resp>`".
4. **tower-batch-control source** — ~800 LoC, readable in an hour,
   implements the batcher policy concretely.
5. **salsa book** — for the demand-driven memoized side (LSP queries).
6. **redux-saga declarative effects docs** — for the mental model of
   "ops yield pure values, interpreter drives."
7. **Swierstra's *Data types à la carte*** — closes the loop by
   showing effects-as-ADTs is a 2008 idea.

## What Rust is missing vs Haskell

- **Effect row polymorphism in types.** Haskell's `Member` constraint
  in extensible-effects lets a function enumerate effects in its
  signature; Rust has no comparable syntax. Closest is associated
  types on `trait Op` or an `HList` of marker types (via `frunk`).
  The **keyword generics** initiative may close this gap; the `gen`
  RFC for Rust generators moves toward saga-style coroutines.
- **Free monad inference.** Haskell's GHC can infer the
  `Sem r A` type across a whole program; Rust needs explicit
  type annotations at every generic callsite.
- **GADTs for effect ADTs.** Rust's enums are regular ADTs, so the
  effect-kind-with-associated-response-type pattern (`EffectKind`
  with `type Response`) is the standard workaround.

None of these block the design; they make the syntax noisier.

## What Haskell is missing vs Rust for this workload

- **Mutable structure sharing** (`Arc<[Cursor]>` without copy).
  Haskell has `ByteString` but the idiomatic Haxl code copies more.
- **Zero-cost async**. Haskell's `IO` + green threads is great
  ergonomically; tokio's stack + `Pin` is the cost of "async fn"
  being monomorphized per call site.
- **Tree-sitter / ast-grep / git2 bindings**. The whole sprefa
  ecosystem is Rust-native; porting to Haskell loses that.

Net: the *design* is Haskell-2014; the *implementation substrate* is
Rust-2024. This is a pattern-transfer problem, not a language
problem.
