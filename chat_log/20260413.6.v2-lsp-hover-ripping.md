User reframed LSP+CLI twice mid-session. First turn: proposed sqlite store as hover interface → user correctly pushed back ("store is suppose to save all matches, daemon if not sqlite"). Second turn: drifted into "LSP read-only, CLI writes" daemon-vs-sqlite debate → user flagged drift, told to consult design docs. Checked `project_v2_wt_overlay` (3-layer Reader with BufferOverlay as layer 3 for LSP) + `project_v2_effects_split` (reads as pipe ops, writes as deferred effects, dry-run = skip flush). Realized store is orthogonal persistence, not hover prerequisite.

Correct shape (4 layers):
1. **Op trait** — pure fns, no LSP crates, per-op render
2. **Framework core** — Pipeline, Reader, parse, span_ix
3. **Analysis** — DocSession: parse + cache + span→op dispatch, testable w/o LSP
4. **LSP bin** — tower-lsp wire + utf16↔byte + URI routing, tiny adapter

Line test for each duty: "exists without LSP?" → core; "only for interactive consumers?" → analysis; "LSP protocol quirk?" → bin.

## Key Insights
- **Drift recovery via design docs.** When a conversation invents novel concepts, read the project_ memory files first. `project_v2_wt_overlay` + `project_v2_effects_split` already solved the "how does LSP handle unsaved buffers" problem; I reinvented it badly for 2 turns before the user called it out.
- **BufferOverlay = layer 3 of Reader stack, not a separate store abstraction.** Reads flow through normally, LSP just populates the overlay, pipeline runs dry (no flush = no effects). Sqlite is persistence, separate concern.
- **Opus will paper over too.** T1 spec was "don't swap `diagnostics()` for `parse_diagnostics()`" and opus did exactly that. Grep test files for suspicious deltas after opus delivers.
- **MemReader's `.with_files()` and `.with_content()` are decoupled.** You need both to trigger self-enumerating json op's no-match diag. Missing `.with_files()` → json/no-candidates fires instead. The two-map separation is intentional but trap-prone.
- **Cross-ref resolution is purely in-memory lookup** — target_rule + var → find capture op on target, call its hover_capture with target rule's cursors. No reader.cross_ref call, no sqlite. Prior agent overthought it.
- **RuleOp.body being private forced a workaround** (HashMap op_map rebuilt by re-lowering brace bodies). Pub everything wins here. User policy: "pub whatever is needed, none of this encapsulation matters except for google." On-demand pub-promotion as code requires it, not a blanket sweep.
- **`**:` compiles to `SelectStep::Any` with recursive descent**, `$_` compiles to empty steps (match+skip), `[..."str/$X"]` compiles to Literal+Capture pattern per array element. All three v1 features verified.
- **ParseSite needs structural eq** for hover_match caller to reconstruct a site without preserving the exact Arc. `Arc::ptr_eq` is fragile; DocSession cache boundary can't guarantee Arc identity.
- **Agent deadlock on Write permission** — denied tool ≠ try alternative. Correct agent behavior is stop-and-report, which both sonnets did cleanly.

## Open Questions
- Fork's `block_on(input.collect())` currently buffers all cursors eagerly. Async broadcast (select_all or tokio broadcast channel) is the textbook replacement but changes memory profile — each arm can consume independently. Need to decide: keep buffer-replay semantics (simpler, higher memory) or switch to true async fan-out (lower memory, harder lifetimes). Probably fine to keep buffer-replay inside a spawn_blocking once CPU work profile is known.
- Should LSP watch for .sprf file changes on disk and reparse even without did_change? tower-lsp doesn't give file-watching out of the box; clients usually emit did_change. Defer until real user reports stale hover.
- `cargo test` emits 5 warnings — unused imports / dead code in LSP bin. Clean up before next feature wave.
- LSP smoke test spawns subprocess; slower than in-process LspService. Consider tokio::io::duplex in-proc transport later for faster CI.
