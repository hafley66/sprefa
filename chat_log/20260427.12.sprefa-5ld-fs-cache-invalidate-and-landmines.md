## Problem/Context
**sprefa-5ld root cause** (took longer to find than expected):

`register_pure::<ReadBytesEffect, _>(...)` in `build_seed_ctx` wraps the reader in a `moka::future::Cache` (CacheLayer). DOMAIN="fs". The cache is keyed on `(repo, rev, path)`.

Pipe 1 reads HOOKS.md → cache stores v0 bytes → comment finds rtkq scope at byte_range 313..337 → write_cursor splices → file is now v1 (grew by 33B because rendered content is bigger than original).

Pipe 2 reads HOOKS.md → CACHE HIT returns v0 bytes → comment finds openapi scope at byte_range 414..438 (computed against v0) → write_cursor splices at offset 414 in v1 file → indexes wrong bytes → CORRUPTION.

Multi-seed makes it worse but isn't the trigger. Each seed builds a fresh ctx so cross-seed cache is clean; the corruption fires *within* a single seed across pipes.

## Solution/Approach
1. **`FsInvalidator` callback** (`Arc<dyn Fn() + Send + Sync>`) added to the `StageAndApprove` variants of both `WriteRangeSink` and `WriteFileSink`. Sink fires it after every Approved + Ok splice. Calls `ctx.invalidate_domain("fs")` which wipes both ReadBytes and FsListFiles caches in one pass (both DOMAIN="fs").

2. **Cycle break via `Weak<OnceLock<RtCtx>>`** in `run::build_seed_ctx`:
   - `Arc<OnceLock<RtCtx>>` cell is created.
   - Closure holds `Arc::downgrade(&cell)` (Weak), NOT a strong Arc. Strong forms a cycle (closure → cell → ctx → registry → sink → closure) and leaks the ctx every seed iteration.
   - Cell parked on `SeedRtCtx._invalidator_cell` so it lives as long as ctx.

3. **The `..` trap that nearly cost us**: the destructure at `run.rs:211` (`let SeedRtCtx { ctx, .., } = build_seed_ctx(...)`) silently dropped my `_invalidator_cell` field even though it was declared on the struct. Cell with no strong owner = `Weak.upgrade()` returns None = invalidation no-op = file corruption returns. Took an `eprintln!` debug trace inside the closure to catch this. The fix: explicitly bind `_invalidator_cell` in the destructure pattern, then `..` for the rest.

4. **Landmine markers**: 4 `// SPRF-LANDMINE <tag>:` comments at:
   - `effects.rs WriteFileSink::write` Approved+Ok branch (`invalidate-after-splice`)
   - `effects.rs WriteRangeSink::write` Approved+Ok branch (`invalidate-after-splice`)
   - `run.rs Arc::downgrade(&invalidator_cell)` (`weak-not-strong`)
   - `run.rs SeedRtCtx destructure binding` (`bind-not-discard`)

5. **`v3/LANDMINES.sprf`**: dogfood — `fs(glob(v3/crates/**/*.rs)) > comment("SPRF-LANDMINE") > lsp[warn](...)`. Found on a probe run: 4 unique landmines × 4 seeds = 16 hits.

## Key Insights
- **Two-layer cache architecture** in v3:
  1. `effect_runtime::CacheLayer` — wraps PureEffect via `register_pure`; keyed on `E::cache_key()`, invalidated by `ctx.invalidate_domain(E::DOMAIN)`. ReadBytesEffect + FsListFilesEffect both DOMAIN="fs".
  2. `pipeline::cache_key::OpCache` — caches op output cursor batches, keyed by content_hash + op_id. Lives as a Store on ctx. Phase F watcher invalidates via `evict_paths`. Different mechanism, different concerns.
- **Weak cycle break pattern**: when a sink/handler needs to call back into the ctx that owns it, hold `Weak<OnceLock<RtCtx>>` and pin the strong cell on a struct that lives parallel to the ctx. The cell-on-SeedRtCtx pattern is reusable for any future "sink talks back to ctx" plumbing.
- **`..` in destructure is a sharp tool**: silently discards fields. If you add a field whose lifetime matters, you MUST audit every destructure of the struct. The compiler doesn't help here. Worth a clippy-style lint.
- **moka `invalidate_all()` vs invalidate(key)**: `invalidate_domain` calls `cache.invalidate_all()` on every domain-tagged entry. moka 0.12 future Cache is documented eventually-consistent but the timestamp-gating semantics make subsequent gets miss reliably (unit test confirms).
- **Daemon CWD trap**: sprefa-server inherits its launching shell's cwd. If a global daemon (e.g. VS Code's --lsp-stdio one) is already running, sprefa-run reuses it and the write paths resolve relative to whatever cwd that daemon was spawned in — usually wrong. Workaround: `sprefa-server --http-unix <path> --no-tcp --info-path <path>` for an isolated daemon launched from the right cwd.
- **Agent worktree dispatch caveat**: `Agent({isolation: "worktree"})` cuts the worktree from the repo's default branch (here: `master`). If the user's active line lives on a non-default branch (here: `wip/kitchen-sink-react-hook-fix`), the worktree is stale and the agent hits a wall. Workaround: pre-cut the worktree manually (`git worktree add -b <agent-branch> <path> <base-branch>`) and tell the agent the absolute path.

## Open Questions
- Should `FsInvalidator` be exposed at a finer granularity (per-path) instead of full domain wipe? Today it pessimistically invalidates ALL fs entries on every splice. Optimization candidate later.
- Is the per-pipe invalidation correct under future Phase 1b (LSP code-action approval where splices are deferred async)? Current design ties invalidation to the sink's Approved+Ok branch, which is the actual splice moment regardless of when it happens. Should hold up.
- Phase F watcher invalidation already handles cross-process file changes via `OpCache::evict_paths`. Does my CacheLayer invalidation overlap or complement it cleanly? They target different caches (CacheLayer = effect cache; OpCache = cursor batch cache) so they're orthogonal.
