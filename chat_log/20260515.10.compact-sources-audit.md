## Phase 1: What IS CompactSourceGraph?

### One-sentence answer

`CompactSourceGraph` is a single-table SQLite sidecar that stores per-file AST subscription records (owner → source + continuation) using a compact binary cursor encoding, bypassing the full multi-table `RUNTIME_NODE`/`RUNTIME_EDGE`/`RUNTIME_CONTINUATION` schema that the generic `effect_runtime` path uses.

### The problem it solves

When an AST component scans a file corpus (say, 50k `.c` files), the generic `record_source_subscriptions` path writes **three rows per file** across three separate SQLite tables:

| Table | Purpose | Rows per file |
|---|---|---|
| `runtime_node` | owner node record | 1 |
| `runtime_node` | source node record | 1 |
| `runtime_edge` | subscribe edge | 1 |
| `runtime_continuation` | resume state (pipe_hash, input cursor, depth) | 1 |

Total: 4 rows, 4 table round-trips, scattered across 4 logical tables, each row holding a `Cursor` hex-encoded as a string.

The compact path collapses all of this into **one row** in one table (`runtime_source_subscription_compact`) with the continuation inlined. The input cursor is stored as a raw BLOB rather than hex text, with a custom fast path for the most common cursor shape (a plain filesystem path — `COMPACT_FS_CURSOR_MAGIC` prefix).

### What it stores

```
runtime_source_subscription_compact
  owner_id       TEXT PRIMARY KEY   -- blake3 hash of owner URI (u64 string)
  source_id      TEXT NOT NULL      -- blake3 hash of source URI (u64 string)
  pipe_hash      INTEGER NOT NULL
  instance_id    INTEGER NOT NULL
  depth          INTEGER NOT NULL
  input_cursor   BLOB NOT NULL      -- compact binary or COMPACT_FS_CURSOR_MAGIC path
  generation     INTEGER NOT NULL
INDEX ON source_id
```

One row per `(ast_uri, input_key, source_uri)` tuple. `owner_id` is the primary key, so re-recording the same owner simply replaces the row (`INSERT OR REPLACE`).

### Why it exists alongside RuntimeGraph

`RuntimeGraph` delegates almost all of its state to `effect_runtime`'s `FactRuntimeGraph` (events, jobs, edges, continuations). That generic path is correct but verbose: each subscription must materialize as multiple rows in normalized tables.

For file-watching, the subscription record is immutable after the first expand pass: the file path does not change, the pipe shape does not change. Writing it to the compact table once is a pure optimization — cheaper writes, cheaper lookups on wake dispatch.

The field is `Option<Arc<CompactSourceGraph>>`. When `None` (the default in `RuntimeGraph::new`), all subscriptions go through the full generic path. When `Some`, `record_source_subscriptions` short-circuits to the compact path.

### SQLite tables

| Table | Owner | Notes |
|---|---|---|
| `runtime_source_subscription_compact` | `CompactSourceGraph` | Compact path only |
| `runtime_node` | `effect_runtime` (generic) | Written by generic path |
| `runtime_edge` | `effect_runtime` (generic) | Written by generic path |
| `runtime_continuation` | `effect_runtime` (generic) | Written by generic path |
| `runtime_event` | `effect_runtime` (generic) | All paths |
| `runtime_job` | `effect_runtime` (generic) | All paths |

### The execution path it serves

```
File changes on disk
  -> AstNmComponent::dispatch (v2_ops.rs:691)
     builds Vec<SourceSubscriptionInput>
  -> RuntimeGraph::record_source_subscriptions (runtime_graph.rs:536)
     if compact_sources.is_some():
       CompactSourceGraph::record()     <-- compact path
     else:
       facts.insert_batch * 3 tables   <-- generic path

Later: file dirty signal arrives
  -> RuntimeGraph::dispatch_wake (runtime_graph.rs:789)
     incoming_subscribers() from generic edge scan
     + compact.owners_for_source()     <-- compact lookup by source_id index
     -> enqueue_jobs_for_unconsumed_events()

Job drain:
  -> GraphReplayRunner::drain (runtime_replay.rs:22)
     runtime_graph.owner_descriptor(owner_uri_id)
       tries facts table first
       falls back to compact.owner_descriptor()
     runtime_graph.continuation_for_owner(owner_uri_id)
       tries core first
       falls back to compact.continuation_for_owner()
```

### Why this hot path was peeled off

The generic `record_source_subscriptions` path (lines 548–648) does ~10 `intern_uri` calls per subscription, builds 3 `Cursor` structs, hex-encodes them, and issues 3 separate `insert_batch` calls. For a 50k-file corpus that is 150k table writes with string-encoded blobs.

The compact path: one `INSERT OR REPLACE` with a BLOB, inside a single transaction, with the owner URI hash computed via `StringId::of` (no global intern table hit). For the common FS-cursor shape it avoids even the full `cursor_codec::encode` call.

## Phase 2: Sprf Coupling

### Genuinely sprf-specific

| Site | File:Line | Sprf concept |
|---|---|---|
| `sprf://runtime/owner/{owner_id}` URI synthesis | runtime_graph.rs:1213, 1235 | sprf URI scheme hardcoded in two query callbacks |
| `StringId::of(owner_uri)` — derives ID without SprfStore | runtime_graph.rs:1156–1157 | `StringId` is sprf's specific `u64` hash type |
| `COMPACT_FS_CURSOR_MAGIC` / `is_plain_fs_cursor` | runtime_graph.rs:1079–1119 | Knows sprf's specific `FOCAL_TERM` (`"&"`) and `"FS"` term names |
| `cursor_codec::encode/decode` | runtime_graph.rs:1083, 1100 | sprf-specific cursor codec |
| `Cursor` struct with `value` / `terms` | runtime_graph.rs:1103–1118 | sprf Cursor type, not generic |

### Accidentally sprf-specific (could be generic)

| Site | File:Line | What it is | Why it's accidental |
|---|---|---|---|
| Single-table schema layout | runtime_graph.rs:1125–1136 | One row per subscription, source_id indexed | Nothing about this requires sprf; any `(owner_id, source_id, blob)` schema could live in core |
| `owners_for_source` lookup | runtime_graph.rs:1199–1220 | Index scan by source_id | Pure relational; only depends on string IDs |
| `INSERT OR REPLACE` batch in transaction | runtime_graph.rs:1144–1192 | Transactional upsert loop | Same pattern would work for any ID type |
| `WriteStats` instrumentation | runtime_graph.rs:1140 | Telemetry counter | sprf telemetry type, but trivially extractable |

### The URI reconstruction bug (line 1213, 1235)

Both `owners_for_source` and `owner_descriptor` reconstruct the owner URI as:
```rust
format!("sprf://runtime/owner/{owner_id}")
```
This is wrong. The canonical URI for owners is produced by `runtime_uri("owner", &[...])` (line 1338), which hashes multiple parts into a `blake3` hex suffix. The compact path short-circuits the full intern table and synthesizes a fake URI from just the stored numeric ID. This means:
- `OwnerDescriptor::ast_uri` is always `Arc::from("")` in the compact path (line 1241)
- `OwnerDescriptor::input_key` is always `Arc::from("")` in the compact path (line 1242)
- `GraphReplayRunner::drain` uses `owner.ast_uri` to discriminate SQL vs continuation owners (runtime_replay.rs:44); a compact-path owner always falls through to the `continuation_for_owner` branch, which does work correctly

The URI synthesis is a known lossy simplification. The compact table deliberately discards the full URI in favor of the numeric hash. This is load-bearing for the replay path: it relies on `continuation_for_owner` succeeding, not on `ast_uri` being populated.

## Phase 3: Three Options

### Option A: Promote to `effect_runtime` as `CompactSourceCache<I: Id>`

Generic over ID type: `I: AsRef<str> + Hash + Eq`. v4 plugs in `StringId`; the cursor-specific encoding becomes a caller-supplied `fn encode(input: &T) -> Vec<u8>`.

**LOC delta:**
- Remove: ~209 LOC from `runtime_graph.rs`
- Add to `effect_runtime`: ~180 LOC (generic struct, schema, `encode` callback param)
- Net: -29 LOC in v4, +180 in effect_runtime crate

**What gets harder:**
- The `COMPACT_FS_CURSOR_MAGIC` fast path is cursor-specific. It would need to be a caller-supplied hint or dropped, adding ~40 bytes per FS subscription row.
- `is_plain_fs_cursor` knows `FOCAL_TERM = "&"` and `"FS"`. No way to genericize without a callback.

**Bench impact:** Neutral to small regression on FS-cursor write path (losing the magic fast path unless caller supplies an encoder). Read path (lookup by source_id) is unaffected.

**Test surface:** Compact-path smoke test moves to effect_runtime. The `record_source_subscriptions` path in `RuntimeGraph` becomes a thin wrapper.

---

### Option B: Keep sprf-side, trim the URI reconstruction

Narrow the scope: fix the fake URI synthesis bug, document the intentional omissions, add a comment explaining why this is not generic infrastructure.

**Specific trims:**
- Replace the two `format!("sprf://runtime/owner/{owner_id}")` occurrences with a lookup through `SprfStore` (the store is already on `RuntimeGraph`; `CompactSourceGraph` would need a reference or a callback)
- Or accept the current lossy behavior and document it explicitly

**LOC delta:** +0 to +15 LOC (adding a comment block and possibly fixing the URI)

**Bench impact:** None.

**Test surface:** Add one test asserting that `owner_descriptor` from the compact path returns a non-empty `ast_uri`. Currently no such assertion exists.

---

### Option C: Delete

Remove `CompactSourceGraph` entirely. The generic `record_source_subscriptions` path (lines 548–648) already exists and is correct.

**LOC delta:** -209 LOC from `runtime_graph.rs`, -1 test in `runtime_graph_smoke.rs` (`compact_source_graph_exposes_write_stats_snapshot`). Remove both `new_with_compact_sources` constructor calls in `app.rs`.

**Bench impact:** Unknown without numbers. The compact path is the only path enabled in production (`new_with_sqlite_facts` and `new_with_sqlite_backends` in app.rs both call `new_with_compact_sources`). Deleting it means production runs on the generic path, which writes 4x as many rows per file subscription and uses hex-encoded strings instead of BLOBs.

For a 50k-file run: approximately 200k additional row writes per pass, string blobs instead of compact binary. On the Linux kernel repo (bench target), this could be significant; no benchmark currently compares the two paths head-to-head.

**Test surface:** One test removed. The smoke test for the feature would disappear along with the feature.

---

### Option D: Keep as-is

Accept the sprf-side specialization. Add a comment block explaining why `CompactSourceGraph` is not promoted: the FS-cursor fast path is cursor-specific, the feature is optional (opt-in via constructor), and the two fake URIs in `owners_for_source`/`owner_descriptor` are load-bearing-by-accident (replay works because `continuation_for_owner` succeeds).

**LOC delta:** 0

**Bench impact:** None.

**Test surface:** None. The existing smoke test covers the write-stats path but not the replay correctness.

---

### Measuring "is it carrying its weight"

No benchmark currently isolates compact vs generic path. The relevant bench files are:

```
v4/bench/linux-join.sprf
v4/bench/linux-tiny-where-mid.sprf
v4/bench/linux.sprf
v4/bench/linux-tiny-join.sprf
v4/bench/linux-antijoin.sprf
```

These are query description files, not Criterion harnesses. There is no `benches/` directory under `v4/` with a Rust bench that toggles `new_with_compact_sources` vs `new`. To measure: add a Criterion bench that constructs both graph variants, calls `record_source_subscriptions` on 10k FS-cursor subscriptions, and measures wall time. The compact path's write-stats are already instrumented (`WriteStats`) so the ratio would be immediately visible from telemetry in a production run.

From the code alone: the compact path eliminates 3 of 4 `insert_batch` calls and replaces hex-string cursor encoding with a 18-byte magic prefix + raw UTF-8 path. For N file subscriptions the generic path does O(4N) table inserts; the compact path does O(N) inside a single transaction. The benefit scales linearly with corpus size.

## Phase 4: End-Goal Anchor

**The end goal is a general programmable shell.**

Hot-path responsiveness matters directly: when a file changes, the shell must wake the affected rules and rerun them with minimal latency. The subscription lookup (`owners_for_source`) and continuation retrieval (`continuation_for_owner`) are on the critical wake-dispatch path.

The tension: the dedupe merge moved generic mechanics into `effect_runtime`. `CompactSourceGraph` is a sprf-side optimization that bypasses those generic mechanics entirely for the most common subscription type. This fights the "effect_runtime as generic substrate" trajectory.

However, the alternative (Option A) genericizes a type whose main value is a cursor-format fast path. That fast path (`COMPACT_FS_CURSOR_MAGIC`) is intrinsically tied to sprf's cursor wire format. Abstracting it would either drop the fast path or require a caller-supplied encoder closure, making the generic type harder to justify.

The URI reconstruction bug (fake `ast_uri = ""`) is the more concrete problem. It means `owner_descriptor` is unreliable for compact-path owners, and any caller that reads `ast_uri` gets an empty string. Currently `runtime_replay` handles this gracefully only by accident. A future caller of `owner_descriptor` could be silently broken.

---

## Recommendation

**Option B (trim) now, Option A (promote) when the cursor codec stabilizes.**

**Immediate (Option B):**
1. Fix the fake URI construction bug in `owners_for_source` and `owner_descriptor` — pass `SprfStore` into `CompactSourceGraph` or compute the URI correctly from the stored fields
2. Add a doc comment on `CompactSourceGraph` that names: (a) what it is, (b) why it is not generic infrastructure, (c) the known lossy omissions in `owner_descriptor`
3. Add one smoke test asserting `continuation_for_owner` round-trips through the compact path on a FS-cursor input

**LOC delta for Option B:** +15 to +30 LOC (doc comment + URI fix + test)

**Later (Option A):**
Once the cursor codec is stable and `effect_runtime` has a clear `InputEncoding` trait surface, move the table schema and lookup logic into a `CompactSubscriptionCache<I, E>` in effect_runtime, keeping the FS-cursor fast path as a sprf-supplied encoder. This aligns with the dedupe trajectory without forcing the abstraction prematurely.

**Is it blocking further dedupe progress?**
No. `CompactSourceGraph` is purely additive — it lives inside `RuntimeGraph` behind an `Option`, uses a separate SQLite table, and does not interfere with the generic path. It does not need to be resolved to continue migrating other mechanics into `effect_runtime`.

**Is it actually carrying its weight?**
Almost certainly yes for large file corpora, but not benchmarked. The 4x write reduction and BLOB vs hex-string encoding are real savings. The instrumentation (`WriteStats`) is in place to confirm with a single production run on the Linux bench. The risk is that the write savings are invisible if the bottleneck is elsewhere (parse time, SQL evaluation). Add the Criterion bench before committing to Option A.
