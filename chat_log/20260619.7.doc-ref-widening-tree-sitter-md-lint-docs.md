## Solution/Approach
### P2.1 doc_ref widening
- `engine.rs:231` — `doc_rel_decls` widens doc_ref from 3 to 5 cols (adds `kind`, `matched_name`). Comment in decl explains: kind = doc_node kind that produced the row (heading/code_block); matched_name = doc-side string that matched.
- `engine.rs:2728` — Bridge rewritten in Rust (was SQL `INSERT OR IGNORE INTO ... JOIN`). Loads `type_entity(sym, name)` into a `HashMap<lowercase_name, Vec<(sym, original_name)>>`. Iterates the in-memory `facts: Vec<(path, DocFacts)>` (already produced by the doc_node pass above). Three match paths per DocNode:
  - heading: try exact `name.to_ascii_lowercase()` lookup; on miss, try `normalize_doc_name(name)`.
  - code_block: tokenize `n.text` via `identifiers_in`, look each token up.
  - other kinds: ignored (forward-compatible with future IngestLang kinds).
- `engine.rs:~3700` — Two new free functions:
  - `normalize_doc_name(s)` — strips at most one leading token (article OR kind word) and at most one trailing kind word, lowercases. Constants `ARTICLES = [the, a, an]` and `KIND = [struct, enum, trait, class, interface, const, module, mod, type, item, macro, function, fn, method, alias, def]`. Examples: "The Engine struct" -> "engine"; "fn do_thing" -> "do_thing"; "Items" -> "items".
  - `identifiers_in(s)` — byte-scan for `[A-Za-z_][A-Za-z0-9_]*` tokens. Used to scan code-block body for type mentions.
- `ingest/mod.rs` — `DocNode` gains `text: String` field (only populated for code_block). `MarkdownDoc::extract_docs` accumulates fence-body lines into `block_body: Vec<String>` and flushes to `node.text` at the closing fence.
- `tests/doc_ref.rs` — 3 existing tests updated to new arity. +2 new tests: `doc_ref_normalizes_heading_articles_and_kind_words` and `doc_ref_bridges_code_block_mentions`.

### P1.1 tree-sitter-md port
- `Cargo.toml` — `tree-sitter-md = "0.5"` added with comment naming MDeiml/tree-sitter-grammars as the source.
- `ingest/mod.rs` — `MarkdownDoc::extract_docs` rewritten. Uses `tree_sitter_md::LANGUAGE` (block grammar only; inline grammar not needed for headings/code blocks). DFS via a LIFO `to_visit: Vec<Node>` stack (children pushed in reverse for source-order visit). Cases:
  - `atx_heading` / `setext_heading` -> heading node (level from `atx_hN_marker` / `setext_hN_underline` child; title from `inline` child for ATX, `paragraph` child for setext — discovered when setext test initially returned empty titles).
  - `fenced_code_block` -> code_block node (lang from `info_string`'s `language` child; body from `code_fence_content`).
  - `indented_code_block` -> code_block node (no language).
  - All other kinds descend so headings/code blocks nested in `block_quote` / `section` / `paragraph` still extract.
- Heading-stack parent-tracking algorithm preserved unchanged (pop entries with level >= current before push).
- Helpers: `heading_text(n, src)`, `fenced_code_block_parts(n, src)`, `text_of(n, src)` (byte-range slice, avoids tree-sitter's `Cow<[u8]>` round-trip).
- +3 ingest tests: setext headings, indented code blocks, nested headings inside blockquotes.
- Lifetime lesson: tree-sitter's `Node::children(&mut cursor)` returns an iterator borrowing the cursor; can't `.find()` or `.collect()` directly inside the same binding scope. Pattern: `let children: Vec<Node> = n.children(&mut cursor).collect();` then iterate the Vec.

### lint-docs.dl (the pivot)
User's three clarifier answers (via question tool):
1. "new" = line-level via `changed_line(path, line)` (tightest signal).
2. refs = `call_site` callers + `type_link` srcs (no doc_ref; would be circular).
3. output = `should_document(sym)`.

Then user pivoted: "like as a warning 'please document this large and important component' and also a line limit to comments lmfao, depending on the sum of its input types". So two rules:
- **needs-doc**: type_entity on changed_line + total_refs > 2 + no doc_ref -> `diag(..., "warn", "needs-doc", "${s} is new and has ${n} refs but no doc...")`.
- **chat-comment**: function's /// block above def_line > `2*arity + 2` -> `diag(..., "warn", "chat-comment", "${s}: ${actual} /// lines for ${ar} inputs...")`.

Three bugs found and fixed while writing the rule:
1. Windowed count over-counted when an earlier fn's /// block fell in the window. Fixed via `block_top = max(non_doc.line)` per def.
2. `///` regex used `.+` so a bare `///` paragraph-break line didn't match, splitting every multi-paragraph block. Fixed via `.*`.
3. `type_link.dst` mixes bare names and file-prefixed syms; `call_refs` keys on file-prefixed syms; the naive inner-join `total_refs` produced 0 rows. Fixed by (a) two `type_refs` clauses covering both `dst` forms, and (b) switching `total_refs` to `sum(n)` over a union (functions usually only have call_refs, types usually only have type_refs).

Other dl lessons learned:
- Arithmetic is allowed in heads only (`budget(s, ar * 2 + 2) <- fn_arity(s, ar).`); body atoms are binding-only (`dl - 1` in a body is a parse error). For "prev line" patterns, derive a relation with the arithmetic in its head.
- `${var}` (with dollar) is the diag template syntax. `{var}` (no dollar) is the gen template syntax. Mixing them silently produces unrendered literals.
- `count(x)` aggregates per group; `sum(n)` over a union aggregates across clauses. Use sum when combining heterogeneous signals.
- Aggregates supported: count, min, max, sum.

## Key Insights
- doc_ref's Rust-side bridge architecture is the right call. SQL JOIN was rigid (exact match only); Rust lets `normalize_doc_name` and `identifiers_in` coexist cleanly. Adding fuzzy / scope-aware / SCIP-resolved matching later drops in as new branches in `refresh_doc_rels`.
- The `DocNode.text` field is the seam between extract-time and bridge-time. doc_node (the relation) doesn't carry text (would bloat the db); the bridge consults text in-memory via the DocFacts Vec before the relation is even written.
- tree-sitter-md's two-parser split (block + inline) is overkill for our needs. Block grammar alone covers ATX + setext headings, fenced + indented code blocks. Inline grammar would add link/inline-code/emphasis nodes; not needed for doc_node today, available when wanted.
- tree-sitter node-types.json is the canonical reference for the parse tree. `cargo info` + `python3 -c "import json"` over `node-types.json` is faster than reading parser source.
- Setext vs. ATX headings differ in heading_content field shape: ATX has `inline`, setext has `paragraph`. Same kind label, different child types. The `heading_text` helper handles both via `c.kind() == "inline" || c.kind() == "paragraph"`.
- v5 dl has TWO template syntaxes: `${var}` for diag msg interpolation, `{var}` for gen template strings. Easy to confuse; lint-unwrap.dl uses `${X}`, gen-doc-index.dl uses `{title}`.
- v5 dl arithmetic: HEAD expressions only (`r(p, line + 1) <- ...` is fine). Body atom positions are binding-only. Body comparison (`n > 2`, `l < dl`) is fine on both sides. Confirmed via tests/arith.rs.
- For "refs per sym" across heterogeneous signals (callers via call_name, type mentions via type_link), `sum(n)` over a union of per-signal counts beats an inner join on `s` — the inner join drops syms that have only one signal type (which is almost all of them, since functions have callers and types have type refs but rarely both).
- The contiguous-block-detection trick (`block_top = max(non_doc.line) below def_line`) avoids the O(defs × doc_lines × non_doc_lines) cross-product that a naive `!non_doc_between(...)` would materialize. First attempt timed out at 90s on engine.rs; the max formulation runs in ~6s on the whole v5 codebase.
- DocNode kinds are forward-compatible: the bridge match arm has an `_ => {}` default so adding `list` / `paragraph` / `pipe_table` kinds later is mechanical (the tree-sitter walk already sees those nodes; just add cases to the match in ingest/mod.rs:97).

## Open Questions
- Functional needs-doc: should we add a function-level "documented" signal so needs-doc fires for new heavily-referenced functions, not just types? The chat-comment rule already detects /// presence; could reuse `fn_doc_count > 0` as the documented predicate.
- chat-comment budget: is `2*arity + 2` the right curve, or should it be `arity + N` (linear, base-only) or `arity * K` (multiplicative)? v5's doc-heavy style may not be the target; AI-generated codebases might warrant a stricter curve.
- chat-comment scope creep: today it counts `///` blocks above `call_def` (functions). Should it also count `//!` module docs above `mod` declarations, or doc comments above `struct`/`enum`/`trait` (which live in `type_entity` not `call_def`)? Would need a unified "definition with optional doc block" relation.
- Should `lint-docs.dl` move to `examples/lints/` alongside `rust.dl` and `ts.dl`, or stay in `examples/` next to `lint-unwrap.dl` and `lint-imports.dl`? The latter two are top-level so lint-docs matches.
- Next direction: P3 per-lang symbol literals, the IngestLang/TypeLang fold (now that both are tree-sitter-shaped), or another example? User hasn't picked.
