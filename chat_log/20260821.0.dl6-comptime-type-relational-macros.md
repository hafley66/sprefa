# Session: dl6-comptime-type-relational-macros

## Goal
Unify DL6 generics, compile-time type computation, type reflection, and eventual rule metaprogramming around one relational term model. Generic parameters should become ordinary ordered arguments whose `: type` role places them in type space, while later arguments may depend on earlier type-valued arguments.

## Problem/Context
The desired language model resembles Lisp/Scheme structural symmetry plus Zig compile-time parameters:
- One term tree.
- Left side of `:` indexes value/member space.
- Right side indexes type/application space.
- Earlier ordered arguments may bind type values used by later argument types.
- A relation returning `type` is a compile-time type function.
- Compiler rules and runtime rules should eventually share a canonical relational representation, enabling controlled relational macros rather than a separate AST macro language.

Desired surface direction:

```dl6
rel Box(
  T: type,
  value: T
).

rel Pair(
  Left: type,
  Right: type,
  left: Left,
  right: Right,
  cousin: cousin_type(Left, Right)
).
```

Current generic surface remains special:

```dl6
rel Box(T)(value: T).
```

Current expansion scans type expressions for ground applications, recursively discovers nested applications to a fixpoint, substitutes template parameters, mints hashed concrete relation declarations, rewrites references, and lowers only concrete runtime columns.

## Solution/Approach
Use a dependent ordered parameter list, a telescope:
1. Parse all declaration arguments into the same structural term representation.
2. Infer compilation phase from argument type:
   - `T: type` is a compile-time binding.
   - `value: T` is runtime data using that binding.
   - An expression returning `type` evaluates during compilation.
3. Keep semantic identity as `application(ConstructorId, ArgumentTypeIds)`.
4. Omit compile-time arguments from runtime rows.
5. Allocate concrete physical storage only after type computation closes.
6. Preserve authored relation names while physical schemas use internal application identity.
7. For future re-rule-able rules, expose canonical compiler rows for rules, evaluate transformations to a stable structural fixpoint, validate safety/stratification, then reconstruct existing Prolog rule terms for lowering.

Retain both authored forms through one internal representation:

```dl6
rel Box(T)(value: T).
rel Box(T: type, value: T).
```

The existing first form explicitly curries the compile-time parameter group.
It normalizes to the second form plus a curry boundary before expansion. The
second form allows compile-time and runtime arguments in one ordered list.
Phase inference may automatically curry the maximal compile-time prefix, while
the explicit generic group preserves current behavior and removes inference
ambiguity. Both forms produce the same semantic application identity.

## Key Insights
- Prolog already provides code-as-data internally. DL6 needs a controlled userland projection, not a new host representation.
- Current inline specialization is schema-driven. It discovers ground generic applications only in type expressions, then mints ordinary concrete declarations.
- Repeated identical generic applications deduplicate to one semantic application and one concrete derivation.
- Nested named applications work: `Box(Pair(int,text))`, `Envelope(Pair(int,text))`, generic enums containing generic relations, and `Outer(T)(inner:Inner(T))`.
- Guarded recursive specialization works when the relation retains stored identity: `Chain(T)(value:T,next:option(Chain(T)))`.
- Unguarded mutual product recursion produces the named `type_cycle` refusal.
- Ordinary mixed arguments are the main missing seam: `rel Box(T:type,value:T)` produces `compiler_relation_mixed_domain`.
- Existing generic syntax already supplies an explicit compile-time curry boundary. It can coexist with the unified argument list by normalizing both surfaces before semantic type expansion.
- Automatic currying should operate on the compile-time prefix rather than create a second specialization mechanism.
- `Box(first(int))` fails because generic discovery precedes type-relation evaluation.
- Compiler facts cannot currently carry or return generic application values such as `Box(int)`.
- Higher-kinded constructor variables do not parse.
- `list(type)` and `Box(type)` cannot enter runtime storage, which matches the need to erase compile-time arguments before lowering.
- The relational macro concept is a later layer: canonical rule rows plus stable structural identity and a bounded fixpoint.

## Open Questions
- Should a relation with any `: type` arguments automatically be staged, or should staging be inferred only when all uses are compile-time-ground?
- Does automatic currying stop at the first runtime argument, or may later compile-time arguments be lifted across runtime arguments through an explicit curry group?
- Should type-valued arguments be inferable from later runtime argument types, comparable to Zig `anytype` or TypeScript inference?
- Should physical tables be allocated per semantic application or per lowered storage signature?
- Should higher-kinded constructor parameters be first-class `type -> type` values?
- How should recursive all-optional relations receive identity without SQL NULL or companion-column disappearance?
- At what phase may compile-time relations generate declarations, facts, and eventually rules without unbounded self-generation?
