## Problem/Context
Original v1 had hardcoded `ProvKind { Repo, Rev, Fs }` threaded through parser, walker, and ops. Adding any new op-owned sigil required central edits across multiple files — violates the "op owns everything" principle. Phase 0 removed that coupling so ops own their own sigils and the core grammar is op-name-agnostic. Renaming `.norm` dot-suffix to `_norm` sibling-sigil form was folded into the same cutover because sigils are now just identifiers.

User reframed naming mid-session: dropped `provenance` (too many syllables, overloaded from v1), rejected `projection` (too abstract), rejected `source/origin/stamp` (too generic). Landed on `ScanPointer` because it emphasizes the forward use: each sigil *points* the demand scanner at something worth scanning (repo, rev, fs path, or any future op-declared resource). "on demand scanning pointers for the runner."

## Solution/Approach
Phase 0 delivered in 11 sequential tasks through `chat_log/20260414.6.phase0-grammar-dispatch-plan.md`. The plan doc itself got renamed from `provenance`/`projection` terminology to `scan_pointer`/`ScanPointer` as the session progressed.

**Scan-pointer runtime (next)** will follow the forward-pass stamping model. Captures stream through the pipeline carrying a `scan_sigil: Option<Arc<str>>` and `verified: Tri` slot. Command-side ops (repo/rev/fs bind modes) stamp at the bind site with `verified=Verified`. Content-side ops (walker-embedded `$$sigil($VAR)` inside json/etc.) stamp with `verified=Claimed`; a later pass cross-checks against the known scan set and flips to `Verified` or `Missing`. `Missing` emits `scan-pointer/unverified` Warn but does NOT drop the row — streaming invariant means the scan set grows over time, so drop-on-miss would be wrong.

## Key Insights
- **Never say "provenance" again.** Dead term. Use `scan_pointer` / `ScanPointer` / `ScanPointerRef` / `scan_sigil` / `scan-pointer/*` diag codes.
- **Scan pointer = type assumption during forward-pass capture.** Not a post-hoc verification concept. Stamping happens as values stream through; verification is a separate upgrade step.
- **Tri-state `verified` is required for streaming soundness.** Can't filter on miss during forward pass because the scan set is still growing. Record the claim, flag the uncertainty, keep the row.
- **The store is the thesis.** User's real goal: a customizable rule-set of import/export relationships across repos; runtime sics the whole crate tree on the fleet and records sigil'd pointers across repo boundaries. The graph of sigil'd captures IS the output. Mermaid/dot/SQL are projections over the store, composed in the DSL via `render` + `sh`. Do NOT treat visualization as a first-class feature.
- **Column widening preview.** `$X` with `scan_sigil="repo"` → `X_str`, `X_repo_id` (FK to `repos` dim table), `X_verified`. No sigil → plain `X_str`.
- **Open tension** (unresolved): full generality requires a registry of "what scan sets exist to verify against." Today `Config.repos`/`revs`/`fs_exclude` are hardcoded names, not sigil-indexed. The open question is whether to sigil-index them or let ops declare their own "known-set" accessor. User acknowledged this tension without forcing resolution.
- **User preference echoed this session**: ScanPointer naming won over projection/source/provenance because it implies the forward-use ("pointer for the scanner"). When the user rejects a name, propose concrete alternatives with 2-3 syllables max and a framing sentence. Avoid abstract mathematical terms (projection, morphism).
- **OpCtx breakage pattern**: when the framework struct grows fields, integration tests with hand-rolled `OpCtx { ... }` literals break. Either use `OpCtx::fresh_xref_state()` helper or add a `OpCtx::for_tests(...)` constructor. Currently the helper exists; tests just needed to call it.

## Open Questions
- Should `Tri` live on `Capture` or on `ResultStore` row? Capture makes streaming stamping trivial but inflates every cursor. A side-table keyed by `(RunId, OpId, capture_name)` is denser but requires lookup. Lean toward Capture for Phase 1 simplicity.
- How does the assumption checker get the "known scan set"? Options: (a) read `Config.repos`/`revs` directly and match by sigil string; (b) introduce a `ScanRegistry` that ops populate with known-values keyed by sigil; (c) defer entirely and ship Phase 1 with no verification, all captures stay `Claimed`. User didn't pick.
- Do content-side captures that extract into a sigil already owned by a command-side ancestor (e.g., inner `$$repo($R)` under outer `repo($ROOT)`) get any special treatment? Might shortcut verification via parent cursor's verified repo. Deferred.
- `ScanPointer.read` fn on the trait — is this still needed once stamping is forward-pass? The `read` shape is used by the Phase 0 integration test's `FooFactory` but no runtime code calls it yet. Might be vestigial; revisit before Phase 1 lands.
