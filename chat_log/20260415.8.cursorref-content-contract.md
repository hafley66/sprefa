# Session: cursorref content-contract + hover gap

## Goal
Make the `&.$X` rebase mechanic actually work end-to-end. The cursor_ref
op landed in session .7 but the post-rebase cursor was being IGNORED by
downstream ops because json read its bytes via `reader.bytes(c.fs)`
instead of from `cursor.content`. This session unfucks the contract,
adds the chained-json test, and surfaces the hover-knowledge gap.

## What landed (uncommitted)

1. **Walker `CaptureAny` step** (`walk/_1_compiled.rs`, `_2_compile.rs`,
   `_3_walker.rs`, `_4_brace_parse.rs`):
   - Bare `$VAR` in json pattern value position emits `CaptureAny`
     instead of `Leaf`.
   - `Leaf` only matches scalar nodes (`as_scalar_text() → Some`), so
     `$OBJ` with an object value silently dropped to zero captures.
     `CaptureAny` matches any node kind and captures the byte range.
   - Cross-refs `${rule.$VAR}` keep `Leaf` — they need constraint-
     matching against pre-seeded scalar values.
   - `is_row_field` extended to include `CaptureAny` so multi-key
     captures like `{a:$A, b:$B, c:$C}` merge into one row instead of
     emitting three.

2. **json content-stamping** (`ops/_5_json.rs` fresh-parse path):
   - Output cursors now carry `c2.content = Some(content_arc.clone())`.
     Without this, downstream `&.$STR` rebase had nothing to slice.

3. **json content-priority dispatch** (`ops/_5_json.rs` candidate
   builder): the actual contract fix.

   Before:
   ```
   Path A: c.fs Some && JSON_TREE slot Some → walk pre-parsed tree
   Path B: read reader.bytes(c.fs) → parse → walk
   ```
   Path B ignored `c.content` entirely. After `&.$STR` set content to
   the unescaped inner JSON, Path B re-fetched the OUTER file. Wrong.

   After:
   ```
   Path A: c.fs Some && JSON_TREE slot Some → walk pre-parsed tree
   Path B: c.content Some → parse content[byte_range or all]
   Path C: c.content None → reader.bytes() fallback
   ```
   Source-of-truth contract: `cursor.content` (sliced by `byte_range`)
   is authoritative when set. Reader is only how content first gets
   populated. The chat log .7 framing already promised this:
   > "Ops are zero-change. They always read from cursor.content +
   >  cursor.byte_range + slots; the CursorRefOp rewrites those
   >  upstream of them."
   This commit makes json honor that contract. Same fix will be needed
   in every future op that reads bytes (ast-grep, md, line).

4. **Extension fallback** in the json candidate loop: when fp has no
   recognized json/yaml/toml ext (e.g. synthesized `<rebased>` path
   from the content branch), default to `"json"` so parse_by_ext can
   still pick a parser.

5. **cursor_ref test #1 extended** (`tests/cursor_ref.rs`):
   - Now tests both halves: rebase shape AND chained downstream json
     consumption.
   - Source: `json({pkg:$PKG}) > &.$PKG > json({version:$V})` —
     asserts `V="1.2.3"` AND that the chained-json output re-publishes
     JSON_TREE for further chaining.
   - This is what the plan doc (project_cursor_ref_plan.md line 52)
     called for in the first place; the landed test was truncated.

## Hover-knowledge gap (raised, NOT addressed)

cursor_ref has zero hover overrides. Hovering on `&.$X`:
- `&` → trait default returns string `"cursor_ref"`. Useless.
- `$NAME` segment → no delegation to the producing op's hover_capture.
- `.fs`/`.repo`/`.rev` → no hover_match on the field segments.

User explicitly DECLINED a `hover_self` markdown blurb (correctly —
it's noise). Wants the real piece:

**Capture-token delegation.** When hovering on `$NAME` inside `&.$NAME`,
the LSP should look up which upstream op bound NAME and call THAT op's
`hover_capture(NAME, cursors)`. So hovering on `$PKG` in `&.$PKG`
should show what json's hover_capture renders — the same way hovering
on `$PKG` inside `json({pkg:$PKG})` does.

This is a DocSession dispatcher change, not a cursor_ref method. Need
to read `analysis/` for how existing capture-token hover finds the
binding op.

**Field-segment hover.** `.fs`/`.repo`/`.rev` segments in the path
should each show what value the cursor field resolves to (per cursor,
grouped). Probably wants hover_match plumbed through cursor_ref op
with PathSeg-level spans registered separately from the OpInvocation
parse_site.

## Key Insights

- **The cursor_ref op was useless without the json contract fix.**
  The four landed integration tests passed by inspecting cursor SHAPE
  (content/byte_range/slots/captures) but never fed the rebased cursor
  through a downstream op. End-to-end the chain silently re-parsed the
  outer file. Chat log .7 explicitly promised the contract; landing
  cursor_ref without enforcing it shipped a half-feature.

- **`byte_range` is the active parseable subrange of `content`.** Not
  the file. Not some abstract span. Just `content[byte_range or all]`.
  Both rebase modes (SpanBacked, Synthesized) collapse to this one
  rule:
  ```
  SpanBacked   content unchanged, byte_range = sub-object span
  Synthesized  content = new bytes, byte_range = None
  ```
  Downstream op semantics: `parse(content[byte_range.unwrap_or(..)])`.

- **`Leaf` step in the walker requires a scalar.** `$OBJ` in a json
  pattern fell off a cliff — walker silently emitted zero captures
  for object values. `CaptureAny` is the additive fix; `Leaf` keeps
  its narrower role (cross-ref constraint matching, leaf-pattern
  promotion).

- **Hover delegation is the missing LSP piece.** cursor_ref's surface
  syntax (`&.$X`) is composed of segments that already have hover
  semantics elsewhere — `$X` is a capture token (hover_capture on the
  binding op), `.fs`/`.repo`/`.rev` are cursor fields (hover_match
  on the field). The cursor_ref op shouldn't reinvent these; the LSP
  should dispatch each segment to its existing handler. Adding a
  `hover_self` markdown blurb on cursor_ref would be noise.
