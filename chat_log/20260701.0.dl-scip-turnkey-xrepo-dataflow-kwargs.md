## Open design threads (user, rapid-fire this session)

### 1. kwargs should be a LANGUAGE-LEVEL thing, not per-op
Correct — today it is NOT. Named/`_`-elided args exist only as OUTPUT-slot sugar
on four source ops (`match`/`ast_yaml`/`sg`/`comment`) via `parse_kwarg_terms` +
`assign_outputs(field_names, pos, named)` (parse.rs:788/817). That machinery
already: fills positional, fills named, defaults unassigned to `Wild`, and makes
an unknown name a PARSE ERROR (the exact typo guard the `diag`-column papercut
wants). What it is NOT: uniform across every call form. `scan` is hard-positional
(papercut #1: `scan(...,p,_)` is even rejected). Rule heads and relation atoms are
positional. So "counting `_`" persists wherever `assign_outputs` isn't wired.

The language-level version is the already-DECIDED cons/calling-unification design
(auto-memory `project_cons_calling_unification`, Route A: list+kwarg = one Cons
cell, total-ordered; `project_callable_value` is the precondition, merged). Making
it universal means ONE call parser (pos + `name:` + `_`, unknown-name = error)
behind every call surface: source ops, `scan`, relation atoms, rule heads. Then
`_`-counting disappears language-wide, not op-by-op. This is a grammar change, not
a bolt-on; sequence it as the cons-unification epic, not a quick patch.

### 2. Cross-repo SCIP + transport-spec bindings + dataflow annotation
Vision (user): index relevant/adjacent projects together; bind them through
transport specs (OpenAPI); annotate whole dataflows across the boundary — API 1 →
API 2, API 1 → UI routes, backend SQL-table patterns → query/dataflow tuning.

Maps onto the current base cleanly:
- **Multi-index is done in primitive form**: `merge_files` already unions N SCIP
  indexes into one co-loaded `index.scip` (SCIP symbols are tool/package-
  namespaced, no cross-lang key collision). Adjacent-repo indexing = run `dl index`
  per repo, merge. Next: a `dl index --with <path>...` / workspace manifest so the
  merge set is declared, not manual.
- **Intra-repo interprocedural flow exists**: `examples/flow-interproc.dl` unions
  `df_edge` (intra-proc) with a `call_edge`-resolved hop into `flow_edge`;
  `closure(flow_edge)` walks value flow across fns (auto-memory
  `project_interproc_flow`). The missing hop is the CROSS-REPO / CROSS-TRANSPORT one.
- **The bridge = a transport-spec-seeded relation.** An OpenAPI spec maps a client
  call site (repo A symbol issuing `GET /pets/{id}`) to a server handler (repo B
  symbol serving that route). Model it as `xrepo_link(sym_a, sym_b, kind∈
  http|sql|event)` — same shape as `scip_impl`/`type_link`, seeded from the spec
  (a new source op parsing OpenAPI, or a `json`/`jsonp` extract over the spec file)
  rather than the compiler. Then `flow_edge` unions `xrepo_link` and
  `closure(flow_edge)` crosses the network boundary end to end. API→UI routes and
  SQL-table→query are the same pattern with a different spec source (a route table;
  a schema/migration file).
- **LSP notes = an annotation rel rendered through the existing diag/LSP renderer.**
  `diag` is already "just a relation, two renderers" (--check + --lsp). A cross-repo
  dataflow annotation is a `note`/`diag`-shaped rel keyed on a `ref` span; the LSP
  path surfaces it as a hover/inlay on the client call site pointing at the server
  handler. No new transport — reuse the diag sink.
- **SQL table patterns**: a source op (or `json`/regex extract) over migrations/
  schema → `table`/`column` rels; join to backend query sites; `flow_edge` +
  node2vec/closure for the tuning/hotspot queries.

Sequencing: (a) `xrepo_link` rel + an OpenAPI source op; (b) union into
`flow_edge`; (c) annotation rel + LSP hover; (d) workspace/merge manifest for the
adjacent-repo index set. Each rides a primitive that already exists.

### 3. Automate the changelog via comment-space
Fits the existing comment-pin + gen precedent exactly (`@op`/`@example` pins →
gen-reference.dl splices generated blocks; auto-memory
`feedback_never_edit_autogen_zones`). A `@changelog` pin in a Rust comment (or a
per-PR fragment) → a dl program harvests `comment(...)` rows heading a
`changelog(kind, text)` rel → splices a `<!-- BEGIN: changelog -->` block. Manual
CHANGELOG.md now; the generator is the same shape as op-table.dl when wanted.
