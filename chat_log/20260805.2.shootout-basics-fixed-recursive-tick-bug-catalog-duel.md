## Problem/Context
**THE COMPILER BUG (failure-modes.md entry 41, committed):** a recursive rule derives only one round per tick. Oracle vs tsv2, same program same schedule: `[[edge(1,2),edge(2,3)]]` gives oracle 3 rows, tsv2 2 rows (missing (1,3)); one edge per tick gives both 3 rows. Hits the alpha flagship (`flagship_flow_reach_over_resolved_edges.dl6` loses `flow_reach(app,entry,sink,persist)` when batched). Chain: `applyLevelsBeforeEdges` (1_incremental.ts:783) stages via `levelFrontierCopies(false)` (:335) writing frontier only, never next-frontier; `promoteFrontiers` (:1070) reads carry from `EXISTS(SELECT 1 FROM __next_frontier_*)` so carry is always false; that same promote then DELETEs the frontier, destroying round 2's input; `recomputeLevelsAfterEdges` (the only next-frontier writer) is gated on retractions. No test caught it because every recursive fixture feeds one hop per tick (4_flagship_flow.pl:34-35).
**Fix attempts, in order:** (1) rotate frontiers between rounds -> broke 6 tests because rotation destroys the arrival frontier later phases read; (2) append-only loop -> correct, but 6 failures remain since non-recursive programs pay one extra probing round; (3) narrow the loop to heads genuinely on a CYCLE of the level graph (DAG closes in one dependency-ordered pass) -> THIS EDIT WAS REJECTED, unapplied.
**Shootout, every engine had a basics defect:** retired hand mono packed `Pair((source<<32)|target)` and hashed it as one u64, so fxhash's multiply left only `target` in the low bits: 9M keys collapsed to 3000 distinct low-24-bit values against 6825320 for `(u32,u32)`. Isolated by holding the loop fixed and swapping only the set type: 7135ms / 249ms / 138ms for packed-u64 / tuple / sharded. A 4th layout, bitmap per source, does 37ms in 7.5MB but needs nodes^2/8 = 125GB at 1M nodes.

## Key Insights
- Every headline number in the shootout was reporting a memory mistake rather than a design. Fixing all three moved mono's lead from 30x-behind to 1.11-1.63x-ahead and handed rxgraph one win.
- fxhash over a packed composite key cannot spread: a product's low bits depend only on the operands' low bits, and hashbrown indexes buckets with exactly those bits. This is a 1NF violation that the hash function bills you for.
- Swapping the allocator hid an allocation-volume bug and stopped paying once the bug was fixed; mimalloc then made it worse.
- macOS `sample <pid>` found all of it with no instrumentation build.
- The oracle reaches full closure in one tick, so per-tick fixpoint is the semantics to match; drain-based spreading would fork the tick log from the oracle and is an open question in the budget plan.
- Flash stopped correctly at a pinned checksum mismatch and named the root cause down to the function; the STOP was worth more than a fudged benchmark row.
