## Problem/Context
Two open theoretical questions for the 500-repo polyglot ambition: (1) how do
you MEASURE soundness of a parse-only flow lift, and (2) can you predict
asymptotic call cost automatically from the flow/call graphs — and at what
graph-algorithm storage/time cost, since "it's just graph algorithms over and
over" and full closure is O(V^2) which is fatal at ~10M nodes (500 repos x ~22k
nodes each).

## Solution/Approach
Survey-level (no code this segment), three fields:

SOUNDNESS ESTIMATION — can't measure directly (needs ground truth). Practical:
differential vs a soundier oracle (rust-analyzer HIR or SCIP index) on a sample
corpus, recall = |tool ∩ oracle| / |oracle|. Plus per-rule positive/negative
test packs (CodeQL's model) + mutation testing. Theory: abstract interpretation
(Cousot 1977); the "soundiness" movement (Smaragdakis 2015) — sound for 95%,
explicitly unsound for the hard 5%. sprefa is soundy and UNDER-approximates
(holes) where typical taint tools over-approximate.

AUTOMATED BIG-O — prior art: COSTA/SACO (Java bytecode, cost relations + size
analysis), RAML (OCaml, amortized), AutoBound/C4B (C). All need what parse-only
lacks: loop trip counts + size relations + compositional cost. Realistic sprefa
output is SYMBOLIC Big-O ("call at depth-3 over collection C") not resolved
("O(n^3)") — needs no size solver. The composition rule = recurrence over
call_edge annotated with loop-nest depth. The missing relation to build:
nest(call_id, loop_id, depth, collection_id).

GRAPH COMPRESSION / SCALING — full closure O(V*E) time, O(V^2) storage = fatal
at 10M nodes. The stack that fits speed-tier:
- SCC condensation (already in scc.rs) — cycles collapse, closure runs on DAG.
- bounded-depth reachability O(kE) — perf-shape queries are 2-3 hop, not full.
- hierarchical / separate composition — per-file closure (small), merge only at
  exported call_edge / type_link boundaries; cross-repo only at exported syms.
  Matches real code's locality (flow stays in-file 95%+ of the time).
- semi-naive evaluation (already in rebuild_derived).
- 2-hop labeling (Cohen 2003) — only if cross-repo reach becomes a hard query.
- differential dataflow EXCLUDED on RAM grounds (memory-tiering skill).
Unifying trade: resolve STRUCTURE up front, VALUES at query time.

CODEQL COMPOSITION — CodeQL is a peer Datalog (per-repo DB, build-verified, deep
taint libs, mature query packs). Two structural limits at 500 repos: compiled-
lang DB needs a clean build per repo (drops repos that don't build); NO native
cross-database join (sprefa's one-DB-cross-repo model is the opposite). Compose
by running CodeQL per-repo where the build succeeds and emitting its findings as
a sprefa relation (codeql_alert(repo, rule, file, line, severity)); sprefa stays
the corpus-wide join + the home for queries CodeQL can't express.

## Key Insights
- Soundness is measured as recall vs a stronger oracle; sprefa UNDER-approximates
  (holes) which is unusual — most taint tools over-approximate. Both are "soundy".
- Symbolic Big-O ("depth-N over collection C") is the speed-tier slice of COSTA;
  resolved Big-O needs a build you don't have. The nest relation is the one thing
  to build to enable it.
- Full closure O(V^2) is fatal at 10M nodes. Bounded-depth + SCC condensation +
  hierarchical per-file merge is the speed-tier compression stack and covers
  ~all perf-shape queries (they're 2-3 hop). Real code is local: flow stays
  in-file 95%+, so per-file closure + boundary merge captures most reach.
- CodeQL and sprefa compose (per-repo deep + corpus-wide join), not compete.
- The unifying trade across soundness/Big-O/scaling: resolve structure up front,
  values at query time. That IS the speed-tier position.
- The user's lattice framing = the right mental model: a base floor of facts,
  oracle-imported facts to reach 80%, then graph theory to ratchet the rest. The
  differential (naive vs oracle) IS the soundness measurement, closing in a loop.
