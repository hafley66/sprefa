## Key Insights
- Store ID columns as SQLite `TEXT` decimal strings, not `INTEGER`, because arbitrary u64 IDs can exceed SQLite's signed i64 range.
- Keep writes plural: collect rows, call `Db::insert_rows`; no per-row DB loops.
- `_strings` can be INSERT-only because ids are content-derived; no read-back allocator is needed.
- Git blob OIDs are content addresses and should be preserved as `_files.content_hash` for committed revs.
- Git blob OIDs are useful power, but not a full scaling story: they avoid content reads for committed objects, while cross-repo/object-store lifecycle and non-git content still need explicit design.
- `git ls-tree -r -l` gives blob OID and size, which is enough for current `_files` rows without `git show` per file.
- `_where_bytes` remains sentinel-only right now; next work must thread real byte spans through extraction.

## Open Questions
- Should `ref` expose all extracted text values, only named captures, or only fields explicitly marked in a rule? Current `_strings` ingestion is broad over source row text values.
- For regex `match`, current extractor has line-local capture text but not byte offsets for each named capture. Need decide whether to compute capture spans now or start with line/match span where available.
- For `sg`, `run_sg` returns match span and capture text, but not per-capture node spans. If refs are intended for captured identifiers/specifiers, `sg` needs richer capture metadata.
- How should `_prov` migrate from path-string keyed to file-id/source keyed without breaking current incremental retraction semantics?
- Should committed git blob `FileId` use raw OID prefix (current) long-term, or hash a tagged namespace like `git-sha1:<oid>` to avoid theoretical cross-hash collisions with blake3 prefixes? Current code uses prefix directly to preserve the existing content address shortcut.
