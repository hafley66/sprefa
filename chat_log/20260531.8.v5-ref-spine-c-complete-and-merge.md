## Key Insights
- `diag(path,line,[col],[end_line],[end_col],severity,code,msg,[hint])` is the LSP note schema:
  recognized by column NAME (order-free), only path/line/msg required. Severity strings:
  error/warn/info/hint (lsp.rs:98). Save-driven (didChange ignored), disk-truth.
- For WORK, `FileId::of_bytes(content)` == `FileId::from_content_address(blake3hex, size)` (both
  = first 8 bytes of blake3), so unifying on from_content_address is safe and also handles git
  blob OIDs — one code path, no WORK gate.
- from_content_address ignores `size` except size==0 -> SYNTHETIC, so passing content.len() is safe.
- `_where_bytes` PK is content-derived `WhereBytesId`; `path` is attribution only (for retraction),
  not identity. Byte-identical files therefore can't both keep a row — documented edge, full-tick repairs.
- Lines from `content.lines()` are subslices, so line byte offset = `ln.as_ptr() - content.as_ptr()`;
  add regex `m.start()`/`m.end()` for absolute file byte span. No re-scan needed.
- ast-grep `node.range()` (Range<usize>) and tree-sitter `node.start_byte()/end_byte()` give
  per-capture byte spans cheaply.
- `ref`/`string` query rels are wholesale-refreshed from the meta tables (DELETE+insert via
  refresh_rel), skipping the '0' sentinel rows so queries see only real interned rows.
- Reserving `ref` is a breaking DSL change (an existing test used it as a user rel); accepted
  because the ledger names the relation `ref` and it's the refactor coordinate.
