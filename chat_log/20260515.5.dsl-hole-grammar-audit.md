# DSL hole grammar audit — `${NAME?}` and `$$${NAME}`

Branch: `worktree-agent-a41b8d7f344118e88` off `fb7f105`. Read targets: each
DSL's `compile()` (native engine) and its `OperatorDef::lower` path.

## Rule under audit

- `${NAME?}` is universal. Every backtick DSL must accept it. Per-DSL splice
  semantics determine what binding/lowering happens.
- `${NAME}` is universal read.
- `$$${NAME}` (triple-dollar) is **ast-grep only**. Mirrors ast-grep native
  `$$$NAME` for sibling-sequence captures.

## Two-layer architecture (reference)

- **Host pre-pass** (`v4/src/compile/lower/op_def.rs::default_plain_dsl_parse`):
  scans every dsl body for `${...}` and produces a `Vec<DslInterp>` with
  `kind = Term { mode: Read|Bind, field? }` or `kind = SubPipe { lowered }`.
  This is dsl-blind, always runs.
- **Per-DSL lower** (`v4/src/compile/lower/ops.rs::<Op>Def::lower`): decides
  whether to splice the body itself (static path) or hand it to a dynamic
  recompile component (`with_dyn_body` + `template::render_segments`).
  Today, **only `SubPipe` interps trigger dynamic**; Term Bind/Read interps
  fall through the static path, where the DSL's native compiler sees the
  raw `${X?}` bytes.

So a DSL "works" with `${NAME?}` if at least one of the following holds:
1. The DSL's native compiler handles `${...}` itself (ast, json), OR
2. The DSL's `lower` rewrites `${...}` from `body.interps` before invoking
   the native compiler (glob, sql, sql_where).

## Phase 2 — glob `$$${...}` decision: **Option A**

Per the user rule verbatim: "`$$${...}` is **ast-grep ONLY**. No other DSL
should have it." This is stronger than the "pick A unless tests rely on it"
heuristic; the test that relies on it (`glob_capture_smoke.rs::multi_segment_capture_with_triple_dollar`)
is the violation, not evidence of intent.

Plan:
1. Drop the `$$${X?}` branch from `glob_body_to_regex` (`v4/src/compile/lower/ops.rs:706-715, 731-739`).
2. Migrate the existing test to express multi-segment via `**` in the glob path:
   `glob\`**/${PARENT?}/${FILE?}.rs\`` — but `**` already maps to `.*` literal,
   no capture. To preserve the capture into `PARENT`, switch to two-segment shape:
   `glob\`**/${PARENT?}/${FILE?}.rs\`` and accept that `PARENT` captures only the
   immediate parent segment (single segment). The "multi-segment greedy bound to
   one name" feature is dropped; existing test changes to single-segment.
3. Emit a `glob/triple-dollar-not-allowed` diagnostic when `$$$` is seen at a
   position not eaten as ordinary literal — or, since the host pre-pass treats
   the inner `${X?}` as a normal Term interp, the leading `$$` becomes two literal
   `$` characters in the regex literal walk. That is acceptable: glob bodies with
   `$$$` no longer carry meaning; they match the literal `$$` followed by the
   capture. Tests must explicitly call out that this is dropped.

Justification:
- Universal rule says triple-dollar is ast-only.
- "Multi-segment greedy bound to one name" is achievable with explicit
  segment shape, the same way real globs (ripgrep/globset) work.
- Keeps the universal-rule contract clean for tooling (LSP, completions,
  diagnostics) that needs one canonical interpretation across DSLs.

## Open question: SQL bind semantics

The user's rule says "sql: parameter binding". Two reasonable interpretations:

a. **Parameter substitution at compile**: `${X?}` becomes `?` and the value of
   captured `X` is passed via rusqlite `params_from_iter`. Requires routing
   binders into the params slot.
b. **Column reference, `?` is decorative**: `${X?}` and `${X}` both lower to
   `"input"."X"`. The `?` only signals to the parser/LSP that this is the
   "introducing" form. SQL doesn't actually bind anything new; the rule
   head's `X?` is what introduces.

This audit picks **(b)** for the fix. Rationale:
- Matches sql_where's surface (predicates already treat `${X?}` and `${X}`
  identically post-fix).
- Matches the user's verbatim phrasing: "`${NAME?}` to bind, `${NAME}` to read"
  is about syntactic surface, not about runtime SQL parameters.
- Avoids a new `params_from_iter` integration that would require threading
  capture names through `SqlQueryComponent`.

If the user wants (a), it's a separate change — flag in final report.

## What stays out of scope

- **markdown**: no compile/match shape; `${X}` is a host-template interp
  handled by `render_segments` for the wrapping op (e.g. `render_markdown`).
  No DSL-side change needed.
- **ast_yaml**: native compile delegates to ast-grep RuleCore YAML; sprf
  carveouts are pre-processed by `collect_ast_yaml_carveout_names_and_positions`
  which already handles `${NAME?}`. Verified via existing
  `rust-doc-ast-yaml-map.sprf` usage. No new test needed beyond a smoke.

## Empirical evidence (probe results)

Native `Dsl::compile` results on raw bodies (probe run, then removed):

```
glob `${X?}.txt`         → Ok (DSL grammar skips `${...}` as ERROR → literal walk; lower-time regex bind fills it)
glob `$$${X?}/foo`       → Ok (same path; lower's $$$ branch adds the multi-segment group)
glob `${X}`              → Ok at DSL; rejected at lower (glob-read-not-supported)
re `TODO\\(${WHO?}\\)`   → Err re.syntax (regex::Regex::new chokes on `{WHO?}`)
re `$$${WHO?}`           → Err re.syntax
json `{ name: ${N?} }`   → Ok (brace_parse strips `?`)
json `{ name: $$${N?} }` → Err json.parse-body (extra `$` chars start an inner capture)
sql `SELECT 1 AS ${V?}`  → lower error: "sql: bind interpolation is not valid inside sql bodies"
sql_where `${X?} = 'foo'`→ parses but lex captures `Hole("X?")`, runtime get returns None
```
