## 15. Unified-interpolation model (your callout)

Restating what you just said: every paren / bracket / brace body — whatever
DSL it speaks (regex / glob / ast / cst / sh / json / shell-literal / ...)
— is uniformly:

```
literal_padding  ${pipe_arg}  literal_padding  ${pipe_arg}  literal_padding ...
```

The DSL owns the *padding* (its native syntax: regex meta-chars, glob
meta-chars, ast pattern syntax, etc.). The host owns the `${...}`
*carveouts*, which are pipe args interleaved with the padding.

Materialization, end to end, is:
1. Walk the body's CST (DSL sub-tree).
2. For each carveout range, run the carveout's pipe arg, splice the result
   (DSL-appropriate escape) into the surrounding padding.
3. Hand the fully-materialized literal string to the DSL's compiler
   (`Regex::new`, glob compile, ast pattern compile, ...).
4. Match against the input.

This subsumes the "lift to regex" question entirely — *every* pattern
op is "lift to its native compiled form after carveout materialization." 
There is no separate non-lift code path at the matcher layer; the
non-lift case only appears when the *outer source-op* is composing an
arg-pipe that doesn't reduce to a single pattern op (e.g.
`repo(tag(:repo, $R?))`).
