## Problem/Context
Three threads came together.

The rails-noise thread: the prior session's graph-aware conn rule still path-
scoped via `changed(p)`, so every touch on engine.rs fired ~46 warnings (most
of engine.rs reaches via `tick`). The queued fix was changed_line(p,l); this
session shipped it and switched the rail. The line-scoping is the precision
win the graph property needed.

The cursor-wiring thread: the prior session's gen(:mode,...) byte-cursor port
used literal offsets in its gate tests because the spine integration wasn't
wired. The match op emitted only `line`; there was no direct join key linking a
match instance to its spine id. This session added the optional id output
column so match -> ref(id,lo,hi) -> gen(:mode) closes end-to-end.

The CST-architecture thread (the real one): the prior session's big plan was a
generic ingestion registry so any tree-sitter grammar feeds the relation soup.
This session shipped the first slice (DocLang + doc_node + markdown) but the
user pushed back: doc_node is an island with no join to the code graphs, and
the framing of "three peer extractors" was wrong. The rectified model:
- tree-sitter is the extraction unifier (comment nodes free, uniform CST).
- syn (Rust) and oxc (TS) are the two adapters that need interfacing IN to the
  tree-sitter shape (kept for better semantics, but they drop comments and need
  a scan to refill). Kotlin already uses tree-sitter; tree-sitter-rust is
  already a dep but UNUSED (Rust extracts via syn); tree-sitter-yaml/toml/c/json
  are deps, idle; tree-sitter-typescript would replace oxc.
- SCIP is the second language-neutral carrier (uniform descriptors + role/kind
  tags), already live and overriding syntactic name resolution in refresh_type_rels.
- addressing is the segment-list + (delimiter, resolver) scheme table; desc.rs's
  Desc = Vec<Segment> + DescKind IS already this model.
- the kind/tag column on every relation family is where "neutral but tagged"
  lives in the schema, at three scales (CST, symbols, soup).

## Solution/Approach
Four slices shipped, then the architecture got rectified.

### S1: changed_line builtin (`e061631`)
Followed the sprefa-v5-new-builtin-rel skill (8 wiring sites in engine.rs).
The refresh fn has two sources: (1) `git diff -U0 HEAD` new-side hunks parsed
via hunk_new_range (`@@ -a,b +c,d @@` -> (c,d); count defaults to 1); (2)
untracked files from `git status --porcelain -uall` (which the diff omits) emit
every line 1..=N. Paths canonicalized to repo-relative exactly like
refresh_changed_rel so rows join call_site on equal text. One batched diff read
+ one status read, no per-row writes. Verified the real hunk formats empirically
(append -> `@@ -1,0 +2 @@`, middle-delete -> `@@ -2 +1,0 @@`) before writing
the parser.

### S2: rails line-scoping (`dab730e`)
One-line rule edit (changed(p) -> changed_line(p, l)) plus collapsing a
duplicated comment block. The l variable is already bound by conn_fn(fn, p, l),
so the join is clean. Verified changed_line reports the 9 edited lines of
.dl/rails.dl against the warm db; the rail silence is genuine precision, not a
broken empty rel. Reinstalled the dl binary so the PostToolUse hook picked up
changed_line.

### S3: match id column (`19a51dc`)
Added `id: Option<Term>` to BodyItem::Match. The parser peeks Tok::Comma after
the line term for the optional 5th arg. Engine match arm: for each capture
iteration, compute the whole-match span's WhereBytesId via
`WhereBytesId::of_located(wb, repo, path)` (deterministic from span + source,
no db access, parallel-safe), bind it to the id var, and push_span the whole-
match text ONLY when id is requested (4-arg form's spine behavior unchanged:
named captures only). The id equals what insert_spine_where_bytes assigns
later, so `ref(id, _, _, lo, hi)` resolves to the exact match. The ref
relation's file column is a file_id not the path, so the rule gets p from
match and lo/hi from ref. Two end-to-end gate tests (:replace and :wrap).

### S4: ingest DocLang + doc_node + markdown (`ad50aee`)
Additive slice, source extractors untouched. New module v5/src/ingest/mod.rs:
DocLang trait (name/matches/extract_docs, : Sync for rayon), DocFacts/DocNode
structs (file/line/kind/name/parent -- same shape as typegraph::TypeEntity),
doc_langs() registry, MarkdownDoc hand-rolled extractor (ATX headings via 1-6
`#`+whitespace, fenced code blocks via >=3 backticks/~, heading stack pops
>= level so siblings don't nest, #tag-without-space is not a heading).
engine.rs: DOC_RELS const, doc_rel_decls, doc_rels_used, reserved guard,
declare_builtins, refresh_doc_rels (rayon-parallel, no resolution pass, no
legacy mirror), tick wiring at both sites. Files come from _file (a source rule
scanning `**/*.md` feeds it exactly as `**/*.rs` feeds the type graph). 3 e2e
tests: 4-node fixture, doc_node joins changed(p) for a doc-scoped rail, reserved.

### Architecture rectification (no code, the real deliverable)
Through user pushback, the framing shifted from "three peer extractors + a
parallel DocLang" to the rectified model in Problem/Context. Key concessions:

## Key Insights
- doc_node as shipped is an island. It shares only SHAPE with type_entity
  (file/line/kind/name/parent); no shared key, no join. The usefulness lives in
  EDGES between the doc and code graphs (a doc_ref relation), not in the nodes.
  Without the bridge, "track docs/plans from outside the codebase as a .dl rule"
  is unimplemented. The easy half (extraction) shipped; the useful half (the
  link) is still ahead.
- tree-sitter is the extraction unifier, not a peer with syn/oxc. Every
  tree-sitter grammar exposes a `comment` node type, so comments become doc
  space automatically once extraction is tree-sitter-shaped. The ONLY reason
  comments are "hard" is syn strips them and oxc replaces tree-sitter-typescript.
  tree-sitter-rust is already a Cargo.toml dep but UNUSED; Kotlin already uses
  tree-sitter; yaml/toml/c/json are idle deps.
- The schema's kind/tag column is where "language-neutral but tagged" lives in
  the system, at three scales: tree-sitter CST (node-type tags), SCIP symbols
  (role/kind tags), and the SQLite soup (every family carries a kind column:
  type_edge.kind, df_node.kind, doc_node.kind, EntityKind.tag). The DL layer is
  the join across those tagged tables. tree-sitter unifies the CST, SCIP
  unifies the symbols, the soup unifies them with each other.
- Addressing is already half-built. desc.rs's Desc IS Vec<Segment> + DescKind;
  a path literal is scheme:body where body lexes into segments. The scheme
  picks exactly two things -- (delimiter, resolver) -- and nothing else varies.
  fs: -> `/` -> filesystem; rs: -> `::` -> TYPE/CALL soup; kt:/ts: -> `.` ->
  same; md: -> `#` -> doc_node; http: -> `/` -> URL. Adding rs: is one
  SchemeSpec row + a resolver that joins the soup. The segment parser is reused.
- The symbol address literal joins DIRECTLY with the graph relations because
  their columns ARE the file::kind::name sym strings. So `loop_hot_fn(rs:engine::tick, _)`
  collapses a type_entity name-join into one literal, and it is unambiguous
  (resolves via the soup's file/kind context) where a name-text join is not.
- changed_line is the precision tool the graph-property rails needed. The conn
  rule was never wrong about the graph property; it was path-scoped, so it
  surfaced every loop-reachable .conn() in a touched file. Line-scoping makes
  each warning a real per-edit risk. The rail caught the .conn() this session
  ADDED in refresh_doc_rels (engine.rs:2691) -- line-scoping validated on the
  author's own edit.
- The match id column closes the loop the cursor port deferred. The id is
  computed in parse_file via WhereBytesId::of_located(wb, repo, path) --
  deterministic, parallel-safe, equals the id insert_spine_where_bytes assigns
  later. The 5-arg form pushes the whole-match span ONLY when id is requested,
  so existing 4-arg rules keep their spine behavior.

## Open Questions
- tree-sitter-rust vs syn for Rust: replace syn entirely (lose better type
  resolution) or keep syn + add a tree-sitter-rust comment scan as the adapter?
  The user's framing ("syn/oxc are exceptions that need interfaced in") implies
  the latter -- keep syn for semantics, interface in the comment nodes.
- Does the doc_ref bridge match doc text against symbol NAMES or against
  ast-grep patterns over doc code blocks? Names is simpler; ast-grep is
  precise. Probably both: name-match for prose mentions, ast-grep for code
  blocks.
- Should the default tree-sitter-grammar path (P1.2) ship a curated grammar set
  in the binary, or accept grammar config files at runtime (v4's
  cst/build/grammar_walk.rs compiled grammars on the fly)?
- Does changed_line need a rev-aware variant (git diff -U0 <rev>) for history
  queries, or is worktree-scope enough for rails?
- Phase ordering: P3 (addressing) can slide before P1/P2 since rs: resolves
  against the already-populated TYPE/CALL soup. Does the user want the terse
  symbol literals before the comment-extraction work?
