# v2 → v3: Lift zero-cursor-output diagnostics

**Date:** 2026-04-27  
**Context:** v2 had per-op "no-match" diagnostics when ops matched zero items.  
v3 has empty-pattern-body diagnostics but NOT zero-cursor-output diagnostics.

---

## v2 Implementation

### File Reference
- **v2/src/ops/_7_line.rs** (lines 248–253)
- **v2/src/ops/_9_ast_grep.rs** (lines 337–338, 590–592)
- **v2/src/ops/_5_json.rs** (lines 332, 464)

### Behavior Summary
After an op processes a cursor and accumulates matches into `per_cursor: Vec<Cursor>`:
- **If `per_cursor.is_empty()`** after all lines/nodes scanned → emit diagnostic with code `"{op}/no-match"`
- **If `per_cursor.is_not_empty()`** → emit the batch arc; skip diagnostic

Example from **line.rs:248–253**:
```rust
if per_cursor.is_empty() {
    diags.0(Box::new(LineDiag::NoMatch {
        site: (*site).clone(),
        path: fp.0.to_string_lossy().into_owned(),
        pattern: pattern.src.as_ref().to_string(),
    }));
} else {
    out.push(Arc::from(per_cursor.into_boxed_slice()));
}
```

### Diagnostic Shape
- **Code pattern:** `"{op}/no-match"` (e.g. `line/no-match`, `ast/no-match`, `json/no-match`)
- **Severity:** `Severity::Error` (for line & ast); Error for json
- **Anchor:** ParseSite of the op invocation in the .sprf source
- **Message content:** OP_NAME`(`PATTERN_OR_ARG`) matched nothing in `PATH``

### Emission Scope
- **Per-op:** Each op emits independently when it sees zero output for one input cursor
- **Per-input-cursor:** Logic runs inside the per-cursor loop; if one cursor has no match, emit diag; next cursor may match
- **NOT inside fork arms:** (observation: no special fork-arm suppression in v2; each arm's ops emit independently)

## v3 Current State

### Diagnostic Framework
- **Parse-time diags:** `PatternDiagnostic` struct with `code`, `message`, `byte_range` (Range<usize>)
  - Emitted during `registry.build_from_node()` → lowering phase
  - Example: `json/empty-body`, `ast/bad-pattern`
- **Runtime-time diags:** `RunEvent::Diag { code: String, severity: String, message: String }`
  - Currently only for parse errors and SQLite drain errors
  - Emitted in `run_pipeline()` in `/crates/server/src/run.rs`
- **Op output:** Each op returns `BoxFuture<Arc<[Cursor]>>` (cached) or `BoxStream<Arc<[Cursor]>>`
- **Op execution:** `Pipeline::Op(op)` calls `op.pipe_flat_map()` → internally uses `buffer_unordered(64)` mergeMap over per-batch `pipe` calls
  - **No hook currently exists** to inspect empty batches emitted by an op

### Span Information Available
- v3 ops store `byte_range` during lowering in most cases
  - **ast_grep.rs:126–128, 131–133:** stores `byte_range: inv_node.byte_range()`
  - **json.rs:91–94:** stores `byte_range` in PatternDiagnostic during error; ops themselves can hold it
  - Tree-sitter `Node` has `.byte_range()` available at lowering time
- **Problem:** Op trait does NOT expose `byte_range` as a method; ops don't carry it at runtime
  - Ops only expose `name()`, `arg_spec()`, `bound_captures()`, `term_positions()`, `cache_key()`

---

## v3 Architecture Gap

**Issue:** Between lowering (where spans are available) and runtime (where we see empty batches), the span is lost.

The v3 op flow:
1. `registry.build_from_node(op_name, inv_node, src, diags)` → constructs `Arc<dyn Op>` + diags
   - Has access to `inv_node.byte_range()`
   - **Could** store span in the op struct IF it were part of the op trait
2. `Pipeline::Op(arc_op)` runs at runtime
   - Calls `op.pipe_flat_map(ctx, upstream)`
   - Receives `Arc<[Cursor]>` batches
   - **Cannot** access original source span
3. No place in `run_pipeline()` to emit zero-output diagnostics post-op

---

## Design Recommendation

### Hook Point: Framework-level wrapper in Pipeline::Op

**Rationale:**
- v2 style (per-op) required each op to track `per_cursor.is_empty()`.
- v3 streams are lazy; ops emit batches asynchronously. Inspecting "did this op emit anything?" requires buffering upstream, which defeats streams.
- **Better:** Wrap the op's output stream at the Pipeline::Op level, AFTER `pipe_flat_map()` drains, to detect empty emission.

**Approach:**
1. Modify `Op` trait to expose source byte_range:
   ```rust
   fn source_byte_range(&self) -> Option<std::ops::Range<usize>> { None }
   ```
   - Ops that store span during construction set it (return `Some`); others default to `None`.

2. In `Pipeline::run()` for `Pipeline::Op(op)` variant:
   - After collecting all batches from `pipe_flat_map()`, check: did this op emit **any** cursors across **all** input cursors?
   - If upstream had ≥1 cursor AND op emitted 0 total → prepare zero-cursor diag.
   - Inject diag into the stream before it yields Done for this op.

3. Diagnostic shape:
   ```rust
   RunEvent::Diag {
       code: format!("{}/no-output", op.name()),
       severity: "Error".to_string(),
       message: format!("{} matched zero items in the input stream", op.name()),
   }
   ```
   - Byte-range anchorability: pass through LSP context separately (currently not part of RunEvent, so TBD with LSP lead).

### Smallest Patch Outline

#### File 1: `v3/crates/pipeline/src/_1_op.rs`
- Add to `Op` trait:
  ```rust
  fn source_byte_range(&self) -> Option<std::ops::Range<usize>> { None }
  ```

#### File 2: `v3/crates/pipeline/src/_2_pipeline.rs`
- Modify `Pipeline::Op(op)` match arm in `Pipeline::run()` (line 53–126):
  - Collect all emitted batches from the inner stream.
  - Track: `(input_cursor_count, output_cursor_count)`.
  - After stream fully drains, if `input_cursor_count > 0 && output_cursor_count == 0`:
    - Emit a diagnostic batch containing zero cursors but tagged metadata for diag emission.
  - OR: yield a synthetic RunEvent-adjacent signal (requires server/run.rs integration).

#### File 3: `v3/crates/server/src/run.rs`
- Modify the per-seed per-pipe loop (lines 236–264):
  - Wrap `pipeline.run(&ctx, seed_upstream(seed))` to yield RunEvent::Diag on zero emission.
  - Consume the pipeline stream, track batches per op, emit diag on empty.

#### File 4: ops that store spans (e.g., `_ast_grep.rs`, `_json.rs`, `_line.rs`, etc.)
- Add `source_byte_range(&self)` implementation:
  ```rust

      Some(self.byte_range.clone())
  }
  ```

## Diagnostic Severity & Conditions

### Severity
- **Error** (same as v2) — op ran OK but matched zero.
- Rationale: zero-match is useful signal for query debugging; helps catch typos and misunderstands.

### Conditions
- **Only if** upstream fed ≥1 cursor to the op
- **Not if** op itself is the data source (e.g., `repo`, `rev`, `fs` — these legitimately match zero if filters don't match)
- **Not if** inside a fork arm **where** it's expected to filter

**Refinement needed:** Which ops should emit? Filtering ops (line, ast, json, etc.) should; source ops (fs, repo) should not.
- **Marker:** ops that have `pipe()` returning a *subset* of input (filtered) vs. *augmented* (widened).
- **Heuristic:** if op has bound_captures, it's likely a matcher → emit. If no captures, it's a source/passthrough → skip.

## Open Questions

1. **Byte-range in RunEvent?**  
   `RunEvent::Diag` currently only has `code`, `severity`, `message`.  
   To anchor the diag in LSP, we'd need byte_range.  
   Option A: Extend RunEvent::Diag to include `byte_range: Option<Range<usize>>`.  
   Option B: Emit diag during lowering (pre-computation) like empty-body → requires per-rule pre-analysis.  
   Option C: Keep message only; LSP hover renders without anchor.

2. **Deferred per-fork-arm:**  
   Should `Fork(arms)` suppress the diag if arm's output is empty, since arms are mutually exclusive?  
   v2 doesn't suppress; design assumes each arm may legitimately filter all. Confirm with UX.

3. **Per-pipe vs. per-op:**  
   Should we emit once per op invocation in the pipeline, or aggregate per pipe?  
   Design picks per-op. Confirm with use case: user sees `line: matched zero`, not `rule X: matched zero`.

4. **Severity for source-style ops:**  
   If `fs()` with a glob matches zero files, is that an error or expected?  
   Design defers to "marker heuristic" — needs a trait method or annotation to override.
