# JSON arm of the v6 surface (user directive 2026-07-27)

Directive: "we need json and aggregate json ability... probably make it part of
the type language with the whole braces things."

## Design: JSON is not a second value world

The surface already has one value world (ARCH.pl kernel: structs/tuples/terms
nest in columns; symmetric struct/tuple discipline). JSON slots into it as the
UNTYPED corner of that same world, reachable from the typed corner by decode.

| JSON | term representation (reference engine) | surface spelling |
|---|---|---|
| object | `obj([key-Value, ...])`, keys sorted, unique | `{ tag: "v1", stars: 4 }` |
| array | prolog list | `[1, 2, 3]` |
| string | `str(Text)` | `"text"` |
| number (int) | `int(N)` | `42` |
| true/false/null | `bool(true)`, `bool(false)`, `none` | `true` / `false` / `none` |

- The braces literal is the SAME braces production as struct construction:
  `Entry { tag, .. }` (typed, field set closed by the decl) and
  `{ tag: "v1" }` (untyped Json) share one grammar; the leading type name is
  what picks the typed reading. One parser production, two typings.
- Column type `Json` = the closed recursive union above. No user extension.
- `none` is shared with Option(T): absent field and null coincide at decode.
- Floats: DEFERRED (v5 corpus is int-only; `+` law already Int-only).
- Key ordering: objects are canonical (sorted, dup keys an error at parse).
  Equality = term equality, so interning/content-addressing works unchanged.

## Decode: braces patterns over Json (the typed_decode sugar, made real)

`typed_decode` already exists in kernel.pl sugar ([envelope_match]). The goal
form in rule bodies:

    decode(JsonExpr, Pattern)         succeeds iff shape matches, binds holes
    entry := decode(body, Entry)      typed result via the struct's decl

- Pattern is the braces/struct grammar again: `{ name: RepoName, owner: { login: Login } }`.
- Object patterns are OPEN by default (extra keys ignored) matching jsonp's
  reality; `..` therefore optional in json patterns, required in struct
  patterns (struct fields are closed, omission = wildcard in body position).
- Missing key vs null: both fail a bare field pattern; `field: none` matches
  null only; `field?: X` (optional-key) DEFERRED until a corpus receipt.
- List element fan-out: `elem in decode(body, [..])` stays with the parked
  `in` sugar; the engine goal `json_each(JsonList, Elem)` is the kernel form.

## Aggregate JSON: two new reserved head forms

Rides ruling q9 (reserved head-position aggregate forms, not stdlib fns):

    repo_langs(Repo, json_array(Lang))        <- repo_lang(Repo, Lang);
    repo_meta(Repo, json_object(Key, Value))  <- repo_kv(Repo, Key, Value);

- `json_array(Expr)`: bag of per-derivation values (q7 bag), CANONICAL ORDER
  (msort) in the reference engine; sqlite lowering = `json_group_array` over
  an ORDER BY, so both targets agree bytewise.
- `json_object(KeyExpr, ValueExpr)`: keys must be Str, duplicate keys across
  the group = keyed_conflict-shaped error (same-key-two-values is the
  aggregate twin of the FD law), sqlite lowering = `json_group_object`.
- Both nest: values may themselves be obj/list, so one level rule can build
  the full nested document observers read (db IS the API: the JSON column is
  the outward-facing shape).

## Receipts

- v5 corpus: json 10 + jsonp 14 files (extraction side); the missing half was
  CONSTRUCTION (no v5 program can emit a JSON document; gh-cache.dl stores
  response bodies as opaque Str and re-parses per read).
- sqlite has the whole runtime already: json_group_array/json_group_object,
  json_extract for decode lowering, `->>'path'` for dot access.
- tier: values+decode = T0/T1 seam (decode of a world-fed Str body is T1;
  the value world itself is T0). Aggregate heads = T0 (rides q9).

## Not in this arm

Floats, optional-key patterns, JSON Schema import (TypeSpec-replacement far
tier), jsonpath strings (dot access sugar covers the corpus), user-defined
Display on Json.
