## 0. Buy verdict, in three sentences

Nothing on the market does what this arc needs end to end, because every mature tool
sits on one side of the spec (generate it from code, or consume it) and this design
generates it from a *third* place — prolog facts that are neither. So the buy is a
**shopping list of consumers, not a framework**: `openapi-typescript` (devDependency,
zero runtime output) for the TS types, Redocly CLI (already proven working here, via
`pnpm dlx`, no dependency added) as the validator gate, and `utoipa` on the rust side
*only if* the axum flip wants annotations-as-truth — which it should not, because the
facts already are the truth. The one thing worth buying at runtime is request
validation against the emitted spec (`ajv` compiled from the spec's schemas), and even
that is optional given `batchProblem` in `4_http.ts` already validates the only body
that has structure.

## 1. Buy research, candidate by candidate

Grading columns, per the brief: **direction** (does it consume a spec or produce one),
**timing** (runtime vs codegen), and **fit with generated-artifact-checked-in** —
which is this repo's established shape (`cli/0_inventory.ts` is generated by
`compile/2_emit_cli_inventory.pl`, checked in, and staleness-gated by
`tests/bopCommandInventory.test.ts`).

### (a) TypeScript / node side

| candidate | version | direction | timing | fit | verdict |
|---|---|---|---|---|---|
| **openapi-typescript** | 7.13.0 | consumes | codegen | **excellent** | **BUY (dev)** |
| **openapi-fetch** | 0.17.0 | consumes | runtime (tiny) | good | buy only if a typed client is wanted |
| **ajv** | 8.20.0 | consumes | runtime | good | conditional buy (see §6 card 4) |
| express-openapi-validator | 5.6.2 | consumes | runtime | poor | **no** |
| fastify-openapi-glue | 4.11.3 | consumes | runtime | poor | **no** |
| @hono/zod-openapi | 1.5.1 | produces | runtime | wrong direction | **no** |
| @fastify/swagger | — | produces | runtime | wrong direction | **no** |
| OpenAPI Generator (java) | — | consumes | codegen | poor | **no** |

**openapi-typescript 7.13.0.** Reads an OpenAPI 3.0/3.1 document and writes a single
`.d.ts` of `paths`/`components` types. Output has **zero runtime dependencies** — it is
types, nothing executes. That is exactly the shape this repo already uses: a generated
file, checked in, diffed by a test. It becomes a *second* generated artifact downstream
of `openapi.json`, and the same staleness gate covers both. It also cannot lie about the
server, only about the spec — which is what §4's parity gate is for. Only real cost: it
is a devDependency (878 KB unpacked) and one more `just` recipe. **Buy.**

**openapi-fetch 0.17.0.** Typed `fetch` wrapper (228 KB unpacked; advertised at ~6 KB min+gzip) that consumes openapi-typescript's
output; `client.GET("/idb/{rel}", { params: { path: { rel } } })` type-checks the path,
params, and response. `bop.ts` currently hand-rolls this with `routePath()` +
`JSON.parse(text) as {rows: IRow[]}` — an unchecked cast on every read. openapi-fetch
would delete those casts. Against it: it is a *runtime* dependency in a file whose own
header says "NO SECOND HTTP CLIENT LAYER: `fetch` is node's own global", and the CLI has
seven call sites total. **Defer** — the types alone (openapi-typescript) already remove
the casts if `bop.ts` annotates its `fetch` results, at zero runtime cost. Revisit when
the CLI grows past ~15 calls.

**ajv 8.20.0.** The JSON Schema validator every other tool here embeds. Feed it
`components.schemas` from the emitted spec and it validates a request body against the
same document the client generated from. This is the only candidate that closes the loop
*at runtime* rather than at compile time. Against it: 1 MB unpacked, a real runtime dep,
and OpenAPI 3.1 is JSON Schema 2020-12, so ajv needs `ajv/dist/2020` (the plain entry is
draft-07) — a known sharp edge. Also `4_http.ts::batchProblem` already rejects bad
arrival batches with *better* messages than a schema violation ("'x' takes 3 columns, got
2"), because it knows the loaded program. **Conditional** — card 4.

**express-openapi-validator 5.6.2.** Genuinely good at what it does: point it at a 3.1
spec and it validates requests (and optionally responses) as express middleware, with
`ajv` underneath. Two disqualifiers, neither about quality. It requires **express**, and
`4_http.ts` is deliberately `node:http` with no framework ("four literal path shapes; a
router library would be more machinery than the problem"). And it is *middleware*, i.e.
imperative interception, in an app that is one cold observable with a single subscription
— it would need a shim from express's `(req,res,next)` into the rxjs graph, which is more
adapter than the thing it adapts. **No**, and the reason is architecture, not merit.

**fastify-openapi-glue 4.11.3.** The most *conceptually* aligned candidate found: it is
genuinely spec-first — hand it an OpenAPI document and a service object and it wires
fastify routes from the spec at boot, validating requests against it, and errors on an
operation with no handler ("Operation findPetsByStatus not implemented", 500). That
"missing handler is an error" behavior is a live parity gate for free, which is precisely
what §4 builds by hand. It also ships an `openapi-glue` CLI generator for scaffolding.
Rejected anyway: adopting it means adopting fastify, replacing a 410-line hand-written
`node:http` front whose one-subscribe/switchMap/teardown properties are load-tested by
`serve-leak-soak` and `serve-endurance`. Trading a proven 410 lines for a framework plus
a plugin, to gain a check we can write in 40 lines, is the wrong trade at this size.
**No — but it is the design to copy**, and if the server ever *does* take a framework,
this is the first thing to re-evaluate.

**@hono/zod-openapi 1.5.1** and **@fastify/swagger.** Both are code-first: you declare
routes with zod (or JSON Schema) and the spec falls out. This is the dominant modern
node pattern and it is exactly inverted from this arc. Adopting either would make
TypeScript the source of truth and demote the prolog facts to documentation — the thing
the directive explicitly rejects. Recorded so the inversion is a stated choice rather
than an oversight: if the prolog-as-source premise were ever dropped, `@hono/zod-openapi`
is the strongest node option, because zod schemas double as runtime validators.

**OpenAPI Generator.** The 60-language java behemoth. Generates typescript-fetch clients
and node server stubs from a spec. Against it: a JVM in the toolchain, generated output
measured in dozens of files with its own class hierarchy, and templates that fight any
hand-written runtime. `openapi-typescript` produces one `.d.ts` for the same purpose.
**No.**

### (b) Rust / axum side (post-flip)

| candidate | version | direction | timing | fit | verdict |
|---|---|---|---|---|---|
| **direct emission** (facts → `.rs`) | — | produces | codegen | **native** | **DEFAULT** |
| utoipa (+ utoipa-axum) | 5.5.0 / 0.2.0 | produces | compile-time macros | fair | fallback |
| aide | 0.15.1 | produces | runtime builder | fair | second fallback |
| progenitor | 0.14.0 | consumes | codegen | good, but client-only | buy for CLIENTS |
| schemars | 1.2.2 | produces (schemas) | derive | good as a piece | maybe, under aide |

**Direct emission.** The emitter already turns facts into OpenAPI JSON; a second emitter
turning the same facts into `axum::Router` wiring plus `serde` structs is the same shape
as `emit_ts.pl` (which already emits real TypeScript with real SQL in it) and
`2_emit_cli_inventory.pl`. It costs one more prolog module and zero rust dependencies.
It also keeps the *one* property the other three cannot: the spec and the router are
siblings from one parent, so they cannot drift — with utoipa or aide the spec is derived
from the rust code, which is derived from the facts, and the middle link is where drift
lives. Sketch in §5. **Default.**

**utoipa 5.5.0 + utoipa-axum 0.2.0.** By far the most used (11.9M recent downloads);
`#[derive(ToSchema)]` + `#[utoipa::path(...)]` annotations, and `utoipa-axum`'s
`OpenApiRouter` + `routes!` macro registers a handler with axum and adds its path to the
spec in one call, so a route cannot be served without appearing in the document. That
last property is genuinely valuable and is a *stronger* version of §4's gate. Two costs:
it is macro-heavy (a recurring complaint in the community, and macro attributes are
exactly the kind of hand-maintained metadata this arc is trying to delete), and it makes
rust the spec's source — so the emitted document would have to be diffed against the
prolog-emitted one, which is a parity gate between two generators instead of one
generator and one server. **Fallback**, taken only if emitting axum wiring proves harder
than expected. If taken, emit the annotations from facts rather than hand-writing them.

**aide 0.15.1.** Same code-first direction, different taste: no `linkme` global registry,
no macro soup — plain functions, `schemars` for schemas, `OperationInput`/`OperationOutput`
traits, builder-pattern transforms. Materially more readable than utoipa and materially
less adopted (573K vs 11.9M recent). Same structural objection as utoipa (rust becomes
the source). **Second fallback**, preferred over utoipa on style if the rust side ever
wants hand-written handlers with generated docs.

**progenitor 0.14.0.** Oxide's spec→rust-**client** generator. Three delivery modes, all
compatible with this repo's habits: a macro, a `build.rs` writing code included via
`include!()`, and `cargo-progenitor` producing a standalone checked-in crate. **Client
only** — no server generation of any kind, targeted at Dropshot-emitted documents. It is
therefore not a candidate for the axum server, but it *is* the answer to "how does a rust
`bop` talk to the node server (or vice versa) during the flip": generate the client from
the same `openapi.json`, so both implementations are graded against one document.
**Buy — for the client half only.**

**schemars 1.2.2.** Not a competitor; the schema-derive layer aide sits on and utoipa
optionally interops with. Relevant only if a fallback is taken. Noted so the table is
complete.

### (c) CLI-from-OpenAPI

| candidate | direction | timing | fit | verdict |
|---|---|---|---|---|
| **extend `2_emit_cli_inventory.pl`** | produces | codegen | **native** | **DEFAULT** |
| Restish | consumes | runtime | interesting | **no** (but steal `x-cli-*`) |
| openapi-cli-generator | consumes | codegen | dead | **no** |
| OpenAPI Generator CLI templates | consumes | codegen | poor | **no** |

**Extend the existing emitter.** `registry.pl`'s `cli_command/3` already generates
`cli/0_inventory.ts`, and `bop.ts` already reads `HTTP_ROUTES` from it to build URLs.
The gap between today and "the CLI is generated from the spec facts" is small: emit the
commander `.command()/.argument()/.option()` declarations too, from
`http_operation` + `http_path_param` + `http_query_param`, with the handler bodies
staying hand-written. That is the same split `1_host_expand.pl` uses (plans as data,
execution hand-written) and the same split `4_http.ts` keeps today. **Default.**

**Restish.** Danielgtaylor's successor to `openapi-cli-generator`: it loads an API
description **at runtime** and turns every operation into a shell command, with
`x-cli-name` / `x-cli-aliases` / `x-cli-hidden` / `x-cli-ignore` extensions to shape the
surface, plus a documented streaming mode. Structurally the best answer to "CLI from
OpenAPI" that exists. Rejected for `bop` because **three of seven verbs are not routes at
all** — `serve` boots the process, `run` boots a process *and* posts to itself, `check`
never opens a socket (it spawns swipl). A runtime spec-driven CLI can express the other
four and nothing else, so `bop` would become two CLIs. **No** — but adopt its
**`x-cli-*` extension vocabulary** as the fact columns for CLI shaping, so a future
Restish user gets a usable CLI from our document for free.

**openapi-cli-generator.** Go/cobra codegen; its own README says it is superseded by
Restish. **No** — superseded by its author.

**OpenAPI Generator's CLI templates.** Same JVM objection as (a), and its CLI generators
are the least maintained corner of that project. **No.**

| candidate | version | result here |
|---|---|---|
| **@redocly/cli** | 2.41.1 | **installed and used**; `pnpm dlx`, no dependency added, full 3.1, structural `spec` rules + configurable rules |

## 2. Current surface, as it actually is

Read from `v6/tsv2/serve/4_http.ts` (410 lines) and `v6/tsv2/cli/bop.ts` (382 lines), not
from `registry.pl`'s existing `http_route/3` rows.

### HTTP: 5 routes, 5 operations, 14 responses

| method | path | request | 200 | other |
|---|---|---|---|---|
| POST | `/program` | `text/plain` .dl6 source | `{loaded, rels[], arrivalTargets[], hosts[], binds[{name,literals[]}]}` | 400 `{error}` |
| POST | `/arrivals` | `{batch:[{rel,sign,row[]}]}` | `{ticks:[{tick,line}]}` | 400, 409, 500 `{error}` |
| GET | `/idb/:rel` | — | `{rows: Row[]}` | 404, 500 `{error}` |
| GET | `/ticks` | — | `text/event-stream`, `data: <tick log line>` per tick | 404 `{error}` |
| GET | `/stats` | `?tables=a,b` | `{memory:{rssBytes,heapUsedBytes,externalBytes}, sqlite:{pageCount,pageSize,freelistCount,dbBytes,freelistBytes,dbstatAvailable,objectBytes[]}}` | 404, 500 `{error}` |

Plus a **catch-all** any other path → 404 `{error, routes: ROUTE_LIST}`. It is not an
operation (see §6 crack 2).

Shapes worth naming because they constrain the spec:

- `IRow = readonly (string | number | boolean)[]` — **positional**. No column names cross
  this boundary in either direction. `bop q` renders tab-separated rows with no header
  for exactly this reason.
- `ITickLogLine = string`. The `line` field of a tick report is *itself* a JSON document,
  carried as text. That is deliberate: the item-9 cross-target log contract grades by
  diffing those lines byte-for-byte against the oracle, so re-parsing them into the
  envelope would break the contract. The spec must say `string`, and say why.
- `sign` is a closed set `add | del`.
- Nothing on this surface returns `null`, matching the standing no-null ruling.

### CLI: 7 verbs

| verb | HTTP route used | generatable from the spec? |
|---|---|---|
| `serve` | — (boots the server) | no — process lifecycle |
| `run` | `POST /program`, then in-process events | partly — the POST, not the lifecycle |
| `check` | — (spawns swipl) | no — never opens a socket |
| `load` | `POST /program` | **yes** |
| `q` | `GET /idb/:rel` | **yes** |
| `stats` | `GET /stats` | **yes** |
| `ticks` | `GET /ticks` (SSE) | **yes**, modulo streaming (§7) |

4 of 7. This is the single most important inventory number for the CLI half of the arc:
a spec-driven CLI generator covers the client verbs and cannot express the other three.

## 3. Fact schema

Lab file: `v6/prolog/labs/openapi_codegen/0_facts.pl`. On landing these rows move into
`registry.pl` beside `cli_command/3` and the existing `http_route/3`, and the lab dies.

```prolog
http_operation(OpId, Method, PathTemplate, Summary).
http_path_param(OpId, Name, TypeExpr, Description).
http_query_param(OpId, Name, TypeExpr, Required, Description).
http_request_body(OpId, MediaType, TypeExpr, Required, Description).
http_response(OpId, Status, MediaType, TypeExpr, Description).

http_schema(Name, object, Description).
http_schema(Name, alias(TypeExpr), Description).
http_schema_field(Name, Field, TypeExpr, Required, Description).

api_info(Title, Version, Description).
api_server(Url, Description).
```

**Five tables, not five more columns on `http_route/3`.** Same reason `registry.pl` keeps
`surface/5` and `expression/5` apart: a route with no request body should not carry a
request-body column, and widening one row until it covers `/ticks` and `/program` at once
produces a row that is mostly `none`.

**`http_route/3` is subsumed.** `http_operation/4` carries the same
`(Method, Path, Summary)` plus an operation id; the existing generated
`cli/0_inventory.ts` `HTTP_ROUTES` array can be emitted from it unchanged, so this is
additive, not a migration.

**Path templates keep the SERVER's `:rel` spelling.** `4_http.ts` and the generated
inventory both use it. `{rel}` is OpenAPI's dialect and the emitter converts
(`path_template/2`). Target-neutral facts, target-specific emission — the same rule the
tsv2 plan term already follows.

### Type vocabulary

Reuses the existing column-type words (`0_type_plane.pl`: `int` / `text` / `bool` /
`float`) and adds only what a wire boundary needs that a stored column does not:

| TypeExpr | JSON Schema | note |
|---|---|---|
| `text` `int` `float` `bool` | `string` `integer` `number` `boolean` | unchanged words |
| `list(T)` | `{type: array, items: T}` | |
| `schema(Name)` | `{$ref: "#/components/schemas/Name"}` | |
| `enum([a,b])` | `{type: string, enum: [...]}` | `sign` |
| `one_of([...])` | `{type: [string, number, boolean]}` | `RowValue`; **3.1 only** |

Deliberately absent: `null`. Deliberately absent: `ref(Rel)` in the
`0_type_plane.pl` sense — a *relation* reference is a storage concept and crosses this
boundary as its canonical text, so the wire vocabulary does not need the word.

Field order is source order and is significant in the emitted property list, matching the
`decl_column_spelling` ruling for rel columns.

### The emitter

`emit_openapi.pl`, 229 lines, same shape as `2_emit_cli_inventory.pl`: an
`openapi_json_text/1` that builds the artifact in memory (so a test diffs it without
writing) plus `emit_openapi/0` that writes it. It owns the **dialect** — `{rel}`
templating, the `#/components/schemas/` pointer prefix, the 3.1 union spelling,
media-type nesting — and owns **no route, parameter, or schema**. Adding a route is
adding a fact.

Emitted document: 5 paths / 5 operations / 14 responses / 14 schemas / 13,130 bytes.
Two places it is 3.1-and-not-3.0, both named in the source: the `type: [..]` union for
`RowValue`, and `$ref` carrying a sibling `description` (legal under JSON Schema
2020-12; 3.0 needed the `allOf: [$ref]` workaround).

An unknown `TypeExpr` throws `unsupported_construct(openapi_type_unknown(T))` — the
refusal-by-absence discipline `registry.pl` already uses, so a typo in a fact is a named
failure and never a silently untyped field.

## 4. Parity gate

`v6/prolog/labs/openapi_codegen/2_parity.mjs`. The lift of
`tests/bopCommandInventory.test.ts` from CLI verbs to HTTP routes, with two more sources
available because a running server can be interrogated and a CLI cannot.

Four inventories, all normalized to `METHOD /seg/seg` with path parameters collapsed to
`*`:

1. **SPEC** — the emitted `openapi.json`'s paths × methods.
2. **ROUTE_LIST** — `4_http.ts`'s exported literal (what the catch-all 404 claims).
3. **DISPATCH** — the routing *conditions* parsed out of `4_http.ts`
   (`method === "M" && segments.length === N && segments[0] === "first"`). This is the
   only source that **cannot lie by omission**: a route that is served but listed nowhere
   still has a dispatch branch. The branch *count* is asserted (`=== 5`) as well as the
   set, so a route added in a different spelling fails loudly instead of passing
   silently.
4. **LIVE** — a real `serve/main.ts` process on an ephemeral port, asked for
   `/__parity_probe__`; the 404 body carries `routes`. Catches the case where the source
   parse is right and the running thing differs. No program needs loading: the route
   table exists before any program does.

**Why `*` and not the parameter name.** The dispatch conditions compare
`segments.length` and `segments[0]` and never name the parameter (`segments[1]!` is
passed positionally), so a parameter's *name* is not something the server source proves.
Comparing on `*` keeps each source honest about what it actually knows; the name is
pinned by the spec and by the generated `cli/0_inventory.ts` instead. Stated in the file
header rather than silently assumed.

**generate `ROUTE_LIST` from the facts** (it is a 5-element string array in a file that
already imports one generated module), turning legs 1↔2 from a check into an identity and
leaving legs 3 and 4 as the real gate. Card 8.

## 5. Axum sketch (post-flip)

One page, no rust written. Verdict from §1(b): **emit the router directly**, keep
`utoipa` as a fallback.

The same four fact tables feed a second emitter, `emit_axum.pl`, whose output is one
generated `.rs` — the same relationship `emit_ts.pl` has to the TS runtime today.

```rust
// GENERATED by v6/prolog/compile/emit_axum.pl from registry.pl. Do not edit.

pub fn router(state: ServeState) -> axum::Router {
    axum::Router::new()
        .route("/program",  axum::routing::post(load_program))
        .route("/arrivals", axum::routing::post(post_arrivals))
        .route("/idb/{rel}", axum::routing::get(read_relation))   // axum 0.8 brace syntax
        .route("/ticks",    axum::routing::get(stream_ticks))
        .route("/stats",    axum::routing::get(read_stats))
        .fallback(not_found)
        .with_state(state)
}

// from http_schema/http_schema_field, in field-declaration order
#[derive(serde::Serialize)]
pub struct ProgramLoaded {
    pub loaded: bool,
    pub rels: Vec<String>,
    pub arrival_targets: Vec<String>,   // serde(rename = "arrivalTargets")
    pub hosts: Vec<String>,
    pub binds: Vec<BindSummary>,
}

// handler SIGNATURES generated, BODIES hand-written in a sibling module —
// the split 1_host_expand.pl already uses (plans as data, execution by hand)
// and the split 4_http.ts keeps today.
async fn read_relation(
    State(state): State<ServeState>,
    Path(rel): Path<String>,
) -> Result<Json<RelationRows>, ApiError> { handlers::read_relation(state, rel).await }
```

**Why direct emission over utoipa.** With utoipa the chain is
facts → rust annotations → spec, and drift lives in the middle link; the emitted document
would then have to be diffed against the prolog-emitted one, which is a parity gate
between two *generators* rather than between a generator and a server. With direct
emission the chain is facts → {spec, router, structs}, three siblings from one parent,
and §4's gate (dispatch branches parsed from the generated `.rs`, plus the live 404
probe) transfers unchanged — the DISPATCH leg's regex changes shape, nothing else does.

**Where utoipa wins and it is worth saying.** `utoipa-axum`'s `routes!` macro makes it
structurally impossible to serve a route that is absent from the spec, because one call
does both registrations. Direct emission gets the same guarantee only because the gate
enforces it. If the gate is ever weakened, utoipa is the safer default.

**What the flip does not change.** Parameter names in path templates (`{rel}` is axum
0.8's syntax too, same braces), the positional `Row` shape, and the SSE route (§7) —
axum's `Sse<S>` response type is a direct fit for `text/event-stream`, arguably cleaner
than node's manual `response.write("data: ...\n\n")`.

**Client half.** `progenitor` generates a rust client from the same `openapi.json` via
`build.rs` or `cargo-progenitor`, so a rust `bop` and a node server (or the reverse,
mid-flip) are graded against one document. That is the one rust dependency worth buying
outright.

## 6. SSE / streaming, honestly

`GET /ticks` is the sore spot and it does not have a clean answer in 3.1.

**What the spec can say.** OpenAPI 3.0 and 3.1 have **no native SSE support**. The
representable form is a response with content type `text/event-stream` and a schema —
which is what this emitter produces:

```json
"200": { "description": "one `data: <tick log line>` frame per tick until the client
                         closes the socket.",
         "content": { "text/event-stream": { "schema": { "type": "string" } } } }
```

That is honest and it is nearly useless. `type: string` describes the *wire bytes*, not
the frames, and says nothing about the fact that each frame's `data:` payload is itself a
JSON tick-log line. Every consumer has to be told out of band.

**What codegen tools do with it.** Uniformly badly, and this is documented across the
ecosystem rather than being our problem alone: openapi-generator has open issues for SSE
support in multiple languages; huma emits `null` types for SSE outputs that then break
downstream generators like orval; oapi-codegen needed a fix to stop mangling streaming
responses; `$ref`-ing an SSE schema null-pointers the spring generator. The safe
assumption is that **any generated client will treat `/ticks` as returning a string body
and will buffer it** unless hand-corrected — which is exactly what `bop ticks` already
does correctly by hand (`Readable.fromWeb(response.body)` and copy chunks to stdout).

**What actually fixes it: OpenAPI 3.2.** 3.2.0 introduces `itemSchema` for
`text/event-stream` media types, giving first-class per-event structure. When the toolchain
supports 3.2, the `TickReport`-shaped payload becomes expressible and the frames become
generatable. Until then this is a known, named gap.

**The call taken here.** Emit the 3.1-legal form, describe the frame shape in the
`description` prose so a human reader gets it, and **do not generate a client for
`/ticks`** — keep `bop ticks`'s hand-written streaming read and mark the operation so a
future generator skips it (Restish's `x-cli-ignore` vocabulary, or our own). Card 7.

Second, smaller streaming note: `POST /program`'s 200 is written **last**, after the tick
loop, host effects, and bind timers are all subscribed, so a client reading
`loaded: true` cannot beat the tick loop into existence. That ordering is a real part of
the contract and OpenAPI has no way to say it. It lives in the `description`.

## 7. Cracks found while building this

1. **`serveFailure` can answer with no body at all.** If a branch raises *after*
   `headersSent` (the SSE path being the realistic case), the handler calls
   `response.end()` with no JSON. The spec says every response has content. Small, real,
   and unowned.
2. **The catch-all 404 is unspeakable.** `{error, routes: [...]}` is a different shape
   from every described `{error}` body, and `Error` is emitted with
   `additionalProperties: false`. No described operation returns it (verified: all three
   404 sites in `4_http.ts` return `{error}` alone), so the document is not lying — but
   the spec cannot describe what the server does for an unknown path, which is the one
   route every client hits first when it is wrong.
3. **`GET /idb/{rel}` is only typeable in the abstract.** `rel` is any rel the *loaded
   program* declares, and `Row`'s width is that rel's arity. A static document can say
   `array of RowValue` and nothing more. See card 6 — a per-program spec is expressible.
4. **`bop.ts` casts unchecked**: `JSON.parse(text) as { rows: readonly IRow[] }`. Today
   nothing checks that the server agrees. openapi-typescript output would make that cast
   a checked annotation at zero runtime cost.
5. **`ROUTE_LIST` and the dispatch branches are two hand-kept lists in one file.** They
   agree today (the gate proves it), and nothing structural keeps them agreeing. Card 8.
