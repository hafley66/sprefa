### Proposal 1: merge-lane-closeout (coverage 130+39+50 = 219)

````markdown
---
name: v6-merge-lane-closeout
description: Integrate a merged lane back onto main in the v6 repo. Re-run the
  lane's claimed receipts on the merged tree, regen the generated artifacts,
  write the ARCH.pl + ledger rows, pass the arch gate. Trigger when a merge
  commit lands that touched v6 (subject begins with "merge" or "Merge").
---
# v6 merge-lane close-out

A lane's merge commit is not done until its receipts hold on the merged tree.

## Steps
1. Confirm branch is main and the merge is clean. Resolve merge conflicts one
   file at a time; keep both halves together per the measured receipt.
2. Re-run the receipts the lane claimed, on the merged tree, from
   `v6/justfile`. Do not trust the lane's in-branch numbers.
3. Regenerate every generated artifact: run `just sweep` (manifest + gen
   artifacts), refresh SCOREBOARD and the `justfile` expect comments, and rerun
   any `door-handwritten` / `dl_view` / INDEX that the merge touched.
4. Run the standing suite and record the exact numbers in the commit message:
   conformance, plunit, TEXT_DOOR, roundtrip, sweep both modes, compile-speed.
5. Write ARCH.pl rows (done vs in-flight vs defect) and the ledger block.
6. Run `just arch` and confirm green before committing.

## Validate
- `just green` then `just green-all` (or the subset the lane touched).
- Ship only the receipts you re-ran, with the numbers you measured on main.
- Emerald (green) before commit; exit 0.

## Never
- Do not claim a receipt you did not re-run on the merged tree.
- Do not skip the sweep regen; a stale generated artifact is its own defect
  class (the staleness gate exists because this recurs).
- Do not rabbit-hole into the lane's unresolved design fork; file it as an
  ARCH/ledger row and stop.
````

### Proposal 2: lab-lifecycle (coverage 119)

````markdown
---
name: v6-lab-lifecycle
description: Run a v6 hypothesis lab end to end, from scaffolding to grading to
  land-or-death. Trigger on any "lab:" / "lab death" / "verdict" shape, or when
  a user word requires lab-first before production code.
---
# v6 lab lifecycle

Labs prove a hypothesis before any production surface changes. Every lab lands
(folds into production) or dies (is deleted), never lingers silently.

## Steps
1. Scaffold under its lab dir: `v6/prolog/labs/<name>/` or `v6/tsv2/labs/`.
   Write the header doc `plans/YYYY-MM-DD-<name>-header.md` first: hypothesis,
   the receipts that would confirm it, the two doors (prolog and tsv2).
2. Build `receipts.sh` that grades the claim against BOTH doors and exits 1 on
   any wrong/ungraded/missing proof. Record a sabotage receipt (deliberately
   break the claim, confirm the run goes red, restore).
3. Run the graded corpus. Publish a verdict `plans/YYYY-MM-DD-<name>-verdict.md`
   that states what held, what was refuted, and the follow-up ruling.
4. Land: fold the lab into production per protocol, or delete it. On lab death,
   record the last copy sha in the verdict (e.g. "last copy <sha> in <merge>").
5. Write the ARCH + ledger rows for the landing.

## Validate
- `receipts.sh` green; verdict doc exists; the lab dir is folded or deleted.
- `just green` still passes after the fold.

## Never
- Do not let a lab linger silently with no verdict and no death.
- Do not delete a lab without recording the last copy sha.
- Do not claim "landed" while the dir still lives or the verdict is unwritten.
- Do not skip the user word: some arcs are lab-first by directive.
````

### Proposal 3: fixture-golden (coverage 82)

````markdown
---
name: v6-fixture-golden
description: Add a conformance fixture, a golden gate, a coverage row, or a
  program promotion into green-all for v6. Trigger on conformance/fixture/
  golden/coverage/gate/PASS/promote shapes.
---
# v6 fixture-golden

Every construct and every fixed defect deserves a fixture that is red before it
is green, and a gate that would catch the regression forever.

## Steps
1. Add fixtures under `v6/prolog/conformance/fixtures/` (prolog door) and the
   matching golden under `v6/tsv2/goldens/` (tsv2 door). Use the per-surface
   junction convention (LANG-JUNCTION / door comment) from the repo skills.
2. Make the fixture fail-first: confirm it is RED before the fix or feature
   (the sabotage receipt), then GREEN after. A gate that was never red does not
   count.
3. Wire a `just` recipe for the fixture and add it to `green` or `green-all`.
4. Refresh the coverage account and the SCOREBOARD / justfile expect comments.
5. Re-run `just sweep` so the manifest and generated artifacts match.

## Validate
- `just green` / `just green-all` on the touched subset; `just sweep`;
  `just staleness-gate`.
- The new gate must have a recorded red before its green.

## Never
- Do not promote a golden that was never observed red (no sabotage receipt).
- Do not add a coverage row without literally counting it (numbers, not
  adjectives).
- Do not let a generated artifact drift; the staleness gate is a standing law.
````

### Proposal 4: ruling-refusal (coverage 72)

````markdown
---
name: v6-ruling-refusal
description: Record a semantic ruling or convert a silent miscompile into a
  named refusal, on both doors, in v6. Trigger on ruling(np)/refusal shapes.
---
# v6 ruling-refusal

Semantics are pinned as rulings. Every silent wrong answer becomes a named
refusal at BOTH doors with a fail-first fixture.

## Steps
1. Write the ruling into the rulings registry / a plans doc (repo `rulings`
   convention), naming the executive: "RULED semantics executed".
2. Add the named refusal clause to the prolog door AND the tsv2 door. One door
   alone is a divergence, which is itself a defect.
3. Write a fail-first fixture that is RED while the behavior is silent-wrong
   and GREEN when the refusal fires.
4. Confirm the two doors agree byte-for-byte on the new refusal (no
   mode-disagreement).
5. Log the ruling + defect row in ARCH + ledger.

## Validate
- `just conformance`, `just text-door`, `just roundtrip`, `just sweep`.
- Both doors identical for the new refusal; exit 0.

## Never
- Do not add a refusal to only one door.
- Do not read a relation by a literal string name (the no-magic-rels law).
- Do not leave a silence: named refusals over silent-empty, every time.
````

### Proposal 5: perf-fix (coverage 60)

````markdown
---
name: v6-perf-fix
description: Repair a compile-speed / clock / perf regression in v6 with a
  stated root cause and measured receipts. Trigger on perf / clock check /
  parse-phase cost / compile trace / soak shapes.
---
# v6 perf-fix

A perf regression is fixed with a named suspect and receipts, never vibes.

## Steps
1. Reproduce through the gate first: `just compile-speed`, golden-flex parse,
   or the clock checker, and capture the regressed number.
2. Profile to name the suspect (the compile trace / per-phase timing is
   always-on for this reason). State the root cause in the commit, e.g. who
   called what how many times and why it is the wall.
3. Fix it. After the fix, re-run the full receipts and report the before/after
   with their arithmetic (inference counts, wall ms, fold change).
4. If a baseline cannot be met, rebaseline ONLY the rows that moved, with the
   deviation and arithmetic stated in the commit. Never move untouched rows.
5. Confirm no sibling row regressed inside the acceptance band.

## Validate
- `just compile-speed` (regressions=0), `just conformance`, `just plunit`,
  `just text-door`, `just sweep` both modes.
- The commit names the suspect and states the arithmetic.

## Never
- Do not claim a fix without a named root cause in the message.
- Do not silently rebaseline a moved baseline; state the deviation and why.
- Do not fix something you did not reprodure via the gate.
````

### Proposal 6: defect-fix-fail-first (coverage 48)

````markdown
---
name: v6-defect-fix-fail-first
description: Fix a v6 defect the repo's native way: write the failing fixture
  first, prove it red for the right reason, then fix. Trigger on fix/defect/
  D1..D8 / F1..F8 shapes.
---
# v6 defect-fix, fail-first

The repo's defect shape (D1..D8, F1..F8, plus named defects) fixes in a fixed
order: red first.

## Steps
1. Write the fail-first fixture that reproduces the defect. Verify it is RED,
   and confirm the red is for the defect asked for, not a coincidence (a red
   that does not test the right behavior does not count; verify by the
   discriminating assertion, exact-count + wrong-file where shape is ambiguous).
2. Fix BOTH doors if the construct exists on both. Check the fixture is GREEN.
3. Run the standing battery for the touched surface.
4. Record the defect row in ARCH + ledger and close it in the message.

## Validate
- `just green` on the touched subset; `just sweep` both modes `0 wrong`.
- The fixture is red before, green after; the discriminator actually
  discriminates (prove by the sabotage that it would catch the leak).

## Never
- Do not fix without the red first (no green without a red is the standing
  rule).
- Do not delete or weaken a red to make it pass.
- Do not remove a test that pins failed behavior; it is the regression rail.
````

## 5. The miner script

Recomputes every taxonomy count in this file from `git log`. bash + awk only,
no gawk, no python, runs in well under 10s (measured 0.014s on 926 rows).

```bash
#!/bin/bash
# Recompute v6 task-shape taxonomy from git log. Runs in <1s. bash+awk only.
# Usage: miner.sh [shas-subjects.tsv]   (default /tmp/v6_hash_subj.tsv; regenerated if absent)
set -u
IN="${1:-/tmp/v6_hash_subj.tsv}"
if [ ! -f "$IN" ]; then
  git -C /Users/chrishafley/projects/sprefa log --format='%H%x09%s' -- v6/ > "$IN"
fi

# NOTE: BSD awk has no \b and no gawk-only fns, so word boundaries are written as
# (^|[^A-Za-z0-9_]) X ([^A-Za-z0-9_]|$). Priority = first match wins (cascade).
awk -F'\t' '
function sh(s){
  if (s ~ /^[Mm]erge/) return "merge-closeout"
  if (s ~ /comment[[:space:]](sweep|trim|rails)|narration|change-log|incident-history/) return "comment-sweep"
  if (s ~ /verdict|lab-death|lab[[:space:]]death|(^|[[:space:]_\/.-])labs?([[:space:]:_,.\/]|$)/) return "lab"
  if (s ~ /(^|[[:space:]_\/.-])extract([[:space:]:_,.\/]|$)|Resolve<|TypeF|CallF|DfF|ast-grep|madge|scip-typescript/) return "extract-port"
  if (s ~ /rulings?|refus/) return "ruling-refusal"
  if (s ~ /(^|[[:space:]_\/.-])fix([[:space:]:_,.\/]|$)|defect|(^|[[:space:]:])(D[0-8]|F[1-8])([[:space:]:]|$)|repair|error-recovery/) return "defect-fix"
  if (s ~ /perf|bench|clock[[:space:]]check|profil|measure|latency|parse-phase|compile[[:space:]]trace|soak|inferences|parse[[:space:]]regression/) return "perf-fix"
  if (s ~ /regen|manifest|SCOREBOARD|door-handwritten|dl_view|generated|run-results/) return "sweep-regen"
  if (s ~ /(^|[[:space:]_\/.-])ledger([[:space:]:_,.\/]|$)|close-out|^ARCH|scoreboard|expect[[:space:]]comments/) return "arch-ledger"
  if (s ~ /conformance|fixture|golden|coverage|gate|ratchet|PASS|promot|green-all|stopping-point/) return "fixture-golden"
  if (s ~ /atlas|self-map|flowchart|render|diagram|MAP\.md|visual|flow_edge/) return "diagram-atlas"
  if (s ~ /redteam|red-team|adversarial/) return "redteam"
  if (s ~ /tsv2:|feat\(|docs\(|emitter|compiler|lower|runtime|serve|construct|\.dl6|(^|[^A-Za-z0-9_])(E[0-7]|G[0-7]|M[0-9]|P[123]|R[0-9]|I[0-9])([^A-Za-z0-9_]|$)|board|epic|seed/) return "engine-build"
  if (s ~ /brief|plans:|header/) return "plan-brief"
  return "other"
}
{ c[sh($2)]++ }
END{
  n=split("merge-closeout comment-sweep lab extract-port ruling-refusal defect-fix perf-fix sweep-regen arch-ledger fixture-golden diagram-atlas redteam engine-build plan-brief other",ord," ");
  printf "%-18s %6s\n","SHAPE","COUNT"
  for(i=1;i<=n;i++) printf "%-18s %6d\n", ord[i], c[ord[i]]
  t=0; for(k in c) t+=c[k]; printf "%-18s %6d\n","TOTAL",t
}' "$IN"
```

Verified: on this repo the script prints the 14 counts and TOTAL 926 in
0.014s. To rerun forever, save it, run `miner.sh`, and compare the table
against section 1.

## 6. What the taxonomy could not classify (residual)

Residual is 111 of 926 (12.0%). The `other` bucket is not noise; it is several
small-but-real recurring activities I chose not to promote to shapes because
each is below 2% and none would change the ranking:

- Single-word pull-request-style commits (`feat(v6)`, `docs(v6)`, `chore`,
  `PASS`, `test:`, `wip`, `checkpoint`, `board`, `epic`) that are progress
  markers rather than a named ritual. These cluster in the early v6/dl M1..M9
  and v6/store G-series epochs (1ad0029e, 6bd491ac).
- Milestone and program-tracking commits (M8 closure, M9 dispatched, board
  rows) that got classified as `other` because they carry no other shape
  keyword (76bfea51 "cuts grade HOLDS", and the board/epic markers that the
  word-boundary rule did not catch).
- Session and research artifacts: `chat_log: session save ...`, `DEVLOG.md`,
  `SESSION-DIGEST`, `SELF-RESEARCH`, `v6 plan / seed / docs` early-arc commits.

Caveats on the method, stated so the counts are not oversold:

- A commit is assigned exactly one shape by cascade. A single sentence like
  "merge ... + ledger + ARCH + sweep regen" lands as merge-closeout and its
  ledger/regen freight is invisible in the count but visible in the
  co-occurrence table (section 3).
- The topology successor analysis and the taxonomy table both use the same
  shape set but the Python reference classifier used for the successor/edges
  analysis drifts up to a few commits per shape from the awk miner (word
  boundary handling). The counts in section 1 are the awk-miner numbers, which
  are the reproducible ones; the edge counts in sections 2 and 3 are from the
  near-equivalent Python run and should be read as the shape-level topology,
  not precise to the unit commit.
- `git log` subjects only were classified. Full message bodies would raise the
  co-occurrence and successor fidelity but add little to the ranking, which is
  dominated by subjects that already state a ritual.
