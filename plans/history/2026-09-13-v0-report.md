## 1. What v0 was

Rust plus SQLite, run over 500-plus polyglot repos at work. Your summary of the
question it asked: "Can string fts5 get me far for refactoring and code
queries". The storage was four tables you later wrote out from memory:
`strings(id, value, norm, norm2)`, `refs(id, byte_range, string_id, file_id)`,
`file(id, path, content_hash)`, `file_repo(file_id, repo_id, rev_id)`. Every
string in every file got extracted, normalized twice (punctuation and digits
stripped, lowercased), interned, and put behind an FTS5 trigram index so that
cross-repo linking was a fuzzy match on `norm` rather than a typechecker.

On top of that sat a rule language whose bodies nested and piped:

```
rule xuz > {
  repo("a") > rev("a") > fs("a") > json({special json syntax})/ast({extension of ast-grep pattern lang})
}
```

Each rule auto-schemaed a wide SQLite table from its capture set. A second form,
`query(x) { ... }` "looked like datalog", and you stopped it to focus on
parse-to-SQLite. Parsers were oxc for TS and syn for Rust, ast-grep elsewhere,
with per-repo ignore patterns and a programmable `norm2`. A git-on-disk watcher
kept it fresh, and an LSP over the SQLite cache showed, for any string, file,
import or export, which files referenced it "within %% certainty", plus `$X`
capture hover. A full run over 500 repos took about 2.5 minutes, faster in
release. The point was super-refactor: rename or move something and see the
cross-repo breakage, `openapi.json` codegen included, in real time.

Unknown: the repo name, the exact `norm2` algorithm, what the colon-prefixed
literals looked like, and whether any of it still runs. No v0 source file exists
on this machine under any name I could find.

Two cautions. "v0" in many chat logs means the first milestone of whatever
version was being built that day (`20260506.0:77`, `20260426.10:134`).
And `book/what-if/03-the-nested-dsl-spirit.md` attributes `rule(name) { ... }`
blocks to "the v0 prototype (spring 2026 archive)", where that archive is v1 and
v2; its reading of the syntax still matches your own account.

## 3. What v1 kept from v0 and what it changed

Kept, from `git show 343a029de` and the birth-day README: the four-table core
(`repos`, `files`, `strings` with FTS5 trigram, `refs` with byte spans),
normalize-for-fuzzy-match, cross-repo import resolution, the daemon plus watcher
plus rename plan, oxc and syn, per-repo and per-branch filter config, the name.

Changed: extraction rules moved out of hand-written Rust into data. v1's first
pass was a JSON-schema rule format, replaced within a week by the `.sprf` text
DSL with `rule(name) { ... }` bodies, `>` selector chains, JSON destructuring
and `link()` declarations. v1 added the `matches` and `match_links` tables,
the part v0 did not have: a place to say that two strings in different repos
mean the same thing, under a named link predicate. What you called "crude and
highly connected" became 14 crates.

## 4. v0 ideas still alive in v7 and v8

- Every string interned, consumers read decoded views, never the integer.
- Refs as physical coordinates: repo, rev, file, byte range.
- File identity is the git blob oid for committed bytes, blake3 for dirty ones.
- A rule is a table declaration; its captures become the columns.
- Writes go in bulk batches, never one row at a time in a loop.
- Progressive refinement through a chain, now term-form ops joined on a shared
  variable rather than `>`.
- Colon-prefixed literals, dropped after v0 and brought back in v5.
- The `query(x)` form that "looked like datalog", which is now the whole engine.
- No machine learning. Deterministic pattern matching and statistics only.
- Reverse refs and blast radius from a byte, bounded against dumping.
- 500 polyglot repos as the sizing target, and a full run measured in minutes.
