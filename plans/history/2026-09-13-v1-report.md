## 1. What v1 was trying to be

The README says it in your words: "You touch 30 repos a week. You `cd` into one, grep for a string, find it references something in another repo, `cd` there, grep again, open a YAML, squint at an image tag. That loop eats hours every day. sprefa encodes that loop into declarative rules and runs it across all your repos at once. Every captured string lands in a SQLite table. The connections between repos become SQL joins." A cross-repo string index, an extraction language on top, and a watcher that rewrote imports when you moved a file.

## 2. The language

Two statement kinds: `rule(name) { body };` for rows, `check(name) { SELECT ... };` where returned rows are violations. A body chains selector tags with `>`, narrowing repo to revision to folder to file to structure to text. Each `$VAR` became a column in that rule's table; captures from one site shared a `group_id`. Braces forked into independent branches, and naming another rule inside a body bound its columns and created a dependency edge.

Cargo and npm, from `sprefa-rules.sprf`:

```sprf
rule(package_name) {
  fs(**/Cargo.toml) > json({ package: { name: $NAME } })
};

rule(dep_name) {
  fs(**/Cargo.toml) > json({ re:^(dev-)?dependencies: { $NAME: $_ } })
};

rule(tsconfig_path) {
  fs(**/tsconfig.json) > json({ compilerOptions: { paths: { $ALIAS: [...$TARGET] } } })
};
```

The three-level cross-repo chase, from `EXAMPLES.sprf`, the whole pitch in twelve lines:

```sprf
rule(deploy_ref) {
  fs(**/values.yaml) > json({ image: { repository: $REPO, tag: $TAG } })
};

rule(internal_dep) {
  deploy_ref(repo: $REPO, rev: $TAG) {
    fs(**/package.json) > json({ dependencies: { $DEP: $SPEC } })
  }
};

rule(lock_pin) {
  internal_dep(dep: $DEP, repo: $REPO) {
    fs(**/package-lock.json) > line($DEP.*resolved.*#$PINNED_REV)
  }
};
```

Dogfooding, from `self_check.sprf`, which kept the README in sync with the source:

```sprf
rule(lsp_tag) {
  fs(crates/sprf-lsp/src/main.rs) > ast[rust](("$TAG", $$$_))
};

rule(readme_tag) {
  fs(**/README.md) > md(### Selector tags) > line(re:`$TAG\()
};

rule(code_cmd) {
  fs(crates/cli/src/main.rs) > line(re:^\s+$CMD\s*[\{,])
};
```

## 3. The engine

Rust, fourteen crates, SQLite through sqlx, tokio for async. Files came out of git via libgit2 tree walks instead of a `git ls-files` subprocess, so bare clones and any branch worked without a checkout. Extraction ran under rayon with xxh3 hashes skipping unchanged files and touched no database: `index::scan_repo()` returned plain `Vec<FileRefs>`, and the cache wrote deltas in one transaction per repo. Four extractors fed one `RawRef` shape: oxc for JS/TS imports, syn for Rust use paths, the rule walker for JSON/YAML/TOML, ast-grep for tree-sitter grammars.

Evaluation was batch with a fixed-point outer loop. Rules were topologically ordered; a rule capturing a repo and a revision made the scanner check that repo out at that tag, scan it, and go around again until nothing new appeared, capped at ten rounds (`crates/cli/src/main.rs:735`). Incrementality meant hash skipping, `scan_diff(old_sha)`, and a `notify` watcher correlating moves by content hash and renames by span proximity, then planning import rewrites.

Three files carry the weight: `crates/sprf/src/_3_lower.rs` (1498 lines, lowering parsed `.sprf` into executable rules), `crates/rules/src/extractor.rs` (827 lines, walk-match-emit), and `crates/schema/src/migrations.rs`, holding `repos`, `files`, `strings` with an FTS5 twin, `refs`, `rev_files`, `repo_revs`, `discovery_log`, `invariant_violations`, plus one generated table per rule.

```d2
direction: right

sprf: ".sprf rules" {shape: document}

repos: "registered repos\n(git2 tree walk)" {shape: cylinder}

  js: "js (oxc)"
  rs: "rs (syn)"
  rules: "rules: tree walk\njson/yaml/toml"
  sg: "ast-grep"
  line: "line / comment / md"
}

sprf -> parse -> extract.rules
repos -> index -> extract

```

## 4. What it could do by the end

Eleven CLI subcommands worked: `init`, `add`, `scan`, `daemon`, `watch`, `serve`, `query`, `check`, `sql`, `eval`, `status`. The `eval` path ran a rule against files or stdin with no database. A VS Code extension shipped with a TextMate grammar and an LSP client doing diagnostics, hover, tag completions, rule-scoped capture completions, cross-rule names, and gitignore-aware file and folder completions.

The battery was 527 test attributes, anchored on `crates/sprf/tests/fixtures/kitchen_sink.sprf`, 392 lines whose header reads: "This single file exercises EVERY parser feature, every matcher, every emit pattern." Four end-to-end suites backed it: `kitchen_sink_e2e.rs`, `discovery_e2e.rs` (the demand loop), `sprf_meta_e2e.rs`, `full_stack_e2e.rs`.

You wrote down no performance numbers. Every quantity in the docs is a threshold you picked: 100ms for move correlation, 64 bytes for rename span proximity, 10 discovery rounds, a sub-100ms query target in `docs/periscope.md`.

## 5. Why it ended

The last fifteen commits are all LSP repair: hover, completions, git-root detection from subdirectories, cross-ref capture ranges, folder completion limits, alphabetical sorting. The editor was eating every session.

The final commit is a plan rather than code, `chat_log/20260412.12.diagnostic-redesign-plan.md`. Its root cause section says the analyzer "GUESSES what's wrong instead of scanner reporting it", names `check_json_path_mismatch()` sampling files to invent an error message, and notes "Multiple scan_file functions exist but are unused (dead code)". Your requirement was blunt: "LSP does NO parsing/analysis, just displays what scanner reports" and "No guessing". Every operator owning its own diagnostics was a shape the v1 pipeline had nowhere to put.

The same day you dumped `NOTES.md`, opening with "i want to take this sprefa repo and add every tool i have ever wanted, they all involve parsing". Shell integration, codegen into comment ranges, let bindings, and Feature 5, which rewrote the engine as RxJS on paper: "there are no types of data (files vs content vs rows vs captures), there is cursor", every tag the same shape of cursor in and cursors out, rule streams as ReplaySubjects. A four-stage walk-transform-emit pipeline had no room for that.

Two days later `20260413.0.zero-copy-store-effects` locked v2, and the first v2 commit calls itself "a fresh pipeline/op runtime with the same Reader/Writer layer abstractions as v1 but grown from a clean schema", landing as a parallel module under `v2/`. v1 was left standing and stopped receiving commits.

## 6. What survived

- The tag vocabulary: `fs`, `json`, `line`, `ast`, `md`, `comment`, `repo`, `rev`, `folder`, and the `>` chain.
- `$VAR` as capture and column at once, one table per rule.
- SQLite as the single store, SQL as the query surface you never wrapped in a DSL.
- `check(name) { SELECT ... }` with rows as violations, ancestor of the rails.
- ast-grep as structural matcher (`src/sg.rs` in v5) and per-filetype extraction (`v6/sprefa-extract/src/lang/`).
- The v1 table set, preserved by explicit v2 decision: repos, revs, files, strings, refs, rule_data.
- Feature 5's RxJS framing became v2's Cursor and `Op::pipe`, and the law that design talk uses rxjs, prolog, or SQL words.
- Demand scanning over repo and revision became the org-wide GitHub watcher.
- The LSP ambition, still the feature that outruns the engine.
- Unknown from this tree: whether any v1 Rust file survives verbatim later. v6 has no `Cursor`, so even the v2 spine stopped short of today's runtime.
