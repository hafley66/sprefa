1. The problem both solve

You have a query over some data. The data changes. Recomputing the whole query from scratch on every change is the naive answer, and it is what most systems do.

Incremental View Maintenance is the alternative: given a change to the input, compute only the corresponding change to the output. The hard part is that this must work for every operator, including joins, aggregations, and recursion, and the deltas must compose so a hundred-operator query still only touches what moved.

DBSP and Differential Dataflow are two answers. They were built by overlapping people. Frank McSherry is an author on both.

2. The shared core: Z-sets

This is the one idea. Learn it and both systems open up.

A Z-set is a relation where every row carries an integer weight. Not a boolean "present / absent". An integer, and it is allowed to be negative. 
ordinary set        Z-set
------------        -----------------
{ alice }           { alice: 1 }
{ alice, bob }      { alice: 1, bob: 1 }
                    { alice: 2 }        alice, twice (a multiset)
                    { alice: -1 }       a RETRACTION of alice

A change to a collection is itself a Z-set. Inserting bob and deleting alice is one value:

delta = { bob: +1, alice: -1 }

Applying a change is just addition, weight by weight. Rows that reach weight 0 vanish.

Why this matters: Z-sets form an abelian group. There is a zero, addition is associative and commutative, and every element has an inverse. That last property is what ordinary sets lack, and it is exactly what lets you subtract one state from another to get a change.

Operators are then classified by how they interact with +:

classpropertyexamplesconsequence
linearf(a + b) = f(a) + f(b)select, project, mapthe delta of the output is just f of the delta. Free.
bilinearlinear in each argument separatelyjoinneeds the product rule; must remember past state
neither—distinct, min/max, aggregationneeds bespoke incremental treatment

The join case is worth seeing, because it is where both systems spend their engineering. From the product rule:

Δ(A ⋈ B)  =  ΔA ⋈ B_old  +  A_old ⋈ ΔB  +  ΔA ⋈ ΔB

To compute a join's delta you must have A_old and B_old on hand. That stored, indexed history is the thing DD calls an arrangement and DBSP calls an integrator, and it is the main memory cost of both.

3. DBSP: streams and circuits Feldera

DBSP models everything as a stream: a value for each tick of a clock, S : ℕ → A. A query becomes a circuit of operators wired together, and it is evaluated tick by tick.

Three primitives carry the whole theory:

operatormeaningdefinition
z⁻¹delay by one tick(z⁻¹ s)[t] = s[t-1], and 0 at t=0
Ddifferentiate: stream of changesD(s)[t] = s[t] − s[t−1]
Iintegrate: running totalI(s)[t] = s[0] + s[1] + … + s[t]

D and I are exact inverses. That is the hinge of the whole system.

The incrementalization theorem. For any query Q, its incremental version is QΔ = D ∘ Q ∘ I. You do not design an incremental algorithm. You derive one.

On its own that would be useless, since it just rebuilds the whole collection at I and runs Q in full. The payoff is the chain rule:

(Q₁ ∘ Q₂)Δ  =  Q₁Δ ∘ Q₂Δ

Incrementalization distributes over composition. So you push the transform down into each operator, the inner I/D pairs cancel, and what survives is a circuit where linear operators became free and only the bilinear ones kept an integrator. That cancellation is the actual engineering win.

Recursion is handled by nesting a circuit inside another with its own faster clock. The outer clock ticks once per input batch; the inner clock runs the fixpoint to convergence. Semi-naive evaluation falls out of applying the same incrementalization inside the inner loop.

4. Differential Dataflow: partially ordered time Timely

DD starts from the same Z-sets and asks a different question: what if time is not a single line?

A collection in DD is a set of triples:

(data, time, diff)

("alice", (epoch=3, iter=0), +1)
("alice", (epoch=7, iter=0), -1)

The collection's contents at any time t is the sum of all diffs whose time ≤ t. Since time is drawn from a lattice rather than a line, "≤" is a partial order: two times can be incomparable.

That is the entire reason DD exists. Recursion needs an iteration counter, and streaming needs an input epoch, and DD makes them independent coordinates instead of forcing one inside the other.

Two ideas do the heavy lifting:

Frontiers

A frontier is a set of mutually incomparable times representing "nothing earlier than this will ever arrive again". Timely Dataflow's progress tracking computes and broadcasts frontiers, and that is what tells an operator it may finally emit a result, or compact old state away. Progress tracking across a distributed cluster is essentially all of what Timely provides.

Arrangements

An arrangement is an indexed, compacted, shared trace of a collection's history. Several downstream operators can read one arrangement rather than each keeping its own copy of the same index. For join-heavy dataflows this is the difference between practical and not, and it has no direct DBSP counterpart at the API level.

5. Where they agree

  • The algebra is identical. Z-sets, integer weights, negative weight means retraction.
  • Deltas, not recomputation. Both compute changes and compose them through the operator graph.
  • Linear operators are nearly free, joins need remembered state, aggregation and distinct need special handling. Same taxonomy.
  • Both do recursion / fixpoint, and both end up doing semi-naive evaluation, arrived at from different directions.
  • Both are single-writer, batch-tick systems at the core: you hand them a batch of changes, they hand you a batch of output changes.
  • Overlapping authorship. McSherry is on the 2013 DD paper and the 2023 DBSP paper.

6. Where they diverge

axisDifferential DataflowDBSP
time a lattice, partially ordered, multi-dimensional a total order, one clock per circuit
recursion add a coordinate to the timestamp nest a circuit with its own faster clock
how you get incremental operators are written incrementally by hand, each one designed against the trace model derived mechanically: QΔ = D ∘ Q ∘ I plus the chain rule
formal style operational; correctness argued per operator denotational; the paper carries proofs about circuits
shared state arrangements are explicit, first-class, shared across operators integrators live inside operators
runtime Timely Dataflow: multi-worker, distributed, frontier progress tracking circuit evaluation, single-node oriented
out-of-order input native. Incomparable times need no ordering the clock is sequential; late data is an application concern
front door a Rust API you build dataflows with SQL, compiled to a circuit by Feldera
Naming, since it will end up in our identifiers. The algebra is Z-sets. The circuit theory is DBSP. Feldera is the company shipping the dbsp crate. There is no such thing as "Feldera algebra".

The name dd-runner is misleading and worth fixing. It runs a "dd plan" and contains none of the algebra described above. Its dependencies are rusqlite, serde, serde_json. Any performance number attributed to "dd" in PERF-REPORT.md belongs to the differential-dataflow library oracle in sprefa-store, on a different benchmark, not to anything our compiler emits.

Our kernel currently has, in the vocabulary above: no signed weights (the relation type is BTreeMap<String, Vec<Tuple>>), no arrangements, no timestamps. Those are the three named unbuilt forks in ARCH.pl. Reading this page top to bottom is roughly the roadmap for closing them.
