# Job queue — decompose the tick, stop the everything-lock

## Survey verdict (2026-07-16, WebSearch-verified)

No turnkey Rust job queue fits. Disqualified: underway/graphile (Postgres server),
faktory-rs (external server), sidekiq-rs/backie (Redis). The two hard
requirements — pending-dedup/coalescing and cancel-of-running — are provided by
NO surveyed library; every candidate makes us build both anyway. Every maintained
candidate is tokio-first and owns its own DB handle, so job claim could not share
the tick's rusqlite transaction (loses the atomicity SQLite-welding buys).
Least-bad library: effectum (SQLite, priorities, backoff, restart recovery;
~2y stale, no dedup, cancels pending only, separate SQLite file). Verdict:
bespoke table + workers, ~200 lines, in the daemon's existing db.

## 1. Type signatures

```rust
// src/jobq.rs (new module; daemon.rs gets wiring lines only)
pub(crate) enum JobKind { Tick, SinkDrain, DeriveStratum /* J3 */ }

pub(crate) struct JobRow {
    key: String,        // dedup identity, e.g. "tick:{root}"
    kind: JobKind,
    root: String,
    arg: serde_json::Value,   // e.g. changed paths, coalesced by UPSERT merge
    priority: i64,
    attempts: i64,
    run_at: i64,              // unixepoch; 0 = now; backoff/cron target
}

pub(crate) struct JobQueue { conn: /* same daemon rusqlite db */ }

impl JobQueue {
    fn enqueue(&self, row: JobRow) -> Result<()>;                    // UPSERT
    fn claim(&self, open_kinds: &[JobKind]) -> Result<Option<JobRow>>; // BEGIN IMMEDIATE
    fn finish(&self, key: &str, outcome: Result<()>) -> Result<Requeue>;
    fn cancel(&self, key: &str) -> Result<()>;                       // flag; workers poll
    fn reset_running_on_boot(&self) -> Result<usize>;                // running -> pending
}

pub(crate) struct Dispatcher {
    queue: Arc<JobQueue>,
    per_kind_cap: HashMap<JobKind, usize>,   // admission control
    workers: Vec<JoinHandle<()>>,            // cap = daemon_thread_count()
}
```

## 2. Pseudo-code bodies

```rust
// enqueue: coalescing IS the upsert.
//   INSERT INTO job ... ON CONFLICT(key) DO UPDATE SET
//     arg      = merge(arg, excluded.arg),        -- union changed paths
//     priority = max(priority, excluded.priority),
//     dirty    = CASE state WHEN 'running' THEN 1 ELSE dirty END
// a re-request while pending collapses; while running sets dirty -> rerun after.

// claim: one BEGIN IMMEDIATE tx (SQLite single-writer = the coordinator):
//   SELECT .. WHERE state='pending' AND run_at<=now AND kind IN (open)
//   ORDER BY priority DESC, id LIMIT 1; UPDATE state='running', started_at=now.

// finish: UPDATE state='done'|'failed'; on failure attempts+=1,
//   run_at=now+backoff(attempts), state='pending' (bounded attempts);
//   if dirty=1 -> state='pending', dirty=0 (the rerun the coalesce promised).

// worker loop: claim -> run (Tick: lock_eng exactly as today) -> finish.
// cancellation: worker checks job.cancelled between strata (J3 seam in tick.rs).
```

## 3. Instance lifetimes

- `JobQueue`: one per daemon process, owned by `Daemon`, lives until shutdown.
- `Dispatcher` workers: spawned in `run_daemon` after budget; exit on shutdown flag.
- `JobRow`s: durable — survive restart; boot calls `reset_running_on_boot`.
- Watcher threads: stop calling `tick_paths` inline; they only `enqueue` (J1).

## 4. Storage layout, read/write sequence, uniqueness

```sql
CREATE TABLE IF NOT EXISTS _job(
  key TEXT PRIMARY KEY, kind TEXT NOT NULL, root TEXT NOT NULL,
  arg TEXT NOT NULL DEFAULT '{}', priority INTEGER NOT NULL DEFAULT 0,
  state TEXT NOT NULL DEFAULT 'pending',   -- pending|running|done|failed
  dirty INTEGER NOT NULL DEFAULT 0, cancelled INTEGER NOT NULL DEFAULT 0,
  attempts INTEGER NOT NULL DEFAULT 0, run_at INTEGER NOT NULL DEFAULT 0,
  enqueued_at INTEGER, started_at INTEGER, finished_at INTEGER, last_error TEXT
) WITHOUT ROWID;
CREATE INDEX IF NOT EXISTS _job_ready ON _job(state, run_at, priority);
```

- Writes: enqueue (1 upsert) / claim (1 select + 1 update, one tx) / finish (1 update).
  Never per-row loops; a sweep enqueues cron rows in one multi-row insert.
- Uniqueness: `key` is the dedup law. `tick:{root}` serializes ticks per root by
  construction (no second pending row can exist). Per-kind concurrency is the
  dispatcher's admission map, not a table constraint.

## Arcs

- **J1 (behavior-preserving)**: `_job` table + Tick jobs. Watchers enqueue
  `tick:{root}` with coalesced paths; one worker per root drains. Same
  throughput, but ticks are now visible, listable (`dl daemon jobs`), durable,
  and dedup'd. Poll-loop `@async` drains become `SinkDrain` jobs.
- **J2**: priorities + backoff live; failed ticks park with bounded retries
  (replaces the bespoke orphan-parking state from 7af0e319 with table rows).
- **J3 (subsumes arc E, tick deadline)**: derived rebuild decomposes into
  `DeriveStratum` jobs using the dependency info `affected_derived` already
  computes; cancellation checks between strata; over-budget strata requeue at
  low priority instead of blocking the tick.

## Verification

- J1: it-test — two rapid saves produce ONE tick job run (coalesce proof);
  kill -9 mid-tick, reboot, job re-runs (durability proof); `dl daemon jobs`
  lists states. Existing daemon it-suite green unchanged.
- J3: derived output byte-equal to inline rebuild on a fixture (oracle),
  deadline test: a synthetic 2s rule defers, tick returns under budget.

## Hardening ledger (2026-07-16, effectum + apalis mined)

Studied effectum (dimfeld/effectum, `master`) and apalis (apalis-dev/apalis,
`v0.7.4` + issue tracker) for the failure modes a fresh queue module hasn't
lived through. Each row: the concern, what jobq does, classification.

### HANDLED (test proves it)
- **worker panic mid-job** — `worker_loop` wraps `runner.run` in
  `catch_unwind(AssertUnwindSafe)` and converts a panic to a job failure; the
  worker thread survives. effectum does the same (`AssertUnwindSafe.catch_unwind`);
  apalis's is opt-in `.catch_panic()` and a bare panic kills the poll task
  (#639). Test: `worker_survives_a_panicking_runner_and_keeps_serving`.
- **claim race under concurrent workers** — `claim` runs `BEGIN IMMEDIATE` +
  `SELECT ... LIMIT 1` + `UPDATE state='running'` in one tx, behind the queue
  `Mutex<Db>`; SQLite single-writer is the coordinator. No double-claim. Test:
  `concurrent_workers_claim_each_job_exactly_once` (8 workers, 24 jobs, each run
  once).
- **poisoned/stuck jobs** — bounded `MAX_ATTEMPTS=5`, then park in `failed`.
  Tests: `failure_backs_off_then_parks_after_the_attempt_bound`,
  `dispatcher_parks_a_persistently_failing_job`.
- **crash recovery (dead process)** — `reset_running_on_boot` re-pends any row
  left `running` by a killed process, at boot before serving. Test:
  `reset_running_on_boot_re_pends_a_crashed_job`.
- **db-locked / SQLITE_BUSY on claim** — the jobq connection goes through
  `db::open`, which installs a 5s busy handler (20ms backoff). Within one process
  the queue `Mutex` serializes writers anyway; the read-only `list` connection is
  a WAL reader and never contends. effectum/apalis both punt this to their
  single-writer architecture.
- **WAL checkpoint pressure** — `db::open` sets `journal_mode=WAL` +
  `synchronous=NORMAL`; default 1000-page autocheckpoint stays on and `Db::Drop`
  runs `wal_checkpoint(TRUNCATE)` on clean close. Row count is bounded by distinct
  key (UPSERT reuses rows), so WAL growth is bounded. Neither library tunes this.

### GAP-FIXED (small fix + regression test, jobq only)
- **expired running rows / lease timeout** — NEW `sweep(lease_secs, retain)`
  resets `running` rows whose `started_at` predates `now - LEASE_SECS` (900s) to
  `pending` — a worker that died WITHOUT the process dying (silent thread exit,
  wedged tick) which `reset_running_on_boot` (boot-only) never reaches. This is
  apalis's live `reenqueue_orphaned`; effectum only recovers such rows at restart.
  Wired: one line in `idle_loop` (~30s). Test:
  `sweep_reclaims_an_expired_running_lease`.
- **reclaim race (finish must not stomp)** — `finish` now short-circuits when the
  row is no longer `running` (the sweep reclaimed it mid-run); the reclaimed
  attempt is authoritative. Mirrors effectum's worker-scoped `expires_at`
  ownership check. Test: `finish_declines_to_stomp_a_reclaimed_row`.
- **queue-table growth / done-row cleanup** — `sweep` also DELETEs `done` rows
  finished before `now - DONE_RETAIN_SECS` (3600s). Bounded-by-key already, so
  this only reaps rows for dropped roots. effectum has a bare `// TODO`; apalis
  has a manual `vacuum()` that is never scheduled. Test:
  `sweep_trims_old_done_rows_but_keeps_fresh_ones`.
- **backoff jitter / thundering herd** — `finish`'s failure path now uses
  `jittered_backoff` (base `backoff_secs` + additive `[0, base/2]` jitter, seeded
  from key+now). Per-root keys mean a bad global config fails every root on the
  same wall-second; without jitter they all wake in lockstep on the engine mutex.
  effectum multiplies backoff by `1 + rand()*randomization`; apalis adds none.
  Test: `jittered_backoff_stays_in_band_and_never_panics`.

### GAP-DEFERRED (real, not J1-scope)
- **per-job heartbeat** — the lease (`LEASE_SECS`) is coarse: it must exceed the
  longest legitimate tick so a slow-but-live tick is never reclaimed. effectum's
  `expires_at` monotonic-extension heartbeat (worker pings mid-run) is the finer
  tool and belongs with J3's per-stratum jobs, where progress is observable.
- **graceful shutdown drain** — on shutdown the workers check the flag at the
  loop top and return WITHOUT finishing an in-flight job; that job is left
  `running` and re-pended on next boot (at-least-once). effectum/apalis both
  wait for in-flight workers with a timeout (`Queue::close`, `shutdown_timeout`).
  A drain-with-timeout is a nicety here since boot reset already recovers; wire
  it when the dispatcher gains a join handle in the daemon.
- **clock skew in run_at** — timestamps are raw wall-clock (`SystemTime`); a
  backward jump can defer a backed-off job or (forward) run it early. effectum
  derives a monotonic clock (`start_time + start_instant.elapsed()`); adopting
  that is a queue-wide time-source change, out of J1 scope. Single-host daemon,
  so cross-machine skew does not apply.
- **enqueue during shutdown** — `enqueue` always persists the row regardless of
  the shutdown flag; a late enqueue is simply served next boot (durable, benign).
  No explicit rejection like effectum's `QueueClosed`; not needed for a
  single-process daemon.
