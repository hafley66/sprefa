  The pre-IR dd engine at `63c33b94e` reused one dataflow for all macrotime calls
  (`dd dataflow reuse reused=true`).
- Eight timely operators per IR node. Two of them are the `observe` inspect taps:
  `ivm-dd` sets `taps = Some(..)` for every install
  (`sqlite_ivm/crates/ivm-dd/src/2_dd.rs:862`), so every node's output rows are cloned into a
  `Vec<DdTap>` and consolidated in a `BTreeMap` per settle only to fill `Counters`.
  dl8 reads those counters only in `dl8 eval` (`src/bin/dl8.rs:487`).
- Experiment, taps off (env-gated hack, reverted): operators 8679 -> 6409 and 27399 -> 19851;
  install 85 -> 64 ms and 45 -> 33 ms; settles 101 -> 48-53, 98 -> 35, 140 -> 74, 133 -> 52 ms.
  Whole build 1.41 -> 0.95 s, same bytes.
- Macrotime install cost is superlinear in operators (8.7k operators: 85 ms; 27k: 45 ms). The

  `((Location, usize), Antichain<Product>)` for the nested scope (sampled hottest frame in
  install).
- Settle time is timely scheduling: `schedule` / `propagate_pointstamps` are most of each
  worker's samples; operator count drives it. Epochs per settle 1-4, steps 11-738.
- Joins: 364 of 1072 macrotime nodes, 1026 of 3401 comptime nodes. Each join arranges both
  inputs separately (two key-extraction `flat_map`s, two arrangements, the join, a map).
  Unions fold binary `concat` (n-1 operators per n inputs).
- Term transport is small: `intern_terms`, `intern_text` each round-trip the worker channel
  once per call; samples under 1%. No per-row lock contention; the interner is an `Rc<RefCell>`
  on the worker thread.

## Consequence for the target

The main thread alone (front end plus IR glue) is about 0.23 s of CPU. A 0.25 s build would
leave about 20 ms for six DD installs and eight settles. The levers below are ranked by
measured or projected savings.

| lever | measured / projected | where |
|---|---|---|
| no taps unless counters are asked for | -0.45 s measured | ivm-dd install mode, dl8 `IrSession` |
| one macrotime session across unit expansions | up to 3 installs (~190 ms after taps) | `_1_macrotime/_4_expand.rs`, `_8_driver/_2_macro.rs` |
| n-ary union via one `concatenate` | operator count | ivm-dd `union` |
| share arrangements of one input on one key | operator count, install, step | ivm-dd `join` |

## How it works (round 2 fixes)

Profile units below are sampled CPU microseconds of the dl8 main thread from
`samply record -r 10000` (one sample capped at 150 us); before is `4c09cf825`, after is the
round-2 tree. They compare within a column, not with wall time.

### 1. A dropped DD engine no longer blocks the caller (`ivm-dd`)

Problem: every `IrSession` drop joined its worker thread. On `Stop` the worker leaves its
command loop, `timely::execute_directly` then steps the dataflow until it has no dataflows:
the inputs close, every operator sees its frontier go empty and runs once more, and every
arrangement drops its trace. Measured with a probe around `Drop`: 5.5, 6.3, 4.5, 4.3, 6.1 ms
for the five macrotime engines and 18.6 ms for the comptime engine, 45 ms per build on the
main thread.

Mechanism, comptime engine (14541 timely identifiers):

| step | before | after |
|---|---|---|
| `Dd::drop` | send `Stop`, `join()` | send `Stop`, keep no handle when `Mode::Unmeasured` |
| worker after the loop | `execute_directly` steps every operator until the dataflow completes | `drop(built)`, then `worker.drop_dataflow(id)` for each installed dataflow: operators and traces are freed without being scheduled |
| main thread | waits 18.6 ms | continues at once |

Measured and traced installs (`dl8 eval`, the oracle tests, `install_observed` hooks) keep
the join and the full shutdown, so their loggers still see every event.

Code: `sqlite_ivm/crates/ivm-dd/src/2_dd.rs` `impl Drop for Dd` and the end of `worker`
(`if mode == Mode::Unmeasured`).

### 2. Stratification by strongly connected components (`stratify`)

Problem: `stratify` (`src/_6_eval/_2_stratify.rs`) ran 25 times per build: 16 calls over
programs of 26 relations and 177 reads, 9 over 108-118 relations and 432-485 reads
(`ir_lower::lower` calls it twice per evaluation). It built a `HashSet` reach set per relation and closed
it by repeated passes (3-4 passes, each visiting `reach[r]` for every `r` and `reach[n]` for
every `n` in it), then relaxed levels by scanning all reads per relation per pass (5 passes
over 108 x 432 = 46656 read visits). Measured with the old function run beside the new one
on the same inputs: 1.2-2.7 ms per 108-relation call, 0.4 ms per 26-relation call, 21.2 ms
per build.

Mechanism: one iterative Tarjan pass numbers the components in completion order, so every
component a relation reads finishes before the relation's own. A gap-one read whose head and
body share a component is the strict cycle the old `reach[body] contains head` test found.
Levels then take one pass in completion order. Trace on `a :- b. b :- a. c :- not a. d :- count(c).`
(reads a->b gap 0, b->a gap 0, c->a gap 1, d->c gap 1):

| step | stack | event | component |
|---|---|---|---|
| visit a (index 0) | a | edge a->b | |
| visit b (index 1) | a b | edge b->a: a on stack, low(b) = 0 | |
| finish b | a b | low(b) 0 != index 1, parent low(a) = 0 | |
| finish a | | low(a) == index(a): pop b, a | 0 = {a, b} |
| visit c (index 2) | c | edge c->a: a done, not on stack | |
| finish c | | pop c | 1 = {c} |
| visit d, finish d | | edge d->c done; pop d | 2 = {d} |

Levels in order 0, 1, 2: {a, b} reads only inside itself, level 0; c reads a with gap 1,
level 1; d reads c with gap 1, level 2. No gap-one read stays inside a component, so no
diagnostic.

Code: `src/_6_eval/_2_stratify.rs` `components` and `stratify`. Before/after: 21.2 ms ->
1.5 ms per build (25 calls); main-thread profile 19095 -> 1245 units.

### 3. `EdgeIndex::owned` reads an owner index (`_2_lower`)

Problem: `owned(owner)` walked every edge row of the index and looked up each row's owner in
the owner dictionary to collect the owner's positions. A build makes 2004 calls over indexes of
372 and 1415 rows that return 2-6 edges each: about 1.4 million dictionary lookups.

Mechanism: `EdgeIndex::build` appends each row position to `by_owner[owner]` as it already does
for `by_owner_name`; positions are pushed in source order, so the list is already sorted.
`owned` is one dictionary lookup and one map lookup: for a 1415-row index returning 6 edges,
1415 lookups -> 2.

Code: `src/_2_lower/_10_index.rs` `EdgeIndex::by_owner`, `build`, `owned`. Profile 16193 ->
34 units.

### 4. Equal functors skip the text comparison (`Universe::cmp`)

Problem: comparing two compounds compared arity, then the two functor names as text, then
arguments. Rows of one relation (`edge(..)`, `row(..)`) share their functor `Sym`, so most
comparisons resolved two `Sym`s to text through `Syms::text` and `memcmp`-ed equal strings.
`Universe::cmp` is the comparator of every standard-order sort (`sort_terms`, `prolog_sort`,
the closure row sort).

Mechanism: equal `Sym`s are equal text (one `Sym` per content), so `fx == fy` returns
`Equal` without reading text. Measured by sorting the same input with and without the check:
`sort_terms` over a build (1064 calls) 18.4 ms -> 11.9 ms; its largest call, 14904 rows,
7.5 ms -> 4.5 ms.

Code: `src/_6_eval/_0_term.rs` `cmp_head`, compound arm.

Tried and dropped: ranking each distinct argument once and sorting rows by rank vectors.
Measured beside the plain sort on the same inputs it was slower for `sort_terms`
(20.6 ms -> 47.2 ms per build; distinct arguments were as many as rows) and level for the
closure rows (8.95 ms -> 8.79 ms).

### 5. IR glue after a settle (`_9b_ir_eval.rs`, `_5_evaluate.rs`, `_9a_ir_lower.rs`)

- `decode_terms`: before, one worker round trip per constructor relation, each
  `Interner::snapshot` scanning the whole dictionary, every row copied into a
  `BTreeMap<Cell, (String, Vec<Cell>)>` with the constructor name cloned per row, then passes
  over the whole map until a pass decodes nothing. After: one `Engine::intern_snapshots` call
  (one `InternSnapshots` command, one pass over the dictionary); undecoded terms go into a
  `Vec` sorted by id with the name borrowed; a term's arguments are interned before it, so the
  first ascending `retain` pass decodes all of them and the second only confirms. Profile 12708
  -> 3685 units.
- Declared-fold diagnostics: `fold_generic_row_groups` built a `Store` of every closure row
  once per declared fold (four folds: four stores of the same rows). It now takes every fold
  and builds the store once. Profile 10870 -> 3672 units.
- `ir_lower::lower` marked reachable terms in a `BTreeSet<u32>`; it now marks a `Vec<bool>`
  indexed by term id and sorts the collected ids once. With `stratify` (item 2) the function
  went 29722 -> 13254 units.

### 6. Smaller DD engine items (`ivm-dd`, `ivm-ir`, `ivm-engine`, `ivm-sqlite`)

- Pending terms found their constructor input by a linear scan of every constructor with a
  string compare; a `HashMap<String, RelId>` built at install replaces it.
- Constructors no operator reads (`DdRel::get` records reads) get no input rows; only
  `9:1:const` and `9:2:[|]` are read in this build, so the other constructor rows no longer
  enter the dataflow.
- `Program::node_types` re-walked the input tree of a node on every call (`build_node` asks
  for the input types of every Mfp, join, reduce, topk and window). `Rel::node_types`
  (default: `p.node_types`) lets an engine memoize; `DdRel` and `SqlRel` keep one memo per
  install (`Program::node_types_memo`).
- `Interner` keys (`by_key`, `by_text`, `functors`) moved from `BTreeMap`/`BTreeSet` to
  `HashMap`/`HashSet`; nothing iterates them.
- `Universe::terms` and `Dictionary::terms` hash with `hashbrown::DefaultHashBuilder` instead
  of SipHash. Term hashing went 17172 -> 2731 profile units and
  `IndexSet<Term>::insert_full` 22614 -> 17713; the whole-build CPU medians of
  SipHash, hashbrown default and foldhash-quality builds were within noise (0.58, 0.56,
  0.56 s at load 13-15), so the hasher stays the dependency already present.
