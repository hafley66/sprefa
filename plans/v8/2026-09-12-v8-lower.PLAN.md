## 1. The boundary: input and output terms

`lower_datalog/5` is declared at `0_lowerer.pl:36`, `lower_datalog/4` at `:27`
(it supplies `expression_environment([], [], [])`), `lower_datalog_deferred/5`
at `:47`. All three funnel into `lower_datalog_mode/6` at `:52`, whose first
argument is the call policy: `strict` or `defer_unknown_calls`.

Wrapping only `lower_datalog/5` captures one call per compile, the macrotime
unit. The prelude and every source unit go through `lower_datalog_deferred/5`
(`0a_module_lowerer.pl:49`, `:103`, `:140`, `:167`), so the oracle dump
`v8/oracle/lower/dump_lower.pl` wraps both and records the policy.

## 3. The `:`/2 and `:`/4 story

### 3.1 `(: Name Target)` is the one declaration form

`bind_form/4` at `:1940` matches `form([atom(':'), atom(Name), Target])` and
`form([atom(':'), form([]), Target])`; the second spells the empty product,
binding the name `'()'`. `edge_bind_form/4` at `:1948` is the same shape with an
arbitrary label node, used inside a constructor.

`lower_bind/5` `:701` splits on `expression_bind_target/1` `:713-717`: a target
that is a `form` whose head is not `*`, `+` or `Host`, and is not the empty
form, is an EXPRESSION and defers (`finish_derived_bind/6` `:719`). Everything
else is structural and goes to `lower_target/4` `:748`:

| target node | `:748` clause | kind | emitted |
|---|---|---|---|
| `form([atom(*) \| Bindings])` | 748 | `product` | `node(Owner)`, `product(Owner)`, `relation(Owner, Arity, KeySets)` |
| `form([atom(+) \| Bindings])` | 754 | `sum` | `node(Owner)`, `sum(Owner)`, no relation (`:889`) |
| `form([atom('Host'), Impl, In, Out])` | 760 | `product` + `host` reservation | product rows plus `Hosted`/`HostPort` rules |
| `atom(Name)` | 772 | `reference` | `name(Owner, Name)` |
| `form([])` | 774 | `reference` | `name(Owner, '()')` |
| `literal(Value)` | 776 | `literal` | `const(Value)` |
| `variable(_, _)` | 778 | error `variable_bind_target` |
| any other `form(_)` | 780 | error `unsupported_bind_target` |

A product mints `Owner = owner(ModuleIdentity, NodeId)` at `:750`. Its arity is
the count of pending edges it owns (`:884-887`), and its key set is the single
`[all positions except the `return` edge]` when exactly one `return` edge
exists, `[]` otherwise (`return_key_sets/4` `:893`).

### 3.2 `:`/4 is the edge relation

Every bind becomes one row

```prolog
pending_edge(Owner, Name, Target, Index)
```

(`:721`, `:734`, `:974`), with `Index` the ordinal within the owner. The
compiler's filesystem grapher mints the same shape for the project tree
(`0b_filesystem_grapher.pl:196`). `pending_edge/4` is the compile-time list; at
run time the same fact is the kernel relation `':'/4` with the slot labels
`owner, name, target, index` (`kernel_slot_label/3` `:1278-1281`) and the key
sets `[[0,1],[0,3]]` (`:1617`).

A derived bind emits a RULE whose head is a `:`/4 call, `:385-387`:

```prolog
rule(call(name(Owner, ':'),
          [ref(Owner), const(Name), var(derived_bind(BindNodeId)), const(Index)]),
     BindGoals)
```

A compound label `(: (Key "account" Options) int)` emits the same head with the
label position holding `var(derived_label(BindNodeId))` (`:348-350`), and the label
expression's goals in the body. From `2_partial_deferred.json`:

```prolog
rule(call(name(owner(file('.../2_partial.dl7'), reader_node('...', 88)), ':'),
          [ ref(owner(file('.../2_partial.dl7'), reader_node('...', 88))),
            var(derived_label(reader_node('...', 90))),
            name(owner(file('.../2_partial.dl7'), reader_node('...', 88)), int),
            const(0) ]),
     [ pending_goal(positive,
                    call(name(owner(...), 'Key'),
                         [ const("account"),
                           ref(owner(file('.../2_partial.dl7'),
                                     reader_node('...', 79))),
                           var(derived_label(reader_node('...', 90))) ]))])
```

The promotion step at `:150-278` rewrites a `reference` reservation whose target
resolves through a chain of names to a deferred expression into an `expression`
reservation, and emits the alias rule at `:259-267`: a `:`/4 head reading a `:`/4
goal on the immediate owner.

### 3.3 Node and edge products

`node/1` is the identity carrier and `product/1`, `sum/1`, `module/1` are
ordinary classifier rows (`:880-882`). A module owner gets all three at `:288`;
a nested constructor owner gets `node(Owner)` plus its classifier at `:875-876`.
`node/1`, `module/1`, `product/1`, `sum/1` are all kernel relations of arity 1
(`:1958-1961`), so the emitted graph is queryable by the same rules that query
user relations.

### 3.4 TSI relations

TSI (TypeScript interface) rows do NOT enter through `0_lowerer.pl`. They enter
in `2_compiler.pl:566` `tsi_expression_environment/3`, which builds an
`expression_environment` from extracted rows, and `:611` `install_tsi_graph/6`
plus `:614` `expose_tsi_relations/8`, which install alias edges from every
exporter module into every importer module. From the lowerer's side a TSI
relation is indistinguishable from a prelude relation: it is a
`reservation(Owner, Name, target(Callable), product)` row plus a
`relation(Callable, Arity, KeySets)` row in `ImportedEnvironment`. This lane
ports none of it; `_2_lower` consumes whatever environment it is handed.

### 3.5 `kernel_relation/2`, whole (`:1958-1973`)

```prolog

kernel_relation(module, 1).
kernel_relation(product, 1).
kernel_relation(sum, 1).
kernel_relation(':', 4).
kernel_relation(edge_snapshot, 4).

kernel_relation(cons, 3).
kernel_relation(edge_ref, 3).

    integer_comparison(Name, _, _).
```

`integer_comparison/3` is imported from
`v7/src/1_libtime/0_evaluator.pl`, `integer_comparison/3`; its names are the comparison relations

### 4.4 Storage layout, read and write sequence, uniqueness

| store | key | value | written | read |
|---|---|---|---|---|
| `ReservationIndex.owners` | `TermId` | `OwnerId` | `build` | every `scoped` |
| `ReservationIndex.by_owner_name` | `(OwnerId, NameId, View)` | `Vec<ReservationId>`, source order | `build`, `install_promoted` | `scoped` |
| `ReservationIndex.product_by_owner_name` | same | first product-kind row | same | `scoped` first probe, `:1575` |
| `ReservationIndex.parent_by_target` | `(OwnerId, View)` | first owner with `target(Owner)` | same | `scoped` walk, `:1587` |
| `EdgeIndex.by_owner_name` | `(OwnerId, NameId)` | `Vec<usize>`, source order | `build` | `forward`, `:93` |
| `EdgeIndex.by_owner_index` | `(OwnerId, u32)` | `Vec<usize>` | `build` | `callable_slot`, `:113` |
| `EdgeIndex.by_target_owner` | `OwnerId` | `Vec<usize>` | `build` | `parent`, `:102` |

Write then read, never interleaved: `build` runs to completion before the first
probe; `install_promoted` is the one later write and it happens before the edge
index exists. `Vec<usize>` entries are appended in source order so `first()`
reproduces `memberchk/2` and `once/1` exactly, which is the correctness
condition `0_graph_lookup.pl:57-60` states in prose.

Uniqueness: `owners` and `names` are `IndexSet<TermId>` dictionaries, so an
owner term is stored once and compared as a `u32`. No composite string key
anywhere; `(OwnerId, NameId)` is a pair of integers.

Formerly-quadratic paths that need COUNT tests: `scoped_reservation/5` is
`memberchk/2` over 112 rows per probe in the list path (`:1592`) and one hash
probe in the arena path. The v8 port keeps a probe counter on `Cx` so a test can
assert probes per lowering grows with calls, not with `calls * reservations`.

## 6. Forks for the user

Language and type-system calls. Each is cited, none is decided here.

**F1. `expression_bind_target/1` at `:713-717` makes `Host` a keyword.**
`(: Name (Host Impl In Out))` is structural, `(: Name (AnyOther ...))` is an
expression. Three atoms, `*`, `+` and `Host`, are hard-coded heads. A user
relation named `Host` in scope cannot be applied in a bind target. Is `Host` a
reserved word of the language, or should the test read the reservation table
first?

**F2. `lower_target/4:778` rejects a variable bind target outright.**
`(: Name ?Var)` is `variable_bind_target`. Every other target form has a
lowering. Is a variable target meaningless, or unbuilt?

**F3. `kernel_relation/2:1971-1973` declares `def/2`, `head/2` and `body/4`
with no slot labels and no key sets.** `kernel_slot_label/3` (`:1278-1301`) has
no clause for them, so `callable_slot/4:1276` returns `none` for every position,
and `kernel_relation_keys_for_expression/2:1627` returns `[]`, which makes
`expression_mode_diagnostics/6:1816` reject every embedded use with
`ambiguous_expression_projection`. Are these three meant to be callable as
expressions, or are they goal-position only?

**F4. `finish_call_arguments/6:1152-1162` allows at most one `count` aggregate
per head and `lower_argument/5:1909` allows `count` only in a head.** Is one
aggregate per head the design, or the current limit?

**F5. `compound_edge_target/5:581-596` reads an atom target through the nearest
deferred binding but a nearer non-deferred binding wins.** The comment at
`:577-580` states the rule. Is this shadowing order the intended lexical
semantics for compound-label edges?

**F6. The `Curry` and `Literal` products are looked up by NAME at `:414-421`.**
`partial_bind_rules/9` requires `scoped_reservation(Owner, 'Curry', ...)` and
`scoped_reservation(Owner, 'Literal', ...)` to resolve to products, otherwise it
reports `partial_application_requires_more_arguments`. Partial application is
therefore only available where the prelude is in scope, and the failure is
reported as an arity problem rather than a missing-prelude problem. Should the
kernel own `Curry` and `Literal` instead?
