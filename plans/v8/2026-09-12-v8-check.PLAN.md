### 2.1 Bind checks, `:477-567`

Three passes over `PendingEdges`, concatenated in this order at `:481`:
duplicate name per owner (`:483`), duplicate index per owner (`:495`),
non-dense index (`:507`). Each is a first-occurrence-wins scan: the first edge
with a given `(Owner, Name)` is clean and every later one is a
`duplicate_bind`. `dense_index_diagnostics/4` picks the assoc-indexed path at
`:509` when both lists are ground and the scanned path at `:512` otherwise;
both compute the same count, so Rust ports the indexed one only.

`owner_edge_count_index/2` at `:546` counts edges per owner; an index is dense
when `0 =< Index < Count`.

### 2.2 The origin arena, `:46-172`

`arena_edge_origin/6`, `arena_seed_origin/4`, `arena_rule_origin/4` and
`arena_goal_origin/5` are module-level dynamic predicates keyed by a gensym
arena id. `edge_origin/5` at `:1104` reads the arena when
`checker_origin_lookup_scope(arena(_))` holds and `memberchk/2` over the
`Origins` list otherwise, and both are cut to the first match.
`checker_origin_lookup/2` at `:125` only selects the arena when the arena's
installed sequence equals this exact `Origins` list, so the two paths read the
same data and both mean "first occurrence in `Origins`".

Rust: `OriginArena` in `_1_graph.rs`, four `HashMap`s filled with
`entry().or_insert()` in list order, built by value and passed by `&`. No
globals, no gensym, no `close`.

`origin(node(_), _)` and `origin(relation(_), _)` rows are skipped without
advancing the sequence (`:100`, `:102`).

### 2.3 The kernel graph, `:622-725`

`kernel_relation_rows/1` runs `kernel_relation/2`
(`0_lowerer.pl:1958-1973`, already ported at
`v8/src/_2_lower/_9_kernel.rs:18`) against a checker-local key table
`kernel_relation_keys/2` at `:629-645`. That table is NOT the lowerer's
`kernel_keys/1` (`_9_kernel.rs:51`): the checker gives `nil` `[[0]]` where the
lowerer gives `[[]]`, and the checker adds `def`, `head`, `body`, `node`,
`module`, `product`, `sum`. `_5_kernel.rs` carries its own copy.

`kernel_graph/2` at `:647` concatenates 25 head node rows, the six

six tail rows for `def`/`head`/`body`. `CheckedNodes` is

observable. `integer_comparison/3` declaration order in
`0_evaluator.pl:60-65` is `int_lt, int_le, int_eq, int_ne, int_ge, int_gt`;
`v8/src/_2_lower/_9_kernel.rs:7` `INTEGER_COMPARISONS` is in a different order
(`int_lt, int_le, int_gt, int_ge, int_eq, int_ne`) and cannot be reused for
the node list. `_5_kernel.rs` declares `COMPARISONS` in the v7 order.

Kernel edges are sorted by `msort/2` at `:425`, so their order is free.

## 3. Name resolution, the one recursive core

`resolve_name/6` at `:599`:

```prolog
resolve_name(Owner, Name, Edges, Nodes, Visited, Resolved) :-
    \+ memberchk(Owner-Name, Visited),
    (   graph_forward(Edges, Owner, Name, Target)
    ->  resolve_target(Target, Edges, Nodes, [Owner-Name | Visited], Resolved)
    ;   graph_parent(Edges, Owner, Parent),
        resolve_name(Parent, Name, Edges, Nodes, [Owner-Name | Visited], Resolved)
    ;   graph_module_member(Nodes, Owner), kernel_relation(Name, _),
        Resolved = ref(kernel(Name))
    ;   graph_module_member(Nodes, Owner), primitive_name(Name),
        Resolved = ref(primitive(Name))
    ).
```

`;` is right associative, so this is
`(Forward -> Target ; (Parent ; (Kernel ; Primitive)))`. Three consequences
the Rust port must keep:

1. A forward edge COMMITS. If `resolve_target/5` then fails, `resolve_name/6`
   fails; the parent, kernel and primitive alternatives are not tried.
2. The parent alternative does NOT commit. `graph_parent/3` is `once`-wrapped
   (`0_graph_lookup.pl:102`) so it has no choice point of its own, but the
   `;` does: when the recursive call fails the kernel alternative runs.
3. `primitive_name/1` at `:617-620` is exactly `int`, `text`, `any`, `type`.

Every caller takes the first solution only (`:582` under `->`, `:991` under
`->`, `:1023` under `->`), so an `Option`-returning recursive function is
faithful.

`graph_forward/4` (`0_graph_lookup.pl:91`) is the first edge with that
`(Owner, Name)` in source order; `graph_parent/3` (`:100`) is the first edge
whose target is `target(Owner)`; `graph_module_member/2` (`:128`) is
membership of `module(Owner)` in `Nodes`. `EdgeIndex` in
`v8/src/_2_lower/_10_index.rs:200` covers only `forward`; its
`by_target_owner` map has no accessor and it holds no module nodes, so
`_3_check/_1_graph.rs` carries `CheckerGraph` with all three.

`resolve_call/5` at `:990` matches ONLY `call(name(Owner, Name), Args)`; any
other callable makes the predicate fail, which fails `check_datalog/4`
outright. See defect D1.

`memberchk(relation(Target, Arity, _), Relations)` at `:994` reads the
sorted-and-deduplicated relation list, so it finds the lowest arity for a
target. Rust builds one `HashMap<TermId, (i64, TermId)>` from that sorted list
with first-wins insertion.

## 4. Mode and safety checking

`check_goal_sequence_failures/7` at `:807` folds goals left to right over two
variable sets:

| set | seeded by `resolve_rules` `:757` | seeded by `check_goal_sequence/4` `:803` |
|---|---|---|
| `Available` | `HeadVariables` | `Bound0` |
| `Produced` | `[]` | `Bound0` |

`check_goal_transition/6` at `:823`: a negative goal leaves both sets alone
and checks against `Produced`; a positive goal checks against `Available`,
grows `Available` through `check_goal_with_variables/5`, and grows `Produced`
only when the reason is `none`.

`check_goal_with_variables/5` clause order at `:840`, `:851`, `:864`, `:876`,
`:887` is integer comparison, `cons`, `edge_ref`, `intern`, then everything
else. Declared input modes:

| kernel | required | reason when unmet |
|---|---|---|
| `int_*` | every argument bound | `underconstrained_kernel_goal(Name, [[0, 1]])` |
| `cons` | `List`, or `Head` and `Tail` | `underconstrained_kernel_goal(cons, [[2], [0, 1]])` |
| `edge_ref` | `Owner` and `Label` | `underconstrained_kernel_goal(edge_ref, [[0, 1]])` |
| `intern` | `Constructor` and `Arguments` | `underconstrained_kernel_goal(intern, [[0, 1]])` |

`check_goal/4` at `:891` adds the negative cases:
`negative_constructive_kernel_goal(Name)` for `cons`, `edge_ref`, `intern`,
`nil` (`:897`), then integer comparisons (`:901`), then the generic
`unbound_negative_goal(Unbound)` (`:912`).

Two variable collectors disagree, deliberately:

| predicate | line | reads |
|---|---|---|
| `argument_variables/2` | `:939` | every `var(_)` SUBTERM, sorted and deduplicated |
| `goal_variables/2` | `:1058` | only TOP-LEVEL `var(_)` arguments, unsorted, not deduplicated |

`head_variables/2` at `:978` uses the first; `head_safety_from_variables/4` at
`:1048` uses the second for body variables. So a head variable that only
appears inside `aggregate(count, var(X))` in a body goal is reported
`unsafe_head_var`. Fork F1.

`unbound_variables/3` at `:952` keeps order and duplicates, so
`unbound_negative_goal([V, V])` is a real shape.

`add_variables/3` at `:960` prepends each unseen variable in iteration order,
so `Bound` grows `[Vn, ..., V1 | Bound0]`. Only `check_goal_sequence/4`
exports it, and the comptime lane reads it, so the Rust `Bound` is a `Vec`
with the same insertion order plus a `HashSet` for membership.

## 6. Oracle and test

`v8/oracle/check/dump_check.pl` wraps `dl7_checker:check_datalog/4` and
`dl7_checker:check_resolved_rules/5` with `wrap_predicate/4` and writes one

| byte-distinct cases the Rust binary reproduces | 75 |

## 8. Forks for the user

**F1. Head variables and body variables use different collectors.**
`head_variables/2` (`:978`) reaches into `aggregate(count, var(X))` through
`argument_variables/2` (`:939`, `sub_term/2`); `head_safety_from_variables/4`
(`:1048`) collects body variables with `goal_variables/2` (`:1058`), which
reads top-level `var(_)` arguments only. A head variable bound only inside a
body aggregate is therefore reported `unsafe_head_var`. v7 behavior is kept.
The symmetric collector would be `argument_variables/2` on both sides.

**F2. `unresolved_name/1` names the edge, not the missing target.**
`resolve_edges/6` at `:585` reports `unresolved_name(Name)` where `Name` is
the edge label. For `(: point (* (: x MissingType)))` the diagnostic is
`unresolved_name(x)`, not `unresolved_name('MissingType')`. v7 behavior is
kept; the reader's node id does point at the right form.

**F3. The negative-goal mode check reads `Produced`, not `Available`.**
`check_goal_transition/6` at `:823-826` passes `Produced` to `check_goal/4`.
From `resolve_rules` `Produced` starts `[]` (`:757`), so a head variable is
NOT considered bound for a negative goal even though it is for a positive
one. That is what makes `(<- (r 1) (not (point ?X)))` an
`unbound_negative_goal` while `(<- (r ?X) (point ?X))` is clean. v7 behavior
is kept.

**F4. `check_resolved_rules/5` does not relocate stratifier diagnostics.**
`:252` returns `StrataDiagnostics` unchanged, so `strict_dependency_cycle`
from that entry keeps `none` as its node, while `check_datalog/4` relocates it
at `:434`. v7 behavior is kept.

## 9. Defects found while reading

**D1. `check_datalog/4` fails rather than diagnosing on a malformed call.**
`resolve_call/5` (`:990`) has one clause, matching `call(name(_, _), _)`;
`resolve_goals/8` (`:779`) has one recursive clause, matching
`pending_goal(_, _)`; `resolve_rules/8` (`:751`) unifies `Rule = rule(_, _)`.
Any other shape makes the predicate FAIL, which propagates out through the
cut at `:191` and makes `check_datalog/4` fail instead of returning a
diagnostic. Every sibling malformed-input path returns
`invalid_basement_program` (`:203`). Rust returns `Stop::Fail` and the CLI
exits 3 rather than inventing a diagnostic.

**D2. Three `check_resolved_rules/5` diagnostics are unreachable.**
`resolved_rule_diagnostic/3` at `:360` computes the diagnostic list AND runs
`check_goal_sequence_failures/7` on the same body.

| reason | line | what fails first |
|---|---|---|
| `invalid_generated_polarity(P)` | `:383` | `check_goal_transition/6` has no clause for a polarity that is neither `positive` nor `negative` (`:823`, `:828`) |
| `invalid_generated_goal(Goal)` | `:391` | same, for a body item that is not `checked_goal/2` |
| `invalid_generated_call(Call)` | `:413` | `goal_variables/2` at `:1058` requires `call(_, Arguments)` |

In each case the whole predicate fails before the diagnostic can be returned.
`invalid_generated_rule/1` at `:373` has no such conjunct and IS reachable.

**D3. `parent_owner/3` at `:614` is dead.** No caller in the file, and the
module exports do not include it. Not ported.

**D4. `dense_index_diagnostics_scanned/4` at `:532` is dead in practice.**
`:509` takes the indexed branch whenever both edge lists are ground, and
`check_datalog_body/4` has already run `must_be(ground, Origins)` on a caller
that only ever passes ground programs. Only the indexed path is ported;
