## 1. What dl8 holds in memory today

| thing | site | shape |
|---|---|---|
| the arena | `v8/src/_6_eval/_0_term.rs:28-33` | `Universe { syms: IndexSet<String>, terms: IndexSet<Term>, nil: Sym, cons: Sym }` |
| a term | `_0_term.rs:19-26` | `Int(i64) \| Float(OrderedFloat<f64>) \| Bool(bool) \| Atom(Sym) \| Str(Sym) \| Compound(Sym, Vec<TermId>)` |
| sym id | `_0_term.rs:54-60` | `IndexSet` insertion position, cast `u32` |
| term id | `_0_term.rs:66-69` | `IndexSet` insertion position, cast `u32` |
| the row store | `_5_evaluate.rs:44-47` | `Store { tables: HashMap<TermId, Table> }` |
| one relation | `_3_table.rs:19-24` | `Table { rows: IndexSet<Box<[TermId]>>, frontier: usize, index: Vec<HashMap<TermId, Vec<u32>>> }` |
| the semi-naive delta | `_3_table.rs:61-67` | `bounds(Range::Delta) = (frontier, rows.len())` |
| the column index | `_3_table.rs:33-39` | one `HashMap<TermId, Vec<u32>>` per column, appended on insert |
| the seam already threaded | `_5_evaluate.rs:487` | `evaluate_into(store: &mut Store, u, program, fx)` |
| the reducer shape | `_5_evaluate.rs:471-480` | `impl Slice for Evaluate { type State = Store; ... }`, `_7_effect.rs:5-15` |
| the process door | `v8/src/bin/dl8.rs:121` | `Universe::new()` per invocation, dropped at exit |
| the output door | `_5_evaluate.rs:642-656` | the whole store flattened, sorted, deduped into `Closure.rows` |

Nothing under `v8/src` opens a file for writing rows. `v8/Cargo.toml:11-19`
lists eight dependencies and none of them is a database.

Two facts from this list drive the whole design.

**`TermId` and `Sym` are already dense integer surrogate keys.** They are
`IndexSet` positions, assigned in insertion order and never reused. The storage
ruling (`v6/prolog/conformance/rulings.pl:117-121`, `storage_integer_keys`) asks
for exactly this shape, so persisting the arena is an append of a dense integer
range, and no re-keying step exists to design.

**A `Compound`'s arguments always carry a lower id than the compound itself.**
Every constructor interns children before the parent: `u.compound` at
`_0_term.rs:97-100` takes already-interned `Vec<TermId>`, `u.list` at
`_0_term.rs:107-114` builds tail-first, `term_from_json` at `_6_json.rs:49-55`
recurses before it calls `u.compound`. A single `ORDER BY id` pass therefore
rebuilds the arena with no forward reference and no second pass.

Three consequences.

**A relation is a compound term, never an atom.** The four busiest relation
terms in the largest closure are `ref(kernel(':'))` at 557 rows,
`ref(kernel(edge_snapshot))` at 557, `ref(kernel(node))` at 157 and
`ref(kernel(product))` at 146. A `rel` column therefore holds a `TermId`
pointing into the same arena as every cell, not a separate name string.

**One program holds one relation at two arities.**
`v8/oracle/eval/12_repeated_vars_and_arity.json` carries `ref(edge)` at arity 2
and at arity 3 in the same closure. Any layout that assumes "one relation, one
fixed column count" is wrong at this fixture. This kills naive table-per-relation
on its own, before any cost argument.

**Hash-consing pays about 30x on this corpus.** 174,081 arena nodes reduce to
1,587 distinct subterms. A term table stores the 1,587, and every row cell is a
4-byte reference to one of them.

**The corpus is small.** 1,495 rows is the largest closure this tree can
produce today, so no measurement here proves anything about a million-row store.
§13 measures 200,000-row tables for that reason: the shapes are compared at a
volume the corpus has not reached yet.

## 3. Type signatures, and the critique of the brief's candidate

### 3.1 The candidate in the brief

```rust
pub trait RowStore {
    fn load(&mut self, u: &mut Universe) -> Result<Store, StoreError>;
    fn commit(&mut self, u: &Universe, delta: &[(TermId, Box<[TermId]>)]) -> Result<(), StoreError>;
}
```

Four defects, each with the site that produces it.

| # | defect | site that forces it |
|---|---|---|
| 1 | `commit` takes `&Universe`, so it cannot know which terms are new. The arena is append-only with no watermark field, so a non-mut borrow either rewrites every term every tick or writes none. | `_0_term.rs:28-33`, no cursor on `Universe` |
| 2 | `delta: &[(TermId, Box<[TermId]>)]` is a fresh allocation of rows that already sit contiguously in each `Table`. Building it copies the whole delta once for nothing. | `_3_table.rs:21` `rows: IndexSet<Box<[TermId]>>`, `:61-67` `bounds` |
| 3 | `load` returns an owned `Store`, so opening a program materializes every row before the first rule fires. | `_5_evaluate.rs:487` already accepts `&mut Store`; returning a second one splits ownership |
| 4 | There is no transaction verb, so a process killed mid-write leaves the arena and the rows disagreeing. v6 learned this and has `begin_tick` / `commit_tick` / `rollback_tick`. | `v6/sprefa-engine-rs/src/sql.rs:273,282,288` |

### 3.2 The signatures this plan proposes

```rust
/// Dense arena cursor. Everything below each index is already durable.
#[derive(Copy, Clone, Default, Debug, PartialEq, Eq)]
pub struct Watermark {
    pub syms: usize,
    pub terms: usize,
}

#[derive(Debug)]
pub enum StoreError {
    /// begin_tick while a tick transaction is open: a driver defect,
    /// distinct from an ordinary SQL failure (sql.rs:90 precedent).
    NestedBegin,
    /// The db carries an arena whose head disagrees with Universe::new().
    ArenaMismatch { at: usize, stored: String, expected: String },
    Sql(rusqlite::Error),
}

pub trait IRowStore {
    /// Idempotent DDL for one program name. Runs once per open.
    fn open(&mut self, program: &str) -> Result<(), StoreError>;

    /// Refills `u` from the term table. Returns the cursor past the last
    /// durable id. `u` must be a fresh `Universe::new()`.
    fn load_arena(&self, u: &mut Universe) -> Result<Watermark, StoreError>;

    /// Refills `store` from the row tables and rebuilds every column index.
    /// Returns rows loaded.
    fn load_rows(&self, store: &mut Store) -> Result<usize, StoreError>;

    fn begin_tick(&self) -> Result<(), StoreError>;

    /// Appends `u.syms[from.syms..]` and `u.terms[from.terms..]`.
    /// Returns the new cursor.
    fn commit_arena(&self, u: &Universe, from: Watermark) -> Result<Watermark, StoreError>;

    /// Appends, for every relation, the rows past this store's own durable
    /// cursor for that relation. Reads `Store` directly; builds no Vec.
    fn commit_rows(&mut self, store: &Store) -> Result<usize, StoreError>;

    fn commit_tick(&self) -> Result<(), StoreError>;
    fn rollback_tick(&self) -> Result<(), StoreError>;
}
```

`IRowStore` carries the `I` prefix per the interface law in `CLAUDE.md`.

### 3.3 The durability cursor is NOT `Table.frontier`

`Table.frontier` is the semi-naive wavefront and moves every round:
`_5_evaluate.rs:621` calls `store.mark_all()` before each round's sink drains at
`:623-627`, and `mark_all` at `_5_evaluate.rs:58-62` sets every table's frontier
to its current length. At the end of evaluation the frontier sits at the
second-to-last round's length, which is a number about the fixpoint and says
nothing about what reached disk.

A store that reuses `frontier` as its durability marker skips every row derived
in the final round and rewrites every row derived in the one before it. The
store therefore owns a second cursor:

```rust
pub struct SqliteRowStore {
    conn: rusqlite::Connection,
    program: String,
    /// rows of each relation already written: the store's own cursor,
    /// never Table.frontier.
    durable: HashMap<TermId, usize>,
    arena: Watermark,
    in_tick: bool,
}
```

This keeps `_3_table.rs` and `_5_evaluate.rs` untouched, which matters: the
evaluator is graded byte-for-byte against v7 by `v8/tests/_0_eval_oracle.rs`,
through the real binary.

## 4. Pseudo-code bodies

```rust
fn open(&mut self, program: &str) -> Result<(), StoreError> {
    // for each of the six CREATE TABLE texts in §6:
    //   execute it verbatim with IF NOT EXISTS
    // read sqlite_master.sql for each name; if a standing CREATE differs
    //   from the one we just asked for, raise StoreError::Sql rather than
    //   dropping rows (v6 drops here at sql.rs:228-246; a store that holds
    //   the only copy must not).
    // self.program = program.to_string();
}

fn load_arena(&self, u: &mut Universe) -> Result<Watermark, StoreError> {
    // SELECT id, kind, ival, fval, sym FROM <p>_term ORDER BY id     (one statement)
    // SELECT id, text FROM <p>_sym ORDER BY id                       (one statement)
    // SELECT term, pos, child FROM <p>_term_arg ORDER BY term, pos   (one statement)
    //
    // for (id, text) in syms:
    //     let got = u.sym(&text);
    //     if got.0 as usize != id { return ArenaMismatch }   // ids must line up
    // for (id, kind, ...) in terms:
    //     let t = match kind { 0 => Term::Int(ival), 1 => Term::Float(fval),
    //                          2 => Term::Bool(ival != 0), 3 => Term::Atom(Sym(sym)),
    //                          4 => Term::Str(Sym(sym)),
    //                          5 => Term::Compound(Sym(sym), args_of(id)) };
    //     let got = u.intern(t);
    //     if got.0 as usize != id { return ArenaMismatch }
    // Watermark { syms: u.syms.len(), terms: u.terms.len() }
    //
    // Children are safe to read from `args_of(id)` in this single pass
    // because child < term always holds (§1, §8 condition U4).
}

fn load_rows(&self, store: &mut Store) -> Result<usize, StoreError> {
    // for arity in 0..=MAX_ARITY:
    //     SELECT rel, c0..c<arity-1> FROM <p>_row<arity> ORDER BY rel, __seq
    //     for each row: store.insert(TermId(rel), cells.into_boxed_slice())
    // Table::insert at _3_table.rs:27 rebuilds the column index as a side
    // effect, so no index is read from disk and none is written (fork 2 note).
    // then: for every table, self.durable[rel] = table.len()
}

fn commit_arena(&self, u: &Universe, from: Watermark) -> Result<Watermark, StoreError> {
    // if u.syms.len() == from.syms && u.terms.len() == from.terms { return from }
    // chunk u.syms[from.syms..] at 16383 rows   (2 variables per row)
    //     INSERT INTO <p>_sym(id, text) VALUES (?,?),(?,?),...
    // chunk u.terms[from.terms..] at 6553 rows  (5 variables per row)
    //     INSERT INTO <p>_term(id, kind, ival, fval, sym) VALUES ...
    // collect the compound args of that same range, chunk at 10922 (3 per row)
    //     INSERT INTO <p>_term_arg(term, pos, child) VALUES ...
    // statements = f(new terms / chunk size), never f(rows): rulings.pl:127
}

fn commit_rows(&mut self, store: &Store) -> Result<usize, StoreError> {
    // for (rel, table) in &store.tables:
    //     let from = *self.durable.get(rel).unwrap_or(&0);
    //     if from == table.len() { continue }              // nothing new
    //     let arity = table.rows[from].len();
    //     // a relation at two arities splits here, not at DDL time:
    //     group table.rows[from..] by row.len()
    //     for (arity, rows) in groups:
    //         chunk at (32766 / (arity + 1)) rows
    //         INSERT OR IGNORE INTO <p>_row<arity>(rel, c0..) VALUES ...
    //     self.durable.insert(*rel, table.len());
    // OR IGNORE rather than a NOT EXISTS prefilter: measured 1.4x faster at
    // every duplication rate (.claude/skills/sqlite-costs/SKILL.md).
}
```

## 5. Instance lifetimes

| type | created | lives | dropped | who owns it |
|---|---|---|---|---|
| `rusqlite::Connection` | at `dl8 eval --db` / server boot | whole process | process exit | `SqliteRowStore` |
| `SqliteRowStore` | after the connection | whole process, one per program name | process exit | the driver, beside the `Universe` |
| `Universe` | `dl8.rs:121`, once | whole process; append-only, never truncated | process exit | the driver |
| `Watermark` | `load_arena` return | one field on the store, replaced per commit | with the store | `SqliteRowStore.arena` |
| `Store` | `_5_evaluate.rs:484` (fresh) or `load_rows` (refilled) | one evaluation today; one program for the resident runtime | end of evaluation, or process exit when resident | the driver |
| `Table` | `Store::insert` at `_5_evaluate.rs:51` | as long as its `Store` | with the `Store` | `Store.tables` |
| `Table.index` | `_3_table.rs:33-39` on first insert | rebuilt on every load, never persisted | with the `Table` | `Table` |
| tick transaction | `begin_tick` | one tick | `commit_tick` or `rollback_tick` | `SqliteRowStore.in_tick` |
| `Eval` and its `memo` | `_5_evaluate.rs:321` per fire | one rule firing | end of that firing | the fixpoint; never persisted |

Two lifetime rules fall out of the table.

The `Universe` outlives every `Store` and is never rebuilt mid-process. A
`TermId` written to disk in tick 3 still resolves in tick 900 because the arena
only grows (`_0_term.rs:66-69` has no removal path).

The `memo` at `_5_evaluate.rs:136` is keyed on `(TermId, Pattern)` and lives one
rule firing. It is a cache of a pure function of the store and must not reach
disk: persisting it would let a stale memo outlive the rows it summarized.

## 6. Storage layout

Program name `p`. Six object kinds, all integer-keyed.

```sql
CREATE TABLE "<p>_sym" (
  "id"   INTEGER PRIMARY KEY,
  "text" TEXT NOT NULL UNIQUE
);

CREATE TABLE "<p>_term" (
  "id"   INTEGER PRIMARY KEY,
  "kind" INTEGER NOT NULL,          -- 0 Int, 1 Float, 2 Bool, 3 Atom, 4 Str, 5 Compound
  "ival" INTEGER,                   -- Int, and Bool as 0/1
  "fval" REAL,                      -- Float
  "sym"  INTEGER REFERENCES "<p>_sym"("id")   -- Atom, Str, Compound functor
);

CREATE TABLE "<p>_term_arg" (
  "term"  INTEGER NOT NULL REFERENCES "<p>_term"("id"),
  "pos"   INTEGER NOT NULL,
  "child" INTEGER NOT NULL REFERENCES "<p>_term"("id"),
  PRIMARY KEY ("term", "pos"),
  CHECK ("child" < "term")
) WITHOUT ROWID;

CREATE TABLE "<p>_row0" ("rel" INTEGER PRIMARY KEY REFERENCES "<p>_term"("id")) WITHOUT ROWID;

CREATE TABLE "<p>_row4" (
  "rel" INTEGER NOT NULL REFERENCES "<p>_term"("id"),
  "c0"  INTEGER NOT NULL, "c1" INTEGER NOT NULL,
  "c2"  INTEGER NOT NULL, "c3" INTEGER NOT NULL,
  PRIMARY KEY ("rel", "c0", "c1", "c2", "c3")
) WITHOUT ROWID;
-- one such table per arity actually used, 1 through 8 (§2 arity spread)
```

| decision | the law it satisfies | receipt |
|---|---|---|
| `sym.id` and `term.id` are the arena positions verbatim | integer surrogate keys every time | `rulings.pl:117-121`; `_0_term.rs:58,67` |
| the single TEXT column lives once, in `<p>_sym`, with UNIQUE | natural keys in a dictionary, id everywhere else | `.claude/skills/sql-relational-design/SKILL.md` |
| no composite TEXT PRIMARY KEY anywhere | composite TEXT PK is a defect | same skill; `CLAUDE.md` style laws |
| `term_arg` is one row per argument | 1NF, no JSON-in-a-column pretending to be a key | same skill |
| `Bool` rides `ival` as 0/1 | booleans are INTEGER, never text | same skill |
| WITHOUT ROWID on every composite-key table | beats rowid+UNIQUE on a fixpoint head by 5.4-7.6% and 2.4x memory | `.claude/skills/sqlite-costs/SKILL.md` |
| no SQL index on non-leading columns | `Table.index` is rebuilt in RAM on load; a SQL index costs +43.6% pages and answers a question nobody asks of the file | measured, §13.4; `_3_table.rs:33-39` |
| absence is no row; no NULL cell | null never enters storage | `CLAUDE.md` user decisions |

`ival`, `fval` and `sym` are NULL-able on `<p>_term` and that does not break the
no-null law: they are per-kind payload slots, not absent facts. A `Term::Int`
row carries `ival` and leaves the other two unset, which is how one table holds
a six-variant sum. The alternative is six tables and a six-way union on load;
this plan takes the one table and names the trade here rather than burying it.

### 6.1 Why table-per-arity and not table-per-relation

Table-per-relation is not available. `v8/oracle/eval/12_repeated_vars_and_arity.json`
holds `ref(edge)` at arity 2 and arity 3 in one closure, so a per-relation table
needs a per-arity split anyway and degenerates into this same shape with more
tables. Once the split is forced, the count is 8 fixed tables against 99 tables
for this corpus, and 8 tables need no DDL when a program grows a relation.

Cost of the choice, measured in §13.2: a leading `rel` column costs 16% on
insert (1.30M rows/s against 1.55M). The v6 measurement says the seam was 11.9%
of the wall on a real fold (sqlite-costs skill), so 16% of 11.9% is under 2% of
a tick, paid for 91 fewer tables and zero runtime DDL.

## 7. Sequence of reads and writes per tick

Statement counts are per tick and depend on relations touched and chunk count,
never on row count (`rulings.pl:127`, `n1_statement_budget`).

```
step  verb                                   statements   touches
0     BEGIN IMMEDIATE                        1            -
1     INSERT <p>_sym    (syms[wm.syms..])     ceil(n/16383) <p>_sym
2     INSERT <p>_term   (terms[wm.terms..])   ceil(n/6553)  <p>_term
3     INSERT <p>_term_arg (args of that range) ceil(n/10922) <p>_term_arg
4     INSERT OR IGNORE <p>_row<a>             1 per (arity, chunk)  <p>_row1..8
5     advance durable[rel] in RAM             0            -
6     COMMIT                                  1            -
```

Chunk sizes come from `SQLITE_LIMIT_VARIABLE_NUMBER = 32766` on the bundled
build, divided by variables per row: 2 for `sym`, 5 for `term`, 3 for
`term_arg`, `arity + 1` for a row table. That limit is recorded in the
sqlite-costs skill as read from a live connection; this lane did not re-read it,
because doing so needs a `cargo build` and the brief writes no Rust. The command
that re-reads it is
`conn.limit(rusqlite::limits::Limit::SQLITE_LIMIT_VARIABLE_NUMBER)`, the same
call `v6/sprefa-engine-rs/src/sql.rs:211-216` already makes.

Open sequence, once per process:

```
step  verb                                    statements
0     CREATE TABLE IF NOT EXISTS x6           6
1     SELECT ... FROM <p>_sym ORDER BY id     1
2     SELECT ... FROM <p>_term ORDER BY id    1
3     SELECT ... FROM <p>_term_arg ORDER BY   1
4     SELECT ... FROM <p>_row<a> ORDER BY     1 per arity in use
5     rebuild Table.index in RAM              0
```

One transaction per tick is kept, and the sqlite-costs skill records it as a
wash on throughput (992/972 ms with, 984/993/998 without). It is not kept for
speed. It is kept because the arena and the rows must never disagree after a
SIGKILL: a `<p>_row4` row referencing a `<p>_term` id that was never written is
a store that cannot be opened. v6 reached the same call at `sql.rs:271-280`.

## 8. Uniqueness conditions

| # | condition | enforced by | what breaks without it |
|---|---|---|---|
| U1 | `<p>_sym.text` appears once | `UNIQUE` on the column | two ids for one string; `Sym` equality stops meaning string equality |
| U2 | `<p>_term.id` equals the arena position of that term | load asserts `u.intern(t).0 == id`, else `ArenaMismatch` | every stored row cell points at the wrong term |
| U3 | `Universe::new()` pre-interns `[]` as `Sym(0)` and `[\|]` as `Sym(1)` | `_0_term.rs:49-50`; load must start from `Universe::new()` and find those two rows at 0 and 1 | list detection at `_0_term.rs:117-129` silently reads non-lists as lists |
| U4 | `term_arg.child < term_arg.term` | `CHECK` constraint, and the constructors at `_0_term.rs:97-114` | a single-pass arena load hits a forward reference |
| U5 | `(rel, c0..cn)` appears once per row table | WITHOUT ROWID composite INTEGER PK | duplicate rows in the closure; `_5_evaluate.rs:655` `rows.dedup()` hides it in output but the store grows unbounded |
| U6 | a term is hash-consed once | `IndexSet` in RAM; `<p>_term.id` PK on disk | two ids for one term, so `==` on `TermId` stops being term equality |
| U7 | `durable[rel] <= table.len()` at all times | `commit_rows` writes the cursor only after the INSERT returns | a crash between INSERT and cursor write re-inserts, which `OR IGNORE` absorbs; the reverse order loses rows |
| U8 | one program name owns one table prefix | `open(program)` and the `<p>_` prefix | two programs interleave rows in one table with no way to tell them apart |

U7 is the ordering that makes the design crash-safe without a second journal:
writing the cursor after the commit can only ever re-write rows, and `INSERT OR
IGNORE` makes a re-write free. The sqlite-costs skill records `OR IGNORE`
rejection beating a `NOT EXISTS` prefilter by 1.4x at every duplication rate, so
the safe order is also the fast one.

## 9. Delta: the frontier at rest

`Table.frontier` is a RAM cursor over a RAM `IndexSet` (`_3_table.rs:22`). It
partitions rows into `Old`, `Delta` and `All` (`_3_table.rs:9-17`) so a
semi-naive round reads only what the previous round added.

Step trace of one stratum, showing the two cursors side by side. `len` is
`table.rows.len()`, `fr` is `Table.frontier`, `dur` is the store's own cursor.

```
step  event                          len  fr   dur  what the store writes
0     open, load_rows                120  120  120  -
1     round 0 fires, sink has 34     120  120  120  nothing yet
2     mark_all()      (:621)         120  120  120  -
3     sink drains     (:623-627)     154  120  120  -
4     round 1 fires on rows[120..]   154  120  120  -
5     mark_all()                     154  154  120  -
6     sink drains, 9 new             163  154  120  -
7     round 2 fires on rows[154..]   163  154  120  -
8     mark_all()                     163  163  120  -
9     sink drains, 0 new -> break    163  163  120  -
10    commit_rows                    163  163  163  rows[120..163], 43 rows, 1 statement
11    COMMIT                         163  163  163  -
```

Read step 10 against step 8. A store that had used `fr` as its cursor would have
written `rows[120..163]` at step 5 and `rows[154..163]` at step 8, double-writing
rows 120-153 and, on a restart between steps 8 and 9, losing nothing but having
written twice. At the last round the two cursors differ by exactly the final
round's output. §3.3 is that difference.

Rows a restart must replay: none. Every row past `dur` is derivable from the
rows below it by the same rules, which is what a fixpoint means. The store's job
is to skip the re-derivation, not to enable it. That makes `dur` a pure
optimisation cursor and U7 safe in both directions.

### The `want` row at rest

The brief cites `chat_log/20260913.2.dl8-host-annotation-want-rows-share-macro-self-host.md`
as the source for the runtime this store serves. That file does not exist in
this worktree; `ls chat_log/` returns no file with that name and no `.dl7` or
Rust file under `v8/` or `v7/` declares a `want` relation (`grep -rn "want("`
over `**/*.dl7` returns nothing). This plan therefore states the schema
consequence of a `want` row without claiming what its columns are, and fork 4
carries the measurement rather than a decision.

The nearest thing dl8 already runs is the intern request. `Kernel::Intern`
(`_4_kernel.rs:13`) makes the evaluator push a row into `intern_requests`
(`_5_evaluate.rs:200-202`), which the round drains into the `ref(kernel(intern))`
relation at `_5_evaluate.rs:628-632`. That is a demand row minted by the
evaluator, stored in the same `Store` as every derived row, with no state column
and no second table. If a `want` row follows that shape it needs no schema at
all beyond §6.

The standing decision on what a pending row means is
`rulings.pl:133-141`: cancellation is the kernel primitive, demand-row deletion
is the abort signal, and a demand whose refCount hits zero aborts the run and
deletes its pending cache row. A schema that cannot delete a pending row cheaply
contradicts that ruling, which is why fork 4 measures deletion cost rather than
update cost.

## 10. Retraction at rest

Two shapes, both live in this repo. This section states the schema consequence
of each and decides nothing: retraction is task 3 of the pending list and
`CLAUDE.md` reserves language design for Chris.

### 10.1 Delete-rederive, the v6 shape

`v6/prolog/lower.pl:4536` emits `DELETE FROM <head-table>` once per adjacent
same-head rule group, then one INSERT per clause of that group. The comment at
`lower.pl:4500-4516` records why the grouping exists: an unconditional DELETE per
clause wiped the previous clause's rows when two clauses shared a head.

| aspect | consequence |
|---|---|
| schema change needed | none; §6 runs it unchanged |
| write volume per tick | the whole derived relation, every tick it changes |
| measured cost | 1.55M rows/s on shape A (§13.2), so a 1M-row derived relation costs 0.65 s per tick |
| the 10-second law | crossed at roughly 15M rows in one derived relation, on this machine, at this shape |
| interaction with `durable` | `durable[rel]` resets to 0 on every DELETE; the cursor stops being monotone |
| interaction with the arena | none; terms are never deleted, so no dangling reference is possible |

### 10.2 Signed rows, the differential shape

A `sign INTEGER NOT NULL` column, `+1` for an arrival and `-1` for a departure,
with the true contents of a relation being the rows whose signs sum positive.

| aspect | consequence |
|---|---|
| schema change needed | `sign` column on every `<p>_row<a>` table |
| if `sign` joins the PK | a row can exist twice, `+1` and `-1`, and membership becomes `GROUP BY ... HAVING sum(sign) > 0` |
| if `sign` stays out of the PK | membership stays a PK probe, but flipping a sign is an UPDATE, measured 6x the cost of moving a row between tables (§13.5) |
| interaction with `Table` | `Table.rows` is an `IndexSet<Box<[TermId]>>` (`_3_table.rs:21`) with nowhere to put a count; a signed store needs a `HashMap<Box<[TermId]>, i64>` instead, which changes the kernel |
| interaction with `Table.index` | posting lists at `_3_table.rs:23` hold row ids and have no sign, so a probe returns cancelled rows and every caller filters |
| interaction with the oracle | `v8/tests/_0_eval_oracle.rs` compares closures byte-for-byte against v7, and v7 has no signed rows; a signed store must project back to unsigned before printing |
| write volume per tick | the delta only, never the whole relation |

The line that decides it: delete-rederive needs no schema change and no kernel
change, signed rows need both. Whichever Chris picks, §6 runs delete-rederive
today and would need one column plus a kernel change for signs. In either
direction the blocker is `Table`, and the schema is the cheap half.

## 11. Forks for Chris

Each fork names the site that forces the question, costs every option, and
carries this lane's recommendation. None of them is decided.

### Fork 1. Arena persistence: term table, or re-intern on load

Forced by `_0_term.rs:66-69`: a row cell is a `TermId`, which is an arena
position, so a row is meaningless without the arena that minted it.

| option | cost | note |
|---|---|---|
| persist `<p>_term` + `<p>_term_arg` | 0.05 s to write 100k terms and 33,332 args; 510 pages; 0.04 s to read 100k back (§13.3) | ids reproduce exactly, because they are IndexSet positions written in order |
| re-intern from the row tables on load | zero extra tables, but rows store TermIds, so there is nothing to re-intern FROM | not available: the cells are integers, not terms |
| re-intern from a JSON side-file | the existing `term_to_json` / `term_from_json` (`_6_json.rs:23-78`) already does it | a second source of truth beside the db, against one-server-one-db |

**Recommendation: persist the term table.** The second option is not actually an
option, because §1 shows a row cell is already an opaque integer; there is no
text left in a row to re-intern from. The measured cost is 0.04 s per 100k terms
on load, against a corpus whose whole distinct-subterm count is 1,587.

### Fork 2. Row layout: table per relation, table per arity, or row plus cell

Forced by `12_repeated_vars_and_arity.json` (one relation, two arities) and by
`_3_table.rs:21` (rows are variable-length boxed slices).

| option | insert, 200k rows, 3 samples | pages | tables for this corpus | verdict |
|---|---|---|---|---|
| table per relation | 0.13 / 0.12 / 0.13 s | 1,660 | 99, plus a split for the two-arity relation | fastest, and needs runtime DDL |
| table per arity, `rel` leading | 0.16 / 0.15 / 0.15 s | 1,771 | 8, fixed | 16% slower, no runtime DDL |
| row plus cell | 1.07 / 1.09 / 1.12 s | 5,520 | 2, fixed | 8.4x slower, 3.3x pages |

**Recommendation: table per arity.** The 16% sits on a seam measured at 11.9% of
a real fold's wall (sqlite-costs skill), so it costs under 2% of a tick. The
row-plus-cell shape buys schema uniformity for an 8.4x write penalty and a
membership test that stops being a single btree probe; it is the shape to reach
for only if arity stops being bounded, and §2 measures it bounded at 8.

### Fork 3. When to commit: per tick, per stratum, or per evaluation

Forced by `_5_evaluate.rs:535` (the stratum loop) and `:576` (the round loop).

| option | durability after a SIGKILL | statements per evaluation | re-derivation on restart |
|---|---|---|---|
| per tick | the last completed tick | 1 BEGIN + 1 COMMIT per tick | the in-flight tick only |
| per stratum | the last completed stratum | 2 per stratum, so `max_level + 1` pairs | the in-flight stratum |
| per evaluation | the last completed evaluation | 1 pair | everything, on any crash |

The sqlite-costs skill records one transaction per tick as a throughput wash on
the file-backed path (992/972 ms with, 984/993/998 without), so this fork is
about crash behaviour only.

**Recommendation: per tick.** A stratum boundary is not a consistent point for a
reader: `_5_evaluate.rs:535-640` runs strata in order and a higher stratum's
negation reads a lower stratum's completed rows, so a store opened between two
strata holds a closure no program ever asserted. A tick is the unit the outside
world names, and v6 already draws the line there (`sql.rs:271-280`).

### Fork 4. The `want` row at rest: one table with a state column, or two tables

Forced by `rulings.pl:133-141`: demand-row deletion is the abort signal, so
whatever shape is picked has to delete cheaply. No `want` relation exists in
this tree yet (§9), so both options are priced on 50,000 synthetic rows.

| option | move 50k rows pending to settled, 3 samples | what a state change costs |
|---|---|---|
| one table, `state` column, index on `state` | 0.06 / 0.06 / 0.06 s | UPDATE rewrites the WITHOUT ROWID key and the state index for every row |
| two tables, pending and settled | 0.01 / 0.01 / 0.01 s | INSERT ... SELECT then DELETE, both sequential btree work |

**Recommendation: two tables.** Measured 6x on the transition that the
cancellation ruling makes the hot one, and deleting a pending row becomes a
`DELETE FROM pending`, which is the abort signal spelled directly. The cost is
that "is this row wanted in any state" becomes a two-table read; that question
is asked at the boundary, not in the fixpoint.

Caveat named plainly: this is a measurement of two shapes, not of the real
workload, because the real workload has no code yet.

### Fork 5. Dictionary release: refcount, sweep, or never

Forced by `.github/CI-KNOWN-RED.md:110`, the memory-soak entry. v6's string
dictionary grows without bound: `INSERT OR IGNORE INTO "__str"` runs per distinct
text value (`v6/sprefa-engine-rs/src/text_plane.rs:141-160`), no `DELETE FROM
"__str"` exists anywhere in the tree, and the soak measured `page_count`
climbing 8 to 57 monotonically over 101 samples with `freelist_count` 0 at every
one. The entry names it a dictionary-release design decision, not a soak edit.

| option | cost | what it breaks |
|---|---|---|
| refcount per sym | a counter column plus a decrement on every row delete | `Universe.syms` is an `IndexSet` with no removal path (`_0_term.rs:54-60`); removing a sym shifts every later position, so every stored `TermId` moves |
| periodic sweep | one `DELETE FROM <p>_sym WHERE id NOT IN (SELECT sym FROM <p>_term)` | the same id-shifting defect the moment a row is actually removed |
| never release, with a rail | zero runtime cost; one test asserting the dictionary's page count against a ceiling | the file grows with the number of distinct strings the program has ever seen |

**Recommendation: never release, plus a ceiling rail.** The arena's ids are
positions in an append-only `IndexSet` (`_0_term.rs:28-33`), so releasing a sym
or a term is not a storage question at all: it invalidates every `TermId` in
RAM and on disk. Releasing requires an arena with a free list and stable ids,
which is a kernel change and needs Chris in the room. Until then the rail is
what the tree can actually check: measure the dictionary's page count, fail when
it crosses a stated ceiling, and treat a crossing as the trigger to design the
free list rather than as a number to raise.

| 1 | arena persistence | term table / re-intern | term table |
| 2 | row layout | per relation / per arity / row+cell | per arity |
| 3 | commit point | tick / stratum / evaluation | tick |

**rusqlite 0.40.2.** Already in this repository at
`v6/sprefa-engine-rs/Cargo.toml:13` with `features = ["bundled", "functions",
"limits", "hooks"]`, so the version is proven against this workload rather than
guessed. `bundled` compiles SQLite into the binary, which removes the system
SQLite from the equation: this machine's CLI is 3.43.2 and its Python links
3.53.2, and a store whose behaviour depends on which one it found is a store
that reproduces differently on two machines. The API is synchronous, which is
what the `CLAUDE.md` law asks for above the seam, and `v6/sprefa-engine-rs/src/sql.rs`
is 300+ lines of working precedent for the transaction, statement-budget and
prepared-cache shapes this plan reuses. The one real cost is compile time from
the bundled C, paid once per clean build.

**sqlx 0.9.0.** The most downloaded of the candidates and a genuinely good
library, with compile-time-checked queries that would catch a column typo in
§6's DDL at build time. Two things rule it out here. It is async to the core, so
taking it means a tokio runtime inside a CLI whose `v8/Cargo.toml:11-19` has no
runtime at all, and the `CLAUDE.md` law says async lives at the SQL seam and
nowhere above it; v6 paid that price already and confines it behind `SqlRunner`.
Its MSRV of 1.94.0 is also the highest in the table, and dl8 states no MSRV, so
adopting sqlx sets one by accident. The compile-time checking is the real loss
and worth revisiting if the DDL ever stops being generated from one place.

**turso 0.7.2.** The SQLite rewrite in Rust, formerly Limbo, actively released
(2026-07-30) with 900,429 lifetime downloads and 6 required dependencies. It
promises a pure-Rust build with no C, which would delete rusqlite's one real
cost, and an async-by-default API with io_uring on Linux. The reason not to take
it today is specific rather than dismissive: `v8/tests/_0_eval_oracle.rs` grades
dl8 byte-for-byte against v7 output, so any difference in collation, integer
affinity, or `INSERT OR IGNORE` conflict ordering shows up as an oracle failure
with the database as the suspect. A 0.7.x version number is the project saying
its edges are still moving. The right move is a re-measurement when turso reaches
1.0, not a bet now.

**limbo 0.0.22.** The same project under its old name, last published
2025-06-19 with 10,922 lifetime downloads. It exists on crates.io only as the
pre-rename artifact. Nothing to evaluate separately.

**libsql 0.9.30.** The fork SQLite-with-extensions the TypeScript door used, and
the source of the `reverse` scalar note at `v6/sprefa-engine-rs/src/sql.rs:295-297`.
Its 30 optional dependencies are the replication and remote-server machinery,
which is exactly the feature set a one-file local store has no use for. The TS
door is paused by user decision (`CLAUDE.md`, 2026-08-21), so the one argument
for matching it is gone.

**redb 4.2.0.** The cleanest dependency graph in the table: one required
dependency, pure Rust, MIT OR Apache-2.0, a real ACID embedded store with
typed tables. It would serve `Store` well, since `HashMap<TermId, Table>` is a
key-value shape before it is a relational one. The reason not to: it is not SQL,
so the file cannot be opened by `sqlite3`, inspected by hand, or queried by any
tool that already exists here, and the repo's standing posture is that a store's
query surface is plain SQL. Every join, index and aggregate in §6 would become
Rust code this lane would have to write, which is the build side of a
build-vs-buy question that the SQLite decision already answered.

**sled 0.34.7.** Last published 2021-09-12, five years before this measurement,
with 8 required dependencies. The project's own README has carried a "beta"
warning for years and its 1.0 has not landed. Fifteen million downloads say it
was widely trusted; the release date says a defect found today has no upstream
fix coming. The same not-SQL argument as redb applies on top.

**fjall 3.1.10.** Actively maintained (2026-08-30), an LSM-tree store with
separate key-value partitions and a write-ahead log. LSM is the right shape for
a write-heavy append-only log and the wrong shape for §10.1's delete-rederive,
where a derived relation is wiped and rewritten every tick: that pattern turns
into compaction pressure and write amplification in an LSM, where a btree just
rewrites its pages. The not-SQL argument applies here too.
