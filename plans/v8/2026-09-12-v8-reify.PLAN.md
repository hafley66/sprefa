(`0_evaluator.pl:73`) and stops there, so the key validator is ported here, in
`_5_reify/_5_validate.rs`, and moves to `_6_eval` when a lane owns that file.

The reifier is a pure function of its inputs. No file IO, no clock, no globals,
no statics. In the redux shape `Slice { State, Event, Context, Output, Effect }`
its `Effect` is `Never`, so no `fx: &mut dyn FnMut(E)` parameter is carried:
there is no effect to route. `&mut Universe` is the term arena, the same
parameter `_3_check` and `_6_eval` already take, not an effect channel.

## Storage layout, reads and writes, uniqueness

Rows and calls are `TermId` values in the one `Universe` arena
(`v8/src/_6_eval/_0_term.rs:25`). A row is the interned term, so row identity is
`u32` identity and `prolog_sort` (`v8/src/_3_check/_0_api.rs:51`) gives SWI
standard order with duplicates removed, which is what every v7 `sort/2` in this
subject does.

Occurrence ids are structural terms, never counters: `seed_id(I)`,
`rule_id(I)`, `call_id(seed, I)`, `call_id(rule(I), head)`,
`call_id(rule(I), goal(J))`, `argument_id(CallId, Position)`,
`argument_child(ArgumentId, input)`, `goal_occurrence(RuleId, Position)`.
They are stable because the checker has already fixed relation, seed, rule and
goal order (`0_logical_program_reifier.pl:12-14`).

Reads then writes, per entry:

1. read `Checked` or the case term, write the row vector;
2. read the row vector plus `CompilerFacts`, write calls and diagnostics;
3. read `CompilerFacts` once into `PreludeIndex`, a `HashMap<Sym,
   Vec<TermId>>` sorted and deduplicated per key, then answer every row's
   lookup from it. v7 re-runs `findall/3` over the whole fact list per row
   (`:126-134`); the map answers the same question in one pass. Same rows, same
   order, same diagnostics.

Uniqueness conditions:

- a prelude name maps to exactly one relation, else missing or ambiguous;
- an artifact name maps to exactly one output relation, else
  `duplicate_artifact_name`;
- a functional key tuple selects exactly one row per relation, else
  `functional_key_conflict`.

## Oracle

`v8/oracle/reify/dump_reify.pl` wraps all seven exported predicates with
`wrap_predicate/4` and writes one JSON case per call, using the term encoding of
`v8/oracle/eval/json_terms.pl`. `v8/oracle/reify/freeze.sh` pins `REV` to
`f5018ad23`, `git archive`s v7 into `/tmp/dl8-reify-oracle` so no committed byte
carries a worktree path, and runs three modes:

| mode | driver | result |
|---|---|---|
| `compile` | `compile_dl7/4` over all 42 `.dl7` files under `v7/test/fixtures/` and `v7/applications/` | 0 reifier calls on every one. The compiler never reaches `src/3_emit`; this mode is the receipt for that claim. |
| `test` | the five v7 plunit suites that name `emit_compiled/4` or `logical_program_rows/2` | the real calls |
| `case` | each `v8/oracle/reify/cases/*.pl` | one authored program per diagnostic reason, 3-17 KB per case |

The five suites are exactly the output of
`grep -ln "emit_compiled\|logical_program_rows" v7/test/*.pl`: `1_entrypoints`,
`9_dbsp_plan`, `15_interned_storage`, `16_storage_plain_field`,
`17_dl6_interned`.

`1_entrypoints` reports three failing tests at `f5018ad23`, before any wrapper
is installed, because `v7/test/fixtures/5_curry.dl7` no longer compiles:
`compile_dl7/4` returns `source_refreeze_limit_exhausted(16)`, thrown at
`v7/src/2_comptime/2_compiler.pl:833`. Reproduced at two different staging path
lengths, so it is not a staging artifact. It costs the suite-driven coverage of
the `prolog`, `monomorphic_datalog` and `relational_program` arms; the authored
cases 0, 1, 2 and 14-16 cover all four arms instead.

Committed-set rule: every authored case, every suite case at or under 64 KB,
and the smallest over-limit case of each entry kind, so each entry is proven
once against a real compile without a megabyte per entry. `status.json` carries
the counts, the skip list and the uncovered diagnostic reasons.

`v8/tests/_7_reify_oracle.rs` runs `dl8 reify <case.json>` through
`env!("CARGO_BIN_EXE_dl8")` and compares every field of `expected` byte for
byte, plus the exit code.

| calls dumped | 131 |
| byte distinct | 91 |
| committed | 57 files, 3.74 MB |
| distinct checked, not committed | 34, all swept green through the binary |

## Forks

Behaviors v7 has that a redesign would change. All are kept exactly as v7 has
them.

1. **A `reference` argument target is wrapped on the calls path and unwrapped on
   the graph path.** `logical_argument_target/2`
   (`0_logical_program_reifier.pl:113-116`) wraps every `ref(Identity)` target as
   `ref(logical_program(Identity))`, including the `reference` label whose
   identity is a relation, not an occurrence. `argument_target/3`
   (`0a_logical_program_grapher.pl:115-120`) special-cases `reference` and leaves
   it unwrapped. The same edge therefore reads two ways depending on which door
   produced it.
2. **`program_rule_kind` is always `level`.** `rule_rows/3`
   (`0_logical_program_reifier.pl:228`) writes the atom `level` for every rule
   with no reference to the rule. The row exists but carries no information.
3. **The dl7 arm returns `artifacts([])` rather than `[]` when key validation
   fails.** Every other diagnostic path returns the bare list `[]`
   (`1_artifact_emitter.pl:69`, `:104`, `:116`). `continue_dl7_emitter_refs/5` at
   `:107` fixes the functor `artifacts/1` in the clause head before the
   diagnostics are known, so a `functional_key_conflict` yields
   `artifacts([])`. `cases/8_emit_functional_key_conflict.pl` freezes it.
4. **`materialize_artifact_refs/5`'s third argument is named `CompilerFacts`
   at `:231` and `:240` but is the evaluation closure.** Name only, no
   behavior; the port names it `rows`.
5. **Polarity is a string on the calls path and an atom on the graph path.**
   `logical_row_arguments/2` at `0_logical_program_reifier.pl:162-168` runs
   `atom_string/2`, so `program_goal` carries `const("positive")`.
   `logical_graph_row/2` at `0a_logical_program_grapher.pl:63-65` passes the
   atom through, so the same fact reads `const(positive)`. Frozen in
   `case-11_calls_all_relations_1.json` and `case-13_graph_calls_1.json`.
6. **`logical_row_call_if_requested/4` looks the relation up twice** on the
   filtered path, once in `logical_row_relation/3` (`:90`) and again inside
   `logical_row_call/3` (`:110`). The port looks it up once. Same answer, same
   diagnostics, because the lookup is a pure function of the fact list.

## `CompiledUnit` versus `_4_comptime::Compiled`

`compiler_view/2` and `emit_compiled/4` take
`compiled_unit(TypeGraphFacts, RuntimeProgram, CompilerFacts)`
(`1_artifact_emitter.pl:23`). A parallel lane is porting the comptime output as
`pub struct Compiled` under `v8/src/_4_comptime/_1_api.rs`, with fields named
after the same three functor arguments, and that file does not exist on this
branch yet. This lane therefore declares `CompiledUnit` in
`v8/src/_5_reify/_0_api.rs` with those three fields and builds it from JSON with
`crate::_6_eval::json`. After both PRs land, the coordinator deletes
`_5_reify::CompiledUnit` and repoints `compiler_view` and `emit_compiled` at
`_4_comptime::Compiled`. The two structs must agree field for field; nothing
else in `_5_reify` reads the unit.
