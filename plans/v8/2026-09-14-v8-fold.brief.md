## 1. Job
One fold path in the evaluator. `count`, `sum`, `min`, `max` become instances of `Fold { seed, step, order }` where `step` is any 3-ary relation (kernel `int_add`, or a program rule) and `order` is `term_lt`. A program can declare its own aggregate as a rule head carrying `(fold <step> <seed> ?X)`. A `linear(Step)` fact table in the kernel registry records which steps admit incremental lowering later; nothing incremental is built here. The Rust folds for the four builtins stay as the fast path and are proven equal to the generic path on every existing fixture.

## 5. Design (decided)
Astra's objection is accepted as scope: this lane changes nothing about when aggregate rows are recomputed (whole-group recompute per evaluation, as today) and nothing about retraction. It changes only HOW a group folds.

```rust
// v8/src/_6_eval/_1_program.rs
pub struct Fold {
    /// 3-ary relation called as (step ?Acc ?Value ?Next); kernel or program rule.
    pub step: TermId,
    pub seed: TermId,
    /// Values are visited in term_lt standard order; the fold is deterministic
    /// even when step is not commutative.
    pub order: Order,          // enum Order { TermLt }  (one variant now)
}
pub enum Arg { Var(VarId), Ground(TermId), Aggregate(AggregateKind, Box<Arg>), Fold(Fold, Box<Arg>) }
impl AggregateKind { pub fn as_fold(self, u: &mut Universe) -> Fold; }
//   Count => step (kernel count_step ?Acc ?_ ?Next) i.e. int_add with 1, seed 0
//   Sum   => step int_add, seed 0
//   Min   => step (kernel min_step) built on term_lt, seed = first value
//   Max   => step (kernel max_step), seed = first value

// v8/src/_6_eval/_5_evaluate.rs
/// Generic path: sort values by term_lt, then run step as a goal per value.
fn fold_generic(u, cx, fold: &Fold, values: &[TermId]) -> Result<TermId, Diagnostic>;
//   acc = seed; for v in sorted(values): acc = solve (step acc v ?next) expecting exactly one row,
//   zero rows => Diagnostic fold_step_no_row(step, acc, v); two+ => fold_step_ambiguous
/// Fast path stays: fold_group(kind, values) for the four builtins.
/// Under cfg(test) both paths run and must agree; the equality is the COUNT-style receipt.

// v8/src/_6_eval/_4_kernel.rs
/// linear(step): the step admits an incremental lowering. Facts only; nothing consumes them yet.
pub fn linear(step: &str) -> bool;   // int_add => true; count_step => true; min_step, max_step => false
```
Surface spelling, ONE form, taken as an assumption and flagged to Chris in the PR: a rule head position may carry `(fold <step-name> <seed-term> ?X)` beside the existing `(count ?X)` etc. The four builtins become macrotime macros over fold (`(sum ?X)` expands to `(fold int_add 0 ?X)`) ONLY if the expansion keeps every `v8/oracle/**` and `v8/fixtures/**` expected file byte-identical; if it does not, keep the builtins as `AggregateKind` and write the macro as a fork in the PR, do not refreeze oracles.
Instance lifetime: `Fold` is part of `Rule`, lives as long as the `Program`. Storage: none new. Uniqueness: one aggregate position per head, as today (`malformed_aggregate_head`).
