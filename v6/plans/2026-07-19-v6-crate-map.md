# V6 crate map — boundaries, the math, and the size budget

## Context

V5 is a two-crate workspace that is really one crate: `sprefa-dl` (lib
`sprefa_v5`) holds CLI, daemon, LSP, MCP, extraction, query compiler, and
storage (root `Cargo.toml:7-10`); `tree-sitter-dl` is a vendored grammar.
**89,151 lines of Rust** (`wc -l` over `src/`, 2026-07-19 @ `8d7b6092`,
includes inline tests/comments).

The seams exist but are soft:

- The DB seam (`src/db.rs`, `src/storage.rs`) is a *statement-execution*
  boundary, not a storage boundary — ~30 counted verbs, but SQL text lives at
  call sites in ~40 files, and `format!`-spliced SQL appears in `derive.rs`
  (33 sites), `extract/mod.rs` (25), `symbols.rs` (16), `declare.rs` (15).
  Burn-down record: `plans/2026-07-18-db-seam-migration.md`; rail:
  `.dl/no-new-rusqlite.dl`.
- Three JSON-RPC dialects: HTTP envelopes (`src/rpc.rs`), LSP Content-Length
  stdio (`src/lsp.rs`), hand-rolled NDJSON stdio (`src/channel.rs:29-70`).
- Every protocol has a duplicated in-proc fallback: MCP's `Pump::Daemon` /
  `Pump::Local` (`src/mcp.rs:49-68,71-180`), LSP's mirrored RPCs
  (`src/lsp.rs:532,547,591`) with its own `Engine::new` (`src/lsp.rs:130`),
  CLI's `DL_NO_DAEMON` path (`src/cli/mod.rs:394-397`).
- Every client call builds a private tokio runtime
  (`src/daemon_client.rs:32-58`).

The 2026-07-18→19 infra arc (commits `dc774375`, `c9b04d21`, `8d7b6092`; plan
`plans/2026-07-18-infra-library-adoption.md`) proved library-first works. V6
generalizes it: the boundaries become crates, and crates don't negotiate.

## The practicality ruling (owner, 2026-07-19)

Crates are **dependency firewalls**, not architecture art. This plan splits
exactly where a boundary walls off dependencies or ratchets a size ceiling —
and nowhere else. Concretely:

- **Concrete types until a second implementation actually arrives.** This is
  the owner's own 2026-07-18 ruling (`.dl/no-new-rusqlite.dl:5-8`: the seam
  stays a struct; it becomes a trait when a second backend arrives),
  generalized to every V6 boundary. `Engine` has concrete fields, not
  `Engine<S: Store, G: GraphSource>`. Where multiplicity is real, a trait is
  already earned and stays — `EffectExec` has the shell executor and test
  mocks (`src/effect.rs`). The rule is "second implementation," never
  "never traits."
- **No DI containers, no generic-for-generics'-sake.** The "proper DB API"
  is a clean concrete object in the Python sense, not a trait lattice.
- **Reactive machinery tops out at BehaviorSubject + combineLatest** — and
  dl already *is* that layer: a port is a subject, a rule join is
  combineLatest, `@next` is a BehaviorSubject. Do not build observer or
  event-bus machinery in Rust to serve the language.
- **No crate-per-concept.** `sprefa-telemetry` died in committee: one
  `init()` does not earn a firewall; it is a module in `sprefa-server`.
  Seven crates, each with a firewall justification.

## The backend-neutrality ruling (owner, 2026-07-19)

**The backend is configuration, not identity.** The storage API speaks rels,
rows, keys, and plans — never SQL text, never a driver type, never a
SQLite-ism. All SQL generation (repository queries *and* fixpoint codegen)
goes through the **sea-query** builder with the dialect as config; SQLite is
the first backend, not the permanent one. Neutrality is enforced by a
greppable API rail, not deferred to a trait someday — the trait still
arrives only with the second backend, per the practicality ruling. Full
design: [the storage plan](2026-07-19-v6-storage-crate.md).

## The demand ruling (owner, 2026-07-19)

**Nothing computes without a subscription.** V5 is eager: a live root ticks
its whole program until it idle-reaps. V6 rels are cold observables — a
refcounted subscription over `(root, query rel)` activates that query's
static dependency cone (including the cross-repo cut), ticks compute only
active cones, and the last unsubscribe puts the cone back to sleep. Full
design: [the demand plan](2026-07-19-v6-demand.md).

## Sync/async ruling (owner pushback, 2026-07-19)

The server is **fully async** — axum, rmcp, tower-lsp, and the storage
boundary too. The only sync zone is the tick hot path, and it is sync on
evidence, not taste: a fixpoint issues thousands of tiny prepared statements
per tick against a local file and *waits on nothing* — async's one job is
harvesting wait time, and there is none to harvest. Making 26K lines of
engine async for that is colored-function tax for zero gain.

The split:

- `Store` — sync, owns the single writer connection, lives on the writer
  thread. The engine talks to it directly; hot path stays fast and dumb.
- `StoreHandle` — cloneable async handle the **server** holds: reads fan out
  to a reader pool, writes serialize through the writer thread. ~100 lines
  of channel plumbing (actor pattern — the one piece no library sells; same
  shape as Zed's sqlez and atuin's single-writer daemon).
- Nobody calls `spawn_blocking` per request. Server code is 100% async.

Escape hatch is a measurement, not an argument: the bench todo below
(rusqlite vs sqlx driver performance on the real tick workload). If sqlx
lands within noise, the writer thread goes async and the bridge shrinks.

## Size budget

The File-Size Law already governs files (`scripts/filesize-rail.sh`,
2026-07-11: hard 500/file, target 300, `filesize-allow.txt` ratchets down
only, CI diffs it; 36 grandfathered today). V6 extends the **same mechanics
one level up**: per-crate ceilings in `scripts/crate-size-allow.txt`,
ratchet-down-only, CI diffed. A crate over ceiling fails the rail; lowering a
ceiling is always allowed; raising one needs a plan pointer.

Starting ceilings = verified V5 measurements of the code being extracted,
minus committed deletions:

| crate | ceiling | verified basis |
|---|---|---|
| `sprefa-lang` | 5,500 | parse 1,626 + typecheck 1,457 + ast 749 + frontend 635 + lower.rs minus SQL emission |
| `sprefa-store` | 9,500 | db.rs 2,052 + storage.rs 385 + storage/ 1,938 + meta 1,570 + declare 1,167 + staged_delta 984 + cold_stage 503 + symbols 665 + codegen-on-sea-query ~400 + StoreHandle ~100 (arc must find ~300 lines of consolidation on entry) |
| `sprefa-graph` | 12,500 | graph/ 12,379 as-is — fenced, ratchet pressure starts here |
| `sprefa-rels` | 3,700 | rels/ 2,575 + decls.rs 1,093 |
| `sprefa-engine` | 26,000 | 32,060 − 5,982 stripped |
| `sprefa-server` | 8,500 | daemon 4,490 + lsp 1,406 + mcp 545 + rpc/channel/client/supervise/trails + trace-init module − ~730 deletions below |
| `sprefa-cli` | 2,500 | cli/ 1,865 + rendering |

Committed deletions (extraction must delete, not only move):

- hand-rolled NDJSON stdio channel (`src/channel.rs`) — rmcp replaces it
- retired Content-Length codec (`src/rpc.rs:22-78`)
- MCP `Pump::Local` duplicate path (`src/mcp.rs:71-180`)
- in-proc LSP engine + mirrored RPCs (`src/lsp.rs:130,532,547,591`)
- `DL_NO_DAEMON` in-proc path (`src/cli/mod.rs:394-397`)
- one of the two build-mismatch restart mechanisms
  (`client.rs:91-111` vs `budget.rs:187-212` — versioned socket kills both,
  keep neither)
- runtime-per-client wrapper (`src/daemon_client.rs:32-58`)

Candid total: identified deletions are **~730 lines, 0.8% of the codebase**.
The ceilings + ratchet are the control mechanism; the real headroom is
unknown until the duplication census (todo below) runs. Every extraction arc
reports lines **moved vs deleted**; a move-only arc needs a written excuse.

## Decisions

Seven crates, dependency direction strictly downward:

| crate | owns | may depend on | may NOT depend on |
|---|---|---|---|
| `sprefa-lang` | AST, grammar, lowering, spec, diagnostics | nothing in-workspace | tokio, rusqlite, axum — anything with IO |
| `sprefa-store` | all persistence: schema, migrations, interning, delta stores, sea-query SQL generation (dialect = config); sync core + async `StoreHandle` | lang, tokio (channels), sea-query, one driver crate | axum; any second driver |
| `sprefa-graph` | CSR snapshots (`petgraph::Csr`), graph algorithms (call/type/module/df); per-language construction stays custom | lang, store, petgraph | rusqlite, tokio |
| `sprefa-rels` | builtin relation families + their decls | lang, store | rusqlite, graph (keep it leaf-simple) |
| `sprefa-engine` | tick loop, fixpoint, derivation, dependency-cone demand | lang, store, graph, rels | rusqlite, axum, tokio |
| `sprefa-server` | singleton lifecycle, all transports, trace init, subscription registry | engine, store, lang | — |
| `sprefa-cli` | clap, rendering, daemon ensure | server (client lib) | engine, store, rusqlite |

Rejected:

- **sqlx for the tick hot path** — see the sync/async ruling above: nothing
  to await inside a fixpoint, and an async engine pays colored-function tax
  for it. The server side is async regardless via `StoreHandle`. Flips if
  the bench todo shows parity.
- **ORMs (diesel/sea-orm)** — schema DSLs can't model generated `rel_*` tables;
  magic we don't need. The sea-query *builder* (no ORM) is the adopted
  middle.
- **String SQL anywhere** — sea-query AST or it doesn't ship; `format!`
  splicing is the V5 disease being cured.
- **In-proc fallback modes** — the source of every duplicated code path above.
  One anonymous-daemon path replaces them all (singleton math below).
- **Graph inside engine** — 12.4K lines of self-contained algorithms over
  adjacency data; owning the CSR snapshot API is what fixes the memory
  amplification. Its own crate makes that API a boundary, not a convention.
- **DI containers / blanket generics** — see the practicality ruling above.
  Concrete fields; a trait appears when its second implementation does.
- **A telemetry crate** — one `init()` is a module in `sprefa-server`, not a
  firewall.
- **Rewriting** — extraction order is one crate per arc, hollow types first.

## Extraction order

Sized by the census, cheapest-and-most-depended-on first:

1. **lang** (~4.2K + ast/frontend) — pure, small, everything depends on it.
   SQL emission moves out to store as part of this arc.
2. **store** (lands at ~9.5K) — the seam already exists (`db.rs` verbs); this
   arc absorbs it plus the storage code stripped from `engine/` (meta,
   declare, staged delta, cold stage, symbols). Engine sheds ~4.9K here.
   `StoreHandle` + the writer thread + the sea-query codegen land in this
   arc too.
3. **graph** (12.4K) — self-contained; defines the CSR snapshot API that
   engine consumes.
4. **rels** (3.7K incl. decls.rs) — small, leaf, depends only on lang+store.
5. **engine** (~26K after the strip) — extracted last of the library crates,
   fenced at its ceiling, shrunk by later arcs. The tick signature gains the
   demand cone here (demand plan).
6. **server + cli** — per the daemon plan; lands last because it serves
   everything above. The trace-init module and the subscription registry
   land here.

## Type math

Hollow first. No call site moves until a human reviews the set. Concrete
types, per the practicality ruling:

```rust
// sprefa-lang — pure data. No IO, no async, no DB types, ever.
pub struct Program { pub decls: Vec<RelDecl>, pub rules: Vec<Rule> }
pub struct LoweredPlan { /* backend-neutral physical ops */ }

// sprefa-store — concrete API object, Python-style. Speaks rels/rows/plans;
// no driver or dialect type appears in any signature. Becomes a trait only
// when a second backend arrives.
pub struct RepoRev { pub repo: RepoId, pub rev: RevId }  // on every call, never ambient
pub enum BackendConfig { Sqlite { path: PathBuf }, /* Postgres { .. } later */ }

/// Sync core. Lives on the writer thread; the engine uses this directly.
pub struct Store { /* one writer connection, backend-chosen */ }
impl Store {
    pub fn open(home: &Path, backend: BackendConfig) -> Result<Store>;
    pub fn migrate(&self) -> Result<SchemaVersion>;
    pub fn tx(&self) -> Result<Tx>;                // single writer
    pub fn rows(&self, rel: RelId, at: &RepoRev, key: &Key) -> Result<Rows>;
    pub fn one(&self, rel: RelId, at: &RepoRev, key: &Key) -> Result<Option<Row>>;
    pub fn exec_plan(&self, tx: &mut Tx, plan: &LoweredPlan, at: &RepoRev) -> Result<Delta>;
}

/// Async handle for the server: reads fan out to a reader pool, writes
/// serialize through the one writer thread. Cloneable; ~100 lines of
/// channel plumbing (actor pattern).
#[derive(Clone)]
pub struct StoreHandle { /* tokio mpsc to the store threads */ }
impl StoreHandle {
    pub async fn rows(&self, rel: RelId, at: &RepoRev, key: &Key) -> Result<Rows>;
    pub async fn write<F, T>(&self, f: F) -> Result<T>
    where F: FnOnce(&Store) -> Result<T> + Send + 'static, T: Send + 'static;
}

// sprefa-graph — concrete cache. Same rule: trait on second implementation.
pub struct Csr { /* compressed adjacency for one (rel, rev) */ }
pub struct GraphCache { /* Arc<Csr> per (rel, rev), invalidated on tick commit */ }
impl GraphCache {
    pub fn csr(&mut self, rel: RelId, at: &RepoRev) -> Result<Arc<Csr>>;
}

// sprefa-engine — concrete fields. No generics, no DI.
pub struct Engine { store: Store, graphs: GraphCache, /* tick state */ }
impl Engine {
    /// Computes only the demanded dependency cones (demand ruling).
    pub fn tick(&mut self, at: &RepoRev, demand: &Cone) -> Result<TickReport>;
}

// sprefa-server — owns the singleton, the subscriptions, and every
// transport. Sees StoreHandle, never Store.
pub struct Daemon {
    engines: Map<Root, Engine>,
    store: StoreHandle,
    subs: SubscriptionRegistry,   // per-root union of active cones
    listeners: Listeners,         // UDS + ephemeral TCP
}

// sprefa-cli — parses, connects, renders. No traits.
```

Key move: SQL *generation* (today `src/lower.rs` → `exec_derived`) moves
**into** `sprefa-store` as sea-query builders consuming `LoweredPlan` from
`sprefa-lang`, rendered for the configured dialect at execution. That makes
"no SQL text outside store" a greppable invariant — and the backend a config
choice, not an identity.

## Struct math

- One `Daemon` per user. Owns N `Engine`, one per served root.
- One `Store` per corpus database, owned by a single writer thread; engine
  ticks run on that thread, so the hot path is plain sync calls.
- The server never sees `Store` — it holds a `StoreHandle` (reads fan out
  to the reader pool; writes serialize through the writer thread).
- One `SubscriptionRegistry` per daemon: refcounted `(root, query rel)`
  handles, reduced to a union of active cones per root; that union is the
  only `demand` an engine ever sees.
- One `GraphCache` per engine; invalidates per `(rel, rev)` on tick commit.
- `RepoRev` is a **value parameter** on every storage/engine/graph call. V5's
  bug class "repo baked into sym strings" is impossible when the coordinate
  is a column the API forces you to pass.
- `LoweredPlan` is produced by lang, executed by store, opaque to engine.

## Singleton math

Exactly one server per user, plus anonymous servers for one-shots:

- **Path:** `$XDG_RUNTIME_DIR/sprefa/v<maj.min>.sock` (macOS fallback:
  `$TMPDIR/sprefa-$UID/`). **Version in the filename** — client computes the
  path from its own version, so a stale daemon is simply the wrong socket and
  the right one gets spawned. This deletes *both* V5 build-mismatch
  mechanisms (`src/daemon/client.rs:91-111`, `src/daemon/budget.rs:187-212`).
- **Liveness:** connect-probe only. Pidfiles are informational; the flock
  (V5 already has this, `src/daemon/home.rs:109-122`) stays as the
  single-instance witness.
- **Ensure:** explicit verbs spawn; implicit paths attach or fail
  (`DL_AUTOSTART=1` opt-in, same policy as V5 `client.rs:113-121`). Plus
  `dl socket-path --ensure` prints the socket path, spawning if needed
  (watchman `get-sockname` pattern).
- **Anonymous:** `dl run …` spawns
  `sprefa-server --socket $TMPDIR/sprefa-<uuid>.sock --idle-exit 120 --die-with-parent`,
  talks to it, walks away. One code path — client→server — always. This
  deletes `Pump::Local`, the in-proc LSP engine, and `DL_NO_DAEMON`.

## Dataflow math

```
demand:   client subscribe(Q) → registry activates cone(Q) (+ cross-repo cut)
          → ticks compute active cones only → last unsub → cone cold
write:    watcher / CLI   → RPC → StoreHandle.write → writer thread →
          Engine.tick(RepoRev, demand) → corpus db
read:     CLI / LSP / MCP → RPC → StoreHandle read pool → render client-side
graph:    sprefa-graph builds CSR adjacency once per (rel, rev); engine and
          algorithms borrow the Arc. Never derive adjacency per query —
          that is the V5 memory amplification.
reactive: a port is a subject; a rule join is combineLatest; @next is a
          BehaviorSubject. The language IS the reactive runtime — no
          observer/event-bus machinery in Rust to serve it.
```

One corpus database, `(repo, rev)` as columns, backend chosen by config —
see the storage plan.

## Verification

- **Dependency rails** (script or CI):
  `cargo tree -p sprefa-lang | grep -Ei 'rusqlite|tokio|axum'` must be empty;
  same shape for each row of the may-NOT column.
- **Persistence rails:** zero `rusqlite::`, `sqlx::`, `sea_query::` outside
  `sprefa-store`; zero `format!` SQL anywhere; `sprefa-store`'s public API
  names no driver or dialect type (neutrality is greppable, CI-enforced).
- **Crate-size rail:** `scripts/crate-size-rail.sh` checks each crate against
  `scripts/crate-size-allow.txt`; the ceilings file may only shrink (CI diff),
  mirroring `filesize-rail.sh` mechanics. The file-level law is unchanged.
- **Move-vs-delete report:** every arc prints lines moved and lines deleted.
- **Isolation:** `cargo check -p <crate>` passes per crate with hollow types.
- **Anonymous e2e:** `dl run examples/<x>.dl` spawns an anonymous server and
  the CLI binary contains no `Engine` (no `sprefa-engine` dep — enforced by
  the dep rail, not by hope).
- **No spawn_blocking per request:** server handlers use `StoreHandle`
  (async); grep rail for `spawn_blocking` in `sprefa-server` outside the
  writer-thread bridge.
- **Demand:** zero-subscriber roots never tick; a cold one-shot computes
  only the query's cone (demand plan's tests).
- Each extraction arc ends green on `scripts/verify.sh` before the next starts.
