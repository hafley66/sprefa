# V6 demand — cold by default, Observable + subscribe

> **2026-07-23 banner:** the mechanism here is fully canonical, restated as
> the subscription law (R3): no daemon concept, process lifetime = sum of
> held subscriptions. Only the Rust-crate vocabulary is stale.

## Context

V5 is eager: every served root ticks its **whole program** whenever a watcher
or poll fires, and only stops when the root idle-reaps after 30 minutes
(`src/daemon/shell/timers.rs:15-40`). `@async` and `@next` were the first
cracks in that eagerness, but the default is still "compute everything, keep
it warm forever."

At the corpus vision — hundreds of repos, one network — eager means
computing the world to answer one question. Owner ruling (2026-07-19): in V6
**nothing computes without a reason, and the reason is a subscription.** The
RxJS model: cold `Observable` + `subscribe`, refcounted.

## Decisions

**Rels are cold observables.** No subscription, no computation. This
completes the reactive mapping from the crate map — port = subject, join =
combineLatest, `@next` = BehaviorSubject — with the piece it was missing:
*cold until subscribed*.

**A subscription is a refcounted handle over `(root, query rel)`.** Sources:

- **LSP open document** → diagnostics/hover cone for that file; unsubscribes
  on close.
- **MCP tool call / CLI one-shot** → subscribe, `take(1)`, unsubscribe.
- **dl-declared `@serve` route** → standing subscription while the route is
  registered (see the language-interfaces plan).
- **File watcher** → standing subscription to *source* rels only —
  extraction stays warm and incremental; derived layers go cold.

**Demand granularity is the dependency cone, not the tuple.** The lowered
program's static rel-dependency graph gives `cone(Q)`; subscribing activates
it, and a tick computes only active cones. No salsa rewrite. Per-tuple
demand is rejected for now — revisit only on profiling evidence.

**Cross-repo demand propagation.** A subscription on repo A that reads repo
B's rels activates B's cone too. You only ever compute the *subscribed cut*
of the network — this is the amplification control for the corpus vision,
and it costs nothing when idle.

**Unsubscribe → cold.** The cone stops ticking within one poll cycle.
Derived rows stay on disk as warm cache by default; retraction policy is an
open todo below.

`@async` / `@next` are unchanged — they were the first laziness; this
generalizes it.

## Type math (delta on the crate map)

```rust
pub struct Subscription { pub root: Root, pub query: RelId, /* refcounted */ }
pub struct SubscriptionRegistry { /* per-root union of active cones */ }

// engine:
impl Engine {
    pub fn tick(&mut self, at: &RepoRev, demand: &Cone) -> Result<TickReport>;
}

// daemon:
pub struct Daemon {
    engines: Map<Root, Engine>,
    store: StoreHandle,
    subs: SubscriptionRegistry,
    listeners: Listeners,
}
```

Wire protocol: `subscribe` / `unsubscribe` RPCs; standing subscriptions push
over the existing SSE `/watch` channel (`src/daemon/shell/http.rs:176-181`).
A one-shot query is subscribe + `take(1)` internally — same path, no second
implementation.

## Dataflow math

```
demand:   client subscribe(Q) → registry activates cone(Q) (+ cross-repo cut)
          → ticks compute active cones only → last unsub → cone cold
```

## Verification

- **Zero subscribers:** a served root with no subscriptions produces no
  ticks and no extraction — provable as silence in `events.jsonl`.
- **Cold one-shot:** a one-shot query on a cold root computes `cone(Q)` and
  nothing else — rel count vs the eager baseline, printed by the test.
- **Last unsubscribe:** tick activity for the cone stops within one poll
  cycle.
- **Cross-repo:** a subscription touching repos A+B computes the cut in both
  and nothing outside it.
- **MVP:** in the ghcacher program, the served route's standing subscription
  is the *only* thing keeping the poll cone warm — kill the route, polling
  stops.
