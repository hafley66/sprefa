# V6 delivery — vertical slices, and what crosses each boundary

> **2026-07-23 banner:** the slices/crate-arithmetic below are stale
> (pre-pivot). Still canonical: the kill-number slice discipline, the
> FileExtract/ProjectExtract split, and the v5 baseline numbers (`_strings`
> 65.4MB, df 163.6MB, wake median 3/255).

## Context

The schema in `2026-07-19-v6-schema.sql` is not half-migratable: you cannot
run V5's coordinate-string model and V6's surrogate spine against the same
tables. But V6 can be *built alongside* V5 and fed by an importer, which
makes slices 0-2 pure addition at zero risk to the shipping tool.

Slicing rule: **every slice ends in a number that could kill the thesis.**
Not "the crate compiles" — a receipt. The two claims under test are (a) the
storage model is 4-6x smaller, (b) demand means a median of 3 of 255 rels
wake. A slice that cannot falsify one of those is not a slice, it is busywork.

## Inter-crate math

### The typed core already exists in V5 — derive it, do not invent it

Working backwards from V5 is the correct move here, because the pure
extraction seam is **already written and already storage-free**. Two traits
cover all four families:

```rust
// src/graph/typegraph/mod.rs:417 — types, calls, dataflow
pub trait TypeLang: Sync {
    fn name(&self) -> &'static str;
    fn matches(&self, path: &str) -> bool;
    fn extract(&self, file: &str, content: &str) -> TypeFacts;
    fn extract_calls(&self, file: &str, content: &str) -> CallFacts;
    fn extract_dataflow(&self, file: &str, content: &str) -> DataflowFacts;
    fn extract_bundle(&self, file: &str, content: &str, mask: AnalysisMask)
        -> AnalysisBundle;                        // one parse, many projections
}

// src/graph/modgraph/mod.rs:171 — modules
pub trait ModuleResolver: Send + Sync {
    fn exts(&self) -> &'static [&'static str];
    fn edges(&self, file: &str, content: &str, cx: &ProjectCx) -> Vec<ModuleRef>;
}
```

Neither touches a database. Both take `(path, content)` and return plain
facts. Three things V5 already got right that V6 keeps verbatim:

1. **`AnalysisMask` / `AnalysisBundle`** (`typegraph/mod.rs:448-460`) is the
   demand cone, already built, at the extraction layer: extract only the
   families asked for, sharing one parse. V6 does not invent this — it
   extends the mask with `modules` and wires it to the subscription cone.
2. **`ProjectCx.reader: Option<&dyn Fn(&str) -> Option<String>>`**
   (`modgraph/mod.rs:96`) is the IO seam, already a closure. That single
   field is why extract can be lifted into its own crate without a store
   dependency: the blob reader is injected, never imported.
3. **`ProjectCx`'s `OnceLock` per-language indexes** (`RustCrates`,
   `KotlinIndex`, `GoIndex`, `ts_packages`, `python_roots`) are lazy
   whole-project state built once per refresh — the right shape already.

The two traits differ in exactly two places, and unifying them is a ~30-line
change, not a redesign:

| | `TypeLang` | `ModuleResolver` | unified |
|---|---|---|---|
| path recognition | `matches(path)` | `exts()` | `matches(path)` |
| project context | none (per-file) | `&ProjectCx` (needs the file set to resolve a specifier) | always passed; per-file extractors ignore it |

Two shapes, and they stay two traits on purpose — the difference is the
**cache key**, which is too important to erase for tidiness:

```rust
/// "here is a code file, get data" — a PURE function of content.
/// Cache key: (blob_hash, lang, mask). Content-addressed, so a file
/// byte-identical across 50 revs or 50 repos extracts exactly ONCE.
pub trait FileExtract: Sync {
    fn name(&self) -> &'static str;
    fn matches(&self, path: &str) -> bool;
    fn extract(&self, path: &str, content: &str, mask: FamilyMask) -> FileFacts;
}

/// "here is a codebase, get data" — depends on the whole file set.
/// Cache key: (blob_hash, project_digest, mask). Invalidated whenever a
/// file appears or disappears, because that can change a resolution.
pub trait ProjectExtract: Sync {
    fn name(&self) -> &'static str;
    fn matches(&self, path: &str) -> bool;
    fn resolve(&self, path: &str, facts: &FileFacts, cx: &ProjectCx) -> ProjectFacts;
}

pub struct FamilyMask { pub types: bool, pub calls: bool,
                        pub dataflow: bool, pub modules: bool }
```

`FileExtract` is `TypeLang` with the mask promoted to the main method.
`ProjectExtract` is `ModuleResolver` with the per-file half factored out.

### Nodes are content-addressed; edges are project-scoped

The two shapes are not two families — they are two **phases**, and every
family has both:

| phase | produces | depends on | example |
|---|---|---|---|
| `FileExtract` | **nodes**: defs, sites, spans, names | content only | `CallDef`, `CallSite`, `DfNode`, `TypeEntity`, a module ref's `specifier` |
| `ProjectExtract` | **edges**: a name resolved to a target | the file set | `call_edge`, `type_edge`, `ModuleRef.target` |

V5 already works this way and the split is visible in the code:
`extract_calls` returns `CallDef` + `CallSite` per file, and edge resolution
happens later in the engine. `ModuleRef` is the exception that proves it —
it carries `specifier` (phase 1) and `target: Resolution` (phase 2) in one
struct, because `edges()` gets a `ProjectCx` and does both at once. V6 splits
that struct along the seam that is already there.

The schema consequence is direct and large:

```sql
-- nodes key on the BLOB, not the rev: extraction is a pure function of
-- content, so identical bytes anywhere in the corpus share one node set.
CREATE TABLE node_<family> (
  node_id    INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  blob_id    INTEGER  NOT NULL,          -- <-- not rev_id, not file_id
  byte_start INTEGER  NOT NULL,
  byte_len   INTEGER  NOT NULL,
  kind       SMALLINT NOT NULL,
  name_id    INTEGER,
  weight     INTEGER  NOT NULL DEFAULT 1,
  UNIQUE (blob_id, byte_start, kind)
);

-- edges key on the rev: resolution depends on which files exist.
CREATE TABLE edge_<family> (
  rev_id INTEGER  NOT NULL,
  src_id INTEGER  NOT NULL,
  dst_id INTEGER,                        -- NULL = External or Unresolved
  kind   SMALLINT NOT NULL,
  weight INTEGER  NOT NULL DEFAULT 1,
  PRIMARY KEY (rev_id, src_id, dst_id, kind)
);
```

"Nodes of file F at rev R" is `rev_file` joined to `node_<family>` on
`blob_id` — the same indirection git uses, applied to extraction results
instead of to file contents.

At 500 repos this is the difference between re-extracting vendored and
duplicated files once per repo and extracting them once, period. It also
means an unchanged file across a rev bump costs **zero** new node rows,
which is what makes history affordable at all.

### The one real change: identity becomes a span

The fact *types* copy over almost verbatim. What changes is how a fact names
things. Two functions mint the coordinate strings that the storage autopsy
found:

| V5 | produces | measured cost | V6 |
|---|---|---|---|
| `mint_sym` (`typegraph/mod.rs:390`) — `format!("{file}::{kind}::{name}")` | qualified symbols | **26.6% of `_strings` bytes** | `(file_id, byte_start)` |
| `salt_rev` (`engine/extract/mod.rs:978`) — `format!("{rev}\u{1}{id}")` | rev-disjoint node ids | **36.4% of `_strings` bytes** | `rev_id` column |

Deleting those two functions *is* the storage fix. Every `sym: String` /
`id: String` field in `TypeFacts` / `CallFacts` / `DataflowFacts` becomes a
span, and everything else in those structs is unchanged.

### Correction to the earlier node/edge claim

"One shape, four families" is true of the *storage* core and not of the whole
fact set. `ModuleRef` carries two things a bare node/edge pair would lose:

- `Resolution` — `File(path)` / `External(name)` / `Unresolved(spec)`. Maps
  cleanly: `edge_module.dst_id` is NULL for the last two, and which one it was
  is the edge `kind`.
- `bindings` / `module_bindings` — local-name to imported-name pairs. These
  are **not** an edge property; V5 already models them as their own relation
  (`module_binding`, `module_binding_resolved`), and V6 keeps them as a
  family side table.

So the rule is: `node_<family>` + `edge_<family>` is the common core every
family instantiates, and a family may add side tables for facts that are
neither a node nor an edge. Module has one. The other three have none.

### What this buys

- extract is testable with **no database at all** — content in, `Facts` out.
- extract needs no `sprefa-store` dependency, so the 16.7K-line crate is a
  true leaf an agent can work without being able to break persistence.
- id resolution happens **once, in batch**, at the engine seam — the N+1 law
  enforced by the type system rather than by discipline.

### What crosses each boundary

| boundary | crosses | never crosses |
|---|---|---|
| lang → all | `Program`, `RelDecl`, `Rule`, `LoweredPlan`, `RelId` | anything with IO |
| extract → engine | `RawNode`, `RawEdge`, `NodeKind` | ids, rows, connections |
| store → engine | `Rows`, `Delta`, `RevId`, `FileId`, `StrId`, `Tx` | SQL text, driver types, sea-query types |
| graph → engine | `Arc<Csr>` | rows, connections |
| engine → server | `TickReport`, `Cone`, `RelId` | `Store` (the server holds `StoreHandle`) |
| server → cli | the RPC envelope only | `Engine`, `Store`, any engine type |

The id newtypes (`RevId`, `FileId`, `StrId`, `BlobId`, `NodeId`) live in
`sprefa-store` and travel **upward only**. Nothing below store defines or
consumes them. This is why extract sits below the id layer and lang sits
beside it.

### Crate arithmetic (measured @ `8d7b6092`)

The graph split changes the map: `src/graph/` is 11,934 lines of per-language
extraction and 445 lines of algorithms, so it becomes two crates.

| crate | lines | composed of | ceiling |
|---|---|---|---|
| `sprefa-lang` | ~5,100 | parse 1,626 + typecheck 1,457 + ast 749 + lex 332 + desc 333 + frontend 635, minus SQL emission | 5,500 |
| `sprefa-store` | ~9,500 | db 2,052 + storage 2,323 + meta 1,570 + declare 1,167 + staged_delta 984 + cold_stage 503 + symbols 665 + sea-query codegen ~400 | 9,500 |
| `sprefa-extract` | ~16,700 | typegraph 9,106 + modgraph 2,828 + engine/extract pure half 2,388 + scip_import 842 + scip_setup 631 + tests 943 | 16,800 |
| `sprefa-graph` | ~750 | walk 251 + scc 180 + mod 14 + CSR/snapshot API ~300 | 1,000 |
| `sprefa-rels` | ~3,670 | rels 2,575 + decls 1,093 | 3,700 |
| `sprefa-engine` | ~22,750 | engine 27,402 − store strip 4,889 − decls 1,093 + extract driver 1,327 | 23,000 |
| `sprefa-server` | ~8,500 | daemon 4,490 + lsp 1,406 + mcp 545 + rpc/channel/client + trace init − ~730 deleted | 8,500 |
| `sprefa-cli` | ~2,500 | cli 1,865 + rendering | 2,500 |

Two changes against the earlier crate map: `sprefa-engine` drops from 26,000
to 23,000 (the extract split takes more than the store strip did), and
`sprefa-graph`'s 12,500 ceiling becomes 1,000 — the 12,379 was never
algorithms. `sprefa-extract` is now the largest crate, which is honest: it is
every language's parser, and it is also the most trivially decomposable later
since each language is independent.

Dependency direction, still strictly downward:

```
lang ──┬─> store ──┬─> graph ──┐
       │           ├─> rels ───┤
       └> extract ─┴───────────┴─> engine ─> server ─> cli
```

`extract` depends on `lang` only (for `Lang`/diagnostic types) and on the
grammar crates. It is a sibling of `store`, not a child.

## The slices

### Slice 0 — the spine, alone, with an importer
**Crates:** `sprefa-store` (schema half only).
**Ships:** the filesystem/git tables (`str`, `dir`, `file`, `blob`,
`file_head`, `repo`, `worktree`, `rev`, `rev_parent`, `tree`, `tree_entry`,
`rev_root`), migrations, and a binary that walks a real checkout plus a V5
root db and populates them. No rels, no graph, no engine, no server.
**Receipt:** spine bytes for the sprefa corpus vs the V5 equivalent
(`_strings` 65.4MB + `_file` + `_files`). Predicts ~10x on the dictionary
alone, since 92% of V5's `_strings` is coordinates this schema does not mint.
**Kills the thesis if:** the normalized spine is not dramatically smaller, or
path-segment dedup does not materialize.
**Risk to V5:** zero. Nothing reads it.

### Slice 1 — one family, end to end, no engine
**Crates:** `+ sprefa-extract` (module family only), `+ sprefa-graph`.
**Ships:** `modgraph` moved behind the `RawNode`/`RawEdge` boundary,
`node_module` / `edge_module`, and a CSR snapshot built from them.
Module is chosen because it is the smallest extractor (2,828 lines) and
`module_edge` is a two-column rel — the shape is proved with the least code.
**Receipt:** (a) `cargo tree -p sprefa-extract` contains no rusqlite, tokio,
or axum; (b) `node_module`+`edge_module` bytes vs V5 `rel_module_edge`;
(c) the extractor's tests run with no database.
**Kills the thesis if:** extract cannot be made storage-free without
contortions, or the node/edge shape cannot express a family.

### Slice 2 — the dataflow family (the size proof)
**Crates:** same set, df family added.
**Ships:** `dataflow.rs` behind the same boundary; `salt_rev` deleted; the
four `df_node*` projections collapsed to one `node_df`.
**Receipt:** the number this whole arc exists for — V5 spends **163.6MB** on
`rel_df_node` + `_rev` + `_repo_rev` + `_in_fn` for one fact set. Print the
V6 figure beside it.
**Kills the thesis if:** the collapse is under ~3x, or losing the rev-salted
ids breaks a real query the panel depends on.

### Slice 3 — demand, cold by default
**Crates:** `+ sprefa-engine` (tick gains `demand: &Cone`).
**Ships:** `rel_name`, `trace_dep`, `subscription`, `rel_state`, the four
views (`v_demand`, `v_cone`, `v_wake`, `v_why_computing`), and runtime rel
DDL. The `save` keyword lands in `sprefa-lang` here (spec update, human
review first).
**Receipt:** (a) loading a 255-rel program with zero subscriptions creates
zero tables — counted from `sqlite_master`; (b) a source change wakes a
median of 3 rels, matching the V5 measurement; (c) `take_one` on a cold
corpus materializes, emits, completes, leaves a transient rel at zero bytes.
**Kills the thesis if:** the wake set is not selective on a real program, or
cone activation costs more than the eager tick it replaces.

### Slice 4 — weights
**Crates:** engine.
**Ships:** the `weight` column live on one family; retraction as `-1`; the
nested fixpoint for SCC groups.
**Receipt:** deleting a file retracts exactly its scope with no separate
retraction path in the diff; a self-supporting cycle settles instead of
diverging (the red test from the D10 todo).
**Kills the thesis if:** cyclic weights need machinery beyond the nested
fixpoint.

### Slice 5 — the server
**Crates:** `+ sprefa-server`, `+ sprefa-cli`.
**Ships:** the daemon plan (axum UDS, rmcp, tower-lsp-server), `StoreHandle`,
the subscription registry wired to the RPC surface, and the deletion of every
in-proc fallback.
**Receipt:** the daemon plan's e2e tests, plus `sprefa-cli` having no
`sprefa-engine` dependency.

### Slice 6 — cutover
V5 read paths repoint at the V6 store; the importer becomes a one-time
migration; the V5 tables are dropped. Only now does the shipping tool change
behavior.

## Why this order

Slices 0-2 are **additive**: they build and measure a parallel store while V5
keeps shipping. Both falsifiable claims (size, demand) are answered by the end
of slice 3 — before any call site in the shipping engine has moved. If the
numbers come back wrong, the sunk cost is three crates that never entered the
hot path.

The alternative order — extract the crates first, change the model later — is
the one that fails, because it spends the whole budget on mechanical moves and
discovers the model was wrong at the end.
