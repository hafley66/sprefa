One monotonic counter, four jobs — and SQLite already runs it

Single binary + SQLite, reactive-temporal, efficient dirty-check, retraction. The reason it feels symmetric is that dirty-checking, retraction, and temporal history are the SAME operation stamped with the SAME clock — and SQLite's WAL is already a monotonic, append-only, multi-version log. You are not building three engines. You are retaining what SQLite currently throws away.

one fact’s whole life · an edge (caller→callee), never DELETEd

R = 4 · born
INSERT edge(key, valid_from=4, valid_to=NULL, weight=1) insert
R = 5 · re-derived, same
digest unchanged → early cutoff: nothing written, changed_at stays 4. downstream never wakes. dirty-check
R = 7 · a second rule also derives it
weight = 2. the fact now has two supports. multiplicity
R = 9 · one support retracts
weight = 1. still live — the other rule holds it. (the exact bug the naive-set delta got wrong; the Z-set oracle passed.) retract
R = 12 · last support retracts
weight = 0 → close the interval: SET valid_to = 12. No DELETE. the row stays as history. retract = temporal close
any time · as-of read
WHERE valid_from ≤ R AND (valid_to IS NULL OR valid_to > R) — the live set at R, or the past at any old R, same query. time-travel

Retraction and temporal history are one write: closing the interval. Making it append-only (close, don’t delete) is simultaneously what makes it durable/transactional and what gives you the past for free.

why SQLite is “halfway there” · it already runs the machine, transiently

monotonic clock ✓

rowid / AUTOINCREMENT / a revs table / PRAGMA data_version. The revision counter already exists.

atomic revision commit ✓

a transaction IS a revision boundary. Multi-statement writes land at one R or none. That is your transactional guarantee, built in.

multi-version reads ✓

WAL gives snapshot isolation: readers see a consistent revision while a writer appends. That is MVCC — the temporal mechanism at the page layer.

reactive change signal ✓

sqlite3_update_hook / preupdate_hook fire on every row change (rusqlite exposes it). The “something changed” edge is already emitted.

the one thing to add →

SQLite versions pages for concurrency and then checkpoints the history away. You want the same versioning at the row/fact level, retained: on retract, SET valid_to = R instead of DELETE. That single change turns SQLite’s transient MVCC into a retained bitemporal store. Everything else above you already have.

the deepest symmetry · you are already half-bitemporal

valid-time — “which world”
the git rev being analyzed. already in the coordinate model (span.file.rev.repo). Which commit the fact is true of.
transaction-time — “when we knew”
the salsa revision: when the engine recorded/superseded the fact. The counter this whole page is about.

Two independent time axes = bitemporal. One (rev) is already carried by every coordinate. Adding transaction-time is the counter you already need for dirty-checking. --move’s “apply-against-analyzed-rev” is exactly a bitemporal constraint (act on valid-time = the rev you analyzed, at transaction-time = now).
