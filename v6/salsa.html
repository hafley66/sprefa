Salsa — the red-green reactor, and why it never touches the RAM budget

Salsa is how rust-analyzer stays incremental. It is the algorithm for Layer 2 (the rule DAG). The trick that keeps it off the memory budget is one design choice: its memo stores a digest + two revision numbers, never the relation's rows. The rows stay on disk in the cascade.

2 · the red-green walk  — asking for a derived rel Q at revision R

✓
verified_at(Q) == R ? → already known current this revision. return memo. zero work.
✓
else: did any dep change since verified_at(Q)? walk maybe_changed_after(dep, verified_at) for each. If NONE did → bump verified_at = R, return old value WITHOUT re-executing. (the backdating win — most of the DAG takes this path)
↻
some dep changed → RE-EXECUTE Q. run the derive fn, get a new value.
✓
new digest == old digest ? → BACKDATE: leave changed_at alone. downstream rels see "Q unchanged" and never re-run. (early cutoff / firewall)
△
new digest != old digest → set changed_at = R. only NOW do the rels that read Q become suspect.

Two revision numbers per query is the whole engine: verified_at says "I checked this at R," changed_at says "my output last actually moved at R." The gap between them is where all the skipped work lives.

4 · two levers that skip whole subtrees

Durability — Low / Medium / High
Tag inputs by how often they move (your code = Low, deps = High). Salsa keeps the last revision each durability level changed. If nothing High-durability moved since verified_at, every query that only reads High inputs is green without walking its deps at all.
LRU eviction — the memo is a CACHE, not a ledger
Memo values can be dropped under an LRU cap. Evicted query? Re-execute on next demand. Memory is bounded by the cache size you choose, not by how big the graph is. This is the second reason RAM stays flat.

The 10M facts never enter the reactor — it holds "rel R was computed at revision 7 and its content hashes to ab3f…," and asks the cascade to do the row work on disk. Independent axes: facts scale with the corpus, reactor scales with the rule count.

6 · how i lab it out (same discipline as frp-lab)

  • Model: a reactor-lab crate. Rels are salsa-style tracked nodes whose memo value is a blake3 digest of the rel's content, plus deps[], changed_at, verified_at. The rows themselves sit in a stub "disk" map keyed by rel — standing in for the cascade — so the reactor genuinely never holds them.
  • Differential oracle (the thing you made me build): under a random source-edit stream, assert the reactor's computed dirty-set == the set of rels whose digest actually changed by from-scratch recompute. If it ever re-runs a rel it didn't need, or skips one it did, the oracle catches it — seed+step localizes it.
  • Early-cutoff test: edit a source so a derived rel recomputes to the SAME digest; assert zero downstream rels re-run (backdating works, the firewall holds).
  • The RAM proof — two independent axes: grow facts (rows per rel) and rels (DAG size) separately. Measure reactor RSS. Show it is flat in fact-count and linear only in rel-count — the exact opposite of the sqlite side. That is the receipt that it does not eat the budget.
  • Build-vs-buy: the salsa crate IS the candidate for this algorithm (rust-analyzer runs it). Caveat to measure: its default memo holds VALUES in RAM — we need it to hold digests instead. Lab decides: drive salsa with digest-values, or hand-roll the ~200-line red-green core. Not asserting bespoke first.

salsa = Layer 2 control plane (digests + revisions, RAM, tiny)  ·  cascade = Layer 1 facts (rows + weights, disk, big)  ·  they meet at "recompute rel R"
